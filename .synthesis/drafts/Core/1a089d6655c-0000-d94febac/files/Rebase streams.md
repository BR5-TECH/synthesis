## Intent

Project source branches can change outside Synthesis IDE after a stream is created. Add an **Update** action for one selected stream so the author can bring that stream's branch up to its recorded base branch before starting another run. The existing **Merge** action is unchanged: it merges the stream branch into its base branch. **Update** performs the opposite direction and changes only the selected stream.


## User journey

- The author opens the streams control in the IDE top chrome.
- Each stream row shows whether its branch is behind its recorded base branch. The recorded base branch is the source branch for Update, regardless of the branch in the active project worktree.
- For one selected stream, the row shows **Update** between **Merge** and **Delete**.
- **Update** is enabled only when the selected stream is behind its base branch and has no queued or active jobs. It is disabled when the branches are up to date or the stream has queued or active jobs.
- Activating **Update** opens a modal overlay. The modal names the stream and base branch, captures and displays the current tip revision of that base branch, lists the commits from the base branch that are missing from the stream, and offers **Merge source into stream**, **Rebase stream onto source**, and **Cancel**. Confirming either strategy submits the captured base revision. After the backend validates that the recorded base branch still points to the captured revision, the operation uses that immutable revision as its source for all comparison, merge or rebase, and semantic reconciliation steps; it must not read the branch tip again. External movement of the base branch after this validation therefore cannot change the Update result. If the recorded base branch no longer points to that revision, Update refuses with a typed stale-preview error, changes no branch or file, and requires the author to reopen the modal.
- The existing **Merge** action remains the stream-to-base operation. It is disabled when the stream has nothing to merge into the base branch.
- Before either Update strategy starts, the selected stream working copy and the worktree for its recorded base branch must be clean. If either is not clean, Update does not change any branch or file; the modal identifies the dirty worktree or worktrees and shows the complete changed-path list for each. If the recorded base branch has no checked-out worktree, Update refuses with the existing `base_not_checked_out` error.
- After the author chooses a strategy, the operation updates only the selected stream branch and working copy. The base branch does not change. A merge creates the required merge commit; a rebase rewrites the stream commits onto the updated base.
- If Git cannot resolve conflicts, both Update strategies use the existing semantic reconciliation flow. For **Rebase stream onto source**, the backend completes the rebase comparison, collects all unresolved paths across the complete rebase, and dispatches one semantic reconciliation pass for that combined set; it must not dispatch a separate reconciliation pass for each rebased commit. The UI shows progress and the final result using the durable stream operation state.


## Requirements

- Update operates on one selected stream at a time.
- Update uses the stream's recorded `base_branch` as its source branch, regardless of the active project worktree branch.
- Update is enabled only when the selected stream branch is behind `base_branch` and the stream has no queued or active jobs.
- Update is disabled when the selected stream branch is up to date or the stream has queued or active jobs.
- The Update action is placed between **Merge** and **Delete** in the stream row.
- The existing **Merge** action remains stream → base. It is disabled when there is nothing to merge into the base branch.
- Update requires both the selected stream working copy and the worktree for its recorded `base_branch` to be clean. If either is dirty, Update changes nothing and reports the complete changed-path list for each dirty worktree using the existing `stream_dirty` and `base_dirty` errors. If the recorded base branch has no checked-out worktree, Update refuses with the existing `base_not_checked_out` error.
- Update offers two strategies:
  - **Merge source into stream**: merge the recorded base branch into the selected stream branch and create the resulting merge commit.
  - **Rebase stream onto source**: rebase the selected stream commits onto the recorded base branch and rewrite those stream commits.
- Both strategies change only the selected stream branch and working copy. The base branch remains unchanged.
- Both strategies use the existing semantic reconciliation flow for conflicts that Git cannot resolve. Rebase collects unresolved paths from all conflicting replay steps and sends them in one reconciliation pass for the complete rebase; it does not reconcile each rebased commit separately.
- The update operation is durable and observable after the modal closes or the project reloads. The stream row shows running, success, conflict, escalation, cancellation, and failure outcomes using the existing stream-operation patterns.
- Add the required typed backend operation, UI contract, and durable state for Update. Update the existing work-stream, rebase, and work-stream-selector specifications because the current rebase contract only defines stream → base merge and its current dirty checks, base-worktree preconditions, and publication behavior target the base branch. Preserve the existing `stream_dirty`, `base_dirty`, and `base_not_checked_out` refusal semantics for Update.
- Define Update as a separate durable operation from the existing stream-to-base Merge record. Its contract must include: the selected strategy (`merge_source` or `rebase_source`), the recorded base branch, the pinned base revision submitted with confirmation, the commits missing from the stream, progress, cancellation, escalation, conflict, success, and failure state; a read operation that survives modal close and relaunch; and an event that refreshes the stream row. Before any dirty-worktree check or write, the backend must verify that the recorded base branch still points to the pinned revision. If it does not, Update refuses with a typed stale-preview error, changes nothing, and the author must reopen Update to obtain a new preview. A stream must not run Update and Merge at the same time, and each operation must refuse while the other is running. The stream summary must expose the behind-base state needed to enable Update and the commit list needed by the modal. On cancellation, conflict, escalation, stale-preview refusal, or failure, Update must leave both branches and both working copies unchanged. For Update states that are conflicted or escalated, the UI must expose the corresponding existing review, answer, retry, clear, and dismiss actions through the Update record, without invoking the stream-to-base Merge actions.
