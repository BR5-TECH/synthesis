## Intent

Synthesis IDE already allows to run AI agents locally using a graduation process. However, alternatively we might want to publish the draft as a GitHub issue. Later this issue can be picked up by remote AI agent that runs in cloud.

## User journey

- User works on draft as long as needed until it’s ready.
- User clicks flyover button, and he sees “Discuss”, “Graduate, “Publish to GitHub”, “Archive” buttons.
- User clicks “Publish to GitHub” button.
- GitHub issue is created, with draft content posted as body.
- Show the current publication and append-only history in both the draft tab and the draft Information modal. Render the current record first, then the history in newest-first order; each record shows the repository, issue number, issue URL, publication time, and marker. The history is read-only. Activating an issue URL opens it with the system's external browser and does not open an in-app page.
- The existing Drafts panel “Graduated” filter includes drafts with either `graduated` or `published` status. Each row displays its stored status clearly (`Graduated` or `Published`); `published` rows remain editable and support deliberate re-publication, while `graduated` rows remain read-only for prompt edits, renaming, and lifecycle changes. **Publish to GitHub** remains available for an eligible `graduated` row because publication changes metadata, not the prompt or local graduation state. A draft with local `graduated` status stays in that status when it is also published to GitHub.
- Only drafts with `active`, `published`, or `graduated` status may be published. For an `archived` draft, disable **Publish to GitHub** and explain that the draft must be restored before publication. Archiving a `published` draft changes its stored status to `archived` without changing its current publication or append-only history; restoring it changes the status to `active` and preserves that metadata. A publication attempt is disabled while another publication attempt for the same draft is in progress.

## Requirements

- We only implement IDE side of GitHub integration: agent that will pull issues from GitHub and will work on them is out of scope.
- Remote selection must follow this flow: first enumerate all configured Git remotes without mutation. If a persisted choice exists, use it only when that remote is still present, its URL resolves to a GitHub repository, and the project-resolved token passes the repository Issues API checks; otherwise ignore the persisted choice for this attempt. If exactly one configured Git remote exists and it passes those checks, use it automatically. If two or more configured Git remotes exist, show a picker listing every remote; disable each non-GitHub remote and each GitHub remote that fails validation, and show the exact reason for each disabled entry. If zero configured Git remotes exist, or no remote passes validation, keep publication disabled and explain whether no remote was found, no GitHub remote was found, the token cannot access the repository's Issues API, or the token cannot create issues. Do not make a GitHub mutation while enumerating or validating remotes.
- When multiple remotes are shown, the picker must offer an explicit **Use this remote for future publications** option. Selecting it persists the chosen remote in project-local settings; leaving it clear applies the choice only to the current attempt. A persisted choice is reused only when both the remote name and its canonicalized URL still match the current enumeration, while remote resolution still validates its URL and token access before publication. A remote rename or URL change invalidates the persisted choice for that attempt. The picker must state whether the current choice is automatic, persisted, or selected for this attempt only.
- Use a programmatic Rust GitHub client (for example, `octocrab`, or direct HTTPS through GitHub's official REST API); do not require or invoke the `gh` CLI. Create the issue through the GitHub Issues API and use the project-resolved token.- The issue title is exactly the draft's current name. The issue body contains the complete current draft content followed by one machine-readable marker on its own line, using a fixed format such as `<!-- synthesis-publication-marker: <opaque-marker> -->`; the marker is generated once per attempt, is stable and unique, is searchable by exact match in issue bodies, and is not written into the draft prompt.

- "Publish to GitHub" should be a grayed out if GitHub token doesn’t allow issues access.- "Publish to GitHub" should be disabled if the project token lacks permission to create issues. For v1, publication is also disabled when the draft contains local asset references; the disabled state must explain that local media attachments are not supported and list the affected paths.

- Media attachment and local-asset upload is out of scope for v1. Existing remote URLs remain unchanged. Local asset references must be detected before publication and reported as unsupported; no issue or remote asset is created when they are present.
- When the draft is not locally graduated, change it to `published` only after issue creation succeeds. If the draft already has local `graduated` status, keep it `graduated` and append the GitHub publication record without changing its status. If any step fails, keep the previous draft status, report the exact failure, and leave the attempt marker available for retry recovery; a retry must search for the marker before creating an issue, so an uncertain create result cannot silently create a duplicate.- Publication metadata is append-only. Each successful GitHub publication adds one record containing provider (`github`), repository owner/name, issue number, issue URL, publication time, and the unique publication marker. Re-publishing creates a new issue and appends a new record; it never updates, deletes, or replaces earlier records. The latest successful record is the current publication, while all earlier issue records remain available.
- A publication attempt reuses its persisted publication marker when retried and searches the target repository for that marker before creating an issue. The retry always uses the draft's latest name as the issue title and latest prompt content as the issue body, while retaining the attempt's marker. If no issue with the marker exists, it creates the issue. If an issue with the marker exists and its title or body differs from the latest draft, show a recovery choice: **Update existing issue** or **Publish as a new issue**. **Update existing issue** edits that issue to the latest title and body, then records one successful publication-history entry for the attempt; **Publish as a new issue** starts a deliberate re-publication with a new marker and a new issue. If the existing issue already matches the latest title and body, reuse it without another GitHub issue creation. Cancelling the recovery choice leaves the attempt recoverable and adds no history entry. A deliberate re-publication always starts a new attempt with a new marker and creates a new issue. Before the first GitHub request, persist a publication-attempt record containing the draft id, unique marker, resolved remote and repository, and attempt state. A retry of the same attempt reuses that record and marker; a deliberate re-publication creates a new record and marker. This attempt record is separate from append-only successful publication history, and the issue body carries the marker without modifying the draft prompt.
- Publication history and publication-attempt records are draft-owned persisted data, separate from the scalar draft status and prompt content. Store both in one draft-owned publication store inside the draft folder, with distinct sections or record types for append-only successful publication history and publication attempts; do not use separate publication-history and publication-attempt stores. The updated draft-storage contract must define the store's exact location, schema, state transitions, atomic-write and reload rules, and how completed, cancelled, or abandoned attempts are retained or cleared. The attempt record must be written atomically to disk before the first GitHub request; its eventual Git commit is best-effort and must not be required for the request to proceed. On application restart, every non-terminal attempt remains recoverable and must not leave **Publish to GitHub** permanently disabled: the UI must offer retry or the defined recovery choice, and must prevent a second active attempt for the same draft.
- Publication metadata must distinguish GitHub publication from local graduation. A published draft remains editable, and its previous publication records remain valid references even after later publications.
- The updated draft-storage contract must also state that when a graduation run that established `graduated` is later discarded or terminally fails, the existing graduation release rules apply; publication history does not by itself restore `published` or prevent that release.- Graduation must update the existing specifications for draft storage, the Drafts panel, the New Artifact tab, the action control, the Draft Information modal, and project-local settings. The draft-storage update must explicitly extend every existing “exact layout” or “only these paths” rule so the new draft-owned publication store is part of the defined layout, ownership, indexing, deletion, Git commit, conflict, and migration behavior. These updates must define the `published` status, the combined Graduated filter, published-row editability, graduated-row read-only behaviour, archive/restore transitions, the **Publish to GitHub** action and its disabled reasons, the publication metadata shape, and persisted GitHub remote selection. Add a dedicated core contract for GitHub publication and its typed errors, retry marker, and append-only history.
