## Intent

Merging a work stream into its base branch is an author-started operation. When Git cannot resolve conflicts, the author needs a reliable reconciliation process that checks the result for semantic drift before it reaches the base branch. Treat that reconciliation as a special Graduation Run: show it in Runs, use a dedicated merge prompt, and use the existing work→review flow and run controls.

## User story

- As a stream author, I start **Merge** from the Work Stream Selector. If Git merges cleanly, I see the result there and no Graduation Run is created. If Git finds conflicts, I can follow and manage the reconciliation as **Merge <stream>** in Graduation Runs.
- As the author, I can see the merge's progress, review findings, and final result in the run view, and continue or discard it using the run's available controls.

## Requirements

- **Scope and trigger**
  - Keep merge author-started and in the existing stream→base direction. Keep the current publication choice: leave the result uncommitted in the base worktree or commit it with the message the author supplied.
  - Run Git's ordinary merge first under the existing repository merge/update guard. A clean merge completes through the Work Stream Selector and creates no Graduation Run or durable merge history. If Git finds conflicts, leave both branches and worktrees unchanged, capture the merge snapshot, and create a merge Graduation Run. Do not put the pre-conflict Git operation in the Graduation Run queue.
  - Show transient running and clean-result feedback in the Work Stream Selector. Before a conflict run exists, do not add a durable merge record. If the application exits before conflict handoff, the author starts Merge again.
- **Merge run and reconciliation**
  - Use the existing Graduation Run queue for the stream and the existing project-wide concurrency limit once semantic reconciliation is needed. The run waits in that queue if required; it does not hold a queue slot while Git performs the initial merge check.
  - Make the merge run a first-class Graduation Run and its sole durable record: replace `StreamMergeRecord` rather than synchronizing a second merge record. Link stream surfaces to the run for its current status. Name it **Merge <stream>**, never with a draft name; retain the stream and base-branch identity, the pinned branch tips and merge snapshot, publication choice, changed paths, and unresolved paths in its run data.
  - Run the merge through repeated work→review passes using the normal run controls and checkpoint behavior. Compile `resources/prompts/graduation/merge-work.md` and `merge-review.md`; use neither the draft prompts nor the existing single `merge.md` prompt. Each pass is one merge-work turn followed by a fresh merge-review turn. The work turn runs in an isolated, run-owned worktree seeded from the captured merge snapshot; it may make additional repository changes needed to reconcile the merge, but must not write to either live branch or worktree before approval. A revise review sends its findings to the next work turn. The review is read-only except for build and test output in its disposable checkout. It checks the final result against both pinned branch versions and repository specifications for every path changed by the merge, including Git-clean paths, and every additional path changed during reconciliation. It also runs the project-defined build and test commands, including `task specs` and `task tests`, without inventing commands. The review returns ready only when its merge-intent and specification checks pass and the required commands pass; otherwise it returns actionable findings for the next pass.

  - Give merge runs their own pass budget: default **2**. When the budget is spent, the run waits for the author; **Continue** adds 2 passes and resumes the saved snapshot. Release the queue and project slot while the author decides. Continue requeues the run at the front. Refuse to resume or apply the snapshot if either branch tip has changed; make no branch or worktree writes on refusal.
  - Apply the merge to the base branch only after a ready review. Honor the recorded publication choice. Until then, keep both branches and worktrees unchanged. Discard, cancellation, failure, or a non-ready review leaves them unchanged.
- **Frontend behavior**
  - Add conflict merge runs to the existing Runs history and run detail surface. Reuse its queue position, progress visualization, pass history, findings, logs, notifications, keyboard behavior, and accessible status patterns. Show **Merge <stream>**, the stream and base branch, merge-specific progress, and the result; do not show draft-only actions or imply the run is a draft graduation.
  - Keep Merge initiation and pre-conflict progress/result in the Work Stream Selector. After conflict handoff, show a link/status for the run there; manage, continue, and discard the reconciliation in Graduation Runs. Render status from backend state, not only from the initiating window.
- **Specifications and verification**

Remove or replace the conflicting `StreamMergeRecord`, single-semantic-turn, draft-only run, and merge-log attribution contracts; preserve ordinary graduation and stream Update behavior.
  - Add backend and frontend coverage for clean merges with no run, conflict handoff, queue and project-limit behavior, work/review revisions and budget exhaustion, author Continue and discard, branch-tip changes, publication choices, restart before and after handoff, Runs presentation, and stream-row updates. Run `task specs` and `task tests`; report any unavailable prerequisite or pre-existing failure, and do not report verification as passing unless both commands pass.
