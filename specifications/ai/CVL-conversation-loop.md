# Conversation loop

**Spec code:** `CVL`

## Intent
The loop that holds a conversation with a model. Handed an agent's own instructions, the material a conversation calls for already assembled into named sections, and the endpoint resolved for that agent, this module puts the question to the model under a **prompt that ships with the application**, lends the agent a fixed set of tools, and keeps calling until there is an answer. A section is a sequence of content parts rather than a block of prose, so the pictures a draft's prompt embeds and the pictures a conversation has accumulated travel to the model in the order the material puts them, as the framework's own image content; whether a turn carries any is settled before it reaches here and is never revisited within it. The prompt is what makes an answer dependable: it is a text compiled into the binary and chosen by the target of the conversation rather than a phrasing assembled per call, it states the form a reply takes and how the material is to be read, and the agent's own instructions are composed into it at a single placeholder — so what differs between two turns of one kind is the persona and the material, never the shape of the request. A turn is a **loop** rather than a single call, which is the whole reason this module exists: the agent reaches for tools when the question turns on something the project has already settled — finding the specifications that bear on a topic, reading what those specifications actually say, surveying and loading the project's own skills — and each result comes back into the exchange and is put to the model again, so an answer rests on the decisions the project has accumulated rather than on the passage in front of the agent alone. Where the provider carrying the turn serves them, the agent reaches past the project as well — searching the web, and retrieving a page or a PDF it has the address of — through **that provider's own tools**, which the provider defines and executes and this module only offers, so a question about a library, a standard, or a product as it stands today is answered from today rather than from what the model last remembers. Four of the tools end the turn where they stand instead of feeding it: one asks the author a single clarifying question, one puts several questions with proposed answers to a discussion at once, one offers a rewrite of a draft's prompt, and one offers a rewrite of a prompt the project already holds, each for the author to answer, accept, or decline, so a turn is never obliged to answer — an agent facing an ambiguous request asks which reading was meant rather than guessing, and one that can see how a passage would be better shows the author rather than describing it. Reaching the model is the one part of a turn that fails for reasons having nothing to do with what was asked — a host that does not resolve, a connection that drops mid-answer, a reply that carries nothing at all — so a call that fails that way is simply **made again**, a small fixed number of times, after a short randomized wait, against the exchange exactly as it stood before it, and the author waits a moment longer rather than reading an error they are expected to interpret. Everything the loop does is bounded twice over — the rounds it may take and the attempts each round may spend — and the project sets the turn's timeout, the deadline on one provider call, and the attempts a round may spend, while the waits between them stay constants of this module, so two turns of one project that failed the same way waited the same way whoever dispatched them and wherever. Out of scope: deciding what material a conversation carries and reading it, which is `../core/AGC-agent-conversations.md`'s per-kind builders; registering, cancelling, reporting, or delivering a turn, all of which are that module's, so nothing here is a Tauri command, emits a Tauri event, or is reachable from the frontend; defining a tool, each of which is `../tools/TLC-tool-conventions.md`'s group rather than this module's, and this module names the set and holds no registry; repeating a **tool** call, since a tool's refusal is already the model's to answer inside the loop rather than anything to re-issue behind its back; retrying anything in the background, on a schedule, or across a relaunch, a failure surviving no better than the turn that produced it; authoring the prompt, which is application data compiled into the build rather than anything an author supplies or edits; choosing an endpoint, a key, or a model, all of which are resolved before a call reaches here (per `../core/AAP-ai-api-integrations.md` AAP-FR-34); carrying out a web search or a page retrieval, which the provider does for itself inside the call this module was already making and which this module neither implements nor stands in for (`../tools/WST-web-search-tool.md`, `../tools/WFT-web-fetch-tool.md`); and driving an agent that writes files, which is `GRL-graduation-loop.md`'s separate loop with its own prompt, its own tools, and its own state — nothing here is specialized, parameterised, or extended to serve it, and no target of this module's reaches it.

## Contract surface
The module owns the four embedded prompts, the per-target prompt selection, the tool set each target is attached, the exchange a turn accumulates, the model call, and the retry policy behind it. It registers no Tauri command, emits no Tauri event, and is unreachable from `src/**` by any `invoke()`; its consumer is `../core/AGC-agent-conversations.md`, which assembles what it is given and delivers what it produces. It also **reports to that consumer what it measured of the calls it made** — the tool calls it began and finished, the turn's execution boundaries and whether it reached the model, and each reliable provider-reported token usage record with its own identity, round, and attempt — and persists, folds, and attributes none of it itself (CVL-FR-WQZD, CVL-FR-JBTX).

### The prompt
The instruction a turn works under. Four prompt files are compiled into the binary, each holding the whole of one instruction and each carrying two placeholders — `{{ agent-title }}`, into which the addressed agent's title is substituted, and `{{ agent-instructions }}`, into which its own instructions are (CVL-FR-04). Which one a turn carries is decided by its target — the owner kind of the discussion and whether the discussion has a fragment target (CVL-FR-03):

```
resources/prompts/comment.md           → artifact or draft target, fragment present
resources/prompts/discuss-artifact.md  → artifact target, no fragment
resources/prompts/discuss-draft.md     → draft target, no fragment
resources/prompts/discuss-note.md      → note target (never a fragment)

compile_prompt(target, instructions, title) -> string
```

### The tools
The capabilities a turn lends its agent, so that an answer can rest on what the project has already decided, on what it is planning, and on what the author has written down for themselves, on the reference documents the user selected rather than on the material under discussion alone, so that an agent that cannot answer well can say so, and so that one working on a prompt — published or not — can offer a rewrite of it. Each tool is defined by its own spec in `../tools/` and conforms to `../tools/TLC-tool-conventions.md`. This module names the set, holds no registry, and defines no tool of its own; which **portable** tools a turn is attached is decided by its **target** — the owner kind and whether a fragment is present — and by nothing else (CVL-FR-08):

```
                          artifact     draft     note
search_specifications         ✓           ✓            ✓     // ../tools/SPS-specification-search-tool.md
read_file                     ✓           ✓            ✓     // ../tools/RFT-read-file-tool.md
search_drafts                 ✓           ✓            ✓     // ../tools/DST-draft-search-tool.md
read_draft                    ✓           ✓            ✓     // ../tools/RDT-read-draft-tool.md
search_notes                  ✓           ✓            ✓     // ../tools/NST-note-search-tool.md
search_documents              ✓           ✓            ✓     // ../tools/SDT-search-documents-tool.md
get_document                  ✓           ✓            ✓     // ../tools/GDT-get-document-tool.md
search_skills                 ✓           ✓            ✓     // ../tools/SST-skill-search-tool.md
list_skills                   ✓           ✓            ✓     // ../tools/SLT-skill-list-tool.md
load_skill                    ✓           ✓            ✓     // ../tools/LSK-load-skill-tool.md
ask_user_comment              ✓           ✓            ✓     // ../tools/AUC-ask-user-comment-tool.md
ask_discussion_questions      d           d            ✓     // ../tools/ADQ-ask-discussion-questions-tool.md
propose_draft_changes         ·           ✓            ·     // ../tools/PDC-propose-draft-changes-tool.md
propose_prompt_changes        ✓           ·            ·     // ../tools/PPC-propose-prompt-changes-tool.md

d — a discussion with no fragment target alone; a discussion with a fragment target is attached none
```

The eleven gathering tools are attached to every turn whatever its origin; `ask_discussion_questions` is attached to a discussion with no fragment target alone, and a proposal tool is attached wherever the origin has a prompt to offer a rewrite against (CVL-FR-08). All but one of the eleven are read-only, so nothing a turn gathers from the project changes anything (CVL-FR-09). The four that write each end the turn on the call that succeeded (CVL-FR-15): `ask_user_comment`, the eleventh of the eleven, gathers its answer from the author rather than from the project and appends one comment to the conversation the turn is already in; `ask_discussion_questions`, on a discussion with no fragment target, records one pending question set against that discussion and appends **no** comment; `propose_draft_changes`, on a draft target, records a candidate beside the draft and appends one comment referring to it; and `propose_prompt_changes`, on an artifact target, records a candidate in the project's own proposal store and appends one comment referring to it. None of them writes a file of the project or of the draft, so a turn still leaves the material it was given byte-for-byte as it found it however it ended.

Two further tools are the **provider's** rather than the application's, and which turn carries them is decided by the provider serving the call and by nothing else (CVL-FR-30). Each is one definition entry standing in the same tool array beside the portable definitions, conforming to `../tools/TLC-tool-conventions.md`'s provider-native class (TLC-FR-21):

```
                          openrouter   anthropic   openai   custom
openrouter:web_search         ✓            ·         ·        ·     // ../tools/WST-web-search-tool.md
openrouter:web_fetch          ✓            ·         ·        ·     // ../tools/WFT-web-fetch-tool.md
```

OpenRouter executes both, gives both results to the model, and returns the reply the model composed with them already read — all inside the one model call this module made. So this module carries neither the call nor the result anywhere, makes no web request of its own, and reports and records what the provider ran (CVL-FR-31, CVL-FR-32, CVL-FR-34).

### The assembled request
What the loop is handed and its first call carries. The `input` is produced by the origin's builder (per `../core/AGC-agent-conversations.md` AGC-FR-05) and this module reads it rather than composing it. It exists only for the duration of the turn:

```
ContentPart =
  | { kind: "text",  text }
  | { kind: "image", media_type, data, context }
                             // data: the image's own bytes; context: the Markdown
                             //   reference and alt text, or the filename and the
                             //   comment it belongs to (per `../core/AGC-agent-conversations.md`
                             //   AGC-FR-35)

InputSection {
  tag,                       // "artifact" | "note_context" | "discussion_history" | "current_comment"
  attributes,                // the tag's own attributes, e.g. an artifact's path
  body: ContentPart[],       // the material itself, in the order the material has it;
                             //   a section carrying no image is one text part
  truncated: bool            // true when the section holds less than the whole of its material
}

AgentRequest {
  instructions,              // the compiled prompt, carrying the agent's instructions within it
  input: InputSection[],     // ordered: the material section, discussion history, current comment
  tools                      // the portable definitions the target decides (CVL-FR-08),
                             // and the provider-native entries the provider decides (CVL-FR-30)
}
```

### The exchange
What a turn accumulates while it runs. It opens with the input as the single first message and grows by one entry per model reply and one per tool result, in the order they occurred (CVL-FR-12). It exists in memory for the duration of the turn and is never persisted, echoed, or emitted (CVL-FR-26):

```
AgentExchange = [ Message ]     // the input, then each model reply and each tool result in turn
```

### The failure class
Every failed attempt is reduced to a normalized class before it is logged or reported (CVL-FR-21), and the class is what the retry decision is taken on (CVL-FR-18) and what the turn's reported `AgentTurnFailure` is derived from (per `../core/AGC-agent-conversations.md` AGC-FR-15). The classes distinguish a name that would not resolve, a connection that would not open, a connection reset in flight, a response the provider actually returned carrying its status alone, the provider-call deadline of CVL-FR-17, a request the framework refused to build, and a reply that carried nothing.

### Internal (no UI consumer; not Tauri commands and unreachable from the frontend)
- `compile_prompt(target, instructions, title)` — selects the target's embedded template (CVL-FR-03), substitutes the agent's title and its instructions into it, and returns the prompt the request carries (CVL-FR-04). It reads no file and reaches no network.
- `complete(exchange, endpoint)` — the single seam through which a model is called (CVL-FR-11); the only place in this module that reaches the network. It is invoked once per round of the loop, carrying the exchange as it stands at that moment, and each **invocation** is made as up to three **physical attempts** under its own deadline and its own retry budget (CVL-FR-17, CVL-FR-19). A logical invocation is what the loop counts (CVL-FR-13); a physical attempt is what reaches the provider. It is also where what a call presents is marked for caching (CVL-FR-23), where the input is split at its stable head (CVL-FR-39), and where a call asks for the upstream the last one was routed to (CVL-FR-40) — all three being part of carrying a call rather than of assembling one.
- `drive(request, endpoint)` — the bounded loop of CVL-FR-12: it calls `complete`, reports and records whatever the provider ran for itself (CVL-FR-31, CVL-FR-34), dispatches whichever tool the model asked for, reports that call begun and finished (CVL-FR-33), appends the result to the exchange, and calls again, until the model answers with prose and no tool call, or asks the author a question (CVL-FR-15), or the bound of CVL-FR-13 is reached, or a `complete` invocation exhausts its attempts (CVL-FR-19).
- `report_usage(usage_record)` — the seam through which one reliable provider-reported usage record leaves this module (CVL-FR-WQZD). It is called once per distinct record the provider reports, carries no part of the exchange, and is consumed by `../core/AGC-agent-conversations.md` (AGC-FR-BVNT), which decides whether the turn is a draft's and records it where it belongs.
- `backoff_delay(attempt)` — the wait before a retry: the attempt's base delay varied by the jitter source of CVL-FR-19. The source is a seam like `complete`, substituted wholesale under test so a schedule is asserted exactly rather than tolerated.
- `begin_agent_session()` — begins the agent session a turn runs inside and yields the filesystem instance its tools read through (CVL-FR-24, per `../core/FSA-filesystem-access.md` FSA-FR-29). The session ends when the turn terminates, by whichever route.

## Functional requirements
1. **CVL-FR-01** The request carries three things and no others: the **compiled prompt** as the instructions the model works under, the **input** the origin's builder produced as the single first message it answers, and the **definitions of the tools** the turn is offered — the portable ones the target decides (CVL-FR-08) together with the provider-native entries the provider decides (CVL-FR-30) — each of them that tool's own fixed text rather than anything composed here (per `../tools/TLC-tool-conventions.md` TLC-FR-05, TLC-FR-22). Nothing else of the application's own is added — no persona this module invents beyond the one the prompt composes, no opinion about the material, and no instruction about the subject the author did not write — and nothing of the request is assembled by concatenating a phrasing this module chooses per call.
2. **CVL-FR-02** The prompts are `resources/prompts/comment.md`, `resources/prompts/discuss-artifact.md`, `resources/prompts/discuss-draft.md`, and `resources/prompts/discuss-note.md`, all compiled into the binary at build time. No turn reads any of them from disk, so a turn is unaffected by what the installed application's directories hold, an author cannot edit or replace one, and a build either carries all four prompts or does not build at all. They are application data on the same footing as a provider descriptor (per `../core/AAP-ai-api-integrations.md` AAP-FR-01): nothing in the contract surface accepts, returns, or overrides any of them.
3. **CVL-FR-03** A turn's prompt is selected by its target and by nothing else: the owner kind of its discussion, and whether the discussion has a fragment target. `comment.md` serves an artifact or draft target **with** a fragment, which is a discussion about a passage and is answered under one instruction whichever file the passage is in; both may offer the author a rewrite of the prompt the passage sits in (CVL-FR-08), so that instruction says so once for the two of them without naming which store the rewrite would be recorded in, that being the tool's affair rather than the prompt's. `discuss-artifact.md` serves an artifact target with no fragment, where the material is a whole file the project already holds and what is asked of the agent is what to do with the document as it stands — and where, when that file is a prompt, the agent may offer the author a rewrite of it (CVL-FR-08), a capability an instruction has to tell the agent it has. `discuss-draft.md` serves a draft target with no fragment, where the material is unpublished working material on its way to being graduated and handed to an agent that will act on it — so what is asked is what that material will *cause* — and which can likewise offer the author a rewrite of it, of the draft's own prompt. `discuss-note.md` serves a note target, where the material is a few lines the author wrote to themselves about a gap, an issue, or a follow-up — so what is asked is what to make of that observation, and the instruction names `note_context` as what is under discussion and tells the agent that the scope the note is filed against is where it sits rather than what it is about (`../core/AGC-agent-conversations.md` AGC-FR-07). The selection is the extension point beside the builder of AGC-FR-05: an owner kind added later brings a target kind, a builder, and whichever of the prompts already compiled in answers its shape — or a new one of its own — and changes no command signature and no payload shape.
4. **CVL-FR-04** `compile_prompt(target, instructions, title)` produces the prompt a turn carries by replacing the selected template's two placeholders and leaving every other byte of it as it is. `{{ agent-instructions }}` takes the agent's instructions as `../core/AGR-agent-registry.md` stores them (AGR-FR-08) and `{{ agent-title }}` takes the agent's title as that module stores it, already trimmed (AGR-FR-23). Both substitutions are literal and performed in one pass over the template: neither value is parsed, escaped, or re-scanned, and neither is scanned for the other's placeholder, so a placeholder occurring inside an agent's own instructions or inside its title is text like any other and expands to nothing further. Instructions that are empty or hold nothing but whitespace are no instructions for the purpose of the call and their placeholder is replaced with nothing, which is an ordinary state rather than an unconfigured one — an agent carrying none still answers under the whole of the rest of the prompt. An **empty title** is the one value that substitutes something rather than nothing: `{{ agent-title }}` is replaced with exactly `Not defined`, so no compiled prompt anywhere carries an empty value in that position. That fallback belongs to this substitution alone and to nothing a reader sees (per `../ui/CTA-comment-agent-turns.md` CTA-FR-KFUF), and what the registry stores is untouched by any of it.
5. **CVL-FR-05** Every prompt tells the agent five things: the role it is taking in this conversation, which is where its title stands (CVL-FR-04); **what it has been given** — the sections that turn carries, and that the material section holds the whole of its material except where that section itself says it is partial (`../core/AGC-agent-conversations.md` AGC-FR-11); that it may gather material before answering; that the project's own specifications are the authority on what has already been decided; and that where a request admits of more than one reading it should ask the author which was meant rather than guess or answer each in turn — as it would be put to a colleague. What that last thing says differs by target, as the tool set does (CVL-FR-08): `comment.md` says to ask one question, and the three whole-target prompts say to gather everything unsettled and put it as one set where the likely answers can be proposed, and to ask one open question where they cannot. What it has been given is stated so that an agent does not spend a round of the loop (CVL-FR-13) fetching the document it was already handed. The statement is per target, exactly as the sections are: the prompts whose material section is `artifact` say that section holds the file or the draft prompt under discussion, and `discuss-draft.md` says its `discussion_history` names each change a proposal offered and what the author decided about it (per `../core/AGC-agent-conversations.md` AGC-FR-RVQP), and `discuss-note.md` says its `note_context` holds the note and that the file the note is filed against is **not** provided (AGC-FR-07) — so an agent there is told what it does not have as plainly as what it does. None of them names a tool, describes an argument, or states a limit: what a tool is called and what it takes is that tool's own fixed definition (per `../tools/TLC-tool-conventions.md` TLC-FR-05), and a prompt restating it would be a second place to keep correct. A prompt saying material need not be fetched therefore describes the material rather than the tool that would fetch it.
6. **CVL-FR-MZTK** `discuss-draft.md` states a working method: assess the whole draft one time, settle the intent before any change is offered, offer that assessment's changes as one pass, then stop. It states the bar a change meets, which is that the change alters what the graduated draft causes. A decision about a proposal is not a request for more changes.
    - *Why:* Without a stopping condition an agent offers a further small rewrite on every turn a decision dispatches, and the author decides the same passage many times.
6. **CVL-FR-06** A prompt and the input assembled beside it name the same three tags, in the same order. Every section a builder emits is a tag the prompt that turn carries describes, and no prompt describes a tag no builder emits for its targets, so the instruction telling a model how to read the material and the material itself cannot drift apart. The parity is per target rather than across the corpus of prompts: `discuss-note.md` names `note_context`, `discussion_history`, and `current_comment` and names no `artifact`, exactly as its builder emits (`../core/AGC-agent-conversations.md` AGC-FR-06, AGC-FR-07), and the other three prompts name `artifact` in that first position and no `note_context`.
7. **CVL-FR-07** Nothing a participant wrote and nothing a tool returned reaches the instruction position. An artifact's text, a draft file's text, a comment's body, an attachment's name, and the bytes of an image a prompt embeds or a comment carries enter the request only inside the sections of `../core/AGC-agent-conversations.md` AGC-FR-06; a specification's excerpt, a file's text, a skill's description, and a skill's body enter the exchange only as tool results; and the instructions carry the compiled prompt alone — the template, the agent's title the author configured (per `../core/AGR-agent-registry.md` AGR-FR-23), and the agent's instructions the author configured (per `../core/AGR-agent-registry.md` AGR-FR-08) — on the last round of the loop exactly as on the first. Material the agent fetched is governed by the same rule as material it was handed, so a file whose text reads as a command to the model is a file the model was shown and the prompt it works under is unchanged by its having read it. `load_skill` returns a procedure the model may well decide to carry out, and it arrives as material it decided to act on rather than as text occupying the position the author's own instructions occupy: no amount of what a turn reads can displace what it was asked to do.
8. **CVL-FR-08** A turn's **portable** tool set is decided by its **target** and by nothing else, as the first table of the contract surface has it; the provider-native entries beside them are decided by the provider alone (CVL-FR-30) and neither add nor remove one of these. Every turn is attached the eleven of `search_specifications`, `read_file`, `search_drafts`, `read_draft`, `search_notes`, `search_documents`, `get_document`, `search_skills`, `list_skills`, `load_skill`, and `ask_user_comment`. A turn on a discussion **with no fragment target** — an artifact, draft, or note target alike — is attached `ask_discussion_questions` beside them, and a turn on a discussion with a fragment target is attached none, a passage under review being one remark rather than a set of open points. A turn on a **draft** target, with or without a fragment, is attached `propose_draft_changes`. A turn on an **artifact** target, with or without a fragment, is attached `propose_prompt_changes`. The two proposal tools are never attached together, and a turn on a note target is attached neither. Nothing else varies the set: an agent's definition carries no tool field, no surface selects tools for one, and no project, agent, or model widens or narrows what an target decides, so two turns of one target were offered byte-identical definitions of byte-identical tools whoever asked and wherever. Reading what the project has planned is a move every agent has everywhere, for the reason reading what it has decided is: a specification, a draft, and a note are each answered better by an agent that knows which unpublished work already anticipates the question. Reading what the author has noted is a move every agent has everywhere on the same principle: a note is where a gap or a small thing still to be done is written down, so work of any kind is answered better by an agent that can tell whether the project already holds a note that work would close (per `../tools/NST-note-search-tool.md` NST-FR-04). Asking the author something is likewise a move every agent has everywhere, on the principle that a collaborator who may not ask what was meant is one who must guess. Asking several things at once is a move a **discussion** agent has, because a discussion is where material is decided rather than corrected and an agent reading a whole document finds several open points where one reading a passage finds one (per `../tools/ADQ-ask-discussion-questions-tool.md` ADQ-FR-LFDX). Offering the author a rewrite is a move an agent has wherever there is a **prompt** in front of it to offer one against, and the target decides which prompt that is and therefore which of the two tools reaches it: a draft target is about a draft's own prompt, and an artifact target is about a file of the project, whose rewrite is offered only where that file's resolved artifact type is `prompt` — a condition the tool itself checks, the target saying which store is in play rather than what the file turned out to be (per `../tools/PPC-propose-prompt-changes-tool.md` PPC-FR-06). A note is neither, so a turn on a note target is attached the eleven and no proposal tool at all, there being nothing about a note for one to rewrite; `search_notes` is attached everywhere as `search_drafts` is. Reading the reference documents the user selected is a move every agent has everywhere on the same principle: a PDF, Markdown, or text reference may live outside the project, and work of any kind is answered better by an agent that can find and read it through `search_documents` and `get_document` (per `../tools/SDT-search-documents-tool.md` SDT-FR-LNNL and `../tools/GDT-get-document-tool.md` GDT-FR-LITM). These two tools read selected Documents paths through the documents grant of `../core/FSA-filesystem-access.md` (FSA-FR-DMKC), and they give an agent's own filesystem tools no reach outside the project (FSA-FR-TXZU). Reading a draft and rewriting one are therefore separate reaches: `read_draft` loads any draft's current prompt from any target and changes nothing (per `../tools/RDT-read-draft-tool.md` RDT-FR-16), while each proposal tool offers a rewrite bounded by what its constructor bound it to (per `../tools/TLC-tool-conventions.md` TLC-FR-15). This module names the tools and holds no registry (per `../tools/TLC-tool-conventions.md` TLC-FR-19), so a tool added to that group reaches a conversation only by being named here and only on the targets named with it.
9. **CVL-FR-09** No attached tool touches the project's own material, and none touches a draft's. The eleven that gather are read-only in full (per `../tools/TLC-tool-conventions.md` TLC-FR-17) but for the one that asks the author something, the two that reach a draft included — `search_drafts` ranks over the drafts index and `read_draft` reads one live prompt, and neither writes a draft's prompt, history, proposals, comment log, or record (per `../tools/DST-draft-search-tool.md` DST-FR-20, `../tools/RDT-read-draft-tool.md` RDT-FR-16) — and the one that reaches the author's notes included, `search_notes` ranking over the notes index and writing no note, no note discussion, and no note record, and neither reading a note out of the project nor marking one as seen (per `../tools/NST-note-search-tool.md` NST-FR-19), and the two that reach the user's reference documents, `search_documents` ranking over the documents index and `get_document` reading one selected document by id, neither writing a document, a source reference, or any other state (per `../tools/SDT-search-documents-tool.md` SDT-FR-NZEH, `../tools/GDT-get-document-tool.md` GDT-FR-PXQL); `ask_user_comment`'s whole declared effect is one comment appended to the conversation the turn is already in (per `../tools/AUC-ask-user-comment-tool.md` AUC-FR-01); `ask_discussion_questions`'s is one pending question set recorded against the discussion the turn is already in, with no comment appended at all (per `../tools/ADQ-ask-discussion-questions-tool.md` ADQ-FR-KZNV); `propose_draft_changes`'s is one candidate recorded beside the draft together with the one comment referring to it (per `../tools/PDC-propose-draft-changes-tool.md` PDC-FR-01); and `propose_prompt_changes`'s is one candidate recorded in the project's own proposal store together with the one comment referring to it (per `../tools/PPC-propose-prompt-changes-tool.md` PPC-FR-01). Each of the last two is an offer rather than an edit — the write that lands it is the author's, performed from the surface that showed it to them (per `../core/DCP-draft-change-proposals.md` DCP-FR-11, `../core/PCP-prompt-change-proposals.md` PCP-FR-12) — and neither creates, renames, moves, or deletes a file anywhere. The two provider-native tools touch nothing of the application at all, a search and a retrieval being carried out elsewhere and reaching the turn as material to read (CVL-FR-31). So a turn creates, modifies, and deletes no file of the project, no file of any draft, and no note, mutates no other store, and touches no repository state beyond the conversation's own log and the candidate a proposal left beside it, however many tools it called. An agent in a conversation reads in order to answer, and writes only what it says and what it offers; an agent that acts on the project is `../core/AIC-agentic-integrations.md`'s and is reached by no path from here.
10. **CVL-FR-10** The conversation is composed and driven through the `rig` framework — its message construction, its completion request, its tool calling, and the provider client behind it, so the shape of a turn is the same whichever provider serves it. The compiled prompt occupies the request's instruction position, which is `rig`'s system instruction, and the input occupies its first user message; no provider receives the two in any other arrangement and none receives them merged into one. That first user message is **multimodal where the input is**: each section's parts become `rig`'s own text and image content in the order the section holds them, an image carrying its bytes and its media type, so a provider receives a picture as the framework's image content rather than as an encoded string inside prose, and the wire format is the framework's affair exactly as it is for text (CVL-FR-37). The application's own tools are attached as `rig` portable tools and reach the provider as its own tool definitions, so what differs between two providers is the wire format the framework produces and never which of them an agent was offered or what a call of one does. A provider-native entry travels in that same tool array, unaccompanied by any implementation of this application's (CVL-FR-30). The `openrouter` provider reaches its endpoint through the `openrouter-rs` client (per `../core/AAP-ai-api-integrations.md` AAP-FR-23), the choice of provider changing which client carries the call and nothing else about it. The `custom` provider is reached through the framework's OpenAI-compatible client, configured as CVL-FR-ZPGW states.
11. **CVL-FR-11** `complete(exchange, endpoint)` is the single seam through which a model is reached and the only place in this module that touches the network. Every round of the loop goes through it, and the tools reach no network of their own (per `../tools/TLC-tool-conventions.md`'s posture) — the provider-native ones included, whose own requests are the provider's and are made inside the call this seam had already made (CVL-FR-32) — so a turn's whole network footprint is its model calls. The seam is expressed as `rig`'s own model abstraction for a completion, so a build under test substitutes a scripted implementation wholesale rather than intercepting a URL, and a scripted reply may ask for a tool exactly as a real one does: every requirement here is exercisable, every failure of `../core/AGC-agent-conversations.md` AGC-FR-15 reachable, and every path through the loop drivable, without a request leaving the machine or a token being spent.
12. **CVL-FR-12** A turn is a **loop** rather than a single call. `complete` is called with the exchange as it stands; a reply that asks for no tool ends the loop and its prose is the answer, unless that prose is a tool call written as prose (CVL-FR-UJXD); a reply that asks for tools has each of them dispatched, each result appended to the exchange in the order the model asked for them and marked with the call it answers (CVL-FR-EKHH), and `complete` called again with the whole exchange. A reply asking for several tools at once has all of them dispatched before the next call, so an agent that asked for three specifications reads three results. A reply that reports a provider-native tool call is unlike this in every part: the provider executed that call inside the model call that has just returned, the model read its result before it composed the reply, and so there is nothing to dispatch, nothing to append, and no round owed to it (CVL-FR-31). The one exception is a reply asking for `ask_user_comment`, which ends the loop where it stands (CVL-FR-15).
13. **CVL-FR-13** A turn's model calls are bounded twice over, and the two bounds count different things. The **logical** bound is on `complete` **invocations** — the rounds of the loop, one per reply the model is asked for — and it is what stops an agent searching indefinitely. On reaching it the turn delivers whatever prose the model's final reply carried and dispatches no tool that reply asked for. The **physical** bound is on the attempts that actually reach a provider, and it is the logical bound multiplied by the retry budget each invocation may spend (CVL-FR-19): a turn presents at most that product in requests to one endpoint and never more, however many of its calls the network lost. A retried attempt advances the physical count alone, and neither bound is derived from the other at run time — the loop counts invocations and an invocation counts its own attempts.
    A final reply carrying no prose at all leaves nothing to deliver: that is the `empty_reply` outcome, recoverable on the terms of CVL-FR-18 like any other. Repeating it repeats that same logical invocation as a further **physical** attempt rather than granting the loop another round, so an empty reply on the invocation the logical bound falls on is retried exactly as one in the middle of the loop is and the logical bound stands either way. A turn whose attempts for that invocation are spent terminates `empty_reply` and appends nothing (per `../core/AGC-agent-conversations.md` AGC-FR-18), on the same terms as any other answer with no content in it.
14. **CVL-FR-14** A tool's refusal is not a turn's failure. A refusal reaches the model as that tool call's own result, carrying the message and the retryable flag the tool declared (per `../tools/TLC-tool-conventions.md` TLC-FR-09, TLC-FR-11), and the loop continues. A failure the provider reports for one of its own tools reads the same way and is governed by CVL-FR-32. A turn fails only when a model call fails, by one of the values of `../core/AGC-agent-conversations.md` AGC-FR-15.
15. **CVL-FR-15** A reply asking for `ask_user_comment`, for `ask_discussion_questions`, for `propose_draft_changes`, or for `propose_prompt_changes` **ends the turn on that call**. The call is dispatched; if it posted a question, recorded a question set, or recorded a proposal, the loop makes no further model call and the turn terminates `awaiting_reply`, that question, that set, or that proposal being the turn's one contribution (`../core/AGC-agent-conversations.md` AGC-FR-01). Every other tool call in the same reply is left undispatched, and any prose that reply carried is not appended — an agent that has asked something or offered something has said its piece, and results nothing will read and prose nobody asked for are both noise in a conversation that should read as one person putting one thing to another. A reply asking for two of them is the same case: the first is dispatched and the rest are not, a turn having one contribution and not two. A call that refused instead (per `../tools/AUC-ask-user-comment-tool.md` AUC-FR-12, `../tools/ADQ-ask-discussion-questions-tool.md` ADQ-FR-BSYE, `../tools/PDC-propose-draft-changes-tool.md` PDC-FR-15, and `../tools/PPC-propose-prompt-changes-tool.md` PPC-FR-16) ends nothing: its refusal is appended to the exchange like any other and the loop continues, so an agent whose question could not be posted, whose set was refused because one was already pending, or whose proposal was refused because the file it named is not a prompt, answers with what it has or names a different file.
    A turn ending on `ask_discussion_questions` is the one case in which `awaiting_reply` carries **no comment at all**: the set is the whole of what the turn left behind, and the conversation's log is byte-for-byte what it was (per `../tools/ADQ-ask-discussion-questions-tool.md` ADQ-FR-DHZK).
16. **CVL-FR-16** The turn is bounded by the **turn timeout** its provider stores (per `../core/AAP-ai-api-integrations.md` AAP-FR-FGNK); where the provider stores none, by the project's **execution timeout** (per `../core/PSS-project-settings-storage.md` PSS-FR-TQMV); and where the project configures none either, by five minutes. The bound spans the whole of the turn — every model call, every tool call, every wait before a retry, and the waiting between them — rather than each model call separately. A turn that has not answered within the bound terminates as `timed_out`, whatever it was doing at the moment: the model call in flight is abandoned, a tool call in flight is abandoned and its result discarded, a backoff wait in progress is abandoned and the retry it was waiting for is never made, and nothing is appended to the conversation. This is the bound on the turn and the per-call deadline of CVL-FR-17 does not replace it: the shorter deadline bounds one attempt at reaching the provider and is repeated on expiry, this one bounds the whole of the turn's work and is repeated by nothing (CVL-FR-18).
   - *Why:* A bound applied per call would let a turn that keeps reaching for tools run without limit while no single call ever exceeded it.
17. **CVL-FR-17** Each `complete(exchange, endpoint)` invocation carries a **provider-call deadline** of its own: the project's provider-call deadline (per `../core/PSS-project-settings-storage.md` PSS-FR-HDBN), which is five minutes where the project configures none, or the time remaining under the whole-turn deadline of CVL-FR-16, whichever is **less**. A call that has not answered by it is abandoned where it stands. Which deadline expired is what the outcome says: the shorter one is the provider-call `timed_out` and is recoverable, and the whole-turn one is the turn's own `timed_out` and is not (CVL-FR-18). The cap is what keeps the two from disagreeing: a call begun with ninety seconds left on the turn is given ninety seconds and not five minutes, so no per-call deadline ever outlives the turn it belongs to and no expiry is ever ambiguous about which bound it was.
18. **CVL-FR-18** A failure is **recoverable** when repeating the same call, against the same exchange, could plausibly succeed, and only three are repeated automatically: `unreachable` — which is where a name that will not resolve, a connection that will not open, and a connection reset mid-answer all surface — the provider-call `timed_out` of CVL-FR-17, and `empty_reply`, a completion that supplied neither usable prose nor a tool request, a tool call written as prose being no usable prose (CVL-FR-UJXD). `tls_untrusted` is also recoverable, because the author can fix the trust on the machine and retry the turn, but it is never repeated automatically: the same certificate is refused again until that trust changes. `invalid_response` is recoverable on the same terms: the author can retry the turn, but it is never repeated automatically, because an endpoint that returned a reply this module cannot read returns the same shape again. `invalid_request` is recoverable on the same terms too: the author can retry the turn, but it is never repeated automatically, because the same exchange builds the same request again and the framework refuses it again. Everything else is not recoverable, and is never repeated by any route: `rejected`, because credentials the provider refused are refused again; `keychain_unavailable`, `agent_not_found`, `agent_unavailable`, `context_unavailable`, and `thread_locked`, because each names a condition of the application rather than of the call, and calling again changes none of them; the whole-turn `timed_out` of CVL-FR-16, whose budget is spent by definition; and every cancellation, whether the author's, the agent's deletion, the note's, the project's close, or the application's quit — a turn nobody wants any more is not a turn to try harder at.
19. **CVL-FR-19** A failed `complete` invocation whose failure is recoverable is repeated automatically. Each invocation gets the project's **retry budget** of physical attempts (per `../core/PSS-project-settings-storage.md` PSS-FR-WPKS), which is three where the project configures none — the original call and the retries the budget leaves — and each invocation of the loop gets its own budget, so an invocation that spent its budget is a spent invocation and not a spent turn, and the next logical call after a tool result begins at attempt one again. The waits are a capped exponential schedule with jitter: the first retry has a base delay of **500 ms** and each retry after it doubles the one before, the delay actually taken is drawn uniformly within **±20%** of that base, and no delay is ever above **2 seconds**. The jitter source is a seam substituted under test, and the delay chosen is the one the record of CVL-FR-28 names.
    The wait is part of the turn: it counts against the whole-turn deadline of CVL-FR-16, it is cancellable where it stands, and **no retry begins** after that deadline expires, after the turn is cancelled by any route, or after the conversation becomes locked (`../core/AGC-agent-conversations.md` AGC-FR-19) — in each of which the turn terminates on that condition rather than on what the provider last did. An invocation whose attempts are all spent terminates the turn `failed` carrying the **last** attempt's normalized failure, which is `unreachable`, a provider-call `timed_out`, or `empty_reply`; an attempt that succeeds returns its reply to the loop, which proceeds through CVL-FR-12 exactly as though the call had succeeded the first time.
20. **CVL-FR-20** A retry repeats the failed call and **nothing else**. It carries the exchange byte-for-byte as it stood before that call, so no tool is dispatched a second time, no tool's side effect is duplicated, no comment is appended, no session is re-begun, no key is fetched again, and the input is not reassembled — a turn retrying is the same turn making the same request, and a conversation that changed while it waited is the next turn's business (`../core/AGC-agent-conversations.md` AGC-FR-13). Nothing about a retry reaches any surface: no `"agent turn state changed"` event is emitted for one, the turn stays `running` throughout, and its progress operation keeps the label it was registered with (AGC-FR-24, CVL-FR-27), so a turn that answered on its third attempt and one that answered on its first are indistinguishable to the surface that dispatched them, differing only in how long they took.
21. **CVL-FR-21** Every failed attempt is reduced to a **normalized failure class** before it is logged or reported, and the classes are distinguishable enough to act on: a name that would not resolve, a connection that would not open, a connection reset in flight, a response the provider actually returned — carrying its status alone — the provider-call deadline of CVL-FR-17, a certificate the TLS check refused — carrying the host and the cause code alone — a reply the provider returned that could not be read (`decode`, which is `invalid_response`), a request the framework refused to build before it sent anything (`request`, which is `invalid_request`), and a reply that carried nothing. An error of the framework is classified by its **kind** before any text of it is read: a reply body the framework could not decode is `decode`; a reply it reports as cut off in transit is the connection reset in flight; a request the framework refused to build, or an option it reports the model cannot honour, is `request`; a credential the framework reports the provider refused is `rejected`; and a response the provider returned with an error status is a **structured** error (CVL-FR-35). A reply that holds no message and no tool call is `empty_reply` (CVL-FR-UALC). Only an error whose kind does not settle its class is classified from its text. A transport error matching none of them is normalized all the same: it carries a safe error code and a redacted diagnostic **category**, never the underlying error's own payload. A **structured** provider error is not a transport error and is treated as its own thing (CVL-FR-35). The class is what the record of CVL-FR-28 names, what the retry decision of CVL-FR-18 is taken on, and what the turn's `AgentTurnFailure` is derived from, so a log line, a retry, and a reported failure can never disagree about what happened.
   - *Why:* A driver's error string is the one place a URL, a header, or a token reaches a log by accident.
22. **CVL-FR-22** The **waits** of the retry policy are not configurable. The base delay, its doubling, the jitter fraction and the delay ceiling are constants of this module: no command accepts one, no provider descriptor carries one, and no agent's definition names one, so two turns that failed the same way waited the same way whoever dispatched them and wherever. The attempt count and the provider-call deadline are the project's own settings, the whole-turn timeout is the provider's or else the project's (CVL-FR-16), and each is read before every turn (CVL-FR-PDXK).
23. **CVL-FR-23** Every call a turn makes marks what it presents for **provider-side caching**. The exchange's own shape is what makes that sound: it opens with the input and only ever grows (CVL-FR-12), so each call presents byte-for-byte everything the call before it presented and then more, and the compiled prompt and the tool definitions accompanying it are the same on the last round as on the first (CVL-FR-07). A retry presents what its failed attempt presented (CVL-FR-20) and is marked identically, the marking being derived from the exchange rather than chosen per attempt. Caching is a property of how a call is **carried** and of nothing else: it adds no section, alters no message, changes no tool definition, and leaves the assembled request of CVL-FR-01 and the arrangement of CVL-FR-10 exactly as they are — a provider that caches and one that does not are asked the same thing and answer on the same terms, so no behaviour here is contingent on a cache hit and no test needs one to pass. A provider that caches a repeated prefix of its own accord is relied on to do it and is marked with nothing; one that caches only what it is told to cache is told, at each call, wherever the client carrying that provider can say so (per `../core/AAP-ai-api-integrations.md` AAP-FR-23). Where that client can be told to **advance the boundary itself** — to hold what a call ends with, rather than to hold up to a place this module names — it is told that instead. The boundary a call wants is always its own last message, the exchange growing only at its end (CVL-FR-12), and a client that moves its own is that rule expressed on its side: it reaches the replies and the tool results a round accumulated, which this module could otherwise mark only by reshaping a message into a form not every endpoint accepts. What this module names for itself is what a moving boundary cannot express — the fixed places whose reuse spans **turns** rather than rounds (CVL-FR-39). The lifetime asked for is the provider's **short** one — five minutes — which spans a whole loop by a wide margin under the bound of CVL-FR-16, and which is the lifetime asked for everywhere rather than one negotiated per provider or per turn. Nothing about any of it is configurable, on exactly the terms CVL-FR-22 holds the retry constants to: no command accepts it, no provider descriptor carries it, no agent's definition names it, and no project setting varies it. A provider that declines to cache — one whose prefix falls below whatever minimum it enforces, or one with no such facility at all — answers exactly as it would have, caching changing what a turn **costs** and never what it says.
24. **CVL-FR-24** A turn runs inside an **agent session** of its own, begun when the turn is registered and ended when it terminates by any route, `awaiting_reply` included — a turn that asked the author something keeps no session open while it waits, and the fresh turn its answer dispatches begins a session of its own. The session carries the filesystem instance of `../core/FSA-filesystem-access.md` FSA-FR-29 — the active worktree and a session temp directory of its own, no reach to `app_data_dir()`, symbolic links refused — and `read_file` reads through that instance and through no other (per `../tools/RFT-read-file-tool.md` RFT-FR-05). Turns in flight at once hold sessions of their own, so no turn reaches another's temp directory, and ending a session discards its temp directory with it.
25. **CVL-FR-25** Cancellation reaches the loop wherever it stands. `cancel_agent_turn` abandons a model call in flight and a tool call in flight alike, discards the exchange, ends the session, and appends nothing (`../core/AGC-agent-conversations.md` AGC-FR-20), and every other route that cancels a turn — the agent deleted or withdrawn from the project, the project closed, the application quitting — does the same. A tool whose result arrives after its turn was cancelled is discarded rather than appended to anything.
26. **CVL-FR-26** Neither the assembled request nor the exchange it grew into is persisted, echoed into the reply, or included in any event payload — no argument of a tool call the model made, no tool result it read, and no intermediate message it composed among them. The **name** of a tool being called and the order it was begun in are the one thing about the exchange that leaves this module, reported while the call is active and for no longer (CVL-FR-33). The comment a turn appends carries the model's final answer alone, less its citation markers (CVL-FR-VSSU).
27. **CVL-FR-27** Tool use reaches a surface as **activity** and never as content. What a surface may know is that a call of a named tool is active in a turn now and the order the active calls were begun in (CVL-FR-33), which is what lets a conversation say what an agent is doing while it does it (per `../ui/CTA-comment-agent-turns.md` CTA-FR-FBJR). Nothing else about a call reaches anywhere: no argument the model composed, no result a tool returned, no count of the calls a turn made, and nothing at all once the call has finished. The progress operation of `../core/AGC-agent-conversations.md` AGC-FR-24 keeps the label it was registered with, and a delivered comment names no tool, quotes no tool result, and lists nothing the agent consulted — a turn that called eleven gathering tools and one that called none contribute indistinguishably to the conversation they answer, differing only in how long they took and in what was reported while they ran, and so do a turn that searched the web and one that did not. `ask_user_comment`, `ask_discussion_questions`, `propose_draft_changes`, and `propose_prompt_changes` are the exceptions to what a call may leave behind, and are exhaustively so: what each makes visible is its own contribution — the question as a comment, the question set as a durable record the discussion renders above its composer, the proposal as a comment carrying a reference to the candidate — together with the turn's terminal state saying the agent is owed an answer. No contribution anywhere names a tool or mentions anything the agent consulted on its way to making it.
28. **CVL-FR-28** A turn emits through `../core/LGC-logging.md`'s internal API under the `ai` and `backend` domains together, and every record it emits is **correlated** by the same fields, so the whole of one turn is read by querying its turn id and nothing has to be reconstructed by timestamp: the turn id, the agent's nickname and id, the provider identifier, and the model identifier appear on every one of them.
    A turn emits a record at each of three moments. It emits one per **failed physical attempt** at reaching the provider, additionally naming the attempt number, the retry budget it counts against, the normalized failure class (CVL-FR-21), whether that failure is being retried, and — where it is — the planned delay before the retry actually chosen (CVL-FR-19), so a schedule can be read back from the log rather than inferred. It emits one per **answered call**, additionally naming the upstream the provider routed that call to (CVL-FR-40); what the call presented in input tokens as the provider counted them; the output, cache-write, and reasoning tokens the provider reported; the provider's own identifier for the response and for the request; the model the provider says answered; and the reason the reply ended, so the round-over-round cost of a growing exchange and the routing the caching of CVL-FR-23 depends on are both read from the log rather than inferred — an upstream, an identifier, or an ending reason the provider did not give is named as not reported rather than guessed at, on the same terms a token count it declined to give is. It emits an `INFO` record when the turn **terminates**, additionally naming the terminal state, the total elapsed time of the turn, the number of logical `complete` invocations, the total number of **physical** attempts including every retry — the two counts separately, because a turn that made four calls and one that made four calls across nine attempts are the same turn to the loop and very different ones to the endpoint — and the turn's **cached** and **uncached** input token totals as the providers reported them, so whether the caching of CVL-FR-23 is actually landing is read from the log rather than inferred from an invoice a month later. A provider that reports neither contributes nothing to either total, which is indistinguishable from a turn whose prefix was never cached and is meant to be: both mean the turn paid full price, which is the thing worth noticing.
    No record a turn emits carries any part of the exchange — no input section, no exchange message, no tool argument, no tool result, and no part of the answer — nor any credential, authorization header, or key, on the terms `../core/AGC-agent-conversations.md` AGC-FR-26 and CVL-FR-26 already bind every other route out of this module. What a record names is who was asked, of what, how it went, and how many times; never what was said. Each tool logs its own call on its own terms, and what a tool's record may name is that tool's specification's affair rather than this one's (per `../tools/TLC-tool-conventions.md` TLC-FR-14).

29. **CVL-FR-29** A prompt template's **instruction text is its content with every authoring comment removed**, and the removal happens **before** `compile_prompt` replaces its two placeholders (CVL-FR-04), so a comment can never contribute a placeholder, a substituted value, or a word of what a turn is told. A comment in one of the four files is a note to whoever maintains it and is never part of the instruction: what a turn carries is the template with every comment taken out and the blank space the removal leaves closed up, beginning at its first real word. Nothing else about a template is altered — its words, its order, its Markdown, and its line breaks are what the file holds — and a template carrying no comment contributes itself unchanged. The comments stay in the files, where they are worth something to a reader of this repository and nothing to a model.

30. **CVL-FR-30** A turn's **provider-native** tool entries are decided by the provider carrying the call and by nothing else. A call carried by `openrouter` carries `{ "type": "openrouter:web_search" }`, byte-for-byte as its own spec fixes it (per `../tools/WST-web-search-tool.md` WST-FR-02), in the request's tool array beside the portable definitions the target decided. `{ "type": "openrouter:web_fetch" }` is **withheld**: the entry is unchanged and offered to no turn, because the provider refuses a request carrying it on the models an author most uses (per `../tools/WFT-web-fetch-tool.md` WFT-FR-16). The two remain tools a model would see separately and are never merged behind one name; what is suspended is the offering of one of them, and restoring it is a decision about this list rather than a change to either entry. A call carried by `anthropic`, by `openai`, or by `custom` carries neither, and nothing of this application's stands in for them there; another provider joins by its own native contract being defined and mapped rather than by this one being translated (per `../tools/TLC-tool-conventions.md` TLC-FR-23). Every conversational target is treated alike, the entries neither adding nor removing a portable tool, and nothing else varies them: no target, no agent's definition, no project, no selected model, and no setting of any kind (per `../tools/TLC-tool-conventions.md` TLC-FR-22). Only a conversation carries them, this module being the one that attaches them and `GRL-graduation-loop.md`'s phases attaching none (per `../tools/TLC-tool-conventions.md` TLC-FR-24).
31. **CVL-FR-31** A provider-native tool call is carried out **inside** the model call this module had already made, and it is finished before the reply that reports it arrives. OpenRouter runs a tool loop of its own within one call: it executes the search or the fetch, gives the result to the model, and returns the reply the model composed with that result already read. So this module dispatches nothing for such a call, appends neither the call nor its result to the exchange, and owes the turn no further round for it. A request that replayed one — as a function call for a tool that request never declared, answered by a tool result — is a malformed request rather than a continuation of the conversation, and the provider refuses it. One reply reports as many of them as the provider ran: several searches, several fetches, and the two kinds mixed, each one reported to a surface (CVL-FR-33) and recorded (CVL-FR-34). Nothing here rewrites any of it and nothing here reads it: what the provider produced is what the model had already read. A reply that reports provider tool calls and carries neither prose nor a tool call of its own has answered nothing and is empty on the terms of CVL-FR-13, there being no round that follows in which it would say what it made of the result.
32. **CVL-FR-32** This module makes no web request of its own. It implements no search and no retrieval, holds no client and no credential for one, and keeps no fallback that answers when the provider's own execution fails, so the provider's request is made inside the model call this module had already made and a turn's outbound footprint is unchanged by its agent having reached the web (CVL-FR-11). A failure the provider reports for one of its tools is that call's result rather than the turn's failure: the model read it inside the call that produced it, the loop continues, and what the turn terminates as is decided on the model call alone (CVL-FR-18), exactly as a portable tool's refusal leaves a turn's outcome to the call rather than to the tool (CVL-FR-14). Neither tool is retried, repeated, or completed by any route of this module's, there being no call here to make a second time.
33. **CVL-FR-33** The loop **reports** every tool call it begins and every one it finishes to `../core/AGC-agent-conversations.md`, which is what holds a turn's active tool calls and emits for them (per `../core/AGC-agent-conversations.md` AGC-FR-33, AGC-FR-34). A reply asking for several tools reports each of them begun, in the order the model asked for them and before any of their results is appended, so calls made in one round carry an order of their own rather than arriving as a set. A call is reported finished when its result is produced, when it refuses (CVL-FR-14), and when it is abandoned — by cancellation, by the whole-turn deadline, or by the turn ending on the call itself (CVL-FR-15, CVL-FR-16, CVL-FR-25) — so no call is left active after the loop has stopped working on it and a terminating turn leaves none behind. A **provider-native** call is reported on the same terms, begun when the provider's report of it is in hand and finished when the loop has reported and recorded it (CVL-FR-31, CVL-FR-34), the provider having executed it inside the model call this module had already made and the model having read the result before the reply arrived. What a report carries is the tool's name and its order and nothing else: no argument, no result, and no part of the exchange leaves this module by this route (CVL-FR-26, CVL-FR-27).
34. **CVL-FR-34** A turn **records** what the provider ran for itself. One record per provider-native call names the tool by its entry type, the identifier the provider gave the call, and the call's position in the reply, and it measures what the call carried: the number of characters of the arguments the model composed, and the number of characters of the result the provider produced. A call the provider produced no result for is recorded at `WARN` rather than at `DEBUG` — that is the shape a refused, an exhausted, or an unserved provider tool takes, and it is not a failure of the turn (CVL-FR-32). Where the provider counts its own tool loop, one further record names those counts: the calls the model asked for, the calls the provider executed, and the searches among them. That record is written whether or not any call came with the counts, because a provider that counted a call and executed none reports no call at all — which is the one case the counts exist to make visible. A count of asked-for calls above a count of executed ones is recorded at `WARN`. A provider that counts nothing contributes no such record, and a count the provider did not report is named as not reported rather than as zero. The records of CVL-FR-28 that name a model call additionally name how many provider-native entries the request carried and which of them, by entry type. A reply the loop **discards** for carrying nothing (CVL-FR-13) is recorded on these terms too and reported on none of them: the provider ran what it ran, and a turn that spent its attempts on such replies would otherwise read as one that never reached the web — but no surface shows a call from a reply the turn threw away. No record of any of this carries a query the model composed, an address it supplied, or any part of what came back (CVL-FR-26, CVL-FR-27): a length is not the thing it measures, and the tool is named as the provider named it, the provider owning that name (per `../tools/WST-web-search-tool.md` WST-FR-07, `../tools/WFT-web-fetch-tool.md` WFT-FR-07) and this application neither declaring it nor rewriting it.
35. **CVL-FR-35** A provider that answers with a **structured** error is recorded in its own terms, whichever provider carries the call. Where a client reports a refusal as a parsed error object rather than as a rendered request — a status, the provider's own error code as text, the provider's own identifier for the request, and the provider's own message — the failure carries each of the four the provider gave and the record names them. The message is **bounded**, a provider being free to answer at any length, and is cut by character so a message in any script is cut where it reads. This is deliberately not the transport case of CVL-FR-21 and must never be applied to it: a transport error's string is the driver's own rendering of the request it made, which is where a URL, a header, or a bearer token reaches a log by accident, while a structured error's message is the provider's account of a request it refused and is the only thing that says *why*. A request id is what takes a refusal to the provider's own record of it rather than to a reproduction attempt. The classification a structured error is given is the same one a status is given anywhere else, so a log line, a retry decision (CVL-FR-18), and a reported failure still cannot disagree.
36. **CVL-FR-36** A request the provider refuses **for the sake of a provider-native entry it offered** is made again with fewer of them, rather than failing the turn. OpenRouter answers such a request with a `400` and refuses it before the model reads anything, so the graceful path of CVL-FR-32 — where a provider's own tool failure is material the model acts on — never opens: one entry the model never used is otherwise enough to cost a turn the capability that works beside it. The refusal is told from every other `400` by the provider's own message (CVL-FR-35), because narrowing on any `400` would take an agent's capabilities away over a malformed message or an oversized context. `web_fetch` is given up before `web_search`, search alone leaving an agent able to reach the web at all while fetch alone leaves it able to read only what it already has the address of. The narrowing stands while `web_fetch` is withheld (CVL-FR-30) and is not conditioned on it: it is the guard for any entry a provider will not serve, and a turn that never offers a refused entry simply never finds anything to give up. What a model refuses is **remembered for that model** for the life of the process, so a turn pays for the lesson once rather than on every call; it is remembered per model rather than per provider, two models of one provider differing in it, and it is not persisted, a provider that repairs its own service being under no obligation to wait for an author to clear a cache this application wrote about it. A refusal that outlives every entry was never about them and is the turn's failure as any other is. Each narrowing is recorded (CVL-FR-34), so an agent that reached the web with less than it was offered says so.

37. **CVL-FR-37** A section's **content parts reach the model in the order the section holds them**, and the sections keep the order and the tags they arrived in (CVL-FR-06). A text part is text, an image part is `rig` image content carrying that image's bytes and media type, and the context an image part carries — its Markdown reference and alt text, or its filename and the comment it belongs to — is text beside it in that same position, so a model reads a picture where the material put it and reads what the material said about it. An image is never re-encoded into prose, never replaced by its filename, and never moved to the head or the foot of the input. The exchange grows on exactly the terms it always did (CVL-FR-12), so an input carrying images is presented again on every round like any other prefix and is marked for caching like any other (CVL-FR-23).
38. **CVL-FR-38** This module **decides nothing about whether a turn may carry an image**. The capability of the resolved endpoint is settled before the request is assembled and the input arrives already shaped by it (per `../core/AGC-agent-conversations.md` AGC-FR-36, AGC-FR-37): an input holding image parts is sent whole, and an input holding none is sent whole. Nothing here inspects a provider, strips a part, downgrades a request, or repairs one — a retry presents the exchange byte-for-byte as it stood (CVL-FR-20), so a request refused for any reason is never re-issued with fewer of its images or with some of them turned into text. The narrowing of CVL-FR-36 applies to provider-native **tool entries** alone and reaches no part of the input.
39. **CVL-FR-39** The input is marked in **two parts rather than one**: the leading sections whose bytes are the same on the next turn of a conversation as on this one — the material under discussion — and the tail the conversation itself grows. The order of CVL-FR-06 is what makes that split available, the material standing first and what has been said about it following, so the head is a run of **whole leading sections** and never a cut through one. Which sections are the head is the target's, as its tag order already settles (CVL-FR-06). The two reach the provider as two content parts of the one first message, and their concatenation is byte-for-byte the text that message would have carried as one — no separator added, none removed, and no part left empty — so the model reads the message it always read. The split is made by the client carrying the call and reaches neither the assembled request of CVL-FR-01 nor the arrangement of CVL-FR-10: a provider marked with nothing receives the single message it always received, and an input carrying images keeps every part in the position CVL-FR-37 puts it in. Material with no stable head, and material stable to its last character, are each marked as an unsplit input is: in the first there is nothing to mark apart, and in the second the boundary is where the mark already stands.
40. **CVL-FR-40** Where a provider **routes a call onward** to one of several upstreams that serve the model, a call asks for the upstream that served the last answered call of that model. A cache belongs to the upstream that wrote it, so a call routed elsewhere presents a prefix nothing holds however well it was marked, and the marking of CVL-FR-23 is worth what the routing lets it be worth. The upstream is learned from what the client reports of the call it carried, never guessed and never chosen here. It is remembered per **model** — two models of one provider are served by different upstreams, and one model's next turn benefits from what its last turn wrote — and it is held for the life of the process alone and never persisted, a routing fact an author cannot see being one they should never have to clear. **Fallback stays allowed**: an upstream that has gone away costs a call its cache and never the call itself, and whichever upstream answered instead is what the next call asks for. A call made before anything is known of a model asks for no upstream at all, and so does every call of a model whose client reports none. Nothing about any of it is configurable, on exactly the terms CVL-FR-22 holds the retry constants to: no command accepts it, no provider descriptor carries it, no agent's definition names it, and no project setting varies it.
41. **CVL-FR-WQZD** The loop **surfaces every reliable provider-reported token usage record** it receives, and surfaces nothing else as one. A record is reliable when the provider itself reported it for a call this loop made; a number this module could compute is not a usage record, and no usage value is ever derived from the input, the answer, a character or word count, a model's context limit, or a price. Each surfaced record carries: the **stable identity** the provider gave that usage record, or one derived deterministically from the provider's own call identifier where it named no other, so the same record surfaced twice is the same identity twice; the **logical `complete` invocation** it belongs to, numbered as the loop counts rounds (CVL-FR-13); the **physical attempt** within that invocation that produced it, numbered as CVL-FR-19 counts attempts; its **representation**, `per_call` for a record the provider reported against one call and `turn_aggregate` for one it reported for the turn as a whole; and the token values the provider actually reported — an explicit input total, its cached and uncached components, and an output total — each present only where the provider reported it. The input total counts every token the call presented, cache reads and cache writes included, on every provider. The cached component is the cache reads. The uncached component is the input total less the cache reads and the cache writes the provider reported, and it is absent where the input total is. A price the framework attaches to a usage record is not a usage value and is never surfaced. A direction the provider declined to report is **absent** from the record rather than reported as zero, on exactly the terms CVL-FR-28 already records a token count that was not reported as not reported. Every answered round surfaces its record, the rounds that follow a portable-tool result included; a failed attempt that was never answered surfaces none, having been billed for nothing; a **successful retry** surfaces its own record, which is a distinct reliable record of the same logical invocation rather than a second invocation; and a provider-native tool call, being carried out inside one provider call (CVL-FR-31), surfaces no record of its own and is present only in that call's reported usage. Which of two representations a consumer uses, and how duplicates are reconciled, are the consumer's (per `../core/DSS-draft-statistics-storage.md` DSS-FR-AWKD); this module reports what it was told, once per distinct record, and takes no view.
42. **CVL-FR-JBTX** The loop reports a turn's **execution boundaries** and whether it ever reached the model to `../core/AGC-agent-conversations.md`, which is what composes the durable lifecycle record for a draft's conversation (per `../core/AGC-agent-conversations.md` AGC-FR-YQMD). A turn has reached the model once one `complete` invocation has been made, whatever that invocation returned; a turn that ended before the first invocation — a request that could not be assembled, a cancellation that arrived first — has not. The boundaries are the loop's **own execution**: they close when the loop stops, by an answer, by a question or a proposal that ends the turn where it stands (CVL-FR-15), by a bound being reached, or by a failure, and they hold no interval this module spent waiting for anything but a provider. This module still persists nothing itself: the exchange remains unpersisted and unemitted (CVL-FR-26), and what leaves here is these boundaries, that boolean, and the usage records of CVL-FR-WQZD.
43. **CVL-FR-PDXK** The turn timeout, the provider-call deadline and the retry budget are read **before every turn** and bound that turn whole. A turn whose budget is spent terminates `failed` carrying the exhausted budget, and the turn `../core/AGC-agent-conversations.md` AGC-FR-32 registers for the author's retry reads the settings again and begins with a whole budget.
44. **CVL-FR-VSSU** Before the loop reads a reply, it removes every **provider citation marker** from the reply's text and from every string in every tool call's arguments. A marker is a span that opens with U+E200 and closes with U+E201, together with the spaces and tabs just before it. A lone character from U+E200 to U+E2FF is a marker too.
    - *Why:* OpenAI models mark web-search sources with these private-use spans, which no surface can render and which a model copies from its history.
45. **CVL-FR-POAR** Removing markers changes nothing else in a reply. The record of the call states how many characters were removed and holds nothing of the text. A reply whose text was markers alone is empty on the terms of CVL-FR-13.
46. **CVL-FR-UJXD** A reply that asks for no tool and whose whole text is a **tool call written as prose** (CVL-FR-JPHT) supplies no usable prose. It is `empty_reply` (CVL-FR-18): the same logical call is retried, nothing of the text is appended, and the warning recorded for it names the tool and holds no text.
46. **CVL-FR-UALC** A reply with no message and no tool call is `empty_reply` (CVL-FR-18). So is a reply that the framework reports as **failed** — a refusal, filtered content, or a provider-reported failure: none of its tools is dispatched and none of it is appended. An unknown finish reason ends a reply normally, as the output-token limit does.
    - *Why:* The framework fails a reply on a finish reason it does not know, so a gateway with a reason of its own would lose every answer.
47. **CVL-FR-JPHT** Text is a tool call written as prose when, trimmed and with one enclosing code fence removed, it is exactly one JSON object, and that object either holds every key one attached tool's schema requires and no key that schema does not name, or names an attached tool in `name` beside an `arguments` or `parameters` object.
    - *Why:* Some models emit a call's arguments as text, and delivering that text shows the author raw JSON in place of what the tool would have drawn.
48. **CVL-FR-ARTC** Each of the three discussion prompts tells the agent to ask the author through the questions tool, and never to write a set of questions, or the arguments of any tool, as the text of its reply.


49. **CVL-FR-ZPGW** The `custom` provider is an integration of the existing Rig-backed OpenAI-compatible adapter and adds no transport of its own. The adapter is configured with the provider's normalised base URL (`<base>/v1` is the framework client's base), the bearer secret, the resolved model id, the reasoning of the call, and the model's route `mode` (per `../core/AAP-ai-api-integrations.md` AAP-FR-ADPX). `mode` `chat` restricts the adapter to Chat Completions and `mode` `responses` restricts it to Responses. When `mode` is null or absent, both routes are permitted and the adapter keeps the route selection and fallback behaviour it has for any unrestricted model; the loop adds no preference rule and does not guess a route from the model id. The same adapter carries graduation calls and agent turns, so streaming, portable tool calls and tool-result rounds, image content, reasoning, usage reporting, retries, the provider-call deadline, the turn timeout, cancellation, empty replies, and normalised errors are the common behaviour of this module (CVL-FR-13, CVL-FR-16 through CVL-FR-20, CVL-FR-28, CVL-FR-37). The completion request and response formats, route paths, stream events, tool-call delta assembly, image serialisation, and structured provider-error parsing belong to the framework and are not restated or tested here, with the one exception of CVL-FR-TQRD. A `custom` model carries no reasoning declaration, so a `custom` call carries no reasoning parameter.
50. **CVL-FR-KXTQ** Every call that the `anthropic` provider carries states an explicit **output-token limit** of 32000. The application sets this limit. It does not depend on the framework having a default for the model id, so a model that the framework does not recognise is carried on the same terms as one that it recognises. All current Anthropic models accept the value. The limit is a constant of this module on the terms that CVL-FR-22 gives to the retry constants: no command accepts it, no provider descriptor carries it, no agent definition names it, and no project setting changes it. The `openrouter`, `openai`, and `custom` providers receive no output-token limit from this module.
    - *Why:* The Anthropic Messages API refuses a request without a limit. When the framework has no default for a model id, it refuses the call locally before it sends a request. The turn then fails, and the provider records nothing about it.
51. **CVL-FR-HBNW** A call that the `anthropic` provider carries contains no `reasoning` object. A reasoning choice on an Anthropic turn sends nothing and leaves the model at the framework's default for it (per `../core/AAP-ai-api-integrations.md` AAP-FR-31). That default is adaptive thinking where the framework's model catalog marks the model for it, and no thinking elsewhere.
    - *Why:* The Anthropic Messages API refuses a request that contains an unknown top-level field, so a `reasoning` object makes the whole turn fail.
51. **CVL-FR-ETAH** A reply that asks for tools enters the exchange as the framework returned it: its text, its tool calls, its thinking, and the provider's own identifiers for each, less the markers that CVL-FR-VSSU removes. The next round of the same turn presents that reply to the provider unchanged.
    - *Why:* A provider refuses or discards thinking that returns without its signature and identifiers, and the model loses what it reasoned before the tool call.
52. **CVL-FR-TQRD** The application applies two tolerances to a reply that the `custom` provider returns on the Responses route, before the framework decodes it. First, when the top-level `text` object has no `format` or a null `format`, the reply is read as though `format` were `{ "type": "text" }`. Second, in each `message` item of the top-level `output` array, an `output_text` content part whose `text` is null or absent is removed. Every other content part stays as it is, which includes a `refusal` part and an `output_text` part whose `text` is a string, also an empty string. Every other output item stays as it is. A `message` item can be left with no content parts. A reply that then has no text and no tool call is `empty_reply` (CVL-FR-UALC). The tolerances change nothing else in the body. A body that needs neither tolerance, and a body that is not valid JSON, passes unchanged. No other provider and no other route receives these tolerances.
    - *Why:* A gateway can return `"text": {}` or a text part whose `text` is null, and a reader that requires either field refuses the whole reply.
53. **CVL-FR-EKHH** A tool result carries the **id** of the call it answers, unchanged, and the name of the tool. The id is the one the provider gave the call, on the Responses route its `call_id`. Every appended result carries them: a tool's result, a tool's refusal, and the result of CVL-FR-15. Nothing else of the call is copied.
    - *Why:* The OpenAI Responses route matches a `function_call_output` to its `function_call` by `call_id`, so a result without it fails the next model call.

## Non-functional requirements
- The model calls are the only network access this module performs, and the turn carrying them is bounded, so a provider that does not answer degrades one conversation rather than the application. The portable tools reach no network at all, and the provider-native ones are carried out by the provider inside the call this module had already made, so a turn's whole outbound footprint is the loop's calls to one endpoint whether or not its agent reached the web.
- The prompt is fixed at build time, so two turns for one agent differ in the material they carry and in what the agent chose to gather, and in nothing else. A reply that varies where neither did is a fault in the model rather than in what was asked of it, which is what makes a regression in an agent's answers worth investigating at all.
- A turn's cost is the loop rather than one call: worst case is the logical bound of CVL-FR-13 invocations, each carrying an exchange larger than the last as fetched material accumulates in it. That bound is the ceiling on a turn's length and on how much material it can accumulate. What it costs to present that material again on every round is bounded separately, by the caching of CVL-FR-23: each call presents what the one before it presented and then more, so the repetition is charged at whatever a provider charges for material it already holds, and a turn's spend tracks what it gathered rather than how many times it went back. The prompt and the tool definitions, which are identical on every round, are the part that benefits most and the part an agent has no way to shorten. Retries do not raise the cost in any way that costs tokens: an attempt that failed transport-side was never answered and so was never billed, and one that returned an empty reply was billed for nothing. The physical bound of the retry budget times the logical one is therefore a bound on **requests presented to an endpoint** rather than on spend, which is the number that matters to a provider's rate limit and not to an invoice.
- Caching is an economy and never a behaviour. The same exchange produces the same answer whether the provider held it in a cache or read it afresh, so the suite exercises every requirement here against a seam that caches nothing (CVL-FR-11) and a cache hit is something the log reports rather than something any test asserts an answer depends on.
- A retry costs the author a wait rather than a turn: the ceiling of 2 seconds holds every wait, so a default budget's two backoff delays together are under two seconds at their bases and under 2.4 seconds at the widest jitter, against a whole-turn bound measured in minutes, so exhausting an invocation's attempts leaves the turn nearly all of its budget and a transient failure is invisible in how long an answer took. The ceiling of 2 seconds is what keeps that true if the schedule is ever lengthened.
- Retry timing is deterministic under test. The jitter source and the clock are seams like the completion seam of CVL-FR-11, so a schedule is asserted to the millisecond rather than tolerated to a margin, and a suite exercising exhaustion runs in the time three scripted failures take rather than in the time three real backoffs take.
- A tool call is cheap beside a model call — a BM25 lookup over an in-memory index, one file read, or one line appended to a conversation — so a turn's wall-clock is dominated by how many times it went back to the provider rather than by what it did in between.
- An agent that gathers material answers later than one that does not, and what it is reaching for while the author waits is reported as it happens (CVL-FR-33) rather than left blank. The timeout of CVL-FR-16 is what bounds that wait, and it is the reason the bound spans the turn rather than each call within it.
- Compiling the prompt is a string substitution over data already in memory: it touches no file, no network, and no keychain, so it cannot fail a turn that would otherwise have succeeded.
- The whole test suite runs without a network request and without a provider credential, because the completion seam is substituted rather than reached. A test that would spend a token is a test that has bypassed CVL-FR-11.
- A turn's size is bounded by the material it was handed. Every tool returns text, and no tool fetches, decodes, or returns an image, so what a turn accumulates while it runs is prose. The images a turn carries are in its first message alone, are bounded by the material's own limits (per `../core/AGC-agent-conversations.md` AGC-FR-11), and are presented again on each round like any other part of the prefix — which is what the caching of CVL-FR-23 is worth most for, a picture being the largest thing an exchange holds.
- The tags are the vocabulary the prompt and the builders share, so changing what a section holds is a change to one requirement here and to one paragraph of the prompt, rather than to a phrasing spread across the module.
