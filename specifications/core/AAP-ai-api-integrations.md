# AI API integrations

**Spec code:** `AAP`

## Intent
The backend home for the conversational AI endpoints Synthesis calls directly over HTTP: it holds one record per supported provider — OpenRouter, Anthropic, OpenAI, and the Custom LLM Gateway — each carrying the base URL to call, an API key kept in the application's single keyring entry (`ASV-application-secret-vault.md`), the models that endpoint offers together with the reasoning each of those models can be asked for, the model the author chose, the reasoning level they chose for it, and how long one conversation turn on it may run, and it records which single provider is active and which provider a given project overrides to. It is the backend half of the AI API level of `../ui/AII-ai-integrations.md`, and the single place in the application that answers "which endpoint, which key, which model, how much reasoning" for a feature about to hold a conversation with a model. Two read paths answer it, and which one a caller takes decides whose selections it runs on: a graduation run takes the integration the open project resolves to together with the model and the reasoning that integration stores, which is what the author chose in the AI API level; an agent's turn takes the provider the open project resolves to, together with the model and the reasoning the agent itself carries, which is what the author chose in the Agents section, and the stored selections have no part in it. The Custom provider is the company's OpenAI-compatible LLM Gateway: the author supplies a host or base URL without the `/v1` path and a static bearer secret that is always required, the models come from `GET <base>/v1/models`, and every conversation call goes through the existing Rig-backed OpenAI-compatible adapter, which owns the completion routes and their wire format. Reasoning is a property of a model rather than of a provider, and a model that declares nothing about it is simply asked for no reasoning at all, so the author is never offered a depth the model in front of them cannot honour. A conversational model may also accept an image in its input, and whether the one in front of the author does is a fact only the provider can report, so a record carries it and the caller that is about to send a picture asks rather than assumes. Out of scope: the completion request and response formats of the Custom LLM Gateway, which belong to the Rig adapter and are not restated here; endpoints of another modality — no record here describes a voice, an embedding, or an image-generating endpoint, and a feature that needs one has no representation in this module; agent execution, which is a different kind of integration entirely and lives in `AIC-agentic-integrations.md`; a reasoning budget expressed as a count of tokens, which no record here can hold, because reasoning is chosen as a level the model itself declares; and minting a key, which only a provider can do — this module stores a key the author already has and never obtains one.

## Contract surface
The module owns the `ai_api.providers` namespace of the application secret vault (`ASV-application-secret-vault.md` ASV-FR-03), the AI API provider registry inside the user-global store (`GSS-global-settings-storage.md` GSS-FR-27), the per-project override in that store's per-project slot (GSS-FR-28), the per-provider descriptors that ship with the application, and the Tauri commands below. Names match `../ui/AII-ai-integrations.md` byte-for-byte.

### The provider descriptor
Four providers are supported, each identified by a stable id and described by data that ships with the application rather than by anything the author supplies:

```
AiApiProvider {
  provider:          "openrouter" | "anthropic" | "openai" | "custom",
  display_name:      string,                     // "OpenRouter", "Anthropic", "OpenAI", "Custom"
  default_base_url:  string | null,              // null for "custom" — the author supplies it
  model_catalog:     ModelOption[],              // bundled fallback list, may be empty
  key_required:      bool,                       // true for every provider
}

ModelOption {
  id:                string,
  label:             string,
  reasoning:         ModelReasoning | null,      // null when the model declares no reasoning at all
  accepts_image_input: bool,                     // true only where the provider or the shipped
                                                 //   descriptor declares this model takes an
                                                 //   image in its input (AAP-FR-35)
  mode:              "chat" | "responses" | null, // the conversation route the model serves;
                                                 //   null or absent means both (AAP-FR-RTMZ);
                                                 //   only "custom" models carry a value
}
```

### The model reasoning descriptor
A model that can reason declares what may be asked of it. The descriptor is read from the provider, never authored here, and it is what makes the reasoning offered to the author compatible with the model in front of them:

```
ModelReasoning {
  mandatory:         bool,                       // reasoning cannot be switched off for this model
  default_enabled:   bool | null,                // whether the model reasons when nothing is asked
  supported_efforts: string[] | null,            // this model's own ladder, in the order it declares
  default_effort:    string | null,              // a member of supported_efforts when both are present
}
```

### The reasoning choice
What the author asked for, stored per provider beside the chosen model:

```
ReasoningChoice =
  | { kind: "off" }                              // reason as little as the model permits
  | { kind: "on" }                               // reason, at the model's own depth
  | { kind: "effort", effort: string }           // reason at a named level from the model's ladder
```

### The outbound integration record
Every command that describes an API integration returns this shape and no other. It carries no key material beyond the masked hint:

```
AiApiIntegration {
  provider:           "openrouter" | "anthropic" | "openai" | "custom",
  display_name:       string,
  base_url:           string | null,
  key_state:          "set" | "unset" | "unavailable",
  masked_hint:        string | null,             // the key's last four characters
  key_required:       bool,
  state:              "unconfigured" | "verified" | "key_unavailable",
  verified_at:        timestamp | null,
  models:             ModelOption[],
  models_origin:      "probed" | "catalog",
  selected_model:     string | null,             // null means the provider's own default
  selected_reasoning: ReasoningChoice | null,    // null means the selected model's own default
  turn_timeout_ms:    number | null,             // null means the project's execution timeout, or five minutes
  active:             bool,
}
```

### Tauri commands

Global configuration (per `../ui/AII-ai-integrations.md` AI API level):
- `"list ai api integrations"` → `list_ai_api_integrations` → `AiApiIntegration[]`, one record per supported provider in a stable order, configured or not. Reads the registry and asks the vault once for the presence of every record's key; makes no network request.
- `"verify ai api integration"` → `verify_ai_api_integration(provider, base_url, api_key)` → `AiApiIntegration` on success, or a typed error (`base_url_empty`, `base_url_invalid`, `key_missing`, `unreachable`, `rejected`, `not_an_ai_endpoint`, `timed_out`, `keychain_unavailable`). For `custom`, the base URL is the gateway root without `/v1` and the secret is required (AAP-FR-KRVT, AAP-FR-MDLQ).
- `"set ai api model"` → `set_ai_api_model(provider, model_id)` → `AiApiIntegration`, or a typed `unknown_model` error. A null `model_id` selects the provider's own default.
- `"set ai api reasoning"` → `set_ai_api_reasoning(provider, choice)` → `AiApiIntegration`, or a typed error (`no_model_selected`, `reasoning_unsupported`, `unknown_effort`, `reasoning_mandatory`). A null `choice` selects the model's own default.
- `"set ai api turn timeout"` → `set_ai_api_turn_timeout(provider, timeout_ms)` → `AiApiIntegration`, or a typed `turn_timeout_out_of_range` error. A null `timeout_ms` clears the stored value.
- `"set active ai api integration"` → `set_active_ai_api_integration(provider)` → `AiApiIntegration[]`, or a typed `not_verified` error.
- `"clear ai api integration"` → `clear_ai_api_integration(provider)` → `AiApiIntegration[]`.

Agent surfaces (per `../ui/AGT-agents.md` Global settings section):
- `"get active ai api catalog"` → `get_active_ai_api_catalog` → `{ resolution: "overridden" | "inherited" | "override_unavailable" | "none_selected" | "none_configured", catalog: AiApiCatalog | null }`, where `AiApiCatalog` is `{ provider, display_name, state, models }` with the key assumed present (AAP-FR-APRV). `catalog` describes the provider the open project resolves to and is null when none resolves. It reads the registry alone.

Project override (per `../ui/AII-ai-integrations.md` project control and `../ui/SET-project-settings.md` SET-FR-14):
- `"get project ai api integration"` → `get_project_ai_api_integration` → `{ provider: string | null, resolution: "overridden" | "inherited" | "override_unavailable" | "none_selected" | "none_configured", override: string | null }`
- `"set project ai api integration"` → `set_project_ai_api_integration(provider)` → the same shape, or a typed `not_verified` error. A null `provider` clears the override.

Internal (no UI consumer; none is a Tauri command and none is reachable from the frontend):
- `resolve_ai_api_call()` — returns `{ provider, base_url, api_key, model_id, reasoning }` for the integration the open project resolves to, together with that integration's own stored model and reasoning, or the same typed refusal `get_project_ai_api_integration` would justify. Called by `../ai/GRL-graduation-loop.md` for every model call a graduation run makes (GRL-FR-EKXT), which is the one consumer of the model and the reasoning an integration stores.
- `resolve_ai_api_endpoint(provider, model_id, reasoning)` — returns `{ base_url, api_key, model_id, reasoning, accepts_image_input, mode, turn_timeout_ms }` for a **named** provider, `accepts_image_input` being that model's own image-input capability (AAP-FR-35), `mode` that model's route metadata (AAP-FR-RTMZ), and `turn_timeout_ms` that provider's stored turn timeout (AAP-FR-TXNM), carrying the caller's own model and reasoning rather than the provider's stored selections, or a typed refusal (`not_verified`, `key_unavailable`, `unknown_model`, `reasoning_unsupported`, `unknown_effort`, `reasoning_mandatory`, `keychain_unavailable`). Called by `AGC-agent-conversations.md` for each turn (AGC-FR-14), with the provider that `resolve_agent_provider` returned.
- `resolve_agent_provider(project_key)` — returns the id of the AI API provider the open project resolves to (AAP-FR-16), reading the registry alone, or a typed refusal (`provider_unconfigured` when no provider is configured at all, `not_verified` when providers exist but none resolves). It touches neither the network nor the vault. Called by `AGR-agent-registry.md` and by `AGC-agent-conversations.md` (AAP-FR-APRV).
- `validate_ai_api_selection(provider, model_id, reasoning)` — reports whether that provider is verified and currently serves that model, and whether that model can honour that reasoning, returning the same typed refusals minus the key ones. It reads the registry alone and touches neither the network nor the vault. Called by `AGR-agent-registry.md` when an agent is created or updated (AGR-FR-06), with the provider that `resolve_agent_provider` returned.

## Functional requirements
1. **AAP-FR-01** Four providers are supported — `openrouter`, `anthropic`, `openai`, `custom` — each described by a provider descriptor that ships with the application. A provider's id, display name, default base URL, bundled model catalog, and whether it requires a key are application data, not author input, and none of them is editable through any command here.
2. **AAP-FR-02** `list_ai_api_integrations` returns exactly one record per supported provider in a stable order, whether or not that provider is configured, so the UI never has to reason about an absent record. It reads the registry and asks the vault once for the presence of every record's key (`ASV-application-secret-vault.md` ASV-FR-30); it makes no network request.
3. **AAP-FR-03** A provider's base URL is stored per provider and is whatever the author verified, prefilled by the UI from the descriptor's `default_base_url`. A named provider reached through a gateway or proxy is therefore configurable by verifying a different URL against it, and `custom` carries no default at all because its whole purpose is a gateway host only the author knows.
4. **AAP-FR-04** Every provider, `custom` included, declares `key_required = true`, so each stored configuration holds a key and a non-null `masked_hint`. A verification that resolves no key at all — none supplied and none stored (AAP-FR-32) — returns `key_missing` without a network request.
5. **AAP-FR-05** `verify_ai_api_integration(provider, base_url, api_key)` calls the endpoint under a bounded timeout with the smallest request that proves it answers as a conversational API, and distinguishes every way that can fail with its own typed error: an empty URL is `base_url_empty`, one that is not a well-formed absolute URL is `base_url_invalid`, a host that cannot be reached is `unreachable`, credentials the provider refuses are `rejected`, a URL that answers but not as a conversational API is `not_an_ai_endpoint`, and one that does not answer within the bound is `timed_out`.
6. **AAP-FR-06** A successful verification is what commits a configuration. It writes a supplied key into the vault — leaving the stored key untouched where the verification re-presented it (AAP-FR-32) — and then the base URL, the verification timestamp, and the model list to the registry, and returns the resulting record. A verification that fails for any reason writes neither, leaving the registry and the vault exactly as they were, so a provider that was working is never degraded by a failed attempt against a different URL or key.
7. **AAP-FR-07** A provider's API key is held only in the application secret vault (`ASV-application-secret-vault.md` ASV-FR-01), at the path `["ai_api", "providers", <provider_id>]`, and this module holds no keyring entry of its own. No key is written to `app_data_dir()/synthesis.toml`, to any file under a project's `.synthesis/`, to any log line, to any error payload, or into a URL.
8. **AAP-FR-08** No Tauri command returns a key or any part of it beyond `masked_hint`, the last four characters. `AiApiIntegration` is the only representation of a provider that crosses the IPC boundary, and it is the shape every command in the contract surface returns.
9. **AAP-FR-09** A record whose key the vault does not hold, or cannot answer for — the keychain was wiped, the machine was restored from a backup that excluded it, the vault value is malformed, or the OS refuses access — reads back with `key_state = "unavailable"` and `state = "key_unavailable"`. The record is retained with its base URL and model selection rather than pruned, because the author is better served by a row they can re-verify than by a configuration that silently vanished; it cannot be activated and does not resolve.
10. **AAP-FR-10** Verification probes the endpoint for the models it offers, and for each model the reasoning it declares. A probe that returns models yields `models_origin = "probed"`; a probe that returns nothing, is unsupported by the endpoint, or fails yields the provider descriptor's bundled catalog and `models_origin = "catalog"`. A probe never fails a verification that otherwise succeeded — the model list degrades, the verification does not. The one exception is `custom`, whose model list must be a valid gateway model list (AAP-FR-MDLQ): a response that is malformed fails the verification as `not_an_ai_endpoint`.
11. **AAP-FR-11** `selected_model` is optional, and null means the provider's own default rather than an unconfigured state. `set_ai_api_model` persists immediately, accepts null, and rejects a value absent from the record's current list with a typed `unknown_model` error rather than storing it.
12. **AAP-FR-12** A selection that a re-verification's refreshed model list no longer offers is cleared to null, so the integration falls back to the provider's own default rather than requesting a model that endpoint does not serve.
13. **AAP-FR-13** `set_active_ai_api_integration(provider)` records that provider as the user-global active API integration and returns a `not_verified` error for one whose state is anything other than `verified`. At most one provider is ever recorded as active: activating one clears any other, so the registry cannot hold two.
14. **AAP-FR-14** The user-global active API integration resolves implicitly when exactly one provider is verified and none has been explicitly activated, so an author with a single key is never asked to choose from a set of one. An explicit activation always wins over the implicit resolution, and a record's `active` flag reports whichever provider is active by either route, so the UI marks the same one it resolves.
15. **AAP-FR-15** `clear_ai_api_integration(provider)` removes that provider's path from the vault and returns its record to `unconfigured` — no base URL, no key, no masked hint, no verification timestamp, no model selection, not active — and is idempotent. Neither a path the vault does not hold nor an already-unconfigured record makes it fail. A cleared provider that was active leaves nothing active; a project override naming it is left recorded and stops resolving (AAP-FR-16).
16. **AAP-FR-16** `get_project_ai_api_integration` resolves the open project's API integration by these rules, and the `resolution` it returns is what tells the UI what to say: an override naming a currently-verified provider resolves `overridden`; with no override, the user-global active provider — explicit or implicit (AAP-FR-14) — resolves `inherited` naming it; an override naming a provider that is no longer verified resolves `override_unavailable`, carrying the user-global active provider as the one actually in effect, or null when there is none. When nothing resolves, the distinction is whether anything is configured at all: at least one provider configured resolves `none_selected` and no provider configured at all resolves `none_configured`, each with a null provider.
17. **AAP-FR-17** `set_project_ai_api_integration(provider)` records the override for the open project and returns a `not_verified` error for a provider that is not currently verified, so an override can only ever name an integration the author has already made work. A null `provider` clears the override, returning the project to inheriting the user-global choice.
18. **AAP-FR-18** The override is written into the user-global per-project slot (`GSS-global-settings-storage.md` GSS-FR-28), keyed by project rather than by directory (per `GSS-global-settings-storage.md` GSS-FR-18), so it is one fact for the repository, survives a change of active worktree, and is never written into a project's `.synthesis/`, which is committed content one clone would carry to everyone.
19. **AAP-FR-19** `resolve_ai_api_call()` and `resolve_ai_api_endpoint(provider, model_id, reasoning)` are the only read paths for a key and an endpoint in the application, and they differ in what selects the integration: the first resolves the one the open project resolves to and carries that integration's own stored model and reasoning, the second resolves a provider the caller names and carries the caller's model and reasoning. The two consumers are settled and do not overlap: `resolve_ai_api_call` serves the graduation loop alone (`../ai/GRL-graduation-loop.md` GRL-FR-EKXT), and `resolve_ai_api_endpoint` serves an agent's turn alone (`AGC-agent-conversations.md` AGC-FR-14), so a stored selection never reaches an agent and an agent's selection never reaches a graduation run. Both read the same provider record, so the Custom transport of AAP-FR-ADPX applies to both. Neither is registered as a Tauri command, so no frontend call can reach either, and neither returns a key where its integration does not resolve — `resolve_ai_api_call` refuses with the same typed distinction `get_project_ai_api_integration` reports, and `resolve_ai_api_endpoint` refuses `not_verified` for a provider that is not currently verified.
20. **AAP-FR-20** Every typed failure the vault reports (`ASV-application-secret-vault.md` ASV-FR-31) becomes one `keychain_unavailable` error from whichever operation touched it, and leaves the registry exactly as it was. Listing integrations keeps working while the vault is unavailable, because listing asks for presence rather than reading a key (AAP-FR-09).
21. **AAP-FR-21** Every provider here is a **conversational endpoint**. No descriptor, record, or command names an endpoint of another modality, so this module cannot describe a voice, an embedding, or an image-generating endpoint, and a feature asking it for one gets a conversational integration or nothing. The one thing about content that a record does carry is `accepts_image_input` on a model (AAP-FR-35), which says what a conversational endpoint will take in its input rather than naming a second kind of endpoint.
22. **AAP-FR-22** Every command in the contract surface exists with a typed payload in the walking-skeleton build. A stub may keep the registry in memory, use the walking-skeleton vault of `ASV-application-secret-vault.md` ASV-FR-33, return the bundled catalog for every model list, and treat any well-formed base URL as verifying, provided it returns the documented shapes and still never returns a key.
23. **AAP-FR-23** The `openrouter` provider is reached through the `openrouter-rs` crate, which is what its verification, its model probe, and the reasoning parameter of every call it carries go through. The other three providers are reached through their `rig` clients for conversation and directly over HTTP for verification, so no provider depends on another's client and a fault in one leaves the rest callable. `custom` conversation calls use the `rig` OpenAI-compatible client (AAP-FR-ADPX).
24. **AAP-FR-24** Every `ModelOption` carries the reasoning its model declares, or `null` where the model declares none. A model list obtained from the bundled catalog rather than a probe carries `null` on every option, because reasoning is something only the provider can report about a model.
25. **AAP-FR-25** `openrouter` is the provider whose probe reports reasoning; the model options of the other three carry `null` reasoning, so the author is offered a reasoning choice exactly where the application knows what the model can honour. A `custom` model never carries reasoning, because the gateway model list declares none (AAP-FR-MDLQ), so Custom models use the model default.
26. **AAP-FR-26** A model's declared ladder is authoritative over any effort level this application knows by name. An effort the application ships no knowledge of is carried through to the record and is selectable, and an effort the application knows that the model does not list is not offered for it, so a provider adding a level needs no change here to become choosable.
27. **AAP-FR-27** `set_ai_api_reasoning(provider, choice)` persists immediately and accepts null, which means the selected model's own default. It rejects a choice the selected model cannot honour rather than storing it: `no_model_selected` when the provider's `selected_model` is null, because no model's capability is known until one is chosen; `reasoning_unsupported` when the selected model declares no reasoning; `unknown_effort` for an effort absent from that model's ladder; and `reasoning_mandatory` for `{ kind: "off" }` against a model whose reasoning is `mandatory`.
28. **AAP-FR-28** The reasoning choice is stored per provider beside its chosen model (`GSS-global-settings-storage.md` GSS-FR-27), so each provider holds one reasoning choice and changing one provider's leaves every other provider's untouched.
29. **AAP-FR-29** A reasoning choice the currently selected model cannot honour is cleared to null, whether it was the model that changed under it or a re-verification's refreshed descriptor that stopped offering the level. The integration therefore falls back to the model's own default rather than asking a model for a depth it does not serve, exactly as a stale model selection falls back to the provider's default (AAP-FR-12).
30. **AAP-FR-30** `clear_ai_api_integration` returns the reasoning choice to null along with the rest of the record, so a cleared provider carries no residual depth into its next configuration.
31. **AAP-FR-31** `resolve_ai_api_call()` returns the reasoning the resolved integration holds alongside its endpoint, key, and model, and it is the only place the stored choice is turned into the reasoning a request carries — which is what makes a graduation run the only thing the author's selections in the AI API level govern (per `../ui/AII-ai-integrations.md` AII-FR-54). A null choice sends nothing, leaving the model to its own default.
32. **AAP-FR-32** A verification supplied with no key re-presents the key already stored for that provider rather than proceeding without one. The key field is never populated from the record (per `../ui/AII-ai-integrations.md` AII-FR-07), so an empty field means the key is unchanged, not that it has been withdrawn — without this a configured provider could never be verified again without the author holding their key a second time, which is the one thing storing it was meant to avoid. A key the author supplies replaces the stored one; an empty field against a provider holding no readable key resolves to no key at all, which every provider refuses as `key_missing` (AAP-FR-04). Withdrawing a stored key is what `clear_ai_api_integration` does (AAP-FR-15), so no verification ever deletes one.
33. **AAP-FR-33** `validate_ai_api_selection(provider, model_id, reasoning)` answers whether a caller's chosen combination is one this module could serve, by exactly the rules that govern a provider's own selections: the provider, which the caller takes from `resolve_agent_provider` (AAP-FR-APRV), must be verified, the model must be one its record currently offers (AAP-FR-11), and the reasoning must be one that model can honour (AAP-FR-27). It reads the registry alone — no network request, no vault access — so a caller storing a selection of its own can validate it while the vault is unavailable and while the machine is offline, and no selection is ever stored anywhere in the application against a model the endpoint does not serve.
34. **AAP-FR-34** `resolve_ai_api_endpoint(provider, model_id, reasoning)` returns the base URL and key of the named provider together with the model and reasoning the **caller** supplied, having first validated that combination by AAP-FR-33. It never substitutes the provider's own stored model or reasoning, and it consults no project override itself, because the caller has already decided which integration it means by calling `resolve_agent_provider` (AAP-FR-APRV) — which is what lets a feature holding several conversations at once run each against the model its own configuration named rather than against one global choice. The result also carries the resolved model's route metadata (AAP-FR-RTMZ).

35. **AAP-FR-35** Every `ModelOption` carries `accepts_image_input`, and it is **true only where the capability is declared**. A probe that reports the model's input modalities settles it; where the provider reports nothing about them, the shipped descriptor's own catalog entry for that model settles it; and where neither declares anything, it is **false**. An undeclared capability is therefore treated as absent rather than guessed at, which is the safe direction: a caller told a model takes no image sends text and metadata and the author reads a warning (per `AGC-agent-conversations.md` AGC-FR-37), while a caller told a model takes one and finding it does not would cost the turn. `resolve_ai_api_endpoint` returns the flag of the model it resolved, so the caller about to build a request learns the capability of the exact endpoint that will serve it rather than of the provider in general — two models of one provider differ in it freely. `validate_ai_api_selection` neither reads nor reports it: an agent is never refused for the pictures a conversation might later carry.

36. **AAP-FR-36** This module supplies the vault with one migration candidate per configured provider: the legacy service name `com.synthesis.ai-api-provider`, the provider's id as the legacy account name, and the path of AAP-FR-07 (`ASV-application-secret-vault.md` ASV-FR-20). It reads no legacy entry itself, and it supplies a candidate for every configured provider whether or not the vault already holds that provider's key, because which keys are adopted and which legacy entries are deleted is the vault's decision (`ASV-application-secret-vault.md` ASV-FR-21, ASV-FR-25).
37. **AAP-FR-FGNK** Each provider's record stores an optional **turn timeout** in milliseconds beside its chosen model (`GSS-global-settings-storage.md` GSS-FR-27). `set_ai_api_turn_timeout` stores a whole number from 30,000 to 3,600,000 and clears the value on null. It refuses any other value with `turn_timeout_out_of_range` and changes nothing. Setting one provider's value leaves every other provider's untouched.
38. **AAP-FR-TXNM** `resolve_ai_api_endpoint` returns the named provider's stored turn timeout, or null where it stores none, and no other read path returns it. The value bounds the conversation turns that run on that provider (per `../ai/CVL-conversation-loop.md` CVL-FR-16) and nothing else.

39. **AAP-FR-KRVT** The `custom` base URL is an absolute HTTP or HTTPS host or base URL **without** a `/v1` path. Trailing `/` characters are removed before it is stored and before a route is appended. A URL whose path ends in `/v1` is `base_url_invalid`, so a route is never built as `/v1/v1/...`. The same normalised value is used for model discovery and is the base URL given to the Rig-backed adapter (AAP-FR-ADPX).
40. **AAP-FR-MDLQ** `custom` verification sends `GET <base>/v1/models` with `Authorization: Bearer <secret>` under the bounded timeout of AAP-FR-05. The response is valid only if `object` is `list`, `data` is an array, and every entry has a string `id` and `object` equal to `model`; an entry may also carry `mode` (AAP-FR-RTMZ). Every other field is ignored: no reasoning level, image support, tool support, or streaming support is inferred from the response, so a `custom` model carries `null` reasoning and no image-input declaration. A response that is not valid is `not_an_ai_endpoint`, and a verification that fails for any reason leaves the last verified `custom` configuration exactly as it was (AAP-FR-06). The stored model list is replaced only after the whole response has been validated. The old routes `<root>/models` and `<root>/completions` are never used.
41. **AAP-FR-RTMZ** A `custom` model entry carries `mode`, which is `"chat"`, `"responses"`, or `null`. A missing or null `mode` means that the model supports both conversation routes. A `mode` with any other value makes the response invalid (AAP-FR-MDLQ). The value is stored with the model, returned in the model options, and returned by `resolve_ai_api_endpoint` and `resolve_ai_api_call` for the resolved model. It is route metadata only: the stored Agent record holds no route.
42. **AAP-FR-ADPX** Every conversation call to `custom`, from a graduation run or from an agent turn, goes through the existing Rig-backed OpenAI-compatible adapter of `../ai/CVL-conversation-loop.md` CVL-FR-10. This module configures that adapter with the normalised base URL, the bearer secret, the model id, the reasoning, and the model's `mode`: `chat` restricts the adapter to Chat Completions, `responses` restricts it to Responses, and a missing or null `mode` leaves the adapter to select the route as it does for any model with no restriction, with the same fallback behaviour and no new preference. This module does not define a completion request or response format, a route path, or a stream format, and it never builds a parallel completion client. The secret is given to the adapter only for the duration of the call (AAP non-functional requirements) and appears in no log line, error, or event.
43. **AAP-FR-APRV** `resolve_agent_provider(project_key)` applies the resolution rules of AAP-FR-16 and AAP-FR-14 to the registry alone, with every stored key assumed present, so it makes no network request and reads no key; a locked keychain does not stop an agent from being edited. It returns the provider the open project resolves to, `provider_unconfigured` when no provider is configured at all, and `not_verified` when providers are configured but none resolves. `get_active_ai_api_catalog` returns the same provider's `AiApiCatalog` with the resolution, and returns a null catalog when none resolves. A change to the active provider, to the project override, or to a verification is seen by the next call of either.

## Non-functional requirements
- `list_ai_api_integrations` completes without network access, so the AI API level renders offline and instantly; its only work beyond reading the registry is one presence request to the vault covering every record, and a vault that will not answer downgrades the records rather than failing the listing.
- Verification is the only operation this module performs against the network, and it is bounded: it abandons a request and returns `timed_out` rather than waiting indefinitely, so an endpoint that does not answer cannot wedge the settings surface.
- A failure to reach a provider is always distinguishable from a provider that refused the key, because the two call for different corrections by the author.
- A key exists in application memory only for the duration of the operation that carries it — the verification that checks it, the call that presents it to the provider — and is not retained between operations or cached.
- No error message, event payload, or streamed line produced anywhere in the application can contain a key; the only key-derived text that ever leaves this module is `masked_hint`.
- The user-global store stays free of secret material, preserving the property that `synthesis.toml` can be read, copied, or attached to a bug report without disclosing a credential.
- Verification transmits no project path, artifact, prompt, or file content; the request it makes is the smallest one that proves the endpoint answers.
- What reasoning a model offers is read from the provider at verification rather than compiled in, so a model gaining, losing, or renaming a level becomes choosable without a release of this application, and no list of level names is maintained here.
- A model's reasoning descriptor is capability data and carries nothing an author typed; it is safe to log, attach to a bug report, or cache alongside the model list.
- The third-party client the `openrouter` provider uses is given a key only for the duration of the call that needs it, under the same rule as every other key path here, and it is confined to that one provider so the application's ability to reach the other three does not depend on it.

## Open questions
- Whether a re-verification whose probe lists no models at all should be allowed to clear the author's selections. A probe that returns nothing degrades the model list to the provider's bundled catalogue (AAP-FR-10), which for `openrouter` and `custom` is empty because which models exist depends entirely on the account or the deployment. An empty list then offers neither the selected model (AAP-FR-12) nor the reasoning chosen for it (AAP-FR-29), so a transient answer costs the author both selections — where a probe that failed outright would have cost them nothing, because a failed verification commits nothing (AAP-FR-06).
- Whether a reasoning choice should survive the model it was made against being re-selected. A choice is cleared the moment the selected model changes to one that cannot honour it (AAP-FR-29), so returning to the original model returns the model but not the depth, and one record holds one choice (AAP-FR-28) rather than one per model.
- What a graduation run does with a reasoning choice the resolved integration carries but the provider's own API expresses differently. `resolve_ai_api_call` returns the choice as this module stored it (AAP-FR-31), and nothing here states whether a caller reaching a non-OpenRouter provider is expected to translate it or to ignore it — a question that stays theoretical only while `openrouter` is the sole provider reporting reasoning (AAP-FR-25).
