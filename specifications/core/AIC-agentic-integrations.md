# Agentic integrations

**Spec code:** `AIC`

## Intent
The backend home for the agent backends Synthesis may drive on the author's behalf. An agentic integration comes in one of two kinds: a **CLI** the application launches on this machine — Claude Code, Codex, OpenCode — or an **API** agent-execution endpoint it calls over HTTP. Whichever kind, this module locates or reaches it, verifies it by asking what it is, holds the credential it needs where it needs one, in the application's single keyring entry (`ASV-application-secret-vault.md`) — an API-kind vendor's key, and Claude Code's credential, which is an OAuth token for a subscription or a token for a custom gateway and which it requires because that CLI is expected to run in an isolated container carrying no session of its own — learns which models that installation or deployment offers, records the model and the reasoning effort the author chose — one default for the integration, and a selection of its own for a kind of turn the author wants run differently — and resolves which integration applies to the open project. It is the backend half of the Agentic level of `../ui/AII-ai-integrations.md`, and the single place in the application that answers "which agent, reached how, which model, how much thinking" for whatever feature is about to hand work to an agent, and for whichever kind of turn it is about to hand over. The one thing it hands out beyond a description is launch material, and it hands that to exactly one place: `../tools/EAC-execute-agent-cli.md` asks it, at the moment of a launch, for Claude Code's launch environment or for the location of Codex's own login directory, and no command, record, log line, error, or configuration file carries either. Out of scope: conversational, voice, and every other direct model API, which are a different level of integration entirely and live in `AAP-ai-api-integrations.md`; running an agent, which this module never does — it verifies a backend, reports what it found, and answers one executor's request for what that launch needs, and nothing here starts work on the author's behalf; and the container an agent runs in, which is decided nowhere here — the image belongs to the project (`PSS-project-settings-storage.md` PSS-FR-22) and the Docker backend to the machine (`GSS-global-settings-storage.md` GSS-FR-35).

## Contract surface
The module owns the agentic integration registry inside the user-global store (`GSS-global-settings-storage.md` GSS-FR-14), the `agentic.vendors` namespace of the application secret vault (`ASV-application-secret-vault.md` ASV-FR-03) that holds agent credentials — an API-kind vendor's key, Claude Code's OAuth token, and Claude Code's gateway token — the per-project override in that store's per-project slot (GSS-FR-26), the per-vendor descriptors that ship with the application, and the Tauri commands below. Names match `../ui/AII-ai-integrations.md` byte-for-byte.

### The vendor descriptor
Five vendors are supported, each identified by a stable id, belonging to one kind, and described by data that ships with the application rather than by anything the author supplies:

```
AgenticVendor {
  vendor:             "claude_code" | "codex" | "opencode"
                    | "claude_agent_api" | "custom_agent_api",
  kind:               "cli" | "api",
  display_name:       string,                     // "Claude Code", …, "Custom agent API"
  executable_names:   string[],                   // cli kind: what detection looks for on PATH; empty for api kind
  default_base_url:   string | null,              // api kind: prefilled endpoint; null for cli kind and for custom_agent_api
  key_required:       bool,                       // true where the vendor holds a credential:
                                                  // both api-kind vendors and claude_code
  model_catalog:      ModelOption[],              // bundled fallback list, may be empty
  reasoning_efforts:  EffortOption[],             // fixed per vendor, may be empty
}

ModelOption  { id: string, label: string }
EffortOption { id: string, label: string }
```

### The outbound integration record
Every command that describes an integration returns this shape and no other. A record carries the configuration fields of its own kind and leaves the other kind's fields absent, and it carries the credential fields only where its vendor holds a credential. No field of it holds a key or a token:

```
AgenticIntegration {
  vendor:             "claude_code" | "codex" | "opencode"
                    | "claude_agent_api" | "custom_agent_api",
  kind:               "cli" | "api",
  display_name:       string,
  binary_path:        string | null,              // cli kind
  path_origin:        "detected" | "user_supplied" | "unset",   // cli kind
  base_url:           string | null,              // api kind
  key_state:          "set" | "unset" | "unavailable",          // api kind and claude_code
  masked_hint:        string | null,              // api kind and claude_code:
                                                  // the credential's last four characters;
                                                  // for claude_code, the OAuth token's
  auth_mode:          "subscription" | "custom_gateway" | null,  // claude_code only
  gateway_base_url:   string | null,              // claude_code only
  gateway_token_var:  string | null,              // claude_code only: the variable name
                                                  // the gateway token is passed under
  gateway_key_state:  "set" | "unset" | "unavailable",  // claude_code only
  gateway_masked_hint: string | null,             // claude_code only: the gateway token's
                                                  // last four characters
  gateway_check_skipped: bool,                    // claude_code only: true when the
                                                  // author accepted the gateway with
                                                  // no gateway check
  env_vars:           string[],                   // claude_code only: "NAME=value" entries
  key_required:       bool,                       // true for both api-kind vendors
                                                  // and claude_code
  state:              "unconfigured" | "verified" | "missing" | "key_unavailable",
  version:            string | null,
  verified_at:        timestamp | null,
  models:             ModelOption[],
  models_origin:      "probed" | "catalog",
  selected_model:     string | null,              // the default for every turn kind;
                                                  // null means the backend's own default
  model_overrides:    { [turn_kind: string]: string },  // per turn kind; a kind absent
                                                  // from it takes `selected_model`
  reasoning_efforts:  EffortOption[],
  selected_effort:    string | null,              // the default for every turn kind;
                                                  // null means the backend's own default
  effort_overrides:   { [turn_kind: string]: string },  // per turn kind; a kind absent
                                                  // from it takes `selected_effort`
  active:             bool,
}

TurnKind = "work" | "review" | "semantic_rebase"
```

### Tauri commands

Global configuration (per `../ui/AII-ai-integrations.md` Agentic level):
- `"list agentic integrations"` → `list_agentic_integrations` → `AgenticIntegration[]`, one record per supported vendor in a stable order, configured or not. Reads the registry, stats each stored CLI path, and asks the vault once for the presence of every credential a record is meant to hold; runs no binary and makes no network request.
- `"detect agentic cli binary"` → `detect_agentic_cli_binary(vendor)` → `{ path: string | null }`, or a typed `not_a_cli_integration` error. Locates a candidate; persists nothing and executes nothing.
- `"verify agentic integration"` → `verify_agentic_integration(vendor, config)` → `AgenticIntegration` on success, or a typed error. `config` is `{ path }` for Codex and OpenCode, `{ base_url, api_key }` for an API-kind vendor, and for Claude Code either `{ path, oauth_token?, env_vars? }` or `{ path, auth_mode: "custom_gateway", gateway_base_url, gateway_token_var?, gateway_token?, env_vars?, skip_gateway_check? }`; any other shape for a vendor returns `wrong_config_kind`, including an `oauth_token` supplied for Codex or OpenCode. CLI-kind failures are `path_empty`, `not_found`, `not_executable`, `not_the_expected_cli`, `execution_failed`, `timed_out`, plus `token_missing`, `token_malformed`, `token_var_invalid`, `env_var_invalid:<entry number>`, `env_var_reserved:<NAME>`, `base_url_empty`, `base_url_invalid`, `gateway_status:<http status>`, `gateway_unreachable:<cause>`, `gateway_timed_out`, `gateway_not_a_model_list`, `tls_untrusted`, and `keychain_unavailable` for Claude Code; API-kind failures are `base_url_empty`, `base_url_invalid`, `key_missing`, `unreachable`, `tls_untrusted` (with host and cause, per `AAP-ai-api-integrations.md` AAP-FR-HZTB), `rejected`, `not_an_agent_endpoint`, `timed_out`, `keychain_unavailable`.
- `"set agentic integration model"` → `set_agentic_integration_model(vendor, turn_kind, model_id)` → `AgenticIntegration`, or a typed `unknown_model` or `unknown_turn_kind` error. A null `turn_kind` sets the record's `selected_model`, which every turn kind falls back to; a named one sets that kind's entry in `model_overrides`. A null `model_id` clears the entry rather than storing a null: against a null `turn_kind` it selects the backend's own default, and against a named one it returns that kind to the record's default.
- `"set agentic integration effort"` → `set_agentic_integration_effort(vendor, turn_kind, effort_id)` → `AgenticIntegration`, or a typed `unknown_effort` or `unknown_turn_kind` error. A null `turn_kind` sets the record's `selected_effort`, which every turn kind falls back to; a named one sets that kind's entry in `effort_overrides`. A null `effort_id` clears the entry rather than storing a null: against a null `turn_kind` it selects the backend's own default, and against a named one it returns that kind to the record's default.
- `"set active agentic integration"` → `set_active_agentic_integration(vendor)` → `AgenticIntegration[]`, or a typed `not_verified` error.
- `"clear agentic integration"` → `clear_agentic_integration(vendor)` → `AgenticIntegration[]`.

Project override (per `../ui/AII-ai-integrations.md` project control and `../ui/SET-project-settings.md` SET-FR-13):
- `"get project agentic integration"` → `get_project_agentic_integration` → `{ vendor: string | null, resolution: "overridden" | "inherited" | "override_unavailable" | "none_selected" | "none_configured", override: string | null }`
- `"set project agentic integration"` → `set_project_agentic_integration(vendor)` → the same shape, or a typed `not_verified` error. A null `vendor` clears the override.

Internal (no UI consumer; not a Tauri command and unreachable from the frontend):
- `resolve_agentic_invocation(turn_kind)` — returns a kind-tagged invocation for the integration the open project resolves to — `{ kind: "cli", vendor, binary_path, model_id, effort_id }` or `{ kind: "api", vendor, base_url, api_key, model_id, effort_id }` — or the same typed refusal `get_project_agentic_integration` would justify. `model_id` and `effort_id` are the model and the effort that integration holds for `turn_kind`; a null `turn_kind` resolves the record's own defaults. Called by the features that drive an agent; `../tools/EAC-execute-agent-cli.md` calls it on every launch (EAC-FR-03).
- `resolve_agent_launch_credential(vendor)` — the executor-only handoff. Returns the material one container launch needs and nothing describing an integration, or a typed refusal:

```
AgentLaunchCredential =
    ClaudeEnvironment(LaunchVariable[])                   // claude_code
  | CodexConfigMount { source: PathBuf, target: PathBuf }  // codex

LaunchVariable { name: string, value: SecretString, masked: bool }

refusals: not_an_executable_cli | token_missing | keychain_unavailable
        | registry_unavailable | codex_config_missing
```

  `AgentLaunchCredential` is a Rust type with no `Serialize`, no `Deserialize`, and no `Debug` or `Display` that renders what it holds. It crosses no Tauri boundary, appears in no `AgenticIntegration` record, and is returned to no caller but the executor.

### The Codex configuration datum
Codex authenticates through a login directory the vendor's own CLI wrote on this machine. Its host location and the container path the pinned CLI expects to find it at are per-vendor descriptor data that ships with the application, not author input and not a caller argument. This module resolves the pair and hands it over; it never opens the directory, reads a byte of it, copies it, or writes to it.

## Functional requirements
1. **AIC-FR-01** Five vendors are supported — `claude_code`, `codex`, `opencode` of kind `cli`, and `claude_agent_api`, `custom_agent_api` of kind `api` — each described by a vendor descriptor that ships with the application. A vendor's id, kind, display name, executable names, default base URL, bundled model catalog, and reasoning-effort levels are application data, not author input, and none of them is editable through any command here.
2. **AIC-FR-02** `list_agentic_integrations` returns exactly one record per supported vendor in a stable order, whether or not that vendor is configured, so the UI never has to reason about an absent record. It reads the registry, stats each stored CLI path, and asks the vault once for the presence of every credential a record is meant to hold (`ASV-application-secret-vault.md` ASV-FR-30); it runs no binary and makes no network request.
3. **AIC-FR-03** `detect_agentic_cli_binary(vendor)` searches the current `PATH` and the platform's conventional install locations for a CLI-kind vendor's executable names and returns the first match, or null when nothing matches. Detection neither persists its result nor executes what it found, and it returns a typed `not_a_cli_integration` error for an API-kind vendor, which has no binary to find.
4. **AIC-FR-04** Verifying a CLI-kind integration runs the binary at the supplied path with the vendor's version argument, under a bounded timeout, in a working directory this module chooses, and with no argument derived from the open project. A run that exceeds the timeout returns `timed_out` and the child process is terminated.
5. **AIC-FR-05** CLI-kind verification confirms identity, not merely existence: the binary's output must identify it as the vendor being verified, and one that does not returns `not_the_expected_cli`. A path that does not exist returns `not_found` and one that exists but cannot be executed returns `not_executable`, so the author can tell a wrong path from a permissions problem.
6. **AIC-FR-06** A successful verification is what commits a configuration, whichever kind. It persists the kind's configuration fields — the path and its origin for a CLI, the base URL for an API agent, whose key it writes to the vault first — together with the reported version, the verification timestamp, and the model list, and returns the resulting record. Claude Code is the one vendor whose credential is written after rather than before, because a token is worth storing only for an installation that has proved to exist (AIC-FR-28). A verification that fails for any reason persists nothing and leaves the registry and the vault exactly as they were, so an integration that was working is never degraded by a failed attempt against a different path, URL, key, or token.
7. **AIC-FR-07** `path_origin` records whether a CLI-kind integration's stored path came from `detect_agentic_cli_binary` or from the author. A path the author supplied is never replaced by a later detection; detection is offered only where no path is stored.
8. **AIC-FR-08** Verification probes the backend for the models that installation or deployment offers. A probe that returns models yields `models_origin = "probed"`; a probe that returns nothing, is unsupported by the vendor, or fails yields the vendor descriptor's bundled catalog and `models_origin = "catalog"`. A probe never fails a verification that otherwise succeeded — the model list degrades, the verification does not.
9. **AIC-FR-09** Reasoning-effort levels come from the vendor descriptor and are never probed. A vendor with no notion of reasoning effort declares an empty list, which is what its records carry. A CLI-kind vendor declares **every** level its pinned CLI accepts, as that CLI's own protocol specification states them (for Claude Code, the five of `../infra/CCP-claude-code-cli-protocol.md` CCP-FR-05). A descriptor that declared fewer would put a level the executor can generate and the CLI would honour beyond the author's reach, which is a setting nobody can choose and nothing reports as missing.
10. **AIC-FR-10** `selected_model` and `selected_effort` are both optional, and null means the backend's own default rather than an unconfigured state. `set_agentic_integration_model` and `set_agentic_integration_effort` persist immediately, accept null, and reject a value absent from the record's current list with a typed error rather than storing it.
    **The model and the reasoning effort are each held per turn kind, over one default.** `selected_model` is the model every turn kind uses and `selected_effort` is the effort every turn kind uses; `model_overrides` and `effort_overrides` name the kinds that use something else. The model resolved for a kind is that kind's entry in `model_overrides` where it holds one and `selected_model` otherwise, and the effort resolved for a kind is read from `effort_overrides` and `selected_effort` on exactly those terms. The two maps are independent of each other and of the defaults above them: a kind may take a model of its own and the default effort, an effort of its own and the default model, both, or neither, and setting or clearing an entry in one map leaves the other map and both defaults where they stand. Neither map stores a null — a kind that follows the default is absent from it — so a record carrying an empty map resolves one model and one effort for every kind, which is what an integration configured before any kind was distinguished reads back as, and nothing has to be migrated for such a record to remain correct. An override under a `turn_kind` outside the closed set of `../tools/EAC-execute-agent-cli.md` EAC-FR-IRRD is `unknown_turn_kind` and is never stored, on the same terms a model outside the record's current list is `unknown_model` and an effort outside the record's list is `unknown_effort`; every one of those rejections leaves both defaults and both maps exactly as they were. Which turn is which kind is decided by the feature that dispatches it and never here.
11. **AIC-FR-QVWX** An override stored under a turn kind this build does not offer is **dropped on read**, exactly as AIC-FR-11 drops a model the refreshed list no longer offers. The record falls back to `selected_model` and `selected_effort` for that kind, and nothing is written until the next selection.
11. **AIC-FR-11** A model selection that a re-verification's refreshed model list no longer offers is cleared, so the integration falls back rather than requesting a model it does not have, and the clearing reaches every model selection the record holds: `selected_model` reads back null where the refreshed list has dropped it, and every entry of `model_overrides` naming a model the refreshed list no longer offers is removed, which returns that turn kind to the record's default. A selection the refreshed list still offers is kept exactly as it was, whether it is the default or one turn kind's override. The effort selections are unaffected, because effort levels do not change with the installation.
12. **AIC-FR-12** `set_active_agentic_integration(vendor)` records that vendor as the user-global active agentic integration and returns a `not_verified` error for one whose state is anything other than `verified`. At most one vendor is ever recorded as active, across both kinds: activating one clears any other, so the registry cannot hold two.
13. **AIC-FR-13** The user-global active agentic integration resolves implicitly when exactly one vendor is verified and none has been explicitly activated, so an author with a single agent backend is never asked to choose from a set of one. An explicit activation always wins over the implicit resolution, and a record's `active` flag reports whichever integration is active by either route, so the UI marks the same one it resolves.
14. **AIC-FR-14** `clear_agentic_integration(vendor)` returns that vendor to `unconfigured` — no path, no base URL, no credential, no masked hint, no version, no verification timestamp, no selections, not active — removing the vault path of every credential the vendor holds, an API-kind vendor's key or both of Claude Code's tokens, as part of the same operation, and is idempotent. Clearing Claude Code also returns its authentication mode, gateway fields, and `env_vars` to their unset values. A cleared vendor that was active leaves nothing active; a project override naming it is left recorded and stops resolving (AIC-FR-16).
15. **AIC-FR-15** A record's `state` is `unconfigured` when nothing is stored for it, `missing` when a CLI-kind vendor's stored path no longer exists on disk, `key_unavailable` when the vault does not hold, or cannot answer for, the credential of a vendor that holds one (for Claude Code, the credential of its authentication mode), and `verified` otherwise. Claude Code can reach either degraded state, and `missing` wins where both hold, because a path that no longer exists is the first thing the author has to correct. A degraded integration of either kind keeps its stored configuration and selections rather than being cleared, because an author is better served by a row they can re-verify than by a configuration that silently vanished; it cannot be activated and does not resolve.
16. **AIC-FR-16** `get_project_agentic_integration` resolves the open project's integration by these rules, and the `resolution` it returns is what tells the UI what to say: an override naming a currently-verified integration resolves `overridden`; with no override, the user-global active integration — explicit or implicit (AIC-FR-13) — resolves `inherited` naming it; an override naming an integration that is no longer verified resolves `override_unavailable`, carrying the user-global active integration as the vendor actually in effect, or null when there is none. When nothing resolves, the distinction is whether anything is configured at all: at least one vendor configured resolves `none_selected` and no vendor configured at all resolves `none_configured`, each with a null vendor.
17. **AIC-FR-17** `set_project_agentic_integration(vendor)` records the override for the open project and returns a `not_verified` error for a vendor that is not currently verified, so an override can only ever name an integration the author has already made work. A null `vendor` clears the override, returning the project to inheriting the user-global choice.
18. **AIC-FR-18** The override is written into the user-global per-project slot (`GSS-global-settings-storage.md` GSS-FR-26), keyed by project rather than by directory (per `GSS-global-settings-storage.md` GSS-FR-18), so it is one fact for the repository, survives a change of active worktree, and is never written into a project's `.synthesis/`, which is committed content one clone would carry to everyone.
19. **AIC-FR-19** `resolve_agentic_invocation(turn_kind)` is the single read path for an actual invocation, and what it returns is tagged by the resolved integration's kind, so a caller cannot mistake a binary path for an endpoint: a CLI resolves to a path, a model, and an effort, and an API agent to a base URL, a key, a model, and an effort. The model and the effort it returns are the two AIC-FR-10 resolves for `turn_kind`, so a caller supplies the kind of turn it is about to run and never the model or the effort that kind is to use — the selections stay the author's, held here, and the caller states only which of them applies. **Which integration answers and what that integration is set to are two separate questions**, and this command asks them in that order: the project override selects the integration on the terms of AIC-FR-16, and the model and the effort then come from that integration's own default and its own overrides. An override therefore carries no model and no effort of its own, and moving a project from one integration to another moves it to the selections the author made for the integration it moved to. It is not registered as a Tauri command, so no frontend call can reach it, and it refuses with the same typed distinction `get_project_agentic_integration` reports rather than returning an invocation when the project resolves no integration.
20. **AIC-FR-20** The secret material in this module is an API-kind vendor's key, Claude Code's OAuth token, and Claude Code's gateway token. Each is held only in the application secret vault (`ASV-application-secret-vault.md` ASV-FR-01), at the path `["agentic", "vendors", <vendor_id>]`, where the gateway token's id is `claude_code_gateway`, and this module holds no keyring entry of its own — the same credential-storage convention every other secret in the application follows (per `GTS-github-token-storage.md` GTS-FR-01 and `AAP-ai-api-integrations.md` AAP-FR-07). None is written to `app_data_dir()/synthesis.toml`, to any file under a project's `.synthesis/`, to any log line, to any error payload, or into a URL, and no command returns a credential or any part of it beyond `masked_hint`. Codex and OpenCode hold no credential here, because each authenticates itself through its own mechanism: Codex through a login directory its own CLI wrote on this machine, whose location this module resolves for one executor (AIC-FR-30) but never opens, reads, copies, or writes; and OpenCode through a mechanism this module neither performs, observes, nor resolves anything about.
21. **AIC-FR-21** Every command in the contract surface exists with a typed payload in the walking-skeleton build. A stub may keep the registry in memory, use the walking-skeleton vault of `ASV-application-secret-vault.md` ASV-FR-33, return the bundled catalog for every model list, and treat any non-empty path or well-formed base URL as verifying, provided it returns the documented shapes, still enforces Claude Code's token rules (AIC-FR-26, AIC-FR-27), and never returns a credential.
22. **AIC-FR-22** Verifying an API-kind integration calls the endpoint under a bounded timeout with the smallest request that proves it answers as an agent-execution endpoint, and distinguishes every way that can fail with its own typed error: an empty URL is `base_url_empty`, one that is not a well-formed absolute URL is `base_url_invalid`, an absent key where the vendor requires one is `key_missing`, a host that cannot be reached is `unreachable`, a host whose certificate the TLS check refuses is `tls_untrusted` with the host and the cause (per `AAP-ai-api-integrations.md` AAP-FR-HZTB), credentials the endpoint refuses are `rejected`, a URL that answers but not as an agent-execution endpoint is `not_an_agent_endpoint`, and one that does not answer within the bound is `timed_out`.
23. **AIC-FR-23** Both API-kind vendors speak the same agent-execution protocol, and they differ only in what ships prefilled: `claude_agent_api` carries a default base URL, and `custom_agent_api` carries none because it exists so that a self-hosted, proxied, or otherwise relocated deployment of that protocol can be pointed at by URL. A stored base URL is whatever the author verified, so a named vendor reached through a gateway is configurable by verifying a different URL against it.
24. **AIC-FR-24** Every typed failure the vault reports (`ASV-application-secret-vault.md` ASV-FR-31) becomes one `keychain_unavailable` error from whichever operation touched it, and leaves the registry exactly as it was. Listing integrations keeps working while the vault is unavailable, because listing asks for presence rather than reading a credential, which is what resolves the `key_unavailable` state of AIC-FR-15.
25. **AIC-FR-25** A record carries the configuration fields its vendor actually has and no others: a CLI-kind record carries no base URL, and an API-kind record carries no binary path or path origin. The credential fields follow the credential rather than the kind — `key_required`, `key_state`, and `masked_hint` describe an API-kind vendor's key and Claude Code's OAuth token, while Codex and OpenCode carry `key_required = false`, `key_state = "unset"`, and a null `masked_hint` because they hold nothing. The gateway fields and `env_vars` belong to Claude Code alone: every other record carries a null `auth_mode`, no gateway value, `gateway_key_state = "unset"`, `gateway_check_skipped = false`, and an empty `env_vars`. No record of any vendor carries a field holding a token or a key. Everything else — version, verification timestamp, model list and its origin, selections, state, and the active flag — is common to every vendor, which is what lets one surface present them side by side.
26. **AIC-FR-26** In subscription mode, Claude Code's configuration payload is `{ path, oauth_token }` when the author supplies a new token and `{ path }` when they keep the one already stored. The shorter form is accepted only where the vault holds a Claude Code token; where it holds none, verification returns a typed `token_missing` error and the vendor stays exactly as it was rather than becoming configured on a path alone, so Claude Code is never `verified` without a token behind it. A supplied token always replaces the stored one, and the two forms are otherwise indistinguishable in what they return.
27. **AIC-FR-27** A supplied `oauth_token` is validated against `^sk-ant-oat01-[A-Za-z0-9_-]+$` and against nothing else, and a value that does not match returns a typed `token_malformed` error before the binary is run and before the vault is touched. The check is structural and complete: this module asks no service and runs no CLI to decide whether a token is genuine, current, or entitled to anything, so a well-formed token that has been revoked verifies here and fails wherever it is eventually presented.
28. **AIC-FR-28** Claude Code's token reaches the vault only once the binary at the supplied path has verified, and the single whole-object write that lands it (`ASV-application-secret-vault.md` ASV-FR-10) replaces the previously stored token in one step, so the vendor holds exactly one token at every observable moment and never zero between the two. A verification that fails at any stage — malformed token, missing token, absent path, wrong binary, timeout, or a vault that refuses the write — leaves the registry and the vault byte-for-byte as they were, so an author who mistypes a new token still has the one that was working.
29. **AIC-FR-29** `resolve_agent_launch_credential` is the only way either of Claude Code's tokens leaves this module, and it leaves for exactly one destination. `resolve_agentic_invocation()` returns a CLI invocation of a path, a model, and an effort and carries no token (AIC-FR-19); no Tauri command, no `AgenticIntegration` record, no log line, no error payload, and no configuration file carries one or any part of one; and no command places one in a process environment, an argument list, a container image, or a file. Outside this module and the one container `../tools/EAC-execute-agent-cli.md` hands it to (EAC-FR-15), the token's whole observable effect is that Claude Code's record reads `key_state = "set"` with a masked hint.
30. **AIC-FR-30** `resolve_agent_launch_credential(vendor)` answers only for a vendor this application can execute, and only with what one launch needs: Claude Code's launch environment (AIC-FR-XZCS), read from the vault for that one request, or Codex's login-directory source and the container target its pinned CLI expects. It returns `not_an_executable_cli` for `opencode` and for either API-kind vendor, `token_missing` where Claude Code has no stored token for its authentication mode, `keychain_unavailable` where the vault will not answer, `registry_unavailable` where the stored authentication mode cannot be read or a gateway record holds no base URL, and `codex_config_missing` where the resolved login directory does not exist — and it returns nothing at all about which integration is selected, which is `resolve_agentic_invocation()`'s answer and not this one's. `binary_path` is never part of what it returns, because a stored path is a verification and detection datum (AIC-FR-05, AIC-FR-07) rather than an execution input.
31. **AIC-FR-31** The handoff type is unserializable by construction: it derives no `Serialize` and no `Deserialize`, renders nothing it holds through `Debug` or `Display`, zeroizes every variable value when dropped, and is returned by no Tauri command and to no caller other than the executor. A refusal from AIC-FR-30 carries no credential-derived text and no filesystem path, so a launch that fails for want of a credential is diagnosable from its typed variant alone.
32. **AIC-FR-32** This module supplies the vault with one migration candidate per vendor that holds a credential, and none for the gateway token, which no earlier layout stored: the legacy service name `com.synthesis.agentic-integration`, the vendor's id as the legacy account name, and the path of AIC-FR-20 (`ASV-application-secret-vault.md` ASV-FR-20). It reads no legacy entry itself, and it supplies no candidate for Codex or OpenCode because neither holds a credential here. For every vendor that does hold one it supplies a candidate whether or not the vault already holds that credential, because which credentials are adopted and which legacy entries are deleted is the vault's decision (`ASV-application-secret-vault.md` ASV-FR-21, ASV-FR-25).

33. **AIC-FR-33** The vendor `resolve_agentic_invocation()` resolves is the **identity a project's committed Docker image entry is selected by**: the executor asks `PSS-project-settings-storage.md` for the entry of that vendor and of no other (`../tools/EAC-execute-agent-cli.md` EAC-FR-38). This module holds no image reference, no image digest, no Dockerfile path, and no Docker backend value, in a record, a descriptor, a command, or the store it owns, so which image a vendor runs in is a fact about the project and how Docker is reached is a fact about the machine — neither is a property of an integration. The executable vendors are `claude_code` and `codex` alone (AIC-FR-30): `opencode` may be configured, verified, activated, and overridden to like any other CLI-kind vendor, and it resolves no launch, so a project that configures an image for it has configured an image nothing can yet run.
34. **AIC-FR-WNQR** Claude Code holds an authentication mode, `subscription` or `custom_gateway`. A record with no stored mode reads as `subscription`. A payload that names any other mode returns `wrong_config_kind`. A successful verification commits the mode, and nothing else changes it. The mode decides which credential the launch uses (AIC-FR-XZCS) and which one `state` depends on (AIC-FR-15).
35. **AIC-FR-UFNB** A Custom gateway verification carries `path`, `auth_mode = "custom_gateway"`, `gateway_base_url`, and optionally `gateway_token_var`, `gateway_token`, `env_vars`, and `skip_gateway_check`. A gateway field or `skip_gateway_check` in a subscription payload, and an `oauth_token` in a gateway payload, return `wrong_config_kind`. A base URL is refused as `base_url_empty` or `base_url_invalid`. A URL that carries a credential, a query, or a fragment is invalid.
36. **AIC-FR-CVPW** `gateway_token_var` is the name the gateway token is passed under. An absent or blank value means `ANTHROPIC_AUTH_TOKEN`. A value that does not match `^[A-Za-z_][A-Za-z0-9_]*$`, `ANTHROPIC_BASE_URL`, and a name that AIC-FR-XTEZ reserves return `token_var_invalid`. The stored value is returned in the record.
37. **AIC-FR-IOWS** The gateway token is required. A `gateway_token` replaces the stored one. An absent one keeps the stored one, and returns `token_missing` where none is stored. A supplied token is trimmed. One that is then empty, or holds whitespace or a control character, returns `token_malformed`. This check runs before the binary runs and before any vault write.
38. **AIC-FR-PADP** After the binary verifies, a gateway verification sends one `GET <gateway_base_url>/v1/models` under a bounded timeout, with the token as a bearer token. When `gateway_token_var` is `ANTHROPIC_API_KEY`, the token is sent as `x-api-key` instead. A 2xx answer that lists models succeeds, and the models it lists become the record's model list with `models_origin = "probed"` (AIC-FR-08).
39. **AIC-FR-DRPC** A gateway check fails with `gateway_status:<http status>` for any answer that is not 2xx, `gateway_unreachable:<cause>` for a network error, `gateway_timed_out` for no answer in time, `tls_untrusted` for a refused certificate (AIC-FR-22), and `gateway_not_a_model_list` for a 2xx body that is not a model list. The check does not follow a redirect. It reports the redirect status. A failure persists nothing (AIC-FR-06). No binary failure uses one of these codes, so a caller can tell a gateway failure from a binary failure by its code alone.
40. **AIC-FR-KWMV** A gateway verification with `skip_gateway_check = true` runs every check of AIC-FR-UFNB, AIC-FR-CVPW, AIC-FR-IOWS, and AIC-FR-XTEZ, and verifies the binary (AIC-FR-04). It sends no request to the gateway. The model list is the bundled catalog with `models_origin = "catalog"`. It commits what AIC-FR-YXAB commits, and it commits `gateway_check_skipped = true`. A gateway verification that runs the check commits `gateway_check_skipped = false`, and so does every subscription verification. A binary failure fails the verification and persists nothing. The flag lets an author use a gateway that does not answer `GET /v1/models`, such as a gateway in front of Amazon Bedrock.
41. **AIC-FR-YXAB** A gateway verification commits `auth_mode`, the normalized base URL, and `gateway_token_var` to the registry. It also commits the token's masked hint when the token has eight or more characters. It writes the token to the vault at `claude_code_gateway` in one whole-object write after verification succeeds (AIC-FR-28). It never touches the OAuth token. A subscription verification never touches the gateway token.
42. **AIC-FR-XTEZ** `env_vars` is a list of `NAME=value` entries, valid in both modes. `NAME` must match `^[A-Za-z_][A-Za-z0-9_]*$`. The value holds no line break and no NUL. Otherwise the verification returns `env_var_invalid:<entry number>`. A reserved name returns `env_var_reserved:<NAME>`. A name is reserved, in any case, when the Docker client or executor uses it, or it starts with `DOCKER_`, `LD_`, `DYLD_`, or `XDG_`.
43. **AIC-FR-SXVA** An absent `env_vars` keeps the stored list. A supplied list, empty or not, replaces it. The registry stores the entries as given. A log record, an error payload, and a typed failure name an entry by `NAME` at most and never carry its value.
44. **AIC-FR-XZCS** The Claude Code launch environment is a list of named variables. Subscription mode holds `CLAUDE_CODE_OAUTH_TOKEN` set to the OAuth token. Gateway mode holds `ANTHROPIC_BASE_URL` set to the base URL, and the gateway token under `gateway_token_var`, and no `CLAUDE_CODE_OAUTH_TOKEN`. Each `env_vars` entry follows and replaces a variable of the same name. The handoff skips a stored entry with a reserved name.
45. **AIC-FR-ISOC** Each variable in the launch environment carries a `masked` flag. The flag is true for a token, and for an `env_vars` value of eight or more characters. The flag is false for the `ANTHROPIC_BASE_URL` that the gateway base URL sets. The executor uses the flag to decide which values its records mask (`../tools/EAC-execute-agent-cli.md` EAC-FR-29).

## Non-functional requirements
- `list_agentic_integrations` completes without network access and without running any binary, so the Agentic level renders offline and instantly; its only work beyond reading the registry is a stat per stored path and one presence request to the vault covering every record that holds a credential.
- Verification is bounded whichever kind it targets: it terminates a child process or abandons a request and returns `timed_out`, or `gateway_timed_out` for the gateway check, rather than waiting indefinitely, so a hung CLI or an unanswering endpoint cannot wedge the settings surface.
- API-kind verification uses the shared TLS configuration of `AAP-ai-api-integrations.md` AAP-FR-WMCX and AAP-FR-QLNV. A failure to reach an API agent is always distinguishable from one whose certificate is not trusted, and both are distinguishable from one that refused the key, and a wrong CLI path is always distinguishable from a permissions problem, because each pair calls for a different correction by the author.
- Detection touches only the current process environment and the filesystem; it never contacts a vendor's service and never installs anything.
- The user-global store stays free of secret material, preserving the property that `synthesis.toml` can be read, copied, or attached to a bug report without disclosing a credential. The `env_vars` values are author-supplied configuration and not credentials, and the Agentic level says so (`../ui/AII-ai-integrations.md` AII-FR-EJMG).
- A credential — an API key or either of Claude Code's tokens — exists in this module's memory only for the duration of the operation that carries it, and this module retains it nowhere. The vault owns the one process cache of every stored secret (`ASV-application-secret-vault.md` ASV-FR-ZUGZ, ASV-FR-27); that cache grants this module no right to hold a credential, and a launch holds the credential for that one launch only. No error message, event payload, or streamed line produced anywhere in the application can contain one. The only credential-derived text that leaves this module for a reader is `masked_hint`; the only credential itself that leaves it is the one `resolve_agent_launch_credential` hands the executor, in a type that cannot be serialized, rendered, or persisted.
- Verification passes no project path, artifact, prompt, or file content to any backend: a CLI is run with a version argument and nothing else, with no credential in its arguments or its environment, and an endpoint receives the smallest request that proves it answers.
