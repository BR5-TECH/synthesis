# Artifact scanning

**Spec code:** `ASC`

## Intent
The backend engine that makes the Project panel real: it treats the project's filesystem as the source of truth, walks the project root recursively, and classifies every file it finds into one of the fixed built-in artifact types (Skill, Agent, Prompt, Spec, Flow, Architecture, Instructions, Scenario, Scratchpad, Document). Document is the type a user gives a file or folder to make it a source of the project's Documents collection (`DCL-documents-collection.md`); it comes only from an assignment and is not reported to agents as an artifact type. Classification combines multi-ecosystem path inference (different agents — Claude Code, GitHub Copilot, Codex — keep Skills and Agents under different paths) with user-authored overrides that may tag a single file or a whole folder. Attribution overrides persist inside `.synthesis/` so they are shareable and survive relaunch, while the displayed tree always mirrors what is actually on disk. Nothing is reached through a symbolic link — links are skipped rather than resolved — so every node in the tree names a real path under the root. A large repository, such as a monorepo, is a normal project: the scan builds a **project index** in the background, and every tree command answers from it for one folder at a time, so the size of the project never blocks the window. A git submodule or another repository inside the project is a **nested repository**: its content is classified and ignored by its own rules, as git treats it. A recursive filesystem watcher keeps the Project panel live: externally created, deleted, moved, or renamed files produce a debounced "project tree changed" event the UI reacts to, carrying the paths that disappeared so the surfaces holding them can let them go, and each change it observes is accounted for in the session log. Out of scope for v1: the initialisation of a submodule, which the author does outside the app; third-party (plugin-supplied) recognizers and user-defined artifact types; the built-in type set and recognizers are fixed, and the command surface is forward-stable so a later plugin category may add recognizers without renaming anything.

## Contract surface
This module composes the `FSA-filesystem-access.md` primitives into a higher-level scan/classify/watch surface. The tree-read, mutation, rescan, and watch operations below are owned here. Quoted names are the canonical operation names as they appear in the owning UI spec's "Delegated to backend (abstract)" line and MUST match byte-for-byte: the type-curation commands in `../ui/LCM-library-context-menu.md`, the tree reads and rescan in `../ui/LIB-library.md`, and the artifact and path lists in `../ui/FLO-flow.md` and `../ui/NTS-notes.md`.

### UI-facing (Tauri commands)
Every command below answers from the project index (ASC-FR-HPUY) and runs off the main thread (ASC-FR-TPJO). Per `../ui/LIB-library.md` (tree reads and rescan):
- `"list tree children (folder path)"` → `list_tree_children(path)` — the direct children of one folder, as `[TreeNode]` with no `children` field, in tree order (ASC-FR-KVIE). `path = ""` names the project root. Errors with `path_not_in_tree` for a path that the index does not hold as a folder.
- `"list tree path (path)"` → `list_tree_path(path)` — `[{ folder, children: [TreeNode] }]` for the project root and for each ancestor folder of `path`, from the root down (ASC-FR-AGGG). Returns `null` for a path that the index does not hold.
- `"filter project tree (text, lens, limit)"` → `filter_project_tree(text, lens, limit)` — `{ root: [TreeNode], truncated }`: the nodes that match, with their ancestor folders, as nested nodes (ASC-FR-SKRN). `lens` is `all_artifacts`, `all_files`, or one artifact type of ASC-FR-02.
- `"list project artifacts"` → `list_project_artifacts()` — `[TreeNode]` with no `children` field: every file with a resolved `artifact_type` and every folder with a folder-scope assignment, in tree order (ASC-FR-YNJR).
- `"search project paths (text, kind, limit)"` → `search_project_paths(text, kind, limit?)` — `{ paths: [string], truncated }`, where `kind` is `file`, `folder`, or `any` (ASC-FR-AVVY).
- `"filter existing project paths (paths)"` → `existing_project_paths(paths)` — the subset of `paths` that the index holds, in input order (ASC-FR-QKXR).

Per `../ui/LCM-library-context-menu.md` (type curation) and `../ui/LIB-library.md` (rescan):
- `"assign artifact type (path, type, scope = file | folder)"` → `assign_artifact_type(path, artifact_type, scope)` — records a user type assignment for `path` into `.synthesis/library.toml`. `artifact_type ∈ { skill, agent, prompt, spec, flow, instructions, scenario, scratchpad, doc }`; `scope ∈ { file, folder }`. Returns the updated node (or subtree root) so the UI can re-tag without a full reload. Errors with a typed "no project open" when no project is open.
- `"clear artifact type assignment (path)"` → `clear_artifact_type(path)` — removes any stored assignment for `path`; on the next evaluation the node reverts to its inferred / inherited / unclassified state. No-op (not an error) if no assignment existed.
- `"rescan project tree"` → `rescan_project_tree()` — builds the project index again from a fresh recursive scan and returns the children of the project root, as `list_tree_children("")` returns them. Never throws on transient filesystem races.

### Events (Tauri event bus)
- `"project tree changed"` — emitted, debounced, when the watcher observes a create / delete / rename / move under the project root that affects the tree. Payload: `{ change_count, removed_paths, changed_folders }`, where `removed_paths` lists the project-relative paths that no longer exist once the coalesced burst is applied (ASC-FR-22), and `changed_folders` lists the folders whose children changed (ASC-FR-JYXO). The UI responds by reloading the children of the changed folders it holds (per `../ui/LIB-library.md` LIB-FR-10) and by closing the tabs the removed paths backed (per `../ui/TAB-tabs.md` TAB-FR-19); bursts within the debounce window coalesce into a single event.

### Internal (Rust API consumed by `PST-project-storage.md`, by `CHC-changes.md`, by `SCC-search.md`, by `BMI-bm25-indexing.md`, and by `DSL-dynamic-skills-loading.md`)
- recursive scan of the project root → the project index, an in-memory tree mirroring the on-disk folder structure (ASC-FR-HPUY);
- the classifier (path-convention recognizers + optional content-marker tiebreak + stored assignments);
- per-folder `has_artifacts` computation that drives empty-folder hiding in the UI;
- the scan's file-node set as an enumerable candidate list, which `SCC-search.md` matches against and `BMI-bm25-indexing.md` indexes (ASC-FR-17);
- the watcher's raw path channel, carrying every path the watcher observes whether or not the scan surfaces it, which `DSL-dynamic-skills-loading.md` filters for the folders it enumerates itself (ASC-FR-20).
- the **document assignments** of the active worktree — every `doc` assignment in `.synthesis/library.toml` with its path and scope — and the resolved type of one project-relative path under ASC-FR-06, both consumed by `DCL-documents-collection.md` (DCL-FR-DKXQ);
- the **attribution notice**, raised after every attribution write and after every change of `.synthesis/library.toml` the watcher observes, consumed by `DCL-documents-collection.md` (DCL-FR-RMVT).
- the **attribution write**, which records or removes a single type assignment in `.synthesis/library.toml` at file or folder scope. It is what `assign_artifact_type` and `clear_artifact_type` are built on, and it is the path `PST-project-storage.md` records a folder-scope assignment through when it creates a typed folder (PST-FR-24) and a file-scope assignment through when it creates a typed artifact (PST-FR-29), including the removal that a failed typed creation rolls back with (ASC-FR-24).

### Tree node shape
Returned by the tree reads and `rescan_project_tree`, and used by `assign_artifact_type`:
```
TreeNode {
  id,                         // stable key derived from the project-relative path (ASC-FR-13)
  name,                       // basename
  path,                       // project-relative path
  node_kind: "folder" | "file",
  artifact_type?,             // a file's resolved type, or a folder's own folder-scope
                              // assignment — one of the ten built-in types (ASC-FR-18)
  type_source?: "inferred" | "assigned" | "inherited",
  display_name?,              // the name the file declares for itself, for the artifacts
                              // whose filename does not identify them (ASC-FR-19)
  has_artifacts?,             // folders only: subtree contains >= 1 artifact (ASC-FR-08)
  subtree_types?: [type],     // folders only: the types present in the subtree (ASC-FR-OGRB)
  has_children?,              // folders only: the folder holds >= 1 node (ASC-FR-YSWU)
  nested_repo?: "submodule" | "repository" | "uninitialised",
                              // folders only (ASC-FR-YLGN)
  children?: [TreeNode]       // folders only, and only in a filter_project_tree result
}
```

## Functional requirements
1. **ASC-FR-01** A scan walks the project root recursively and produces a tree that mirrors the on-disk folder structure: every directory becomes a `folder` node and every surfaced file becomes a `file` node. The project root is the directory of the project's active worktree (per `WTC-worktree-context.md` WTC-FR-03), so the scan covers exactly one checkout and never descends into a sibling worktree of the same repository. The filesystem is the source of truth for tree structure; no node exists in the tree without a corresponding path on disk. A nested repository (ASC-FR-SFCR) is a folder of the tree like any other, and the scan descends into it.
2. **ASC-FR-02** The classifier recognises exactly the fixed built-in artifact-type set: `skill`, `agent`, `prompt`, `spec`, `flow`, `architecture`, `instructions`, `scenario`, `scratchpad`, `doc`. `flow` is the type the UI opens in the Flow tab (per `../ui/LIB-library.md` LIB-FR-03 and `../ui/FLO-flow.md`). `architecture` is a FINOS CALM architecture document that the Editor also shows as a diagram (per `../ui/CAD-calm-architecture-diagrams.md`). The set less `doc` matches the artifact subtypes of `../ui/SCH-search.md` SCH-FR-03. No other type is produced in v1.
3. **ASC-FR-QVCN** A file whose name ends `.calm.json`, matched without regard to letter case, is inferred as `architecture` wherever it sits, and this suffix rule outranks every folder convention of ASC-FR-03. No content marker produces `architecture`; any other JSON file reaches it only through an assignment (ASC-FR-05).
3. **ASC-FR-WOQW** The OpenSpec conventions are path conventions of ASC-FR-03. A file named `spec.md` below `openspec/specs/` is inferred as `spec`. A Markdown file below `openspec/changes/` and not below `openspec/changes/archive/` is inferred as `spec`. The file `openspec/config.yaml` is inferred as `instructions`. Each path is relative to the repository root of the file (ASC-FR-LXOQ).
3. **ASC-FR-YODA** No path convention gives a type to a file below `openspec/changes/archive/`. Such a file is an artifact only through an assignment (ASC-FR-05, ASC-FR-06).
3. **ASC-FR-NBNP** The OpenSpec conventions apply whatever the OpenSpec mode of the project is (per `OSM-openspec-mode.md` OSM-FR-UILN), as every other path convention of ASC-FR-03 applies without a setting.
3. **ASC-FR-JWPH** The `doc` type comes only from an assignment (ASC-FR-05). No path convention and no content marker produce it, and a frontmatter `type: doc` is not a marker. A file below a folder with a `doc` assignment resolves to `doc` at level (3) of ASC-FR-06, so a per-file assignment or an inferred type of another kind wins over it.
3. **ASC-FR-03** Type is inferred from path/location convention across multiple agent ecosystems — for example `.claude/skills/**` → `skill` and `.claude/agents/**` → `agent` (Claude Code), `.synthesis/skills/**` → `skill` (Synthesis), `AGENTS.md` → `agent` (Codex), `.github/**instructions**` → `instructions` (GitHub Copilot), `specifications/**` → `spec`, `**/*.flow` → `flow` (a Flow's contents are JSON but its name is not — `.json` is not the convention, and a file named `*.flow.json` reaches `flow` only through an explicit assignment), and `**/*.calm.json` → `architecture`. An inferred node carries `type_source = "inferred"`. The full recognizer table is the implementer's to complete from these representative mappings; the type set in ASC-FR-02 is fixed.
4. **ASC-FR-04** When path convention is ambiguous, the classifier MAY read a candidate text file's content (e.g. Markdown frontmatter `type:` or an equivalent marker) to confirm or assign a type, via `FSA-filesystem-access.md::read_text`. Path convention is the primary signal; the content read is a tiebreak, not a requirement for every file. The read covers at most the leading 64 KiB of the file (ASC-FR-HWQJ).
5. **ASC-FR-05** `assign_artifact_type(path, artifact_type, scope)` persists a user override into `.synthesis/library.toml` via `FSA-filesystem-access.md::write_toml_atomic`. `scope = file` tags exactly that file; `scope = folder` tags the folder's subtree as a default type for the files it contains.
6. **ASC-FR-06** Classification precedence, highest to lowest, is: (1) a per-file assignment, (2) path-convention inference (with the optional content tiebreak of ASC-FR-04), (3) the nearest ancestor folder-scope assignment, (4) unclassified. `type_source` on the node reports which level won: `assigned` for (1), `inferred` for (2), `inherited` for (3); an unclassified file carries no `artifact_type`.
7. **ASC-FR-07** `clear_artifact_type(path)` removes the stored assignment for `path` from `.synthesis/library.toml`; the node's type is recomputed by ASC-FR-06 on the next scan. Clearing a path with no stored assignment is a no-op, not an error.
8. **ASC-FR-08** A `file` node is an artifact iff it has a resolved `artifact_type` from any precedence level of ASC-FR-06. A `folder` node's `has_artifacts` is true iff its subtree contains at least one artifact node or the folder itself carries a folder-scope assignment. This flag is what `../ui/LIB-library.md` LIB-FR-09 uses to hide empty folders.
9. **ASC-FR-09** These exclusions govern the tree and everything derived from it, and not the watcher's raw path channel (ASC-FR-20), which reports an excluded path like any other for the consumers that have their own inclusion rules. Symbolic links are excluded on separate terms of their own (ASC-FR-23). The scan walks the whole project root but always skips the `.git` entry of every repository root (ASC-FR-SFCR), honours the ignore rules of the repository each path belongs to (ASC-FR-TWVB), skips `.synthesis/cache/` (gitignored per `PST-project-storage.md`  PST-FR-02), and skips `.synthesis/notes/` and `.synthesis/drafts/`, whose committed files are the module-owned storage of `NTC-notes-storage.md` (NTC-FR-16) and `DRS-draft-storage.md` (DRS-FR-04) and are never files a user curates in the Project panel. It also skips `.synthesis/comments/` and `.synthesis/statistics/`, the folders an earlier build committed conversation and statistics logs into and which `RMS-repository-machine-storage.md` imports from (RMS-FR-JVEC). The `.synthesis/library.toml` attribution file is never itself surfaced as an artifact node.
10. **ASC-FR-10** While a project is open, ASC maintains a recursive filesystem watcher on the project root. A create, delete, rename, or move under the root that affects the tree updates the project index and triggers a debounced `"project tree changed"` event carrying `{ change_count, removed_paths, changed_folders }`; multiple changes within the debounce window coalesce into a single event (per `../ui/LIB-library.md` LIB-FR-10).
11. **ASC-FR-RSGA** A watcher burst whose changed paths are all excluded by `.gitignore` on the terms of ASC-FR-09 triggers no re-evaluation and no `"project tree changed"` event. Of those paths, only the ones under the five special folders of `DSL-dynamic-skills-loading.md` DSL-FR-06 stay on the raw path channel (ASC-FR-20). Such a burst starts no pass of `BMI-bm25-indexing.md` (BMI-FR-GJLW) and none of `EMB-embeddings-index.md` (EMB-FR-HWRQ).
11. **ASC-FR-11** `rescan_project_tree()` builds the project index again from a full fresh scan and returns the children of the project root. It never throws on a transient filesystem race (e.g. a file deleted mid-walk): the affected path is skipped, not fatal.
12. **ASC-FR-12** Every read and write performed by this module goes through `FSA-filesystem-access.md` primitives (`read_text` for content tiebreak, `write_toml_atomic` for `.synthesis/library.toml`) and is subject to FSA's path-escape rejection (FSA-FR-10). This module writes nothing outside `.synthesis/`.
13. **ASC-FR-13** Each node's `id` is a stable key derived from its project-relative path, identical across every tree read of the contract surface, `rescan_project_tree`, and watcher-driven reloads. This is the identity `PST-project-storage.md` PST-FR-08 (`open_artifact_by_id`) resolves and the single-tab rule of `../ui/TAB-tabs.md` TAB-FR-04 compares.
14. **ASC-FR-14** Closing a project (per `PST-project-storage.md` PST-FR-14) tears down the watcher for that project; no `"project tree changed"` event fires after close, and no scan touches the closed project's files.
15. **ASC-FR-15** The same watcher additionally detects **content modifications** to existing files (distinct from the create/delete/rename/move structural changes of ASC-FR-10). A content edit that changes no answer of the tree reads does **not** trigger `"project tree changed"`. A content edit that changes the resolved type or the `display_name` of the file is a change of its parent folder (ASC-FR-JYXO). In both cases the modified path is surfaced on an internal channel consumed by `PST-project-storage.md` to drive its `"artifact changed externally"` event (PST-FR-16), by `CHC-changes.md` to drive its `"changes updated"` event (CHC-FR-16), by `BMI-bm25-indexing.md` to re-index that file (BMI-FR-16), and by `EMB-embeddings-index.md` to embed its changed chunks (EMB-FR-HWRQ). Closing a project tears down this detection together with the watcher (ASC-FR-14).
16. **ASC-FR-16** Changing the project's active worktree (per `WTC-worktree-context.md` WTC-FR-08) tears the watcher down on the outgoing content root exactly as ASC-FR-14 does and mounts a fresh one on the new root, discarding the previous root's scan state and cached classification rather than merging them. Stored attribution is re-read from the new root's `.synthesis/library.toml`, so type curation committed on one branch takes effect the moment a worktree on that branch becomes active. No `"project tree changed"` event fires for the outgoing root after the teardown.

17. **ASC-FR-17** The project index's `file` nodes are exposed internally as an enumerable candidate list — every file the scan surfaces, in a deterministic order, each carrying the node's `id`, project-relative path, and resolved classification. It is the file set `SCC-search.md` matches against (SCC-FR-03) and the set `BMI-bm25-indexing.md` draws its indexed files from (BMI-FR-03), so both inherit the exclusions of ASC-FR-09 rather than restating them. The list is kept current by the watcher (ASC-FR-10, ASC-FR-15) and is torn down with the scan on project close (ASC-FR-14) and on a worktree change (ASC-FR-16).

18. **ASC-FR-18** A `folder` node carrying a folder-scope assignment reports it on the node itself: `artifact_type` names the assigned type and `type_source` is `"assigned"`. A folder with no assignment of its own carries neither field, whatever its descendants resolve to — a folder-scope assignment is the only thing that types a folder, since no path convention infers a type onto a directory and no inheritance travels upward into one. This is what lets a folder be filtered and tagged by its own type rather than only by what it contains (`../ui/LIB-library.md` LIB-FR-09), and it is the field `create_folder` populates on the node it returns (`PST-project-storage.md` PST-FR-24).

19. **ASC-FR-19** A `file` node whose filename does not identify it carries the name the file declares for itself in `display_name`, read from its leading frontmatter through the same `FSA-filesystem-access.md::read_text` the content tiebreak uses. Today that is exactly a skill's `SKILL.md`: every skill in a project shares one filename, so the declared `name` is the only thing that tells two of them apart, and it is what `../ui/FLO-flow.md` FLO-FR-11 renders. A surface that has a path to show alongside the name — the Project panel's tree, where a skill sits under its own folder — is free to go on showing the filename. Every other node carries no `display_name`, which means "go by the basename"; so does a `SKILL.md` that declares no usable name or that cannot be read, since a scan never fails over a file's contents (ASC-FR-11). Only files that name themselves are opened for this — the scan does not read a project file by file to build its tree.

20. **ASC-FR-20** The watcher additionally surfaces, on an internal raw path channel, every path it observes a create, delete, rename, move, or content modification at — including paths the scan itself excludes under ASC-FR-09, and `.gitignore`d paths above all. What is filtered from it is the `.git` entry of every repository root (ASC-FR-SFCR), being the watcher's own churn rather than the project's, together with the `.synthesis/` subtrees that carry a dedicated channel of their own or that no consumer observes — `cache/`, `drafts/` (`DRS-draft-storage.md` DRS-FR-28, DRS-FR-42), `notes/`, `comments/`, and `statistics/`, whose logs are read by folding them on demand rather than by watching them (`DSS-draft-statistics-storage.md` DSS-FR-YOVS) — which this channel would otherwise report a second time. The channel carries paths alone and no contents, applies no classification, and drives no `"project tree changed"` event, so nothing that reads the tree observes it. It exists for the consumers that maintain their own file set rather than drawing on the scan's — today exactly `DSL-dynamic-skills-loading.md`, whose five special folders a project may legitimately gitignore (DSL-FR-06, DSL-FR-19) and which would otherwise have no way to learn that one of them changed. The channel is mounted, torn down, and remounted with the watcher itself (ASC-FR-14, ASC-FR-16).

21. **ASC-FR-21** Every structural change the watcher observes — each file or folder created, deleted, renamed, or moved under the project root — produces one `INFO` record through `LGC-logging.md`'s internal API under the `backend` domain, naming the affected project-relative path and which of those four things happened to it. The record is per change rather than per emitted event: a burst that coalesces into a single `"project tree changed"` (ASC-FR-10) still accounts for each path it carried, so the log explains what the Project panel refreshed for rather than only that it refreshed. A content modification (ASC-FR-15) produces no record here, changing no tree shape and prompting no refresh. Records name paths alone and never any part of a file's contents.

22. **ASC-FR-22** `removed_paths` on the `"project tree changed"` payload lists, in the coalesced burst the event reports, every project-relative path that existed in the tree before the burst and does not exist after it. A deleted folder contributes its own path; the paths beneath it need not be enumerated, since a consumer treats a removed folder as removing everything under it (per `../ui/TAB-tabs.md` TAB-FR-19). The source side of a rename or a move is a removed path like any other, because the path itself is gone whatever took its place; nothing correlates it with the destination that appeared in the same burst. A path created and removed inside one burst appears in neither the tree nor `removed_paths`, and a burst that removed nothing carries an empty list rather than omitting the field.

23. **ASC-FR-23** The scan never follows a symbolic link and never surfaces a node for one. A symbolically-linked directory is not descended into and contributes nothing to the tree; a symbolically-linked file yields no `file` node however its path would classify. The link's own path is therefore absent from the tree, from the candidate list of ASC-FR-17, and from every `has_artifacts` computation, exactly as an excluded path of ASC-FR-09 is, and the decision is made from the link alone without ever resolving where it points — so a link into the project root is skipped exactly as a link out of it is. This is what keeps the tree a set of paths `PST-project-storage.md` can act on, since that module refuses every symlinked path it is handed (PST-FR-27). The watcher's raw path channel (ASC-FR-20) is unaffected and reports a symlinked path like any other, being the stream of what the watcher saw rather than of what the scan admits.
24. **ASC-FR-24** A type assignment is recorded in exactly one way, whichever surface asked for it: through this module's attribution write into `.synthesis/library.toml` (ASC-FR-05). `assign_artifact_type` is that write reached as a Tauri command; the typed-artifact creation of `PST-project-storage.md` PST-FR-29 is that same write reached internally, at `scope = file`, for the file it has just created, so a file created with a type and a file typed afterwards from the Project context menu (`../ui/LCM-library-context-menu.md` LCM-FR-04) end in the identical stored assignment and resolve identically under ASC-FR-06. Because the assignment and the file are one transaction there, this module also provides the reverse: an assignment recorded for a creation that then fails is removed again, so `.synthesis/library.toml` never holds an assignment for a path the project does not have. An assignment for a path that nonetheless goes missing is inert rather than an error — it is retained, it surfaces as nothing, and it applies again if that path returns — so no scan is failed by one and no repair pass exists to run.
25. **ASC-FR-REKM** The scan, the classification, and the watcher are held per open project. Every command of this module takes `project_id`. The `"project tree changed"` event carries `project_id` and goes to the window of that project only (`PWN-project-windows.md` PWN-FR-AINZ). A project tab that is not in front keeps its watcher running.

26. **ASC-FR-HPUY** The **project index** is the tree of ASC-FR-01 with its classification, held in memory per open project. It is built from one scan when the project opens, when the active worktree changes (ASC-FR-16), and on `rescan_project_tree`. Every tree read, the candidate list (ASC-FR-17), and every internal consumer of the tree read the index and walk no folder of the disk.
27. **ASC-FR-TPJO** No command of this module runs on the main thread, and the index build runs on background threads. A command that arrives while the index builds waits for the build to end, and then answers from the new index. The build reports its progress per `PRG-progress-reporting.md` PRG-FR-11.
28. **ASC-FR-UWMI** A watcher burst updates the project index for the paths of the burst alone, and walks only a folder that the burst created or moved in. A burst that the index cannot apply builds the index again, as `rescan_project_tree` does.
29. **ASC-FR-KVIE** `list_tree_children(path)` returns each direct child of the folder once, in the order the tree gives its children: folders first, then files, each group by name. The answer holds every child, whatever the lens of the caller, and its size grows with the number of children, not with the size of the project.
30. **ASC-FR-AGGG** `list_tree_path(path)` returns, for the project root and for each ancestor folder of `path`, the answer `list_tree_children` gives for that folder. A folder `path` also gets its own entry. The result holds enough to show `path` with every ancestor expanded.
31. **ASC-FR-SKRN** `filter_project_tree(text, lens, limit)` returns each node whose name holds `text` without regard to letter case and that `lens` admits, on the terms of `../ui/LIB-library.md` LIB-FR-05 and LIB-FR-09, with every ancestor folder of it. At most `limit` matches are returned, in tree order, and `truncated` is true when more exist.
32. **ASC-FR-YNJR** `list_project_artifacts()` returns every file node with a resolved `artifact_type` and every folder node with a folder-scope assignment (ASC-FR-18), each with its `id`, `path`, `artifact_type`, `type_source`, and `display_name`.
33. **ASC-FR-AVVY** `search_project_paths(text, kind, limit)` returns the project-relative path of each node of `kind` whose path holds `text` without regard to letter case, in tree order. An empty `text` matches every node. With no `limit`, every match is returned; with a `limit`, at most that many, and `truncated` is true when more exist.
34. **ASC-FR-QKXR** `existing_project_paths(paths)` returns each path of `paths` that the project index holds as a file or a folder, in input order. A path that the index does not hold is left out and is not an error.
35. **ASC-FR-OGRB** A `folder` node carries `subtree_types`: each artifact type that a file of its subtree resolves to, or that the folder or a folder of its subtree carries as a folder-scope assignment. Each type is listed once. A folder with `has_artifacts` false carries an empty list.
36. **ASC-FR-YSWU** A `folder` node carries `has_children`, true when the folder holds at least one file or folder node, whatever the lens.
37. **ASC-FR-JYXO** `changed_folders` lists, in the coalesced burst, each folder whose `list_tree_children` answer is different after the burst: a child came or went, or a child's `artifact_type`, `type_source`, `display_name`, `has_artifacts`, `subtree_types`, `has_children`, or `nested_repo` changed. The project root is `""`. A burst that changes no such answer fires no `"project tree changed"`.
38. **ASC-FR-HWQJ** A content read of the classifier (ASC-FR-04, ASC-FR-19) reads at most the leading 64 KiB of a file. Frontmatter that does not end inside those bytes is absent for the classifier, and the file resolves as if it had none.
    - *Why:* a monorepo holds many large Markdown files, and a frontmatter block is always at the start of a file.
39. **ASC-FR-SFCR** A **nested repository root** is a folder below the project root that holds a `.git` entry, a file or a folder. The `.git` entry of the project root and of every nested repository root is skipped by the scan, by the watcher's raw path channel (ASC-FR-20), and by everything derived from the tree.
40. **ASC-FR-TWVB** The ignore rules of a path are the rules of its nearest repository root: the `.gitignore` files from that root down to the path, and the `info/exclude` file of the git directory that the root's `.git` entry names, through its `gitdir:` line for a file. The rules of an enclosing repository do not apply below a nested repository root.
    - *Why:* git applies no rule of the parent repository inside a submodule, so a parent rule such as `build/` must not hide a file that the submodule tracks.
41. **ASC-FR-LXOQ** Each path convention of ASC-FR-03 matches the path relative to the nearest repository root of the file, so `vendor/lib/specifications/X.md` in the nested repository `vendor/lib` is inferred as `spec`. The paths of `.synthesis/library.toml` (ASC-FR-05) stay relative to the project root.
42. **ASC-FR-YLGN** A folder carries `nested_repo` when it is a repository boundary. It is `submodule` for a nested repository root whose path the `.gitmodules` file of the enclosing repository lists. It is `repository` for any other nested repository root. It is `uninitialised` for a folder that `.gitmodules` lists and that holds no `.git` entry.

## Non-functional requirements
- The index build walks the tree with parallel workers, one walk per repository root. A project of 200 000 files builds its index in seconds, and the window responds to input during the build.
- The answer of a tree read grows with the folder or the matches it returns, not with the size of the project. A burst of the watcher costs work in proportion to its paths, not to the project.
- The watcher is async / event-driven and therefore lives in this module, deliberately not in `FSA-filesystem-access.md`, whose non-functional contract is synchronous, caller-owned concurrency only.
- `.synthesis/library.toml` is plain, committed, diffable TOML mapping project-relative path → `{ artifact_type, scope }`. It is shareable across a team so type curation is not per-machine.
- The debounce window is an implementation choice (order of a few hundred milliseconds); the contract is only that bursts coalesce and the UI is not flooded.
- The raw path channel of ASC-FR-20 is the watcher's own event stream with only the `.git` entries of the repository roots filtered out of it. It carries no contents and performs no read, so a consumer with a narrow inclusion rule pays a path comparison per event rather than a walk.
