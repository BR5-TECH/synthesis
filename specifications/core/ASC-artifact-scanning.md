# Artifact scanning

**Spec code:** `ASC`

## Intent
The backend engine that makes the Project panel real: it treats the project's filesystem as the source of truth, walks the project root recursively, and classifies every file it finds into one of the fixed built-in artifact types (Skill, Agent, Prompt, Spec, Flow, Instructions, Scenario, Scratchpad). Classification combines multi-ecosystem path inference (different agents — Claude Code, GitHub Copilot, Codex — keep Skills and Agents under different paths) with user-authored overrides that may tag a single file or a whole folder. Attribution overrides persist inside `.synthesis/` so they are shareable and survive relaunch, while the displayed tree always mirrors what is actually on disk. Nothing is reached through a symbolic link — links are skipped rather than resolved — so every node in the tree names a real path under the root. A recursive filesystem watcher keeps the Project panel live: externally created, deleted, moved, or renamed files produce a debounced "project tree changed" event the UI reacts to, carrying the paths that disappeared so the surfaces holding them can let them go, and each change it observes is accounted for in the session log. Out of scope for v1: third-party (plugin-supplied) recognizers and user-defined artifact types; the built-in type set and recognizers are fixed, and the command surface is forward-stable so a later plugin category may add recognizers without renaming anything.

## Contract surface
This module composes the `FSA-filesystem-access.md` primitives into a higher-level scan/classify/watch surface. The tree-read command (`load_project_tree`) is owned by `PST-project-storage.md` and is backed by this module's scan; the mutation, rescan, and watch operations below are owned here. Quoted names are the canonical operation names as they appear in the owning UI spec's "Delegated to backend (abstract)" line and MUST match byte-for-byte: the type-curation commands in `../ui/LCM-library-context-menu.md`, and rescan in `../ui/LIB-library.md`.

### UI-facing (Tauri commands)
Per `../ui/LCM-library-context-menu.md` (type curation) and `../ui/LIB-library.md` (rescan):
- `"assign artifact type (path, type, scope = file | folder)"` → `assign_artifact_type(path, artifact_type, scope)` — records a user type assignment for `path` into `.synthesis/library.toml`. `artifact_type ∈ { skill, agent, prompt, spec, flow, instructions, scenario, scratchpad }`; `scope ∈ { file, folder }`. Returns the updated node (or subtree root) so the UI can re-tag without a full reload. Errors with a typed "no project open" when no project is open.
- `"clear artifact type assignment (path)"` → `clear_artifact_type(path)` — removes any stored assignment for `path`; on the next evaluation the node reverts to its inferred / inherited / unclassified state. No-op (not an error) if no assignment existed.
- `"rescan project tree"` → `rescan_project_tree()` — forces a fresh recursive scan and reclassification and returns the current tree in the same node shape `load_project_tree` returns. Never throws on transient filesystem races.

### Events (Tauri event bus)
- `"project tree changed"` — emitted, debounced, when the watcher observes a create / delete / rename / move under the project root that affects the tree. Payload: `{ change_count, removed_paths }`, where `removed_paths` lists the project-relative paths that no longer exist once the coalesced burst is applied (ASC-FR-22). The UI responds by reloading the tree (per `../ui/LIB-library.md` LIB-FR-10) and by closing the tabs the removed paths backed (per `../ui/TAB-tabs.md` TAB-FR-19); bursts within the debounce window coalesce into a single event.

### Internal (Rust API consumed by `PST-project-storage.md::load_project_tree`, by `CHC-changes.md`, by `SCC-search.md`, by `BMI-bm25-indexing.md`, and by `DSL-dynamic-skills-loading.md`)
- recursive scan of the project root → an in-memory tree mirroring the on-disk folder structure;
- the classifier (path-convention recognizers + optional content-marker tiebreak + stored assignments);
- per-folder `has_artifacts` computation that drives empty-folder hiding in the UI;
- the scan's file-node set as an enumerable candidate list, which `SCC-search.md` matches against and `BMI-bm25-indexing.md` indexes (ASC-FR-17);
- the watcher's raw path channel, carrying every path the watcher observes whether or not the scan surfaces it, which `DSL-dynamic-skills-loading.md` filters for the folders it enumerates itself (ASC-FR-20).
- the **attribution write**, which records or removes a single type assignment in `.synthesis/library.toml` at file or folder scope. It is what `assign_artifact_type` and `clear_artifact_type` are built on, and it is the path `PST-project-storage.md` records a folder-scope assignment through when it creates a typed folder (PST-FR-24) and a file-scope assignment through when it creates a typed artifact (PST-FR-29), including the removal that a failed typed creation rolls back with (ASC-FR-24).

### Tree node shape
Returned by `load_project_tree` / `rescan_project_tree` and used by `assign_artifact_type`:
```
TreeNode {
  id,                         // stable key derived from the project-relative path (ASC-FR-13)
  name,                       // basename
  path,                       // project-relative path
  node_kind: "folder" | "file",
  artifact_type?,             // a file's resolved type, or a folder's own folder-scope
                              // assignment — one of the eight built-in types (ASC-FR-18)
  type_source?: "inferred" | "assigned" | "inherited",
  display_name?,              // the name the file declares for itself, for the artifacts
                              // whose filename does not identify them (ASC-FR-19)
  has_artifacts?,             // folders only: subtree contains >= 1 artifact (ASC-FR-08)
  children?: [TreeNode]       // folders only
}
```

## Functional requirements
1. **ASC-FR-01** A scan walks the project root recursively and produces a tree that mirrors the on-disk folder structure: every directory becomes a `folder` node and every surfaced file becomes a `file` node. The project root is the directory of the project's active worktree (per `WTC-worktree-context.md` WTC-FR-03), so the scan covers exactly one checkout and never descends into a sibling worktree of the same repository. The filesystem is the source of truth for tree structure; no node exists in the tree without a corresponding path on disk.
2. **ASC-FR-02** The classifier recognises exactly the fixed built-in artifact-type set: `skill`, `agent`, `prompt`, `spec`, `flow`, `instructions`, `scenario`, `scratchpad`. `flow` is the type the UI opens in the Flow tab (per `../ui/LIB-library.md` LIB-FR-03 and `../ui/FLO-flow.md`); the set matches the artifact subtypes used by `../ui/EDT-editor.md` EDT-FR-03 and `../ui/SCH-search.md` SCH-FR-03. No other type is produced in v1.
3. **ASC-FR-03** Type is inferred from path/location convention across multiple agent ecosystems — for example `.claude/skills/**` → `skill` and `.claude/agents/**` → `agent` (Claude Code), `AGENTS.md` → `agent` (Codex), `.github/**instructions**` → `instructions` (GitHub Copilot), `specifications/**` → `spec`, `**/*.flow` → `flow` (a Flow's contents are JSON but its name is not — `.json` is not the convention, and a file named `*.flow.json` reaches `flow` only through an explicit assignment). An inferred node carries `type_source = "inferred"`. The full recognizer table is the implementer's to complete from these representative mappings; the type set in ASC-FR-02 is fixed.
4. **ASC-FR-04** When path convention is ambiguous, the classifier MAY read a candidate text file's content (e.g. Markdown frontmatter `type:` or an equivalent marker) to confirm or assign a type, via `FSA-filesystem-access.md::read_text`. Path convention is the primary signal; the content read is a tiebreak, not a requirement for every file.
5. **ASC-FR-05** `assign_artifact_type(path, artifact_type, scope)` persists a user override into `.synthesis/library.toml` via `FSA-filesystem-access.md::write_toml_atomic`. `scope = file` tags exactly that file; `scope = folder` tags the folder's subtree as a default type for the files it contains.
6. **ASC-FR-06** Classification precedence, highest to lowest, is: (1) a per-file assignment, (2) path-convention inference (with the optional content tiebreak of ASC-FR-04), (3) the nearest ancestor folder-scope assignment, (4) unclassified. `type_source` on the node reports which level won: `assigned` for (1), `inferred` for (2), `inherited` for (3); an unclassified file carries no `artifact_type`.
7. **ASC-FR-07** `clear_artifact_type(path)` removes the stored assignment for `path` from `.synthesis/library.toml`; the node's type is recomputed by ASC-FR-06 on the next scan. Clearing a path with no stored assignment is a no-op, not an error.
8. **ASC-FR-08** A `file` node is an artifact iff it has a resolved `artifact_type` from any precedence level of ASC-FR-06. A `folder` node's `has_artifacts` is true iff its subtree contains at least one artifact node or the folder itself carries a folder-scope assignment. This flag is what `../ui/LIB-library.md` LIB-FR-09 uses to hide empty folders.
9. **ASC-FR-09** These exclusions govern the tree and everything derived from it, and not the watcher's raw path channel (ASC-FR-20), which reports an excluded path like any other for the consumers that have their own inclusion rules. Symbolic links are excluded on separate terms of their own (ASC-FR-23). The scan walks the whole project root but always skips `.git/`, honours the repository's `.gitignore`, skips `.synthesis/cache/` (gitignored per `PST-project-storage.md`  PST-FR-02), and skips `.synthesis/notes/` and `.synthesis/drafts/`, whose committed files are the module-owned storage of `NTC-notes-storage.md` (NTC-FR-16) and `DRS-draft-storage.md` (DRS-FR-04) and are never files a user curates in the Project panel. It also skips `.synthesis/comments/` and `.synthesis/statistics/`, the folders an earlier build committed conversation and statistics logs into and which `RMS-repository-machine-storage.md` imports from (RMS-FR-JVEC). The `.synthesis/library.toml` attribution file is never itself surfaced as an artifact node.
10. **ASC-FR-10** While a project is open, ASC maintains a recursive filesystem watcher on the project root. A create, delete, rename, or move under the root that affects the tree triggers re-evaluation and a debounced `"project tree changed"` event carrying `{ change_count, removed_paths }`; multiple changes within the debounce window coalesce into a single event (per `../ui/LIB-library.md` LIB-FR-10).
11. **ASC-FR-11** `rescan_project_tree()` performs a full fresh scan and returns the current tree. It never throws on a transient filesystem race (e.g. a file deleted mid-walk): the affected path is skipped, not fatal.
12. **ASC-FR-12** Every read and write performed by this module goes through `FSA-filesystem-access.md` primitives (`read_text` for content tiebreak, `write_toml_atomic` for `.synthesis/library.toml`) and is subject to FSA's path-escape rejection (FSA-FR-10). This module writes nothing outside `.synthesis/`.
13. **ASC-FR-13** Each node's `id` is a stable key derived from its project-relative path, identical across `load_project_tree`, `rescan_project_tree`, and watcher-driven reloads. This is the identity `PST-project-storage.md` PST-FR-08 (`open_artifact_by_id`) resolves and the single-tab rule of `../ui/TAB-tabs.md` TAB-FR-04 compares.
14. **ASC-FR-14** Closing a project (per `PST-project-storage.md` PST-FR-14) tears down the watcher for that project; no `"project tree changed"` event fires after close, and no scan touches the closed project's files.
15. **ASC-FR-15** The same watcher additionally detects **content modifications** to existing files (distinct from the create/delete/rename/move structural changes of ASC-FR-10). Because a content edit does not change tree shape, it does **not** trigger `"project tree changed"`; instead the modified path is surfaced on an internal channel consumed by `PST-project-storage.md` to drive its `"artifact changed externally"` event (PST-FR-16), by `CHC-changes.md` to drive its `"changes updated"` event (CHC-FR-16), and by `BMI-bm25-indexing.md` to re-index that file (BMI-FR-16). Closing a project tears down this detection together with the watcher (ASC-FR-14).
16. **ASC-FR-16** Changing the project's active worktree (per `WTC-worktree-context.md` WTC-FR-08) tears the watcher down on the outgoing content root exactly as ASC-FR-14 does and mounts a fresh one on the new root, discarding the previous root's scan state and cached classification rather than merging them. Stored attribution is re-read from the new root's `.synthesis/library.toml`, so type curation committed on one branch takes effect the moment a worktree on that branch becomes active. No `"project tree changed"` event fires for the outgoing root after the teardown.

17. **ASC-FR-17** The scan's `file` nodes are exposed internally as an enumerable candidate list — every file the scan surfaces, in a deterministic order, each carrying the node's `id`, project-relative path, and resolved classification. It is the file set `SCC-search.md` matches against (SCC-FR-03) and the set `BMI-bm25-indexing.md` draws its indexed files from (BMI-FR-03), so both inherit the exclusions of ASC-FR-09 rather than restating them. The list is kept current by the watcher (ASC-FR-10, ASC-FR-15) and is torn down with the scan on project close (ASC-FR-14) and on a worktree change (ASC-FR-16).

18. **ASC-FR-18** A `folder` node carrying a folder-scope assignment reports it on the node itself: `artifact_type` names the assigned type and `type_source` is `"assigned"`. A folder with no assignment of its own carries neither field, whatever its descendants resolve to — a folder-scope assignment is the only thing that types a folder, since no path convention infers a type onto a directory and no inheritance travels upward into one. This is what lets a folder be filtered and tagged by its own type rather than only by what it contains (`../ui/LIB-library.md` LIB-FR-09), and it is the field `create_folder` populates on the node it returns (`PST-project-storage.md` PST-FR-24).

19. **ASC-FR-19** A `file` node whose filename does not identify it carries the name the file declares for itself in `display_name`, read from its leading frontmatter through the same `FSA-filesystem-access.md::read_text` the content tiebreak uses. Today that is exactly a skill's `SKILL.md`: every skill in a project shares one filename, so the declared `name` is the only thing that tells two of them apart, and it is what `../ui/FLO-flow.md` FLO-FR-11 renders. A surface that has a path to show alongside the name — the Project panel's tree, where a skill sits under its own folder — is free to go on showing the filename. Every other node carries no `display_name`, which means "go by the basename"; so does a `SKILL.md` that declares no usable name or that cannot be read, since a scan never fails over a file's contents (ASC-FR-11). Only files that name themselves are opened for this — the scan does not read a project file by file to build its tree.

20. **ASC-FR-20** The watcher additionally surfaces, on an internal raw path channel, every path it observes a create, delete, rename, move, or content modification at — including paths the scan itself excludes under ASC-FR-09, and `.gitignore`d paths above all. What is filtered from it is `.git/`, being the watcher's own churn rather than the project's, together with the `.synthesis/` subtrees that carry a dedicated channel of their own or that no consumer observes — `cache/`, `drafts/` (`DRS-draft-storage.md` DRS-FR-28, DRS-FR-42), `notes/`, `comments/`, and `statistics/`, whose logs are read by folding them on demand rather than by watching them (`DSS-draft-statistics-storage.md` DSS-FR-YOVS) — which this channel would otherwise report a second time. The channel carries paths alone and no contents, applies no classification, and drives no `"project tree changed"` event, so nothing that reads the tree observes it. It exists for the consumers that maintain their own file set rather than drawing on the scan's — today exactly `DSL-dynamic-skills-loading.md`, whose four skill folders a project may legitimately gitignore (DSL-FR-06, DSL-FR-19) and which would otherwise have no way to learn that one of them changed. The channel is mounted, torn down, and remounted with the watcher itself (ASC-FR-14, ASC-FR-16).

21. **ASC-FR-21** Every structural change the watcher observes — each file or folder created, deleted, renamed, or moved under the project root — produces one `INFO` record through `LGC-logging.md`'s internal API under the `backend` domain, naming the affected project-relative path and which of those four things happened to it. The record is per change rather than per emitted event: a burst that coalesces into a single `"project tree changed"` (ASC-FR-10) still accounts for each path it carried, so the log explains what the Project panel refreshed for rather than only that it refreshed. A content modification (ASC-FR-15) produces no record here, changing no tree shape and prompting no refresh. Records name paths alone and never any part of a file's contents.

22. **ASC-FR-22** `removed_paths` on the `"project tree changed"` payload lists, in the coalesced burst the event reports, every project-relative path that existed in the tree before the burst and does not exist after it. A deleted folder contributes its own path; the paths beneath it need not be enumerated, since a consumer treats a removed folder as removing everything under it (per `../ui/TAB-tabs.md` TAB-FR-19). The source side of a rename or a move is a removed path like any other, because the path itself is gone whatever took its place; nothing correlates it with the destination that appeared in the same burst. A path created and removed inside one burst appears in neither the tree nor `removed_paths`, and a burst that removed nothing carries an empty list rather than omitting the field.

23. **ASC-FR-23** The scan never follows a symbolic link and never surfaces a node for one. A symbolically-linked directory is not descended into and contributes nothing to the tree; a symbolically-linked file yields no `file` node however its path would classify. The link's own path is therefore absent from the tree, from the candidate list of ASC-FR-17, and from every `has_artifacts` computation, exactly as an excluded path of ASC-FR-09 is, and the decision is made from the link alone without ever resolving where it points — so a link into the project root is skipped exactly as a link out of it is. This is what keeps the tree a set of paths `PST-project-storage.md` can act on, since that module refuses every symlinked path it is handed (PST-FR-27). The watcher's raw path channel (ASC-FR-20) is unaffected and reports a symlinked path like any other, being the stream of what the watcher saw rather than of what the scan admits.
24. **ASC-FR-24** A type assignment is recorded in exactly one way, whichever surface asked for it: through this module's attribution write into `.synthesis/library.toml` (ASC-FR-05). `assign_artifact_type` is that write reached as a Tauri command; the typed-artifact creation of `PST-project-storage.md` PST-FR-29 is that same write reached internally, at `scope = file`, for the file it has just created, so a file created with a type and a file typed afterwards from the Project context menu (`../ui/LCM-library-context-menu.md` LCM-FR-04) end in the identical stored assignment and resolve identically under ASC-FR-06. Because the assignment and the file are one transaction there, this module also provides the reverse: an assignment recorded for a creation that then fails is removed again, so `.synthesis/library.toml` never holds an assignment for a path the project does not have. An assignment for a path that nonetheless goes missing is inert rather than an error — it is retained, it surfaces as nothing, and it applies again if that path returns — so no scan is failed by one and no repair pass exists to run.

## Non-functional requirements
- The scan is incremental/streaming for large trees; a large subtree must not block the Project panel (matches `../ui/LIB-library.md` and `PST-project-storage.md` incremental-render requirements).
- The watcher is async / event-driven and therefore lives in this module, deliberately not in `FSA-filesystem-access.md`, whose non-functional contract is synchronous, caller-owned concurrency only.
- `.synthesis/library.toml` is plain, committed, diffable TOML mapping project-relative path → `{ artifact_type, scope }`. It is shareable across a team so type curation is not per-machine.
- The debounce window is an implementation choice (order of a few hundred milliseconds); the contract is only that bursts coalesce and the UI is not flooded.
- The raw path channel of ASC-FR-20 is the watcher's own event stream with only `.git/` filtered out of it. It carries no contents and performs no read, so a consumer with a narrow inclusion rule pays a path comparison per event rather than a walk.
