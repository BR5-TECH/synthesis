# BM25 indexing

**Spec code:** `BMI`

## Intent
The project's ranked-retrieval substrate: a set of in-memory BM25 indexes — one per artifact type, one for drafts, one for the notes the author has written down, one for the skills an agent may invoke, and one for the reference documents the user selected — kept continuously in agreement with what is on disk. It exists so that an AI integration asking "which specs and skills bear on worktree teardown?" gets a short list of the most relevant passages instead of a whole-project text sweep — a question of relevance rather than of matching, which the universal search bar's engine (`SCC-search.md`) deliberately does not answer. Indexing is invisible infrastructure: it runs on project open and on every filesystem change thereafter, reports itself through the status bar and the session log, and needs no decision from the user. Out of scope: the universal search bar and everything it renders, which keeps its own index-free engine unchanged; any user-facing control — there is no setting, no toggle, and no manual rebuild; any persistence, since an index is rebuilt from disk rather than stored; and the AI integrations that will consume this, which choose their own queries and are specified elsewhere.

## Contract surface

### Internal Rust API
The whole surface of this module. Exposed by `synthesis-core` alongside `FSA-filesystem-access.md`'s primitives and `LGC-logging.md`'s emit functions, and imported directly by the backend modules that retrieve against it. This module registers no Tauri command and emits no Tauri event, so no `invoke()` in `src/**` can reach it.

- **`search(indexes, query, limit)`** → `[ChunkHit]` *(consumed by `../tools/SPS-specification-search-tool.md`, `../tools/DST-draft-search-tool.md`, `../tools/NST-note-search-tool.md`, and `../tools/SDT-search-documents-tool.md`)* — the `limit` highest-scoring chunks across the selected indexes, ordered by descending `score`. Returns a list and never an error (BMI-FR-10). Reads nothing from disk and mutates nothing.

### Payload shapes
```
IndexId =
    "skill" | "agent" | "prompt" | "spec"        // the eight built-in artifact
  | "flow" | "instructions" | "scenario"          // types of ASC-FR-02
  | "scratchpad"
  | "drafts"                                      // every draft of the active worktree
  | "notes"                                       // one body per persisted note
                                                  // (NTC-notes-storage.md)
  | "skills"                                      // one descriptor per invocable skill
                                                  // (DSL-dynamic-skills-loading.md)
  | "documents"                                   // the text of every available document of the
                                                  // Documents collection (DCL-documents-collection.md)

ChunkHit {
  index,           // the IndexId this chunk was found in
  path,            // project-relative for the eight artifact indexes and for the
                   // skills index; draft-relative for the drafts index; the note's
                   // own file for the notes index; the document id for the documents
                   // index, which holds no filesystem path
  node_id?,        // artifact indexes only: the ASC node id (ASC-FR-13)
  draft_id?,       // drafts index only: the draft's id (DRS-FR-02)
  note_id?,        // notes index only: the note's id (NTC-FR-02)
  document_id?,    // documents index only: the document's id (DCL-FR-QKJO)
  chunk_ordinal,   // 0-based position of this chunk within its file; always 0 in
                   // the skills and notes indexes, where a skill's descriptor and
                   // a note's body are each one whole document
  score,           // BM25 score against its own corpus's statistics (BMI-FR-11)
  text             // the chunk's text
}
```

`indexes` is a set of `IndexId`; an empty set selects every index. `query` is free text. `limit` bounds the returned list.

## Functional requirements
1. **BMI-FR-01** `search` exists as an internal Rust API with the documented shape. This module registers no Tauri command, emits no Tauri event, and exposes nothing the frontend can invoke, so every observable effect it has on the user is the progress it reports (BMI-FR-21) and the records it logs (BMI-FR-22).
2. **BMI-FR-02** There are exactly twelve indexes: one for each of the eight built-in artifact types of `ASC-artifact-scanning.md` ASC-FR-02, one for drafts, one for notes, one for skills, and one for documents. The nine artifact and draft indexes hold the chunks of the files that belong to them (BMI-FR-03, BMI-FR-04); the `notes` index holds instead one document per persisted note, supplied whole by `NTC-notes-storage.md` (NTC-FR-24), and the `skills` index one document per invocable skill, supplied whole by `DSL-dynamic-skills-loading.md` (DSL-FR-13), each of those two modules being the only thing that decides what belongs to its index (BMI-FR-28). The `documents` index holds the chunks of the text that `DCL-documents-collection.md` supplies (BMI-FR-WBKZ). No index's statistics are influenced by the contents of another. Within an index, a chunk is scored against the corpus of files sharing its language (BMI-FR-08): each index holds one BM25 corpus — its own document count, term frequencies, and average document length — for each language actually present in it, and a query runs against every one of them. A corpus exists only while it holds a chunk, so an index whose files are all of one language holds exactly one.
3. **BMI-FR-03** A file belongs to an artifact index when the project scan surfaces it (`ASC-artifact-scanning.md` ASC-FR-17) and its resolved `artifact_type` (ASC-FR-06) names that index — whichever precedence level resolved it. A file the scan surfaces with no resolved type is indexed nowhere, so unclassified source files, playbooks, workstreams, and roles that carry no artifact type contribute no chunks. A file therefore belongs to at most one artifact index.
4. **BMI-FR-04** The drafts index holds one file per draft of the active worktree: that draft's **current live prompt**, at the `prompt_path` of `DRS-draft-storage.md` DRS-FR-01. A draft holds exactly one file and nothing else (DRS-FR-11), so there is never a second file of a draft to index and never a choice about which of its files the index means. Membership is independent of status: every status a draft may hold is indexed on identical terms, an archived draft exactly as an active one (DRS-FR-10), and a status draft storage later retains enters the index without a change here. The rest of a draft's folder is indexed nowhere — no accepted history entry or its snapshot payload (`DHS-draft-history.md` DHS-FR-01), no proposal record or candidate (`DCP-draft-change-proposals.md` DCP-FR-01), no comment log, no attachment, and no conversation log — so a passage a live prompt no longer holds is a passage no query can reach, and the only version of a draft any index carries is the one the author is working in now. A draft whose `files/` is not that single prompt contributes nothing rather than having one of its files chosen on the author's behalf. Draft files reach no artifact index, because the scan does not surface them (ASC-FR-09), and the drafts index holds nothing but live draft prompts.
5. **BMI-FR-05** In the nine file-backed indexes an indexed file is split into chunks, and a chunk is the indexed document; the `documents` index splits the text of each document on the same rules (BMI-FR-FGGU); the `skills` and `notes` indexes are not split at all, because a skill's descriptor and a note's body are each already one whole document and neither has sections to cut at (BMI-FR-02, BMI-FR-28). In a Markdown file a chunk runs from one heading to the next heading of any level, so headings never nest one chunk inside another; the content preceding the first heading is a chunk of its own when it holds anything but whitespace.
6. **BMI-FR-06** Every chunk is bounded. A file with no heading structure — a heading-less note, a `.flow`'s JSON, any non-Markdown text — is split into size-bounded blocks cut at blank lines, and a heading section that exceeds the same ceiling is split further on the same rule. No file is ever indexed as a single unbounded document, however large it is.
7. **BMI-FR-07** `chunk_ordinal` is a chunk's 0-based position within its own file in file order, so the chunks of one file are addressable and orderable without re-reading it.
8. **BMI-FR-08** Language is detected once over the whole of an indexed document's source text — a file's text for the nine file-backed indexes, a skill's descriptor for the `skills` index, a note's body for the `notes` index, a document's text for the `documents` index — and that language governs the tokenisation and stemming of every chunk of it — a short heading-only chunk is therefore stemmed as the document it came from rather than guessed at on its own few words. A file whose language cannot be determined, or whose language has no stemmer available, is indexed with English stemming. Every chunk is stemmed; none is indexed raw. Stemming is what makes a language's own corpus the only one that can answer a query in it: a term stemmed by one language's rules matches nothing stemmed by another's, which is why a language's chunks are scored together (BMI-FR-02) rather than mixed into one corpus that would leave a German document unfindable by a German query.
9. **BMI-FR-09** A file that does not decode as UTF-8, or whose size exceeds a fixed ceiling, contributes no chunks to any index. Encountering one is skipped rather than fatal: the pass that met it carries on and completes.
10. **BMI-FR-10** `search(indexes, query, limit)` returns the `limit` highest-scoring chunks across the selected indexes, ordered by descending `score`, and returns a list in every circumstance rather than an error: an empty `query`, a `limit` of zero, no project open, and an index set that is entirely empty each yield an empty list. It never blocks and never waits for indexing to settle — it answers from the indexes as they stand at the moment of the call, so a query issued while a build is still running returns what has been indexed so far.
11. **BMI-FR-11** A `score` is computed against the statistics of the corpus the chunk lives in (BMI-FR-02). Results are merged across every corpus a query reached — the languages within an index, and the indexes the caller selected — and ordered by that raw score, which orders one result set rather than measuring relevance on a scale comparable between two separate calls. A hit carries the `index` it came from; the language behind its corpus is not part of the payload, because a caller selects by index and never by language.
12. **BMI-FR-12** Every index pass runs in the background, off the thread serving the UI. No command of this or any other module blocks on indexing, and the project is fully usable — its tree browsable, its artifacts editable, its search working — while the first build after an open is still running.
13. **BMI-FR-13** Opening a project builds all twelve indexes from scratch against the active worktree's current contents. Nothing is read back from a previous session, so the state of an index is always derived from what is on disk now.
14. **BMI-FR-14** Nothing this module holds is written anywhere: no project file, no `.synthesis/` content — `cache/` included — and nothing under `app_data_dir()`. An index lives in memory for as long as the content root it was built against is mounted, and is discarded rather than saved.
15. **BMI-FR-15** A structural change under the project root — a create, delete, rename, or move — reaches this module through the project watcher of `ASC-artifact-scanning.md` ASC-FR-10 and adds or removes the affected files' chunks. This module mounts no watcher of its own and walks no tree of its own.
16. **BMI-FR-16** A content modification to an existing file reaches this module on the internal channel of `ASC-artifact-scanning.md` ASC-FR-15 and causes that file to be re-chunked and re-indexed, its previous chunks replaced whole rather than amended, so a chunk that the edit removed leaves the index with it.
17. **BMI-FR-17** A file whose resolved artifact type changes — through `assign_artifact_type` or `clear_artifact_type` (`ASC-artifact-scanning.md` ASC-FR-05, ASC-FR-07), or through a folder-scope assignment that changes what it inherits — leaves the index it was in and enters the one its new type names. A file that loses its type altogether leaves every index, and one that gains a type enters the corresponding index.
18. **BMI-FR-18** A change written by Git — a pull from GitHub, a checkout, a branch switch — reaches this module through exactly the paths of BMI-FR-15 and BMI-FR-16, because it is a filesystem change like any other. This module observes no Git state, subscribes to no Git event, and has no trigger of its own for a remote update.
19. **BMI-FR-19** A change to a draft's prompt reaches this module on the internal channel of `DRS-draft-storage.md` DRS-FR-28 and updates the drafts index on the same terms BMI-FR-15 and BMI-FR-16 update an artifact index. A draft holds one prompt for its whole life (per `DRS-draft-storage.md` DRS-FR-11), so the channel carries rewrites of that one path and a draft is added to and removed from the index only by being created or deleted. Draft changes travel this channel rather than the project watcher, because `.synthesis/drafts/` is outside what the scan surfaces (ASC-FR-09).
20. **BMI-FR-20** Graduating a draft moves nothing between indexes. A graduated draft keeps its prompt, keeps its record, and stays in the drafts index exactly as it was (per `DRS-draft-storage.md` DRS-FR-20), because a prompt that produced a specification is still working material an agent may want to find. The specification files a graduation publishes reach their artifact index the way every other project write does — through the watcher's report of those paths (BMI-FR-15) — so a graduation costs this module nothing of its own and there is no notification here to take precedence over anything. A published specification and the prompt it was written from are therefore both findable, in the index each belongs to, which is the intended answer rather than a duplication: they are two documents saying different things.
21. **BMI-FR-21** Changes arriving close together collapse into one pass, so a pull that rewrites three hundred files is indexed once rather than three hundred times, and a burst of keystroke-driven draft saves costs one pass rather than one per save.
22. **BMI-FR-22** Every pass registers one operation with `PRG-progress-reporting.md` under `kind = "index"` (per PRG-FR-11) and terminates it when the pass ends, whatever the outcome. The operation becomes determinate once the pass knows how many files it will index, and PRG's coalescing (PRG-FR-07) absorbs the churn of passes dispatched in quick succession. The status bar renders it from its label alone, needing no knowledge of this module (per `../ui/STB-status-bar.md` STB-FR-09).
23. **BMI-FR-23** Every pass emits through `LGC-logging.md`'s internal API under the `backend` domain: an `INFO` record when it starts and when it ends, carrying its file and chunk counts in `fields`; a `WARN` record naming a file skipped under BMI-FR-09; and an `ERROR` record for a pass that fails.
24. **BMI-FR-24** A pass that fails leaves the indexes as they were before it rather than partially updated, terminates its operation as `failed` (per `PRG-progress-reporting.md` PRG-FR-09), and is followed by the next change's pass as normal. A failed pass therefore costs staleness until the next change, never a corrupt index.
25. **BMI-FR-25** Closing a project (per `PST-project-storage.md` PST-FR-14) discards all twelve indexes, and changing the project's active worktree (per `WTC-worktree-context.md` WTC-FR-08) discards the eleven that were built from the worktree and keeps the `documents` index (BMI-FR-NEIW). A new content root builds fresh under BMI-FR-13; nothing from the outgoing root is carried over or merged, and no pass runs against a root the application is no longer reading.
26. **BMI-FR-26** Every read this module performs goes through `FSA-filesystem-access.md`'s `read_text` and is subject to its path-escape rejection (FSA-FR-10). The `skills`, `notes`, and `documents` indexes perform no read here at all, since their documents arrive already read — a document's from `DCL-documents-collection.md` (BMI-FR-WBKZ) — — a skill's from `DSL-dynamic-skills-loading.md` (DSL-FR-23) and a note's from `NTC-notes-storage.md` (NTC-FR-24). This module creates, modifies, and deletes no file anywhere, mutates no store, and touches no repository state, so indexing is observable only as progress and log records.
27. **BMI-FR-27** Indexing is deterministic: the same tree indexed twice yields the same chunks, the same `chunk_ordinal` for each, and the same index membership. A set of indexes brought to a state incrementally is identical to one built from scratch against the same tree, so an incremental history never drifts from what a rebuild would produce.
28. **BMI-FR-28** The `notes` index holds **one document per persisted note** of the active worktree, and that document is the note's `body` and nothing else (`NTC-notes-storage.md` NTC-FR-03). The note's scope, its last-known entity path, its reminder, its revision, its `created_at`, and its `updated_at` are indexed nowhere, so a query reaches what the author wrote and never where the note was filed or when. Membership is every note the store persists, without exception: project-scoped and entity-scoped notes alike, a note whose entity no longer resolves (NTC-FR-10), and a note authored against a historical revision (NTC-FR-18) are each one document on identical terms. A note is bounded at 1 KiB of UTF-8 by the store that writes it (NTC-FR-23), which bounds the whole of the one document this index holds for it; a note whose stored body nonetheless exceeds that bound, and one the store could not read (NTC-FR-14), each contribute no document rather than being truncated into one, and meeting either is skipped rather than fatal on the terms of BMI-FR-09. A note's own TOML file reaches no artifact index, because the scan does not surface `.synthesis/notes/` (`ASC-artifact-scanning.md` ASC-FR-09, NTC-FR-16), and the `notes` index holds no part of that file but the body.
29. **BMI-FR-29** A change to the project's notes reaches this module on the internal channel of `NTC-notes-storage.md` NTC-FR-24 and updates the `notes` index on the same terms BMI-FR-15 and BMI-FR-16 update an artifact index: a note created adds its document, a note whose body was rewritten has its document replaced whole rather than amended, and a note deleted has its document removed. A change that leaves the body alone costs this module nothing — moving a note between entities or to and from project scope (NTC-FR-07), following it through a correlated rename (NTC-FR-11), leaving it unresolved when a rename could not be followed (NTC-FR-12), and setting or clearing its reminder each surface no work here, none of them touching what is indexed. Note changes travel this channel rather than the project watcher, because `.synthesis/notes/` is outside what the scan surfaces (ASC-FR-09). Changing the project's active worktree discards this index with the other ten and rebuilds it against the new content root's own notes (BMI-FR-25, NTC-FR-15), so the notes of the outgoing worktree are unreachable by any query the moment the new root is mounted.
30. **BMI-FR-WBKZ** The `documents` index holds the text of **every available document** of the Documents collection, as `DCL-documents-collection.md` supplies it: file text for `markdown` and `text`, extracted text for `pdf` (per DCL-FR-GLUS). A document with no text, an unavailable document, and a document over the ceiling of BMI-FR-09 contribute no chunks and are skipped, not fatal.
31. **BMI-FR-FGGU** Each document's text is chunked on the rules of BMI-FR-05 and BMI-FR-06: a `markdown` document at its headings, a `text` or `pdf` document into bounded blocks cut at blank lines. Language is detected once over the whole text (BMI-FR-08). A hit carries the document id in `document_id` and in `path`, and no index holds a document's filesystem path.
32. **BMI-FR-MWNQ** A change to the Documents collection reaches this module on the internal channel of `DCL-documents-collection.md` DCL-FR-QGLH. An added document adds its chunks, a changed `revision` replaces its chunks whole, and a document that left the collection or became unavailable loses its chunks. Changes arriving close together collapse into one pass (BMI-FR-21).
33. **BMI-FR-NEIW** The `documents` index is built when a project opens (BMI-FR-13) and survives a change of the active worktree, because the Documents sources belong to the repository (`DCL-documents-collection.md` DCL-FR-XHSJ). The pass that follows a worktree change rebuilds the `documents` index from the same sources, so the result equals a fresh build (BMI-FR-27).

## Non-functional requirements
- The languages a file can actually be stemmed in are the intersection of what the detector recognises and what a stemmer exists for; every other file falls back to English under BMI-FR-08 rather than being left out. Today that intersection is Arabic, Dutch, English, French, German, Italian, Portuguese, Russian, Spanish, Swedish, and Turkish. A language the detector recognises but cannot be stemmed — Chinese, Hindi, Japanese, Korean, Vietnamese — is still tokenised by Unicode word segmentation and stays findable, matching on whole words rather than on stems. Widening the set is a matter of the detector and the stemmer table alone: nothing in this contract names a language, and an index gains a corpus for one the moment a file of it is indexed.
- BM25 scoring, tokenisation, stemming, and language detection come from the `bm25` Rust crate rather than being implemented here; its `k1` and `b` parameters and its set of supported stemmer languages are implementation choices, and the contract is only the behaviour stated above.
- An index's memory footprint is bounded by the text of the documents it indexes together with their term statistics — artifacts, drafts, note bodies, skill descriptors, and the user's selected reference documents only, never the whole project tree — and by the per-file ceiling of BMI-FR-09. The `skills` and `notes` indexes are the smallest of the eleven by a wide margin, holding a name and a sentence or two per skill and at most 1 KiB per note. A project of ordinary source code with a few hundred Markdown artifacts costs a fraction of what indexing every file would.
- The chunk size ceiling of BMI-FR-06 is an implementation choice; the contract is only that every chunk is bounded and that a boundary falls at a blank line rather than mid-sentence.
- The window over which changes collapse into one pass (BMI-FR-21) is an implementation choice of the same order as the watcher's own debounce; the contract is only that a burst costs one pass.
- A `search` call is a pure in-memory lookup and performs no I/O, so it is cheap enough to sit inside a consumer's own loop.
- The cost of a build is proportional to the text actually indexed rather than to the size of the tree walked, because the file set comes from a scan that has already run.
- Nothing in this module requires network access.
