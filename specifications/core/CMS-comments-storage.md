# Comments storage

**Spec code:** `CMS`

## Intent
The persistence home for the **discussions** of a project: every conversation an author holds about a passage of text, about a whole file, about a draft, or about a note. A discussion is one record shape for all of them. It names an **owner target** — one file of the project, a draft, or one of the project's notes (`NTC-notes-storage.md`) — and optionally one **fragment target**, a range of text inside the owner that the discussion is about. A discussion without a fragment target is about the whole owner. A fragment target is possible only where the owner has text to point into: the text of an artifact, or the prompt of a draft. Every discussion is read and continued in one shared conversation surface, wherever its owner shows it (`../ui/CVP-conversation-presentation.md`); fragment-targeted discussions are also shown beside their fragment in the Editor's comment rail (`../ui/CMT-comments.md`), and every discussion is listed across the whole project in the Comments panel (`../ui/CMP-comments-panel.md`). A discussion's whole life is recorded as a sequence of immutable events — one JSON object per line — in a JSONL log this machine keeps for the repository the project belongs to (`RMS-repository-machine-storage.md`): a discussion is opened, comments are added to it, it is locked, resolved, reopened, and its fragment is moved, and no line is ever rewritten or removed. That shape makes a conversation safe to append to from two application processes at once: each writes whole lines, and the fold applies the first event it sees for an identity and ignores every later one. The log stands outside every worktree of the project and reaches Git by no route, so a checkout is never modified by a conversation and no word an agent wrote is published with the work. Every event names the participant who produced it, and a participant is either a **human**, whose identity is resolved from the project's GitHub credential — or is the fixed local human participant **Me** where the project stores no GitHub token — and stamped at the moment of the append, or an **agent**, stamped with the handle, model, and title it answered under at that moment rather than as it is defined today, so a conversation between an author and an automated collaborator is the same log shape as a conversation between two authors and reads years later as the one that was actually held. A comment carries **attachments** as well as prose — the screenshot of the thing being objected to, or a link to one already hosted — and an attachment supplied as bytes is stored once under the SHA-256 of its content so the log line references it rather than carrying it. A third kind of attachment carries no content at all and is not the author's to add: a reference to a change an agent has proposed to a file of a draft (`DCP-draft-change-proposals.md`), which lets a surface offer a control to read that change as a diff from the very comment that announced it. Every append announces itself: the module emits the folded discussion on the event bus as it writes, so a surface showing that conversation redraws from what was just written instead of asking again on a timer. A draft's discussions live under the draft's stable id and are deleted with the draft, because a review of a draft ends when the material does. A note carries at most one discussion, created with the author's opening message and destroyed with the note, in a folder of the note's own. A discussion may additionally hold one durable **pending question set** — the several things an agent asked at once, waiting on the author (`../tools/ADQ-ask-discussion-questions-tool.md`) — which is a small record beside the log rather than a line in it, and which the author's submission turns into ordinary comments in one committed step. A log that records passage-level threads and whole-target discussions as two kinds is read as unified discussions by a read-time normalisation that never rewrites a line. Out of scope: rendering, fragment highlighting, and the fragment re-anchor search, all owned by `../ui/CMT-comments.md`; counting anything, since a log holds what was said rather than an account of what it cost — a discussion opened, a comment appended, and an attachment stored each contribute no line to a draft's statistics log, which `DSS-draft-statistics-storage.md` owns and which is folded from the events the modules performing that work append rather than from these logs (per `DSS-draft-statistics-storage.md` DSS-FR-GAWO); addressing a comment to a particular participant; editing or deleting a comment, since the log is append-only and a discussion that has outlived its usefulness is resolved rather than erased; commenting against a historical revision, so a fragment targets the artifact's current version alone; watching for a write this module did not perform, since it maintains no watcher and a line another process appends becomes visible on the next read; fetching what a `url` attachment addresses, which the surface rendering it reaches for itself; and GitHub's own pull-request review comments, which are remote data served by `GTC-git.md`.

## Contract surface
All Tauri commands below are invoked by the UI; the quoted name is the canonical operation name as it appears in the "Delegated to backend (abstract)" line of `../ui/CMT-comments.md`, `../ui/CMP-comments-panel.md`, or `../ui/CVP-conversation-presentation.md`, and the snake_case identifier is the Rust function name. Every path this module resolves is resolved against the open project's **repository machine store** (per `RMS-repository-machine-storage.md` RMS-FR-ZXHM), which is outside every worktree. A draft-owned path is addressed beneath that store by the draft's **stable id**, exactly as a statistics log is (per `DSS-draft-statistics-storage.md` DSS-FR-KQVN). This module resolves no path inside the active worktree.

### Record shapes

```
Participant =
  | { kind: "human",
      login,                 // GitHub account login; the empty string on the local participant (CMS-FR-HTOA)
      display_name?,         // the account's display name, absent when GitHub reports none;
                             //   "Me" on the local participant
      email? }               // the account's email, absent when GitHub reports none;
                             //   always absent on the local participant
  | { kind: "agent",
      agent_id,              // stable id of the agent, e.g. an `AGR-agent-registry.md` agent id
      handle,                // short display handle — an agent's nickname, e.g. "arch"
      model?,                // the model the agent ran as, when it reports one
      title? }               // snapshot of the agent's title as it stood when the line was
                             //   appended; absent on a participant stamped without one (CMS-FR-65)

DiscussionTarget =           // the OWNER of a discussion (CMS-FR-53)
  | { kind: "artifact", artifact_id }  // one file of the project; project-relative path
  | { kind: "draft",    draft_id }     // one draft, files included
  | { kind: "note",     note_id }      // one note of the project

FragmentTarget {             // a range of text inside the owner (CMS-FR-53)
  owner: DiscussionTarget,   // kind "artifact" or "draft" only
  path,                      // artifact owner: project-relative path, equal to owner.artifact_id;
                             //   draft owner: draft-relative path of the draft prompt or file
  start,                     // character offset into the source text
  end,                       // exclusive end offset; end > start
  quote                      // the exact source substring the range covered
}

CommentQuote {
  comment_id,                // a comment in this same discussion
  excerpt                    // the portion of that comment's body being quoted
}

Attachment =                 // as stored and as served back
  | { kind: "url",
      url,                   // the address the attachment lives at
      media_type,            // IANA media type, e.g. "image/png"
      label? }               // display name, absent when none was supplied
  | { kind: "blob",
      digest,                // lowercase hex SHA-256 of the stored bytes
      media_type,
      filename,              // the name the file was attached under
      bytes }                // byte length of the stored content
  | { kind: "proposal",
      proposal_id,           // a draft change proposal (DCP-draft-change-proposals.md)
      draft_id,
      path }                 // draft-relative path the proposal would replace
  | { kind: "prompt_proposal",
      proposal_id,           // a prompt change proposal (PCP-prompt-change-proposals.md)
      artifact_id,
      path }                 // project-relative path the proposal would replace
  | { kind: "proposal_hunk",
      proposal_id,           // a draft change proposal (DCP-draft-change-proposals.md)
      hunk_id,               // one change of it, which this comment is about
      draft_id,
      path }                 // draft-relative path that change applies to

AttachmentInput =            // what a caller supplies on an append
  | { kind: "url",    url, media_type, label? }
  | { kind: "inline", media_type, filename, data }   // base64 of the file's bytes
  | { kind: "proposal_hunk", proposal_id, hunk_id, draft_id, path }
                             // no input produces a `proposal` or a `prompt_proposal`
                             //   attachment (CMS-FR-60, CMS-FR-66)

Comment {
  id,                        // opaque, unique within the project
  author: Participant,
  body,                      // Markdown source
  quotes: CommentQuote[],    // empty when the comment quotes nothing
  attachments: Attachment[], // empty when the comment attaches nothing
  created_at                 // RFC 3339 UTC
}

Discussion {
  id,                        // opaque, unique within the project, stable for ever
  target: DiscussionTarget,  // the owner
  fragment_target: FragmentTarget | null,  // null: the discussion is about the whole owner
  comments: Comment[],       // oldest first
  locked,
  resolved,
  created_at,                // RFC 3339 UTC
  updated_at                 // RFC 3339 UTC
}

PendingQuestionSet {                 // a discussion's one question set (CMS-FR-QLDW)
  set_id,                            // opaque, unique within the project
  discussion_id,                     // the discussion this set belongs to; the key
  asked_by: Participant,             // the asking agent's participant, agent kind
  asked_at,                          // RFC 3339 UTC
  questions: [ { position, text,
                 options: [ { position, value } ] } ]   // 2 to 3 options each
}

QuestionAnswer {                     // one entry of a submission (CMS-FR-TXRB)
  question_position,
  option_position?,                  // absent where the author answered in their own words
  option_value?,                     // absent where the author answered in their own words
  own_answer?,                       // absent where the author chose an option
  note?                              // a chosen option's addition only
}
```

`PendingQuestionSet` is the durable record `../tools/ADQ-ask-discussion-questions-tool.md` defines (ADQ-FR-GMDK). This module stores it, serves it, and deletes it, and takes no view of what it says.

### Event shapes
Every line of a log is one event. All events carry `v`, `event_id`, `thread_id`, `at`, and `by`. The `thread_id` of an event is the id of the discussion it belongs to:

```
{ v, event_id, type, thread_id, at, by: Participant, … }

discussion_opened … target: DiscussionTarget, fragment_target?: FragmentTarget
fragment_moved    … fragment_target: FragmentTarget
comment_added     … comment_id, body, quotes: CommentQuote[],
                     attachments: Attachment[]
thread_locked     … (no further fields)
thread_unlocked   … (no further fields)
thread_resolved   … (no further fields)
thread_reopened   … (no further fields)
```

A log may also hold lines written in the legacy vocabulary: `thread_opened`, which carries `artifact_path` and `anchor`, and `thread_reanchored`, which carries `anchor`. The fold reads them as `discussion_opened` and `fragment_moved` (CMS-FR-83). This module writes neither.

### Tauri commands
- `"list discussions for target"` → `list_discussions(target: DiscussionTarget)` → `Discussion[]`, every discussion of that owner, fragment-targeted and whole-target alike. Fragment-targeted ones come first, ordered by `fragment_target.start` ascending and tie-broken by `created_at`; whole-target ones follow, ordered by `created_at` ascending.
- `"list all discussions"` → `list_all_discussions()` → `Discussion[]` spanning every log of every owner kind — artifact, draft, and note — each carrying its owner `target`, ordered by `updated_at` descending and tie-broken by `id`.
- `"read discussion"` → `read_discussion(discussion_id)` → the one `Discussion` that id names, folded as it stands on disk, whatever its owner. The only read keyed by a discussion rather than by the owner it belongs to (CMS-FR-61).
- `"open discussion (target, fragment target, body, attachments)"` → `open_discussion(target: DiscussionTarget, fragment_target?: FragmentTarget, body, attachments)` → the created `Discussion`. It refuses a `note` target with a typed `not_supported`, a note's one discussion being reached through the get-or-create below and never through an operation that can open a second (CMS-FR-62).
- `"get or create note discussion (note, body, attachments)"` → `get_or_create_note_discussion(note_id, body, attachments)` → the one `Discussion` that note carries: the existing one where the note already has a discussion, appending nothing; the newly created one carrying `body` and `attachments` as its single opening comment where it does not. Atomic and idempotent under concurrent and repeated calls (CMS-FR-62).
- `"add comment to discussion (discussion, body, quotes, attachments)"` → `add_comment(discussion_id, body, quotes, attachments)` → the updated `Discussion`.
- `"set discussion lock"` → `set_discussion_lock(discussion_id, locked)` → the updated `Discussion`.
- `"set discussion resolution"` → `set_discussion_resolution(discussion_id, resolved)` → the updated `Discussion`.
- `"reanchor discussion fragment"` → `reanchor_discussion_fragment(discussion_id, fragment_target)` → the updated `Discussion`.
- `"resolve comment author identity"` → `resolve_comment_author_identity()` → the human `Participant` this machine writes as — a GitHub account, or the local participant where no token is stored (CMS-FR-HTOA) — or a typed refusal. It is also the read a surface uses to learn the current project identity it displays (CMS-FR-KTHN).
- `"read comment attachment"` → `read_comment_attachment(discussion_id, digest)` → `{ media_type, filename, data }`, the stored bytes base64-encoded. `discussion_id` is what resolves which owner's attachment folder the digest is looked up in (CMS-FR-49).
- `"read discussion question set"` → `read_discussion_question_set(discussion_id)` → the `PendingQuestionSet` that discussion holds, or null where it holds none (CMS-FR-JWVH).
- `"submit discussion question answers"` → `submit_discussion_question_answers(discussion_id, set_id, answers)` → `{ discussion, final_answer_comment_id }`, the ordered question-and-answer append committed and the pending set deleted (CMS-FR-TXRB).

Both append commands take `attachments` as an `AttachmentInput[]`; every other shape above carries the stored `Attachment`.

Errors are typed: `no_project_open`, `store_unavailable`, `discussion_not_found`, `draft_not_found`, `artifact_not_found`, `note_not_found`, `not_supported`, `discussion_locked`, `quoted_comment_not_in_discussion`, `invalid_fragment`, `not_fragment_targeted`, the attachment refusals `attachment_too_large`, `unsupported_media_type`, `malformed_attachment`, `attachment_not_found`, the question-set refusals `question_set_already_pending`, `question_set_not_found`, `question_answers_incomplete`, and the identity refusals `identity_selection_required`, `github_unreachable`, `keychain_unavailable`.

### Events
- `"discussion changed"` — carries one `Discussion`, the discussion as it folds after an append this module has just performed (CMS-FR-51).
- `"discussion question set changed"` — carries `{ discussion_id, set }`, the discussion's `PendingQuestionSet` as it now stands or null where it now holds none, emitted when a set is reserved and when one is deleted (CMS-FR-BQEN).

### Internal (Rust API, not registered as Tauri commands)
- `append_as(participant, event)` — the single writer every command in this module funnels through; it validates the event, stamps it, appends the line, and emits `"discussion changed"` for the discussion it wrote into. It accepts an agent `Participant` as readily as a human one, which is how an agent posts a comment; `AGC-agent-conversations.md` calls it with an agent participant when a turn delivers (AGC-FR-16).
- `store_attachment(owner, input)` — normalises one `AttachmentInput` into the `Attachment` a log line carries, writing an `inline` payload's bytes to the owner's attachment folder and passing a `url` through unfetched. The single path by which an attachment reaches disk.
- `fold(owner)` — reads the owner's logs and returns its `Discussion[]`, normalising legacy lines on the way (CMS-FR-83); the read half every command funnels through. `fold_discussion_log(target)` is the same read over the owner's reserved whole-target log (CMS-FR-55).
- `fold_log(path)` — folds one log file whose owner is not known in advance, resolving that owner on the terms of CMS-FR-33; what `list_all_discussions` applies to each file it enumerates.
- `read_attachment_bytes(discussion_id, digest)` — the stored bytes, media type, and filename of one `blob` in that discussion's owner folder, resolved exactly as `read_comment_attachment` resolves them (CMS-FR-48) and returning the same typed `attachment_not_found`. It is what `AGC-agent-conversations.md` reads an image attachment through when it assembles a turn's input (AGC-FR-35), so a conversation and a card fetch a picture through one path (CMS-FR-67). It writes nothing, emits nothing, and is registered as no Tauri command.
- `note_discussion_index()` — the map from `note_id` to discussion id for every note in the project that carries a discussion, read in one pass over the note comments root (CMS-FR-63). It is what `NTC-notes-storage.md` reads to tell a note row whether it has a conversation (NTC-FR-19); no Tauri command exposes it.
- `delete_note_discussion(note_id)` — removes a note's discussion, its log, and its stored attachments in one recoverable step, and reports success where the note carries none (CMS-FR-64). It is the step `NTC-notes-storage.md`'s deletion transaction performs before it removes the note itself (NTC-FR-21); no Tauri command exposes it, so no frontend call deletes a conversation.
- `reserve_discussion_question_set(discussion_id, set)` — reserves the discussion's one pending-set slot and writes the record in one exclusive step, or refuses `question_set_already_pending` where the slot is held (CMS-FR-QLDW). It is what `../tools/ADQ-ask-discussion-questions-tool.md` records through (ADQ-FR-GMDK); no Tauri command exposes it, so no frontend call can record a question set.
- `delete_draft_comments(draft_id)` — removes that draft's whole `drafts/<draft-id>/` folder in the store, its logs and its stored attachments together, and reports success where the draft carries none (CMS-FR-39). It is reached from `DRS-draft-storage.md`'s deletion alone (DRS-FR-WNTA); no Tauri command exposes it.

## Functional requirements
 1. **CMS-FR-01** Every artifact that carries fragment-targeted discussions has exactly one log at `comments/<log-id>.jsonl` inside the open project's repository machine store (per `RMS-repository-machine-storage.md` RMS-FR-ZXHM). The store is outside every worktree, so no log is a file of the project and no log reaches the project's Git repository.
 2. **CMS-FR-02** `<log-id>` is derived deterministically from the artifact's project-relative path, so the same artifact resolves to the same filename on every branch of the repository and in every worktree of it. One artifact therefore has one log, whichever checkout it was commented on from.
 3. **CMS-FR-XQBM** The store this module resolves is selected by the **repository identity** and never by the active worktree (per `RMS-repository-machine-storage.md` RMS-FR-QJVT, RMS-FR-LPWG). Every worktree of one repository therefore reads and writes one set of logs, and a second repository opened on the same machine reads and writes another. This module writes no `.gitattributes`.
 4. **CMS-FR-04** Each line of a log is exactly one JSON object describing one event, terminated by a newline. No line is ever rewritten, reordered, or removed: appending is the only mutation this module performs on a log.
 5. **CMS-FR-05** The event vocabulary is exactly `discussion_opened`, `fragment_moved`, `comment_added`, `thread_locked`, `thread_unlocked`, `thread_resolved`, and `thread_reopened`, each carrying the fields of the Contract surface. Exactly one `discussion_opened` event begins a discussion and fixes its owner target and its fragment target (CMS-FR-53). There is no event that edits or deletes a comment. Legacy lines are read on the terms of CMS-FR-83 and are never written.
 6. **CMS-FR-06** Every event carries an `event_id` that is opaque and unique. The fold applies the first event it sees for a given `event_id` and ignores every later one, so a log a repeated append or a concurrent process has duplicated a line in folds to the same state as one in which it has not.
 7. **CMS-FR-07** Every event carries `v = 1`, the schema version of the line. A line whose `v` this build does not recognise is skipped by the fold rather than failing it, so a log written by a newer build still serves the events this one understands.
 8. **CMS-FR-08** A line that is not valid JSON, carries no recognised `type`, or is missing a field its type requires is skipped by the fold rather than failing it: one damaged line never prevents the remaining discussions from being served. The skipped line is left in the file untouched.
 9. **CMS-FR-09** A discussion's state is the fold of the events sharing its `thread_id`, replayed in ascending `at` order and tie-broken by `event_id`. The fold is total and deterministic: the same log always folds to the same discussions, whatever order its lines physically appear in.
10. **CMS-FR-10** A discussion's `created_at` is the `at` of its opening event and its `updated_at` is the `at` of the latest event folded into it. Neither is ever rewritten, because no event is.
11. **CMS-FR-11** Every write command resolves the acting human `Participant` before appending anything and stamps it into the event as `by`. The identity is never supplied by the caller and is never re-resolved afterwards, so no frontend call attributes a comment to someone else and a later change of GitHub token rewrites no authorship. Lock, resolution, and fragment events stamp the same participant.
12. **CMS-FR-12** The human identity is read through `GTS-github-token-storage.md`'s `resolve_github_identity_if_stored()` (GTS-FR-ZKOD). A returned GitHub account is stamped as it is. `None`, which means that no token is stored, resolves the local participant (CMS-FR-HTOA). `identity_selection_required`, `github_unreachable`, and `keychain_unavailable` are each returned as their own typed error, nothing is written, and the log is byte-for-byte what it was.
13. **CMS-FR-13** `resolve_comment_author_identity()` returns that same participant without writing anything, and refuses with the same typed distinction. It is what lets `../ui/CMT-comments.md` CMT-FR-24 decide whether commenting is possible before the author has typed anything.
14. **CMS-FR-14** `open_discussion(target, fragment_target, body, attachments)` appends a `discussion_opened` event and a `comment_added` event carrying `body` and the stored form of `attachments`, both in one append, and returns the folded discussion. A new discussion is never created empty.
15. **CMS-FR-15** A discussion whose folded events include no `comment_added`, or no opening event (CMS-FR-05, CMS-FR-83), is not returned by any command.
16. **CMS-FR-16** `add_comment(discussion_id, body, quotes, attachments)` appends one `comment_added` event to the discussion's log. Each entry of `quotes` names a `comment_id` that must already belong to that discussion; one that does not is a typed `quoted_comment_not_in_discussion` error and nothing is appended.
17. **CMS-FR-17** `add_comment` on a discussion whose folded state is `locked` is refused with a typed `discussion_locked` error and appends nothing. This is the only thing a lock prevents.
18. **CMS-FR-18** `locked` and `resolved` are independent booleans, each false on a newly opened discussion and each freely reversible: `set_discussion_lock` appends `thread_locked` or `thread_unlocked`, `set_discussion_resolution` appends `thread_resolved` or `thread_reopened`, and neither reads or writes the other. A discussion may be locked, resolved, both, or neither.
19. **CMS-FR-19** Setting a discussion to the state it already holds appends nothing and returns the discussion unchanged.
20. **CMS-FR-20** Both `set_discussion_lock` and `set_discussion_resolution` operate on a locked discussion, on a resolved discussion, and on one that is both. A lock is not a freeze of the discussion's own status.
21. **CMS-FR-21** `reanchor_discussion_fragment(discussion_id, fragment_target)` on a fragment-targeted discussion appends a `fragment_moved` event carrying the discussion's new `path`, `start`, `end`, and `quote`, and is accepted on a locked or resolved discussion, because moving with the text the discussion is attached to is not a contribution to the conversation. A `fragment_target` whose `end` is not greater than its `start`, or whose `owner` differs from the discussion's `target`, is a typed `invalid_fragment` error and nothing is appended.
22. **CMS-FR-22** A fragment's `start` and `end` are character offsets into the owner's source text and its `quote` is the source substring that range covered. This module stores and serves them and never reads the owner's text to verify them; matching a fragment against content is owned by `../ui/CMT-comments.md` CMT-FR-18.
23. **CMS-FR-23** `list_discussions(target)` returns every discussion of that owner, in both of its logs — locked, resolved, and neither alike. Fragment-targeted discussions come first, ordered by `fragment_target.start` ascending and tie-broken by `created_at`; whole-target discussions follow, ordered by `created_at` ascending, so an owner's conversations read in the order they were begun. A note target returns the one discussion that note carries or an empty list. No discussion is ever withheld; which of them a surface renders is that surface's decision.
24. **CMS-FR-24** When the `ASC-artifact-scanning.md` watcher reports a rename or move this module can correlate to a single old path and a single new path, the artifact's log files are renamed to the new path's `<log-id>`. No line inside them is rewritten: the path an event carries is a human-readable record of where the discussion was opened, and the file's name is what binds a log to an artifact.
25. **CMS-FR-25** A filesystem change this module cannot correlate to a single rename — a delete, or a delete-and-create pair the watcher reports separately — leaves the log under its existing `<log-id>`. The log is retained rather than removed, so nothing an author wrote is lost to a move this module could not follow.
26. **CMS-FR-26** `append_as(participant, event)` is the single write path in this module and accepts an agent `Participant` on the same terms as a human one. The Tauri commands are wrappers that resolve the human identity (CMS-FR-11) and call it; an agent posting through it produces a line the fold and the rail read exactly as they read an author's.
27. **CMS-FR-27** Every write this module performs goes through `FSA-filesystem-access.md` primitives — `append_lines` for a log line (FSA-FR-15), `write_bytes_atomic` for an attachment's bytes (FSA-FR-04), `rename_path` for a rename — and is subject to FSA's path-escape rejection (FSA-FR-10). This module performs no raw `fs::write`, `fs::remove`, or `fs::rename` calls, and writes nothing outside the scope's own comments folder in the store.
28. **CMS-FR-28** Changing the project's active worktree (per `WTC-worktree-context.md` WTC-FR-08) selects the same store (per `RMS-repository-machine-storage.md` RMS-FR-TCAF). Every discussion reads the same after the change as before it, every subsequent append lands in the same log, and no log is copied, moved, or re-resolved.
29. **CMS-FR-29** No log and no stored attachment is ever surfaced as an artifact node. The store stands outside every worktree, so the scan never reaches one (`ASC-artifact-scanning.md` ASC-FR-09), and neither a log file nor an attachment appears in the Project panel, in project search, or in a Git status of the project.
30. **CMS-FR-30** Every command errors with a typed `no_project_open` when no project is open, and with a typed `discussion_not_found` when `discussion_id` names no discussion in the open project.
31. **CMS-FR-31** A command's result is folded from the log as it stands on disk at the moment the command runs. This module maintains no watcher on any comments folder, so a line another process appends — a second checkout, a `git pull`, a hand-edited log — becomes visible on the next command rather than announcing itself. What this module announces is its own writes and nothing else (CMS-FR-51).
32. **CMS-FR-32** `list_all_discussions()` returns every discussion of every log in the store — the `comments/` folder, every draft's comments folder, and every note's folder — locked, resolved, and neither alike, each carrying the owner `target` it was opened against, ordered by `updated_at` descending and tie-broken by `id`. No discussion is withheld; how they are grouped and ordered for reading is `../ui/CMP-comments-panel.md`'s decision.
33. **CMS-FR-33** The artifact a log belongs to is the one its log's **filename** names, because the filename is what binds a log to an artifact and is kept current through a rename (CMS-FR-24), where the path an event carries records only where the discussion was opened and is never rewritten. `<log-id>` is a one-way derivation of a path (CMS-FR-02), so the filename is read back by enumerating the project's own paths and matching their derivations against it — an inversion by enumeration, the artifact set being the only domain the derivation has to cover. A whole-target log's reserved suffix (CMS-FR-55) is stripped before that match, both of a file's logs naming it through one derivation. A log whose filename matches no path in the project falls back to the path its opening event carries — the last place the artifact was known to be — which keeps the discussions of a deleted artifact, and of one moved by a change this module could not correlate, readable (CMS-FR-25). A discussion whose folded events include no opening event names no owner at all and is not returned, on the same principle as one holding no comment (CMS-FR-15).
34. **CMS-FR-34** The project's paths are enumerated only when some log's recorded path no longer derives to its own filename, since that disagreement is the only thing a rename produces. A project in which nothing has been renamed since its discussions were opened resolves every artifact from the recorded paths alone and reads no directory beyond the comments folder.
35. **CMS-FR-35** A log file that cannot be opened or read is skipped and every other log is still served, on the same terms a damaged line is skipped within a log (CMS-FR-08): one unreadable file never fails a project-wide read, and the file is left untouched.
36. **CMS-FR-36** A discussion's **owner target** names what it belongs to: an `artifact` target, a file of the project; a `draft` target, a draft developed in the New Artifact tab (per `../ui/NAW-new-artifact.md` NAW-FR-14); or a `note` target, one of the project's notes (`NTC-notes-storage.md` NTC-FR-01). Every command, record, event, and requirement above applies to every owner kind unchanged — a discussion is opened, commented on, locked, and resolved identically whichever it is — so a surface invokes one set of operation names and this module resolves where the log lives. The owner kind decides exactly two things: where the log is written and how long it lives. Every owner's logs live in the repository machine store (CMS-FR-37). Fragments are possible only where the owner has text to point into (CMS-FR-84): a note is a few lines of text with no passages to pin a remark inside, so no fragment-targeted discussion is ever opened in one.
37. **CMS-FR-37** An artifact owner's logs live in the store's `comments/` folder: fragment-targeted discussions in `comments/<log-id>.jsonl` (CMS-FR-01) and whole-target ones in `comments/<log-id>.discussion.jsonl` (CMS-FR-55), attachments beside them (CMS-FR-44). A note owner's log lives at `comments/notes/<note-id>/discussion.jsonl`, its attachments under `attachments/` in that same per-note folder. `<note-id>` is the note's own opaque id rather than a derivation of anything (`NTC-notes-storage.md` NTC-FR-02), so a note moved between entities or to project scope keeps the folder it started with. A draft owner's logs live at `drafts/<draft-id>/comments/` in the same store — `<log-id>.jsonl` for fragment-targeted discussions and `discussion.jsonl` for whole-target ones — addressed by the draft's **stable id** (`DRS-draft-storage.md` DRS-FR-02) and by nothing about where the draft is filed, so renaming a draft, filing it under a folder, and moving it between folders each leave its whole review where it is. No owner's log is inside a worktree, is committed, or is named in any commit this application writes (per `RMS-repository-machine-storage.md` RMS-FR-HDNZ).
38. **CMS-FR-38** A draft owner's fragment log filename is derived from the prompt's **draft-relative** path by the same one-way derivation an artifact's is (CMS-FR-02), so a prompt renamed by its draft being renamed (per `DRS-draft-storage.md` DRS-FR-14) is followed exactly as an artifact rename is (CMS-FR-24), and two drafts whose prompts share a name never share a log, their folders differing.
39. **CMS-FR-39** A draft owner's logs live exactly as long as the draft does, and **deleting the draft is the only thing that ends them**. `delete_draft_comments(draft_id)` removes that draft's whole `drafts/<draft-id>/` folder in the store — its logs and its stored attachments alike — and is reached from `DRS-draft-storage.md`'s deletion alone (`DRS-draft-storage.md` DRS-FR-21, DRS-FR-WNTA). **Graduation removes nothing**: a graduated draft is retained whole, its record, its prompt, its assets, its history, its proposals, and its discussion logs all exactly as they were (`DRS-draft-storage.md` DRS-FR-20, per `GRD-graduation.md` GRD-FR-ARLT). What graduation does not do is **carry** the discussions: the files it writes into the project begin with no discussions at all (per `../ui/NAW-new-artifact.md` NAW-FR-20), and a draft owner's log is never copied, re-targeted, or re-anchored onto an artifact owner by any route. No artifact owner's log is touched by a deletion or by a graduation.
40. **CMS-FR-40** `list_all_discussions()` returns discussions of **every** owner kind (CMS-FR-32): artifact, draft, and note owners, fragment-targeted and whole-target alike, so the project-wide Comments panel (`../ui/CMP-comments-panel.md`) indexes every conversation the project holds. Each carries its owner target, which is what lets the panel route an activation to the owner's surface or, where the owner no longer resolves, to the fallback conversation tab (per `../ui/CMP-comments-panel.md` CMP-FR-10).
41. **CMS-FR-41** An agent-authored comment is written through `append_as` with an agent `Participant` and through no other path: no Tauri command accepts a participant, so a frontend call can neither attribute a comment to an agent nor forge one, exactly as it cannot attribute one to another human (CMS-FR-11). The agent write is subject to every rule an author's is — a locked discussion refuses it with the same `thread_locked` error and gains no line (CMS-FR-17), a quote must name a comment of the same discussion (CMS-FR-16), and the appended line is the same `comment_added` event with the same fields — so a lock stops an agent exactly as it stops a person, and a discussion's log carries no evidence of who or what appended it beyond the participant already stamped in `by`.
42. **CMS-FR-42** A comment carries an ordered list of **attachments**, empty on a comment that attaches nothing. A stored attachment is one of exactly five kinds: a `url`, which is an address together with the media type it is expected to serve; a `blob`, which is content this module holds, named by the SHA-256 digest of its bytes and carrying its media type, the filename it was attached under, and its byte length; a `proposal`, which is a reference to a change an agent has proposed to a draft's prompt (per `DCP-draft-change-proposals.md` DCP-FR-05), carrying that proposal's identity, its draft, and the draft-relative path it would replace; a `prompt_proposal`, which is a reference to a change an agent has proposed to a prompt artifact the project already holds (per `PCP-prompt-change-proposals.md` PCP-FR-05), carrying that proposal's identity, its artifact, and the project-relative path it would replace; and a `proposal_hunk`, which names **one change** of a draft change proposal and marks the comment as being about that change alone. All five render as attachments of the same comment. The first two differ only in where their content lives; the last two hold no content at all and name something this module neither stores, reads, nor knows the state of (CMS-FR-60, CMS-FR-66). The two reference kinds are separate rather than one kind carrying a target, naming two stores with two lifetimes: a `proposal` dies with the draft folder it points into, while a `prompt_proposal` names a file of the project.
43. **CMS-FR-43** The two append commands take `attachments` as an `AttachmentInput[]`, whose variants are `url`, `inline`, and `proposal_hunk` and no others. A `url` input is recorded verbatim as a `url` attachment and is never resolved, requested, or validated against what it serves, this module making no network request of any kind. An `inline` input carries the file's bytes base64-encoded and is stored as a `blob` (CMS-FR-44). An empty list is the ordinary case and stores nothing. No input produces a `proposal` or a `prompt_proposal` attachment, so no caller of a Tauri command can put either on a comment (CMS-FR-60, CMS-FR-66).
44. **CMS-FR-44** An `inline` input's decoded bytes are written to `<owner-comments-folder>/attachments/<digest>` in the store, where `<digest>` is the lowercase hex SHA-256 of those exact bytes, computed by this module over what it decoded. Two comments attaching byte-identical content therefore name one file: when the digest already exists the bytes are not written again and the existing file is left untouched.
45. **CMS-FR-45** An attachment's bytes reach disk before the log line referencing them is appended. A folded comment therefore never names a `blob` whose file is absent, and an append that fails part-way leaves at worst an unreferenced file rather than a comment pointing at nothing.
46. **CMS-FR-46** A stored `blob` is never rewritten and never renamed, and nothing in this module collects unreferenced attachments, on the same principle that nothing compacts a log: the events referencing an attachment are permanent. A blob leaves disk only when the whole of the thing it belongs to does — a draft deleted (CMS-FR-39), a note deleted (CMS-FR-64) — the owner's lifetime ending rather than anything being collected out of a live one. Graduating a draft ends nothing and collects nothing: a graduated draft's blobs are retained with the rest of it (CMS-FR-39).
47. **CMS-FR-47** A supplied attachment is refused before anything is appended when its media type is outside the set this module accepts — images, PDF, and plain text — with a typed `unsupported_media_type`; when its decoded length exceeds this module's bound, with a typed `attachment_too_large`; and when the input does not parse at all — data that is not valid base64, a `url` that is not a well-formed address, an `inline` input carrying no filename — with a typed `malformed_attachment`. A refusal of any attachment in the list refuses the whole append: no line is written, no blob is stored, and the log is byte-for-byte what it was.
48. **CMS-FR-48** `read_comment_attachment(discussion_id, digest)` returns the stored bytes of a `blob` in that discussion's owner folder together with its media type and filename, and it and its internal twin `read_attachment_bytes` (CMS-FR-67) are the only ways the content of an attachment leaves this module. A digest no attachment in that folder carries is a typed `attachment_not_found`. Neither a `url` nor a `proposal` attachment is served by it, this module holding no content for either.
49. **CMS-FR-49** Attachments that have content follow their discussion's owner exactly as its log does (CMS-FR-36): an artifact owner's attachment is stored under the store's `comments/attachments/`, a draft owner's under `attachments/` inside that draft's own comments folder and deleted with the draft (CMS-FR-37, CMS-FR-39), and a note owner's under `attachments/` inside that note's own folder and deleted with the note (CMS-FR-37, CMS-FR-64). No two owners share a blob, and a note's folder is its own rather than shared with the notes beside it, so identical bytes attached in several places are stored once in each. A `proposal` attachment stores nothing under either folder, holding no content of its own.
50. **CMS-FR-50** Attachments are immutable with the comment that carries them. No event adds an attachment to an existing comment, removes one from it, or changes what one references, on the same terms that no event edits a body (CMS-FR-05). A `proposal` attachment is immutable on exactly these terms and not despite the proposal it names being decided afterwards: what it carries is that proposal's **identity**, which never changes, its pending, accepted, or rejected state living in `DCP-draft-change-proposals.md` rather than here.
51. **CMS-FR-51** Every append this module performs emits `"discussion changed"` carrying the discussion as it folds after that write — a discussion opened, a comment added, a lock or resolution set, a fragment move, and an agent's answer arriving through `append_as` alike. The payload is the whole `Discussion`, so a consumer redraws that conversation from the event without a read of its own.
52. **CMS-FR-52** No event is emitted where no line was appended: a refused write (CMS-FR-12, CMS-FR-17, CMS-FR-47), a no-op lock or resolution (CMS-FR-19), and every read command are all silent. A consumer therefore never redraws for a write that did not happen.
53. **CMS-FR-53** A discussion carries one **owner target** and an optional **fragment target**. The owner target says what the discussion belongs to: an `artifact` target is one file of the project, a `draft` target is a draft, files included, and a `note` target is one note of the project, itself — a note's discussion concerns the note rather than whatever entity the note is attached to. The fragment target, where present, says which range of text inside the owner the discussion is about: it names the owner, the path of the text it lies in, the character range, and the exact quoted text. A discussion with no fragment target is about the whole owner. Flow, Diff, History, note, and whole-artifact discussions are always whole-target. The owner target and the presence of a fragment target are both fixed by the opening event (CMS-FR-05) and neither changes afterwards; only the range of an existing fragment moves (CMS-FR-21). Where the conversation was started from — the Editor, a Flow, a Diff, a History view — is a concern of the surface and is not stored.
54. **CMS-FR-54** Every record, event, command, and requirement above applies to a discussion whether or not it carries a fragment target: comments are added to it, quotes name comments within it, attachments are stored and served for it, it is locked, unlocked, resolved, and reopened, its identity is stamped and its appends announced, and an agent writes into it through `append_as` on exactly the terms a person writes into it (CMS-FR-16, CMS-FR-17, CMS-FR-18, CMS-FR-41, CMS-FR-42, CMS-FR-51). Only the fragment-specific operations — moving a fragment (CMS-FR-21) and reserving a question set (CMS-FR-QLDW) — depend on the fragment target.
55. **CMS-FR-55** Whole-target discussions live in a **reserved log**, one per owner, holding every whole-target discussion that owner carries. A draft's is `discussion.jsonl` in that draft's own comments folder (CMS-FR-37): the name is reserved rather than derived, and no derivation of CMS-FR-02 produces it, so a draft file can never be given the reserved log's filename however it is named. It is deleted with the draft exactly as the draft's fragment logs are (CMS-FR-39). An artifact's is at `comments/<log-id>.discussion.jsonl` in the store, beside the `<log-id>.jsonl` its fragment-targeted discussions append to, `<log-id>` being the same one-way derivation of the file's project-relative path (CMS-FR-02) — so a file's two logs are found by one derivation, the reserved suffix tells them apart, and no derivation produces a name ending in it. It lives exactly where the fragment log beside it lives (CMS-FR-01, CMS-FR-37), and a rename of the file renames both logs together (CMS-FR-24). A note's is `discussion.jsonl` in that note's own folder (CMS-FR-37), reserved on the same terms and holding the one discussion that note carries (CMS-FR-62) rather than every discussion of an owner that may accumulate several. A discussion's log is chosen by its opening event: a fragment target selects the fragment log and its absence selects the reserved log.
56. **CMS-FR-56** A discussion's storage follows its owner target: a `draft` target opens a draft-owned discussion, an `artifact` target an artifact-owned one, and a `note` target a note-owned one, each living and lasting exactly as that owner's own rule has it (CMS-FR-36, CMS-FR-37). A conversation about a whole thing is worth having whether that thing is still being shaped in a draft, already in the project, or a line of text an author left themselves — "is this ready?" and "what should I do about this?" are the same shape of question against all three — so the owners differ in nothing but where their log lives and how long it lives.
57. **CMS-FR-57** `open_discussion(target, fragment_target, body, attachments)` appends a `discussion_opened` event carrying the target and the optional fragment target, and a `comment_added` event carrying `body` and the stored form of `attachments`, both in one append into the log CMS-FR-55 selects, and returns the folded discussion. A discussion is never created empty (CMS-FR-14). A target naming nothing in the open project appends nothing and is a typed refusal — `draft_not_found` for a draft, `artifact_not_found` for a path the project does not hold. A `note` target is refused with a typed `not_supported` and appends nothing: this command can open a second discussion on a target that already has one, which is exactly what a note may not have, so a note's is opened through `get_or_create_note_discussion` alone (CMS-FR-62). A fragment target is validated on the terms of CMS-FR-84.
58. **CMS-FR-58** `list_discussions(target)` serves both of an owner's logs in one call (CMS-FR-23), so a surface asking for an owner's conversations never has to know which of them carry a fragment target. `list_all_discussions()` returns the discussions of every owner (CMS-FR-40), so the project-wide Comments panel lists a conversation about a whole specification beside the remarks pinned inside it, a draft's discussions, and a note's.
59. **CMS-FR-59** `reanchor_discussion_fragment` on a whole-target discussion is a typed `not_fragment_targeted` error and appends nothing, there being no fragment to follow. It is the one command of the contract surface a whole-target discussion refuses.
60. **CMS-FR-60** A `proposal` attachment reaches a comment through `append_as` alone (CMS-FR-26), called by `DCP-draft-change-proposals.md` (DCP-FR-05) with the proposing agent's participant, and through no other path. No Tauri command accepts one, no `AttachmentInput` variant produces one, and no route reachable from the frontend puts one on a comment (CMS-FR-43) — so a proposal reference can be forged no more than an agent's authorship can (CMS-FR-41), which matters because the reference is what a surface offers the author a control to accept a rewrite of their working material from. This module validates nothing about what it names: it neither reads the proposal, nor checks that it exists, nor learns of its decision, and a reference whose proposal has since gone with its draft (per `DRS-draft-storage.md` DRS-FR-20, DRS-FR-21) is stored, folded, and served exactly as one whose proposal still stands, on the same terms a `url` attachment survives whatever its address stops serving (CMS-FR-43). A comment carries at most one, and it is the only attachment a comment carrying one has, an agent contributing no file to a conversation on any other terms (per `AGC-agent-conversations.md` AGC-FR-17).
61. **CMS-FR-61** `read_discussion(discussion_id)` returns the single discussion that id names, folded on the terms every other read folds one (CMS-FR-09, CMS-FR-31), and refuses with the typed `discussion_not_found` when the id names no discussion in the open project (CMS-FR-30). It serves a fragment-targeted and a whole-target discussion alike and resolves which owner's log to read from the id itself, exactly as `read_comment_attachment` resolves which owner's attachment folder to look in (CMS-FR-49). It is the read for a caller that holds a conversation's identity and no longer holds the owner it belongs to: a conversation tab opened for a discussion whose owner has since been deleted (per `../ui/CVP-conversation-presentation.md` CVP-FR-53), and every conversation tab of a note discussion, which has no owner surface to be read through at all (per `../ui/CVP-conversation-presentation.md` CVP-FR-59). It writes nothing and emits nothing (CMS-FR-52).
62. **CMS-FR-62** A note carries **at most one** discussion, and the association between the two is the existence of that note's log and nothing else: no field of the note record names a discussion, no line of any log names a note beyond the `discussion_opened` event's own target, and nothing infers the association from a comment's text or from the entity the note is attached to. `get_or_create_note_discussion(note_id, body, attachments)` is therefore the whole of it. Where the note has no discussion, one append creates the log with a `discussion_opened` event carrying the `note` target and no fragment target and a `comment_added` event carrying `body` and the stored form of `attachments`, exactly as `open_discussion` does (CMS-FR-57), and the folded discussion is returned. Where the note already has one, the existing discussion is folded and returned and **nothing is appended** — no second discussion, no second opening comment, and no event (CMS-FR-52). The two outcomes are decided and committed under one exclusion per note, so concurrent and repeated calls resolve to one discussion with one opening comment whichever arrives first and the later caller's body is simply not written; a call that fails part-way leaves the note either with the whole committed discussion or with none, never with a log holding an opening event and no comment. A `note_id` naming no note in the open project appends nothing and is a typed `note_not_found`, and an empty or whitespace-only `body` is refused on the terms every opening append is (CMS-FR-14), a discussion never beginning without something said in it.
63. **CMS-FR-63** `note_discussion_index()` returns the `note_id` → discussion id map of every note in the project that carries a discussion, read in one pass over the store's `comments/notes/` folder rather than one read per note, so a panel listing two hundred notes learns which of them have conversations without two hundred reads. A folder holding no log, or one whose log folds to no discussion, contributes no entry, on the same terms a damaged log is skipped rather than failing the read (CMS-FR-35). It writes nothing and emits nothing.
64. **CMS-FR-64** `delete_note_discussion(note_id)` removes that note's whole folder — its log and its stored attachments together — through `FSA-filesystem-access.md`'s `delete_path` with `recursive = true`, which is what makes the removal one step rather than a sequence that can stop half-way. It is **idempotent**: a note carrying no discussion is reported deleted having had nothing to delete, so a retried transaction never fails on work already done. A removal that cannot be completed is a typed failure that leaves the folder as it stands, so the caller either retries it or reports it, and no partially emptied folder is left presenting as a conversation. It emits no `"discussion changed"`, the discussion being gone rather than changed, and touches no log of any other owner and no other note's folder. It is the one route by which a persisted conversation is destroyed rather than resolved, and it exists because a note's discussion is about the note: material that outlived what it was about would be reachable from nowhere and answerable by nobody (per `NTC-notes-storage.md` NTC-FR-21).

65. **CMS-FR-65** An agent `Participant` carries an optional **title snapshot**: the agent's title as `AGR-agent-registry.md` holds it (AGR-FR-23), copied into the participant at the moment the line is appended and never resolved again. Every path that appends an agent-authored line stamps it — a delivered answer (per `AGC-agent-conversations.md` AGC-FR-16), a question (per `../tools/AUC-ask-user-comment-tool.md` AUC-FR-04), and the comment a proposal is announced by (per `DCP-draft-change-proposals.md` DCP-FR-05 and `PCP-prompt-change-proposals.md` PCP-FR-05) alike — so every agent comment this build writes carries one. The snapshot is what keeps a conversation readable as it was held: an agent retitled afterwards leaves the comments it had already written reading the title it answered under, this module rewriting no line (CMS-FR-04) and reading no agent record while it folds. The field is **absent** rather than empty on a participant stamped without one, and the fold preserves that absence exactly: a line carrying no title folds to a participant carrying none, a line carrying one folds to the string it carries — the empty string included — and nothing anywhere substitutes an agent's current title for a missing one. Absence and emptiness read alike wherever a comment is rendered (per `../ui/CTA-comment-agent-turns.md` CTA-FR-KFUF), so the distinction costs a reader nothing while keeping an old log honest about what it recorded.
66. **CMS-FR-66** A `prompt_proposal` attachment reaches a comment through `append_as` alone (CMS-FR-26), called by `PCP-prompt-change-proposals.md` (PCP-FR-05) with the proposing agent's participant, and through no other path. No Tauri command accepts one, no `AttachmentInput` variant produces one, and no route reachable from the frontend puts one on a comment (CMS-FR-43) — so a reference to a proposed rewrite of a published file can be forged no more than an agent's authorship can (CMS-FR-41), which matters because the reference is what a surface offers the author a control to replace a file of their project from. This module validates nothing about what it names: it neither reads the proposal, nor checks that it exists, nor learns of its decision, and a reference whose proposal or whose artifact has since gone is stored, folded, and served exactly as one whose proposal still stands, on the same terms a `url` attachment survives whatever its address stops serving (CMS-FR-43). A comment carries at most one, and it is the only attachment a comment carrying one has (per `AGC-agent-conversations.md` AGC-FR-17). It is never carried on the same comment as a `proposal` attachment: the two name different stores, and an agent's turn produces one contribution and not two (per `../ai/CVL-conversation-loop.md` CVL-FR-15).
67. **CMS-FR-TQVB** A `proposal_hunk` attachment reaches a comment through **both** append paths, so an author and an agent each address a comment to one change of a proposal. It names a change that already exists and offers no control that rewrites the author's material, so it carries none of the forging rule of CMS-FR-60.


68. **CMS-FR-67** `read_attachment_bytes(discussion_id, digest)` serves a stored `blob` to a caller inside the backend on exactly the terms `read_comment_attachment` serves one to a surface (CMS-FR-48): the same owner resolution from the discussion id (CMS-FR-49), the same bytes, media type, and filename, and the same typed `attachment_not_found` for a digest that owner does not carry. It serves neither a `url`, a `proposal`, nor a `prompt_proposal`, this module holding content for none of them, and it fetches nothing: an address stays an address here as everywhere (CMS-FR-43). Its one consumer is the conversational input assembly of `AGC-agent-conversations.md` (AGC-FR-35), which reads an image a comment carries so an agent can be shown it rather than told about it, and it exists so that reading an attachment for a model and reading one for a card are one path with one set of rules rather than two. It is registered as no Tauri command, so it widens nothing a frontend call can reach.
69. **CMS-FR-VJRP** A log **is never committed**. The store stands outside every worktree (per `RMS-repository-machine-storage.md` RMS-FR-HDNZ), so no log, no attachment, and no folder of the store is staged, committed, or reported as a change of the project by this application or by any module it calls. This module opens no repository, holds no index, and writes no path under a `.git` directory.

70. **CMS-FR-YQND** A command that cannot resolve the store returns the typed `store_unavailable` of `RMS-repository-machine-storage.md` (RMS-FR-WGQS) and appends nothing. A read refuses on the same terms rather than answering with an empty list, so a conversation that could not be read is never presented as one that holds nothing (RMS-FR-HAJC).
71. **CMS-FR-XWDA** A **discussion** may hold one durable `PendingQuestionSet` beside its log, serialized as one JSON object at `<owner-comments-folder>/question-sets/<discussion-id>.json` and written through `FSA-filesystem-access.md`'s `write_bytes_atomic` (FSA-FR-04). The record is not a log line and not a comment: no event carries it, no fold reads it, and no `Discussion` this module returns is changed by one standing.
72. **CMS-FR-QLDW** `reserve_discussion_question_set(discussion_id, set)` reserves the discussion's **one** pending-set slot and writes the record under **one exclusion per discussion**, so reservation and creation are one step that cannot expose two sets. A discussion already holding a set refuses `question_set_already_pending` and keeps its record byte-for-byte; a fragment-targeted discussion refuses `not_supported`; a locked discussion refuses `discussion_locked`.
73. **CMS-FR-BQEN** Reserving a set and deleting one each emit `"discussion question set changed"` carrying that discussion's set as it now stands or null. A refused reservation and a submission that did not commit emit nothing, on the terms every silent write is silent (CMS-FR-52).
74. **CMS-FR-JWVH** `read_discussion_question_set(discussion_id)` returns the record that discussion holds or null where it holds none, resolving which owner's folder to read from the discussion id exactly as `read_discussion` resolves a log (CMS-FR-61). It writes nothing and emits nothing.
75. **CMS-FR-TXRB** `submit_discussion_question_answers(discussion_id, set_id, answers)` appends **two comments per recorded question, in the recorded question order** — the agent-authored question comment stamped with the set's own participant snapshot (CMS-FR-41), then the human-authored answer comment stamped with the acting identity (CMS-FR-11), each carrying the body `../tools/ADQ-ask-discussion-questions-tool.md` fixes (ADQ-FR-MRSK, ADQ-FR-RECR, ADQ-FR-NUEB) — and **then** deletes the set.
76. **CMS-FR-PJBV** The submission is refused and appends nothing when `set_id` names no set the discussion holds or has already committed (`question_set_not_found`), when the answers do not cover every recorded question exactly once, when an `option_position` names no option of its question, and when an `option_value` differs from that option's recorded value (`question_answers_incomplete`).
77. **CMS-FR-GNTB** An answer entry names **either** a chosen option or the author's own words, never both and never neither. The submission is refused with `question_answers_incomplete` and appends nothing when an entry names both, names neither, carries own words that are blank once trimmed, or carries a note beside own words.
78. **CMS-FR-WNQD** A **locked** discussion refuses a submission with the typed `thread_locked` and appends nothing, a conversation that takes no further contribution taking no further answer either. The refusal is **unconditional**: it holds whether the discussion still carries the pending set or the submission it names has already committed, so one rule governs a locked conversation and no operation of this module reads or reports against one. A refused submission keeps the pending set exactly as it stood where one stands, so a discussion unlocked later is answered without anything being entered again.
    - *Why:* A lock is what an author reaches for to stop a conversation moving. An operation that still answered from it — even one only reporting work already committed — would make the lock a rule with an exception a reader has to know about, and the report it would give is recoverable by reading the conversation.
79. **CMS-FR-ZRHF** Every event the submission appends carries the identity `../tools/ADQ-ask-discussion-questions-tool.md` derives from the `set_id` and the question's position (ADQ-FR-YQTB), so a repeated or resumed submission appends lines the fold already ignores (CMS-FR-06). The operation is therefore **idempotent**: a retry after a failure or a restart commits the same ordered result, never a subset and never a duplicate.
80. **CMS-FR-OKMU** The set is deleted **only after** the append is committed. A submission interrupted between the two leaves the set standing and the comments in the log; the retry appends nothing new and deletes the set. A crash therefore never leaves an ambiguous pair, a missing comment, or a lost set.
81. **CMS-FR-GAVT** A repeated submission naming a `set_id` the discussion no longer holds succeeds where the log already carries that set's derived question comment, returning the folded discussion and the same final answer comment id and appending nothing. This holds for an **unlocked** discussion: a locked one refuses first and on the same terms as every other submission (CMS-FR-WNQD), the lock being checked before anything is read or reported.
82. **CMS-FR-EKUP** A pending set lives exactly as long as the discussion's owner does. A deleted draft removes its whole folder and every set inside it (CMS-FR-39), a deleted note removes its own (CMS-FR-64), and nothing else collects, expires, or rewrites one. No route reachable from the frontend creates a set, `reserve_discussion_question_set` being registered as no Tauri command.
83. **CMS-FR-83** **Legacy lines are normalised at read time and never rewritten.** The fold reads a legacy `thread_opened` line, which carries `artifact_path` and `anchor`, as a `discussion_opened` whose `target` is the owner the log's location names — an artifact for a log in `comments/`, a draft for a log in a draft's comments folder — and whose `fragment_target` carries that owner, the path the line recorded, and the anchor's `start`, `end`, and `quote`. It reads a legacy `discussion_opened` line that carries a `target` and no fragment target as a whole-target discussion, unchanged. It reads a legacy `thread_reanchored` line as a `fragment_moved` event carrying the same range. The thread id the legacy line carries is the discussion id. The normalisation is idempotent by construction: it is a pure function of the lines, legacy lines stay in the file untouched (CMS-FR-04), and reading one log any number of times, or folding it again after new lines were appended, yields the same discussions. It loses no discussion id, comment, quote, attachment, lock state, resolution state, pending question set, or agent-turn association, because every one of them is keyed by the discussion id and stored where it was. The folding rules of CMS-FR-06 through CMS-FR-09 apply to legacy and current lines together.
84. **CMS-FR-84** A **fragment target** is accepted only when its `owner` is an `artifact` target or a `draft` target, equal to the discussion's own `target`, and when its `end` is greater than its `start`. A fragment target naming a `note` owner, or a `note` target given any fragment target, is refused with a typed `invalid_fragment` for the first case and `not_supported` for the second, and nothing is appended. A fragment target's `path` is the project-relative path of the artifact for an artifact owner and the draft-relative path of the draft prompt or file for a draft owner. Flow, Diff, History, and whole-artifact discussions carry no fragment target.

85. **CMS-FR-HTOA** The **local participant** is one fixed human `Participant`: `login` is the empty string, `display_name` is `Me`, and `email` is absent. It is stamped into `by`, and so into the comment's author snapshot, when no GitHub token is stored. It is not a GitHub account and reaches no GitHub operation. This module keeps no record, file, or setting for it.
86. **CMS-FR-KTHN** A stored participant is never changed after the line is appended. A comment whose saved author is the local participant keeps that snapshot while a token is added or removed. A surface shows such a comment under the identity `resolve_comment_author_identity()` returns now: the GitHub login when it resolves, **Me** otherwise. A saved GitHub participant is displayed as saved.

## Non-functional requirements
- Reading one discussion by its id costs the fold of the one log holding it rather than of the project, so a conversation tab whose owner surface is gone is no more expensive to render than one that still has it.
- One fragment log per artifact keeps opening an artifact a single-file read regardless of how many artifacts the project has comments on.
- Append is the only write on the hot path, so posting a reply costs one line of I/O rather than a rewrite of the conversation.
- Character offsets are counted in Unicode scalar values, so a fragment means the same range to every reader of the file regardless of platform or encoding of the surrounding tooling.
- List commands read the store without network access; only the identity resolution behind a first append in a session can reach GitHub.
- A log grows monotonically with the conversation it records; nothing compacts it, and no operation in this module shortens a file.
- A log line carries a reference to an attachment rather than its content, so a line stays a line and folding a discussion never decodes a payload.
- Content addressing makes storing an attachment idempotent: re-attaching identical bytes costs a digest and no write, so a screenshot circulated through a review occupies the store once.
- Serving an attachment is a read of one file by name; the cost of rendering a conversation's images scales with what is actually shown rather than with the size of the folder holding them.
- An owner's whole-target discussions share one log rather than taking one apiece, so a tab reading them costs a single read however many conversations the target has accumulated.
- A file's whole-target discussions are a second log rather than lines mixed into its fragment log, so a surface wanting only the fragment-level review of a file never folds its whole-target discussions, and a surface wanting only the whole-target discussions never folds its fragment-targeted ones.
- A note's discussion sits in a folder of its own rather than in a log shared with the notes beside it, which is what makes deleting one note's conversation a single recursive removal that cannot take a neighbour's with it.
- Telling a whole panel of notes which of them have conversations is one directory read (CMS-FR-63), so the Notes panel's list commands cost one single enumeration beyond the list itself, rather than growing a read per row.
- `"discussion changed"` carries the folded discussion, so a surface updates from the payload alone. A conversation that nobody has written to produces no event and costs its readers nothing.
- A pending question set is one small JSON file per discussion, read by name and written whole, so a discussion that holds one costs one extra read when it is mounted and nothing at all when it holds none.
- Submitting a set of ten questions is one append of twenty lines and one file removal, so answering a large set costs what answering a small one costs plus the lines it actually carries.
- The walking-skeleton implementation may keep logs and attachments in memory rather than on disk, provided the record shapes, the fold's determinism, the sort order, the emitted event, and the error types above are the ones returned to the UI.
