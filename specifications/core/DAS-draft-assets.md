# Draft assets

**Spec code:** `DAS`

## Intent
The persistence home for the **images an author puts inside a draft's prompt**. An author who explains a problem, a screen, or a user flow shows it more quickly than they describe it, so the New Artifact tab accepts a pasted or dropped image at the cursor, and the prompt carries it as ordinary Markdown. The bytes sit in the draft's own `assets/` folder beside the `files/` folder that holds the prompt (`DRS-draft-storage.md` DRS-FR-01), so an image travels with the draft, is committed with it, and is deleted with it. This module owns that folder, the store and the read of one asset, the **reference semantics** by which a destination in the prompt resolves to an asset, the **housekeeping** that removes an asset no saved reference names any more, and the read path that hands a conversation the bytes of the images a prompt carries (`AGC-agent-conversations.md` AGC-FR-35). Two rules decide everything here. The first is that a reference is read exactly as the renderer reads it — inline images and reference-style images alike, defined before or after their use — so an author who edits the Markdown by hand is understood rather than punished. The second is that housekeeping **refuses to guess**: it deletes an asset only where the asset is clearly this draft's own and clearly unreferenced, and it leaves everything else exactly as it stands. Out of scope: the draft record, the prompt, and the one write path to it, all owned by `DRS-draft-storage.md`; the files a reviewer attaches to a comment, which are `CMS-comments-storage.md`'s blobs under its own folders and are stored, served, and deleted by that module alone; deciding whether a model may be shown an image and what to send when it may not, which is `AGC-agent-conversations.md`'s (AGC-FR-36, AGC-FR-37); rendering an image, choosing where a reference is inserted, and telling the author that one is broken, all owned by `../ui/NAW-new-artifact.md`; and handing an asset to graduation or to any implementation hand-off, which no operation here does and which `GRD-graduation.md` takes none of.

## Contract surface
All Tauri commands below are invoked by the UI. The quoted name is the canonical operation name as it appears in `../ui/NAW-new-artifact.md`'s "Delegated to backend (abstract)" list; the snake_case identifier is the Rust function name. Every path is resolved inside one draft's own directory, obtained from `DRS-draft-storage.md`'s `draft_assets_dir(id)` (DRS-FR-40). This module composes no path from a draft's id and writes nowhere else.

### Record shapes

```
DraftAsset {
  path,                // draft-relative path of the stored file: "assets/<opaque-id>.<ext>"
  reference,           // the Markdown destination that resolves to it from the prompt:
                       //   "../assets/<opaque-id>.<ext>" (DAS-FR-05)
  media_type,          // IANA media type of the stored bytes, e.g. "image/png"
  filename,            // the name the image was supplied under, absent where none was
  bytes                // byte length of the stored content
}

DraftPromptImage {     // one image use resolved out of the saved prompt (DAS-FR-22)
  reference,           // the destination exactly as the Markdown carries it
  alt,                 // the image's alt text; empty where the image has none
  context,             // the text that identifies this image to a reader: its
                       //   Markdown reference together with its alt text. Always
                       //   present, resolved or not (DAS-FR-22)
  resolved,            // bool; true only where the destination resolved to a
                       //   draft-owned asset whose bytes were read (DAS-FR-22)
  asset_path,          // draft-relative path of the asset it resolves to; null
                       //   when `resolved` is false
  media_type,          // the asset's media type; null when `resolved` is false
  filename,            // the asset's supplied filename; absent when none was
                       //   recorded and when `resolved` is false
  data                 // the asset's own bytes, base64-encoded; null when
                       //   `resolved` is false (DAS-FR-22)
}

DraftAssetSweep {      // what one housekeeping pass did (DAS-FR-12)
  scanned,             // files examined under this draft's assets/
  removed,             // files deleted
  retained,            // files left in place: referenced, held, or uncertain
  failed,              // files whose delete was refused (DAS-FR-28)
  complete             // bool; false where the pass ended without deciding every
                       //   file it had scanned (DAS-FR-20, DAS-FR-21)
}

DraftAssetSweepScheduled {   // what the command answers with (DAS-FR-15)
  scheduled,           // bool; true where a pass will run for this draft
  coalesced            // bool; true where this request joined a pass already
                       //   scheduled or already running rather than adding one
}
```

### Tauri commands
Per `../ui/NAW-new-artifact.md`:
- `"store draft image (draft id, media type, filename, data)"` → `store_draft_image(draft_id, media_type, filename, data)` — validates the image, writes its bytes under an opaque generated identifier, and returns the `DraftAsset`, whose `reference` is the destination the surface inserts (DAS-FR-02, DAS-FR-03, DAS-FR-05).
- `"read draft image (draft id, path)"` → `read_draft_image(draft_id, path)` → `{ media_type, filename?, data }`, the stored bytes base64-encoded. It is how a surface renders an image the prompt references (DAS-FR-08).
- `"discard draft image (draft id, path)"` → `discard_draft_image(draft_id, path)` — removes an asset this session stored whose reference never reached the saved prompt. Idempotent (DAS-FR-09).
- `"sweep draft assets (draft id)"` → `sweep_draft_assets(draft_id)` → `DraftAssetSweepScheduled`. It **schedules** one housekeeping pass over that draft and returns the acknowledgement at once, before the pass has read anything: the answer says that a pass will run and whether this request joined one already pending, and it carries no tally, because no tally exists yet. What the pass then did is the `DraftAssetSweep` the internal pass returns to its own caller and reports through `LGC-logging.md`, and it reaches no command return value and no event (DAS-FR-12, DAS-FR-15).

The **typed error vocabulary** is fixed and every one of its values is enumerated in DAS-FR-27, which also states what each leaves on disk. Every command errors with `no_project_open` when no project is open, with `draft_not_found` when `draft_id` names no draft in the active worktree, and with `draft_not_single_file` when the draft it names is inconsistent (`DRS-draft-storage.md` DRS-FR-15). `store_draft_image` and `discard_draft_image` additionally error with `draft_locked_by_graduation` against a draft a non-terminal graduation run holds and against a graduated one (DAS-FR-25). The remaining values are `unsupported_media_type`, `image_too_large`, `malformed_image`, `asset_store_failed`, `asset_not_found`, `path_escape`, and `asset_cleanup_failed` (DAS-FR-03, DAS-FR-04, DAS-FR-07, DAS-FR-08, DAS-FR-09, DAS-FR-28).

### Internal (Rust API, not registered as Tauri commands)
- `read_prompt_images(draft_id)` → `DraftPromptImage[]` — the images the **saved** prompt uses, in the order they occur in it. Each entry carries its `context` and its `alt` whether or not it resolved, and, where it resolved to a draft-owned asset, that asset's `media_type`, `filename`, and `data` — the bytes themselves, base64-encoded, in the returned value rather than behind a further call. The one path by which asset bytes reach a conversation (`AGC-agent-conversations.md` AGC-FR-35). It **refuses nothing**: an unresolved, external, or escaping destination is returned unresolved rather than raised as an error (DAS-FR-07). It writes nothing (DAS-FR-22).
- `sweep_project_draft_assets()` — one pass over every draft of the active worktree, on the terms one pass over one draft runs (DAS-FR-12). It is what the application-start and project-lifecycle triggers of DAS-FR-19 schedule.

## Functional requirements
1. **DAS-FR-01** A draft's assets live in the `assets/` folder of that draft's own directory, scaffolded empty with the draft and deleted with it (`DRS-draft-storage.md` DRS-FR-01, DRS-FR-21). The folder is obtained through `draft_assets_dir(id)` (`DRS-draft-storage.md` DRS-FR-40) and is never composed from the draft's id, because an id says nothing about where its draft is filed (per `DRS-draft-storage.md` DRS-FR-36). It is committed with the draft's record and prompt, skipped by the project scan, and invisible to project search, exactly as the prompt beside it is (per `DRS-draft-storage.md` DRS-FR-04). An asset is an ordinary Git-managed binary file: it carries no merge attribute, and Git alone settles a conflict in one (per `DRS-draft-storage.md` DRS-FR-JPVB). Filing a draft under a folder or moving it between folders carries its assets with it, the folder being inside the draft.
2. **DAS-FR-02** A stored asset is named by an **opaque identifier generated at the store**, followed by the filename extension that belongs to the accepted media type. The supplied filename never reaches the path: it is recorded as metadata alone, so a name cannot collide with a stored asset, cannot direct a write, and cannot carry a path separator or a traversal segment. Two stores of byte-identical images produce two assets with two identifiers, this module holding no content-addressed store.
3. **DAS-FR-03** `store_draft_image` validates before it writes anything. It accepts the image media types the comment attachment path accepts (per `CMS-comments-storage.md` CMS-FR-47) and no other type, refusing anything else with the typed `unsupported_media_type`; it refuses decoded content beyond the same size bound with the typed `image_too_large`; and it refuses data that is not valid base64, that carries no filename extension it can derive, or whose bytes are not the image kind the media type claims, with the typed `malformed_image`. A refused store writes no file, creates no directory entry, and leaves the draft byte-for-byte as it was.
4. **DAS-FR-04** A store is **atomic**, and a store that could not be completed is the typed `asset_store_failed`. The bytes are written to a temporary name inside the draft's own `assets/` folder — a transient file that is draft-owned storage at no point and is named in no commit (per `DRS-draft-storage.md` DRS-FR-ZIVL) — and moved into their final name in one step, so the folder holds either the whole asset or no entry for it at all: a store interrupted part-way, one whose disk is full, one whose folder cannot be created, and one the filesystem refuses each leave **no partial file, no zero-length file, and no entry a later sweep can find**, and each returns `asset_store_failed` carrying a safe diagnostic category rather than the underlying error's own text. A temporary name left behind by an interrupted store is not an accepted image and is therefore retained rather than deleted by a sweep (DAS-FR-12, DAS-FR-16), and the next store simply writes its own. `asset_store_failed` is distinct from the three validation refusals of DAS-FR-03: those say the image was not acceptable and this says the store did not happen, and a caller reports them differently (per `../ui/NAW-new-artifact.md` NAW-FR-51).
5. **DAS-FR-05** The `reference` a store returns is the **destination that resolves to the asset from the prompt**. The prompt sits at the root of `files/` and the asset under `assets/`, so the destination is `../assets/<opaque-id>.<ext>`, and a surface inserting `![alt text](../assets/<opaque-id>.png)` writes a reference that resolves by the ordinary Markdown rule. The command returns it so no caller derives a path of its own.
6. **DAS-FR-06** A prompt's image references are read with **the same Markdown semantics the prompt is rendered with**. Both the inline image form and the reference-style image form are recognised, the reference-style form in its full, collapsed, and shortcut spellings wherever the renderer recognises those, and a **reference definition may stand before or after** the image that uses it — the whole document is read before anything is resolved. A label is matched by the renderer's own normalization of labels, so two spellings of one label resolve to one destination. This is one reading used for every purpose: what a surface renders, what `read_prompt_images` returns, and what housekeeping counts as a reference are the same set.
7. **DAS-FR-07** A destination resolves by the **standard Markdown relative-path rule** from the prompt's own location inside `files/`. A data URI, an absolute path, a project-relative path, an external address, and any path that leaves the draft's own directory all resolve to **no draft-owned asset**. What follows from that depends on who asked, and the two answers are deliberately different because the two questions are:
    A **direct read** — `read_draft_image`, where a caller has named a path and expects bytes back — is **refused**, with the typed `path_escape` for a destination that leaves the draft and for an absolute, project-relative, or data destination, and with `asset_not_found` for one that stays inside and names nothing. Nothing is opened, nothing is followed, and no address is requested, so a surface can never be handed the content of a file the draft does not own.
    **Resolution** — what `read_prompt_images` performs for a conversation (DAS-FR-22) and what housekeeping performs over the saved prompt (DAS-FR-12) — **refuses nothing and raises nothing**. It classifies each destination and carries the classification forward: for a conversation the reference becomes an unresolved entry carrying its own safe metadata and no bytes, so an agent still learns that a picture stands there and what the prompt calls it (per `AGC-agent-conversations.md` AGC-FR-37); for housekeeping it is simply not evidence about any file, and it protects and condemns nothing (DAS-FR-16). One unsafe destination in a prompt therefore costs neither the rest of the prompt's images nor the whole pass, while no unsafe destination anywhere causes a byte to be read from outside the draft. No route here reads or writes outside the draft it names.
8. **DAS-FR-08** `read_draft_image(draft_id, path)` returns the stored bytes together with the media type and the recorded filename. `path` names a file directly inside that draft's `assets/`; the same destination the prompt carries resolves through the rule of DAS-FR-07 before the read. A path naming nothing there is the typed `asset_not_found`, and a path leaving the draft is the typed `path_escape`. The read is the only way an asset's content leaves this module to a surface.
9. **DAS-FR-09** `discard_draft_image(draft_id, path)` removes one asset, and removes it only where the **saved prompt holds no valid reference to it** (DAS-FR-06). It is the caller's way to take back an insertion that did not finish, and it is **idempotent**: a path naming nothing is reported discarded having had nothing to discard, so a retried insertion never fails on work already undone. An asset a saved reference still names is left in place and reported as retained rather than deleted. It is **atomic per file**: the asset is gone or it is untouched, never truncated and never half-removed. A removal the filesystem refuses is the typed `asset_cleanup_failed` carrying a safe diagnostic category, and it leaves the asset exactly as it was, so the caller may retry it, leave it to the next sweep, or report it (DAS-FR-28). A `path` that leaves the draft is `path_escape` and removes nothing, on the terms of DAS-FR-07.
10. **DAS-FR-10** An insertion is ordered so that **no prompt ever references an asset that was not stored**. The asset is stored first; only then is the Markdown reference written into the prompt through `DRS-draft-storage.md`'s single save path (DRS-FR-12). Where that save fails and no earlier valid reference names the asset, the asset is discarded (DAS-FR-09), so a failed insertion leaves neither a reference nor a file. Where the save fails and an earlier reference does name the asset, the asset stays, the failure having cost the prompt nothing that was already in it.
11. **DAS-FR-11** An asset is protected by **every** valid reference to it, not by the first. A prompt referencing one asset in three places keeps that asset while any one of the three stands, and the asset becomes removable only after the last of them is gone. Removing one of several references therefore deletes nothing.
12. **DAS-FR-12** `sweep_draft_assets(draft_id)` is the housekeeping pass. It reads the draft's **saved** prompt, resolves every reference in it (DAS-FR-06, DAS-FR-07), and then deletes a file under that draft's `assets/` only where **all** of these hold together: the file lies directly inside that draft's own `assets/` folder; it is an ordinary file rather than a directory or a symbolic link; its extension and its content are one of the image kinds DAS-FR-03 accepts; it is not held (DAS-FR-14); and no resolved reference in the saved prompt names it. A file failing any one of them is retained. The pass produces a `DraftAssetSweep` naming what it examined, what it removed, what it retained, what it could not delete (DAS-FR-28), and whether it decided every file it scanned; that tally is returned to the internal caller and reported through `LGC-logging.md`, and it is **not** what the Tauri command answered with (DAS-FR-15).
13. **DAS-FR-13** Housekeeping decides on the **saved prompt** and never on an editor's buffer. An asset is protected from the moment the reference to it is saved, which is why the surface that inserts one writes the prompt immediately rather than waiting its ordinary rest out (per `../ui/NAW-new-artifact.md` NAW-FR-51), and why an asset stored before that write is held until it lands (DAS-FR-14). A prompt this module cannot read, or whose bytes do not decode, protects everything: the pass deletes nothing at all (DAS-FR-16).
14. **DAS-FR-14** An asset this module stored in the running session is **held** from the moment it is stored until the insertion that asked for it settles — the draft's prompt is next saved, `discard_draft_image` removes the asset, or the running application ends. A held asset is skipped by every sweep, so a pass that runs in the instant between a store and the write carrying its reference deletes nothing. The hold is memory of the running session: it is written to no file, it survives no relaunch, and it protects nothing afterwards, the saved prompt being what protects an asset from then on (DAS-FR-13).
15. **DAS-FR-15** A pass runs **asynchronously** and off the path that triggered it. It blocks no keystroke, no prompt render, no project open or close, and no draft open or close. The command's **return contract is an acknowledgement and not a result**: `sweep_draft_assets` returns a `DraftAssetSweepScheduled` the moment the pass is queued — saying that a pass will run and whether this request was coalesced into one already pending — and it returns it **before** the pass has read the prompt, listed the folder, or deleted anything. A caller therefore learns that housekeeping was asked for and never what it found: no command return value, no event, and no payload anywhere carries a `DraftAssetSweep`, which reaches the internal caller and `LGC-logging.md` alone (DAS-FR-12, DAS-FR-21). A caller that wants the outcome reads the log; a surface wants neither and asks for neither (per `../ui/NAW-new-artifact.md` NAW-FR-55). A scheduled pass that never runs — the project closed under it, the application quit — is reported incomplete rather than as having found nothing (DAS-FR-20). Passes for one draft that are triggered close together are **coalesced into one**, and a pass is safe to run concurrently with another pass and with any other operation on the draft: each candidate is decided on its own, the decision is re-checked immediately before the delete, and an asset that gained a reference in between is retained. Running the sweep twice over an unchanged draft removes exactly what running it once removed.
16. **DAS-FR-16** Everything uncertain is **left alone**. None of these is ever grounds for deleting anything: a malformed image reference; a reference-style image whose label matches no definition; a reference definition naming a destination that does not exist; a destination that is external, absolute, project-relative, a data URI, or a path leaving the draft; a symbolic link; a directory; a file under `assets/` whose extension or content this module does not recognise as an accepted image; a prompt that cannot be read or does not decode; and a draft reported inconsistent (per `DRS-draft-storage.md` DRS-FR-15). A pass that cannot read the prompt deletes nothing whatever else it found, because a set of references it could not read is not evidence that an asset is unreferenced.
17. **DAS-FR-17** A **valid reference definition** and a **valid link destination** protect a draft-owned asset exactly as an image use does. An author who defines a label the document has stopped using, or who links a file rather than embedding it, keeps that file. What protects an asset is a valid destination resolving to it anywhere in the saved prompt, whichever construct carries that destination.
18. **DAS-FR-18** A pass **never deletes a file outside the draft's own `assets/` folder**. It deletes nothing under `files/`, `comments/`, `proposals/`, or `history/`, nothing elsewhere under the drafts root, and nothing anywhere in the project. It removes files alone and removes no directory, the `assets/` folder itself included, so a draft whose every image has gone still holds an empty `assets/`.
19. **DAS-FR-19** A pass is scheduled at five moments and at no other: **once after the active project is loaded** at application start, over every draft of the active worktree (`sweep_project_draft_assets`); on each **project open** and on each **project close**; and on each **draft open** and on each **draft close** (per `../ui/NAW-new-artifact.md` NAW-FR-55). A close-triggered pass runs against the project or the draft **before its storage context is released** (per `PST-project-storage.md` PST-FR-14, PST-FR-30), so it addresses material that still resolves rather than material that has already gone.
20. **DAS-FR-20** Application shutdown **never reports success for work it did not complete**. A pass still running at shutdown is given the chance to finish and is then abandoned where it stands; an abandoned pass leaves every asset it had not yet decided untouched and produces a `DraftAssetSweep` whose `complete` is **false**, recorded as incomplete through `LGC-logging.md` and naming the draft and what it had examined. Nothing reports a completed sweep for it, and the next trigger simply runs the pass again (DAS-FR-15).
21. **DAS-FR-21** A **failed pass changes nothing about what opens or closes**. A prompt it could not read, a folder it could not list, a delete it was refused (DAS-FR-28), an unavailable store, and a draft that resolved to nothing each end that pass with `complete` false and leave the project, the draft, and the editor to open or close exactly as they would have. The command that scheduled it had already answered and answered successfully, a scheduling being what it reported (DAS-FR-15), so a failed pass changes no return value anywhere. The failure is reported through `LGC-logging.md` at `WARN` and through no other route: routine cleanup raises no blocking error, opens no dialog, and puts nothing in front of the author.
22. **DAS-FR-22** `read_prompt_images(draft_id)` returns the images of the **saved** prompt in the order they occur in it, and it returns **the bytes themselves** rather than a handle to fetch them by. Every entry carries three things whatever became of its destination: the `reference` the Markdown holds, the `alt` text the image was written with, and the `context` — the reference together with that alt text — which is the text a caller places beside the image so a model reads a picture with what the prompt called it (per `AGC-agent-conversations.md` AGC-FR-35). An entry whose destination **resolved** to a draft-owned asset carries `resolved` true together with the asset's `media_type`, its `filename` where one was recorded, and its `data`: the asset's own bytes, base64-encoded, read at this call and carried in the returned value, so the caller assembling a request needs no second call and no path of its own. An entry whose destination resolved to **no** draft-owned asset — missing, malformed, unresolved by label, external, absolute, project-relative, a data URI, or escaping the draft — carries `resolved` false, a null `asset_path`, a null `media_type`, and a null `data`, and it is still returned in its own position with its `context` intact, so the caller carries safe metadata where the picture would have been rather than dropping the fact that one is there (per `AGC-agent-conversations.md` AGC-FR-37). No such entry is an error and none refuses the call (DAS-FR-07), and no address is ever requested. An asset whose bytes cannot be read is returned unresolved on exactly these terms, one unreadable file costing the caller nothing but that one image. The call reads no comment log, no history, and no proposal, writes nothing, emits nothing, and is registered as no Tauri command, so no frontend call reaches it.
23. **DAS-FR-23** No operation here reaches graduation, an implementation hand-off, or any agent path but the conversational one. `GRD-graduation.md` captures the prompt's text alone and reads no asset, no phase of a graduation run calls this module, and `read_prompt_images` has exactly one consumer, the conversational input assembly of `AGC-agent-conversations.md` (AGC-FR-35).
24. **DAS-FR-24** No asset is surfaced on the prompt-mutation channel of `DRS-draft-storage.md` (DRS-FR-28), which carries a draft's prompt paths alone, so storing, reading, or deleting an asset costs the drafts index no work. Storing and deleting an asset emit no `"drafts changed"` event either: an asset is not the draft's record and not its prompt, and the write that carries a new reference into the prompt already emits for the change the author made (per `DRS-draft-storage.md` DRS-FR-22).
25. **DAS-FR-25** The graduation lock reaches this module exactly as it reaches the prompt. `store_draft_image` and `discard_draft_image` against a draft a non-terminal graduation run holds return `draft_locked_by_graduation` and change nothing, on the terms `DRS-draft-storage.md` DRS-FR-19 refuses a prompt write, and both are refused against a draft whose **graduated** status stands, whose whole content is retained as the record of what a published specification was written from (per `DRS-draft-storage.md` DRS-FR-20). The refusal lasts exactly as long as that status does: a draft released when every run that published for it reached `discarded` or `failed` takes image writes again, on the same terms its prompt does (per `DRS-draft-storage.md` DRS-FR-KQTW). `read_draft_image` and `read_prompt_images` answer for a locked and a graduated draft exactly as for any other, reading being what a run and an author both do. A sweep against either **deletes nothing**: the prompt cannot change, so there is nothing to collect, and a run in flight is reading the material.
26. **DAS-FR-26** Every command in the contract surface exists with a typed payload in the walking-skeleton build. A stub may keep assets in a temporary directory and sweep nothing, provided it returns the documented shapes and still refuses the media types, sizes, and paths above.

27. **DAS-FR-27** The typed errors of this module are exactly these, and each says what it left on disk. `no_project_open`, `draft_not_found`, and `draft_not_single_file` are refusals to resolve, and nothing was read or written. `draft_locked_by_graduation` refuses a write against a locked or graduated draft, and nothing was written (DAS-FR-25). `unsupported_media_type`, `image_too_large`, and `malformed_image` refuse an image before any byte is written, and `assets/` is what it was (DAS-FR-03). `asset_store_failed` says the store was attempted and did not complete, and `assets/` holds no entry for it (DAS-FR-04). `asset_not_found` says the path named nothing under the draft's `assets/`, and nothing was removed or read. `path_escape` says the path was not the draft's to reach, and nothing outside the draft was opened, followed, or requested (DAS-FR-07). `asset_cleanup_failed` says a removal was attempted and refused, and the asset is byte-for-byte what it was (DAS-FR-09, DAS-FR-28). Every one of them carries a safe diagnostic category and never the underlying error's own text, an operating-system error string being where a path outside the draft would otherwise reach a log. No operation of this module reports a failure by any other means: none returns a partial result, none reports success for work it did not do, and none leaves the caller to infer an outcome from what it finds on disk afterwards.
28. **DAS-FR-28** A **cleanup failure is per file and stops nothing**. A sweep that cannot delete one candidate counts it as failed, leaves it exactly as it was, and carries on with the candidates it has left, so one locked or refused file never costs the pass the rest of its work; the resulting `DraftAssetSweep` names how many failed and carries `complete` false, and the failure is recorded through `LGC-logging.md` at `WARN` (DAS-FR-21). A pass that could not read the prompt or list the folder decided nothing and deletes nothing at all (DAS-FR-16). `discard_draft_image` reports the same condition to its caller as the typed `asset_cleanup_failed` (DAS-FR-09), because a caller that asked for one removal is owed the answer for it, while a sweep nobody asked for reports through diagnostics alone. A failed cleanup is never retried inside the pass that met it and is never escalated: the next trigger simply runs the pass again over a draft that still holds the file (DAS-FR-15).

## Non-functional requirements
- An asset is an ordinary file in an ordinary folder inside the draft, so an author can find, copy, or recover one with a file manager if the application will not open, exactly as they can the prompt beside it.
- Housekeeping costs one read of a draft's prompt and one directory listing of its `assets/`. A draft with no images costs the listing alone, and a project of fifty drafts costs fifty of each rather than a scan of anything larger.
- A sweep never holds a lock that a keystroke, a render, or a lifecycle step waits on. The worst a slow pass can do is finish late.
- Reading an image for rendering is one file read, taken when the surface actually shows that image, so a prompt carrying many pictures costs nothing for the ones the author has not scrolled to.
- Nothing here contacts the network. No destination is fetched, no remote address is resolved, and an external image reference is metadata about the prompt rather than something to retrieve.
- The bound on an image's size is the comment attachment bound (per `CMS-comments-storage.md` CMS-FR-47), so one rule governs how large a picture the application accepts, wherever the author put it.
