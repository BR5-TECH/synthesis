# Draft history

**Spec code:** `DHS`

## Intent
The persistence home for a **draft's own version history**: the immutable snapshots of the single prompt a draft holds, taken at the one moment a version of that prompt is settled — when the author accepts a change an agent proposed, which records the prompt as it stood before that change as well as the prompt the change produced. A draft nobody has proposed a change to therefore holds no snapshot at all: its live prompt is its `Original`, and there is nothing it could have moved on from. It exists because refining a prompt with agents is the whole of what a draft is for (`../ui/NAW-new-artifact.md`), and a refinement the author accepted is a version they will want to read back, compare against, and be sure of; the ordinary typing between refinements is not. Because an acceptance has to land in three stores at once — the prompt's bytes, this history, and the proposal's decided state — this module also owns the **acceptance transaction** and the small durable journal that makes it recoverable: the journal is written before either store is touched, the transaction commits at one atomic rewrite of it, and the decision comment the conversation is owed is appended afterwards with an identity minted in advance, so a crash at any point reconciles deterministically to either the whole acceptance or none of it. Every entry this module settles is also **counted**: at the moment an entry becomes exposed, one line naming that entry is appended to the draft's statistics log (`DSS-draft-statistics-storage.md`), so an author can later read how many versions of a prompt were settled without this module keeping a second record or the count being reconstructed from the folder. The line carries the entry's identity and nothing of its bytes. Out of scope: the application-wide artifact and Git history, which is `../ui/HVW-history-viewer.md`'s surface and `HIS-history.md`'s store and shares nothing with this one; the History rail itself — its labels, its read-only snapshot view, and its errors — which is `../ui/NAW-new-artifact.md`'s; the draft, its record, and the one write path for its prompt, all `DRS-draft-storage.md`'s; the proposal, its candidate, its one-pending rule, and what its decision comment says, all `DCP-draft-change-proposals.md`'s; the conversation log this module appends one line to, which is `CMS-comments-storage.md`'s and stays append-only, no line of it ever being rewritten or removed to undo anything here; and any history of decisions, feedback, or rejected proposals, none of which is a version of the prompt and all of which the conversation already holds.

## Contract surface
The module owns the `history/` folder inside a draft's own directory — obtained from `DRS-draft-storage.md` (DRS-FR-36) rather than composed from the draft's id — and the two Tauri commands and one event below. Names match `../ui/NAW-new-artifact.md`'s "Delegated to backend (abstract)" line byte-for-byte. Every path this module resolves is resolved against the project's **active worktree** (per `WTC-worktree-context.md` WTC-FR-03), the same root `DRS-draft-storage.md` resolves against.

### Record shapes

```
DraftHistorySource =
  | { kind: "original" }
  | { kind: "proposal_accepted", proposal_id, hunk_id, agent: Participant }  // CMS's shape

DraftHistoryEntry {
  id,            // opaque, generated at creation, stable for the entry's lifetime
  draft_id,
  seq,           // 1 for Original, increasing by one per entry; the sort key
  path,          // draft-relative path the prompt occupied when the snapshot was taken
  source: DraftHistorySource,
  created_at,    // RFC 3339 UTC
  byte_len,      // length of the snapshot payload
  sha256         // FSA-filesystem-access.md::sha256_file of the payload
}

LivePrompt {
  path,
  byte_len,
  sha256,
  matches_latest    // the live prompt's bytes are the newest entry's bytes;
                    // true where the draft holds no entry (DHS-FR-07)
}

DraftHistoryList {
  entries: [DraftHistoryEntry],   // ascending seq, oldest first
  live: LivePrompt
}
```

### Tauri commands
- `"list draft history"` → `list_draft_history(draft_id)` → `DraftHistoryList` — every exposed entry oldest first, together with the live prompt's own digest. Reads manifests and digests the prompt; reads no snapshot payload (DHS-FR-10).
- `"load draft history entry"` → `load_draft_history_entry(entry_id)` → `{ content, sha256 }` — one entry's snapshot as UTF-8 text together with the digest it was verified against (DHS-FR-11).

Errors are typed: `no_project_open`, `draft_not_found`, `draft_not_single_file`, `entry_not_found`, `snapshot_corrupt`, `acceptance_in_progress`, `acceptance_incomplete`, `history_recovery_failed`, and `write_failed`.

### Events
- `"draft history changed"` — carries `{ draft_id, entry }`, the entry when one became visible and `null` when reconciliation removed one (DHS-FR-22).

### The statistics line
Beside the event above, an entry that becomes exposed contributes one `draft_history_entry` line to the draft's statistics log through `DSS-draft-statistics-storage.md`'s `record_statistics_event` (DSS-FR-EKZI):

```
DraftHistoryStatisticsEvent {
  entry_id,      // the DraftHistoryEntry's own id; the stable identity of the line
  seq,           // the entry's seq
  source_kind    // "original" | "proposal_accepted"
}
```

It carries no path, no digest, no byte of a snapshot, and no proposal rationale (DHS-FR-ZQNM).

### Internal (Rust API, not registered as Tauri commands and unreachable from the frontend)
- `apply_acceptance(input)` → `AcceptedOutcome` — the whole acceptance transaction of DHS-FR-13 through DHS-FR-17, called by `DCP-draft-change-proposals.md` (DCP-FR-11) and by nothing else. Its `input` carries the draft, the proposal, the hunk being accepted, the prompt's draft-relative path, the prompt's new bytes with that hunk applied, the proposal record as it is to stand, whether this decision resolves the proposal, and, where it does, the decision comment's body and human `Participant` as `DCP-draft-change-proposals.md` composed them (DCP-FR-15). Its `AcceptedOutcome` carries the entry that was created — absent where the acceptance changed no persisted byte (DHS-FR-16) — the `Original` it settled on its way past where it settled one (DHS-FR-07), and the id of the comment that was appended where one was due.
- `record_history_statistics(draft_id, entry)` — appends the statistics line of the Contract surface for one newly exposed entry (DHS-FR-ZQNM). It is called from the same point `"draft history changed"` is emitted from, is asynchronous, and cannot fail the acceptance.
- `reconcile(draft_id)` — the deterministic recovery of DHS-FR-18 through DHS-FR-21, run before every operation that reads or writes a draft's history or its proposals.
- `history_dir(draft_id)` — the `history/` folder of DRS-FR-01 inside that draft's directory, resolved through `DRS-draft-storage.md::draft_history_dir` (DRS-FR-36).

## Functional requirements
 1. **DHS-FR-01** A draft's history lives in the `history/` folder of that draft's own directory, alongside the `draft.toml`, `files/`, `comments/`, `proposals/`, and `conversation.jsonl` it already holds (per `DRS-draft-storage.md` DRS-FR-01) and wherever in the drafts hierarchy the draft is filed. Each entry is two files: `<entry-id>.toml` holding the `DraftHistoryEntry` manifest of the Contract surface, and `<entry-id>.snapshot` holding the prompt's bytes. The manifest and the payload are separate files because the payload is a document and a manifest is not, and a manifest carrying a document in a field would be read on every list.
 2. **DHS-FR-02** The whole folder is **private draft storage** (per `DRS-draft-storage.md` DRS-FR-ZIVL, DRS-FR-WYIN): Git ignores it, no commit names it, the project scan skips it, and it is deleted with the draft (DRS-FR-21). A draft's history stays in the checkout that settled it. An acceptance commits nothing. The accepted prompt reaches the repository through the next draft-event commit of its draft (per `PST-project-storage.md` PST-FR-DQZT) or through the author's own commit.
 3. **DHS-FR-03** `journal.toml` and `journal.prior` are **reserved names** in that folder, holding the acceptance journal and the bytes a rollback restores (DHS-FR-13). An entry's id is opaque and well-formed, so no entry's manifest or payload can be given either name, and no entry is ever mistaken for the journal or the journal for an entry. Both are **transient** rather than draft data: they stand only while an acceptance is in flight, they are removed when it settles (DHS-FR-14), and they are named in no commit (per `DRS-draft-storage.md` DRS-FR-ZIVL).
 4. **DHS-FR-04** An entry's `id` is opaque, generated at creation, and stable for its lifetime. It is derived from neither the draft, nor the path, nor the content, so two entries holding identical bytes are two entries.
 5. **DHS-FR-05** Entries are ordered by `seq`, which is `1` for the draft's `Original` entry — the first thing the first acceptance settles (DHS-FR-07) — and one greater than the highest the draft holds for every entry after it. The order is total and deterministic, so the rail renders the same sequence on every list and after every restart without sorting on a timestamp two entries could share.
 6. **DHS-FR-06** An entry is **immutable**. No operation in this module rewrites a manifest or a payload once both are on disk; an entry is removed only by the rollback of an uncommitted acceptance (DHS-FR-19) and by the deletion of the draft (DHS-FR-02). `Original` in particular is never rewritten, whatever the prompt later becomes.
 7. **DHS-FR-07** The **`Original` is the prompt as it stood before the first change was accepted**, and it comes into existence with that acceptance and by no other path: where a draft holds no entry, the acceptance of DHS-FR-15 writes one carrying `seq = 1`, `source = { kind: "original" }`, the prompt's current draft-relative path, and the exact bytes the prompt holds at the moment the transaction begins — the bytes it is about to supersede — before it writes the version that supersedes them. Creating a draft settles no version: a snapshot taken there would be a version of nothing, recorded before the author had written a word and stale from the first one they type. Until a change is accepted a draft therefore holds **no entry at all**, its live prompt being the `Original` (per `../ui/NAW-new-artifact.md` NAW-FR-38), and a draft that is graduated or deleted before any change is accepted was one version of one prompt for its whole life. Every acceptance after the first finds an `Original` already standing and writes only the version it produced, so a draft carries exactly one `Original` for its whole life whatever the prompt later becomes (DHS-FR-06).
 8. **DHS-FR-08** Exactly one operation creates an entry: an **accepted hunk** that changes the prompt's persisted bytes, which creates the version it produced and — where the draft holds none — the `Original` it superseded (DHS-FR-07, DHS-FR-16). The author's own typing, recording a proposal, editing or rejecting a hunk, renaming, archiving, moving, or graduating a draft each create none.
 9. **DHS-FR-09** An entry is a **complete, self-consistent snapshot of the whole prompt**: its exact draft-relative path and the whole of its bytes as they stood, never a patch, a hunk, or a summary. One acceptance creates one entry, a draft holding exactly one prompt file (per `DRS-draft-storage.md` DRS-FR-11). The payload preserves those bytes exactly — empty content, trailing whitespace, a missing final newline, and the line-ending convention the save path applied (per `DRS-draft-storage.md` DRS-FR-12) all survive byte-for-byte, and nothing is trimmed, re-indented, or re-encoded on the way in or on the way out.
10. **DHS-FR-10** `list_draft_history(draft_id)` returns every exposed entry oldest first together with the live prompt's own path, length, and digest. It reads the manifests and digests the prompt with `FSA-filesystem-access.md::sha256_file`; it reads no `.snapshot` payload, so a draft carrying a long history costs a list one directory walk however large its prompt has grown. `matches_latest` is true when the live prompt's digest equals the newest entry's, which is what tells the rail whether the author has typed since the last settled version (per `../ui/NAW-new-artifact.md` NAW-FR-37); it is true for a draft holding no entry, whose live prompt is the `Original` and has moved on from nothing.
11. **DHS-FR-11** `load_draft_history_entry(entry_id)` returns one entry's payload as UTF-8 text. It verifies the payload against the manifest's `sha256` and its `byte_len` before returning, and a mismatch — or a payload that is absent, or that does not decode — is a typed `snapshot_corrupt` naming the entry, returned instead of the text. Content is loaded here rather than by the list, so a rail that is open costs nothing until an entry is actually selected (per `../ui/NAW-new-artifact.md` NAW-FR-40).
12. **DHS-FR-12** An entry is **exposed** — returned by `list_draft_history`, loadable by `load_draft_history_entry`, and counted by the rail — unless the standing journal is in phase `prepared` and names it (DHS-FR-14), either as the version it will produce or as the `Original` it settles. An entry written for an acceptance that has not committed is therefore invisible to every reader, so no partial acceptance is ever presented as a version of the prompt and no `Original` is exposed for a change that may yet be undone.
13. **DHS-FR-13** The journal is one file, `history/journal.toml`, holding at most one **acceptance operation** for the draft at a time, beside `history/journal.prior` holding the prompt's bytes as they stood before the operation began. The record carries an opaque `operation_id`, the draft, the proposal, the prompt's path, the digest of the prior bytes, the digest of the candidate as the save path will persist it, the pre-minted `entry_id` of the entry the operation will create where one is due and the pre-minted id of the `Original` it will settle where one is due (DHS-FR-07), the hunk being accepted, whether this decision **resolves** the proposal, the pre-minted `comment_id` and `event_id` of the decision comment together with its body and its human `Participant` where one is due, and the operation's `phase`. It is not a user-visible history and is exposed by no command, no event, and no surface: the rail lists entries and nothing else, and the record of a decision stays the conversation's alone (per `DCP-draft-change-proposals.md` DCP-FR-15).
14. **DHS-FR-14** An acceptance moves through three phases and commits at one of them. `prepared` says the operation has begun and nothing it did is final. `committed` says the prompt, the entry, and the proposal's accepted state are all final together — it is written by one atomic rewrite of the journal and is the transaction's **commit point**. `complete` says the decision comment has been appended too, after which the journal and its prior payload are removed. Every write of the journal and of the prior payload goes through `FSA-filesystem-access.md`'s temp-file-and-rename primitives (FSA-FR-04), which is what makes a phase transition either wholly visible or not visible at all to the next process to read it.
15. **DHS-FR-15** `apply_acceptance(input)` performs the transaction in one fixed order, and the order is the whole of what makes it recoverable: it normalises the candidate on the terms the save path will persist it (per `DRS-draft-storage.md` DRS-FR-12) and reads the prompt's current bytes; it writes `journal.prior` and then the journal in phase `prepared`; it writes the `Original`'s payload and then its manifest where the draft holds no entry (DHS-FR-07); it writes the entry's payload and then its manifest; it writes the prompt through `DRS-draft-storage.md`'s own save path (DRS-FR-12), which stays the only write path for a draft's prompt whoever composed the text; it writes the proposal's record as `accepted`; it rewrites the journal to `committed`; it appends the decision comment where this decision resolves the proposal; and it rewrites the journal to `complete` and removes it. The only artifact-side write any other reader can observe before the commit point is the prompt itself, and a failure or a crash in that window is undone by the rollback of DHS-FR-19.
16. **DHS-FR-16** An acceptance whose normalised candidate is byte-identical to what the prompt currently holds **creates no entry** — not the version, and not the `Original` either, there being nothing superseded to settle. The transaction still runs — the hunk is accepted, the decision comment is appended where this decision resolves the proposal, and the draft's own save path is still called so its `updated_at` and its indexing follow (per `DRS-draft-storage.md` DRS-FR-22, DRS-FR-28) — but the journal carries no entry id of either kind, nothing is written under `history/`, and no `"draft history changed"` is emitted. A version is a change to the prompt, so an acceptance that changed nothing adds no duplicate of the version already at the head of the rail.
17. **DHS-FR-17** A failure before the commit point returns a typed `write_failed` having rolled the operation back (DHS-FR-19), so the prompt is byte-for-byte what it was, no entry exists, the hunk is undecided again, and no comment was appended. A failure of the comment append **after** the commit point is retried once within the call; where the retry also fails the operation is left journaled at `committed` and a typed `acceptance_incomplete` is returned, which arises only from the decision that resolves the proposal, the prompt and the entry standing and the proposal reading `accepted`, because the acceptance did land and reporting otherwise would be a lie about the author's own draft. The refusals that would make the append impossible — no identity resolving, and a locked conversation — are checked before the transaction begins and refuse it there (per `DCP-draft-change-proposals.md` DCP-FR-15), so the retried case is an I/O failure rather than an ordinary one.
18. **DHS-FR-18** `reconcile(draft_id)` runs before `list_draft_history`, before `load_draft_history_entry`, before every command of `DCP-draft-change-proposals.md` that lists or decides a proposal, and before `apply_acceptance` itself. It reads the journal and does exactly what the phase it finds requires, and it is **idempotent**: running it twice does what running it once did, and a reconciliation interrupted part-way is completed by the next run. A draft carrying no journal reconciles in one absent-file read, so the ordinary case costs nothing.
19. **DHS-FR-19** A journal found in phase `prepared` is **rolled back**. Where the prompt's digest is the operation's candidate digest the prior bytes are restored through the save path; where it is the prior digest the prompt is already as it was and nothing is written to it. The manifest and payload of both entries the operation could have created — the version and the `Original` — are removed if any of them reached disk, so a rolled-back first acceptance leaves behind no `Original` for a version that was never superseded; that hunk's ledger row is restored to undecided with its `decided_at` null and every hunk an earlier operation decided is left exactly as it was, and the journal and its prior payload are removed. **No decision comment is appended**, and none can have been, the append standing after the commit point — which is why no line of the conversation ever has to be rewritten or removed to undo an acceptance (per `CMS-comments-storage.md` CMS-FR-04).
20. **DHS-FR-20** A journal found in phase `committed` is **rolled forward**. The decision comment is appended with the `comment_id` and `event_id` the journal minted, so an append that had already landed before the crash contributes nothing a second time — the fold applies the first event it sees for an `event_id` and ignores every later one (per `CMS-comments-storage.md` CMS-FR-06) — and the journal is then rewritten to `complete` and removed. A journal found in phase `complete` is removed. Neither path writes the prompt, creates an entry, or changes the proposal's state, all three having been settled at the commit point.
21. **DHS-FR-21** Reconciliation never duplicates a comment and never duplicates an entry: the comment is idempotent by its pre-minted `event_id` (DHS-FR-20) and each entry by its own pre-minted id, which names the same two files however many times the operation is resumed. A reconciliation that cannot complete — the prior payload unreadable, a restoring write refused, the conversation's own storage unavailable — returns a typed `history_recovery_failed` naming the draft, leaves the journal standing so the next run tries again, and is surfaced with a retry (per `../ui/NAW-new-artifact.md` NAW-FR-41). Every command of this module and every decision command of `DCP-draft-change-proposals.md` returns that error rather than answering from a state it could not reconcile.
22. **DHS-FR-22** `"draft history changed"` is emitted when an entry becomes exposed — once per entry, oldest first, at the commit point of the acceptance that created it, so a first acceptance emits two and every one after it emits one — carrying the draft and that entry, so a surface showing the draft redraws from the payload without a read of its own. It is emitted **once** carrying a null entry when reconciliation removed the entries of an uncommitted operation (DHS-FR-19), however many it removed, a reader answering a withdrawal by re-reading the list either way. It is emitted nowhere else: not at the creation of a draft, which settles no version (DHS-FR-07), not for a journal phase transition, not for an acceptance that created no entry (DHS-FR-16), and not for an operation that was refused.
23. **DHS-FR-23** `apply_acceptance` refuses with a typed `acceptance_in_progress` while a journal stands for the draft that reconciliation could not clear, so two acceptances never interleave over one prompt and one journal is always enough. Because reconciliation runs first (DHS-FR-18), the refusal is reached only where recovery itself is blocked.
24. **DHS-FR-24** Every write this module performs goes through `FSA-filesystem-access.md` primitives — `write_bytes_atomic` for a payload and for the prior bytes, `write_toml_atomic` for a manifest and for the journal, `delete_path` for the removals above — and is subject to FSA's path-escape rejection (FSA-FR-10). This module performs no raw `fs::write`, `fs::remove`, or `fs::rename` call and writes nothing outside the draft's own `history/` folder, save for the prompt it writes through `DRS-draft-storage.md`'s save path, the proposal record it writes in the transaction of DHS-FR-15, and the one comment it appends through `CMS-comments-storage.md`'s agent-and-human write path (CMS-FR-26).
25. **DHS-FR-25** Every command errors with a typed `no_project_open` when no project is open, with `draft_not_found` when `draft_id` names no draft in the active worktree, with `draft_not_single_file` when the draft it names is not the valid single-prompt draft `DRS-draft-storage.md` DRS-FR-11 requires, and with `entry_not_found` when `entry_id` names no entry of it. Changing the active worktree re-resolves the history folder against the new content root exactly as the drafts themselves are re-resolved (per `DRS-draft-storage.md` DRS-FR-05), so a draft's history in one worktree is invisible from another.
26. **DHS-FR-26** Every operation emits through `LGC-logging.md`'s internal API under the `backend` domain: an `INFO` record when an entry is created and when an acceptance commits, naming the draft, the entry, the operation, and the proposal; a `WARN` record when an operation refuses or a reconciliation rolls an operation back or forward, naming the same and the reason. **No record carries a byte of a snapshot, of the prompt, of a candidate, of a rationale, or of any feedback**, all of which are material an author or a model composed.
27. **DHS-FR-27** Nothing in this module reaches the network, contacts an AI integration, or dispatches an agent turn. The one credential it touches is the GitHub identity the decision comment's append resolves through `CMS-comments-storage.md` (CMS-FR-12), resolved by `DCP-draft-change-proposals.md` before the transaction begins (DHS-FR-17) and carried into it rather than resolved again.
28. **DHS-FR-ZQNM** Every entry that becomes **exposed** (DHS-FR-12) contributes exactly one `draft_history_entry` line to that draft's statistics log, appended at the same commit point `"draft history changed"` is emitted at and carrying the entry's own id as its stable identity, its `seq`, and its `source_kind`. A first acceptance therefore contributes **two** lines — the `Original` it settled and the version it produced, in that order — and every acceptance after it contributes **one**. An acceptance that creates no entry (DHS-FR-16) contributes **none**, there being no version to count; a recorded proposal, an edited candidate, a rejected proposal, a pending proposal, the creation of a draft, the author's own typing, a rename, an archive, a move, and a graduation each contribute none, none of them settling a version (DHS-FR-08). An operation rolled back before its commit point contributes none, its entries never having been exposed, and reconciliation neither appends a line for a withdrawn entry nor removes one already appended — the fold reconciles a re-appended line by the entry's own identity instead (per `DSS-draft-statistics-storage.md` DSS-FR-PNUE), which is what lets a rolled-forward acceptance be safe to resume. The line carries the three fields above and nothing else: no path, no `byte_len`, no digest, no snapshot byte, no prompt byte, no proposal rationale, and no participant. The append is **asynchronous and never blocking** (per `DSS-draft-statistics-storage.md` DSS-FR-TUMX): it is not part of the acceptance transaction, it is not journaled, its failure is logged and dropped, and no acceptance is ever refused, delayed, rolled back, or reported incomplete because a statistics line could not be written.

## Non-functional requirements
- A snapshot is a file on disk in an ordinary folder, so an author can read or recover a past version with a file manager if the application will not open, on the same terms a draft's own prompt can be.
- Listing history reads manifests and one digest, so opening the rail on a draft with a long history costs one directory walk and one hash of the prompt rather than a read of every version.
- An acceptance costs two small atomic writes for the journal, one payload, one manifest, one prompt write, one record write, and one appended line — two payloads and two manifests where it is the first and settles the `Original` too (DHS-FR-07) — bounded by the size of the prompt and independent of how many versions the draft already holds.
- Nothing here holds a snapshot, an entry, or a journal in memory between calls, watches the folder, or maintains a queue: the folder is the whole of the state, so a relaunch mid-acceptance finds the journal exactly where the crash left it.
- Reconciliation is bounded by one draft's journal and never walks the worktree, so it adds a single absent-file read to the ordinary path.
- No operation here contacts the network or any AI integration.
