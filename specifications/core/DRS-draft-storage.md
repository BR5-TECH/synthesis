# Draft storage

**Spec code:** `DRS`

## Intent
The persistence home for the project's **drafts**: the prompts being developed in the New Artifact tab (`../ui/NAW-new-artifact.md`) and listed in the Drafts panel (`../ui/DRP-drafts-panel.md`) before the specifications they produce exist in the project. A draft is a named **single Markdown prompt** held in a folder inside the active worktree. The prompt, its record, and its images are committed and reach every checkout of the project through Git. The proposals, the settled versions, and the publication store stay in the checkout that wrote them. One draft is one prompt: `files/` holds exactly one file, refined by the author and by the agents they bring into it, and a draft whose `files/` holds anything else is reported as inconsistent rather than opened. Beside that prompt the draft owns an `assets/` folder for the images the prompt embeds, which is the draft's own material rather than a second prompt file and is owned by `DAS-draft-assets.md`. Drafts are filed into **folders** the author cuts beneath the drafts root, and those folders are ordinary directories holding the draft folders themselves: where a draft is filed is a fact about the filesystem rather than a record kept beside one, so there is no second copy of the organisation to fall out of step, nothing to repair when it does, and a draft moved between folders is the same folder of files at a different path. This module owns that layout, the draft record and its status, the folder tree the drafts are filed in, the single read and the single write of a draft's prompt, and the content search the Drafts panel filters by. It also owns the two things **graduation** does to a draft from the outside — the lock a run holds it under while it is being turned into a specification, and the terminal `graduated` status a completed run leaves it in — without owning graduation itself, and it owns the draft-owned **publication store** and the `published` status that `GHP-github-publication.md` writes through it, without owning publication itself. It also owns the immutable **GitHub-shadow draft** that a claim of a ready GitHub Task creates through `GPP-github-polling.md`, without owning the claim itself. Out of scope: creating a GitHub issue from a prompt, which is `GHP-github-publication.md`'s and which this module exposes no operation for; turning a prompt into specification files, which is the queued, agent-driven run of `GRD-graduation.md` and which this module exposes no operation for; everything the New Artifact tab renders and decides, owned by `../ui/NAW-new-artifact.md`; the panel's own filter state, which belongs with the other project-local panel states of `PSS-project-settings-storage.md`; the draft's version history and the acceptance transaction that adds to it, which sit inside the draft's folder but are owned by `DHS-draft-history.md`; the images the prompt embeds, which sit in the draft's own `assets/` folder but are stored, read, and collected by `DAS-draft-assets.md`; the review threads anchored to a draft's prompt, whose logs the repository machine store holds under the draft's stable id and which are owned by `CMS-comments-storage.md` (CMS-FR-37); the changes an agent has proposed to a draft's prompt, which likewise sit inside that folder but are owned by `DCP-draft-change-proposals.md` and reach the prompt only by calling this module's own save path (DRS-FR-12); and running any agent or conversational model against a draft, which no operation here does.

## Contract surface
All operations below are Tauri commands invoked by the UI. The quoted name is the canonical operation name as it appears in `../ui/NAW-new-artifact.md`'s and `../ui/DRP-drafts-panel.md`'s "Delegated to backend (abstract)" lines; the snake_case identifier is the Rust function name. Every path this module resolves is resolved against the project's **active worktree** (per `WTC-worktree-context.md` WTC-FR-03), the same root `PST-project-storage.md` PST-FR-21 resolves against.

### Record shapes

```
DraftStatus = "active" | "archived" | "graduated" | "published" | "github_shadow"

GithubIssueLink {
  repository_host,     // normalized host; absent in a stored link, which reads as github.com
  repository_owner,
  repository_name,
  issue_number,
  issue_url,
  project_node_id,     // the selected GitHub Project the claim moved the issue in
  claim_state          // "claimed"
}

Draft {
  id,                  // opaque, generated at creation, stable for the draft's lifetime
  name,                // free text, not required to be unique
  prompt_path,         // draft-relative path of the draft's one prompt file,
                       //   derived from the name (DRS-FR-25)
  status: DraftStatus,
  github_issue,        // GithubIssueLink | null — present on a GitHub-shadow
                       //   draft alone, and never removed (DRS-FR-XDWS)
  created_at,          // RFC 3339 UTC
  updated_at           // RFC 3339 UTC — the draft's last activity
}

BuildState =
  | { kind: "idle" }
  | { kind: "running", started_at }   // no producer yet (DRS-FR-23)

DraftGraduation {
  run_id,              // the graduation run this draft is bound to
  state,               // that run's current GraduationRunState
                       //   (GRD-graduation.md's Contract surface)
  locked               // true while that state is non-terminal (DRS-FR-19)
}

DraftListItem {
  draft: Draft,
  folder,              // drafts-root-relative path of the folder the draft is
                       //   filed in; "" is the implicit root (DRS-FR-29)
  prompt_activity_at,  // RFC 3339 UTC — the filesystem modification time of the
                       //   draft's one prompt file (DRS-FR-41)
  build: BuildState,
  has_pending_proposal,// an agent has proposed a change the author has not
                       //   decided (DCP-draft-change-proposals.md DCP-FR-04)
  graduation,          // the draft's most recent graduation run, or null
                       //   (DRS-FR-18)
  inconsistent         // the draft's files/ is not the single prompt DRS-FR-11
                       //   requires, so the draft cannot be opened (DRS-FR-15).
                       //   The draft's assets/ never makes it true (DRS-FR-11)
}

DraftFolder {
  path,                // drafts-root-relative, e.g. "UI/Components"
  parent               // drafts-root-relative path of the containing folder;
                       //   "" for a top-level folder
}

DraftHierarchy {
  folders: [DraftFolder],   // every folder, at every depth, empty ones included
  drafts:  [DraftListItem]
}

DraftMatch {
  draft_id,
  matched_in: "name" | "contents"
}
```

### Tauri commands
Per `../ui/NAW-new-artifact.md` and `../ui/DRP-drafts-panel.md`:
- `"create draft (name)"` → `create_draft(name?, folder?)` — scaffolds the draft's folder inside the drafts folder `folder` names, naming the draft `Untitled` when the caller supplies no name, and creates its one prompt holding the project's configured draft template, or empty where none is configured (DRS-FR-06, DRS-FR-39). Returns the created `Draft` together with the prompt it is created holding.
- `"list drafts"` → `list_drafts()` — returns the active worktree's whole `DraftHierarchy`: every drafts folder at every depth, empty ones included, and a `DraftListItem` for every draft, most-recent activity first.
- `"open draft (id)"` → `open_draft(id)` — returns the `Draft` record, and the typed `draft_not_single_file` for a draft that is inconsistent (DRS-FR-15).
- `"rename draft (id, name)"` → `rename_draft(id, name)` — returns the updated `Draft`.
- `"set draft status (id, status)"` → `set_draft_status(id, status)` — archives a draft that is `active` or `published`, and restores an `archived` one to `active`; returns the updated `Draft`. It never sets or clears `graduated`, which only `GRD-graduation.md` reaches (DRS-FR-20), and never sets `published`, which only `GHP-github-publication.md` reaches (DRS-FR-VKQO).
- `"delete draft (id)"` → `delete_draft(id)` — removes the draft's statistics log and then the draft's whole folder, and reports success only when both are gone (DRS-FR-ZLBK).
- `"search drafts (text)"` → `search_drafts(text)` — returns a `DraftMatch` for every draft whose name or prompt matches.
- `"load draft file contents"` → `load_draft_file_contents(draft_id, path)` — returns the prompt's text.
- `"save draft file contents"` → `save_draft_file_contents(draft_id, path, contents)` — overwrites the prompt, normalising line endings to the project's convention, and returns `{ checksum }` of the bytes written (DRS-FR-12).

There is **no publish operation here**. A draft becomes specification files through the queued, agent-driven run of `GRD-graduation.md`, which writes into the project through its own targeted publication (`GRB-graduation-rebase.md`) and reaches this module only to read the draft's prompt and to set its status.

The organisation of the drafts root, per `../ui/DRP-drafts-panel.md`. Every `path`, `parent`, `folder`, and `destination` below is a **drafts-root-relative folder path**, `""` naming the implicit root:
- `"create drafts folder (parent, name)"` → `create_drafts_folder(parent, name)` — creates one empty folder named `name` directly inside `parent`; returns the created `DraftFolder`.
- `"rename drafts folder (path, name)"` → `rename_drafts_folder(path, name)` — renames the folder in place, keeping its parent and its subtree; returns the renamed `DraftFolder`.
- `"delete drafts folder (path)"` → `delete_drafts_folder(path)` — reparents every direct child into the folder's parent, then removes the emptied folder (DRS-FR-31). Deletes no draft.
- `"move draft to folder (id, folder)"` → `move_draft_to_folder(draft_id, folder)` — moves the draft's own folder into `folder`; returns the updated `DraftListItem`.
- `"move drafts folder (path, destination)"` → `move_drafts_folder(path, destination)` — moves the folder and its whole subtree into `destination`; returns the moved `DraftFolder`.

A **drafts folder** is one of the author's organising directories under `.synthesis/drafts/`; the five operations above address those alone and never reach inside a draft, and the two content operations above address one draft's own prompt and never reach outside it.

Every command errors with a typed "no project open" when no project is open, with a typed "not found" when `draft_id` names no draft or `path` names nothing inside it, with a typed `draft_not_single_file` when the draft it names is inconsistent (DRS-FR-15), and with a typed `draft_locked_by_graduation` when it would change a draft a non-terminal graduation run holds (DRS-FR-19). Every operation on the drafts root errors with a typed "not found" when the path it names is absent, which is also how a caller acting on a hierarchy that has since changed learns of it (DRS-FR-35).

### Events
- `"drafts changed"` — emitted whenever the set of drafts or any draft's record changes (DRS-FR-22).
- `"draft prompt changed"` — the **content of one draft's prompt file** changed on disk, whoever wrote it. Payload: `{ draft_id, prompt_activity_at }` (DRS-FR-42).
- `"draft build state changed"` — carries a draft id and its `BuildState`. Consumed by `../ui/DRP-drafts-panel.md` DRP-FR-04; no operation in this module produces it yet (DRS-FR-23).

### Internal (Rust API, not registered as Tauri commands)
- `draft_dir(id)` — the absolute path of a draft's own directory, found by the walk of DRS-FR-29 rather than composed from the id, and the typed "not found" when `id` names no draft in the active worktree. Every module reaching a draft's own storage goes through it (DRS-FR-36).
- `draft_proposals_dir(id)`, `draft_history_dir(id)`, and `draft_assets_dir(id)` — the `proposals/`, `history/`, and `assets/` folders of DRS-FR-01 inside that directory, which `DCP-draft-change-proposals.md` (DCP-FR-01), `DHS-draft-history.md` (DHS-FR-01), and `DAS-draft-assets.md` (DAS-FR-01) address their own storage through (DRS-FR-40). The layout of a draft's folder is this module's, so a sibling module names the storage it owns rather than the path that storage sits at.
- `draft_record(id)` → `Draft` — the draft's current record, and `read_draft_prompt(id)` → `{ draft, content }` — that record together with the whole text of its live prompt. The two the agent tools resolve a draft through (DRS-FR-38), returning the same typed "not found" and `draft_not_single_file` the commands above return. `read_draft_prompt` is additionally what `GRD-graduation.md` captures a prompt through (per `GSU-graduation-start.md` GSU-FR-RWYQ), and neither call is refused by the lock, reading a locked draft being exactly what a run does.
- `draft_prompt_activity(id)` → the draft's `prompt_activity_at` alone, for a caller holding an id that needs the activity time without the whole hierarchy (DRS-FR-41). It returns the same typed "not found" and `draft_not_single_file` `draft_record` returns, and refreshes nothing.
- `set_draft_graduated(id, run_id)` — the one path to the `graduated` status, reached by `GRD-graduation.md` alone when a run completes (DRS-FR-20). It is registered as no Tauri command, so no frontend call can graduate a draft.
- `create_github_shadow_draft(name, prompt, link)` → `Draft` — the one path to a GitHub-shadow draft, reached by `GPP-github-polling.md` alone (DRS-FR-INCJ). It is registered as no Tauri command, so no frontend call can create one.
- `set_draft_published(id)` — the one path to the `published` status, reached by `GHP-github-publication.md` alone when an issue exists (DRS-FR-VKQO). It is registered as no Tauri command, so no frontend call can publish a draft.
- `draft_publication_path(id)` — the `publication.toml` of DRS-FR-EJBM inside that draft's own directory, resolved by the walk of DRS-FR-29 on exactly the terms `draft_assets_dir` resolves its folder (DRS-FR-40). It is the one route by which `GHP-github-publication.md` reaches the publication store.

### Internal channel (Rust, consumed by `BMI-bm25-indexing.md`)
- draft prompt mutations — the draft and the draft-relative path a command rewrote (DRS-FR-28). Not a Tauri event; no frontend consumer can subscribe to it.

## Functional requirements
1. **DRS-FR-01** Every draft is one folder named for its id, holding `draft.toml` (the record), `publication.toml` (the publication store, DRS-FR-EJBM), `files/` (the draft's one prompt), `proposals/` (the changes agents have proposed to the prompt, owned by `DCP-draft-change-proposals.md` DCP-FR-01), `history/` (the prompt's settled versions and the acceptance journal, owned by `DHS-draft-history.md` DHS-FR-01), and `assets/` (the images the prompt embeds, owned by `DAS-draft-assets.md` DAS-FR-01). It sits at `.synthesis/drafts/<folder-path>/<draft-id>/` inside the active worktree, `<folder-path>` being the drafts folder it is filed in and empty for a draft at the root (DRS-FR-29). Everything a draft holds is inside that one folder, so filing it somewhere else moves its record, its publication store, its prompt, its assets, its proposals, and its history together as one directory. Its review threads are addressed by its stable id in the repository machine store and move with nothing (per `CMS-comments-storage.md` CMS-FR-37). The `drafts/` parent is part of the project scaffold (`PST-project-storage.md` PST-FR-02).
2. **DRS-FR-02** A draft's `id` is opaque, generated at creation, and stable for its lifetime. It is derived from neither the draft's name nor its contents, so renaming a draft changes neither its id nor its folder.
3. **DRS-FR-03** `draft.toml` carries the `Draft` record of the Contract surface: `id`, `name`, `prompt_path`, `status`, `created_at`, and `updated_at`, the last two RFC 3339 instants in UTC. `created_at` is never rewritten after creation.
4. **DRS-FR-04** The **committed draft storage** of DRS-FR-ZIVL is committed to the project's Git repository, so a draft's record, prompt, and images reach every checkout and every worktree through Git. No ignore rule covers it (per `FSA-filesystem-access.md` FSA-FR-08). The whole `.synthesis/drafts/` subtree is skipped by the project scan (`ASC-artifact-scanning.md` ASC-FR-09) and absent from the Project panel and from project search (`SCC-search.md` SCC-FR-03).
   - *Why:* Two authors of one project work on the same drafts, so a draft that stayed on one machine would take the whole collaboration around it with it.
5. **DRS-FR-05** Drafts and the folders they are filed in belong to the active worktree, being inside it. Every command resolves `.synthesis/drafts/` against that worktree alone, so a draft or a folder created in one worktree is invisible from another and changing the active worktree changes the whole hierarchy (per `../ui/NAW-new-artifact.md` NAW-FR-24). No organisation crosses between worktrees by any act of this module, and none is copied into a worktree that has none of its own: what reaches a second worktree reaches it through Git alone (DRS-FR-AFSU).
6. **DRS-FR-06** `create_draft(name?, folder?)` scaffolds the draft's folder and creates it holding exactly one Markdown file at the root of `files/`, named from the draft's name (DRS-FR-25) and recorded as the draft's `prompt_path`. That file's contents are the project's **draft template** where the project configures one, and nothing at all where it does not (DRS-FR-39). The `assets/` folder is scaffolded **empty**, holding nothing until the author puts an image in the prompt (per `DAS-draft-assets.md` DAS-FR-01). The `history/` folder is scaffolded **empty** too: creating a draft settles no version, the live prompt being the draft's `Original` until a change is accepted against it (per `DHS-draft-history.md` DHS-FR-07). The draft is created with status `active` (DRS-FR-10). A draft always holds its one prompt from the first moment, whether that prompt arrived empty or carrying the template (per `../ui/NAW-new-artifact.md` NAW-FR-06). A creation whose scaffold cannot be completed creates no draft at all, leaving nothing behind. The command returns the `Draft` together with the prompt's draft-relative path.
7. **DRS-FR-07** `folder` is the drafts folder the new draft is filed in, and it is the **only** thing a creation says about where anything goes. It is expressed by where the draft's folder is created rather than recorded in the record at all; it is `""` — the drafts root — when the caller supplies none, and a `folder` naming no existing drafts folder is a typed "not found" that creates nothing. A draft carries no project destination of any kind: where its specification lands is chosen by the graduation agent from the captured prompt rather than seeded at creation, so a draft created from the Drafts panel's pinned affordance (per `../ui/DRP-drafts-panel.md` DRP-FR-06) and one created from a drafts folder's **New Draft** entry (per `../ui/DRP-drafts-panel.md` DRP-FR-26) differ in which drafts folder they are filed under and in nothing else. Those two are the only routes into this command: no menu of the project tree and no item of the File menu reaches it (DRS-FR-39).
8. **DRS-FR-08** `list_drafts()` returns the active worktree's whole `DraftHierarchy` in one walk: every drafts folder at every depth, empty ones included, and one `DraftListItem` per draft ordered by `updated_at` most-recent first, each carrying its record, the folder it is filed in, its `BuildState`, whether it holds a proposal the author has not yet decided (per `DCP-draft-change-proposals.md` DCP-FR-04), its graduation run where it has one (DRS-FR-18), and whether it is inconsistent (DRS-FR-15). It reads `draft.toml`, enumerates `files/`, stats the one prompt that enumeration finds to fill `prompt_activity_at` (DRS-FR-41), enumerates `proposals/`, and reads the project's graduation queue; it reads no draft's contents and no history, so a worktree holding many large drafts costs the list nothing beyond the walk. Folders are carried in the same result rather than in a call of their own, and the proposal flag and the graduation row in the same row rather than fetched per draft, the Drafts panel's cost being one list call however deep the tree (per `../ui/DRP-drafts-panel.md` DRP-FR-19, DRP-FR-20).
9. **DRS-FR-09** `rename_draft(id, name)` writes the new name and renames the draft's prompt to match it (DRS-FR-25), the two being one act rather than two. A name the caller supplies is taken verbatim and is not required to be unique, a draft being identified by its id (per `../ui/NAW-new-artifact.md` NAW-FR-04). An empty name is a typed validation error and leaves both the stored name and the file untouched. The rename can never collide, the draft holding no other file for the derived name to be taken by (DRS-FR-11), so it fails only for a name that is empty or for an I/O failure, which leaves the record and the file exactly as they were.
10. **DRS-FR-10** `set_draft_status(id, status)` archives a draft whose status is `active` or `published`, and restores an `archived` one to `active`, any number of times. It accepts `active` and `archived` alone: neither `graduated` nor `published` is a position a caller may set, and a call naming either is a typed validation error (DRS-FR-20, DRS-FR-VKQO). Archiving a `published` draft changes the scalar status and not one byte of its publication store, and restoring it leaves that store equally untouched (DRS-FR-EJBM). Archiving is a change to the record and nothing else: not one byte of the prompt, comment log, history entry, or conversation log is moved, rewritten, or removed, and an archived draft answers every command in this module exactly as an active one does — it lists, searches, opens, edits, renames, and graduates on identical terms. The status governs nothing this module does; it is what the Drafts panel filters and groups by (per `../ui/DRP-drafts-panel.md` DRP-FR-07) and what the New Artifact tab's archive action sets (per `../ui/NAW-new-artifact.md` NAW-FR-28). A draft is created `active` (DRS-FR-06).
11. **DRS-FR-11** A draft holds **exactly one prompt file and nothing else under `files/`**: one Markdown file at the root of `files/`, at the draft's `prompt_path`, with no folder, no second file, and no nested path anywhere beneath it. This is the invariant every operation here upholds rather than a convention a caller is trusted with. The draft's own directory holds the named sibling folders of DRS-FR-01 beside `files/`, `assets/` among them: an image the prompt embeds lives outside `files/`, so the invariant is stated over `files/` rather than over the draft's whole directory. A file under `assets/` therefore never makes a draft inconsistent (DRS-FR-15), and no route puts anything under `files/` but the one prompt (DRS-FR-13).
12. **DRS-FR-12** `load_draft_file_contents` and `save_draft_file_contents` read and write the draft's prompt as UTF-8 text, `path` naming that prompt and any other path being a typed "not found". A save overwrites it whole, **normalises every line ending in `contents` to the open project's line-ending convention** (`PSS-project-settings-storage.md` PSS-FR-17) before writing, and returns `{ checksum }` of the bytes actually written, on exactly the terms `PST-project-storage.md` PST-FR-22 normalises and checksums an artifact write. It is **the only write path for a draft's prompt**, whoever composed the text: the debounce that decides when to call it for the author's typing belongs to the UI (per `../ui/NAW-new-artifact.md` NAW-FR-13), and an accepted change an agent proposed lands through this same call inside the transaction of `DHS-draft-history.md` (DHS-FR-15) rather than through one of its own, so the prompt changes in exactly one way however the text that changed it came about and the bytes a history snapshot captures are the bytes this call persisted.
13. **DRS-FR-13** No command here creates, renames, or deletes a file or a folder inside a draft. There is no operation to add a second file to `files/`, to cut a folder beneath it, to move the prompt within the draft, or to remove it: a draft's prompt is settled at creation and changes only when the draft is renamed, which renames the one file it holds (DRS-FR-14). The named sibling folders of DRS-FR-01 are written by the modules that own them and by no command of this one, so a comment log, a proposal, a history entry, and an image asset each appear and go by their owner's own operations (`CMS-comments-storage.md`, `DCP-draft-change-proposals.md`, `DHS-draft-history.md`, `DAS-draft-assets.md`), never by one here. A draft can therefore never be reduced to no file and never grown into a tree, and no caller can put one into a state DRS-FR-11 forbids.
14. **DRS-FR-14** The prompt's path changes in exactly one way: renaming the draft renames it (DRS-FR-09), the record and the file changing together or not at all. The draft-scoped comment log anchored to it is followed by `CMS-comments-storage.md` (CMS-FR-38), so a rename never orphans a review thread, and the history entries already written keep the path each recorded when it was taken (per `DHS-draft-history.md` DHS-FR-06).
15. **DRS-FR-15** A draft whose `files/` is not the single prompt of DRS-FR-11 is **inconsistent**, and it is reported rather than repaired or silently reduced. What the draft's sibling folders hold decides nothing about it: a draft carrying ten images under `assets/`, a full comment log, and a long history is consistent exactly as an empty one is, the test being over `files/` alone. `list_drafts` returns it with `inconsistent` set and every field it could recover, so it is never dropped from the hierarchy and never lost by being unopenable; `open_draft`, both content operations, the prompt capture of `GSU-graduation-start.md` GSU-FR-RWYQ, and every operation of `DCP-draft-change-proposals.md` and `DHS-draft-history.md` against it return the typed `draft_not_single_file`. Nothing is deleted, nothing is moved, and no file is chosen as the prompt on the author's behalf. There is no migration and no repair path: the draft is deleted from the Drafts panel (per `../ui/DRP-drafts-panel.md` DRP-FR-33), which is the one thing left to do with material that is not a draft.
16. **DRS-FR-16** Every `path` argument is draft-relative and is resolved strictly inside that draft's `files/` folder. An absolute path, a path containing a `..` segment, and a symlink escaping the folder are each refused with a typed validation error and touch nothing, so no draft operation can read or write outside the draft it names.
17. **DRS-FR-17** `search_drafts(text)` returns one `DraftMatch` per draft in the active worktree whose name contains `text`, or whose prompt's text contains it, matching case-insensitively as a substring and reporting which of the two matched — `"name"` when the name does, `"contents"` otherwise. A prompt that does not decode as UTF-8 contributes no match, and neither does an inconsistent draft's storage, which is not read. Empty `text` matches every draft. This is the only command that reads a draft's contents on behalf of the panel.
18. **DRS-FR-18** This module writes nothing into the project tree and **deletes no draft on graduation**. A draft becomes committed work through the queued, agent-driven run of `GRD-graduation.md`, which captures the prompt (per `GSU-graduation-start.md` GSU-FR-RWYQ), drives an agent against a work stream, and commits onto that stream's branch; there is no command here that publishes a prompt, chooses a destination, or removes a draft as a consequence of one. A draft's whole relationship to that run is reported rather than owned: `list_drafts` carries a `DraftGraduation` for every draft the project's graduation queue holds a run for — the run's id, its current state, and whether that state locks the draft — read from `GRD-graduation.md` GRD-FR-LGDV's queue and never cached. A draft with no run in the queue carries none. That same queue read resolves the draft's `graduated` status (DRS-FR-KQTW).
19. **DRS-FR-19** A draft a **non-terminal** graduation run holds is **locked**, and the lock is enforced here rather than trusted to a caller. `save_draft_file_contents`, `rename_draft`, `set_draft_status`, `move_draft_to_folder`, `delete_draft`, and every publication operation of `GHP-github-publication.md` (GHP-FR-SRDL) each return the typed `draft_locked_by_graduation` against it and change nothing — not the record, not the prompt, not a byte under its folder — and the accepted-proposal write path of `DHS-draft-history.md` DHS-FR-15 is refused on the same terms, so no route reaches a locked prompt. Reading is untouched: `open_draft`, `load_draft_file_contents`, `search_drafts`, `draft_record`, and `read_draft_prompt` all answer for a locked draft exactly as for any other, which is what lets the run capture it and the author read it while it runs. The lock is the **run's state** rather than the draft's status: it holds for every non-terminal state of `GRD-graduation.md` GRD-FR-QJHM and lifts the moment the run reaches `completed`, `discarded`, or `failed`. Where the run committed, the `graduated` status refuses the same five commands after the lock lifts, until that status is itself released (DRS-FR-20, DRS-FR-KQTW).
20. **DRS-FR-20** `graduated` is a **distinct status** set by exactly one path: `set_draft_graduated`, reached by `GRD-graduation.md` alone when a run commits its work onto a work stream or, for a direct run, onto its pinned branch (GRD-FR-ARLT). `set_draft_status` cannot reach it and no Tauri command can, so no author action sets it. It **stands while a run that committed for this draft stands**, and it is **released** when every one of those runs is discarded (DRS-FR-KQTW). It is **not archiving and not deletion**: the draft's folder, its record, its prompt, its image assets, its history, its proposals, and its conversation log are all retained exactly as they were, and its review threads are retained in the repository machine store — nothing under that folder is removed, copied out, or collected by the run or by anything the run triggers — and the draft stays linked to the completed run through the `DraftGraduation` of DRS-FR-18. `delete_draft` is the **only** operation that ends a draft's storage (DRS-FR-21), and it is refused while the status stands, so a draft whose work is committed keeps its whole folder. A draft whose `graduated` status stands is read-only on the terms of DRS-FR-19 — the same five commands refuse against it, for as long as the status stands rather than for good — while every read answers as it always did, so an author returns to the prompt that produced the work and reads it whole.
21. **DRS-FR-21** `delete_draft(id)` removes everything held for that draft: its statistics log (DRS-FR-ZLBK), its review threads (DRS-FR-WNTA), and its whole folder — record, publication store, prompt, image assets, proposals, history, and any conversation log. The removal reaches the repository through the deletion commit of DRS-FR-QHHY, which names that draft's tracked paths alone (DRS-FR-VECL), so no other draft and no file of the project outside the draft is removed there either. Every operation that removes a draft's complete directory removes its assets with it, an asset being inside the draft rather than beside it (per `DAS-draft-assets.md` DAS-FR-01). Apart from that log it writes nothing anywhere else in the project, a draft having never been in it, and it leaves the drafts folder the draft was filed in standing and empty rather than removing a folder the author made (DRS-FR-29). An inconsistent draft (DRS-FR-15) is deleted on exactly these terms. A locked draft and one whose `graduated` status stands are not deletable (DRS-FR-19, DRS-FR-20): a run in flight is answering that prompt, and a graduated draft is the record of what committed work was written from. A draft whose graduated status has been released is deletable like any other, that record having been released with it (DRS-FR-KQTW).
22. **DRS-FR-22** Any command that creates, renames, deletes, or changes the status or filed location of a draft, and any command that creates, renames, moves, or deletes a drafts folder, emits `"drafts changed"` after the change has landed on disk (per `../ui/DRP-drafts-panel.md` DRP-FR-05). `set_draft_graduated` emits it too, a status change being a status change whichever module set it. A `save_draft_file_contents` call refreshes the draft's `updated_at` and emits the same event. A command that fails emits nothing, so the event never announces a change that did not land.
23. **DRS-FR-23** A draft carries a `BuildState` in every list result. No command here moves a draft out of `{ kind: "idle" }`, so `"draft build state changed"` has no producer yet. A draft is created with no `conversation.jsonl`. A `conversation.jsonl` that an existing draft holds is read by nothing and is deleted with the draft.
24. **DRS-FR-24** `updated_at` is the draft's last-activity instant and is refreshed by every change to its record or its prompt. It is what `list_drafts` orders by (DRS-FR-08) and what the Drafts panel renders as a relative timestamp (per `../ui/DRP-drafts-panel.md` DRP-FR-03).
25. **DRS-FR-25** A draft's name and the name of the file at its `prompt_path` are one thing, held in step by a **one-way derivation**: the filename is the draft's name with every path separator and every character illegal in a filename replaced by `-`, followed by `.md`. The stored name stays the free text the caller supplied, so a draft called `UI: pass 2/final` holds `UI- pass 2-final.md` and the two legitimately differ. The derivation runs at creation (DRS-FR-06) and at every rename of the draft (DRS-FR-09), and it runs in that direction alone, there being no way to rename the file itself (DRS-FR-13).
26. **DRS-FR-26** Changing the project's line-ending convention converts a draft's prompt whenever it is next written and at no other moment (DRS-FR-12). It marks no draft dirty, rewrites nothing on disk by itself, and creates no history entry, a convention change being a fact about how bytes are written rather than a version of the prompt (per `DHS-draft-history.md` DHS-FR-08).
27. **DRS-FR-27** `create_draft` called with no name assigns `Untitled`, or the first of `Untitled 2`, `Untitled 3`, … that no draft in the active worktree already bears. Only this auto-assigned default is disambiguated — a name the caller supplies is stored verbatim however many drafts already carry it (DRS-FR-09).
28. **DRS-FR-28** Every change this module makes to a draft's prompt is surfaced on an internal channel naming the draft and the path affected, which `BMI-bm25-indexing.md` consumes to keep the drafts index current (BMI-FR-19). The channel exists because `.synthesis/drafts/` sits outside what the project scan surfaces (`ASC-artifact-scanning.md` ASC-FR-09), so no watcher reports a draft's prompt. A graduated draft stays in that index, its prompt being retained and still readable (DRS-FR-20), and the specification files a graduation published enter the artifact index the way any other project write does — through the watcher's own `"project tree changed"` event (`ASC-artifact-scanning.md` ASC-FR-10) — rather than through this channel, which carries nothing about the project tree. The channel carries paths alone and no contents, and surfacing on it is not a precondition of any command here: a consumer's absence or slowness delays no draft operation.
29. **DRS-FR-29** The organisation of drafts is the directory structure under `.synthesis/drafts/` and nothing beside it: there is no manifest, index, or membership record anywhere. A directory beneath the drafts root is a **draft folder** when it directly contains `draft.toml`, and a **drafts folder** — one of the author's — otherwise, save only for a directory holding the misplaced storage of a draft filed elsewhere, which the walk reunites with that draft rather than presenting as a folder (DRS-FR-37); a drafts folder contains drafts folders and draft folders, and the walk of DRS-FR-08 stops at every draft folder rather than descending into the `files/`, `proposals/`, and `history/` beneath it. The drafts root is the implicit root: it always exists, being part of the project scaffold (`PST-project-storage.md` PST-FR-02), and no operation renames, moves, or removes it. A drafts folder's identity is its path, so it carries no id of its own and a rename or a move changes the identity of everything beneath it; nothing outside this module addresses a drafts folder, every consumer addressing a draft by the id it keeps through any move (DRS-FR-02). An empty drafts folder is an ordinary drafts folder and is returned by DRS-FR-08 like any other.
30. **DRS-FR-30** `create_drafts_folder` and `rename_drafts_folder` accept a name that is non-empty, free of path separators, neither `.` nor `..`, legal as a directory name on the running platform, and not equal case-insensitively to the name of any entry already in the destination — another drafts folder or a draft folder alike. A name failing any of these is a typed validation error that creates and renames nothing. A draft, by contrast, never collides: a draft folder is named for the draft's opaque id (DRS-FR-01, DRS-FR-02) rather than for the draft's name, so two drafts of the same name sit in one folder as readily as in two (DRS-FR-09), and moving a draft can fail for a missing destination but never for a name already taken.
31. **DRS-FR-31** `delete_drafts_folder(path)` removes the folder without removing anything it holds. It first checks every direct child — each draft folder and each drafts folder — against the destination, the folder's own parent, and refuses the whole call with a typed error naming the collision if any child's name is already taken there; only then does it move each child into that parent and remove the emptied folder, which it removes non-recursively so a folder that unexpectedly still holds something is reported rather than deleted. The only failure the checks leave is an I/O one, so the operation is all-or-nothing in every case a caller can provoke; an I/O failure part-way stops immediately and returns a typed error naming the child that failed, leaving the children already moved in their new parent and the folder in place, which the Drafts panel resolves by re-listing rather than by assuming (per `../ui/DRP-drafts-panel.md` DRP-FR-32). Deleting a top-level folder moves its children to the drafts root. No draft is deleted, no draft's id, prompt, record, or status changes, and the subtree beneath each moved child is preserved whole, each moved directory arriving with everything under it.
32. **DRS-FR-32** `move_draft_to_folder(draft_id, folder)` moves the draft's own directory into the drafts folder `folder` names, which must exist and must be a drafts folder or the root; a `folder` naming a draft folder, or naming nothing, is a typed error and moves nothing. Moving a draft changes exactly one thing about it — the path its directory sits at — and nothing else: its id, name, `prompt_path`, status, `created_at`, its prompt, every comment log, every proposal, every history entry, and its conversation log all travel with the directory unchanged, its `updated_at` is refreshed as any change to it is (DRS-FR-24), and no draft-relative path changes, so the internal channel of DRS-FR-28 surfaces nothing and the drafts index needs no work. A move into the folder the draft already sits in is a typed validation error rather than a no-op.
33. **DRS-FR-33** `move_drafts_folder(path, destination)` moves a drafts folder and its whole subtree into `destination`. It is refused with a typed error when `destination` names nothing, names a draft folder, is the folder's current parent, is the folder itself, or is anywhere inside the folder's own subtree — a folder is never placed inside itself, at any depth — and when an entry of the folder's name already occupies `destination` (DRS-FR-30). A refused move touches nothing. A move that proceeds is one directory rename: the subtree arrives whole, every drafts folder beneath keeps its position relative to the moved folder, and every draft beneath keeps its id and everything it holds.
34. **DRS-FR-34** Every `parent`, `path`, `folder`, and `destination` argument naming a drafts folder is drafts-root-relative and is resolved strictly inside `.synthesis/drafts/` in the active worktree. An absolute path, a path containing a `..` segment, and a symlink escaping the root are each refused with a typed validation error and touch nothing, on the same terms draft-relative paths are refused inside a draft (DRS-FR-16). No operation on the drafts root reads or writes a draft's contents, and none writes anywhere in the project outside `.synthesis/drafts/`.
35. **DRS-FR-35** A caller acting on a hierarchy that has since changed is told so rather than silently doing something else: every operation on the drafts root resolves the paths it was given at the moment it runs and returns a typed "not found" when one of them no longer names what it named, having applied nothing. There is no revision token to carry: the paths are the state. A draft folder whose `draft.toml` is missing or unreadable is reported as a typed error against that draft alone: it is never deleted, never moved, and never dropped from `list_drafts`, which returns it with the record it could recover, and the walk continues past it.
36. **DRS-FR-36** A draft's directory is **resolved through this module and never derived by its caller**. The directory sits at `.synthesis/drafts/<folder-path>/<draft-id>/` (DRS-FR-01), and `<folder-path>` is a fact only the walk of DRS-FR-29 holds: an id says nothing about where the draft carrying it is filed (DRS-FR-02), so a path composed from the id alone names the right directory for a draft that happens to sit at the root and a directory that does not exist for every other. `draft_dir(id)` and the named storage folders beside it — `draft_proposals_dir`, `draft_history_dir`, and `draft_assets_dir` (DRS-FR-40) — are therefore the only way a module outside this one reaches a draft's own storage, and no module writes anywhere inside `.synthesis/drafts/` at a path it did not obtain from one of them — the dual of DRS-FR-34's claim that no operation here writes outside the drafts root. The rule is stated rather than left to convention: writing to a derived path does not error but creates the directories it names, so the draft's own storage stays empty while a directory bearing that draft's id accumulates beside the author's folders (DRS-FR-29). An id naming no draft in the active worktree is the typed "not found".
37. **DRS-FR-37** The walk of DRS-FR-08 reunites a draft with draft-owned storage left outside it. A directory beneath the drafts root is **misplaced draft storage** rather than one of the author's folders (DRS-FR-29) when three things hold together: its name is a well-formed draft id, a draft carrying exactly that id is filed elsewhere in the hierarchy, and it holds nothing but the `proposals/`, `history/`, and `assets/` folders a draft's own directory holds (DRS-FR-01), or a `comments/` folder an earlier build kept that draft's review in. The walk moves what it holds into that draft's directory and removes the emptied husk; a reunited `comments/` folder is then read by the import pass of `RMS-repository-machine-storage.md` (RMS-FR-JVEC) like any other draft's. The merge needs no rule of its own: an append-only log present in both places concatenates, the fold applying each event identity once, an image asset is named by an identifier generated once, so a file present in both places is likewise the same file (per `DAS-draft-assets.md` DAS-FR-02), and a history entry is named by an opaque id over immutable bytes, so one present in both places is the same entry (per `DHS-draft-history.md` DHS-FR-04, DHS-FR-06). A directory that does not empty is left standing rather than removed, and no draft is created, deleted, moved, or changed in id, record, or prompt by any of it. The three conditions are required together: an author may name a folder anything DRS-FR-30 accepts, so a directory is adopted only where the draft whose storage it holds demonstrably exists somewhere else.

38. **DRS-FR-38** `draft_record(id)` and `read_draft_prompt(id)` resolve a draft for a caller that holds an id and nothing else. `draft_record` returns the current `Draft` — its `id`, `name`, `prompt_path`, `status`, and the rest of DRS-FR-03 — read from `draft.toml` and never from a cache. `read_draft_prompt` returns that same record together with the whole text of the draft's live prompt, read from the one file at its `prompt_path` inside `files/` on exactly the terms `load_draft_file_contents` reads it (DRS-FR-12), and never from `history/`, `proposals/`, or `conversation.jsonl`, none of which either call reads or reports. Both resolve the draft's directory through the walk of DRS-FR-36 rather than from the id, both return the typed "not found" for an id no draft in the active worktree carries and the typed `draft_not_single_file` for a draft that is inconsistent (DRS-FR-15), `read_draft_prompt` additionally returns a typed unreadable-prompt failure for a draft that resolves and holds its one prompt whose bytes it cannot read — a third outcome rather than a "not found", because a caller told the draft was missing would report that to its user about a draft the project holds — and both carry no precondition on status and none on the lock: every status a draft may hold — `graduated` among them — and a draft a run currently holds all resolve and read on identical terms, which is what lets `GRD-graduation.md` capture a prompt through `read_draft_prompt` (per `GSU-graduation-start.md` GSU-FR-RWYQ) and an agent read a graduated draft afterwards. Both are read-only — no record is rewritten, no `updated_at` is refreshed, no `"drafts changed"` is emitted, and nothing is surfaced on the channel of DRS-FR-28. They exist because `../tools/DST-draft-search-tool.md` (DST-FR-12) and `../tools/RDT-read-draft-tool.md` (RDT-FR-03) address a draft by id alone and must not compose a path into `.synthesis/drafts/` for the reason DRS-FR-36 gives; they are internal Rust calls and are registered as no Tauri command, so no frontend surface reaches a draft through them.

39. **DRS-FR-39** A draft is created holding the project's **draft template**, and the copy is taken **at creation and never again**. `create_draft` reads the template from the project-public store of `PSS-project-settings-storage.md` (PSS-FR-21) in the active worktree and writes its text into the draft's one prompt as the bytes that prompt is created with, normalised to the project's line-ending convention exactly as `save_draft_file_contents` normalises a write (DRS-FR-12). Where the store reports the template **unset**, the prompt is created empty, which is the whole of the difference between a project that configures a template and one that does not. What is written is a **snapshot**: the draft holds text of its own from that moment, a template later edited or cleared changes nothing in any draft that already exists, and no draft carries a reference back to the template. A template that cannot be read — a malformed or unreadable project-public store (PSS-FR-10) — fails the creation with that typed error and creates no draft, rather than creating one on the empty-prompt terms. Creating a draft is also the **only** thing the template is read for: no other command here reads it, no command rewrites an existing draft's prompt from it, and no operation outside this module applies it — the typed-artifact creation of `PST-project-storage.md` PST-FR-29 creates project files and neither reaches this command nor reads the template (per `../ui/NTA-new-typed-artifact.md` NTA-FR-14).

40. **DRS-FR-40** `draft_assets_dir(id)` resolves the `assets/` folder of a draft's own directory, on exactly the terms `draft_proposals_dir`, and `draft_history_dir` resolve theirs (DRS-FR-36): it walks to the draft rather than composing a path from the id, it returns the typed "not found" for an id no draft in the active worktree carries, and it is the one route by which `DAS-draft-assets.md` reaches an asset (DAS-FR-01). The layout of a draft's folder is this module's, so the module that owns the images names the storage it owns rather than the path that storage sits at. It is an internal Rust call and is registered as no Tauri command, so no frontend call reaches a draft's assets through it, and it carries no precondition on status and none on the lock, the lock being enforced by the operations that write rather than by the resolver (per `DAS-draft-assets.md` DAS-FR-25).

41. **DRS-FR-41** A draft's **prompt activity** is the filesystem modification time of its one prompt file, and nothing else. It is read from disk at the moment it is asked for rather than stored in `draft.toml`, so a prompt rewritten by an external editor carries exactly the activity a prompt rewritten through `save_draft_file_contents` carries. It is reported as `prompt_activity_at` on every `DraftListItem` (DRS-FR-08) and by `draft_prompt_activity(id)`, and it is **separate from `updated_at`** (DRS-FR-24), which follows every change to the record as well: a rename, a status change, a move between drafts folders, and a rewritten `draft.toml` each move `updated_at` and leave `prompt_activity_at` exactly where it was, and so does every write under the draft's `assets/`, `proposals/`, `history/`, or `conversation.jsonl`. Every draft holds its one prompt from creation (DRS-FR-06, DRS-FR-11), so `prompt_activity_at` is always present and no caller needs a fallback for a draft that has none; a draft that is inconsistent (DRS-FR-15) has no single prompt to stat and carries none, which is one more thing an inconsistent draft cannot answer rather than a case to guess at.
42. **DRS-FR-42** While a project is open, this module **watches the active worktree's drafts root** and emits `"draft prompt changed"` carrying `{ draft_id, prompt_activity_at }` whenever a draft's prompt file is written, whoever wrote it — `save_draft_file_contents` (DRS-FR-12), an accepted proposal that lands through it (per `DHS-draft-history.md` DHS-FR-15), or an external editor reaching the file directly. The watch is this module's own because `.synthesis/drafts/` is outside what the project scan surfaces and outside the raw path channel of `ASC-artifact-scanning.md` (ASC-FR-09, ASC-FR-20), so nothing else can observe it. The event reports **prompt content and nothing else**: a write to `draft.toml`, a status change, a rename, a move between drafts folders, and a write anywhere under `assets/`, `proposals/`, `history/`, or `conversation.jsonl` each emit nothing here, and each continue to reach `"drafts changed"` on the terms of DRS-FR-22 where that event covers them. The watch is mounted when a project opens, torn down when it closes, and re-mounted on the new root when the active worktree changes, exactly as `ASC-artifact-scanning.md` ASC-FR-14 and ASC-FR-16 handle the project watcher; no event fires for a closed project or for an outgoing worktree. This event is what keeps the Dashboard's Active workstreams widget current without polling (per `PST-project-storage.md` PST-FR-35).
43. **DRS-FR-QDHB** A **restarted** graduation run is a new run holding this draft, and it reaches this module on exactly the terms every other run does. The new run of `GRD-graduation.md` GRD-FR-ZAMI **locks the draft again** for every non-terminal state it holds, and releases the lock on DRS-FR-19's terms when it ends without committing; a draft whose lock was released when the earlier run was discarded is therefore locked once more from the moment the restart is enqueued (per `GSU-graduation-start.md` GSU-FR-IJEE).
44. **DRS-FR-RWEC** A restart **reads a prompt through no operation of this module and writes nothing here**: the new run answers the captured prompt of the run it was restarted from (per `GSU-graduation-start.md` GSU-FR-RWYQ), so `read_draft_prompt` is not called for it and a prompt edited since the earlier run's capture is neither read nor changed by it.
45. **DRS-FR-SLFN** A restart **changes no draft status**. What a restart changes is the run standing for the draft, and the status follows from the runs alone (DRS-FR-KQTW): a restart that commits nothing calls `set_draft_graduated` no second time, so a draft released when the earlier run was discarded reads `graduated` again from the moment that new run reaches the implementation part, which is a state at or beyond the boundary that has not ended without finishing. A draft that is `active` or `archived` keeps that position until a run's own publication sets it. A draft whose graduated status stands is locked out of editing and out of deletion by that status rather than by the restart (DRS-FR-19, DRS-FR-21).
46. **DRS-FR-ZLBK** `delete_draft(id)` also deletes that draft's statistics log, held under its stable id in the repository machine store (per `DSS-draft-statistics-storage.md` DSS-FR-KQVN), through `DSS-draft-statistics-storage.md`'s `delete_draft_statistics` (DSS-FR-VPBS) and by no other route. The deletion is **scoped to that one stable id**, so no other draft's log is reachable from it whatever the draft's name, path, or folder is. It runs **before** the draft's own folder is removed, which is what makes the operation retryable: the log is removed first, then the folder, and a failure at either step returns a typed error with the draft's record still on disk, so the same `delete_draft(id)` call repeated completes what is left. A statistics log that is **already absent** is an already completed deletion rather than an error and does not prevent or fail the operation, which is also what makes a second `delete_draft` after a partial one succeed. The operation **never reports the draft as deleted while either its storage or its statistics log remains**: success means both are gone. The draft's statistics are removed here and here alone — graduating a draft removes none of them (DRS-FR-20, per `DSS-draft-statistics-storage.md` DSS-FR-NKOZ), and a draft a run holds or a graduated draft is not deletable at all (DRS-FR-19, DRS-FR-21), so neither ever loses its account.
47. **DRS-FR-WNTA** `delete_draft(id)` also deletes that draft's review threads, through `CMS-comments-storage.md`'s `delete_draft_comments` (CMS-FR-39) and by no other route. It runs **before** the draft's own folder is removed, on exactly the terms DRS-FR-ZLBK sets: scoped to that one stable id, idempotent against threads already absent, and retryable. Success means the folder, the statistics log, and the review threads are all gone.

48. **DRS-FR-KQTW** A draft is `graduated` while **any** graduation run of that draft has committed its work onto a work stream or onto a direct run's pinned branch and is not `discarded`, and the status is **released** the moment every one of those runs is `discarded`. The status records work a run put on a stream or a pinned branch and a run that is still answerable for it; a run the author discarded is neither, so the prompt it was written from goes back to being a prompt the author may work on and graduate again. Release is a **resolution against the project's graduation queue** and not a second write path: the status is resolved on the same queue read that fills the `DraftGraduation` of DRS-FR-18, a record that says `graduated` while no run holds that status is reported as `active`, no read rewrites a record to release one (DRS-FR-38), and the stored value is normalised by the next `set_draft_status` the released draft accepts. Publication history releases nothing and holds nothing: a draft with publication records is released on exactly these terms, and the release reads `active` rather than `published` (DRS-FR-VKQO). A released draft is an **ordinary active draft in every respect**: `save_draft_file_contents`, `rename_draft`, `set_draft_status`, `move_draft_to_folder`, and `delete_draft` all succeed against it, the accepted-proposal write path of `DHS-draft-history.md` DHS-FR-15 and the asset writes of `DAS-draft-assets.md` DAS-FR-25 reach it again, and a fresh `start_graduation` is admitted over it (per `GSU-graduation-start.md` GSU-FR-IJEE). An `interrupted` run releases nothing, being non-terminal and therefore holding the draft locked by DRS-FR-19 instead, and a run that reached `implemented` or `implementation_accepted` holds the status for as long as the project holds that run. **Release removes nothing.** The specification files the discarded or failed run published stay in the project exactly as it left them, the run's own record stays readable in full (per `GRD-graduation.md` GRD-FR-LGDV), and nothing under the draft's folder is touched by the release: the draft becomes writable again and no byte of it changes at the moment it does.
49. **DRS-FR-NZSQ** A direct graduation run reaches this module on exactly the terms a stream run does. It locks the draft in every non-terminal state, sets `graduated` when it commits (DRS-FR-20), releases the status when every committing run is `discarded` (DRS-FR-KQTW), and changes no draft file.
49. **DRS-FR-DGMI** `.synthesis/drafts/.gitattributes` marks `*.jsonl` for union merge, the pattern carrying no slash so it reaches every depth beneath the drafts root. This module ensures the file exists **before the first draft is created and before the first append anywhere inside the folder**, preserving any entry already in it (DRS-FR-KORQ).
    - *Why:* Union merge is what lets two checkouts that both appended to one draft's log concatenate their lines instead of presenting a conflict.
50. **DRS-FR-KORQ** A module appending a draft-owned log reaches the ensure of DRS-FR-DGMI **through this module** and writes the attributes file itself at no point. A migrated project whose drafts already exist therefore gets the file on its next draft-owned append, without a draft being created.
51. **DRS-FR-BKFG** The attributes file and the ignore file of DRS-FR-JDRY are committed draft storage from the moment each exists (DRS-FR-ZIVL), and the next commit of DRS-FR-QHHY carries them. They are application-owned project metadata: no author action creates them, and an entry an author added to either is preserved by every later ensure.
52. **DRS-FR-PEAY** The union-merge attribute is a property of the `*.jsonl` pattern of DRS-FR-DGMI and of nothing else. A draft-owned JSONL log is append-only and merges correctly under it. No `.toml`, prompt, `.content`, `.snapshot`, or asset file carries it (DRS-FR-JPVB).
53. **DRS-FR-NXWO** A file the author placed under the drafts root and named `*.jsonl` is matched by the pattern of DRS-FR-DGMI like any other, Git applying an attribute by path rather than by owner. The application appends to it and commits it at no point (DRS-FR-XPQI), and defines neither its schema nor its merge outcome.
54. **DRS-FR-ZIVL** **Draft-owned storage is the defined draft layout alone**: the drafts root's `.gitattributes` and `.gitignore`, the drafts folders, and, in each draft folder, `draft.toml`, `files/`, `assets/`, `publication.toml`, `proposals/`, `history/`, and `conversation.jsonl`. The **committed draft storage** is the two root files, `draft.toml`, `files/`, and `assets/`. The rest is **private draft storage**. A transient file is not draft-owned.
54. **DRS-FR-WYIN** **Private draft storage** stays in the checkout that wrote it. Git ignores it (DRS-FR-JDRY), no commit of the application names it, and it reaches no other checkout and no other worktree.
54. **DRS-FR-JDRY** `.synthesis/drafts/.gitignore` ignores the private draft storage of DRS-FR-ZIVL. Each pattern names a path inside a directory whose name is a well-formed draft id, at any depth, so a drafts folder the author named `history` or `proposals` is not ignored. This module ensures the file at the moments of DRS-FR-DGMI and preserves every entry already in it.
54. **DRS-FR-PIWL** An ignore rule does not apply to a path Git already tracks. A private path that an earlier build committed stays tracked until the author removes it from the index in a commit of their own. No commit of the application names it, except the deletion commit of DRS-FR-21.
55. **DRS-FR-XPQI** A file the author created under the drafts root that DRS-FR-ZIVL does not name is **left exactly as it is**: not deleted, not rewritten, not moved, not staged, and not committed by anything here. The walk reports the directory holding it as one of the author's drafts folders on the ordinary terms (DRS-FR-29, DRS-FR-37).
56. **DRS-FR-QHHY** `.synthesis/drafts/` is **application-owned storage** (per `PST-project-storage.md` PST-FR-XKVD). Its committed draft storage is committed by the draft-event commits that `PST-project-storage.md` PST-FR-DQZT defines, and by no other commit of the application. This module chooses no moment, writes no message, opens no repository, and commits nothing itself.
    - *Why:* The application writes a draft while an agent proposes a change or graduates it, so the modification is one no person chose and none can prevent.
57. **DRS-FR-HRIB** Each draft-event commit is **asynchronous, best-effort, and non-blocking**, on the terms `PST-project-storage.md` PST-FR-KGRW sets: no draft operation waits for it or fails with it. A commit that was skipped or dropped leaves every draft file complete on disk, for the next draft event of that draft or for the author's own commit.
58. **DRS-FR-VECL** A draft-event commit names the committed draft storage of **that one draft** that differs from `HEAD`, the drafts root's `.gitattributes` and `.gitignore` where they differ, and nothing else. The deletion commit names every path Git tracks under the deleted draft's folder. A path the author staged stays staged and uncommitted (per `GTC-git.md` GTC-FR-19).
59. **DRS-FR-JPVB** Every committed draft file is an **ordinary Git-managed file**, and **Git alone settles a conflict in one**. No module writing inside a draft auto-resolves a conflict, chooses a version, overwrites a conflicted file, or deletes either side; the conflict stands in the working tree for ordinary Git status and conflict handling (per `GTC-git.md` GTC-FR-29).
60. **DRS-FR-GWNI** A conflicted draft is **read and reported rather than repaired**: a `draft.toml` or a `publication.toml` that no longer parses is the typed error against that draft alone (DRS-FR-35, DRS-FR-EJBM), and a `files/` holding conflict artefacts is `inconsistent` (DRS-FR-15). The commit of DRS-FR-QHHY is not attempted while a merge, rebase, cherry-pick, or bisect stands (per `PST-project-storage.md` PST-FR-KGRW).
61. **DRS-FR-AFSU** Draft storage is **resolved and committed against the active worktree alone** (DRS-FR-05, per `WTC-worktree-context.md` WTC-FR-03). The commit of DRS-FR-QHHY runs against that worktree, which may be a linked one, so no Git operation here reads or writes a sibling worktree.
62. **DRS-FR-ISPI** An existing project whose `.synthesis/.gitignore` still excludes `drafts/` is **migrated by removing that entry** (per `FSA-filesystem-access.md` FSA-FR-08, run on open by `PST-project-storage.md` PST-FR-CDYM). Every draft file stays where it is: the migration deletes, moves, rewrites, stages, and commits nothing.
63. **DRS-FR-NRQQ** A migrated project's existing committed draft storage reaches the repository through the **next draft-event commit of that draft** (DRS-FR-QHHY) or through the author's own commit. There is no migration commit.

64. **DRS-FR-EJBM** A draft's **publication store** is one file, `publication.toml`, directly inside that draft's own directory (DRS-FR-01). It holds the `DraftPublicationStore` of the Contract surface in two distinct sections: a repeated `[[publication]]` section carrying the append-only successful history oldest first, and at most one `[attempt]` section carrying the draft's standing attempt.
65. **DRS-FR-PSCH** The store is **absent until the first attempt**, and an absent file reads as an empty history with no attempt. Every write replaces the whole file **atomically** through `FSA-filesystem-access.md::write_toml_atomic`, and every read reads the file rather than a cache. A file that no longer parses is a typed error against that draft alone.
66. **DRS-FR-VDQR** An attempt's `state` is `open` or `awaiting_choice`, and both are **non-terminal**. The transitions are exactly three: absent to `open` when an attempt starts, `open` to `awaiting_choice` when a recovery choice is needed, and `awaiting_choice` to `open` when that choice is cancelled.
67. **DRS-FR-JOEV** A **completed** attempt is cleared in the same atomic write that appends its history record, and an **abandoned** attempt is cleared with nothing appended. `[attempt]` is therefore present only while an attempt is recoverable, and a draft never holds two.
68. **DRS-FR-XNLP** A history record already in `[[publication]]` is never rewritten, reordered, or removed by any write here. A write appends at most one record, and the newest record is the draft's current publication. Deleting the draft removes the store with the rest of its folder (DRS-FR-21) and is the only thing that removes a record.
69. **DRS-FR-VKQO** `published` is a **distinct status** set by exactly one path: `set_draft_published`, reached by `GHP-github-publication.md` alone after an issue exists (GHP-FR-BSYH). It is set only over `active`; a draft whose status is `graduated` keeps `graduated` and a draft already `published` stays `published`, the call changing the record in neither case. `set_draft_status` cannot reach it (DRS-FR-10), and no Tauri command can.
70. **DRS-FR-OGZC** The scalar status and the publication store are **separate facts**. A `published` draft is editable in every respect an `active` one is — `save_draft_file_contents`, `rename_draft`, `move_draft_to_folder`, and `delete_draft` all succeed against it, and it is graduatable like any other draft — while a `graduated` draft stays read-only on DRS-FR-KQTW's terms whatever its store holds.
71. **DRS-FR-INCJ** `create_github_shadow_draft(name, prompt, link)` creates a draft at the drafts root with status `github_shadow`, the given name, and the `GithubIssueLink` in its record. Its one prompt holds `prompt` normalised to the project's line-ending convention, and the draft template is not applied.
72. **DRS-FR-WFLY** `github_shadow` is a **distinct status** set by `create_github_shadow_draft` alone. `set_draft_status` cannot set it or move a draft out of it, and no Tauri command can.
73. **DRS-FR-XDWS** A draft whose record carries a `GithubIssueLink` is a **GitHub-shadow draft** for its whole life, whatever its status. No operation removes or rewrites the link, and `list_drafts`, `open_draft`, and `draft_record` report it.
74. **DRS-FR-QPSC** A GitHub-shadow draft is **immutable**. `save_draft_file_contents`, `rename_draft`, `set_draft_status`, `move_draft_to_folder`, and `delete_draft`, the accepted-proposal write of `DHS-draft-history.md` DHS-FR-15, and the asset writes of `DAS-draft-assets.md` DAS-FR-25 each refuse it with `draft_github_shadow` and change nothing.
75. **DRS-FR-JYIO** A GitHub-shadow draft is graduatable on the terms of `GSU-graduation-start.md`, and every read answers for it as for any other draft. The graduation lock of DRS-FR-19 applies to it unchanged.
76. **DRS-FR-EZDB** A GitHub-shadow draft reports `graduated` while a run of it that committed stands (DRS-FR-KQTW), and `github_shadow` otherwise. A released shadow draft reads `github_shadow` rather than `active`, and its prompt, link, and folder are kept.
71. **DRS-FR-WBTA** `publication.toml` is **private draft storage** (DRS-FR-ZIVL). It stays in the checkout that wrote it and no commit names it (DRS-FR-WYIN), the attempt record among the rest. No publication operation waits for a commit.
74. **DRS-FR-LWQT** An attempt and a history record each hold an optional `choice` table, the `PublicationChoice` that `GHP-github-publication.md` declares (GHP-FR-ATCH, GHP-FR-HSCH). A value that is null is absent from the file. A store written before the choice existed parses, and its attempts and records carry no choice.
72. **DRS-FR-ULKN** An existing project whose drafts predate the publication store is **migrated by nothing**: no `publication.toml` is created, and every such draft reads as an empty history with no attempt (DRS-FR-EJBM). The file appears at the draft's first attempt, in the checkout that made it (DRS-FR-WBTA).
73. **DRS-FR-RJYF** `list_drafts` and every read here report the draft's stored status as it stands, `published` among the four values of `DraftStatus`. The walk reads no publication store: the panel's row costs the same for a draft with a long publication history as for one with none, and `publication.toml` never makes a draft `inconsistent` (DRS-FR-15).

## Non-functional requirements
- The drafts-root watch of DRS-FR-42 is async and event-driven, like the project watcher it sits beside, and it reads no file's contents: it stats the prompt a change names and emits. A burst of writes to one prompt costs one stat per change reported rather than a walk of the drafts root.
- A draft's prompt is an ordinary file on disk in an ordinary folder, not an archive or a database, so an author can inspect or recover one with a file manager if the application will not open. The organisation is the same kind of thing: the folders are directories with the names the author gave them, so the hierarchy reads correctly in a file manager and a folder made or moved there is one the next `list_drafts` reports without reconciliation.
- `list_drafts` never reads a draft's contents, so opening the Drafts panel in a worktree holding many large drafts costs one directory walk rather than a read of every draft. Folders cost nothing beyond the directories the walk already visits, whatever the depth of the tree.
- Filing a draft or a folder is one directory rename however much it holds, so moving a draft with a long history costs what moving a fresh one costs and nothing is copied or rewritten to do it.
- `search_drafts` reads contents and is therefore the panel's one expensive call; it is invoked per query rather than per keystroke, which the panel's debounce decides.
- Nothing a draft holds is ever removed as a side effect of its prompt being published. A graduated draft is a complete draft on disk, so the prompt that produced a specification is still readable a year later beside the specification it produced.
- The graduation row a list carries costs one read of the project's graduation queue for the whole walk rather than one per draft, so a worktree of fifty drafts and a queue of two runs cost the list the same as a worktree with no queue at all.
- A draft is ordinary committed content: an author can `git log` a prompt, diff it between branches, and read a colleague's draft after a pull, with no application state on either machine.
- No operation here contacts the network or any AI integration.
