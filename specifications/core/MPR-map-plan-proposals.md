# Map plan proposals

**Spec code:** `MPR`

## Intent
The backend of the planning conversation of the Map tab. An agent in a Map discussion cannot write the delivery plan. It records a **plan proposal**: one batch of **rows**, each row one new issue, one change to a plan issue, or one new draft. The author decides each row on its own, and can reopen a rejected row. While a proposal is open, the agent can update it: change a row, add a row, or withdraw a row. The author uses this to steer the proposal from the discussion, without a second card. Where a change fails because the issue changed on GitHub, the module asks the agent to prepare the change again. When the author has decided every row and accepted at least one, the module gives the agent one **follow-up** turn with the results, so that it can propose the next step that depends on them. Nothing reaches GitHub, and no draft is created, before the author accepts the row that does it. This module stores the proposals, keeps the state of each row, and applies an accepted row through the GitHub delivery plan path of `GDP-github-delivery-plan.md`. It also owns the Map discussions that the proposals belong to, and the plan references that each Map turn reads: the HLD and the other documents the plan answers to reach the agent on every turn, as they are on disk at that turn, so the agent plans against the current design and never against an old copy. Out of scope: the tools that record a proposal, which are `../tools/PPT-propose-plan-changes-tool.md` and `../tools/PIR-plan-issue-read-tools.md`; the card that the author decides on, which is `../ui/MPV-map-proposal-review.md`; and the storage of the discussion log, which is `CMS-comments-storage.md`.

## Functional requirements
1. **MPR-FR-TQVZ** A **plan proposal** belongs to one Map discussion and to one agent comment in it. It holds ordered rows. Each row has a `key` that is unique in the proposal, a kind (`create_issue`, `modify_issue`, or `new_draft`), a state, and the fields of its kind. Only an update (MPR-FR-TMTI) changes its fields.
2. **MPR-FR-QUYY** A row is in one of four states: `waiting`, `accepted`, `rejected`, or `failed`. A new row is `waiting`. A decision moves a `waiting` row to `accepted`, `rejected`, or `failed`. Only a reopen (MPR-FR-MVRX) or an update (MPR-FR-KSRG) moves a decided row, from `rejected` to `waiting`. A decision on a decided row is refused with `row_decided` and changes nothing.
3. **MPR-FR-RVRN** A proposal is stored in the Map owner's folder of the comments store (per `CMS-comments-storage.md`), beside the Map discussion log, and lives as long as that log lives. It is stored through `FSA-filesystem-access.md`. Recording a proposal and appending its comment are one step: a failure of either produces neither.
4. **MPR-FR-MQEQ** A decision applies to one row only. A rejected, failed, or accepted row leaves every other row of the proposal as it was. A failed row does not stop a later decision on another row.
5. **MPR-FR-YCHW** Accepting a `create_issue` row creates the issue through `create_item` of `GDP-github-delivery-plan.md` (GDP-FR-UDOL) with its title, body, Type, milestone, parent, and labels, and adds it to the selected Project. The row becomes `accepted` and holds the number and URL of the new issue.
6. **MPR-FR-FBSH** Accepting a `modify_issue` row applies each changed field through the edits of `GDP-github-delivery-plan.md`: title, body, Type, milestone, parent, labels, Status, and close. Each field is written in that order, with close last. The first failed write stops the row, and the row becomes `failed` with the error of that write. A write that happened stays on GitHub.
7. **MPR-FR-XPXP** Accepting a `new_draft` row creates one draft with the name and the prompt of the row, through the draft storage of `DRS-draft-storage.md`. It makes no request to GitHub. The row becomes `accepted` and holds the id of the new draft.
8. **MPR-FR-RTGH** A `modify_issue` row records the `updated_at` that GitHub gave for the issue at the proposal (per `../tools/PPT-propose-plan-changes-tool.md` PPT-FR-UZEK). Accepting it passes that value to the edit (per `GDP-github-delivery-plan.md` GDP-FR-GBDF). Where the issue changed on GitHub since, the row becomes `failed` with `changed_on_tracker`, nothing is written, and no other row changes.
9. **MPR-FR-YLKL** A `create_issue` row, and the parent change of a `modify_issue` row, can name a `create_issue` row of the same proposal as the parent, by `key`. Such a row is **blocked** while that parent row is `waiting`, `rejected`, or `failed`. Accepting a blocked row is refused with `parent_not_accepted` and a reason of `waiting`, `rejected`, or `failed`, and nothing changes.
10. **MPR-FR-EQAX** When the parent row is `accepted`, accepting the child creates the issue, or writes the parent of the changed issue, with the real number of the parent issue. A parent that is rejected or failed leaves the child blocked for good. The author can still reject the child.
11. **MPR-FR-NGSK** A label change of a row holds an `add` list and a `remove` list. Only labels that exist in the repository are allowed. The check runs at the proposal and again at the accept. A missing name fails with `label_unknown`. 
12. **MPR-FR-WBKZ** A `modify_issue` row can close the issue with the reason `completed` or `not_planned`. The reason is part of the row. Accepting the row closes the issue with that reason through the edit set of `GDP-github-delivery-plan.md`.
13. **MPR-FR-GOHN** A `modify_issue` row can set the Project Status of the issue to one option of the Status field of the selected Project. A name that is not an option of the field fails with `status_unknown`.
14. **MPR-FR-GKOL** A `modify_issue` row carries, for each changed field, the value before and the value after, read at the time of the proposal. For labels it carries the added and the removed names. A field whose new value equals its value before is not part of the row.
15. **MPR-FR-SBYA** A Map discussion has an **open row** while any row of any of its proposals is `waiting`. The proposal that holds it is the **open proposal**. `record_map_plan_proposal` for a discussion that has an open row is refused with `proposal_open`, and records nothing. A row that is accepted, rejected, or failed is not an open row.
16. **MPR-FR-TMTI** `update_map_plan_proposal(discussion_id, updates)` changes the open proposal of the discussion. Each update is a `change` of a row, named by `key`, with the new fields of its kind; an `add` of a new row; or a `withdraw` of a row, named by `key`. An update carries one comment, or none for a later call of a turn (per `../tools/PPT-propose-plan-changes-tool.md` PPT-FR-IRFE). The tool validates the fields.
17. **MPR-FR-NSEP** An update for a discussion that has no open row is refused with `no_open_proposal`, and nothing changes. The update never reaches a proposal that is not open.
18. **MPR-FR-KSRG** A `change` or a `withdraw` applies to a `waiting` or a `rejected` row. One on an `accepted` or a `failed` row is refused with `row_decided`, and a key that names no row with `row_not_found`. A `change` of another kind is refused with `kind_changed`. A changed row keeps its `key`, becomes `waiting`, and loses its error and its result.
19. **MPR-FR-HQXX** A withdrawn row leaves the proposal. An added row goes at the end of the proposal, and is refused with `key_taken` where a row holds its key. An update that leaves no row is refused with `no_row_left`. A remaining row whose parent row is withdrawn is refused with `parent_withdrawn`.
20. **MPR-FR-EAAJ** An update is all or nothing. The update and its comment, where it carries one, are one step, as a recording is (MPR-FR-RVRN). A refusal or a failure of either writes neither. The proposal keeps its `id`, `commentId`, and `createdAt`, and the remaining rows keep their order.
21. **MPR-FR-AESZ** An update runs under the same one-at-a-time rule as a decision (MPR-FR-HKYH), so an update and a decision never run at the same time. A successful update emits `"map plan proposals changed"`.
22. **MPR-FR-MVRX** `reopen_map_plan_row` moves a `rejected` row back to `waiting`. It writes nothing to GitHub, needs no network, and clears the error and the result of the row. A recorded re-prepare request and a recorded follow-up request stay. It is refused with `row_not_rejected` for a row in another state, and with `proposal_open` where another proposal of the discussion has an open row (MPR-FR-SBYA). A refusal changes nothing.
23. **MPR-FR-SKLA** Rejecting a row sets its state to `rejected`. It writes nothing to GitHub, creates no draft, and needs no network. A blocked row can be rejected.
24. **MPR-FR-VMXC** Accepting a `create_issue` or `modify_issue` row refuses with `not_github_source` where the delivery source is not a GitHub Project (per `DSR-delivery-source.md` DSR-FR-AECK), and with the configuration error of `GPP-github-polling.md` where the configuration is not `valid`. A `new_draft` row needs neither.
25. **MPR-FR-HKYH** At most one decision runs at a time for one open project. Decisions apply in the order they arrive, and a second decision on the same row waits and then finds it decided.
26. **MPR-FR-LJRO** After a decision, where no row of the proposal is `waiting`, at least one row is `failed` with `changed_on_tracker`, and the proposal records no re-prepare request, the module requests a re-prepare (MPR-FR-NWEZ) on its own.
27. **MPR-FR-GIJN** `request_map_plan_reprepare` requests a re-prepare for a proposal on the author's demand. It is refused with `nothing_failed` where no row is `failed`, with `proposal_open` where the discussion has an open row, and with `reprepare_requested` where the proposal records a request. A failed append or dispatch refuses with its own typed error (MPR-FR-LOUI).
28. **MPR-FR-NWEZ** A **re-prepare request** appends one comment of the Synthesis participant (per `CMS-comments-storage.md` CMS-FR-MKEV). It names each failed row by its issue number, or a new issue or a new draft by its title, and asks the agent that proposed to read them again and propose again. Then it dispatches one turn of that agent, with the comment as its trigger.
   - *Why:* the agent reads the issue in its new turn, so the new proposal carries the current values and the current `updated_at`.
29. **MPR-FR-QIJF** The agent that proposed is the author of the comment of the proposal. After the dispatch starts, the proposal records `reprepareRequestedAt`, and the module emits `"map plan proposals changed"`.
30. **MPR-FR-LOUI** Where the comment cannot be appended or the turn cannot be dispatched, the module logs the typed error and records no request. A comment that was appended stays in the log.
31. **MPR-FR-SGYA** After a row that wrote to GitHub is applied, the module updates the read cache of the plan (per `GDP-github-delivery-plan.md` GDP-FR-VNNU). Each change of a proposal emits `"map plan proposals changed"` with the discussion id.
32. **MPR-FR-NRNZ** The Map owner holds any number of **Map threads**. A **whole-map thread** carries no node reference, and a **node thread** carries one. Several threads can carry the same node reference, and a resolved thread limits no other. The storage of these discussions follows `CMS-comments-storage.md`.
33. **MPR-FR-CEKS** A **node reference** is `{ lens, kind, id, label }`. `lens` is `delivery` or `specifications`. `kind` is `item`, `milestone`, `index`, or `spec`. `id` is a plan item id (for example `issue-12`), an index node id, or a spec code. `label` is the name shown to the author.
34. **MPR-FR-MYLA** `find_map_discussion(map_node)` returns the open thread of the node reference with the latest `updated_at`, or the open whole-map thread with the latest `updated_at` where the reference is absent, or nothing where no such thread is open. It creates nothing. A node reference matches on `lens`, `kind`, and `id`.
35. **MPR-FR-MAXH** `open_map_discussion(map_node, body, attachments)` creates a new thread with the node reference, or with none, and its first comment as one step. It never appends to an existing thread. An empty body is refused with `empty_body`, and nothing is written. The call is a human write command for a Map thread (per `CMS-comments-storage.md` CMS-FR-VRZA).
36. **MPR-FR-PMLX** A comment can carry one `map_node` attachment: a node reference as the **focus** of the turn it triggers. The focus of a turn is the node reference of the latest human comment that carries one, else the node reference of the thread, else the whole map.
37. **MPR-FR-ZCAM** The plan tools of `../tools/PIR-plan-issue-read-tools.md` and `../tools/PPT-propose-plan-changes-tool.md` are attached to a turn of a Map discussion only while the delivery source is a GitHub Project with a `valid` configuration (per `GPP-github-polling.md` GPP-FR-NLPG), checked at the start of the turn. Other discussions never get them.
38. **MPR-FR-NXDX** The input of a Map turn holds the focus, a short summary of the plan (the milestones, the issue counts, and the unmapped Types), and each row of the proposals of the discussion with its `key` and its state, and the plan references (MPR-FR-HRUK), so the agent knows what the author decided and can name a row of the open proposal in an update.
32. **MPR-FR-HRUK** The input of a Map turn holds the **plan references**: the references of the delivery plan (per `../ui/FLO-flow.md` FLO-FR-YDWT), the HLD among them, in the order the plan holds them. For a `file` source they are the references of the Flow file. For a `github` source they are the references of the overlay (per `DMS-delivery-machine-state.md` DMS-FR-WAUS). With the source `none`, or with a plan that has no reference, the input states in one line that the plan has no plan reference.
32. **MPR-FR-CHRV** Each plan reference is read at the dispatch of the turn, from its file in the active worktree as the file is on disk at that time, through `FSA-filesystem-access.md`. No text of a reference is kept from one turn to the next. Thus an edit that the Editor wrote to disk and an edit made outside the application both reach the next turn. A turn in flight keeps the text it was assembled with (per `AGC-agent-conversations.md` AGC-FR-13).
32. **MPR-FR-SRBV** Each plan reference in the input carries its display name (per `ASC-artifact-scanning.md` ASC-FR-19), its project-relative path, its artifact type, its change mark (MPR-FR-EHCG), and its text. A reference that does not resolve against the project tree carries its stored id, the word `unresolved`, and no text. A file that is not UTF-8 text carries no text, and for a Document it names `get_document` as the way to read it. A file that cannot be read carries the code of the typed error and no text, and the turn continues.
32. **MPR-FR-IIWW** The plan references are bound together by `limit_tokens × 4` characters (per `AGC-agent-conversations.md` AGC-FR-GMSF). The texts fill the bound in the order of the references. Where the texts are larger than the bound, the input holds the first part, carries `truncated`, and names, for each reference that is cut or left out, its size (per `AGC-agent-conversations.md` AGC-FR-OYVH), so that the agent reads the rest with `read_file`.
32. **MPR-FR-EHCG** Each plan reference carries a **change mark** against the fingerprint record of the discussion (MPR-FR-VGCX): `first` where the discussion has no record, `added` where the record does not hold the reference, `changed` where its fingerprint is not the recorded one, and `unchanged` where it is. Each reference that the record holds and the plan no longer holds is listed by its id with the mark `removed`. The fingerprint is the SHA-256 of the bytes of the file, also for a file that is not text. A reference that does not resolve or cannot be read has no fingerprint, and two references with no fingerprint are equal. The marks stand in the `discussion_state` section of the turn (per `AGC-agent-conversations.md` AGC-FR-06), each with the id of its reference, and not beside the texts of the references.
    - *Why:* the comments in the history can rest on an older text. The mark tells the agent which of its earlier conclusions to check again.
32. **MPR-FR-VGCX** A Map discussion has one **fingerprint record**: the id and the fingerprint of each plan reference. It is stored in the Map owner's folder of the comments store, beside the discussion log, through `FSA-filesystem-access.md`, and lives as long as that log lives. When a turn of the discussion whose contribution reaches the discussion terminates `delivered` or `awaiting_reply`, the record is replaced by the ids and fingerprints that the input of that turn was assembled with. Such a turn is a turn outside an agent group, a Meta turn, or the Synthesis turn of a group (per `AGC-agent-conversations.md`). An advisor turn, a participant turn of a synthesis group, and a turn that terminates `failed` or `cancelled` change no record. A failed write logs its typed error and does not change how the turn terminates, and the next turn compares with the older record.
32. **MPR-FR-AGTT** Each assembly of the plan references logs the count of references, the count of each change mark, the count that are unresolved, not text, or not readable, and whether the input is `truncated`, through `LGC-logging.md`. No record carries the text, the name, or the path of a reference.
38. **MPR-FR-CPGZ** In the input of a Map turn, an accepted `create_issue` or `modify_issue` row names its issue number, and an accepted `new_draft` row says that its draft was created.
38. **MPR-FR-IANE** After a decision of the author, the module requests a **follow-up** for the proposal where no row is `waiting`, at least one row is `accepted`, no row is `failed` with `changed_on_tracker`, and the proposal records no re-prepare request and no follow-up request.
38. **MPR-FR-LAAK** A follow-up appends one comment of the Synthesis participant (per `CMS-comments-storage.md` CMS-FR-MKEV). It names each accepted row with its issue number and URL or its draft name, each rejected row, and each failed row with its error code. It asks the agent to propose the next step that depends on them, or to say that the step is done.
38. **MPR-FR-LDJH** Then the follow-up dispatches one turn of the agent that proposed, with the comment as its trigger, on the terms of MPR-FR-QIJF and MPR-FR-LOUI. After the dispatch starts, the proposal records `followUpRequestedAt`, and the module emits `"map plan proposals changed"`.
38. **MPR-FR-BCKW** Where a turn of the agent that proposed runs in the discussion at the decision, the module requests no follow-up then. When that turn terminates, the module checks the conditions of MPR-FR-IANE again and requests the follow-up where they hold.
38. **MPR-FR-JSJE** An update by the agent and a reopen never request a follow-up, and a resolved discussion gets none. A proposal has at most one follow-up request.
38. **MPR-FR-VNDV** Each follow-up logs its outcome, `requested`, `deferred`, or `failed`, and the counts of accepted, rejected, and failed rows, through `LGC-logging.md`. No record carries a title, a body, or a URL.
39. **MPR-FR-KZRN** Each recording, decision, and refusal logs its operation, its outcome, the row kind, and the typed error through `LGC-logging.md`. No record carries a title, a body, a label name, a draft name, or a token.
40. **MPR-FR-RVTT** Each operation refuses with `no_project_open` when no project is open, and logs the refusal.

## Contract surface
### Tauri commands
- `"find map discussion (map node)"` → `find_map_discussion(map_node?)` → `Discussion | null`. Invoked by `../ui/SMP-specification-map.md` (SMP-FR-WNLR).
- `"open map discussion (map node, body, attachments)"` → `open_map_discussion(map_node?, body, attachments, spoken_original?)` → `Discussion`, the new thread.
- `"list map discussions"` → `list_map_discussions()` → `Discussion[]`, every Map thread, resolved ones included, in the order they were opened. The id breaks a tie.
- `"list map plan proposals (discussion id)"` → `list_map_plan_proposals(discussion_id)` → `MapPlanProposal[]`, oldest first.
- `"accept map plan row (discussion id, proposal id, row key)"` → `accept_map_plan_row(discussion_id, proposal_id, row_key)` → `MapPlanProposal`.
- `"reject map plan row (discussion id, proposal id, row key)"` → `reject_map_plan_row(discussion_id, proposal_id, row_key)` → `MapPlanProposal`.
- `"reopen map plan row (discussion id, proposal id, row key)"` → `reopen_map_plan_row(discussion_id, proposal_id, row_key)` → `MapPlanProposal` (MPR-FR-MVRX).
- `"request map plan reprepare (discussion id, proposal id)"` → `request_map_plan_reprepare(discussion_id, proposal_id)` → `MapPlanProposal` (MPR-FR-GIJN).

### In-process
- `record_map_plan_proposal(discussion_id, rows)` → `MapPlanProposal`. Called by `../tools/PPT-propose-plan-changes-tool.md` only. It enforces MPR-FR-SBYA. The tool validates the rows.
- `update_map_plan_proposal(discussion_id, updates, comment?)` → `MapPlanProposal`, the open proposal after the update. Called by `../tools/PPT-propose-plan-changes-tool.md` only. It enforces MPR-FR-NSEP to MPR-FR-AESZ. The tool validates the fields.

### Events
- `"map plan proposals changed"` — payload `{ discussionId }` (MPR-FR-SGYA).

```
MapNodeRef { lens: "delivery" | "specifications", kind: "item" | "milestone" | "index" | "spec", id, label }

MapPlanProposal { id, discussionId, commentId, createdAt, reprepareRequestedAt?, followUpRequestedAt?, rows: MapPlanRow[] }

MapPlanRow {
  key,
  kind,                 // "create_issue" | "modify_issue" | "new_draft"
  state,                // "waiting" | "accepted" | "rejected" | "failed"
  blockedBy,            // null | { rowKey, reason: "waiting" | "rejected" | "failed" }
  error,                // null | { code, message }
  result,               // null | { issueNumber?, issueUrl?, draftId?, appliedChanges? }
  fields                // CreateIssueFields | ModifyIssueFields | NewDraftFields
}

CreateIssueFields { title, body?, type?, milestone?: { number, title }, parent?: { issue: number } | { row: key }, labels: string[] }
ModifyIssueFields { number, title, baseUpdatedAt, changes: RowChange[] }
RowChange { field: "title" | "body" | "type" | "milestone" | "parent" | "labels" | "close" | "status", before, after, added?, removed?, reason? }
NewDraftFields { name, body }

MapPlanUpdate =
  | { action: "change", key, kind, fields }   // fields of the kind of the row
  | { action: "add", key, kind, fields }
  | { action: "withdraw", key }
```

Errors are typed: `no_project_open`, `proposal_not_found`, `row_not_found`, `row_decided`, `row_not_rejected`, `no_open_proposal`, `kind_changed`, `key_taken`, `no_row_left`, `parent_withdrawn`, `nothing_failed`, `reprepare_requested`, `parent_not_accepted`, `proposal_open`, `label_unknown`, `status_unknown`, `changed_on_tracker`, `not_github_source`, `issue_type_unavailable`, `partial_edit`, `draft_create_failed`, `discussion_not_found`, `store_unavailable`, and the configuration and request errors of `GPP-github-polling.md` GPP-FR-SUFH.

## Non-functional requirements
- A decision on a `new_draft` row, and a reject, make no network request.
- A proposal of 20 rows is one file write.
- A proposal record holds the text of the rows. It is project content, and no log record copies it.
