# Notes storage

**Spec code:** `NTC`

## Intent
The persistence home for the project's notes: the short pieces of text a user attaches to an artifact, a Flow, or the project as a whole through the Notes vertical panel (`../ui/NTS-notes.md`). Every note is one committed TOML file under `.synthesis/notes/`, so notes travel with the project, diff cleanly, and are shared with anyone who checks the repository out. A note's body is short by contract — at most 1 KiB of UTF-8 — which is what lets the whole of it stand as one document in the project's `notes` index (`BMI-bm25-indexing.md` BMI-FR-28) and be handed whole to an agent that searches it (`../tools/NST-note-search-tool.md`). Each note carries its own creation and last-edit timestamps, an optional scheduled reminder, and a scope that can be moved from one entity to another without changing the note's identity; because entity ids are derived from a file's path, this module also keeps notes attached across artifact renames and marks the ones it cannot follow so the UI can offer them for reattachment. A note may also carry one **discussion** — a conversation about the note itself, held so an author can think aloud about the gap or the follow-up they wrote down — which `CMS-comments-storage.md` stores under the note's stable id, created with the author's opening message, and which this module reports on the note's row and destroys with the note. The discussion is read and continued in a conversation tab that **Discuss** opens or focuses (`../ui/CVP-conversation-presentation.md`); the Notes panel renders no conversation of its own. Out of scope: rendering, grouping, filtering, and the reminder picker, all owned by `../ui/NTS-notes.md`; opening, reading, and appending to a note's discussion, all owned by `CMS-comments-storage.md`, and presenting it, which is `../ui/CVP-conversation-presentation.md`'s; the Notes panel's own selector and filter state, owned by `PSS-project-settings-storage.md`; and the delivery of a due reminder, which is served to the Dashboard through `PST-project-storage.md`'s `list_due_reminders` loader.

## Contract surface
All operations below are Tauri commands invoked by the UI. The quoted name is the canonical operation name as it appears in `../ui/NTS-notes.md`'s "Delegated to backend (abstract)" line; the snake_case identifier is the Rust function name. Every path this module resolves is resolved against the project's **active worktree** (per `WTC-worktree-context.md` WTC-FR-03), the same root `PST-project-storage.md` PST-FR-21 resolves against.

### Record shapes

```
NoteScope =
  | { kind: "entity", entity_id, entity_path }   // entity_path = last-known project-relative path
  | { kind: "project" }

Note {
  id,                 // opaque, generated at creation, stable for the note's lifetime
  scope: NoteScope,
  body,               // short-form Markdown source, stored verbatim and never rewritten;
                      // at most 1 KiB of UTF-8 (NTC-FR-23)
  reminder?,          // RFC 3339 instant, absent when the note carries no reminder
  revision?,          // Git revision the note was authored against, absent for current-version notes
  created_at,         // RFC 3339 UTC
  updated_at          // RFC 3339 UTC
}

NoteListItem {
  note: Note,
  entity_name?,       // basename of the entity, present only when the entity currently resolves
  unresolved,         // true when scope.kind = "entity" and entity_id resolves to nothing on disk
  discussion_id?  // the note's one discussion, absent when it carries none (NTC-FR-19)
}
```

### Tauri commands
Per `../ui/NTS-notes.md`:
- `"list notes for entity"` → `list_notes_for_entity(entity_id)` — returns the `NoteListItem`s whose scope names `entity_id`, most-recently-edited first.
- `"list project-wide notes"` → `list_project_notes()` — returns the `NoteListItem`s whose scope is `{ kind: "project" }`, most-recently-edited first.
- `"list all notes"` → `list_all_notes()` — returns every `NoteListItem` in the project, entity-scoped and project-wide alike, most-recently-edited first.
- `"create note (scope, body, optional reminder)"` → `create_note(scope, body, reminder?)` — writes a new note file and returns the created `Note`. Refuses a `body` above the size bound of NTC-FR-23.
- `"update note"` → `update_note(id, fields)` — partial update of `body`, `reminder`, and/or `scope`; returns the updated `Note`. Refuses a `body` above the size bound of NTC-FR-23.
- `"delete note"` → `delete_note(id)` — removes the note together with its discussion, in one transaction (NTC-FR-21).

Every command errors with a typed "no project open" when no project is open. `create_note` and `update_note` additionally error with a typed `note_body_too_large` (NTC-FR-23), and `delete_note` with a typed `discussion_cleanup_failed` (NTC-FR-21).

### Consumed from `CMS-comments-storage.md`
- `note_discussion_index()` (CMS-FR-63) — which notes carry a discussion, read once per list command to fill `discussion_id` (NTC-FR-19).
- `delete_note_discussion(note_id)` (CMS-FR-64) — the first step of the deletion transaction (NTC-FR-21).

### Internal (Rust API consumed by `PST-project-storage.md`)
- an enumeration of the notes carrying a `reminder`, with their scope and instant, which backs `PST-project-storage.md`'s `list_due_reminders` widget loader (PST-FR-12).

### Internal (Rust API consumed by `BMI-bm25-indexing.md` and by `../tools/NST-note-search-tool.md`)
- `note_documents()` → `[{ note_id, body }]` — one entry per persisted note of the active worktree, which is the whole content of the `notes` index (NTC-FR-24, `BMI-bm25-indexing.md` BMI-FR-28).
- note mutations — an internal channel naming the note a command created, whose body a command rewrote, or that a command removed, which `BMI-bm25-indexing.md` consumes to keep that index current (NTC-FR-24). Not a Tauri event; no frontend consumer can subscribe to it.
- `note_record(id)` → `Note` — the note's current record, the call `../tools/NST-note-search-tool.md` resolves a note through (NTC-FR-25), returning the same typed "not found" the commands above return.

## Functional requirements
1. **NTC-FR-01** Every note is persisted as exactly one TOML file at `.synthesis/notes/<note-id>.toml` inside the active worktree. The folder is part of the project scaffold (`PST-project-storage.md` PST-FR-02) and is committed to the project's Git repository, so notes are shared with everyone who checks the project out rather than being per-machine state.
2. **NTC-FR-02** A note's `id` is opaque, generated at creation, and stable for the note's lifetime. It is derived from neither the note's body nor its scope, so editing a note or moving it between entities changes neither its id nor its filename.
3. **NTC-FR-03** A persisted note carries the `Note` record of the Contract surface: `id`, `scope`, `body`, an optional `reminder`, an optional `revision`, `created_at`, and `updated_at`. `created_at` and `updated_at` are RFC 3339 instants in UTC.
4. **NTC-FR-04** `create_note(scope, body, reminder?)` writes a new note whose `created_at` and `updated_at` are the same instant. `scope` is either `{ kind: "entity", entity_id }` — the module records `entity_path` from the entity's current project-relative path — or `{ kind: "project" }`.
5. **NTC-FR-05** `update_note(id, fields)` is a partial update: a field absent from `fields` is carried through unchanged. `body`, `reminder`, and `scope` are the writable fields; `id` and `created_at` are not writable.
6. **NTC-FR-06** Any `update_note` call that changes `body`, `reminder`, or `scope` sets `updated_at` to the instant of the write. `created_at` is never rewritten after creation.
7. **NTC-FR-07** Moving a note between entities, or to or from project scope, is an `update_note` call carrying only a new `scope`. When the new scope is an entity, `entity_path` is recorded from that entity's current project-relative path.
8. **NTC-FR-08** `delete_note(id)` removes the note and whatever discussion it carries, as the one transaction of NTC-FR-21. Deleting an id that names no note is a typed "not found" error.
9. **NTC-FR-09** `list_notes_for_entity(entity_id)`, `list_project_notes()`, and `list_all_notes()` each return their items sorted by `updated_at`, most-recent first. `list_notes_for_entity` returns only entity-scoped notes matching `entity_id`; `list_project_notes` returns only project-scoped notes; `list_all_notes` returns both kinds in one list.
10. **NTC-FR-10** An entity-scoped note whose `entity_id` resolves to a node in the current scan (`ASC-artifact-scanning.md` ASC-FR-13) is returned with `unresolved = false` and `entity_name` set to that node's basename. One whose `entity_id` resolves to nothing is returned with `unresolved = true` and no `entity_name`; its stored `entity_path` is what `../ui/NTS-notes.md` NTS-FR-23 renders as the note's last-known location. An unresolved note is never dropped from a list result and is never deleted.
11. **NTC-FR-11** When the `ASC-artifact-scanning.md` watcher reports a rename or move that this module can correlate to a single old path and a single new path, every note whose `scope.entity_id` names the old path is rewritten to the new path's `entity_id` and its `entity_path` updated. The rewrite leaves `updated_at` untouched, because the note's content did not change.
12. **NTC-FR-12** A filesystem change this module cannot correlate to a single rename — a delete, or a delete-and-create pair the watcher reports separately — leaves the affected notes bound to their existing `entity_id`, which is then unresolvable and surfaces per NTC-FR-10. Reattachment is a user action performed through `update_note` (NTC-FR-07).
13. **NTC-FR-13** Every write this module performs goes through `FSA-filesystem-access.md` primitives — `write_toml_atomic` for a note file, `delete_path` with `recursive = false` for a removal, a note being a single file — and is subject to FSA's path-escape rejection (FSA-FR-10). This module performs no raw `fs::write`, `fs::remove`, or `fs::rename` calls, and writes nothing outside `.synthesis/notes/`.
14. **NTC-FR-14** A note file that is missing or malformed is skipped by the list commands rather than failing them: a damaged single note never prevents the remaining notes from being served. The skipped file is left on disk untouched.
15. **NTC-FR-15** Changing the project's active worktree (per `WTC-worktree-context.md` WTC-FR-08) re-resolves `.synthesis/notes/` against the new content root: the next list command reads the new worktree's notes and every subsequent write lands there. No note is copied between worktrees. Because `.synthesis/` is committed content, a repository with several worktrees holds one set of notes per worktree and the active one is authoritative.
16. **NTC-FR-16** `.synthesis/notes/` is never surfaced as artifact nodes in the project tree; the scan skips it (`ASC-artifact-scanning.md` ASC-FR-09), so note files never appear in the Project panel.
17. **NTC-FR-17** A note's `reminder` is an optional scheduled instant set and cleared through `update_note` or supplied at `create_note`. The notes carrying a reminder are what `PST-project-storage.md`'s `list_due_reminders` loader (PST-FR-12) reads to populate the Dashboard's Reminders widget; this module stores and serves the instants and schedules no delivery of its own.
18. **NTC-FR-18** A note authored against a historical revision of an entity carries that revision in its `revision` field, which is what lets `../ui/NTS-notes.md` NTS-FR-07 render it distinctly from a note on the current version. A note with no `revision` is attached to the entity's current version.
19. **NTC-FR-19** Every `NoteListItem` the three list commands return carries `discussion_id` when that note has a discussion and carries none when it does not, read from `CMS-comments-storage.md`'s note discussion index (CMS-FR-63) once per command rather than once per note. It is what lets a note row know, without a call of its own, whether choosing **Discuss** reopens a conversation tab or begins one with its opening composer (per `../ui/NTS-notes.md` NTS-FR-26). This module stores nothing about the association and writes no such field into a note file: what it reports is what the comment store holds at the moment of the read (CMS-FR-62).
20. **NTC-FR-20** A note's discussion is keyed by the note's `id`, which is stable for the note's lifetime and derived from neither its body nor its scope (NTC-FR-02). Editing a note's body, setting or clearing its reminder, moving it between entities or to and from project scope (NTC-FR-07), following it through a correlated rename (NTC-FR-11), and leaving it unresolved when a rename could not be followed (NTC-FR-12) therefore all leave its discussion exactly where it was, still associated and still holding every comment: a conversation is about the note, so nothing that happens to what the note is attached to reaches it. An agent turn dispatched afterwards is given the note's **current** body (per `AGC-agent-conversations.md` AGC-FR-07), the discussion outliving each edit rather than each version of the text.
21. **NTC-FR-21** `delete_note(id)` is **one transaction owned here**, and it runs in one order: `CMS-comments-storage.md`'s `delete_note_discussion(id)` first (CMS-FR-64), then the removal of `.synthesis/notes/<id>.toml`. Both steps completing is the only success, and only then is the note reported deleted. A failure of either step returns a typed error — `discussion_cleanup_failed` for the first, the ordinary write failure for the second — having reported nothing as deleted. The order is what makes the transaction **recoverable**: a failure of the first leaves the note and its whole conversation as they were, and a failure of the second leaves a note whose conversation is gone, which a retry completes and which choosing **Discuss** on begins afresh. Neither failure can leave a discussion no note names, because the only step that could orphan one is the one that runs last. Both steps are idempotent (CMS-FR-64, NTC-FR-08), so a retry of a partially applied deletion completes rather than failing on work already done, and a note carrying no discussion deletes exactly as it does with the cleanup step finding nothing to remove.
22. **NTC-FR-22** A note that has been deleted is a note no operation here resolves: `update_note` and a repeated `delete_note` are each a typed "not found" (NTC-FR-08), the list commands return it nowhere, and `CMS-comments-storage.md` holds no discussion under its id, so no comment, no discussion, and no index entry can be created for it by any route afterwards (CMS-FR-62). An agent turn in flight against that discussion is cancelled and appends nothing (per `AGC-agent-conversations.md` AGC-FR-30), on the same terms a turn is cancelled when the project closes.
23. **NTC-FR-23** A note's `body` is at most **1 KiB — 1024 bytes — when encoded as UTF-8**. The bound is on bytes rather than on Unicode code points or on displayed characters, so a body of emoji or of Japanese reaches it sooner than one of English and the same text is bounded identically wherever it was written. This module enforces it: `create_note` refuses a `body` above it, and so does any `update_note` call whose `fields` carry a `body` above it; each returns the typed `note_body_too_large` naming the bound, and in each case nothing is written, no file is created, no `updated_at` is refreshed, and the note stands exactly as it did. An `update_note` carrying no `body` is unaffected however long the stored body is, a partial update leaving a field it does not name alone (NTC-FR-05). A body at or below the bound is stored verbatim and never rewritten, trimmed, or truncated to fit — a note is refused whole or stored whole. The bound is what keeps a note small enough for the whole of it to be one document of the `notes` index (`BMI-bm25-indexing.md` BMI-FR-28) and to be handed whole to a model rather than as an excerpt of itself (`../tools/NST-note-search-tool.md` NST-FR-11).
24. **NTC-FR-24** Every change this module makes to the set of notes or to a note's `body` is surfaced on an internal channel naming the note affected, which `BMI-bm25-indexing.md` consumes to keep the `notes` index current (BMI-FR-29): a creation, a `body` rewrite, and a deletion each surface, and nothing else does — an `update_note` that changes only the `reminder` or only the `scope` (NTC-FR-07), a rename this module followed (NTC-FR-11), and a note left unresolved by one it could not (NTC-FR-12) each surface nothing, because none of them changes what is indexed. The channel exists because `.synthesis/notes/` sits outside what the project scan surfaces (`ASC-artifact-scanning.md` ASC-FR-09), so no watcher reports a note file and there is nothing else an indexer could observe it through. It carries note ids alone and no body text; the bodies themselves are read through `note_documents()`, which returns one `{ note_id, body }` entry per persisted note of the active worktree — every note the store holds, on the terms NTC-FR-09 lists them, and skipping the missing or malformed ones NTC-FR-14 skips. Surfacing on the channel is not a precondition of any command here: a consumer's absence or slowness delays no note operation.
25. **NTC-FR-25** `note_record(id)` resolves a note for a caller that holds an id and nothing else. It returns the note's current `Note` — its `id`, `scope`, `body`, and the rest of NTC-FR-03 — read from `.synthesis/notes/<id>.toml` in the active worktree and never from a cache, so a caller sees the note as it now stands rather than as some earlier pass found it. It returns the typed "not found" for an id no note in the active worktree carries and for one whose file is missing or malformed (NTC-FR-14), and it reports nothing of the note's discussion, which is `CMS-comments-storage.md`'s. It is read-only — no record is rewritten, no `updated_at` is refreshed, and nothing is surfaced on the channel of NTC-FR-24 — because reading a note is not activity on it. It exists because `../tools/NST-note-search-tool.md` (NST-FR-12) addresses a note by id alone and must report the note's scope and body as this module now holds them rather than as an index pass once captured them; it is an internal Rust call, registered as no Tauri command, so no frontend surface reaches a note through it.

## Non-functional requirements
- One file per note keeps a note's edit from producing a merge conflict with an unrelated note, and keeps every note individually diffable as plain TOML.
- The 1 KiB body bound is a contract rather than a storage constraint: it keeps a note a note — a few lines about a gap or a follow-up rather than a document — and it is what makes the whole of every note affordable both to index and to hand to a model in one piece.
- List commands read the notes folder without network access and complete in a single round-trip; the UI never chains a second load to resolve entity names or to learn which notes carry a discussion.
- The deletion transaction is two removals rather than a journal: it is made recoverable by the order it performs them in and by both being idempotent, so a crash between them leaves a state a retry resolves and never one that needs repairing by hand.
- The walking-skeleton implementation may keep notes in memory rather than on disk, provided the record shapes, sort order, unresolved marking, and error types above are the ones returned to the UI.
