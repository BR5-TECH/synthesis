# Prompt change proposals

**Spec code:** `PCP`

## Intent
A proposal against a published prompt artifact is a **whole alternative document**, held and decided as one. This is deliberately not the shape a **draft's** prompt takes, whose changes are held as anchored hunks and decided one by one (per `DCP-draft-change-proposals.md` DCP-FR-01).

The persistence home for a **proposed change to a prompt artifact**: a complete alternative text for a file the project already holds and whose resolved artifact type is `prompt`, offered by an agent in a conversation about that file (`../tools/PPC-propose-prompt-changes-tool.md`) and held beside the project until the author accepts it or declines it (`../ui/PCR-prompt-change-review.md`). It exists because a collaborator that can see how a prompt would be better should be able to show the author the whole of what it would write rather than describe it in prose — and because an agent that rewrites a published file without being asked is not a collaborator. A proposal is therefore **candidate material**: it sits in a store of its own, it is what the comparison the author reads is computed from, it is the author's to correct while they are reading it, and the one write that lands it in the project is the one they perform by accepting. This module owns the candidate's layout, its record and its state, the single path by which a proposal comes into existence, the single path by which the author's edits reach the candidate, and the decision that ends it. Editing a candidate and changing an artifact are two different acts against two different files here, which is what lets the surface above promise that a rewrite the author is still shaping has cost their project nothing. One artifact carries at most one undecided proposal at a time, so the author is never holding two competing rewrites of the same file in their head. Out of scope: composing a proposal, which is the agent's and reaches this module through one tool (`../tools/PPC-propose-prompt-changes-tool.md`); rendering the comparison, the editing surface the candidate is corrected on, the accept and decline controls, and the notification that calls the author to them, all of which are `../ui/PCR-prompt-change-review.md`'s; writing an artifact's contents, which stays `PST-project-storage.md`'s single write path (PST-FR-09); the artifact's own version history, which is read from Git by `HIS-history.md` and which this module neither writes nor consults; telling the agent what was decided, since the decision comment appended on this module's behalf is what a later turn reads and nothing here dispatches one (`AGC-agent-conversations.md` AGC-FR-29); expiring, retrying, or deciding a proposal on the author's behalf, none of which happens on any timer or at any threshold; creating a file, since a proposal replaces a prompt that already exists and never brings one into being; and proposing to a draft, which is `DCP-draft-change-proposals.md`'s and which keeps its own storage, its own commands, and its own acceptance transaction — the two modules share no record, no folder, and no write path.

## Contract surface
The module owns the `.synthesis/proposals/` folder and the Tauri commands and event below. Names match `../ui/PCR-prompt-change-review.md` byte-for-byte. Every path this module resolves is resolved against the project's **active worktree** (per `WTC-worktree-context.md` WTC-FR-03), the same root `PST-project-storage.md` resolves against (PST-FR-21).

### Record shapes

```
PromptProposalState = "pending" | "accepted" | "rejected"

PromptChangeProposal {
  id,                    // opaque, generated at creation, stable for its lifetime
  artifact_id,           // the stable, path-derived node key of the target
                         //   (ASC-artifact-scanning.md ASC-FR-13)
  path,                  // project-relative path of the prompt artifact
  agent: Participant,    // the agent participant that proposed it (CMS's shape)
  rationale,             // what the agent wrote; also the body of its comment
  thread_id,             // the conversation the proposal was posted into
  comment_id,            // the comment carrying the reference to this proposal
  state: PromptProposalState,
  origin_checksum,       // sha256 of the candidate as the recording wrote it, so
                         //   candidate_edited describes the text rather than the
                         //   history of getting to it (PCP-FR-22)
  candidate_edited,      // true while the candidate differs from the agent's own
  comment_owed,          // true between an acceptance landing and its decision
                         //   comment being appended; the decision is settled
                         //   either way, only the conversation is owed one
                         //   (PCP-FR-14)
  created_at,            // RFC 3339 UTC
  decided_at             // RFC 3339 UTC; null while pending
}
```

### Tauri commands
- `"list prompt change proposals"` → `list_prompt_change_proposals(artifact_id)` → `PromptChangeProposal[]`, every proposal that artifact holds, most recently created first.
- `"load prompt change proposal content"` → `load_prompt_change_proposal_content(proposal_id)` → `{ content, checksum }`, the candidate's text as UTF-8 together with `FSA-filesystem-access.md::sha256_file` of the bytes served. The checksum is the baseline a candidate save is checked against (PCP-FR-24).
- `"save prompt change proposal candidate"` → `save_prompt_change_proposal_candidate(proposal_id, content, baseline_checksum)` → `{ checksum }` of the bytes written. Overwrites the candidate of a **pending** proposal with the author's own text and writes nothing else anywhere (PCP-FR-22).
- `"apply prompt change proposal"` → `apply_prompt_change_proposal(proposal_id, feedback?)` → a `PromptDecisionOutcome`.
- `"decline prompt change proposal"` → `decline_prompt_change_proposal(proposal_id, feedback?)` → a `PromptDecisionOutcome`.
- `"complete prompt change decision"` → `complete_prompt_change_decision(proposal_id)` → a `PromptDecisionOutcome`. Finishes an acceptance whose decision comment is still owed, by running the reconciliation of PCP-FR-14 and returning what it settled. It decides nothing itself: against a proposal that owes no comment it is a no-op returning that proposal as it stands, and against one that was rolled back it returns it `pending`. It is the operation the review's retry invokes (per `../ui/PCR-prompt-change-review.md` PCR-FR-15), and it exists so an owed comment is reachable by a call rather than only by whatever command the author happens to make next.

```
PromptDecisionOutcome {
  proposal:    PromptChangeProposal,   // as it now stands
  comment_id?, // the decision's own comment; absent when it could not be
               //   appended, in which case no turn has anything to answer
  origin_kind  // "artifact_discussion" | "artifact_comment" (AGC-FR-05)
}
```

The last two are carried because `../ui/PCR-prompt-change-review.md` (PCR-FR-14) dispatches one fresh turn naming that comment as its trigger, and re-folding the thread to find what was just appended is both wasteful and ambiguous under a concurrent append.

Errors are typed: `no_project_open`, `artifact_not_found`, `not_a_prompt_artifact`, `proposal_not_found`, `already_decided`, `candidate_stale`, `thread_locked`, `write_failed`, `acceptance_in_progress`, `acceptance_incomplete`, and the identity refusals `identity_selection_required`, `identity_none_stored`, `github_unreachable`, `keychain_unavailable`, which a decision inherits from the comment it appends (per `CMS-comments-storage.md` CMS-FR-12).

### Events
- `"prompt change proposals changed"` — carries `{ artifact_id, proposal }`, emitted when a proposal is recorded and again when it is decided (PCP-FR-15).

### Internal (Rust API, not registered as a Tauri command and unreachable from the frontend)
- `record_prompt_proposal(artifact_id, content, rationale, agent, origin)` — the single path by which a proposal comes into existence (PCP-FR-05). Called by `../tools/PPC-propose-prompt-changes-tool.md` and by nothing else. Refuses `proposal_pending`, `artifact_not_found`, `not_a_prompt_artifact`, `no_change`, and `thread_locked`, which are the refusals that tool reports as its own.

## Functional requirements
 1. **PCP-FR-01** Proposals live in `.synthesis/proposals/` in the active worktree. A proposal at rest is two files: `<proposal-id>.toml` holding the record of the Contract surface, and `<proposal-id>.content` holding the proposed text as UTF-8. The record and the text are separate files, a record that carried a document in a field being read on every list. An acceptance in progress adds two more — `<proposal-id>.prior`, holding the artifact's bytes as they stood before the write, and `<proposal-id>.journal`, holding the transaction's own record together with the identity and `event_id` of the decision comment it owes. Both are removed only once the acceptance is wholly settled, its comment appended included, and the journal is removed last of all (PCP-FR-14), so **a folder holding a journal is a folder with something still to finish** — a transaction to roll back, or a comment to append — and a folder holding neither holds a proposal that is done with. The folder is created by the first write that needs it rather than by the project scaffold, so a project nobody has proposed a change in holds no such folder at all.
 2. **PCP-FR-02** The whole folder is gitignored — registered through `FSA-filesystem-access.md::ensure_gitignored` when it is created — and it is skipped by the project scan on the ordinary terms `.synthesis/` content is (per `ASC-artifact-scanning.md` ASC-FR-09). A proposal is private working material about a published file: it is never committed, never reaches anyone who clones the repository, and is never itself an artifact the Project panel shows or the Editor opens.
 3. **PCP-FR-03** A proposal's `id` is opaque, generated at creation, and stable for its lifetime. It is derived from neither the artifact, nor the path, nor the content, so two proposals of identical text against one file are two proposals.
 4. **PCP-FR-04** One artifact carries **at most one proposal in state `pending`** at any moment. `record_prompt_proposal` refuses while one stands, whichever agent made it. A decided proposal — `accepted` or `rejected` — is no longer pending and frees the artifact for the next one. The check and the writes that follow it are **serialised per artifact**.
   - *Why:* Several turns are in flight at once (per `AGC-agent-conversations.md` AGC-FR-03), and two agents asked about one file could otherwise both pass the check, leaving one proposal unreachable while it holds the slot.
 5. **PCP-FR-05** `record_prompt_proposal` is the **only** path by which a proposal comes into existence, and it is internal: no Tauri command creates one, so no frontend call can record a proposal, forge one against an artifact, or attribute one to an agent — exactly as none can attribute a comment to one (per `CMS-comments-storage.md` CMS-FR-41). It performs two writes and one append as **one act**: the `<proposal-id>.content` file, the `<proposal-id>.toml` record, and one comment appended into `origin`'s thread through `CMS-comments-storage.md`'s agent write path (CMS-FR-41) with the supplied agent participant, carrying `rationale` as its body and exactly one `prompt_proposal` attachment naming the new proposal (per `CMS-comments-storage.md` CMS-FR-66).
 6. **PCP-FR-06** The three writes of PCP-FR-05 succeed together or leave nothing behind. The content and the record reach disk before the comment is appended, so no folded comment ever names a proposal that is not there; and a failure to append the comment removes both files before returning, so no candidate ever sits in the folder that no conversation refers to. The record can name the comment it will be announced by that comment's **id being minted before either write** rather than by the append, the alternative being a record written after an append that cannot be taken back (per `CMS-comments-storage.md` CMS-FR-04). An append that succeeds **announces the conversation it landed in** (per `CMS-comments-storage.md` CMS-FR-51), so an open thread shows the offer at the moment it is made. A refusal announces nothing, nothing having been appended for a surface to redraw.
 7. **PCP-FR-07** `record_prompt_proposal` refuses, appending and writing nothing, in five cases, each with its own typed error. `artifact_not_found` when `artifact_id` names no file the project holds in the active worktree. `not_a_prompt_artifact` when it names a file whose **resolved artifact type** (per `ASC-artifact-scanning.md` ASC-FR-06) is not exactly `prompt` — which covers a file resolving to any of the other seven built-in types (per `ASC-artifact-scanning.md` ASC-FR-02) and a file the scan surfaces with no resolved type at all, the two being one answer to the model. `proposal_pending` when that artifact already carries a pending proposal (PCP-FR-04). `no_change` when `content` normalised on the terms the write path would persist it (per `PST-project-storage.md` PST-FR-22) is byte-identical to what the artifact currently holds — the comparison is made against the normalised form, a candidate differing only in its line endings changing nothing on disk artifact may hold at a time. `thread_locked` when the thread is locked (per `CMS-comments-storage.md` CMS-FR-17).
    **An empty `content` is refused by none of the five on account of being empty.** A candidate of no bytes against an artifact that holds something is a change like any other and is recorded like any other: emptying a prompt is a decision the author is entitled to be offered, and a store that refused to hold the offer would be deciding it for them. It meets `no_change` on the one term every candidate meets it on — an artifact that is **already** empty, where the normalised comparison finds nothing to decide — and on no term of its own, so there is one rule about content here rather than two (per `../tools/PPC-propose-prompt-changes-tool.md` PPC-FR-08).
 8. **PCP-FR-08** No route through this module **creates a file**. `record_prompt_proposal` refuses a target that does not already exist rather than bringing one into being, an acceptance replaces an existing artifact and never restores a missing one, and a decline writes into the project not at all. The one file set this module ever adds to is its own `.synthesis/proposals/` folder, and the project tree the Project panel renders is unchanged by every path through it.
 9. **PCP-FR-09** `<proposal-id>.content` holds the **candidate**: the text as the proposing agent composed it, or as the author has since rewritten it through the one path that may (PCP-FR-22). Nothing else touches it — it is never re-indented, re-encoded, or trimmed, by this module or by anything that reads it, and the line-ending normalisation an acceptance applies is applied by the write rather than to this file, which keeps the bytes it was given. What the author reads in the comparison and what an acceptance puts into the artifact are the same text. A candidate of **no bytes** is held as a `.content` file of zero length and is a candidate like any other: the file exists, `load_prompt_change_proposal_content` returns the empty string and the checksum of no bytes, a candidate save may empty a candidate or fill an empty one (PCP-FR-22), and nothing anywhere in this module treats an empty candidate as an absent one or as a proposal to be swept, refused, or repaired.
10. **PCP-FR-10** `list_prompt_change_proposals(artifact_id)` returns every proposal that artifact holds — pending, accepted, and rejected alike — most recently created first. It reads the records and never a `.content` file, so an artifact carrying a long history of proposals costs a list no more than one carrying a single proposal.
11. **PCP-FR-11** `load_prompt_change_proposal_content(proposal_id)` returns the candidate of any proposal, decided or not. It returns the bytes together with their checksum, which is the baseline the next candidate save is checked against (PCP-FR-24), on exactly the terms `PST-project-storage.md` PST-FR-15 makes a checksum an editing baseline. It is the only operation that reads a `.content` file, and it is invoked when a comparison is actually rendered rather than when proposals are listed (per `../ui/PCR-prompt-change-review.md` PCR-FR-07).
12. **PCP-FR-12** `apply_prompt_change_proposal(proposal_id, feedback?)` accepts a pending proposal. It checks what can be checked first — that the proposal is pending, that its `artifact_id` still names a file the project holds whose resolved type is `prompt`, that an identity resolves, and that the conversation is unlocked (PCP-FR-16) — and then performs the replacement of PCP-FR-13 inside the transaction of PCP-FR-14. The write goes **through `PST-project-storage.md`'s own write path** (`save_artifact_contents`, PST-FR-09), which stays the only write path for an artifact's file, so an accepted proposal normalises line endings to the project's convention (PST-FR-22), records the artifact in the recently-edited list (PST-FR-17), and suppresses its own external-change event (PST-FR-16) exactly as the author's own typing does. The record reads `accepted` with `decided_at` set only where the transaction reached its commit point, and a call that returns the typed `write_failed` has left a proposal that is still `pending` and an artifact holding the bytes it held before the call — not restored to them but never written at all (PCP-FR-14). **This module has no answer that means the artifact may have changed and no state in which a proposal is left unsettled**: every command reconciles an interrupted transaction before it answers.
13. **PCP-FR-13** An acceptance is a **whole-file replacement**, performed verbatim as text against the artifact's contents **as they stand at that moment**. The candidate becomes the artifact's entire contents whatever the artifact held, including changes the author or any other surface made after the proposal was recorded, and a candidate the author edited (PCP-FR-22) is applied on exactly those terms, being a complete document like the one it replaces. **No baseline checksum is compared and no divergence is detected**: the acceptance is a replacement of the file rather than an edit to a version of it, so a file that has moved on since the review opened — by the author, by another surface, or by anything outside the application — is replaced rather than refused, and neither the Editor's baseline of `../ui/EXC-editor-external-change.md` EXC-FR-WCOM nor any `"artifact changed externally"` event standing against it is consulted, awaited, or resolved by this module (per `../ui/PCR-prompt-change-review.md` PCR-FR-05, PCR-FR-11). What the replacement does read is the file's current bytes, and it reads them once, to keep them (PCP-FR-14). Every character of the candidate survives: its whitespace, its indentation, and its missing final newline where it has none. **A candidate of no bytes empties the file**, which is a replacement rather than a write to be skipped: the artifact is written with zero bytes through the ordinary write path, it stays a file of the project and is neither deleted nor removed from the tree (PCP-FR-08), and the acceptance settles on the ordinary terms — the record moves to `accepted` and the recently-edited list moves. An acceptance that **fails** leaves the file holding its own bytes rather than emptying it, on exactly the terms of PCP-FR-14: the emptying write is the last fallible step and is atomic, so a failure means it did not land. The one thing the write settles for itself is the line-ending convention, which is the project's and is applied to every artifact write alike. Nothing is merged, no hunk is resolved, and no conflict is detected, the candidate being a complete document rather than an edit to one (per `../tools/PPC-propose-prompt-changes-tool.md` PPC-FR-04).
14. **PCP-FR-14** The acceptance is a **transaction with one commit point**, and that commit point is **the artifact write landing**. The ordering is what makes the whole guarantee hold, and it is chosen for one reason: the artifact write is the **last fallible step** of the transaction and it is atomic (per `FSA-filesystem-access.md` FSA-FR-04), so it either lands entirely or does not land at all. **The artifact is therefore never restored on any path through this module** — a failure before it means the file was never written, and a failure of it means the write did not land and the file still holds its own bytes. There is no path on which an acceptance reported as failed has changed the author's file, because on every one of them the file was never touched.
    The transaction is performed in this order, and every step of it goes through `FSA-filesystem-access.md` primitives (PCP-FR-25). First the pre-checks of PCP-FR-12 and PCP-FR-16, which write nothing. Then the decision comment's identity and its `event_id` are **minted in advance**. Then `<proposal-id>.prior` is written, holding the artifact's whole current bytes byte-for-byte and unnormalised, and read back and checksummed. Then `<proposal-id>.journal` is written, naming the proposal, the artifact and its path, the checksum of `<proposal-id>.prior`, the checksum of the bytes the artifact write is about to put on disk, and the minted comment identity and `event_id`. Then the **record** is written with `state = accepted`, `decided_at` set, and `comment_owed` true. Then, last of everything that can fail, **the commit point**: the artifact is written through `PST-project-storage.md`'s write path (PCP-FR-12). Then the event is emitted (PCP-FR-17) and the decision comment is appended (PCP-FR-16). **`comment_owed` is cleared only once that append has succeeded**, and the journal and `<proposal-id>.prior` are removed only after it — the journal last of all, so that **a journal on disk always means there is something still to finish**, whether that is a transaction to roll back or a comment to append.
    **Every failure at or before the commit point ends with the artifact untouched and the proposal `pending`, verified, before anything is returned.** A failure of a pre-check, of the mint, of the `.prior` write or its read-back, or of the journal write leaves both the artifact and the record exactly as they were; whatever of `.prior` and the journal was written is removed, and the typed `write_failed` is returned with the proposal still `pending`. A failure of the **record** write leaves the record reading `pending` and the artifact never written, on the same terms. A failure of the **artifact** write is the only case with anything to undo, and what it undoes is this module's own record rather than the author's file: the record is written back to `state = pending` with `decided_at` and `comment_owed` cleared, that rollback is **read back and verified** before the call returns, the journal and `.prior` are then removed, and the typed `write_failed` is returned. `write_failed` therefore always means exactly what the author is told it means — the file is unchanged and the proposal is still theirs to decide.
    Where that record rollback cannot be completed within the call, **nothing is returned that claims otherwise and no reader can observe the intermediate state**: the journal is left in place, and a journal present means the transaction did not finish, so `reconcile(proposal_id)` completes the rollback before any command of this module answers and before any surface is served that artifact. The call still returns `write_failed`, which is true of the artifact on every one of these paths without qualification. There is no unresolved state to report, no flag on the record for one, and no answer of this module that means "the file may or may not have changed".
    **A failure after the commit point is not a failed acceptance, because both halves of the atomic pair have succeeded**: the artifact holds the candidate and the record reads `accepted`. Two things can fail there and neither is reported as a failure of the decision. A **cleanup** failure — the journal or `<proposal-id>.prior` not being removed — is reported to nobody at all: the acceptance returns success, and the next reconciliation sweeps the leftovers, which is the whole of what it takes to settle them. A **comment append** failure leaves the acceptance landed and the comment owed, and is reported as the typed `acceptance_incomplete`, which states that the change was applied and the conversation has not yet been told.
    That owed comment has a **reachable recovery path**, and it is reachable because the journal is still there. The journal carries the minted comment identity and its `event_id`, and it is not removed until the append has succeeded, so an owed comment is never a debt whose paperwork has already been thrown away. Two things settle it, and they are the same work reached two ways: `reconcile(proposal_id)`, which every command of this module runs before it answers and which runs at project open; and `complete_prompt_change_decision(proposal_id)`, a command of its own that runs that reconciliation and returns the resulting `PromptDecisionOutcome`, so the surface that was told the comment was owed has an operation to call and a comment id to dispatch a turn against (per `../ui/PCR-prompt-change-review.md` PCR-FR-15). Either way the append is idempotent by the pre-minted `event_id` (per `CMS-comments-storage.md` CMS-FR-06), so a comment already appended contributes nothing a second time; `comment_owed` is cleared only when the append has succeeded; and the journal and `.prior` are removed only after that. Every filesystem operation on this path is `FSA-filesystem-access.md`'s (PCP-FR-25) and the append itself is `CMS-comments-storage.md`'s ordinary human write path, so the recovery reaches disk by no route the rest of this module does not.
    Completing an owed comment is the completion of a **successful** acceptance's tail and is not a roll-forward of a failed one — no failed acceptance is ever carried forward into a successful one by any route here. The two conditions that would make the append impossible are checked before the transaction begins (PCP-FR-16), so an identity that will not resolve and a locked thread refuse up front rather than stranding an acceptance with a comment nobody can write; where either becomes true after the commit point, the comment stays owed and the recovery path retries it, the acceptance itself being settled and not in question.
    `reconcile(proposal_id)` settles an interrupted transaction and runs before `list_prompt_change_proposals`, before either decision command, inside `complete_prompt_change_decision`, and **at project open before any surface has been served that artifact**. A proposal with no journal is settled already, its comment appended and its cleanup done, and is left alone. A journal present means something is still to finish, and what to do is read from the artifact's own bytes against the two checksums the journal recorded. Where the artifact's checksum equals the journal's **candidate** checksum the commit point was passed: the record is written to `accepted` if it does not already read so, the owed comment is appended where `comment_owed` says one is, `comment_owed` is cleared only on that append succeeding, the event is emitted, and the journal and `.prior` are removed only once the comment is settled — an append that fails again leaves the journal exactly where it was, so the next reconciliation finds the same debt and the same means of paying it. Where it equals the **`.prior`** checksum the artifact write never landed: the record is written back to `pending` with `decided_at` and `comment_owed` cleared, and the journal and `.prior` are removed. Where it matches **neither**, something outside this transaction has written that file, so the file is **left exactly as it is** — nothing this module has is a better answer than the bytes an author or another process put there — and the proposal is settled the safe way, back to `pending`, so it is offered again rather than claimed as accepted on evidence that no longer exists; one `WARN` record names the artifact and the proposal (PCP-FR-28). A reconciliation whose own writes fail leaves the journal in place and is attempted again by the next command, and until it succeeds that command answers with `write_failed` rather than with a decision. A decision attempted while another acceptance of the same proposal is in flight returns the typed `acceptance_in_progress` and writes nothing.
    `<proposal-id>.prior` is written on every acceptance and is read by no ordinary path, the artifact never needing restoring. It is kept because it is the one thing that could put the file back if the atomicity beneath the write were ever violated, and because a recovery that has the bytes is worth more than a recovery that has only a checksum of them.
15. **PCP-FR-15** `decline_prompt_change_proposal(proposal_id, feedback?)` moves a pending proposal to `rejected` and **writes nothing into the project**: the artifact is not modified and no journal is begun, whether or not the author edited the candidate first, and the `.content` file is kept rather than removed, so a declined proposal can still be read back afterwards as the candidate the author declined.
16. **PCP-FR-16** Each decision appends **one comment** into the proposal's own thread, through the ordinary human write path (per `CMS-comments-storage.md` CMS-FR-11), so it is stamped with the acting author's identity like any comment they write themselves. Its body states which way the proposal was decided, states whether the candidate decided was the agent's own or one the author rewrote (PCP-FR-22) — because an agent reading the thread to learn what happened is owed the difference between "your text landed" and "your text was rewritten and that landed" — and carries `feedback` where any was supplied, and it carries no attachment. This comment is the whole of what the record of a decision is in the conversation: the proposal was posted as a comment (PCP-FR-05) and the decision is answered as a comment, so a reader scrolling the thread months later reads the offer and the answer in sequence without opening anything. **The two conditions that would make the append impossible are checked before anything is written.** An identity that does not resolve (per `CMS-comments-storage.md` CMS-FR-12) and a conversation locked between the author reading the comparison and deciding it are each refused with their own typed error up front, so the decision is not taken, the artifact is untouched, and the proposal is still pending. A decline appends its comment as its one act. An acceptance appends its comment after the write has landed, on the terms of PCP-FR-14. A decision comment that is appended announces its conversation on exactly the terms the proposal's did (per `CMS-comments-storage.md` CMS-FR-51).
17. **PCP-FR-17** `"prompt change proposals changed"` is emitted when a proposal is **recorded** — by `record_prompt_proposal` itself, so a proposal made during a session reaches every surface without one of them re-reading — and again when it is decided, carrying the artifact and the whole proposal, so a surface showing that artifact — and the shell surface that raises a notification about it (per `../ui/PCR-prompt-change-review.md` PCR-FR-17) — redraws from the payload without polling. An acceptance emits it **after its commit point** and never before (PCP-FR-14), so no surface is ever told a proposal is accepted while the acceptance could still be rolled back, and a rollback therefore emits nothing at all — a surface that saw no event saw no decision. The `"artifact changed externally"` suppression of `PST-project-storage.md` PST-FR-16 holds for the acceptance's own write, so the artifact's editing session learns of the change from this event rather than as a divergence to resolve (per `../ui/PCR-prompt-change-review.md` PCR-FR-11). No event is emitted where nothing was recorded or decided, and none where a decision was rolled back — a surface that saw no event saw no decision, and there is no third thing for one to announce.
    The payload carries the **whole proposal as it now stands**, its `state` included, which is what makes the event sufficient on its own: a surface reading `accepted` or `rejected` from it knows the proposal is settled without asking this module anything further, and that is the one fact the shell needs in order to take back the notification it raised and clear the marking it left (per `../ui/PCR-prompt-change-review.md` PCR-FR-26, `../ui/NTF-notifications.md` NTF-FR-38). The event goes to **every** subscriber rather than to the caller that decided, so a decision taken in one window settles the proposal for every surface in the application on the same terms and at the same moment. An acceptance whose decision comment is still owed emits it too, and emits it with `state = accepted`: the event is emitted at the commit point rather than at the append (PCP-FR-14), because the decision is what a surface acts on and the comment is what the conversation is owed.
18. **PCP-FR-18** A decision against a proposal that is already `accepted` or `rejected` is a typed `already_decided` error: nothing is written, no comment is appended, and no event is emitted. A proposal is decided once, and a second decision arriving from a second window finds it settled rather than overwriting what the first decided.
19. **PCP-FR-19** An acceptance whose `artifact_id` no longer resolves to a file the project holds, or resolves to one whose artifact type is no longer `prompt`, is the typed `artifact_not_found` or `not_a_prompt_artifact` error: nothing is written, no journal is begun, the proposal stays `pending`, and **no file is created at that path**, because a proposal replaces an artifact rather than restoring one (PCP-FR-08). Declining it succeeds on the ordinary terms of PCP-FR-15, which is how such a proposal is cleared.
20. **PCP-FR-20** This module decides nothing on its own. No proposal expires, is collected, is retried, is auto-accepted, or is auto-declined, at any age or under any load; there is no timer, no queue, and no threshold anywhere in it. A proposal stands until the author decides it — which is what makes a proposal left undecided for a month cost exactly what one decided immediately costs. The one sweep this module performs runs at project open and removes the record and candidate of a **decided** proposal whose artifact the project no longer holds, a decided proposal about a file that is gone being material nothing can read and nothing can decide; a **pending** proposal is never swept, whatever its target has become, because it is still the author's to decline.
21. **PCP-FR-21** This module dispatches no agent turn and reaches no model. Telling the conversation what was decided is its own ordinary business: the decision comment is a human comment like any other, and the turns it dispatches — one for each agent that conversation is currently addressed to, and none where it is addressed to nobody — are the surface's to dispatch (per `../ui/PCR-prompt-change-review.md` PCR-FR-14, `../ui/CTA-comment-agent-turns.md` CTA-FR-LCFU, CTA-FR-QUXJ) and `AGC-agent-conversations.md`'s to run (AGC-FR-29).
22. **PCP-FR-22** `save_prompt_change_proposal_candidate(proposal_id, content, baseline_checksum)` writes the author's own text over the candidate of a **pending** proposal, and is the only path by which anything but a recording changes a `.content` file. It writes exactly one file — `<proposal-id>.content` — and returns the checksum of the bytes written. It sets `candidate_edited` on the record whenever the checksum of the bytes it wrote differs from the `origin_checksum` the recording stamped, and clears it again where an edit restores those bytes exactly, so the flag describes the candidate rather than the history of getting to it. **It is not a change to the artifact**: the artifact's file is not created, modified, or deleted, no `"artifact changed externally"` event follows, nothing is recorded in the recently-edited list, and neither decision operation is called. This is the whole reason the surface above can promise that a candidate under revision has cost the project nothing (per `../ui/PCR-prompt-change-review.md` PCR-FR-22).
23. **PCP-FR-23** A candidate save against a proposal that is `accepted` or `rejected` is a typed `already_decided` error and writes nothing: a candidate is the author's to shape only while the decision it is for is still owed, and the text a decided proposal holds is the record of what was decided. The command emits no `"prompt change proposals changed"` event when it succeeds either, the proposal's state being exactly what it was; the surfaces that care read `candidate_edited` from the record they already hold or from their next list.
24. **PCP-FR-24** A candidate save whose `baseline_checksum` does not match the checksum of the bytes `<proposal-id>.content` currently holds is a typed `candidate_stale` error and writes nothing, so a review that has been editing a candidate another window has since rewritten cannot overwrite it unknowingly; the caller resolves it explicitly (per `../ui/PCR-prompt-change-review.md` PCR-FR-25). A failed write leaves the candidate byte-for-byte as it was, returns `write_failed`, and leaves the proposal `pending` with whatever `candidate_edited` already said, the write being atomic on the terms of `FSA-filesystem-access.md` FSA-FR-04.
25. **PCP-FR-25** Every filesystem operation this module performs goes through `FSA-filesystem-access.md` primitives and through no other route: `write_text_atomic` for a `.content` file, whether written by a recording or by a candidate save, and for the `<proposal-id>.prior` of an acceptance; `write_toml_atomic` for a record and for a journal; `sha256_file` for every checksum; `delete_path` for the cleanup of PCP-FR-06, for the journal and `.prior` an acceptance settles (PCP-FR-14), and for the sweep of PCP-FR-20; and `ensure_gitignored` for the folder of PCP-FR-02. Reading the artifact's bytes before an acceptance, and reading them back during a reconciliation, go through that spec's read and checksum primitives too. This module performs no raw `fs::write`, `fs::read`, `fs::remove`, or `fs::rename` call, and it is subject to FSA's path-escape rejection (FSA-FR-10). It writes nothing outside `.synthesis/proposals/` at all, the one exception being the artifact bytes an acceptance lands, which go through `PST-project-storage.md`'s write path (PCP-FR-12), itself performing its own containment check and its own atomic write through the same primitives. **No rollback of this module writes a file of the project**: a rollback rewrites this module's own record and nothing else, the artifact never needing restoring (PCP-FR-14). The recovery path for an owed decision comment (PCP-FR-14) writes only the record and removes only the journal and `<proposal-id>.prior`, through these same primitives, and appends through `CMS-comments-storage.md`'s own write path.
26. **PCP-FR-26** Every command errors with a typed `no_project_open` when no project is open, with `artifact_not_found` when `artifact_id` names no file in the active worktree, and with `proposal_not_found` when `proposal_id` names no proposal. Changing the active worktree re-resolves the proposals folder against the new content root, so a proposal made in one worktree is invisible from another.
27. **PCP-FR-27** Nothing in this module reaches the network, contacts an AI integration, or touches a credential, save for the GitHub identity the decision comment's append resolves through `CMS-comments-storage.md` (CMS-FR-12), which is the same resolution any comment the author posts performs.
28. **PCP-FR-28** Every operation emits through `LGC-logging.md`'s internal API under the `backend` domain: an `INFO` record when a proposal is recorded and when one is decided, naming the artifact, the proposal, the `path`, and the outcome, a `DEBUG` record when a candidate is saved, naming the artifact and the proposal, and a `WARN` record when an operation refuses, naming the same and the reason. An acceptance additionally emits a `WARN` for each of the three outcomes a reader has to be able to find afterwards: one when a transaction is **rolled back**, naming the artifact, the proposal, and which step failed; one when a reconciliation settles a transaction it found unfinished, naming which of the three readings of PCP-FR-14 it took; and one when a reconciliation leaves a file alone because it matches neither checksum the journal recorded. None of them ever reports a file this module changed and did not settle, there being no such outcome (PCP-FR-14). **No record carries the proposed text, the author's rewrite of it, the artifact's current text, the `rationale`, or any `feedback`**, all of which are material a model or an author composed.
29. **PCP-FR-29** This module and `DCP-draft-change-proposals.md` share nothing. They hold their records in different folders, expose different commands, emit different events, use different attachment kinds, and perform different acceptances — one replacing a published artifact through `PST-project-storage.md`'s write path, the other replacing a draft's prompt through `DRS-draft-storage.md`'s and recording a version in that draft's history. No operation of either reads, decides, lists, or counts a proposal of the other, and the one-pending rule of PCP-FR-04 counts this module's proposals alone, so a draft carrying a pending proposal never blocks a proposal against an artifact and the reverse never happens either.

## Non-functional requirements
- A proposal's text is a file on disk in an ordinary folder, so an author can read or recover one with a file manager if the application will not open.
- Listing proposals reads records alone and never a document, so opening an artifact that has accumulated a long proposal history costs one directory read.
- The candidate is written once by the recording and read when a comparison is rendered, so a proposal nobody opens costs one write and no read at all. An author who revises it pays one further atomic write per settled burst of their typing and nothing else — no record rewrite beyond the `candidate_edited` flag when it actually turns over, no event, and no work anywhere in the project.
- An acceptance costs one read of the artifact, one `.prior` write of the same size, one journal write, one record write, one write through the artifact's own save path, one appended comment, and two removals. All of it is bounded by the size of the prompt and independent of how many proposals the artifact has accumulated. Keeping the pre-acceptance bytes rather than a checksum of them doubles what an acceptance writes; a prompt is a document a person reads, so the extra write is measured in kilobytes, and it buys a recovery that has the bytes rather than only a checksum of them.
- A rollback costs one small record write and happens only where a transaction failed, so the ordinary acceptance never pays for it and no rollback anywhere rewrites a file of the project.
- Nothing here holds a proposal or a candidate in memory between calls, watches the folder, or maintains a queue: the folder is the whole of the state, so a relaunch mid-review finds every pending proposal exactly where it was, an edited candidate included.
- The walking-skeleton implementation may keep records and candidate texts in memory rather than on disk, provided the record shapes, the one-pending rule, the sort order, the emitted event, the checksum semantics of the candidate read and write, and the error types above are the ones returned to the UI.
- No operation here contacts the network or any AI integration.
