# Project storage

**Spec code:** `PST`

## Intent
Owns the project lifecycle and the `.synthesis/` folder structure. Provides the Tauri commands the UI invokes for opening, creating, closing, and inspecting a project; serves the filesystem-derived, type-tagged project tree the Project panel renders (the recursive scan, classification, attribution storage, and change-watching are owned by `ASC-artifact-scanning.md`); serves artifact contents to the Editor and to Flow; and serves the Dashboard's widget loaders from the project's current records and the current state of its filesystem, and owns the application-wide timer that keeps two of those widgets fresh (PST-FR-36). Supports two storage modes: standalone (the `.synthesis/` folder is the root of its own Git repository, preferred) and co-located (`.synthesis/` sits inside an existing code repository). Out of scope: notes, whose record, storage, and commands belong to `NTC-notes-storage.md`; and the interpretation of what an artifact's bytes mean, with one exception that is delegated rather than performed here — a `flow`-typed artifact is checked against the Flow schema by `FGV-flow-graph-validation.md` before it is written (PST-FR-28), so an invalid Flow never reaches disk through this module, and every other artifact is served and stored as bytes whose meaning this module never reads.

## Contract surface
All operations below are Tauri commands invoked by the UI. The quoted name is the canonical operation name as it appears in the corresponding UI spec's "Delegated to backend (abstract)" line; the snake_case identifier is the Rust function name.

Project lifecycle (per `../ui/PPK-project-picker.md`):
- The recent-projects list and its commands (`list_recent_projects` and the management commands) are owned by `GSS-global-settings-storage.md` (GSS-FR-05); this module only appends the current project to that list on successful open/create (PST-FR-06).
- `"open project at path"` → `open_project_at_path(path)` — opens the project rooted at `path` and returns a project handle; uses `discover_project_root` from `FSA-filesystem-access.md` so a parent path of `.synthesis/project.toml` is acceptable. The handle carries both levels of the project's identity: the repository that owns it and the active worktree that roots it (per `WTC-worktree-context.md` WTC-FR-03).
- `"open project from git url"` → `open_project_from_git_url(url)` — clones the URL into a workspace location and then opens the resulting path.
- `"create project (mode = standalone | co-located, target path)"` → `create_project(name, mode, target_path)` where `mode ∈ {standalone, colocated}`; scaffolds `.synthesis/` and returns a project handle.
- `"browse for folder"` → re-exports `browse_for_folder` from `FSA-filesystem-access.md`.

Project panel tree and artifact access (per `../ui/LIB-library.md`, `../ui/EDT-editor.md`, `../ui/TAB-tabs.md`):
- `"load project tree (filesystem nodes tagged by artifact type)"` → `load_project_tree()` — returns the filesystem-mirroring tree (folders and files as they exist on disk) with each file node tagged by its resolved artifact type and each folder node carrying `has_artifacts`. The tree is produced by the scanner in `ASC-artifact-scanning.md` (node shape, classification, and `.synthesis/library.toml` attribution defined there); this module exposes it as the UI-facing command.
- `"open artifact by id"` → `open_artifact_by_id(id)` — returns a stable key plus a kind hint (`markdown` | `flow` | `text`) so the UI routes to Editor or Flow. `text` names a file carrying no artifact type (PST-FR-23).
- `"load artifact contents by id"` → `load_artifact_contents_by_id(id)` — returns `{ body, checksum }` for a markdown-based artifact, a Flow document, or a plain text file, where `checksum` is `FSA-filesystem-access.md::sha256_file` of the file served. The checksum is the Editor's divergence baseline (per `../ui/EXC-editor-external-change.md` EXC-FR-WCOM).
- `"save artifact contents"` → `save_artifact_contents(id, body)` — writes the body back to the file the artifact's primary reference points at, with line endings normalised to the project's convention (PST-FR-22), and returns `{ checksum }` of the bytes written. A `flow`-typed artifact passes `FGV-flow-graph-validation.md::validate_flow_document` first and a body carrying violations is refused with them (PST-FR-28).

File creation (per `../ui/NFI-new-file.md`):
- `"create file (location, name)"` → `create_file(location, name)` — creates an empty file named `name` inside the project-relative folder `location` (the project root when `location` is unset) via `FSA-filesystem-access.md::write_text_atomic` with an empty body. `name` is the file's complete basename, extension included: a value that is empty, contains a path separator, or escapes the project root (FSA-FR-10) is a typed error and nothing is written, and a collision with an existing entry in the destination is a typed error with nothing written. No `artifact_type` argument exists and no type assignment is recorded, so the new file's type is left entirely to inference and folder-scope inheritance (`ASC-artifact-scanning.md` ASC-FR-06). Returns the new file node in the `ASC-artifact-scanning.md` TreeNode shape so the UI can open and reveal it. Errors with a typed "no project open" when no project is open.

Typed artifact creation (per `../ui/NTA-new-typed-artifact.md`):
- `"create typed file (location, name, artifact type)"` → `create_typed_file(location, name, artifact_type)` — creates an empty file named `name` inside the project-relative folder `location` (the project root when `location` is unset) **and** records `artifact_type` as that file's file-scope assignment, as one creation transaction. `name` is the file's complete basename, extension included, validated on exactly the terms `create_file` validates it; `artifact_type` is required and is one of the eight built-in types (`ASC-artifact-scanning.md` ASC-FR-02). Either both the file and its assignment survive the call or neither does (PST-FR-29). Returns the new file node in the `ASC-artifact-scanning.md` TreeNode shape, carrying the assigned type, so the UI can open and reveal it. Errors with a typed "no project open" when no project is open. It creates no draft, reaches nothing under `.synthesis/drafts/`, and copies no draft template.

Folder creation (per `../ui/NFW-new-folder.md`):
- `"create folder (location, name, artifact type)"` → `create_folder(location, name, artifact_type)` — creates an empty folder named `name` inside the project-relative folder `location` (the project root when `location` is unset) via `FSA-filesystem-access.md::create_dir`. `name` is a bare basename: a value that is empty, contains a path separator, or escapes the project root (FSA-FR-10) is a typed error and nothing is created, and a collision with an existing entry in the destination is a typed error with nothing created. When `artifact_type` is supplied it is one of the eight built-in types (`ASC-artifact-scanning.md` ASC-FR-02) and a folder-scope assignment is recorded for the new folder (`ASC-artifact-scanning.md` ASC-FR-05, scope = folder); when omitted, no assignment is recorded and the folder's future contents are left to path inference. Returns the new folder node in the `ASC-artifact-scanning.md` TreeNode shape so the UI can reveal it. Errors with a typed "no project open" when no project is open.

Project panel file operations (per `../ui/LCM-library-context-menu.md`):
- `"delete path (path, recursive)"` → `delete_path(path, recursive)` — deletes the file or folder at project-relative `path` via `FSA-filesystem-access.md::delete_path`. A folder is removed with its subtree only when `recursive` is true; with `recursive` false a folder holding any entry is a typed "not empty" error and nothing is removed, so a caller that has not yet obtained the user's consent to a recursive removal cannot perform one by accident. Errors with a typed "no project open" when no project is open and "not found" when the path does not exist. The resulting structural change reaches the UI through `ASC-artifact-scanning.md`'s `"project tree changed"` event, not a return payload.
- `"rename path"` → `rename_path(path, new_name)` — renames the node at `path` to `new_name` within its parent via `FSA-filesystem-access.md::rename_path`. `new_name` is a bare basename; a value containing a path separator, one equal to the node's current basename, or one that collides with an existing sibling, is a typed error and no rename occurs.
- `"copy path into folder"` → `copy_path_into_folder(source_path, dest_folder)` — copies `source_path` (recursively for a folder) into `dest_folder` as `dest_folder/<basename(source_path)>` via `FSA-filesystem-access.md::copy_path`. A destination name collision is a typed error and nothing is written; the source is left untouched (copy, not move).

Dashboard widget loaders (per `../ui/DSH-dashboard.md`):
- `"list recently edited artifacts"` → `list_recently_edited_artifacts` — enumerates the artifacts the open project currently holds and returns the five whose **primary source file** was modified most recently, as `[RecentlyEditedItem]` (PST-FR-31).
- `"list active drafts"` → `list_active_drafts` — returns the five `active` drafts whose **prompt file** was modified most recently, as `[ActiveDraftItem]` (PST-FR-32).
- `"list recent agent runs"` → `list_recent_agent_runs` — returns the open project's five most recently updated graduation runs, runs still `queued` included, as `[AgentRunItem]` (PST-FR-33).
- `"list pending git activity"` → `list_pending_git_activity` — returns `PendingGitActivity`, the four counts describing what the project has pending in Git (PST-FR-34).
- `"list due/upcoming reminders"` → `list_due_reminders`
- `"list project health signals"` → `list_project_health_signals`

Dashboard payload shapes:
```
RecentlyEditedItem {
  id,            // the artifact's stable path-derived key (ASC-artifact-scanning.md ASC-FR-13)
  name,          // the artifact's display name, from its current record
  kind,          // "markdown" | "flow", the hint of open_artifact_by_id (PST-FR-08)
  modified_at    // RFC 3339 UTC; the primary source file's filesystem
                 //   modification time, read at load
}

ActiveDraftItem {
  draft_id,
  name,          // the draft's stored name (DRS-draft-storage.md DRS-FR-03)
  status,        // always "active"
  activity_at    // RFC 3339 UTC; the prompt file's filesystem modification
                 //   time (DRS-draft-storage.md DRS-FR-41)
}

AgentRunItem {
  run_id,
  draft_id,
  draft_name,        // the source draft's stored name
  stream_id,         // the work stream the run belongs to
  stream_name,       // that stream's own name; for a direct run, the name of the worktree it pinned
  state,             // GraduationRunState (GRD-graduation.md)
  stage,             // GraduationStage
  stage_condition,   // GraduationStageCondition
  queue_position,    // the run's index in its own queue while it is queued; null otherwise
  updated_at         // RFC 3339 UTC; the run's own updated_at
}

PendingGitActivity {
  modified_artifacts,     // count of uncommitted changed paths that carry an artifact type
  modified_source_files,  // count of uncommitted changed paths that carry none
  unpushed_commits,       // commits the current branch holds above its upstream; null
                          //   when the branch has no upstream
  fetchable_commits       // commits the upstream holds above the current branch; null
                          //   when the branch has no upstream
}
```

Notes are not owned here: the note record, its persisted home under `.synthesis/notes/`, and every note command are defined by `NTC-notes-storage.md`. This module scaffolds that folder (PST-FR-02) and reads the reminder instants it stores to serve `list_due_reminders`.

Draft statistics are not owned here either: the event log, its per-draft layout, its fold, and every statistics command are defined by `DSS-draft-statistics-storage.md`. That log stands in the repository machine store (`RMS-repository-machine-storage.md`) rather than in the project, so this module scaffolds no folder for it and reads nothing in it.

Events emitted by this module on the Tauri event bus:
- `"active tab changed"` — fires when the UI's active tab changes, so the Notes panel can rescope (per `../ui/NTS-notes.md` NTS-FR-08). Payload: `{ entity_id? }`.
- `"artifact changed externally"` — fires when an artifact's referenced file has been modified outside the running Editor (e.g. via Git checkout, external editor, or restore). Payload: `{ artifact_id, checksum }`, where `checksum` is the new on-disk `sha256_file`. Backed by the content-modification path of the `ASC-artifact-scanning.md` watcher (ASC-FR-15) and emitted with self-write suppression (PST-FR-16). The Editor **resolves** the event via its external-change modal (per `../ui/EXC-editor-external-change.md` EXC-FR-QCNO–EXC-FR-VNLZ).
- `"dashboard recently edited changed"` — the Recently edited widget's data may have moved. Payload: `{}`. Emitted on the terms of PST-FR-35.
- `"dashboard active drafts changed"` — the Active workstreams widget's data may have moved. Payload: `{}`. Emitted on the terms of PST-FR-35.
- `"dashboard agent activity changed"` — the Last/current agent activity widget's data may have moved. Payload: `{}`. Emitted on the terms of PST-FR-35 and by the timer of PST-FR-36.
- `"dashboard pending git changed"` — the Pending Git activity widget's data may have moved. Payload: `{}`. Emitted on the terms of PST-FR-35 and by the timer of PST-FR-36.
- `"dashboard refresh failed"` — a background refresh of one widget could not be completed. Payload: `{ widget, error }`, where `widget` names one of `recently_edited`, `active_drafts`, `agent_activity`, or `pending_git` and `error` is the typed failure the loader returned. It is the user-visible error path of PST-FR-37: the Dashboard renders that widget's own error state on it (per `../ui/DSH-dashboard.md` DSH-FR-18).

A Dashboard refresh event carries no widget data. A consumer re-invokes the loader the event names and renders what that call returns, so what the Dashboard shows is what the loaders hold rather than what an emitter believed (per `../ui/DSH-dashboard.md` DSH-FR-15, DSH-FR-16).

## Functional requirements
1. **PST-FR-01** `open_project_at_path(path)` resolves the project root via `FSA-filesystem-access.md::discover_project_root`. If no `.synthesis/project.toml` is found at `path` or any ancestor, the operation fails with a typed "not a synthesis project" error; the UI surfaces it inline per `../ui/PPK-project-picker.md` PPK-FR-07. When the resolved root sits inside a Git repository, the open additionally resolves the repository and its worktrees (`WTC-worktree-context.md` WTC-FR-02): the project's identity is the repository, and the worktree that resolution lands in — the one opened, or the remembered one when the recorded primary worktree was opened (WTC-FR-17, WTC-FR-18) — becomes the active worktree and therefore the project root every operation below resolves against.
2. **PST-FR-02** `create_project(name, mode = standalone, target_path)` scaffolds `target_path/.synthesis/` with the layout from the Notion Project storage page: `project.toml`, `artifacts/`, `playbooks/`, `workstreams/`, `roles/`, `notes/`, `.gitignore`, `cache/`, `drafts/`, `local.toml`. The `.gitignore` is created via `FSA-filesystem-access.md::ensure_gitignored` and excludes `cache/` and `local.toml` and not `drafts/` (FSA-FR-08). No `comments/` and no `statistics/` folder is created: the conversation logs of `CMS-comments-storage.md` (CMS-FR-01) and the statistics logs of `DSS-draft-statistics-storage.md` (DSS-FR-KQVN) live in the repository machine store (`RMS-repository-machine-storage.md` RMS-FR-ZXHM). The `drafts/` folder is the committed home of the drafts of `DRS-draft-storage.md` (DRS-FR-04), scaffolded here and written by that module and the draft-storage modules beside it; its `.gitattributes` is theirs to ensure (DRS-FR-DGMI).
3. **PST-FR-03** `create_project(... mode = colocated, target_path)` requires `target_path` to be an existing directory; the `.synthesis/` folder is created inside it without modifying any other file in `target_path`.
4. **PST-FR-04** `create_project` fails with a typed "already a project" error if `target_path` (standalone) or `target_path/.synthesis/` (co-located) already contains `project.toml`.
5. **PST-FR-05** The recent-projects list is user-global and is owned by `GSS-global-settings-storage.md` (GSS-FR-05), where `list_recent_projects` and the list-management commands are defined. This module does not define those commands; it only appends the current project on successful open/create (PST-FR-06).
6. **PST-FR-06** Every successful `open_project_at_path`, `open_project_from_git_url`, and `create_project` records the project as the most-recent entry in the user-global recent-projects list (owned by `GSS-global-settings-storage.md` GSS-FR-10).
7. **PST-FR-07** `load_project_tree` returns the filesystem-derived tree that mirrors the project's on-disk folders and files (per `../ui/LIB-library.md` LIB-FR-02), produced by the scanner in `ASC-artifact-scanning.md` (recursive scan ASC-FR-01, classification ASC-FR-06, `.synthesis/library.toml` attribution ASC-FR-05). Each node carries the shape defined in `ASC-artifact-scanning.md` (`{ id, name, path, node_kind, artifact_type?, type_source?, display_name?, has_artifacts?, children? }`). Flows appear at their natural filesystem location, not under a separate "Flows" branch.
8. **PST-FR-08** `open_artifact_by_id(id)` returns a `{ stable_key, kind }` pair such that the same `id` produces the same `stable_key` across calls and across surfaces (Project panel, Search, Dashboard, Flow click-through). The `id` is the stable, path-derived node key defined in `ASC-artifact-scanning.md` ASC-FR-13. This is the identity the UI compares for the single-tab rule of `../ui/TAB-tabs.md` TAB-FR-04.
9. **PST-FR-09** `save_artifact_contents(id, body)` writes the body to the artifact's primary file reference (per the Notion Artifact model: File references → roles). An unsaved edit is never written anywhere else on the way there: the Editor holds it in memory alone (per `../ui/EDT-editor.md` EDT-FR-28), so this module writes an artifact's own file or nothing at all. `.synthesis/drafts/` holds no working copy of any artifact; it is the committed home of the drafts developed in the New Artifact tab (per `../ui/NAW-new-artifact.md`), which are files in their own right rather than shadows of files in the project.
10. **PST-FR-10** Every write that mutates `.synthesis/` or a referenced artifact file goes through the atomic-write primitives from `FSA-filesystem-access.md`: `write_toml_atomic` for `.synthesis/*.toml` metadata, `write_text_atomic` for Markdown artifact bodies, `write_bytes_atomic` for any other file content. This module does not perform raw `fs::write` calls. The empty file `create_file` creates (PST-FR-25) goes through `write_text_atomic` whatever its extension, because an empty body is text under every convention. Structural mutations of project files — `delete_path`, `rename_path`, `copy_path_into_folder`, and `create_folder` (PST-FR-18–PST-FR-20, PST-FR-24) — likewise go through the corresponding `FSA-filesystem-access.md` primitives; this module performs no raw `fs::remove`, `fs::rename`, `fs::copy`, or `fs::create_dir` calls.
11. **PST-FR-11** Each artifact has at most one `.synthesis/artifacts/<artifact-id>.toml` metadata file (Notion Project storage → Folder structure). This per-artifact-file layout is preserved by all write operations.
12. **PST-FR-12** Dashboard widget loaders (`list_recently_edited_artifacts`, `list_active_drafts`, `list_recent_agent_runs`, `list_pending_git_activity`, `list_due_reminders`, `list_project_health_signals`) exist as commands with the typed return shapes of the Contract surface. Five of the six serve the project's real state: `list_recently_edited_artifacts` (PST-FR-31), `list_active_drafts` (PST-FR-32), `list_recent_agent_runs` (PST-FR-33), `list_pending_git_activity` (PST-FR-34), and `list_due_reminders`, which is backed by the notes carrying a reminder (`NTC-notes-storage.md` NTC-FR-17) — it reads that module's reminder enumeration and returns the due and upcoming ones with the entity each is attached to, so the Reminders widget's click-through (`../ui/DSH-dashboard.md` DSH-FR-06) has a target. `list_project_health_signals` may return an empty list or canned data in the walking skeleton. Every loader answers with a list or a record and never throws for an absent project, an empty project, or an unreadable individual entry; empty returns correspond to widgets being hidden in `../ui/DSH-dashboard.md` DSH-FR-04.
13. **PST-FR-13** The notes surface is owned by `NTC-notes-storage.md`: it defines the note record, the note commands, and the one-file-per-note layout under `.synthesis/notes/`. This module's involvement is limited to scaffolding that folder as part of `create_project` (PST-FR-02) and reading the reminder instants it stores to serve `list_due_reminders` (PST-FR-12).
14. **PST-FR-14** Closing a project unmounts in-memory state for that project (open file handles, caches) and modifies no file of the project on disk, the draft-asset housekeeping of PST-FR-30 being the one write a close may perform and reaching draft-owned material alone. Changing the project's active worktree performs the same unmount for the outgoing content root and then remounts on the new one (per `WTC-worktree-context.md` WTC-FR-08), likewise without modifying any file in either worktree; the project itself stays open throughout.
15. **PST-FR-15** `load_artifact_contents_by_id(id)` returns `{ body, checksum }` and `save_artifact_contents(id, body)` returns `{ checksum }`, where `checksum` is computed with `FSA-filesystem-access.md::sha256_file` (FSA-FR-07) over the exact bytes served or written. These checksums are the baseline the Editor uses for external-change detection (`../ui/EXC-editor-external-change.md` EXC-FR-WCOM).
16. **PST-FR-16** While a project is open, a content modification reported by the `ASC-artifact-scanning.md` watcher (ASC-FR-15) to a file that resolves to an artifact causes this module to emit `"artifact changed externally"` with `{ artifact_id, checksum }` of the new on-disk content. The event fires only when the new checksum differs from the last checksum this module served or wrote for that artifact, so a `save_artifact_contents` write does not produce a divergence event for itself (self-write suppression). Structural changes (create/delete/rename/move) continue to flow through `"project tree changed"` (per `ASC-artifact-scanning.md` ASC-FR-10), not this event.
17. **PST-FR-17** `save_artifact_contents(id, body)` keeps **no record of what it saved**. It writes no most-recently-edited list, invokes no command of `PSS-project-settings-storage.md` for one, and leaves no application save history anywhere. What puts an artifact at the head of Recently edited is the modification time the write itself gives the artifact's source file (PST-FR-31), which is a fact about the project rather than about this application: an artifact written by an external editor and one written by a Flow tab (`../ui/FLO-flow.md` FLO-FR-27) reach the widget on identical terms, and a save that fails moves nothing because it changed no file.
18. **PST-FR-18** `delete_path(path, recursive)` removes the file or folder at the project-relative `path` through `FSA-filesystem-access.md::delete_path` (FSA-FR-11). A file is removed whatever `recursive` says. A folder is removed together with its subtree when `recursive` is true; when `recursive` is false it is removed only if it is empty, and a folder holding any entry yields a typed "not empty" error with nothing removed. That error is drawn from the filesystem rather than from any caller's view of the folder, so it counts entries the scan excludes (`ASC-artifact-scanning.md` ASC-FR-09) and entries the caller's own filters hide; a folder that looks empty to the Project panel still reports as non-empty when it holds gitignored content. `path` resolves against the open project root and is subject to the explicit containment check of PST-FR-26; deleting a path that does not exist is a typed error distinct from "not empty". The deletion is observed by the `ASC-artifact-scanning.md` watcher and reported to the UI through `"project tree changed"` (ASC-FR-10).
19. **PST-FR-19** `rename_path(path, new_name)` renames the node at `path` to `new_name` within the same parent through `FSA-filesystem-access.md::rename_path`. `new_name` must be a bare basename; a value containing a path separator, or one that collides with an existing sibling, is rejected with a typed error and no filesystem change occurs. A `new_name` equal to the node's current basename is rejected on its own terms with a typed "unchanged name" error, distinct from the sibling-collision error a self-collision would otherwise be reported as, and no rename is attempted — a rename that would change nothing is an error rather than a successful no-op, so a caller can never mistake it for work performed.
20. **PST-FR-20** `copy_path_into_folder(source_path, dest_folder)` copies `source_path` (recursively for a folder) into `dest_folder` at `dest_folder/<basename(source_path)>` through `FSA-filesystem-access.md::copy_path`. The copy never overwrites: a pre-existing destination of that name is a typed error and the source is left unchanged. Both paths resolve against the project root and escapes are rejected (FSA-FR-10).
21. **PST-FR-21** Every path this module resolves — `.synthesis/` and its contents, the project tree, artifact files, and the project-relative inputs of `create_file`, `create_folder`, `delete_path`, `rename_path`, and `copy_path_into_folder` — resolves against the project's **active worktree** directory (per `WTC-worktree-context.md` WTC-FR-03). Because `.synthesis/` is committed content, a repository with several worktrees holds several copies of it, and the active worktree's copy is the one this module reads and writes; no operation reaches into a sibling worktree, and `FSA-filesystem-access.md` FSA-FR-10's escape rejection is applied with the active worktree as the root.
22. **PST-FR-22** `save_artifact_contents(id, body)` normalises every line ending in `body` to the open project's line-ending convention (`PSS-project-settings-storage.md` PSS-FR-17) before writing, so the bytes on disk use that convention throughout regardless of what the submitted body or the previous on-disk content used. The `{ checksum }` it returns (PST-FR-15) is computed over the normalised bytes actually written, which is what makes it a valid baseline for the Editor (`../ui/EDT-editor.md` EDT-FR-40). No other content this module writes is normalised: `.synthesis/` metadata is written through the TOML primitive of `FSA-filesystem-access.md` and is unaffected.
23. **PST-FR-23** An `id` naming a file the scan surfaces without a resolved artifact type resolves through the same three commands as an artifact: `open_artifact_by_id` returns its stable key with `kind = "text"`, and `load_artifact_contents_by_id` and `save_artifact_contents` serve and write it with the same `checksum` semantics (PST-FR-15), the same line-ending normalisation (PST-FR-22), and the same external-change detection (PST-FR-16). This is what lets the Editor open it as a plain text file (`../ui/ESH-editor-source-files.md` ESH-FR-ATDS). Such a file never appears in Recently edited, whatever its modification time, because that loader enumerates artifacts and a file carrying no type is not one (PST-FR-31).

24. **PST-FR-24** `create_folder(location, name, artifact_type)` creates an empty folder named `name` inside `location` — a project-relative folder, or the project root when `location` is unset — through `FSA-filesystem-access.md::create_dir` (per PST-FR-10). `name` must be a bare basename: an empty name, a name containing a path separator, or a destination escaping the project root (FSA-FR-10) is a typed error, and a collision with any existing entry in the destination — file or folder alike — is a typed error; in every error case nothing is created and no existing folder is adopted or emptied. When `artifact_type` is supplied (one of the eight built-in types, `ASC-artifact-scanning.md` ASC-FR-02), a folder-scope type assignment for the new folder is recorded via the `ASC-artifact-scanning.md` attribution path (ASC-FR-05, scope = folder, through `write_toml_atomic`), so the files the folder later holds resolve to that type by inheritance (ASC-FR-06); when it is omitted, no assignment is recorded and those files are left to inference. On success the new folder node (the `ASC-artifact-scanning.md` TreeNode shape) is returned so the UI can reveal it, and the creation is observed by the watcher and reaches the UI through `"project tree changed"` (`ASC-artifact-scanning.md` ASC-FR-10). The operation errors with a typed "no project open" when no project is open.
25. **PST-FR-25** `create_file(location, name)` creates an empty file named `name` inside `location` — a project-relative folder, or the project root when `location` is unset — through `FSA-filesystem-access.md::write_text_atomic` with an empty body (per PST-FR-10). `name` is the file's complete basename, extension included, and the operation neither requires an extension nor derives, appends, or validates one: `Makefile`, `.gitignore`, and `helpers.ts` are all accepted as given. A name that is empty, contains a path separator, or names a destination escaping the project root (FSA-FR-10) is a typed error, and a collision with any existing entry in the destination — file or folder alike — is a typed error; in every error case nothing is written and no existing file is truncated. The operation takes no artifact-type argument and records no assignment in `.synthesis/library.toml`, so the new file's type is whatever the classification precedence of `ASC-artifact-scanning.md` ASC-FR-06 yields for its path — an inference, an inherited folder-scope assignment, or none. On success the new file node (the `ASC-artifact-scanning.md` TreeNode shape) is returned so the UI can open and reveal it, and the creation is observed by the watcher and reaches the UI through `"project tree changed"` (`ASC-artifact-scanning.md` ASC-FR-10). The operation errors with a typed "no project open" when no project is open.

26. **PST-FR-26** Every path this module operates on is explicitly resolved and verified to lie inside the active worktree root (PST-FR-21) **before** any `FSA-filesystem-access.md` primitive is invoked with it. This covers the project-relative inputs of `create_file`, `create_folder`, `delete_path`, `rename_path`, and `copy_path_into_folder` — both the source and the destination of the last — together with every path this module derives from an `id` for `load_artifact_contents_by_id` and `save_artifact_contents`. A path that resolves outside the root is refused with a typed "path escapes project root" error: no primitive is called, nothing on disk is read, written, or removed, and no partial effect of any kind survives the refusal. An absolute path, a path built from `..` segments, and a path any component of which is a symbolic link (PST-FR-27) each resolve outside the root for this purpose. Every refusal emits exactly one `ERROR` record through `LGC-logging.md`'s internal API under the `backend` domain, naming the operation and the offending path in its `fields`. The check is this module's own and runs whether or not the primitive it guards would have caught the same path: `FSA-filesystem-access.md` FSA-FR-10 stays in force underneath it as the backstop, and a path both would reject is refused here first and logged once rather than twice.
27. **PST-FR-27** No operation this module performs follows a symbolic link. A path whose final component or any ancestor component is a symbolic link is refused on the terms of PST-FR-26, and a `delete_path` or `copy_path_into_folder` whose subtree contains one anywhere is refused before anything is removed or written. The refusal holds twice over: it is this module's own, and it is also what the `FSA-filesystem-access.md` instance this module runs on does underneath, because the application builds every instance with symlink following left at its default of off, whichever profile it is (FSA-FR-21, FSA-FR-29, FSA-FR-17). A symbolic link is therefore never created, read, written, copied, renamed, or removed through this module, and never reaches it from the Project panel in the first place, because the scan surfaces no node for one (`ASC-artifact-scanning.md` ASC-FR-23). The refusal is decided from the link itself and never from where it points, so a link into the project root is refused exactly as one out of it is.
28. **PST-FR-28** `save_artifact_contents(id, body)` for an artifact whose resolved type is `flow` (`ASC-artifact-scanning.md` ASC-FR-02) submits `body` to `FGV-flow-graph-validation.md::validate_flow_document` (FGV-FR-02) before any write is attempted. A body the report calls valid is written on the ordinary terms of PST-FR-09; a body carrying violations is refused with a typed error carrying the report, and nothing is written — the file on disk keeps the bytes it had, no atomic-write primitive is invoked, no `"artifact changed externally"` follows, and the file's modification time is untouched, so the artifact's position in Recently edited is exactly what it was (PST-FR-31). The gate lives inside the write rather than beside it, so every caller passes through it: the Flow tab's own save (`../ui/FLO-flow.md` FLO-FR-27), Save All (`../ui/SNV-shell-navigation.md` SNV-FR-31), and the flushes that run on tab close, project close, worktree switch, and quit. No other artifact type is inspected: a Markdown artifact and a plain text file are written as the bytes they are.
29. **PST-FR-29** `create_typed_file(location, name, artifact_type)` is the **one typed-file creation operation** both routes into `../ui/NTA-new-typed-artifact.md` reach: the File menu and the Project context menu differ in the `location` they supply and in nothing else. It creates the empty file on exactly the terms `create_file` creates one (PST-FR-25) — the same complete-basename rule, the same rejection of an empty name, a name holding a path separator, and a destination escaping the active worktree root (PST-FR-26), the same typed collision error against any existing entry of that name — and it then records `artifact_type` as a **file-scope** assignment for the new path through the `ASC-artifact-scanning.md` attribution path (ASC-FR-05, scope = file, through `write_toml_atomic`), so the file resolves to that type at the highest precedence level of ASC-FR-06 with `type_source = "assigned"`. The two steps are **one transaction**: the operation returns success only when both have landed, and a failure of either leaves **neither** behind. A file write that fails records no assignment; an assignment write that fails after the file was written removes the file it just created before returning, so no partially-created file and no assignment naming a path that does not exist survives the call. The guarantee is this module's to provide rather than the caller's to repair — the UI is told the creation failed and shows the inputs it still holds (`../ui/NTA-new-typed-artifact.md` NTA-FR-16), and it is never asked to clean up after a half-completed creation. `artifact_type` is required: a call carrying none is a typed validation error and nothing is created, which is what separates this operation from `create_file` (PST-FR-25), whose files carry no assignment at all. The operation writes exactly one file and records exactly one assignment; it creates no draft, invokes nothing in `DRS-draft-storage.md`, writes nothing under `.synthesis/drafts/`, and reads no draft template (`PSS-project-settings-storage.md` PSS-FR-21). On success the new file node is returned and the creation is observed by the watcher like any other write, reaching the Project panel through `"project tree changed"` (`ASC-artifact-scanning.md` ASC-FR-10).

30. **PST-FR-30** Opening a project and closing one each **schedule the draft-asset housekeeping pass** of `DAS-draft-assets.md` (DAS-FR-19), and the application schedules one further pass over every draft of the active worktree once the active project has been loaded at start. A close-triggered pass is scheduled and run **before** the unmount of PST-FR-14 releases the project's storage context, so it addresses drafts that still resolve. The pass runs asynchronously and blocks neither the open nor the close: a project opens and closes at its ordinary speed whatever the pass is doing, a pass that fails leaves the open or the close untouched and is reported through `LGC-logging.md` alone, and a pass still running when the application quits is abandoned and reported as incomplete rather than as done (per `DAS-draft-assets.md` DAS-FR-15, DAS-FR-20, DAS-FR-21). Nothing else about a project's own tree is written, read, or removed by any of it.

31. **PST-FR-31** `list_recently_edited_artifacts` is served from the project's **current artifact records and the current state of its filesystem**, and from nothing else. It enumerates the files the scan surfaces (`ASC-artifact-scanning.md` ASC-FR-17), keeps those whose resolved artifact type makes them artifacts, and reads for each the **filesystem modification time of the artifact's primary source file** — the same file `save_artifact_contents` writes (PST-FR-09). It returns at most **five** `RecentlyEditedItem`s, ordered **descending by that modification time**, with the artifact's stable id **ascending** as the tie-breaker so two files carrying the same instant are ordered the same way on every call. Each item's `id`, `name`, and `kind` are read from the artifact's current record and from `open_artifact_by_id` (PST-FR-08) at the moment of the call, so a renamed or reclassified artifact is described as it now stands. Nothing else is an activity source: `.synthesis/artifacts/` metadata, `.synthesis/local.toml`, draft files, and this application's own account of what it has saved are read for nothing here, and a change to any of them moves no item. Drafts never appear, the scan skipping `.synthesis/drafts/` (`ASC-artifact-scanning.md` ASC-FR-09), and a file carrying no artifact type never appears either (PST-FR-23). An artifact whose primary source file is missing or cannot be statted is **omitted**, the loader continues over the remaining artifacts and returns them, and the omission is recorded through `LGC-logging.md` alone — one file the filesystem cannot describe never fails the widget.
32. **PST-FR-32** `list_active_drafts` reads the active worktree's drafts through `DRS-draft-storage.md::list_drafts` (DRS-FR-08), keeps those whose `status` is `active` — an `archived` and a `graduated` draft are both excluded — and returns at most **five** `ActiveDraftItem`s ordered **descending by `prompt_activity_at`**, the filesystem modification time of the draft's one prompt file (`DRS-draft-storage.md` DRS-FR-41), with the draft id **ascending** as the tie-breaker. The prompt file is the **only** activity source: a rewritten `draft.toml`, a status change, a rename, a move between drafts folders, and a write under the draft's `assets/`, `proposals/`, `history/`, or `conversation.jsonl` each leave the ordering exactly as it was. Each item's `name` and `status` come from the draft's **stored record** (`DRS-draft-storage.md` DRS-FR-03), so a draft renamed or archived through the application is described by what the application holds and no filesystem metadata ever decides a draft's display name or its lifecycle status. Every draft holds its one prompt from creation (`DRS-draft-storage.md` DRS-FR-06, DRS-FR-11), so the loader needs no fallback for a draft carrying no activity time; a draft the module reports as `inconsistent` (`DRS-draft-storage.md` DRS-FR-15) is omitted and the remaining drafts are still returned.
33. **PST-FR-33** `list_recent_agent_runs` reads the open project's graduation queue through `GRD-graduation.md::list_graduation_queue` (GRD-FR-LGDV) and returns at most **five** `AgentRunItem`s, ordered **descending by each run's `updated_at`** with the run id **ascending** as the tie-breaker. A run still in `queued` is returned like any other, so work waiting to start is as visible as work under way, and it carries `queue_position` — its index in **its own** queue — the work stream's queue, or the worktree's queue for a direct run (per `GRD-graduation.md` GRD-FR-VLFO and GRD-FR-ZVNO) — which is null for a run that has left `queued`. Each item also names the stream the run belongs to, by id and by name (GRD-FR-PZAK); for a direct run on an ordinary worktree the id is empty and the name is the pinned worktree's name (GRD-FR-BSNI). A position means nothing without the queue it is a position of. `state`, `stage`, and `stage_condition` are the run's persisted state and its `GraduationObservability` (GOB-FR-XMDU, GOB-FR-HXUZ); this module derives none of them and infers nothing about a run. `draft_name` is read from the run's source draft through `DRS-draft-storage.md::draft_record` (DRS-FR-38); a run whose draft no longer resolves is still returned, carrying its `draft_id` and no name.
34. **PST-FR-34** `list_pending_git_activity` composes `PendingGitActivity` from two reads and no others. `modified_artifacts` and `modified_source_files` are counted over the uncommitted change set of `CHC-changes.md::list_uncommitted_changes` (CHC-FR-03): an entry carrying an `artifact_type` (CHC-FR-10) counts as a modified artifact and an entry carrying none counts as a modified source file, so the two counts partition the change set and no path is counted twice or left out. `unpushed_commits` and `fetchable_commits` are the `ahead` and `behind` of `GTC-git.md::get_upstream_sync_state` (GTC-FR-21), resolved from local refs alone: this loader performs **no fetch** and reaches no network, so a refresh costs the same on a slow connection as on none, and both counts are **null** on a branch with no upstream, which the widget renders as unavailable rather than as zero (`../ui/DSH-dashboard.md` DSH-FR-14). A project whose content root is outside a Git repository returns all four counts null.
35. **PST-FR-35** The Dashboard refresh events follow the filesystem and the records, and each names one widget's loader. `"dashboard recently edited changed"` is emitted when the content-modification channel of `ASC-artifact-scanning.md` ASC-FR-15 reports a path that resolves to an artifact — the same input that drives `"artifact changed externally"` (PST-FR-16) — and when `"project tree changed"` (ASC-FR-10) reports a structural change, because both alter what PST-FR-31 enumerates or how it orders. It carries **no self-write suppression**: a write this module performed moves the file's modification time and must therefore move the widget, which is the whole point of ordering by that time. `"dashboard active drafts changed"` is emitted on `DRS-draft-storage.md`'s `"draft prompt changed"` (DRS-FR-42), which is what moves the ordering, and on its `"drafts changed"` (DRS-FR-22), which changes which drafts qualify and what their names and statuses are; a refresh caused by the second re-reads the same prompt-file times and therefore reorders nothing. `"dashboard agent activity changed"` and `"dashboard pending git changed"` are emitted by the timer of PST-FR-36 and by nothing else, so those two widgets move on the interval rather than on every commit and every run transition. Every event is emitted after the change it reports has landed, and carries no widget data: a consumer re-invokes the loader (per `../ui/DSH-dashboard.md` DSH-FR-15, DSH-FR-16).
36. **PST-FR-36** This module owns **one application-wide refresh timer** for the Last/current agent activity and Pending Git activity widgets. It starts when the application starts and runs for as long as the application runs, whether or not a project is open and whether or not a Dashboard tab exists anywhere. Its interval is **exactly 5 minutes**, and the cadence is fixed rather than derived from how long any refresh takes: a tick **dispatches** a refresh of **both** widgets for the **currently open project** and returns at once, awaiting neither, so the next tick falls due 5 minutes after the last whatever either refresh is still doing. **No tick is skipped, dropped, or silently coalesced away**: every tick dispatches both refreshes, and what a refresh already in flight causes is the pending-refresh handling of PST-FR-37 rather than a lost tick. The tick itself, the refreshes it dispatches, and the events they emit all run on this module's async runtime and never on a thread that serves the UI. A refresh that settles emits `"dashboard agent activity changed"` or `"dashboard pending git changed"` for its own widget; a tick that finds **no project open** dispatches nothing, emits nothing, and keeps the cadence, so the next tick is due 5 minutes later. Closing the Dashboard tab, closing a project, and changing the active worktree each leave the timer running, and a project opened afterwards is picked up by the next tick without the timer being restarted. The timer stops only when the application quits.
37. **PST-FR-37** The background refresh of PST-FR-36 is **non-blocking, overlap-safe, and answerable to the user**, on these four terms.
    - **One refresh per widget at a time, with the ticks behind it coalesced rather than lost.** Each widget holds at most one refresh in flight. A tick that finds one already in flight for a widget records a **pending refresh** for that widget instead of starting a second read of the same source, and the pending refresh starts the moment the in-flight one settles. Several ticks falling due during one long refresh coalesce into exactly **one** pending refresh, because each would read the same source and only the newest reading is of any use — the ticks are honoured, the redundant reads are not. The two widgets are independent throughout: a slow Pending Git read delays neither the agent-activity refresh dispatched by the same tick nor any refresh dispatched by a later one.
    - **Stale results are discarded rather than applied.** Every dispatched refresh carries a sequence number that ascends per widget, together with the project and active-worktree identity it was dispatched for. Its result is applied — and its event emitted — only when that sequence is the highest yet settled for that widget **and** that identity is still the open one. A result whose sequence has been overtaken, and a result belonging to a project or a worktree no longer open, are both **discarded**: no event is emitted, no error is reported, and the widget's data is left as it is. A slow refresh returning after a fresher one therefore never puts older data behind a newer reading, and a refresh in flight across a project switch or a worktree change never reports the outgoing root's data as the incoming one's.
    - **A failed refresh reaches the user, not only the log.** A refresh whose loader fails emits `"dashboard refresh failed"` carrying that widget and the typed error, on which the Dashboard renders that widget's own error state (per `../ui/DSH-dashboard.md` DSH-FR-18) while every other widget, tab, and panel is left exactly as it was. The failure is additionally recorded through `LGC-logging.md`. Nothing is stopped by it: the timer keeps its cadence, the other widget's refresh from the same tick settles on its own terms, the next tick refreshes the failed widget again, and that widget's next successful refresh emits its ordinary refresh event, which is what clears the error state. A discarded stale result (above) is not a failure and emits neither event.
    - **Nothing here occupies a UI thread.** No Dashboard loader, no tick, no dispatched or pending refresh, and no emission runs on a thread that serves the UI. A loader that is slow, a loader that fails, and a refresh that is still running each leave the Dashboard interactive, leave every other tab and panel interactive, and delay no other command this module serves — the Dashboard is refreshed **in the background** and is never waited for.
38. **PST-FR-QNAV** The draft statistics store is owned by `DSS-draft-statistics-storage.md`: it defines the per-draft `<draft-id>.jsonl` layout, the events those logs hold, the fold that produces the totals, and the deletion that takes a log with its draft. Those logs stand in the repository machine store (per `RMS-repository-machine-storage.md` RMS-FR-MVDU) rather than in the project, so this module scaffolds nothing for them, commits nothing of them, and reads no file of them. No loader here is served from them.
39. **PST-FR-XKVD** **Application-owned storage** is one committed folder this module scaffolds: `.synthesis/drafts/` (per `DRS-draft-storage.md` DRS-FR-04). The application writes it on its own account and at a cadence no person controls — a proposal and a history entry for each agent turn against a draft — so it stands modified in the author's checkout at moments the author did not choose and cannot prevent. An accepted change to a draft's prompt stays uncommitted until the next draft event of that draft or the author's own commit. It is named as a set here because several modules ask the same question of a repository path and must answer it identically: is this path the application's own record, or is it the author's work? A **clean-source gate reads past this set**, because it exists to protect the author's uncommitted work and a refusal naming a file the author cannot stop being written is a refusal they cannot clear (per `GSU-graduation-start.md` GRB-FR-QIHE, `GRB-graduation-rebase.md` GRB-FR-QIHE). Membership is the **defined draft layout** (per `DRS-draft-storage.md` DRS-FR-ZIVL): a transient file and a file the author put there themselves are not application-owned and are never committed by this module, though the gates read past the whole prefix. The set is deliberately narrow. `.synthesis/notes/` is **not** in it: a note is authored work, and its author decides when it is committed. The conversation logs and the statistics logs are not in it either, being outside every worktree and outside Git altogether (per `RMS-repository-machine-storage.md` RMS-FR-HDNZ). The gitignored paths — `.synthesis/cache/`, `.synthesis/proposals/`, and `local.toml` (PST-FR-02) — are outside every one of those gates already. This module defines the set and scaffolds the folder. It commits only the committed draft storage of `DRS-draft-storage.md` DRS-FR-ZIVL, at the draft events of PST-FR-DQZT. It reads no file in it, and it applies the set at no gate: a gate is the asking module's.
40. **PST-FR-DQZT** The application commits a draft's **committed draft storage** (per `DRS-draft-storage.md` DRS-FR-ZIVL) at three **draft events** and at no other time: the draft is created, the draft is deleted, and a graduation run of it is started (per `GSU-graduation-start.md` GSU-FR-RNOM). An accepted change to its prompt (per `DHS-draft-history.md` DHS-FR-14) and a stream checkout make no commit.
40. **PST-FR-TYNC** Each draft event is **one commit** through `GTC-git.md`'s `commit_paths` contract (GTC-FR-19) against the active worktree. It names the paths of `DRS-draft-storage.md` DRS-FR-VECL and no other path, so a path the author staged stays staged and uncommitted. The authoring identity is the repository's configured one (per `GTC-git.md` GTC-FR-03).
40. **PST-FR-YWXF** The commit message names the event and the draft's current name, and nothing else: `draft: create "<name>"`, `draft: delete "<name>"`, or `draft: graduate "<name>"`.
40. **PST-FR-BIPA** Draft events are committed **one at a time, in the order they occur**, on this module's own background thread. Two events never share one commit, and no event waits for a quiet interval before it is committed.
41. **PST-FR-KGRW** The commit of every draft event is **best-effort and answerable to nobody**: it runs on this module's own background thread, no command waits for it, no operation fails with it, and no run, author action, or agent turn is delayed, refused, or reported differently because one did not happen. It is **not attempted at all** where committing would be wrong rather than merely unnecessary, and each of those is a **silent no-op** rather than an error, because none is a fault and the next draft event or the author's own commit carries the paths: a content root in no Git repository, which is every project outside Git; a **bare** repository; a repository holding a merge, a rebase, a cherry-pick, or a bisect in progress, a commit into which would land inside an operation the author is in the middle of; a repository with **no commit yet**, where this commit would otherwise become a project's first and would create its branch; a repository with no configured authoring identity; an index another process holds, which is the author running their own Git command or this application publishing a change set; and an event whose paths hold nothing that differs from `HEAD`. A **detached `HEAD` is committed to** rather than skipped, the commit moving that `HEAD` alone and no branch: every operation that leaves a detached head as an intermediate state is already excluded above, so what remains is a checkout an author may sit in for days, and refusing there would leave every draft event of that checkout uncommitted. A commit that **was** attempted and failed is recorded at `WARN` through `LGC-logging.md` and dropped, the files it would have carried staying on disk for the next draft event; a reason equal to the last one reported for that root is not recorded again, so a repository with no authoring identity does not write one record per event for a whole session. Nothing here retries in a loop. Every record carries a count and a reason and carries **no path, no draft identity, and no file content**.
42. **PST-FR-CDYM** Opening a project runs `FSA-filesystem-access.md::ensure_gitignored` against the active worktree's `.synthesis/` folder (FSA-FR-08), which removes an existing project's `drafts/` ignore entry (per `DRS-draft-storage.md` DRS-FR-ISPI). `ensure_gitignored` writes `<synthesis_dir>/.gitignore` and no other file, and removing that entry reads, deletes, moves, rewrites, stages, and commits no draft file. The housekeeping pass PST-FR-30 schedules is untouched here.
43. **PST-FR-MHZB** Opening a project and changing the active worktree each **schedule one import pass** of `RMS-repository-machine-storage.md` (RMS-FR-JVEC) for the worktree that becomes active. The pass runs in the background and blocks neither operation, and it removes, stages, and commits no path of the project (RMS-FR-XRPT).

## Non-functional requirements
- The committed per-artifact and per-project records under `.synthesis/` are plain-text TOML and individually diffable. One file per artifact keeps metadata changes from creating merge conflicts across unrelated artifacts.
- The committed append-only logs under `.synthesis/` are JSONL, individually diffable, and union-merged, one JSON object per line (`DRS-draft-storage.md` DRS-FR-DGMI).
- The committed binary content under `.synthesis/` — a draft's image assets (`DAS-draft-assets.md` DAS-FR-01) — is committed as ordinary Git-managed binary files, and the Markdown prompts, `.content` candidates, and `.snapshot` payloads a draft holds are committed as the ordinary text files they are.
- Version history for artifacts is not duplicated in this module; it is read dynamically from Git through `HIS-history.md`. A local SQLite cache under `.synthesis/cache/` is permitted but must always be rebuildable from Git.
- Semantic version labels are stored in `.synthesis/labels.toml` rather than as Git tags, so they do not collide with code release tags in a co-located repository.
- The project tree must render incrementally; large subtrees should not block the Project panel (per `../ui/LIB-library.md` Non-functional requirements).
- The walking-skeleton implementation may keep tree and artifact data entirely in memory. Dashboard data is not among it: every Dashboard loader but `list_project_health_signals` reads the project's real records and its real filesystem (PST-FR-12).
- A Dashboard loader costs one pass over material the module already holds. `list_recently_edited_artifacts` stats one file per artifact, so its cost grows with the number of artifacts rather than with their size, and it reads no file's contents. The timer of PST-FR-36 runs two loaders every 5 minutes and no others, so the cadence costs one queue read and one working-tree read per tick.
- `save_artifact_contents` is invoked at **editing cadence** rather than at the cadence of a user deciding to save: an Editor tab writes an artifact a short rest after the last keystroke (per `../ui/EDT-editor.md` EDT-FR-70) and a Flow tab writes a graph a short rest after the last change (per `../ui/FLO-flow.md` FLO-FR-27), so one authoring session produces many writes of the same file. Every step the write performs — the atomic write itself (PST-FR-10), the checksum over the written bytes (PST-FR-15), the external-change comparison (PST-FR-16), and the Flow validation that precedes a `flow` write (PST-FR-28) — is sized for that rate and must not make an author's typing wait on it.
