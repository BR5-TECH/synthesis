# Agent vendor images

**Spec code:** `AVI`

## Intent
The two container images Synthesis ships as its reference environment for an agentic CLI, the contract every image an agent runs in must satisfy, and the manifest that pins the shipped pair. An agent driven on the author's behalf needs a working tree, a network route to its vendor's service, and nothing else the host machine happens to have; giving it one of these images instead of the host's own installation is what makes a turn reproducible from the build rather than dependent on which version of which CLI a developer last upgraded. Each image is minimal and single-purpose — one vendor CLI at an exact version, the handful of packages repository work actually needs, the language toolchains that work is written in so a change can be built rather than only described, one headless browser so work on an interface can be seen rather than guessed at, a non-root user, and that CLI as the entrypoint — and each is identified by an immutable digest rather than by a tag that can move under it. What an executor actually launches is the image a project commits for its vendor (`../core/PSS-project-settings-storage.md` PSS-FR-22), and this spec is what that image is measured against: the contract of AVI-FR-19 holds for a shipped image and a project-configured one alike. Out of scope: launching a container, mounting anything into one, or presenting a credential to one, all of which are `../tools/EAC-execute-agent-cli.md`'s; resolving which vendor a project uses, which is `../core/AIC-agentic-integrations.md`'s; and standing in for a vendor CLI during a test, which `ACM-agentic-cli-mock.md` does through the executor's runtime seam rather than through any image defined here.

## Contract surface
This spec owns the image definitions, the packages inside them, the pinned vendor CLI, toolchain, and browser versions, the digest manifest, the commands that build and publish them, and the vendor image contract of AVI-FR-19. It exposes no operation, registers nothing, and is not reachable from any running code path — its whole product is the manifest and the images that manifest names.

### The image definitions
```text
docker/agent-images/claude-code/Dockerfile
docker/agent-images/codex/Dockerfile
docker/agent-images/README.md
docker/agent-images/manifest.toml
```

### The manifest
The single application-owned record of which shipped image is which. It describes the pair this repository builds and publishes and it is read at no launch:

```toml
[claude_code]
image_ref    = "…/synthesis-agent-claude-code:<version>"
image_digest = "sha256:…"
cli_version  = "…"
uid          = 10001
gid          = 10001

[codex]
image_ref    = "…/synthesis-agent-codex:<version>"
image_digest = "sha256:…"
cli_version  = "…"
uid          = 10001
gid          = 10001
```

### The commands
- **Build** — `docker build --file docker/agent-images/<vendor>/Dockerfile --tag <image_ref> docker/agent-images/<vendor>`.
- **Publish** — `docker push <image_ref>`, followed by recording the resulting digest in the manifest.
- **Verify** — a check that each manifest digest resolves to an image whose installed CLI reports the manifest's `cli_version`, whose package floor is the one AVI-FR-02 states, whose toolchains build a program under the launch conditions the executor imposes, and whose browser starts and renders a page under those same conditions.

## Functional requirements
1. **AVI-FR-01** Two images are defined, one per vendor the executor can run — `claude_code` and `codex` — each from its own Dockerfile under `docker/agent-images/`. No image serves both vendors and no vendor has more than one, so an upgrade to one CLI cannot disturb the other.
2. **AVI-FR-02** An image installs its vendor CLI, the packages its work needs — CA certificates, curl, Python with `pip` and `venv`, and the C compiler, linker, and C library headers of `build-essential` — the toolchain floor AVI-FR-17 states, the browser floor AVI-FR-16 states, and nothing else. Python is part of the floor because repository work asks for it directly: a script to run, a test suite to start, a tool that is written in it. `pip` and `venv` accompany the interpreter so an agent can install what a task needs into an environment of its own, which is the answer to Debian's externally-managed system environment rather than a flag that overrides it. No Dockerfile names a Python version: the interpreter is the one the pinned base of AVI-FR-05 carries, so a rebuild reproduces it for the same reason it reproduces everything else in that layer. `build-essential` is the Rust toolchain's floor: `rustc` compiles to object code and then calls a C linker to make a program out of it, so a Rust compiler without a linker cannot produce a binary at all. `pkg-config` and the development packages for OpenSSL and WebKitGTK are the native floor beneath the same toolchain: a Rust crate that binds a system library does not carry that library, its `-sys` build script asks `pkg-config` where the headers are, and a missing answer stops the build inside a transitive dependency before any code in the repository itself is read. The work is a desktop shell, so the GTK and WebKit bindings under `tauri` and the OpenSSL bindings under its Git support are what an image must answer for. The development packages themselves, never a stub `.pc` file that satisfies `pkg-config` and then measures the code against libraries the image does not hold, which is a pass that means nothing. The browser's floor is the shared libraries its build links against and one font family, named package by package rather than installed by the browser tool's own `install-deps` command: that command brings a display server and the fonts of every writing system with it, which an image that runs one headless browser and has no display at all does not need. An image also carries **Git**, on the same terms as the rest of this floor and from the same package archive. A turn that revises or judges a change set has to know what changed in it, and the only alternative to asking Git is reading every file of the working copy whole — which costs more than the judgement itself and grows with the size of the project rather than with the size of the change. What the client in this image can actually reach is decided by the invocation and never by the image: the application makes a run's repository metadata reachable read-only for the turns entitled to it, and masks it for the turn that is not (`../tools/EAC-execute-agent-cli.md` EAC-FR-41). An image that carries the binary therefore grants nothing on its own, which is what keeps that decision in one place. Beyond every floor above, an image carries no editor, no second agentic CLI, and no Synthesis code.
3. **AVI-FR-03** An image declares a non-root user with the fixed UID and GID its manifest entry records, and that user is the one the entrypoint runs as. Nothing in the image is owned by root in a way that would stop that user from working in a mounted directory.
4. **AVI-FR-04** An image's entrypoint is its vendor CLI, so the arguments the executor generates are the CLI's own arguments and nothing wraps or rewrites them.
5. **AVI-FR-05** Each Dockerfile's base image is pinned by digest rather than by a tag, so rebuilding at a later date reproduces the same foundation rather than whatever the tag has since come to mean.
6. **AVI-FR-06** A vendor CLI is installed at an exact version named in the Dockerfile, never from a floating tag such as `latest` and never from a host-installed binary copied in. The version installed is the `cli_version` its manifest entry records.
7. **AVI-FR-07** `docker/agent-images/manifest.toml` is the single record of each **shipped** image's reference, digest, CLI version, UID, and GID, and the publish and verify commands are what read it. The manifest is application data — it is not author-editable through any surface, is not read from a project, and is not overridable by an environment variable. Nothing writes into it at run time: a project's own image build (`../core/PSS-project-settings-storage.md` PSS-FR-26) records neither a reference nor a digest here, so the manifest describes the shipped pair and nothing else.
8. **AVI-FR-08** A shipped image's identity is its digest. A reference's tag names the CLI version it holds followed by a build revision, because an image's package floor, toolchains, and browser can all change while its vendor CLI does not, and publishing a changed image over an unchanged tag is the substitution this requirement exists to prevent: the revision rises with any change to a Dockerfile, in the same change that records the new digest. The manifest carries a reference and a digest together, and `verify` resolves by the digest — addressing the repository without its tag — so an image republished under the same tag is not silently adopted. An image that has been defined but not yet published carries an all-zero digest sentinel rather than a blank, which `verify` fails on by design; a published digest replaces it in the same change that published the image.
9. **AVI-FR-09** Building a **shipped** image is a documented command a developer or a release step runs deliberately; nothing in the application builds, updates, or republishes one, and no surface offers to. A project's own Docker image is a different thing entirely: the author builds it from Project settings on the terms `../core/PSS-project-settings-storage.md` PSS-FR-26 sets, from that project's own Dockerfile and into that project's own image reference, and that build reads no definition here, writes no file under `docker/agent-images/`, and publishes nothing. An execution may ask Docker to pull the **project-configured** reference it is about to run (`../tools/EAC-execute-agent-cli.md` EAC-FR-38); no pull of a shipped image is performed anywhere. The repository's task runner offers that build for both images at once as `task docker` (per `TSK-taskfile.md` TSK-FR-13), which is the same deliberate step under one name rather than an exception to it: it tags what it builds locally, publishes nothing, and leaves the manifest untouched (per `TSK-taskfile.md` TSK-FR-17, TSK-FR-20). Publishing is a separate deliberate step, and the manifest is updated only after the digest it records exists in the published registry.
10. **AVI-FR-10** No image contains a credential of any kind — no OAuth token, no gateway token, no API key, no vendor login directory, and no keychain material — in any layer, environment variable, or file. Every credential reaches a container at run time by the mechanisms `../tools/EAC-execute-agent-cli.md` defines (EAC-FR-15, EAC-FR-16) and never by being built in.
11. **AVI-FR-11** An image declares `/workspace` as its working directory, declares no `VOLUME`, and exposes no port, so what a container can reach is decided entirely by the invocation rather than partly by the image. The declared working directory is a default that nothing depends on: every launch names the directory the turn stands in for itself (per `../tools/EAC-execute-agent-cli.md` EAC-FR-ZKMR), and an image is therefore launched unchanged whichever path that is.
12. **AVI-FR-12** No image variant exists for testing. `ACM-agentic-cli-mock.md` stands in for the container runtime through the executor's `DockerRuntime` seam (per `../tools/EAC-execute-agent-cli.md` EAC-FR-17), so a test never builds, pulls, or runs an image defined here and production image resolution is identical under test and in a shipped build.
13. **AVI-FR-13** The verify command resolves each manifest digest and confirms the image at that digest reports the manifest's `cli_version`, runs as the manifest's UID and GID, answers for the native floor of AVI-FR-02, carries the Python floor of AVI-FR-02 — an interpreter the agent user can build a virtual environment with and install into — gives the launching user the home of AVI-FR-18, carries the toolchains of AVI-FR-17 — proved by compiling, linking, running, and linting a crate, by emitting JavaScript from a TypeScript source and running it, and by an install that writes pnpm's store, rather than by reading a version string — reports from each of those toolchains the version its Dockerfile pins, and carries a browser that starts and renders a page. Everything after the Python floor runs under the launch conditions of `../tools/EAC-execute-agent-cli.md` EAC-FR-13 and EAC-FR-14: every capability dropped, no new privileges, and a UID the image has no account for — an unallocated one, because a UID the base image happens to name is handed a home by the system and never meets the case EAC-FR-14 creates. A version string proves that a binary is on the path; it does not prove that a linker exists, or that the directories a build writes to belong to the user a launch supplies, which is why the check builds something and why nothing in it writes only to a world-writable temporary directory. The version comparison is against the Dockerfile rather than the manifest because a build argument's default can be overridden at build time, so an image can carry a toolchain its own definition does not name. A manifest that has drifted from what was published fails a check rather than failing a launch.
14. **AVI-FR-14** `docker/agent-images/README.md` documents the two image definitions, the pinned base images and CLI versions, the toolchains of AVI-FR-17 with the version argument that pins each one and the rule for upgrading them, the home directory the image names and why it names it, the browser and how a task reaches it, the build, publish, and verify commands, the manifest's fields and who reads them, the non-root user contract, and the rule that no credential is ever built in. Its build section covers both the direct `docker build` command per image and the `task docker` build of both at once, and it states the local image name and tag that build applies, that it publishes nothing, and that it does not touch the manifest.
15. **AVI-FR-15** These images are built and published outside the pull-request pipeline. `CIP-ci-pipeline.md` gains no lane for them, reads no registry secret, and its existing lanes are unaffected, because the executor's tests reach the runtime through the seam of AVI-FR-12 rather than through a container.
16. **AVI-FR-16** An image carries one browser — Chromium, headless — and the Playwright runtime that drives it, so an agent asked to change an interface can open the result and look at it instead of reporting a diff. Both are pinned to an exact version in the Dockerfile, for the reason AVI-FR-06 pins a vendor CLI: the browser build belongs to the runtime version that installed it, so a rebuild of an unchanged definition produces the same browser. Both images pin the same version, because AVI's non-functional requirement that the two share one package floor covers the browser as well. Only Chromium is installed; a second engine is another several hundred megabytes for a capability no check of a view needs. The browser is installed to a fixed path that the image names in one environment variable, `PLAYWRIGHT_BROWSERS_PATH`, and every user can read and run: the layer that installs it runs as root, and the executor launches a container as the host user's UID (`../tools/EAC-execute-agent-cli.md` EAC-FR-14), so a browser left in the installing user's own cache would be unreachable by the process that needs it. That path is not writable by the launching user — the browser is part of the image, at the version the image pins — so a task that needs a different build points the variable at a directory of its own under the directory the turn stands in. Its value, like that of every other environment variable an image sets, is a container path this spec chose; AVI-FR-10 is unaffected, because a path is not a credential.
17. **AVI-FR-17** An image carries the language toolchains the work is written in: the Rust toolchain — `rustc`, `cargo`, `rustfmt`, and `clippy` — and, on the Node side the base image already provides, the `pnpm` package manager and the TypeScript compiler. An agent asked to change a crate or a module has to build what it changed and read what the build says about it; without a compiler it can only describe an edit, which is the same gap AVI-FR-16 closes for an interface. Each is pinned to an exact version named in the Dockerfile, for the reason AVI-FR-06 pins a vendor CLI, and both images pin the same versions, because the non-functional requirement that the two share one package floor covers the toolchains as well. The Rust installer is the one part of an image that arrives over the network without a digest of its own: it is fetched by version from the release archive and checked against a SHA-256 the Dockerfile records for each architecture it supports, and an architecture the file has no checksum for stops the build rather than falling back to an unverified download. The Rust toolchain is installed outside any home directory, at paths the image names in `RUSTUP_HOME` and `CARGO_HOME`, for the reason AVI-FR-16 keeps the browser outside one. Unlike the browser path, the *directories* under both are writable by every user, because Cargo writes its registry index and its package cache into `CARGO_HOME` on every build and rustup writes a toolchain there when a repository asks for a version the image does not carry — a read-only toolchain directory would report its version and then fail on the first build. Directories only: everything those two write is a new file or a new directory, which needs its parent writable and nothing else, so making the installed files writable as well would add nothing but a compiler an agent can overwrite.
18. **AVI-FR-18** An image sets `HOME` itself rather than leaving it to the container runtime. A runtime derives a home from the passwd entry of the user it starts, and the host UID the executor supplies (`../tools/EAC-execute-agent-cli.md` EAC-FR-14) has no entry in an image — so `$HOME` would be `/`, which nothing may write. The vendor CLI's own scratch state, npm's cache, and pnpm's package store all land under `$HOME`, and each fails on a home it cannot write. The named home is therefore writable by whatever UID a launch supplies; a container belongs to one agent alone, so a home every user can write crosses no boundary the launch has not already decided. The image also names pnpm's own directory in `PNPM_HOME` and puts its `bin` directory on `PATH` beside Cargo's, because pnpm refuses a global install when that directory is not on the path. Every environment variable an image sets holds a container path this spec chose, so AVI-FR-10 is unaffected.
19. **AVI-FR-19** The **vendor image contract** is what an image must satisfy to be launched by `../tools/EAC-execute-agent-cli.md`, and it holds for whichever image a project configures exactly as it holds for the shipped pair. That contract is: the vendor CLI as the entrypoint (AVI-FR-04), so the executor's generated arguments are the CLI's own; the stdin and structured-output protocol of that vendor's specification, `CCP-claude-code-cli-protocol.md` for Claude Code and `CDX-codex-cli-protocol.md` for Codex; `/workspace` as the working directory with no `VOLUME` and no exposed port (AVI-FR-11); a non-root user the launch can map to the host user's UID and GID (AVI-FR-03, `../tools/EAC-execute-agent-cli.md` EAC-FR-14); a writable `HOME` the image names itself (AVI-FR-18); no credential built into any layer, environment variable, or file (AVI-FR-10), every credential arriving at run time by the mechanisms the executor defines; the filesystem mounts the executor makes and no other (`../tools/EAC-execute-agent-cli.md` EAC-FR-13); and network access to the vendor's own service. The shipped images are this contract's reference implementation, and an image that does not meet it fails at the point the executor or the vendor CLI needs what is missing rather than being checked here — this spec defines the contract and the images it ships, and validates no image a project configures.

## Non-functional requirements
- An image is as small as its vendor CLI, AVI-FR-02's packages, AVI-FR-17's toolchains, and AVI-FR-16's browser allow; nothing is installed for convenience. Python is on that list because work needs it, not because it is handy to have; the Rust toolchain is installed at its minimal profile with only the two components the work uses; and the browser is one engine rather than the three the tool that installs it offers.
- A rebuild from an unchanged Dockerfile and an unchanged pinned base produces an image whose installed CLI version is identical, so the manifest's `cli_version` is a fact about the definition rather than about when it was built.
- Both images share the same UID, GID, working directory, entrypoint contract, package floor, toolchain versions, home directory, and browser version, so the executor's invocation differs between them only in the vendor arguments themselves.
- Nothing in the repository outside `docker/agent-images/` names a shipped image reference, a shipped digest, or a shipped CLI version, so an upgrade touches the Dockerfile and the manifest and nothing else.
- Upgrading a toolchain, like upgrading the browser, is a change to both Dockerfiles in one step, because a tool that differs between the two images makes a check depend on which vendor a project happens to use.
- Upgrading a vendor CLI is a deliberate change to a pinned version, and a turn run before that change and a turn run after it are distinguishable by the digest each ran under.
