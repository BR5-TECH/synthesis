# CI pipeline

**Spec code:** `CIP`

## Intent
The repository's two GitHub Actions workflows: the pipeline that verifies every pull request before it can merge, and the workflow that publishes the server image when a release is published. The verification pipeline runs the repository's suites — the frontend suite over `src/**`, the application's Rust suite over `src-tauri/**`, the mock's Rust suite over `tools/agentic-cli-mock/**`, and the service's Rust suite over `server/**` — as independent, concurrent lanes, and exposes a single aggregate check that passes only when every lane passes. It exists so that the definition-of-done in `CLAUDE.md` is enforced mechanically rather than by convention: a contributor cannot merge a change that breaks a part of the repository they were not working in. The lane set is deliberately open — new verification lanes are added as additional jobs without touching branch-protection configuration. The publishing workflow is kept apart from it because the two have opposite postures: verification runs on untrusted pull-request content with a read-only token and no secret, while publishing runs only after a maintainer publishes a release, holds the one write-scoped token in the repository, and produces the only artifact either workflow produces (`../server/BMS-backend-microservice.md` BMS-FR-21). Out of scope: building or bundling the native application, deploying anything, running verification on pushes outside pull requests, any verification check that requires a repository secret, publishing anything other than the server image, and publishing that image from anything other than a published release.

## Contract surface
The contract is the set of check names reported to GitHub, the commands each lane runs, and the trigger and permissions of each workflow. Branch protection consumes the check names; contributors consume the commands.

### The verification workflow
- **Workflow** — `.github/workflows/ci.yml`, named `CI`. The only workflow that reports a check on a pull request.
- **`CI / ui`** — the frontend build lane. Runs `pnpm build` and `pnpm exec tsc -p tsconfig.test.json --noEmit`.
- **`CI / ui-tests (editor and documents)`**, **`CI / ui-tests (components)`**, **`CI / ui-tests (app and state)`** — the frontend test lane, one check for each area. The job of an area runs `pnpm exec vitest run --project "<area>"`.
- **`CI / backend`** — the application's Rust lane. Runs `cargo check` and `cargo test`, both from `src-tauri/`.
- **`CI / mock`** — the agentic CLI mock's Rust lane. Runs `cargo check` and `cargo test`, both from `tools/agentic-cli-mock/`.
- **`CI / specs`** — the specification lane. Runs `python3 tools/spec-check/spec_check.py` from the repository root.
- **`CI / server`** — the backend microservice's Rust lane. Runs `cargo build --locked` and `cargo test --locked`, both from `server/`.
- **`CI / gate`** — the aggregate gate. Runs no verification of its own; its sole output is success when every lane succeeded and failure otherwise. This is the single check branch protection marks required.

The check names are stable identifiers. The `ui` lane commands and the `backend` lane commands are byte-identical to the definition-of-done commands in `CLAUDE.md`. The three `ui-tests` areas together run every test file that `pnpm test` runs, and each file in exactly one area. The `mock` lane's commands are the commands `ACM-agentic-cli-mock.md` documents for its crate, and the `server` lane's are the commands `../server/BMS-backend-microservice.md` documents for its crate, so a green local run predicts a green pipeline run.

### The publishing workflow
- **Workflow** — `.github/workflows/server-image.yml`, named `Server image`. It reports no pull-request check and is required by no branch-protection rule.
- **Trigger** — the `release` event with `types: [published]`, and no other trigger.
- **`Server image / publish`** — the only job. It builds `server/Dockerfile` for `linux/amd64` and `linux/arm64` and pushes one manifest list to GitHub Container Registry.

```text
Registry     ghcr.io
Image name   ghcr.io/<owner>/<repository>   (the GitHub repository name, in lower case)
Tag          ${{ github.event.release.tag_name }}, and no other tag
Credential   the run's GITHUB_TOKEN, with `packages: write` on that job alone
Build arg    SYNTHESIS_BUILD_VERSION = the release tag
```

## Functional requirements
1. **CIP-FR-01** The verification pipeline is defined in a single workflow file at `.github/workflows/ci.yml` whose `name` is `CI`. It is the repository's only pull-request verification workflow, and the publication of the server image is a separate workflow (CIP-FR-24) that reports no pull-request check.
2. **CIP-FR-02** The workflow triggers on `pull_request` with the default activity types (`opened`, `synchronize`, `reopened`), for pull requests targeting any base branch. It declares no `paths` or `paths-ignore` filter, so every lane reports a result on every pull request regardless of which files changed. It declares no `push` trigger.
3. **CIP-FR-03** The workflow declares a concurrency group keyed on the workflow and the pull request's ref, with `cancel-in-progress` enabled, so a new commit on a pull request cancels the run still in flight for that same pull request and never cancels a run for a different pull request.
4. **CIP-FR-04** The workflow declares workflow-level `permissions` granting `contents: read` and nothing else. No job in it raises that grant, and none of them holds `packages: write`, so the verification workflow cannot write a package however a lane is later changed.
5. **CIP-FR-05** The `ui`, `ui-tests`, `backend`, `mock`, `server`, and `specs` lanes are six separate jobs. None declares another in `needs`, so all six start when the run begins. No matrix holds two lanes, so a failure in one lane never cancels or suppresses the result of another.
6. **CIP-FR-06** The `ui` lane and each `ui-tests` job check out the repository, provision pnpm at the major version the project targets (11) and Node.js at the major version the project targets (26), then install dependencies with `pnpm install --frozen-lockfile`. A `pnpm-lock.yaml` that disagrees with `package.json` fails the job.
7. **CIP-FR-07** After a successful install, the `ui` lane runs `pnpm build` and then `pnpm exec tsc -p tsconfig.test.json --noEmit` as two ordered steps. A step that exits non-zero fails the lane immediately, and the step after it does not run.
8. **CIP-FR-08** The `ui` lane and each `ui-tests` job restore and save a cache of the pnpm content-addressable store keyed on `pnpm-lock.yaml`. A cache miss slows the job but never changes its result.
9. **CIP-FR-09** The `backend` lane runs on `ubuntu-latest` and, before any Rust compilation, installs the system packages the Tauri crate links against on Linux: `libwebkit2gtk-4.1-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`, `libxdo-dev`, `libssl-dev`, `build-essential`, `curl`, `wget`, and `file`.
10. **CIP-FR-10** Every Rust lane's toolchain is resolved from `src-tauri/rust-toolchain.toml`, which is the repository's single Rust pin and governs the `mock` and `server` lanes as well as the `backend` lane even though those two crates live outside that directory. The workflow does not name a Rust version, channel, or component list of its own, so changing the pinned toolchain in that file changes what CI uses across every Rust lane with no workflow edit. Because rustup searches only a lane's working directory and its parents for that file, a lane whose working directory lies outside `src-tauri/` copies the pin into its working directory before invoking rustup or cargo; the copy is made on the runner and is never committed, so the pinned file remains the only Rust pin in the repository and cannot be shadowed by a second one free to drift from it. Each Rust lane then installs the resolved toolchain unconditionally rather than relying on rustup's auto-install behaviour, so a toolchain that fails to install fails the step that installs it rather than the first step that compiles.
11. **CIP-FR-11** The `backend` lane configures no global Git identity on the runner. The Rust suite's fixtures set repository-local `user.name` and `user.email` on every repository they build, so commit authorship resolves without consulting ambient configuration; running the suite on a runner that has none is what holds that independence in place.
12. **CIP-FR-12** The `backend` lane runs `cargo check` and then `cargo test` with `src-tauri/` as the working directory. Either command exiting non-zero fails the lane immediately.
13. **CIP-FR-13** The `backend` lane restores and saves a cache of the Cargo registry and the `src-tauri/target` build directory keyed on `src-tauri/Cargo.lock` and on `src-tauri/rust-toolchain.toml`, so bumping the pinned toolchain cannot restore artifacts built by the previous compiler. A cache miss slows the lane but never changes its result.
14. **CIP-FR-14** The `gate` job declares every lane in `needs` and runs unconditionally with respect to their outcomes, so it still executes when a lane fails rather than being skipped. It succeeds only when every job it depends on reported `success`; a dependency that reported `failure`, `cancelled`, or `skipped` fails the gate.
15. **CIP-FR-15** The job ids are `ui`, `ui-tests`, `backend`, `mock`, `server`, `specs`, and `gate`, and no job overrides its display name. GitHub reports exactly `CI / ui`, one `CI / ui-tests (<area>)` for each area of CIP-FR-VRPM, `CI / backend`, `CI / mock`, `CI / server`, `CI / specs`, and `CI / gate`. Branch protection requires only `CI / gate`.
16. **CIP-FR-16** Adding a verification lane requires exactly two edits to `.github/workflows/ci.yml`: defining the new job, and adding its job id to the `gate` job's `needs` list. No other file changes and no branch-protection change is needed for the new lane to become blocking. A Rust lane that copies the pin per CIP-FR-10 may additionally ignore the copied file in the directory it builds; that entry keeps a developer who reproduces the lane locally from committing a second pin, and is not required for the lane to run or to block.
17. **CIP-FR-17** Every job in either workflow declares an explicit `timeout-minutes`, so a hung step terminates and fails its job instead of running to the platform default.
18. **CIP-FR-18** No job of the verification workflow reads a repository secret, logs in to a registry, or requires a write-scoped token, so a pull request opened from a fork runs the identical set of lanes and produces the identical set of check results as a pull request opened from a branch in the repository.
19. **CIP-FR-19** The `mock` lane runs `cargo check` and then `cargo test` with `tools/agentic-cli-mock/` as the working directory, and installs none of the system packages CIP-FR-09 lists, because that crate links against nothing outside the Rust toolchain (per `ACM-agentic-cli-mock.md` ACM-FR-01). Either command exiting non-zero fails the lane immediately.
20. **CIP-FR-20** The `mock` lane restores and saves a cache of the Cargo registry and the `tools/agentic-cli-mock/target` build directory keyed on `tools/agentic-cli-mock/Cargo.lock`, which is that crate's own lock file rather than the application's, and on `src-tauri/rust-toolchain.toml` per CIP-FR-13. A cache miss slows the lane but never changes its result.
21. **CIP-FR-21** The `server` lane runs `cargo build --locked` and then `cargo test --locked` with `server/` as the working directory, and installs none of the system packages CIP-FR-09 lists, because that crate links against nothing outside the Rust toolchain (per `../server/BMS-backend-microservice.md` BMS-FR-02). Either command exiting non-zero fails the lane immediately. It resolves its toolchain from the repository's single pin on the terms CIP-FR-10 states, copying that pin into `server/` because the directory lies outside `src-tauri/`.
22. **CIP-FR-22** The `server` lane restores and saves a cache of the Cargo registry and the `server/target` build directory keyed on `server/Cargo.lock`, which is that crate's own lock file rather than the application's, and on `src-tauri/rust-toolchain.toml` per CIP-FR-13. A cache miss slows the lane but never changes its result.
23. **CIP-FR-23** The `server` lane is listed in the `gate` job's `needs`, so it blocks a merge through `CI / gate` and through no check of its own, and branch protection is unchanged by its addition. The verification workflow builds no container image, pushes none, logs in to no registry, and holds no registry credential in any job, so the whole of the server image's build and publication is the publishing workflow's (CIP-FR-24).
24. **CIP-FR-24** The server image is published by a separate workflow file at `.github/workflows/server-image.yml` whose `name` is `Server image` and whose single job is identified as `publish`. The workflow triggers on the `release` event with `types: [published]` and declares no other trigger, so no pull request, no branch push, and no manual dispatch can publish an image.
25. **CIP-FR-25** Because the trigger is the publication of a release rather than the creation of a tag, the workflow runs for a stable release and for a pre-release alike, and does not run for a draft release. A draft that is published later fires the event at the moment it is published and is built then.
26. **CIP-FR-26** The publishing workflow declares workflow-level `permissions` granting `contents: read`, and the `publish` job alone adds `packages: write`. It authenticates to the registry with the run's `GITHUB_TOKEN` and with nothing else: no personal access token, no registry password, and no other long-lived credential is stored in the repository, read by the workflow, or written into the image (per `../server/BMS-backend-microservice.md` BMS-FR-20).
27. **CIP-FR-27** The `publish` job builds `server/Dockerfile` for `linux/amd64` and `linux/arm64` and pushes the result as one manifest list to GitHub Container Registry under `ghcr.io/<owner>/<repository>`, where owner and repository are the running repository's own name folded to lower case, because a registry reference may not carry an upper-case character.
28. **CIP-FR-28** The only tag pushed is the tag of the release that triggered the run. The job pushes no `latest` tag, no commit-hash tag, no branch tag, and no second tag of any kind. A tag is not required to be immutable: a later publication at the same tag replaces the image the tag resolves to wherever the registry permits it.
29. **CIP-FR-29** The job passes the release tag into the image build as the build argument `../server/BMS-backend-microservice.md` BMS-FR-14 names, so the version the published image reports from `GET /v1/health` is the tag of the release it was built from.
30. **CIP-FR-30** A failure of any step of the `publish` job — the registry login, the image build for either platform, or the push — fails the job and the workflow run, so a release whose image did not publish is visible as a failed run rather than as a silent absence.
31. **CIP-FR-31** The publishing workflow declares no aggregate gate job, and no check it reports is named by any branch-protection rule. `CI / gate` remains the only required check, so a failed publication never blocks a merge and a merge never waits on a publication.

32. **CIP-FR-HZKA** The `specs` lane checks out the repository and runs `python3 tools/spec-check/spec_check.py` with the repository root as its working directory (per `SPC-specification-consistency.md` SPC-FR-NUAB). It is a lane of its own rather than a step of `ui` because the check needs neither Node nor a Rust toolchain: as a step of `ui` it would wait on a pnpm install it does not use and would not run at all when that install failed, and a broken reference is exactly the kind of fault worth reporting while another lane is red.
33. **CIP-FR-JTMR** The `specs` lane provisions no language toolchain beyond the Python 3 the runner image already carries, installs no system package, and restores and saves no cache, there being nothing it builds and nothing it downloads.
34. **CIP-FR-KWNP** The `specs` lane is listed in the `gate` job's `needs`, so a specification reference that no longer resolves blocks a merge through `CI / gate` and through no check of its own, and branch protection is unchanged by its addition.
35. **CIP-FR-VRPM** The `ui-tests` lane is a matrix of three areas: `editor and documents`, `components`, and `app and state`. After a successful install, the job of an area runs `pnpm exec vitest run --project "<area>"` as its only test step. A job whose step exits non-zero fails.
    - *Why:* The `ubuntu-latest` runner gives Vitest one worker, so one job needs about 15 minutes for the full suite, and an area name tells which part of the code failed.
36. **CIP-FR-WKIN** The `ui-tests` matrix sets `fail-fast` to `false`, so a failing area never cancels another area, and each area reports its own result.
37. **CIP-FR-RDCY** `vitest.config.ts` declares one Vitest project for each area. `editor and documents` holds the tests of the editor, diff, workspace, flow, notes, comment, discussion, and document components under `src/components/`. `components` holds every other test file under `src/components/`. `app and state` holds every test file that is not under `src/components/`. Every test file is in exactly one area.

## Non-functional requirements
- Every lane and the publishing job run on GitHub-hosted `ubuntu-latest` runners. The application's Rust suite exercises Tauri's mock runtime and never opens a real window, so no virtual display server is provisioned.
- Third-party and first-party actions are referenced by released version tags, never by a mutable branch ref such as `@main`.
- Dependency resolution is deterministic in every lane: `pnpm-lock.yaml`, `src-tauri/Cargo.lock`, `tools/agentic-cli-mock/Cargo.lock`, and `server/Cargo.lock` are committed and are the sole source of dependency versions.
- Network access in the verification workflow is limited to the package registries and system-package mirrors the lanes install from. No lane contacts a project-owned service. The publishing workflow additionally reaches GitHub Container Registry, which is the one registry either workflow writes to.
- Caching is a wall-clock optimisation only. Every lane produces the same verdict on a cold runner with every cache evicted as it does on a warm one.
- The verification workflow gates merges and produces no artifact. The publishing workflow produces one artifact, the server image, and gates nothing. Native bundling of the desktop application belongs to neither and remains a local and release-time concern.
