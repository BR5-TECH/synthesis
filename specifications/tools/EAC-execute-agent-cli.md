# Execute agent CLI

**Spec code:** `EAC`

## Intent
The execution boundary a loop crosses to make an agentic CLI do one turn of work. Handed an existing directory and a structured task, this tool resolves the project's own CLI-kind agentic integration, resolves the image that project commits for that vendor, launches a container from it through the Docker backend the machine is configured to reach, with the directory mounted as its working tree, hands the task to the agent on stdin, and returns one normalized result: what the process did, and — where the process completed cleanly and the agent answered in the protocol — the agent's own report of the turn. It exists so that every future loop drives an agent the same way rather than each one growing its own process handling, its own credential path, and its own idea of what a reply looks like. The boundary is deliberately narrow: this tool decides nothing about *what* the agent should do and verifies nothing about what it did. A valid response envelope is the agent's account of its turn, never proof that a file changed, that a suite passed, or that the work is finished; inspecting the execution directory afterwards is the caller's job and always was. Out of scope: creating, switching, publishing, or deleting a Git worktree or branch, all of which belong to whichever loop owns the directory it supplies; choosing the integration, the model, or the reasoning effort, which `../core/AIC-agentic-integrations.md` resolves and no caller here may override or supply; holding a loop's state machine, its retry policy, its review decisions, or its session persistence; executing an API-kind integration or OpenCode, neither of which has a pinned execution protocol to invoke; the wire protocol of each executable vendor — its argument grammar, its stdin transport, its structured output, its exit statuses, and its session mechanism — each of which belongs to that vendor's own specification, `../infra/CCP-claude-code-cli-protocol.md` for Claude Code and `../infra/CDX-codex-cli-protocol.md` for Codex, and neither of which is restated here; authoring the shipped vendor images and the contract every image an agent runs in must satisfy, which are `../infra/AVI-agent-vendor-images.md`'s; configuring which image a project runs and building it, which is `../core/PSS-project-settings-storage.md`'s; and configuring and verifying the Docker backend, which is `../core/GSS-global-settings-storage.md`'s and which this tool reads rather than probes.

## Contract surface

This is a **loop-facing tool** in the sense of `TLC-tool-conventions.md` TLC-FR-20: an internal Rust API reached by loop code, not a `rig::tool::PortableTool` a model calls. It registers no Tauri command, emits no Tauri event, and is unreachable from `src/**` by any `invoke()`. It owns the vendor execution descriptors, the Docker runtime seam, the task/response protocol, and the process lifetime of one container. It owns no file, no store, and no repository state.

### The operation

```
async fn execute_agent_cli(request: AgentExecutionRequest)
    -> Result<AgentExecution, AgentExecutionError>
```

One call is one container. There is no other entry point, no batch form, and no handle a caller keeps between calls.

### The caller request

```
AgentExecutionRequest {
  execution_directory: PathBuf,     // an existing, canonical directory
  task:                AgentTaskRequest,
  cancellation:        CancellationToken,
  activity:            ActivitySink | null,       // who watches the run (EAC-FR-32)
  durable_output:      DurableOutputSink | null,  // who must keep the run (EAC-FR-VSNM)
  supplementary_mount: SupplementaryMount | null, // internal-only, one kind (EAC-FR-40)
  turn_kind:           TurnKind,                  // which kind of turn this is (EAC-FR-IRRD)
}

SupplementaryMount =
    { kind: "semantic_rebase_artifact", host_path: PathBuf }   // the only member

TurnKind =
    "work" | "review" | "semantic_rebase" | "merge_work" | "merge_review"
```

It carries no vendor, no model, no reasoning effort, no image reference, no credential, and no credential location. There is no field through which a caller could supply one, which is what makes EAC-FR-03 enforceable by shape rather than by discipline. Neither sink is an exception: a sink receives and cannot supply, so a caller that holds one learns what the launch did and still decides nothing about it. The durable sink is the one that may answer back, and the only thing it may answer is whether it stored what it was given (EAC-FR-CXUE). The supplementary mount is not one either: it is a closed enumeration of one member with one fixed container path and one fixed access mode, so what a caller may ask for is *that this run reads that bundle* and never where, how, or with what rights (EAC-FR-40). The turn kind is not one either: it names *which kind of turn this is*, which is a fact the caller already holds about its own work, and every consequence of it — the model and the reasoning effort resolved for it, and whether repository metadata is mounted or masked — is decided here from the resolved integration and the descriptor (EAC-FR-IRRD, EAC-FR-41). A caller that named a different kind would get the author's own selections for that kind, never a vendor, an image, or a credential of the caller's choosing, and never a model or an effort the caller supplied.

### The activity a watcher receives

```
AgentActivityEvent {
  at:                string,     // RFC 3339 UTC, when the line arrived
  channel:           "stdout" | "stderr" | "executor",
  kind:              ActivityKind,
  summary:           string,     // one line, bounded
  payload:           string,     // the whole event, verbatim and masked
  payload_truncated: bool
}
```

`ActivityKind` is one of `invocation`, `task`, `started`, `reasoning`, `message`, `tool_call`, `tool_result`, `command`, `file_change`, `retry`, `usage`, `finished`, `error`, `diagnostic`, `unrecognized`.

### The output a durable sink receives

```
DurableActivity {
  record_id:         string,     // assigned here, stable across every retry
  at:                string,     // RFC 3339 UTC, when the activity arrived
  channel:           "stdout" | "stderr" | "executor",
  kind:              SafeActivityKind,
  summary:           string      // one masked line of at most 300 characters
}

SafeActivityKind =
    "started" | "message" | "tool_call" | "tool_result" | "command"
  | "file_change" | "retry" | "usage" | "finished" | "error" | "diagnostic"

DurableOutputAck =
    { ok: true }
  | { ok: false, failure: { code, message } }   // the sink could not store it
```

`DurableActivity` has no payload field. The kinds `invocation`, `task`, `reasoning`, and `unrecognized` are never delivered to a durable sink.

The sink receives and cannot supply: it learns what the launch produced and decides nothing about it, and it is told no run identifier, the attribution being carried by the sink the caller constructed.

### The task envelope

What a caller supplies, serialized as JSON and strictly decoded, with unknown fields rejected at every level:

```
AgentTaskRequest {
  protocol_version: 1,
  instruction: string,                 // non-empty
  input: object | null,                // task-specific structured context
  result_contract: ResultContract | null,  // which fixed result shape the answer must
                                       // take, named rather than supplied (EAC-FR-43)
  resume: {
    session_id: string | null,
    continuation_token: string | null
  } | null,
  execution: {
    timeout_ms: integer,
    cancellation: "caller_controlled"
  }
}
```

`ResultContract` is one identifier of a closed set the executor holds. Under v1 the set is `review_verdict` alone.

What reaches the agent on stdin is that request carrying one further field, which the executor supplies and no caller can (EAC-FR-35):

```
TaskDocument {
  protocol_version, instruction, input, resume, execution,   // the caller's, unaltered
  response_contract: string,       // the executor's: fixed, vendor-neutral, identical every call
  result_schema: object | null     // the executor's: the fixed schema document the caller's
                                   // result_contract names, absent where it named none
}
```

The two are named apart because the boundary between them is load-bearing. A caller owns *what the agent should do* and the executor owns *what an answer looks like*, and `response_contract` and `result_schema` are the second of those written down — which is why a caller cannot supply either, override either, or read either back. A caller names its result contract and the executor resolves the name: the shape is the executor's text and the choice of shape is the caller's (EAC-FR-43).

### The response envelope

The one document the agent is required to emit, strictly decoded, unknown fields rejected:

```
AgentResponseEnvelope {
  protocol_version: 1,
  outcome: "success" | "failure" | "escalation_required",
  summary: string,                     // non-empty
  result: object | null,               // success only
  failure: {
    code: string,
    message: string,
    retryable: boolean
  } | null,                            // failure only, required there
  escalation: {
    reason: string,                    // non-empty; why the turn cannot finish
    questions: [                       // 1 to 8, in the order they are to be answered
      {
        question: string,              // non-empty
        options: [                     // 0 to 3; empty where no fixed response suits
          {
            answer: string,            // non-empty; the value submitted when chosen
            summary: string,           // one sentence, at most 5 words
            description: string        // display-only; at most 2 sentences, 12 words
          }
        ]
      }
    ]
  } | null,                            // escalation_required only, required there
  session: {
    session_id: string | null,
    continuation_token: string | null
  } | null,
  metadata: object | null
}
```

### The result

```
AgentExecution {
  process_outcome: "completed" | "non_zero_exit" | "invalid_structured_output"
                 | "timeout" | "cancelled" | "terminated",
  exit_code:       integer | null,     // present for completed and non_zero_exit
  response:        AgentResponseEnvelope | null,   // present only for completed
  stdout:          CapturedStream,
  stderr:          CapturedStream,
  duration_ms:     integer,
  container_removed: bool,            // whether removal was confirmed
}

CapturedStream { bytes: Vec<u8>, truncated: bool }
```

`process_outcome` describes the process; `response.outcome` describes the turn. An agent that reports `failure` or `escalation_required` produced a `completed` execution, because the process ran to completion and answered in the protocol — the two axes never collapse into one.

### The failures

Every one of these but the last is returned before any container is created, and each is distinct because each calls for a different correction:

```
AgentExecutionError =
    IntegrationUnresolved(resolution)     // AIC resolved no integration
  | UnsupportedIntegration(vendor)        // api-kind, or opencode
  | CredentialUnavailable(reason)         // AIC handoff refused or failed
  | ExecutionDirectoryInvalid(reason)     // missing, not a directory, unreadable
  | RequestTooLarge(limit_name)           // a documented byte limit exceeded
  | RuntimeUnavailable                    // no usable Docker-compatible runtime
  | ImageUnavailable(vendor)              // configured image absent and pull failed
  | LaunchFailed(reason)                  // runtime refused to create or start
  | VendorImageUnresolved(reason)         // the project configures no usable image
  | SessionStateUnavailable(problem)      // the session-state directory could not be established
  | SupplementaryMountInvalid(reason)     // the supplied bundle is missing, unreadable,
                                          //   over a limit, or in a refused location
  | RepositoryMaskingUnavailable(reason)  // repository metadata inside the execution
                                          //   directory could not be masked (EAC-FR-41)
  | DurableOutputFailed(failure)          // the durable sink could not store an activity;
                                          //   returned after the container is gone (EAC-FR-ZVRP)
```

### The vendor execution descriptor

Immutable application data, one per executable vendor, transcribed from that vendor's own protocol specification and holding every parameter of an invocation. Nothing in it is author input, project state, or a caller argument:

```
VendorExecutionDescriptor {
  vendor:            "claude_code" | "codex",
  protocol_spec:     &'static str,  // the vendor spec this descriptor transcribes
  cli_version:       string,        // the version that vendor's protocol is pinned against
  fresh_argv:        fn(&Resolved) -> Vec<String>,   // the whole vector for a fresh turn
  resume_argv:       fn(&Resolved, &str) -> Vec<String>,  // the whole vector for a resumed turn
  stdin_transport:   StdinTransport,
  response_sources:  &[ResponseSource],  // ordered positions the envelope may sit at
  session_source:    SessionSource,      // where the vendor reports its session identity
  credential_form:   CredentialForm,     // env variable, or mount
  session_state:     SessionStateMount,  // how session state survives the container
}
```

A vendor's fresh and resumed vectors are generated whole and separately rather than assembled from shared fragments, because a resumed turn is not a fresh turn with an addition — `../infra/CDX-codex-cli-protocol.md` CDX-FR-09 is the case that makes the distinction load-bearing.

### The container specification

What the executor composes for one launch, whole and immutable, from the vendor's descriptor, the named Docker constants, and the image the project configures:

```
ContainerSpec {
  image:        string,   // the project's configured reference, from PSS (EAC-FR-38)
  name:         string,   // unique per request
  argv:         Vec<String>,          // the vendor's own argument vector
  workdir:      string,               // the execution directory's own path, or
                                      //   "/workspace" in the fallback shape
  mounts:       &[Mount],             // execution directory, credential, session state, and
                                      //   the semantic-rebase artifact where one was supplied
  capabilities: &[Capability],        // the least the pinned CLI works under
  security:     &[SecurityOption],
  network:      NetworkMode,
}
```

### The Docker runtime seam

Every container operation goes through one internal abstraction rather than through direct process spawning at call sites:

```
trait DockerRuntime {
    async fn run(&self, container: &ContainerSpec, env: &[(String, SecretString)], stdin: &[u8])
        -> Result<RuntimeOutcome, RuntimeError>;
}
```

Production binds it to the Docker backend the machine has verified (EAC-FR-39): the **Docker CLI** runtime, which renders the specification into the `docker run` argument vector the descriptors define and executes the verified `docker` executable with it, or the **Docker Engine** runtime, which creates and starts the container over Bollard's connection to the configured endpoint from the same specification. A test binds the seam to a recording double that asserts the exact rendered argv and the exact stdin bytes and replays a configured stdout, stderr, and exit status — which is how `../infra/ACM-agentic-cli-mock.md` stands in for the runtime without any production path changing.

## Functional requirements

1. **EAC-FR-01** The execution surface is `execute_agent_cli`, an internal Rust API taking a typed request and returning a typed result or a typed error. It is not registered as a `#[tauri::command]`, emits no Tauri event, and is unreachable from `src/**`, so no frontend call can launch an agent.
2. **EAC-FR-02** The caller request carries an execution directory, an `AgentTaskRequest`, a cancellation token, the turn kind of EAC-FR-IRRD, and at most one typed supplementary mount of the one kind EAC-FR-40 defines, and carries no vendor, model, reasoning effort, image reference, credential, or credential location. No field of it, and no field of any type it contains, can express one. A turn kind is not one of them: it is a closed set of five names for the kind of work a turn does, it is a fact the caller already holds about its own run, and what follows from it is resolved here rather than supplied with it.
3. **EAC-FR-03** The executor calls `../core/AIC-agentic-integrations.md`'s `resolve_agentic_invocation()` (AIC-FR-19) itself on every launch, and that call is the sole source of the vendor, the model, and the reasoning effort. A caller cannot select, override, pre-resolve, or supply any of the three, and a resolution that refuses returns `IntegrationUnresolved` carrying the same distinction `get_project_agentic_integration` reports, with no container created.
4. **EAC-FR-04** Only `claude_code` and `codex` are executable here. A resolution naming `opencode` or either API-kind vendor returns `UnsupportedIntegration` before any credential is requested and before any container is created, neither having an execution protocol pinned in this spec.
5. **EAC-FR-05** Launch material reaches the executor only through `../core/AIC-agentic-integrations.md`'s executor-only handoff (AIC-FR-30): Claude Code's one-request OAuth token, or Codex's read-only config-mount source and target. A handoff that refuses, or a keychain that is unavailable, returns `CredentialUnavailable` with no container created. The executor never reads a keychain, a config file, or an environment variable of its own to obtain either.
6. **EAC-FR-06** The execution directory is validated before launch and refused with `ExecutionDirectoryInvalid` when it does not exist, is not a directory, or cannot be accessed. Validation goes through `../core/FSA-filesystem-access.md` rather than through a bare path predicate, and the executor neither creates the directory nor any part of its path.
7. **EAC-FR-07** `AgentTaskRequest` is strictly decoded at every level: `protocol_version` must be the integer `1`, `instruction` must be non-empty, `execution.cancellation` must be `"caller_controlled"`, and a field the schema does not define anywhere in the document is a rejection rather than an ignored key.
8. **EAC-FR-08** Every caller-visible payload is bounded by a named byte limit, and the serialized task is checked against its limit before any container is created, returning `RequestTooLarge` naming which limit was exceeded. The limits are: serialized task 1 MiB, `instruction` 256 KiB, `input` 512 KiB, each `resume` field 512 B, captured stdout 64 MiB, captured stderr 1 MiB, parsed envelope 1 MiB, `summary` 8 KiB, `result` 256 KiB, `metadata` 64 KiB, each `session` field 512 B, `escalation` 64 KiB, its `reason` 4 KiB, each `question` 2 KiB, and each proposed response's `answer` 512 B, `summary` 128 B, and `description` 256 B. One further limit belongs to the supplementary mount rather than to a payload: **any one file of the semantic-rebase bundle is 1 MiB**, checked before the container is created and returning `SupplementaryMountInvalid` naming the limit (EAC-FR-40). The bundle **whole** carries no limit, and a mount is never refused for its total size: it is the caller's own generated material rather than a payload anybody composed, its file count is the size of a change set, and the agent reads it one file at a time out of three path-keyed mirrors (per `../core/GRB-graduation-rebase.md` GRB-FR-YPEX), so a total would refuse a report nobody was going to read at once. What this executor guards is what one read can cost, and that is the per-file limit.
9. **EAC-FR-09** The serialized task reaches the agent only on the container's stdin. It is never placed in an argument vector, an environment variable, an image layer, a mounted file, a persisted configuration, a log record, or an error payload — and the same holds for the instruction, the structured input, and every resume field considered separately.
10. **EAC-FR-10** Every Docker parameter and every vendor argument fragment is a named constant or a field of an immutable vendor execution descriptor, the image alone excepted, which is the project's own (EAC-FR-38). No call site assembles an argument string of its own, so the complete container specification — and the `docker run` vector the Docker CLI backend renders from it — is derivable from the descriptors, the named constants, and that one resolved image.
11. **EAC-FR-11** `../infra/CCP-claude-code-cli-protocol.md` is the sole authority on Claude Code's invocation and output extraction. Claude Code's descriptor transcribes that spec's argument grammar (CCP-FR-02), its stdin transport (CCP-FR-06), its ordered extraction positions (CCP-FR-09), its session mechanism (CCP-FR-16, CCP-FR-17), and its credential form (CCP-FR-20), and this spec restates none of them — a change to that vendor's wire behavior is a change there and reaches the executor as a changed descriptor rather than as a changed requirement here.
12. **EAC-FR-12** `../infra/CDX-codex-cli-protocol.md` is the sole authority on Codex's invocation and output extraction, on the same terms and independently: Codex's descriptor transcribes that spec's two argument grammars (CDX-FR-02, CDX-FR-09), its stdin transport (CDX-FR-08), its single extraction position (CDX-FR-12), its session mechanism (CDX-FR-20, CDX-FR-21), and its credential form (CDX-FR-24). Neither vendor spec constrains the other, so an upgrade or protocol change to one vendor leaves the other's descriptor and every requirement here untouched.
13. **EAC-FR-13** One request creates exactly one container, from the image EAC-FR-38 resolved, under a name no other request has used or will reuse, removed after the agent exits or is terminated. The invocation mounts the execution directory read/write at the path EAC-FR-ZKMR gives it and sets that path as the working directory; it connects the client's stdin to the container, without which EAC-FR-09's payload is written to a stream nothing reads and a CLI that takes its whole prompt from stdin exits non-zero on an empty one; it allocates no pseudo-terminal, because a terminal invites the CLI to print progress decoration into the same stream EAC-FR-19 parses; it publishes no port, sets no privileged mode, and mounts nothing else beyond the vendor's own credential mount, the vendor's session-state mount (EAC-FR-31), the one supplementary mount a caller may supply (EAC-FR-40), and the read-only repository metadata of EAC-FR-FNFV — not the host root, not the Docker socket, not `app_data_dir()` itself, not any other directory, and no worktree but the execution directory itself. The container has network access, because both vendor CLIs reach their own services, and it runs with the least Docker capabilities and security options the pinned CLI works under, each one named in the descriptor rather than assumed.
14. **EAC-FR-14** The container runs as the non-root user its image declares (per `../infra/AVI-agent-vendor-images.md` AVI-FR-19), and the invocation maps that user to the host user's UID and GID, so a file the agent creates in the execution directory is owned by the host user and readable and writable by them after the container is gone.
15. **EAC-FR-15** Claude Code's OAuth token is passed as `CLAUDE_CODE_OAUTH_TOKEN` in the environment of that one container and reaches nothing else. It never appears in an argument vector, on stdin, in an image layer, in a mounted file, in a process diagnostic, in a log record, in an error payload, in persisted state, or in the returned result, and it is not inherited by any other container, request, or child process.
16. **EAC-FR-16** Codex's configuration directory is mounted read/write at the target AIC supplied, for that one container, and is addressed by `CODEX_HOME`. It is read/write rather than read-only, that vendor writing its session state beneath the same directory it reads its login from (per `../infra/CDX-codex-cli-protocol.md` CDX-FR-23). The executor still never reads, copies, alters, logs, or returns any part of its contents, and never resolves its location itself; what the container writes there is the vendor's own doing. A Codex authentication failure arising from that mount is the vendor's own non-zero exit or reported failure rather than an executor error.
17. **EAC-FR-17** Every container operation goes through the `DockerRuntime` seam. A backend that is unverified, missing, or unusable returns `RuntimeUnavailable`, a configured image that is absent from the local image store and cannot be pulled returns `ImageUnavailable`, and a runtime that refuses to create or start the container returns `LaunchFailed` — three distinct failures, because a machine without Docker, a machine without the image, and a machine that refused this container each call for a different correction.
18. **EAC-FR-18** `AgentResponseEnvelope` is strictly decoded and its exclusivity rules are enforced: `protocol_version` must be `1`, `summary` must be non-empty, `success` requires `failure` and `escalation` both null, `failure` requires a `failure` object and both `result` and `escalation` null, and `escalation_required` requires an `escalation` object and both `result` and `failure` null. An `escalation` object is itself closed the same way: its `reason` must be non-empty, its `questions` list must hold between 1 and 8 entries, every entry must carry non-blank `question` text and between 0 and 3 `options`, and every option must carry a non-blank `answer`, a `summary` of one sentence and at most 5 words, and a `description` of at most 2 sentences and 12 words in total. A singular `question` or `options` field at the escalation's own level is an undefined field and is refused as one. Any violation is `invalid_structured_output`, never a partially accepted envelope.
19. **EAC-FR-19** The envelope is extracted from the vendor's structured output at the ordered positions the descriptor names, taking the first position that yields a document and never consulting a later one once an earlier has produced one. A vendor whose spec names one position has one; a vendor whose spec names two has both, in that order and no other. Exactly one envelope document must be found at the position used. Prose, partial JSON, several response documents at one position, invalid UTF-8 where JSON is required, a wrong protocol version, an unknown field, a schema or exclusivity violation, and every position being exhausted without a document are all `invalid_structured_output` with a null `response`, and none of them is ever reported as an agent-reported outcome.
20. **EAC-FR-20** `metadata` is an allowlisted, vendor-neutral object, and the v1 allowlist is empty. Every key the allowlist does not hold is **discarded before the envelope is validated and before any caller sees it**, so the field a caller receives is always null. The field exists so that a later protocol version admits a reviewed key by an allowlist edit rather than a schema change, and the emptiness is what makes it impossible for raw vendor transcript data, a filesystem claim, a prompt, or a credential to arrive through it — a key that never reaches a caller carries none of them. Discarding rather than refusing is deliberate: the guard is identical and refusing would spend a whole completed turn on a field nothing reads. Where a vendor validates the response against a schema the executor supplies, that schema states this bound (`../infra/CCP-claude-code-cli-protocol.md` CCP-FR-07), so the agent is corrected inside the run and the discard is a backstop rather than the only statement of the rule. One ordering is stated rather than left to be discovered: EAC-FR-08's envelope bound is applied to the serialized document **before** it is parsed, so `metadata` large enough to carry the document past that bound is `invalid_structured_output` and is not reached by the discard. The bound outranks it deliberately — removing a field requires parsing the document that holds it, and parsing an unbounded document to save a turn is a worse trade than losing the turn.
21. **EAC-FR-21** `session` carries only a resumable-session reference the pinned vendor actually supports, bounded by EAC-FR-08's limits, and never a credential or any part of one. The identifier is taken from the position the descriptor's `session_source` names rather than from the envelope, an agent not reliably knowing the identifier its CLI assigned and a reference nobody can produce making EAC-FR-30's resume unreachable. Where a vendor lets the executor assign the identifier before the run, the value asserted back is the one assigned and a mismatch is `invalid_structured_output`; where a vendor only reports one afterwards, the reported value is what the caller receives. A vendor with no resumable session yields a null `session`, which is a fact the caller can act on rather than an error.
22. **EAC-FR-22** The result records the process-level outcome and the agent's report on separate axes. A `response` is present only for `completed`; `non_zero_exit`, `invalid_structured_output`, `timeout`, `cancelled`, and `terminated` all carry a null `response`. An agent-reported `failure` or `escalation_required` is a `completed` execution and is distinguishable from every value of `AgentExecutionError` and from every other `process_outcome`.
23. **EAC-FR-23** stdout and stderr are captured separately and never merged, each bounded by its EAC-FR-08 limit, with `truncated` reporting whether the bound was reached. Truncated stdout is never parsed for an envelope — a run whose stdout hit the bound is `invalid_structured_output` with the captured prefix preserved for the caller to read. The stdout bound is sized for an event stream rather than for one document.
   - *Why:* Both pinned CLIs write a line per event, so a bound sized for the result document alone would fail a long, successful turn for nothing but its length.
24. **EAC-FR-24** `execution.timeout_ms` bounds the run. On expiry the executor terminates the container and its whole process tree, waits for reaping and for confirmed container removal, and returns `timeout` with a null `response`, whatever bytes had already arrived on stdout. A partial response is never promoted to a success.
25. **EAC-FR-25** Cancellation is caller-controlled through the supplied token and carries exactly the termination and removal guarantees of EAC-FR-24, returning `cancelled`. Whether and how to retry after a `timeout` or a `cancelled` is the caller's decision, and this tool retries nothing on its own.
26. **EAC-FR-26** The container is removed on every path out of the call — clean exit, non-zero exit, invalid output, timeout, cancellation, termination, and any error raised while reading its streams — and the call does not return until removal has been attempted and its outcome established. A removal that cannot be confirmed is reported rather than discarded: the result carries `container_removed = false` and an `ERROR` record names the vendor and the container, nothing here being able to clean it up on the caller's behalf. No container name is ever reused.
27. **EAC-FR-27** The executor itself reads, writes, diffs, validates, and commits no project file. Its only effect on the execution directory is whatever the invoked CLI did inside the mount, and it never treats a field of the response envelope as evidence that a file was created, changed, or deleted — verifying the directory is the caller's, always.
28. **EAC-FR-28** Independent requests may run concurrently and share no mutable state: not a session, not a stdout or stderr buffer, not an environment, not a credential mount, not a container, not an execution directory, and not task data. Each request resolves its own integration, obtains its own launch material, and creates its own container, so nothing one request carries can be observed by another.
29. **EAC-FR-29** Every call emits through `../core/LGC-logging.md`'s internal API under the `ai` and `backend` domains together: an `INFO` record when the call begins and when it ends, naming the vendor, the container, the process outcome, and the duration, and a `WARN` or `ERROR` record on every failure path including handled ones, naming the failure. A record for a run that did not complete also carries the exit status, the size and truncation of each captured stream, and a bounded excerpt of the tail of stderr. It is the one part of these records an execution carrying the semantic-rebase mount does not get, that caller's streams being file contents rather than diagnostics (EAC-FR-42). **Masking is one rule for every path out of this tool**: a value a record may not carry is replaced, wherever it appears, by its first four and last four characters around an ellipsis, and a value too short for that rendering to hide most of it is removed entirely. The fingerprint tells one token from another and shows that a stale credential rather than a missing one was used, without carrying a value anybody can authenticate with. The values masked are everything the launch handed the container which a record may not carry: the credential values in its environment, the session identity the executor assigned and any session it was asked to resume, and, for a vendor whose credential is a directory, that directory in both the spelling the CLI knows it by and the spelling it was mounted from. Where one masked value contains another, the longer is masked first. Masking is applied over the whole stream before the excerpt is cut. A stream that reached EAC-FR-23's capture bound was cut a second time, before the executor held it, and a credential lying across *that* cut is a whole value nowhere in what was captured — no mask can match it. The final line of a truncated capture is incomplete by definition and is therefore dropped whole, and a truncated capture with no line ending at all yields no excerpt. EAC-FR-15 and the bar on the Codex configuration path are unweakened by any of it. A mask is built from values the executor holds, and EAC-FR-16 forbids it to read the Codex configuration directory, so the *contents* of that directory are guarded by what `../infra/CDX-codex-cli-protocol.md`'s CLI chooses to print and not by anything here. Nothing the executor puts anywhere — a record, an error payload, a returned value, or an activity event — carries an unmasked credential, an unmasked session or resume identity, or the Codex configuration path in either spelling.
   - *Why:* The stderr tail is the one record here that names a cause rather than narrowing one; without it a reader must rebuild the container to read a line the executor already held.
30. **EAC-FR-30** A task supplying `resume` data causes the vendor's resumed argument vector to be generated rather than its fresh one, asking the pinned vendor to continue that session. A vendor whose pinned version cannot resume, or a session reference that vendor no longer recognises, is reported as such rather than silently starting a fresh session — so a caller learns that resumption was unavailable and can decide to issue a new turn instead. Where a vendor's own protocol makes an unrecognised reference indistinguishable from a fresh start (`../infra/CDX-codex-cli-protocol.md` CDX-FR-22 is the case), the executor establishes which occurred from the session identity the run reports back rather than trusting the run to have failed.
31. **EAC-FR-31** Each vendor's session state is carried on a session-state mount that outlives the container, because both pinned vendors write session state inside the filesystem they run on and a container removed after every request would otherwise destroy every session it created, making EAC-FR-30 unreachable. The mount is a Synthesis-owned, per-vendor, per-project host directory, addressed in the container by the environment variable that vendor's protocol names, and it is the only mount besides the execution directory and the vendor's credential mount. It never carries a credential — for a vendor whose credential arrives in the environment the mount is session state alone, and for a vendor whose credential directory is also its session directory the two coincide and EAC-FR-16 governs it. The executor creates the directory through `../core/FSA-filesystem-access.md` rather than through a bare filesystem call, and reads nothing in it: transcripts written there are vendor material, never parsed for an envelope, never logged, and never returned. A directory that is required and cannot be established — no resolvable root, a creation that fails, or something other than a directory already at the path — returns `SessionStateUnavailable` naming which, before any container is created. It is never launched around: a turn that ran without its mount would look entirely successful while every session it created died with the container, which is precisely the failure a caller could not detect afterwards.

32. **EAC-FR-32** A caller may watch a run while it happens. The runtime hands the executor each complete line of stdout and of stderr as it arrives rather than at exit, and the executor passes every one on to the caller's activity sink, if it supplied one, and to a `DEBUG` log record. This exists because a turn is minutes of silence otherwise: both pinned CLIs write a line per event as they work, and without reading them a caller cannot tell a turn that is working from a turn that is wedged, nor learn why one failed without rebuilding its container by hand. Watching changes nothing else — the capture of EAC-FR-23 is unaffected, the result is identical, and a run with no sink is the run it would have been before a sink existed. The sink receives every line for every execution kind; what an execution carrying the semantic-rebase mount does not additionally get is the `DEBUG` record beside each line (EAC-FR-42). Three bounds hold. A line is delivered to the observer as one piece; a line that reaches the reassembly bound of 256 KiB without ending is delivered at that bound and marked as a piece rather than held while it grows, and the executor holds back the tail of such a piece until the next arrives, so a credential split across that delivery cannot be emitted as a fragment. End of stream is delivered whether or not anything is pending, because an observer holding a tail of its own against that hazard has nothing else to prompt it — and a stream that ends exactly on the reassembly bound would otherwise take the agent's last words with it. A retained event is bounded at 64 KiB and says whether it was cut. Observation continues past EAC-FR-23's capture bound, because what a run is doing while it overruns its capture is exactly what somebody watching it wants to see. An **activity** sink that blocks stops the pipe being drained, so an implementation of that sink must not; a **durable output** sink may apply bounded backpressure and is drained on the terms of EAC-FR-VSNM instead.
33. **EAC-FR-33** Each observed line is read into a normalized activity by the vendor's own descriptor, so a reader is not asked to know that one CLI calls a tool call an `item.started` and another calls it a content block. The reading is total: every line yields an activity, a line the vendor's grammar does not cover yields `unrecognized`, and a line that is not JSON at all yields `unrecognized` carrying the line. Nothing is ever dropped — a vendor that adds an event must not be able to make a run go quiet, which would be indistinguishable from a run with nothing to say. The verbatim line is carried beside the reading, so this build's interpretation is never the only account of what the vendor wrote. stderr is not read against any vendor grammar: both pinned protocols define it as diagnostics alone, so it is `diagnostic` carrying what it said. What each vendor's events mean is that vendor's specification's (`../infra/CCP-claude-code-cli-protocol.md` CCP-FR-27, `../infra/CDX-codex-cli-protocol.md` CDX-FR-25) and is not restated here.
34. **EAC-FR-34** Before the run, the executor reports two activities of its own: the complete generated invocation, and the serialized task the agent is handed on stdin. Neither is recoverable afterwards — the container is gone and the argument vector was never written down — and they are the first two questions anybody debugging a turn asks. Both are masked by EAC-FR-29's rule and bounded by EAC-FR-32's. This is the one place the executor deliberately carries task material out of the launch, and it is confined to the activity channel and its `DEBUG` records — and to the activity channel alone for an execution carrying the semantic-rebase mount, whose task holds a captured prompt (EAC-FR-42): the `INFO` and `WARN` records that describe the launch itself stay a boundary account naming the vendor, the container, the outcome, and the sizes, so a reader who raises the level floor to quieten a chatty run still has an unbroken record of every turn.
34. **EAC-FR-THUT** After a launched run, however it ended, the executor reports one `finished` activity on the executor channel. Its one line names the process outcome and the duration. A timeout also names the configured limit, and a non-zero exit names the exit code. It carries no task material and no agent output, and it reaches every sink the caller supplied.
35. **EAC-FR-35** Every task document carries a `response_contract`: fixed text the executor supplies, stating in words the shape of the `AgentResponseEnvelope` the agent is required to answer with — its field set, which fields each `outcome` requires and forbids, that `summary` is non-empty, that `metadata` carries nothing (EAC-FR-20), and, for `escalation_required`, the whole shape of the `escalation` object down to its question count, the option count each question allows, and the format each proposed response's `answer`, `summary`, and `description` must keep (EAC-FR-18). It is compiled into the binary, identical for every call, every vendor, and every caller, and it is the text of its file **with every authoring comment removed** and the blank space the removal leaves closed up: the contract an agent reads begins at its first real word and holds nothing addressed to a reader of this repository. It carries no project material, no captured prompt, no path, and no credential — which is what makes it the executor's to add rather than task material a caller routes through (EAC-FR-09). No caller supplies, overrides, or reads it: an `AgentTaskRequest` carrying the key is rejected before launch as the undefined field it is (EAC-FR-07), and no field of `AgentExecutionRequest` can express one. It states the same structural rules the decoder of EAC-FR-18 enforces and no weaker set, on the terms `../infra/CCP-claude-code-cli-protocol.md` CCP-FR-07 already requires of a vendor schema. It is added before EAC-FR-08's serialized-task bound is applied, so the document that bound is checked against is the document the agent receives. It is supplied **unconditionally** rather than only to the vendor that has no other source for it: a caller cannot choose its vendor (EAC-FR-03), so a guarantee holding for one vendor and not the other is one no caller could rely on.
   - *Why:* An agent cannot conform to a contract nobody stated, and the only other place to state it is each caller's instruction, where every future loop would restate a protocol it does not own.
36. **EAC-FR-36** An `escalation` is decoded **whole or not at all**, and the order its questions arrive in is the only identity a question has. The executor assigns no key, derives none from a question's text, sorts nothing, and drops no entry, so the list a caller receives is the list the agent wrote in the order it wrote it — which is what lets a caller number the questions itself and answer them by that number later. One malformed question or one malformed proposed response refuses the envelope entire (EAC-FR-18) rather than yielding an escalation carrying the questions that happened to parse: a caller that paused a run on a partial question set would ask its author to settle less than the agent stopped for, and the agent would receive answers to questions it did not recognise.
37. **EAC-FR-37** The seam resolves **which program to run** before it runs one, and looks beyond `PATH` to do it. `PATH` is consulted first; where it does not hold the runtime, each well-known installation location is tried in turn and the first that **starts** is the program every operation of that seam then uses. A candidate is judged by starting it and asking the client for its own version — which needs no daemon — rather than by inspecting the filesystem, so a location holding something that cannot be run is passed over exactly as an empty one is. The resolution happens once and is kept. A machine with **no** runtime settles on the plain program name and fails as `RuntimeUnavailable` exactly as it would have, and a runtime that is installed but stopped is found here and reported unavailable by EAC-FR-17 instead. Every `RuntimeUnavailable` emits a `WARN` naming the program the search settled on, the locations it looked in, and the `PATH` it was given.
   - *Why:* An application started the way a user starts one inherits the session launcher's `PATH`, which holds no directory a container runtime installs into.
38. **EAC-FR-38** The image a container is created from is the one the **open project commits for the resolved vendor**, read on every launch through `../core/PSS-project-settings-storage.md`'s `resolve_project_vendor_image(vendor)` (PSS-FR-30), and it is used **directly**: the reference the project configured is the reference the container is created from. There is no fallback to a shipped vendor image, no manifest digest to pin by, and no other place an image can come from, so a project that configures none launches nothing and returns `VendorImageUnresolved` with no container created and no credential requested. Where the image is absent from the local image store the backend may ask Docker to pull that reference, and a pull that cannot find or fetch it is `ImageUnavailable` on the terms EAC-FR-17 already sets. What the image must be is `../infra/AVI-agent-vendor-images.md` AVI-FR-19's contract and is not restated here.
39. **EAC-FR-39** The runtime seam is bound to the **Docker backend the machine has verified**, resolved once per launch through `../core/GSS-global-settings-storage.md`'s `resolve_docker_backend()` (GSS-FR-40). In Docker CLI mode the container specification is rendered into the `docker run` vector the descriptors define and the verified executable is run with it; in Bollard / Docker Engine mode the same specification is created and started over the Docker Engine connection at the configured endpoint, and the Docker CLI path takes no part. The executor **probes no backend of its own**: an unverified or unresolvable backend is `RuntimeUnavailable` before any container is created, and nothing here verifies, re-verifies, or repairs a backend. The container contract is identical under both — the same mounts, the same working directory, the same user mapping, the same capabilities and security options, the same network, and the same stdin and stream handling — so which backend a machine uses changes how Docker is reached and nothing about what the agent runs in.
40. **EAC-FR-40** A caller may supply **one typed supplementary mount, of one kind, for one run**. `SupplementaryMount` is a closed enumeration whose only member is `{ kind: "semantic_rebase_artifact", host_path }`, and the executor decides everything else about it: the bundle is mounted **read-only** at the fixed container path `/rebase`, whose layout below that root is the caller's and no part of this contract, and neither the root, the access mode, nor the presence of the mount can be moved, widened, or added to by a task field, an instruction, an environment value, or anything an agent returns. **The model never chooses a mount**: `AgentTaskRequest` cannot express one, so a mount is something the application supplied before the container existed rather than something the agent asked for.
 **Ordinary executions keep the mount set they already had.** A request supplying none is byte-for-byte the launch it was before this capability existed — the execution directory where EAC-FR-ZKMR puts it, the vendor's credential mount, and the vendor's session-state mount, and nothing else — so no `/rebase` path exists in that container and no argv names one. The capability is **internal-only** in the sense EAC-FR-01 already makes the whole tool internal: no Tauri command reaches it, `src/**` reaches nothing here, and the one caller of it is the turn of a stream update, `../core/GRB-graduation-rebase.md`, through `../core/GXD-graduation-execution.md`'s dispatch seam. The `/rebase` mount serves that update's turn alone: no `work`, `review`, `merge_work` or `merge_review` turn carries it.
    The mount is **validated before any container is created**, returning `SupplementaryMountInvalid` naming which check refused it and creating nothing: the host path must exist, be a directory, and be readable; it is resolved through `../core/FSA-filesystem-access.md` rather than by a bare path predicate, and an absolute path outside **the application's own user-scoped roots**, a path containing a `..` segment, and a path reaching through a symbolic link out of all of those roots are each refused. The roots are **two**, and a bundle inside either one satisfies the check: the application data directory, and the short root of `../core/FSA-filesystem-access.md` FSA-FR-KVWD — which is where `../core/GSU-graduation-start.md` GSU-FR-RJRF puts a graduation run's store, and therefore every semantic-rebase bundle this contract exists to carry. Each root is resolved before it is compared, exactly as the host path is, so a symbolic link that leaves one root without entering the other is refused; it must not be, contain, or be contained by the execution directory, the vendor's credential source, or the vendor's session-state directory, because a bundle overlapping any of those would put a credential, a session, or a change set behind a path nobody audited; and it must be within the bound of EAC-FR-08 — 1 MiB for any one file within it, the bundle whole carrying no bound. The executor **reads nothing inside it**: the bundle's contents are the caller's material, are never parsed, never logged, never returned, and never carried into the task document or an activity payload beyond the fixed container path itself, which carries no project material.
    **Cleanup is the container's.** The mount exists for that one container and is gone when it is removed on the terms of EAC-FR-26; the executor creates no copy of the bundle, writes nothing into it, and deletes nothing from the host — whose bundle it is and when it may be removed is the caller's (per `../core/GRB-graduation-rebase.md` GRB-FR-TOOU). **No vendor image and no Dockerfile gains anything from this**: the bundle is a runtime mount and never an image layer, and no image an agent runs in acquires a Git client, a repository, or a copy of the artifact on account of it, the image contract being the closed package list of `../infra/AVI-agent-vendor-images.md` AVI-FR-02. Both pinned vendors receive the identical mount at the identical path and read it with their own file and editing capabilities, so the contract a caller relies on is the mounted file rather than any vendor's internal tool.

41. **EAC-FR-ZKMR** An execution's container **names the paths its host names**. The execution directory is mounted at its own host path and is the container's working directory, and the repository store of EAC-FR-FNFV is mounted at its own host path as well. What the application calls a file and what the turn inside the container calls it are then one string, so a path either of them reports is one the other resolves — and a run's own records resolve for the same reason, the Git directory a linked worktree names in its `.git` and the store that Git directory names in its `commondir` being where they say they are.
    **A host path is not always a path a container can be given.** One that is not absolute in the form the container runtime takes is not: a path naming a drive rather than a root is a mount **source** the runtime accepts and a **target** it does not. An execution whose directory carries such a path runs in the **fallback shape** instead: the execution directory at a fixed `/workspace`, the store at the fixed path of EAC-FR-FNFV, and the generated `.git` pointer and store record that shape needs. Both shapes are complete, and neither is a degradation of the other.
    **A path the mount syntax cannot express is refused rather than fallen back from.** That syntax separates its own fields with commas, so a path holding one is no more a mount source than it is a target, and there is no shape that can carry it. Such an execution directory is refused before any shape is decided, on the terms EAC-FR-06 sets for a directory this module cannot use.
    **The shape is a property of the path**, decided before the container is composed and by nothing but the execution directory's own text, so which shape a launch takes is answerable without a runtime, a container, or a filesystem.
    **The execution directory alone decides the shape.** Where the store's own path cannot be expressed while the execution directory's can, the repository access is **withheld** on the terms EAC-FR-FNFV already sets, rather than the whole container moving to the other shape — a turn that reaches no repository reads files instead, where a turn whose paths silently stopped matching the application's would report paths nothing on this machine resolves.
    **The invocation names the working directory in both shapes**, so the working directory an image declares (per `../infra/AVI-agent-vendor-images.md` AVI-FR-11) decides nothing about where a turn stands.
42. **EAC-FR-41** An execution carrying the semantic-rebase mount additionally runs with **every repository-metadata path inside its execution directory masked**, and the executor **refuses to launch it otherwise**. Before the container is created it enumerates the `.git` entries the execution directory holds — the one at its root, whether that is a directory or the file a linked worktree carries, and every nested `.git` beneath it — and covers each with an empty read-only mount, so that inside the container a read of one fails and a write to one fails. It verifies each mask is in the composed container specification before the runtime is asked for anything, and where a mask cannot be established for any of them it returns `RepositoryMaskingUnavailable` naming which, with **no container created**. There is no launch-anyway path and no configuration that turns the masking off. The masking is keyed on **either** condition and not on one alone: an execution is masked where it carries the semantic-rebase mount **or** where its turn kind is `semantic_rebase`, so a turn that reached here under the wrong name still cannot read a repository. `semantic_rebase` is the only masked turn kind: a `merge_work` turn and a `merge_review` turn are never masked. Masking and the read-only repository access of EAC-FR-FNFV are exclusive, and masking wins wherever both would apply.
    The masking is stated as a launch rule rather than left to follow from the mount set, because the mount set alone does not carry it. A linked worktree's `.git` file names a gitdir outside every mount and so happens to be useless today; a repository whose metadata sits inside the mounted tree is not, a nested checkout the caller's own work created is not, and neither is a vendor image that later acquires a Git client. A guarantee that holds only while three unrelated things stay true is one nobody can rely on, so the executor makes it hold directly and refuses the launch where it cannot. It applies to **this execution kind alone**: an ordinary execution supplying no semantic-rebase mount launches with exactly the mounts and exactly the visibility it always had (EAC-FR-40), because a caller whose agent is meant to use version control is not one this rule is about. The generated argv is what the masking is asserted in, so a Docker argv test reads it exactly as it reads every other mount.

43. **EAC-FR-FNFV** An execution that EAC-FR-41 does not mask runs with the repository its execution directory belongs to **mounted read-only**. The executor resolves that repository from the execution directory alone, before the container is created, and mounts it in one of two shapes. An **ordinary checkout**, whose `.git` is a directory inside the working tree, has that directory pinned read-only over itself: Git finds it where it always was. A **linked worktree**, whose `.git` is a file naming a Git directory outside the working tree, has the **store** that Git directory lives inside mounted read-only — at its own host path where the container names the host's paths, and at a fixed container path this module chooses and no caller names in the fallback shape (EAC-FR-ZKMR). One mount rather than two, and that is load-bearing: a worktree's Git directory sits **inside** the store it shares, so mounting the store whole holds the two at the offset they have on the host, and two unrelated container paths leave what either records about the other resolving to somewhere neither mount is, a plain `git diff` failing on an unresolvable `HEAD`. Where the Git directory is not inside the store it names, there is no single mount for that shape and the access is withheld.
    **Its `config` is masked, in both shapes.** A repository's `config` holds its remote URLs, and a remote URL routinely carries a credential inside it. A store mounted whole without covering that entry hands every ordinary turn the project's stored credentials, which is a disclosure rather than a convenience, so the same empty read-only cover EAC-FR-41 masks with is applied to it here.
    **The `.git` the next turn resolves from is pinned.** The execution directory is mounted read/write, and a linked worktree's `.git` is an ordinary text file inside it — so a turn that could write it would redirect the **next** turn's mount at any repository on this machine, resolution reading that file afresh every turn. The mount at that path is therefore read-only in every shape. Where the container names the host's paths it is the worktree's own file, pinned over itself and saying what it always said. In the fallback shape it is a `.git` the **application generates**, naming the container path the store was mounted at rather than the host path the worktree's own file records.
    **The record that leads back to the store is generated in the fallback shape.** A worktree's Git directory names the store it shares in a `commondir` file of its own, and what that file holds depends on the tool that made the working copy: the `git` command line writes a path relative to that Git directory, and the library this application creates worktrees through writes the absolute host path. Git resolves that record before it resolves anything else, so a record naming a path the container does not have fails the turn on its first Git command rather than on some later one. Where the container names the host's paths, the record the worktree already holds names a path the container **does** have, and nothing is generated. In the fallback shape the store stands somewhere the record does not name, so the executor generates that record too — as a path relative to the Git directory it belongs to, mounted read-only over the store's own on the same terms as the pointer — and what a turn resolves is then a property of the mounts alone rather than of the tool that made the working copy.
    **What the invocation tells Git is as little as it can be.** It sets no `GIT_DIR`, no `GIT_WORK_TREE`, and no `GIT_COMMON_DIR`: each of those is exported to the whole container and would redirect **every** Git command in it, including the ones a build or a test suite makes about some other directory entirely, and the generated pointer is what makes them unnecessary. It sets `GIT_OPTIONAL_LOCKS` to `0`, without which a plain read fails trying to write a refreshed index into a directory it may not write, and it relaxes `safe.directory`, Git otherwise refusing a repository whose owner it does not recognise — a container launched for one agent, running as the owner of what it mounts, has no second user for that check to protect anything from.
    **A `merge_work` turn and a `merge_review` turn get this grant like a `work` turn and a `review` turn do**, their execution directories being linked worktrees of the project's repository. **The grant is all of it or none of it.** A part that cannot be expressed as a mount takes the whole of it with it: a store mounted without its mask discloses a credential, and a pointer left unpinned lets a turn redirect the next one, so a partial grant is worse than none. Where the execution directory belongs to no repository, or any part of the grant cannot be established, the launch **proceeds without it** and returns no error, and the turn reads the working copy instead. Repository access is a convenience of a turn and never a precondition of one, which is the opposite of the masking above. Read-only is the whole of what is granted: the turn reads history, and it commits, checks out, stages, fetches, and rewrites nothing.
    **What the grant exposes is the repository whole**, save the masked entry — every branch, every commit, and every object the store holds, and not the run's own branch alone. It is stated here rather than left to be inferred from the mount, because it is a widening: the container already holds the working copy and already reaches the network, so this adds to what a turn can **read** rather than to what it can do, and a reader deciding whether a project may be graduated at all is entitled to weigh it.
44. **EAC-FR-IRRD** Every request names its **turn kind** — `work`, `review`, `semantic_rebase`, `merge_work`, or `merge_review` — and the executor uses it for exactly two things. It passes a kind to `resolve_agentic_invocation()`, so the model and the reasoning effort a launch carries are the two the resolved integration holds for that kind of turn (per `../core/AIC-agentic-integrations.md` AIC-FR-10): a `merge_work` turn is resolved as a `work` turn, with the author's `work` selections, and a `merge_review` turn is resolved as a `review` turn, with the author's `review` selections, so the author makes no further selection for merge turns. It reads the kind as the second of EAC-FR-41's two masking conditions: `semantic_rebase` is masked and serves a stream update alone, and neither `merge_work` nor `merge_review` is masked. It selects no vendor, no image, and no credential, and it selects no model or effort of its own — it names the kind, and the author's own selection for that kind is read here from the resolved integration; it changes no other mount, and every kind but `semantic_rebase` gets the read-only repository mount of EAC-FR-FNFV; and it reaches no agent — a turn is never told its kind through this field, the task's own instruction and input being where the work is described. The identifiers `work`, `review`, `semantic_rebase`, `merge_work` and `merge_review` are the names each turn's log records carry for its kind.

45. **EAC-FR-42** An execution carrying the semantic-rebase mount emits **no `DEBUG` record into `../core/LGC-logging.md` and no stream excerpt anywhere**, and its boundary records are the only account of it that reaches that buffer. Three things are suppressed for that execution kind and for no other: the per-line `DEBUG` records EAC-FR-32 writes as stdout and stderr arrive; the two executor activities of EAC-FR-34 — the generated invocation and **the serialized task** — as `DEBUG` records; and the bounded stderr tail excerpt EAC-FR-29 attaches to a record for a run that did not complete. What remains is the `INFO` record at each end of the call and the `WARN` or `ERROR` on every failure path, each naming the vendor, the container, the outcome, the duration, the exit status, and the sizes and truncation of each captured stream — counts and identities, and no content.
    The suppression exists because the caller of this execution kind is held to a stricter rule than this tool's own masking gives it: a reconciliation's records may carry safe path names and counts and **no prompt text, file content, diff hunk, task input, or agent output at all** (per `../core/GRB-graduation-rebase.md` GRB-FR-OHWT), and the task of a semantic-rebase turn carries the captured graduation prompt while its streams carry the specification text the agent is reading and writing. A `DEBUG` floor that a reader can lower, or an excerpt cut from a stream of file contents, would put exactly that material in the session buffer — which is the one place this application's rule about it could be broken without anybody writing a record on purpose.
    **The activity sink is unaffected**, and that is the point of confining the suppression to the log: a sink is the run's own record rather than the application's diagnostic buffer. A caller that supplied an activity sink receives every line and both executor activities exactly as EAC-FR-32 and EAC-FR-34 deliver them, masked on the terms of EAC-FR-29. **Ordinary executions are unchanged in every respect**: a request supplying no semantic-rebase mount writes the same `DEBUG` records, the same executor activities, and the same stderr excerpt it always did, because a loop whose task carries no captured prompt and whose agent writes ordinary work is not what this rule is about.

46. **EAC-FR-43** A task **names the shape its own answer must take**, and the executor supplies that shape. `result_contract` is one identifier of a closed set — `review_verdict` under v1 — and an identifier outside the set, like any undefined field, is a rejection before launch (EAC-FR-07). It names the `ReviewVerdict` of `../ai/GRL-graduation-loop.md` GRL-FR-VIAT and no other shape. A task that names none carries a free-form `result`, so the field constrains nothing for a caller that states no shape. The executor resolves the identifier to a fixed JSON Schema document compiled into the binary, writes that document into the task document as `result_schema` for **every** vendor, and hands it to the vendor descriptor besides. A vendor whose CLI validates an answer against a schema therefore enforces the named shape inside the run (per `../infra/CCP-claude-code-cli-protocol.md` CCP-FR-28); a vendor whose CLI enforces nothing carries the document in the task alone (per `../infra/CDX-codex-cli-protocol.md` CDX-FR-14), which is the same asymmetry EAC-FR-35 already answers the same way — the shape reaches every agent in words it can read, and the vendor that can check it also checks it.
    Each document is **selected by name and never assembled**: it is never derived from the task, never composed from its `input`, never carries project material, and never carries a credential, which is what lets it ride on an argument vector while the task may not (EAC-FR-09). Two turns naming one contract carry byte-identical documents whatever their tasks hold. Like the response contract beside it, it is written into the task document before EAC-FR-08's serialized-task bound is applied, so the document that bound is checked against is the document the agent receives.
    **The executor validates nothing against it.** A returned `result` is bounded by EAC-FR-08 and decoded as the free-form object it has always been, and an answer that does not satisfy the named schema is returned to the caller unrefused. The point of naming a contract is to have the vendor correct the agent **inside** the run; the caller's own validation remains the one authority on what a result means, and a second validator here would refuse after the fact exactly what this exists to stop being refused after the fact.

47. **EAC-FR-44** Every document of the set states **only structural rules the caller's own validation enforces, and none of them more freely**, on the terms `../infra/CCP-claude-code-cli-protocol.md` CCP-FR-07 already sets for the envelope schema. It follows that a rule the document **cannot** state faithfully stays with the caller rather than being approximated. One rule runs the other way, and one only: each object of a document **closes its field set**, which the caller's own validation need not do. An undefined key is the mark of an answer written to a different contract — an agent works with tools of its own, and one of those tools' answers is shaped like this one — and the answer that borrows another contract's field names borrows the name of the field this one reads. Refusing it costs one re-prompt inside the run; accepting it costs the turn, outside it. A field set is closed only where the answer is the caller's own shape: a payload the caller reads through another contract's rules is left open on that contract's terms. The `review_verdict` document admits exactly two answers and nothing else — the verdict object of `../core/GRD-graduation.md` GRL-FR-VIAT with its closed field set, its two `verdict` values, its three `severity` values, and its non-blank `rationale`, `description`, and `correction`; or an `escalate_to_user` request of `ESU-escalate-to-user-tool.md` ESU-FR-19 in place of a verdict (per `../core/GRD-graduation.md` GRL-FR-VBCL) — and it states none of the rules it has no reach over: the stable finding order of `../core/GRD-graduation.md` GRL-FR-VIAT which is a comparison between entries rather than a shape; that each `affected_files` entry is a path the change set holds, which is knowable only from the run's own manifest and is exactly the project material EAC-FR-09 keeps off an argument vector; the readable shapes a proposed response's `summary` and `description` keep, which are counts of words and sentences that a schema states in characters or not at all, on the same terms `../infra/CCP-claude-code-cli-protocol.md` CCP-FR-07 leaves them with the decoder; and that a `success` carries a result at all, which is a key of the envelope around the document rather than of the document. Each remains the caller's to enforce and each remains able to refuse an answer after the turn ends.

48. **EAC-FR-VSNM** A caller may additionally require that a run be **kept**. Where it supplies a `durable_output` sink, the executor hands that sink **every observed activity of a safe kind** (EAC-FR-DWGS), in the order observed, as a `DurableActivity` carrying the instant, the channel, the kind, and the one-line summary. Each activity carries a `record_id` the executor assigns once and repeats on every retry of that same activity, which is what lets a sink refuse a duplicate rather than store one.
49. **EAC-FR-CXUE** The durable sink's **acknowledgement is mandatory**. An activity is not accounted for until the sink answers `ok`, and the executor does not report the call as complete while any activity is unacknowledged. A sink may take its time: the executor applies **bounded backpressure** to the reader by waiting for the answer, and it never drops, truncates, or skips an activity. The activity sink of EAC-FR-32 is unaffected and stays best-effort and non-blocking.
50. **EAC-FR-DUTR** A sink that answers a **typed failure** ends the run's durable delivery there. The executor cancels the container through the path EAC-FR-25 already honours, stops delivering, and returns `DurableOutputFailed` carrying that failure, so the caller learns that the record is incomplete rather than receiving a turn that looks finished over activity nobody kept. It is never launched around and never retried silently.
51. **EAC-FR-FKCN** **Everything a durable sink receives is masked first.** EAC-FR-29's one rule is applied before an activity is handed on, so no credential value, no session identity the executor assigned or was asked to resume, and no login directory in either spelling reaches the sink in any spelling. The executor reads no vendor session-state directory (EAC-FR-31), so no model transcript reaches it either. There is no second rule here and no path out of this tool that is masked on other terms.
52. **EAC-FR-RLIW** The executor **stores nothing itself and knows no run identifier**. It reports what happened; which piece of work the record belongs to is the sink's, exactly as it already is for the activity sink (per `../core/AGV-agent-activity.md` AGV-FR-03). A call supplying no `durable_output` sink is the call it would have been before one existed: the process outcome, the response, the captured streams, and the generated argument vector are identical.
53. **EAC-FR-DWGS** The durable sink receives an activity **only where its kind is a safe kind**: `started`, `message`, `tool_call`, `tool_result`, `command`, `file_change`, `retry`, `usage`, `finished`, `error`, or `diagnostic`. A `finished` activity of the executor channel is delivered after the run ends and before the call is reported as complete (EAC-FR-THUT).
54. **EAC-FR-IRKZ** An activity of the kind `invocation`, `task`, `reasoning`, or `unrecognized` is **never delivered to a durable sink**. `DurableActivity` has no payload field, so the verbatim event, the serialized task, the generated invocation, and every full tool argument and result stay out of it. The activity sink of EAC-FR-32 still receives every kind unchanged.
55. **EAC-FR-ZVRP** Where the durable sink fails, the call returns `DurableOutputFailed` after the container removal of EAC-FR-26 has been tried, whatever the process outcome was. The failure names a code and one message and carries no activity text.
56. **EAC-FR-CPEP** The executor cancels the container for a durable failure through a token **linked to the caller's** token. It never sets the caller's own `cancellation`, so a caller that reads its token afterwards learns only what it decided itself.

## Non-functional requirements

- Nothing here is reachable from the frontend, and no path through this tool reads a Tauri command's arguments, so an agent launch originates only in backend loop code.
- A credential exists in application memory only for the duration of the launch that carries it, is held in a type that neither serializes nor renders in a `Debug` output, and is zeroized when the call ends.
- The full set of Docker parameters and the full set of vendor arguments are each derivable from the descriptors and the named constants without running anything, which is what lets a test assert the rendered vector exactly.
- The executor adds no retry, no backoff, and no schedule of its own. One call is one attempt, and a failure survives no longer than the call that produced it.
- Bounded capture means the executor's memory cost per request is fixed by EAC-FR-08's limits rather than by what the agent chose to print.
- A descriptor carries no image reference and no digest: the image is the project's, resolved per launch, so an image change is a change in that project's committed configuration rather than in this build. The pinned CLI version a descriptor carries is the one its vendor's protocol specification is asserted against, so a vendor upgrade is a change to that specification and to that vendor's descriptor rather than to any call site.
- Each descriptor transcribes exactly one vendor specification and reads nothing from the other. There is no shared vendor fragment, no common flag constant, and no code path that treats a value from one vendor's grammar as valid in the other's, so the two protocols cannot drift into each other.
- What the two vendors offer is not symmetrical, and nothing here compensates for the difference. One validates the response envelope against a schema before returning it and one does not; one lets the executor assign a session identifier and one only reports its own; one authenticates from the environment and one from a mounted directory. A caller receives the same `AgentExecution` shape either way, which is normalization of the result and not of the reliability behind it. The one thing that *is* symmetrical is what each agent was told: EAC-FR-35's contract reaches both, so the vendor that validates nothing has still been given the rules in words. That equalizes the instruction and not the enforcement — being told a contract is weaker than being held to one, and the vendor without a schema stays the likelier source of an `invalid_structured_output`.
- Both pinned vendors load configuration from the mounted working tree — hooks, tool policies, and server declarations a repository carries are read without a trust prompt (`../infra/CCP-claude-code-cli-protocol.md` CCP-FR-22, `../infra/CDX-codex-cli-protocol.md` CDX-FR-26). The container is what bounds that, which is why EAC-FR-13's mount, port, and privilege limits are the security boundary rather than any vendor flag.
- The tool holds no per-call state between calls and is cheap to construct, in keeping with `TLC-tool-conventions.md` TLC-FR-15.
- Observation costs a run nothing it can fail on. A sink that panics, a log buffer that has evicted everything, and a caller that supplied no sink at all each leave the run's outcome unchanged, because the observer sits between the runtime and every reader rather than on the path the result takes.
- A durable sink is the one thing that may slow a run: backpressure is applied to the reader while the sink answers, and a caller that supplies none pays nothing for the mechanism.
- The executor stores no activity of its own and knows no run identifier. It reports what happened; which piece of work that belongs to is the caller's, which is what keeps one loop's narration from ever reaching another's.
