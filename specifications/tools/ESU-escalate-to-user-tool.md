# Escalate to user tool

**Spec code:** `ESU`

## Intent
The request a graduation turn raises when it cannot decide without something only the author knows. A graduation run is unattended by design — the author started it and went back to writing the next prompt — so a turn that hits a genuine fork has no one to turn to and two bad options left: guess, and hand back work nobody vouched for, or approve provisionally, which is guessing with a better name. This request is the third option. Raising it records the questions against the run and stops the run there, in a durable state that survives an application restart and keeps blocking the project's queue, until the author answers from the surface that shows them the run. It is deliberately not a comment: there is no conversation to append to, nobody is watching a thread, and the answers have to come back as structured data the next execution turn can carry. One request carries the whole of what the turn is stuck on — up to eight related questions, each with its own proposed responses — because a turn blocked on two things learns nothing from being told one of them, and a run that stopped twice would ask the author to come back twice for one decision. Out of scope: deciding whether a question is worth asking, which is the raising turn's judgement; presenting the questions and collecting the answers, which are `../ui/GRU-graduation-runs.md`'s; and delivering those answers to the execution agent, which is `../ai/GRL-graduation-loop.md`'s next task input.

## Contract surface
One escalation request, raised by an execution turn and by nothing else. It is no `rig` portable tool, is registered as no Tauri command, emits no Tauri event, and is unreachable from `src/**`.

It reaches the run by **two routes**, and this spec owns the shape and the rules both are held to. The **result form** is an `escalate_to_user` request a turn returns in its structured result **in place of a verdict**, which is how a **Review** turn escalates (per `../ai/GRL-graduation-loop.md` GRL-FR-VBCL). The **envelope form** is an `escalation_required` response carrying the same `reason` and the same questions, which is how an authoring, a validation, a semantic-rebase, and an implementation turn escalate (per `EAC-execute-agent-cli.md` EAC-FR-36). Both record one `GraduationEscalation` through the same `record_escalation` and are answered by the same operation on the same terms. What differs is where the request is written and, for the envelope form alone, whether the clarification judgement answers part of it first (ESU-FR-18).

### The request
```
EscalateToUserRequest {
  kind?: "plan_update",    // envelope form alone; a plan update of an apply run (ESU-FR-VTAZ)
  reason: string,          // required; why the run cannot proceed
  questions: [             // required; 1 to 8, in the order they are to be answered; 0 to 8 for a plan update
    {
      question: string,    // required; one thing asked
      options: [           // optional; 0 to 3 proposed responses
        {
          answer:      string,   // required; the value submitted when this is chosen
          summary:     string,   // required; guidance: one sentence, 5 words
          description: string    // required; guidance: 2 sentences, 12 words
        }
      ]?
    }
  ]
}
```

What each field carries:

- `reason` — why the turn cannot finish without an answer, in a sentence or two, saying what it found and what the decision turns on, so the person reading it understands the questions without going looking.
- `questions` — *"Everything you are stuck on, between one and eight entries. Ask them all here: the run stops once and comes back once, so a thing you leave out is a thing you cannot ask about later."*
- `questions[].question` — *"One question, written as you would put it to a colleague. Ask one thing; a question with three parts comes back with one answer to whichever part they read last."*
- `questions[].options` — *"Up to three concrete responses to this question, if it has them — for example the two paths a requirement could live in. Leave it out where no fixed choice fits; they may answer in their own words either way."*
- `questions[].options[].answer` — *"The answer itself, as it would be given. This is the value that reaches the next turn when they choose this response."*
- `questions[].options[].summary` — *"A label for this response. Aim for one sentence of five words or fewer. It is what they read first, and it is sent with the answer."*
- `questions[].options[].description` — *"What choosing this response means. Aim for two sentences and twelve words altogether. It is shown to them and never sent anywhere."*

### Output
The request has no return value. The run stops where the turn left it, and the answers reach the **next** execution turn rather than the one that asked (ESU-FR-13).

### Validation failures
A request breaking any of these is refused whole and records nothing (ESU-FR-17); what the raising turn is told is `refusals.md`'s text for the form it used.

- **not escalatable now** — the run is in no state to be paused for a question.
- **already escalated** — a question is already waiting on the person who started this run.
- **blank reason or question** — names whether the reason was empty or which question's text was, and what it is for.
- **wrong number of questions** — names how many were supplied and that between one and eight are accepted, or between none and eight for a plan update.
- **too many responses** — names which question carried more than three proposed responses.
- **invalid proposed response** — names which question's response was refused and which of its three fields is blank: `answer`, `summary`, or `description`.
- **too long** — names which value exceeded its limit and what the limit is.

## Functional requirements
1. **ESU-FR-03** The escalation is raised by a **graduation execution turn** and by nothing else. No conversational turn can raise one (per `../ai/CVL-conversation-loop.md` CVL-FR-08), no model-facing step of the graduation loop can (per `../ai/GRL-graduation-loop.md` GRL-FR-EKXT), and no operation the frontend reaches can, so the only thing that pauses a graduation run with a question is a turn doing that run's work. The run the escalation is recorded against is the run whose turn raised it, carried by the dispatch rather than named in the request, so a turn cannot escalate against a run it is not working on.
2. **ESU-FR-05** A valid request records **one** `GraduationEscalation` through `../core/GRD-graduation.md`'s `record_escalation` carrying the `reason`, every question in the order it was given with its own proposed responses as given — an empty option list where none was supplied — the stable position the application assigned each question (ESU-FR-16), the `origin` of the route that raised it, and the instant it was raised; it persists the run's checkpoint and moves the run to `awaiting_user_decision` (per `../core/GXD-graduation-execution.md` GXD-FR-HGSU). Eight questions are one escalation and one decision rather than eight of either. The state is durable: it survives an application restart, keeps blocking the project's queue, and is left only by the author answering every question or discarding the run.
3. **ESU-FR-08** At most one escalation is outstanding per run, and one request raises at most one. A request made while the run already holds an unanswered escalation is the **already escalated** failure and records nothing, whichever route raised the one already standing. The original escalation is kept whole and untouched by the refused attempt, so the author is never asked two sets of questions about one run and the answers they give are never ambiguous about which set they answer.
4. **ESU-FR-10** `reason` is required and must be non-blank once trimmed. `questions` is required and must hold between 1 and 8 entries, or between 0 and 8 for a plan update (ESU-FR-VTAZ), each carrying `question` text that is non-blank once trimmed and between 0 and 3 proposed responses; `options` defaults to no options when absent, an empty list meaning that no fixed response suits. Every proposed response must carry an `answer`, a `summary`, and a `description`, each non-blank once trimmed. A count of words or sentences refuses nothing. A blank reason, a blank question text, a question count outside 1 through 8, a question carrying more than 3 responses, and a response with a blank field are each the matching retryable `InvalidArgs` refusal of the contract surface, naming which question and which field. Nothing here is dropped and salvaged: a response the author would read as a choice is either offered as the model wrote it or refused so the model can write it again, and a whole call refused costs one round while a silently trimmed one costs a decision taken on less than was meant.
5. **ESU-FR-11** Every value is bounded by a named limit and a value exceeding one is the retryable `InvalidArgs` **too long** refusal naming which limit it exceeded and which question it was on: in Unicode code points, `reason` 4096, each `question` 2048, each proposed response's `answer` 512, its `summary` 128, and its `description` 256. The bounds exist because the recorded escalation is persisted in the run's checkpoint and rendered in the run surface, and because the questions and the answers both travel to the execution agent inside a structured input already bounded by `EAC-execute-agent-cli.md` EAC-FR-08 — an unbounded question set would be refused at dispatch, after the run had already stopped for it.
6. **ESU-FR-12** The recorded escalation is what the author reads and answers, verbatim. The application composes no prose of its own around it, adds no framing, reorders nothing, and rewrites nothing the raising turn wrote; `../ui/GRU-graduation-runs.md` renders every question and every proposed response's `summary` and `description` as they were recorded, and the `reason` as recorded inside a disclosure that is closed by default (`../ui/GEA-graduation-escalation-answering.md` GEA-FR-SXXB).
7. **ESU-FR-13** The answers do not come back to the turn that asked, which ended before there was one and is never resumed, retried, or re-entered. `../core/GRD-graduation.md`'s `answer_graduation_escalation` records them as one ordered set covering every recorded question, and they reach the execution agent in the next task's structured input. They also stay in the run's decision ledger, which every later turn of the run carries (per `../core/GXD-graduation-execution.md` GXD-FR-NWSL and GXD-FR-BTIN).
8. **ESU-FR-15** Every escalation emits through `../core/LGC-logging.md`'s internal API under the `ai` and `backend` domains together: an `INFO` record when an escalation is recorded, naming the run id, the origin, how many questions it carried, and how many proposed responses each of them carried, and a `WARN` record when a request is refused, naming the run id, the origin, and the reason. The run id is the one request-adjacent value these records name, a record about a paused run being unfollowable without it. No record carries the `reason`, a question's text, a proposed response's `answer`, `summary`, or `description`, or any of the author's eventual answers.
9. **ESU-FR-16** The application assigns each question a **stable position** in the order the model wrote them, and that position is what every later act names. The question text is never an identifier: two questions may read alike, a text is long enough to mistype, and an answer matched by text would attach to whichever question happened to match first. The positions are recorded with the escalation, are what `../ui/GRU-graduation-runs.md` submits an answer against (`../ui/GEA-graduation-escalation-answering.md` GEA-FR-DNBI), and are what the execution agent receives each answer under (per `../ai/GRL-graduation-loop.md` GXD-FR-XPUR). The model neither supplies a position nor sees one: it writes an ordered list, and the ordering is the whole of what it decides.
10. **ESU-FR-17** A refused request records **nothing at all**. One malformed question or one malformed proposed response refuses the whole request rather than recording the questions that were well formed, so the run is never paused on a question set smaller than the turn was stuck on and the author is never shown half a decision. What the turn is told is the refusal text of `resources/prompts/graduation/refusals.md` for the form it used, beside the application's own account of which rule the request broke.
11. **ESU-FR-18** Authoring, validation, implementation and semantic-rebase turns raise the envelope form, and a Review turn the result form (ESU-FR-19). Both record one escalation. The clarification judgement takes the questions of an authoring, validation or implementation turn first, and the author gets what it leaves. It takes no Review or semantic-rebase question, no question of a plan update (ESU-FR-VTAZ), and none raised while the checkpoint holds `check_gate` (`../ai/GRL-graduation-loop.md` GRL-FR-LNIZ).
   - *Why:* Those questions are what the prompt and the specifications leave open, or what only the author can permit, so the judgement has nothing to answer them from.
12. **ESU-FR-19** The **result form** is how a Review turn escalates, and it is this escalation in every respect but where it is written. A Review turn may return an `escalate_to_user` request in its structured result **in place of** a `ReviewVerdict`: the same `reason`, the same one to eight questions in the order it asked them, and the same up-to-three proposed responses per question, each carrying the `answer`, `summary`, and `description` the envelope form carries. The application validates it on **exactly the rules of the envelope form** — the question count, the shape of each proposed response, the assigned stable positions of ESU-FR-16, and the at-most-one-outstanding rule of ESU-FR-08 — and a request that fails any of them is refused as a Review result the application could not read, on the terms `../core/GRD-graduation.md` GRL-FR-TVXI sets, rather than half-recorded. A valid one records **one** `GraduationEscalation` through the same `record_escalation`, with the origin `review_agent`, and moves the run to `awaiting_user_decision` durably, exactly as ESU-FR-05 does for the envelope form.
    **A successful escalation is read instead of a verdict and never beside one.** Where the same result carries an `escalate_to_user` request and a `ReviewVerdict` together, the request is recorded and **the verdict is not read at all** — not validated, not stored, not treated as `ready`, and not treated as `revise` — because a review that has asked the author something has stopped deciding, and a verdict beside the question is a decision taken without the answer. The Review phase ends there (per `../ai/GRL-graduation-loop.md` GRL-FR-VBCL), no implementation iteration starts, and no publication is offered.
    The answers come back the way they come back everywhere: `answer_graduation_escalation` records the author's complete ordered set for every recorded question (ESU-FR-13, per `../core/GXD-graduation-execution.md` GXD-FR-BJYT), and only then does the Review resume — as **one fresh Review turn** carrying the escalation's own reason and positioned questions beside those answers (per `../core/GRD-graduation.md` GRL-FR-VBCL). Nothing resumes on a partial answer set, nothing resumes on its own, and the questions and what the author said stay readable together on the run afterwards (ESU-FR-12).
13. **ESU-FR-VTAZ** An envelope escalation that carries `kind: "plan_update"` is a **plan update** of an apply run (per `../core/OPU-openspec-plan-updates.md` OPU-FR-RMZN). It holds 0 to 8 questions, and every other rule and limit of ESU-FR-10 and ESU-FR-11 holds for it. It records no `GraduationEscalation`: `../core/OPU-openspec-plan-updates.md` records it in the change discussion.
14. **ESU-FR-ATVP** An envelope escalation with no `kind` is an ordinary escalation. The result form carries no `kind`, so a Review turn gives no plan update; an apply review marks a `plan` finding in its verdict instead (per `../core/OPU-openspec-plan-updates.md` OPU-FR-EPXL).

## Non-functional requirements
- The request is one durable write and one state transition; it reaches no network, no model, and no container, so a question costs the run a write rather than a turn.
- The recorded escalation carries no credential and no part of one, and nothing about it is reachable by a model other than the one that wrote it.
- A question outlives everything transient: the raising turn's session is not resumed, and the escalation is in the run record, so an author answering a week later answers the questions that were actually asked, in the order and with the proposed responses they were asked with.
- Nothing here posts an operating-system notification of its own. Calling the author back to the run is a raise the run surface makes (per `../ui/GRU-graduation-runs.md` GRU-FR-BLSS), on the ordinary terms of `../ui/NTF-notifications.md`.
