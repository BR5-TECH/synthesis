# Propose draft changes tool

**Spec code:** `PDC`

## Intent
The tool an agent reaches for when it can see how the prompt of the draft under discussion would be better and wants the author to decide. It **proposes** a set of changes to that prompt — each one naming the exact text it replaces and the text that should stand in its place — and ends the agent's turn there. The changes are recorded beside the draft and posted into the conversation as an ordinary comment by the agent, carrying its reasoning as prose and a reference the author opens. The author decides each change on its own, with a word of feedback if they have one, and that decision brings the agent back with the whole conversation in front of it. The shape is the shape of a colleague marking up a document: here is what I would change, here is why, and each of them is yours to take or leave — rather than an assistant that edits the document and tells you afterwards. **Nothing this tool does changes the draft's prompt.** A proposed change is material sitting beside the draft until the author accepts it, and the write that lands it is one the author performs from the surface that shows it to them (`../ui/DCR-draft-change-review.md`); an agent whose changes are all declined has cost the draft nothing but a comment. Out of scope: proposing to any draft but the one the turn was asked about, since the tool is bound to that draft at construction and accepts no argument naming another; proposing to an artifact already in the project, which is not a draft and which this tool refuses; proposing to anything but that draft's one prompt, a draft holding no other file; naming a change by line number or by offset, neither of which this tool accepts — a change names the text it changes; waiting for the decision, since the call returns as soon as the changes are recorded and holds no timer, watcher, or open request; applying an accepted change, which is `../core/DCP-draft-change-proposals.md`'s; and rendering the changes, which is `../ui/DCR-draft-change-review.md`'s.

## Contract surface
One tool, conforming to `TLC-tool-conventions.md` in full. It is attached to the turns whose origin kind is a draft conversation and to no others, by `../ai/CVL-conversation-loop.md` (CVL-FR-08), and has no Tauri command, event, or frontend reach of its own.

### The tool
`propose_draft_changes` — a `rig` portable tool. Like `AUC-ask-user-comment-tool.md`'s and unlike the read-only tools of this group, it is **constructed per turn** (per TLC-FR-15), its constructor taking the draft the turn is about, the origin of the conversation the turn belongs to, and the agent participant that turn answers as, so the draft it can propose to and the conversation it can post into are both fixed before the model composes a single argument.

### The description
The fixed text the model reads (per TLC-FR-05):

> Propose changes to the prompt of the draft under discussion, when you can see how its text would be better and want the author to decide. A draft is one prompt, so this is the one file there is to propose changes to. Reach for it instead of describing the improvement in prose, and instead of asking permission to make one. Pass a list of changes. Each one names, in `before`, the **exact text it changes**, copied character for character from the prompt as you read it, and gives in `after` the text that should stand in its place. To insert new text, give `after` alone and put the exact text it follows in `after_text`. To delete, give `before` alone. Copy enough surrounding words into `before` that the text you name appears **once** in the prompt; if it appears more than once the call is refused and you are asked to include more. Say why the changes are worth making, in a sentence or two as you would put it to a colleague. Your proposal is posted as your own comment in this conversation and your turn ends there — this call brings you no answer back, and you will be asked again later with the author's decisions, and whatever they said about them, in front of you. The author decides each change separately, so send the changes you believe in together rather than holding some back. Offer the changes for the whole prompt one time, rather than a small improvement each time you read it. When you are answering about one change the author asked you to reconsider, name that change in `revises` and send **only** the one change that replaces it; the rest of what you would change waits until the author has decided the changes already standing. It reaches only the draft you were asked about, and it changes nothing — the prompt is not rewritten unless the author accepts.

### Arguments
```
ProposeDraftChangesArgs {
  path:      string,     // required; draft-relative path of the prompt
  rationale: string,     // required; why the changes are worth making
  revises:   string?,    // optional; the id of a change being replaced
  hunks: [               // required; one or more, in the order they should be read
    {
      kind:       "replace" | "del" | "add",   // optional; the fields decide
      before:     string?,   // the exact existing text; required but for "add"
      after:      string?,   // the exact new text; required but for "del"
      after_text: string?,   // for "add": the exact text the new text follows
      note:       string?    // optional; one sentence about this change alone
    }
  ]
}
```

Their descriptions in the parameter schema (per TLC-FR-06):

- `path` — *"The draft-relative path of the draft's prompt, which is the one file a draft holds and the only thing you can propose changes to."*
- `rationale` — *"Why the changes are worth making, in a sentence or two as you would put it to a colleague. The author reads this as your comment."*
- `revises` — *"The id of a change you were asked about, when you are replacing it with a better one. A call that names a change carries exactly one change — the one that replaces it. Leave it out when you are proposing something new."*
- `hunks` — *"The changes, in the order they should be read. In each, `before` is the exact existing text you are changing, copied character for character from the prompt, and `after` is what should stand in its place. Copy enough surrounding words into `before` that it appears only once in the prompt. For an insertion give `after` and put the exact text it follows in `after_text`; for a deletion give `before` alone."*

### Output
Data (per TLC-FR-08): `{ proposed: true }`. The turn ends on the call that proposed (per `../ai/CVL-conversation-loop.md` CVL-FR-15), so no further model call reads this value — it is what the exchange records rather than anything the model acts on.

### The comment
What the author reads. The `rationale` as the model wrote it, and nothing else — no identifier, no path, no preamble, and no closing line:

```
The Intent runs to four sentences of scope-setting before it
says what the tab is. I have led with the tab and folded the
scope into the last sentence.
```

Beside it the comment carries exactly one attachment, of the `proposal` kind (per `../core/CMS-comments-storage.md` CMS-FR-60), which is what the rail renders as the control that opens the diff (per `../ui/CMT-comments.md` CMT-FR-48). The attachment carries the proposal's identity and no part of its content, so the comment is a line of prose and a reference however large the file being proposed.

### Refusals
- **no open project** — the shared refusal of `TLC-tool-conventions.md`: kind `NotFound`, not retryable.
- **not a draft conversation** — kind `PermissionDenied`, not retryable: *"This conversation is not about a draft, so there is nothing here to propose a change to. Say what you would change instead; asking again will not succeed."*
- **no such file in the draft** — kind `NotFound`, retryable: names the path and says the draft holds no file at it.
- **no changes** — kind `InvalidArgs`, retryable: *"Pass at least one change. An empty proposal has nothing for the author to decide."*
- **text not found** — kind `InvalidArgs`, retryable: *"The text you gave in `before` is not in the prompt. Copy it character for character from the prompt as you read it."*
- **text is not unique** — kind `InvalidArgs`, retryable: *"The text you gave in `before` appears more than once in the prompt. Include more of the words around it so it names one place."*
- **changes overlap** — kind `InvalidArgs`, retryable: *"Two of your changes cover the same text. Combine them into one change."*
- **blank rationale** — kind `InvalidArgs`, retryable: *"Say why the change is worth making. The author reads this beside the diff."*
- **no change proposed** — kind `InvalidArgs`, retryable: *"Every change you passed leaves the text as it is, so there is nothing to decide."*
- **a proposal is already pending** — kind `PermissionDenied`, retryable: *"A proposed change to this draft is still waiting on the author. Wait for their decision before proposing another."*
- **conversation locked** — kind `PermissionDenied`, not retryable: *"This conversation is locked and takes no further comments, so nothing was proposed and no decision is coming. Answer with what you already have; proposing again will not succeed."*
- **no such change to revise** — kind `InvalidArgs`, retryable: *"The change you named is not one of the changes still awaiting the author. Propose a new change instead."*
- **more than one change beside a revision** — kind `InvalidArgs`, retryable: *"You named a change to replace, so send only the one change that replaces it. Wait for the author to decide the changes already standing before you propose the rest."*
- **could not record** — kind `Other`, retryable: *"The proposed change could not be recorded."*

### Side effects
Declared in full (per TLC-FR-17). One successful call that records a proposal produces **exactly one proposal** and **exactly one comment**, and the tool performs neither write itself: it calls `../core/DCP-draft-change-proposals.md`'s internal recording path (DCP-FR-05), which writes the changes under the draft's own folder and appends the comment through `../core/CMS-comments-storage.md`'s agent write path (CMS-FR-41) as one act, so the record and the reference to it can never disagree. **The draft's prompt is not modified and its version history gains nothing**, no file of the project is touched, no repository state is changed, and no other store is mutated. A successful call that **revises** a change (per PDC-FR-GMWR) produces neither: it replaces one change of the proposal already standing, so the folder gains no file, the conversation gains no comment, and the count of proposals the draft holds does not move. The author reads such a call in the change itself, which is where they asked about it. A refused call produces neither the proposal nor the comment.

## Functional requirements
 1. **PDC-FR-01** The tool exists as a `rig` portable tool named `propose_draft_changes` and conforms to `TLC-tool-conventions.md` in full — its name, description, parameter schema, output shape, refusal shape, and logging are that spec's rules applied to this tool. It is one of the tools of TLC-FR-17 that declare a side effect rather than a read-only posture, and its side effect is the one declared in the contract surface and nothing beyond it.
 2. **PDC-FR-02** Its `description()` returns the fixed text of the contract surface, compiled into the binary, and its `parameters()` returns the JSON Schema for the three documented arguments with the documented parameter descriptions (per TLC-FR-05). Neither varies by draft, by conversation, by agent, or by project, so two agents holding this tool were offered byte-identical definitions of it however different the drafts they are looking at.
 3. **PDC-FR-03** The tool proposes to the draft of the turn that holds it and accepts no argument naming a draft, a conversation, a thread, a participant, or a path outside that draft. Its constructor binds it to that turn's draft, origin, and agent participant (per TLC-FR-15), so no argument a model composes can reach a draft it was not asked about, and an instance outlives no turn.
 4. **PDC-FR-04** Each hunk names the text it changes rather than a position in the file: `before` is the exact existing text and `after` is what stands in its place. The tool interprets no argument as a line number, an offset, or an instruction about a region of the file, and it merges nothing against what the file holds.
 5. **PDC-FR-05** `path` is draft-relative and must name **the draft's own prompt**, which is the one file a draft holds (per `../core/DRS-draft-storage.md` DRS-FR-11). Any other path — one naming nothing, one naming a nested path, or one escaping the draft's own storage — is the retryable `NotFound` refusal of the contract surface and nothing is recorded. This tool proposes a new version of that prompt and never the creation of a file, so a draft's file set is unchanged by every route through it.
 6. **PDC-FR-06** A turn whose origin kind is not a draft conversation refuses with the **not retryable** `PermissionDenied` of the contract surface, and its message says a further call will not succeed (per TLC-FR-11). No argument the model could compose would make an artifact into a draft, and an agent told otherwise would spend its remaining calls proposing into a conversation that cannot hold a proposal. In practice this is a refusal a model is not offered the chance to make, the tool being attached to draft origins alone (per `../ai/CVL-conversation-loop.md` CVL-FR-08); it exists because a tool's refusals are its contract rather than its caller's, and a set of tools selected elsewhere is not a guarantee this tool may rest on.
 7. **PDC-FR-07** An empty `hunks` list, a `rationale` that is empty or blank once trimmed, and a set of hunks that together leave the text byte-identical to what the file holds are each the retryable `InvalidArgs` refusal named for them in the contract surface, and nothing is recorded.
 8. **PDC-FR-08** A call carrying no `revises` made while a proposal on that draft is not yet resolved (per `../core/DCP-draft-change-proposals.md` DCP-FR-04) is the **retryable** `PermissionDenied` of the contract surface and nothing is recorded. A draft carries at most one undecided proposal at a time, whichever agent made it, so the author is never asked to hold two competing rewrites of the same working material in their head. It is retryable because the author's decision is exactly what would make a further call succeed. The message says as much in the terms the model has to act on: that a change it proposed earlier is still waiting on the author, that it should say so plainly in its reply, and that it must not describe the change this call carried as proposed, because nothing was recorded. A model that answers this refusal by writing that it has just submitted the change tells the author something untrue and leaves them waiting for a proposal that does not exist — while the one they have not decided is the very thing holding the slot.
 9. **PDC-FR-09** A conversation whose folded state is locked (per `../core/CMS-comments-storage.md` CMS-FR-17) is the **not retryable** `PermissionDenied` of the contract surface, and neither the proposal nor the comment is produced: a proposal nobody can be told about is a proposal nobody will decide, so the two are recorded together or not at all (PDC-FR-11).
10. **PDC-FR-10** The tool records and returns. It waits for no decision, holds no timer, opens no watcher, and leaves no request outstanding, so TLC-FR-16 holds for it unchanged: the author's decision reaches the agent as a later turn rather than as this call's result (per `../core/AGC-agent-conversations.md` AGC-FR-29).
11. **PDC-FR-11** A successful call produces the proposal and the comment as **one act** through `../core/DCP-draft-change-proposals.md`'s recording path (DCP-FR-05), and a failure of either produces neither: a call that could not append the comment leaves no change on disk, and a call that could not write the changes appends no comment. Any such failure is the retryable `Other` refusal of the contract surface.
12. **PDC-FR-12** The comment's body is the `rationale` as the model wrote it, less its citation markers (per `../ai/CVL-conversation-loop.md` CVL-FR-VSSU), and nothing besides — no path, no identifier, no marker, no machine-readable field, and no instruction to the author about how to decide. What makes the change reachable is the comment's one `proposal` attachment (per `../core/CMS-comments-storage.md` CMS-FR-60), which the rail renders as a control (per `../ui/CMT-comments.md` CMT-FR-48); the prose beside it reads as a colleague's note and nothing about it says a tool composed it.
13. **PDC-FR-13** The comment is appended with the turn's agent participant — its agent id, its nickname as the handle, the model it runs as, and its title as the registry holds it at the moment of the append (per `../core/CMS-comments-storage.md` CMS-FR-65) — which is the same participant shape a delivered answer is appended with (per `../core/AGC-agent-conversations.md` AGC-FR-16). The fold, the rail, and the Comments panel therefore read a proposal's comment exactly as they read any other comment of that conversation.
14. **PDC-FR-14** A successful call returns the data object of the contract surface. It composes no sentence about what it did (per TLC-FR-08), and it returns neither the proposal's identity nor any part of the changes — the model has nothing further to do with either, its turn having ended.
15. **PDC-FR-15** A refusal is not a turn's failure (per `../ai/CVL-conversation-loop.md` CVL-FR-14) **and does not end the turn**: a call that recorded nothing leaves the loop running, so an agent whose proposal was refused corrects the argument, proposes a different file, or answers with prose instead. Only a call that actually recorded a proposal ends the turn (per CVL-FR-15).
16. **PDC-FR-16** With no project open the tool produces the shared no-open-project refusal (per TLC-FR-13), there being no draft to propose to.
17. **PDC-FR-17** The tool holds no state between calls and no state of its own beyond the turn its constructor bound it to (per TLC-FR-15). Two turns hold two instances and neither observes the other's call, so two agents asked about one draft each reach their own instance and neither's proposal is attributed to the other — which the one-pending rule of PDC-FR-08 then decides between.
18. **PDC-FR-18** Each call emits under the `ai` and `backend` domains (per TLC-FR-14): an `INFO` record when a proposal is recorded, naming the tool, the draft, and the `path`; and a `WARN` record when it refuses, naming the tool, the draft, the reason, and — where the refusal is about one hunk of several (per PDC-FR-TZKQ) — that hunk's **place** in the list the model sent. The place is a count of what the model composed and no part of what it wrote, on the terms every other field here keeps; without it a record saying eight hunks were sent and one named text the prompt does not hold cannot tell a model that is one hunk out from one that invented the whole set. The draft is named because a record that cannot be tied to one cannot be followed, and it is not an argument — it was bound at construction rather than composed by the model. `path` is this tool's one **loggable argument** (per TLC-FR-14), a record about a proposed rewrite being unfollowable without saying which file was rewritten; it is bounded to the length a draft-relative path can take, so no value a model composes grows a record past `../core/LGC-logging.md`'s per-record ceiling (LGC-FR-08). **No record carries the `content`, the `rationale`, any part of the comment's body, or any part of the prompt being replaced.**
19. **PDC-FR-19** The tool reaches no network and touches no credential (per TLC-FR-18): recording a proposal is a local write and a local append, and nothing about a proposal is sent anywhere by this tool. A proposal stays in the checkout that recorded it (per `../core/DCP-draft-change-proposals.md` DCP-FR-02), and this tool commits nothing.

20. **PDC-FR-TZKQ** Every hunk's `before` is resolved against the prompt before anything is recorded (per `../core/DCP-draft-change-proposals.md` DCP-FR-JGCD). Text that is not in the prompt, text that occurs more than once, and two hunks that resolve to overlapping ranges are each the retryable `InvalidArgs` refusal named for them, and nothing is recorded. Each of the three names the **place** of the hunk it is about, as the model counted the list it sent — *Change 3 of 8* — where two hunks overlap being the later of them. The place is what makes the refusal correctable: the sentence alone names the kind of mistake, and a model told only that some text was not found can send the same eight hunks again and no more. A failure that is about none of the hunks carries **no place at all** rather than the first, because a caller sent to correct a hunk that is not wrong corrects nothing and calls again.
    - *Why:* This catches a model that invented the text it claims to be changing, while the model can still correct it.
21. **PDC-FR-VKMR** A hunk's kind is read from the fields it carries. `before` with `after` is a replacement, `before` alone is a deletion, and `after` with `after_text` is an insertion. A `kind` the model names that its fields contradict does not override them.
    - *Why:* Acceptance applies the fields, so a record that kept the named kind would show the author a change the draft never takes.
22. **PDC-FR-GMWR** `revises` is read for what it can mean on the draft as it stands. Where the draft holds a standing proposal and `revises` names one of its changes the author has still to decide, the call replaces that one change in place, keeping its id and its position (per `../core/DCP-draft-change-proposals.md` DCP-FR-XDRV), and it carries exactly one hunk — a call carrying more is the retryable `InvalidArgs` refusal of the contract surface that names the correction, because which of several changes was meant to replace the one named is a question only the model can answer. Where the draft holds a standing proposal and `revises` names no change of it, or names one already decided, it is the **no such change to revise** refusal, which the model corrects by naming a change that is still awaiting the author. Where the draft holds **no** standing proposal at all, there is no change for the field to have named, so it is ignored and the call is an ordinary new proposal (per TLC-FR-07). A model that fills the field by mistake can therefore still propose: no state exists in which every call it makes is refused for a change that is not there. A revision is placed against the prompt exactly as a recording is (per PDC-FR-TZKQ), so it refuses in the same words for the same mistakes: a replacement naming text the prompt does not hold is the **text not found** refusal rather than a name that resolved to nothing, the two being told apart because their corrections are opposites — copy the text again, against name a change that is still there.
## Non-functional requirements
- The `rationale` is the only text in this group besides `AUC-ask-user-comment-tool.md`'s question that a person reads, and the same inversion applies: the tool composes none of it, because every byte it added would read as machinery in a conversation that should read as prose. The diff carries the substance; the rationale carries the reason.
- A call costs one file write for the changes, one for the record, and one line of I/O through the conversation's own append path.
- The changes are written to disk rather than held in memory or carried in the comment, so a proposal against a large file costs the conversation a line and the folder a file, and folding the thread never decodes a document.
- Nothing in this tool requires network access.
- The description is written so that a model reading every tool description in this group can tell them apart on their first sentences: this one offers the author a rewrite of a draft file, `PPC-propose-prompt-changes-tool.md`'s offers a rewrite of a prompt the project already holds, `AUC-ask-user-comment-tool.md`'s asks the author something, `RFT-read-file-tool.md`'s reads a file it is given the path of, `SPS-specification-search-tool.md`'s finds which specifications bear on a topic, and the three skill tools answer about skills.
- A proposal the author never decides costs nothing and holds nothing open: the call returned when it recorded, and what became of the turn is `../core/AGC-agent-conversations.md`'s affair rather than this tool's. What it does cost is the draft's one pending slot (PDC-FR-08), which is a decision the author can always make.
- The tool is constructed per turn rather than once for the application. A construction is three values copied into a struct, so the cost is nothing beside the model call the turn is about to make.
