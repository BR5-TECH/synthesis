# Propose diagram changes tool

**Spec code:** `PDM`

## Intent
The tool an agent reaches for when it can see how a **Mermaid diagram** in the document under discussion would be better and wants the author to decide. The document is the prompt of a draft, or a prompt or a project document that the project already holds. The tool **proposes** changes to diagrams — a change of one diagram, the addition of one, or the removal of one — and ends the agent's turn there. A change to a diagram is not a change to text. The author must compare two drawings and not two pieces of source, so a diagram change is a **diagram hunk** of the proposal of the file (`../core/DCP-draft-change-proposals.md`, `../core/PCP-prompt-change-proposals.md`), which the review draws as a diagram with a button that opens a side-by-side comparison of the old drawing and the new drawing (`../ui/DCR-draft-change-review.md`, `../ui/PCR-prompt-change-review.md`). The text tools (`PDC-propose-draft-changes-tool.md`, `PPC-propose-prompt-changes-tool.md`) never carry a diagram change, and this tool never carries a text change. A diagram hunk joins the one open proposal of the file, or opens the proposal where none is open, so the author never holds two proposals of one file. The agent can change and withdraw the diagram hunks that it offered, with the update rules of the existing tools. A diagram is named by its **current source**, because a fence has no identity of its own, and the tool refuses a new source that is not valid Mermaid while the agent can still correct it. **Nothing this tool does changes the file.** A diagram hunk is material beside the file until the author accepts it. Out of scope: proposing to any file but the one the turn was asked about, since the tool is bound to the conversation at construction; proposing to an OpenSpec change, a note, or a file that is neither a prompt nor a project document; a change of a CALM fence; a change of text, which is the text tools'; naming a diagram by a line number or an offset; waiting for the decision; applying an accepted hunk, which is `../core/DCP-draft-change-proposals.md`'s and `../core/PCP-prompt-change-proposals.md`'s; and rendering the hunks and the comparison, which are `../ui/DCR-draft-change-review.md`'s and `../ui/PCR-prompt-change-review.md`'s.

## Contract surface
One tool, conforming to `TLC-tool-conventions.md` in full. It is attached to the turns whose origin kind is a draft conversation or an artifact conversation and to no others, by `../ai/CVL-conversation-loop.md` (CVL-FR-08), and has no Tauri command, event, or frontend reach of its own.

### The tool
`propose_diagram_changes` — a `rig` portable tool. Like `PDC-propose-draft-changes-tool.md`'s and `PPC-propose-prompt-changes-tool.md`'s it is **constructed per turn** (per TLC-FR-15), its constructor taking the origin of the conversation the turn belongs to and the agent participant that turn answers as, so the file it can propose to and the conversation it can post into are both fixed before the model composes a single argument. On a draft origin the file is the draft's prompt. On an artifact origin the file is the artifact the conversation is about.

### The description
The fixed text the model reads (per TLC-FR-05):

> Propose changes to Mermaid diagrams in the prompt of the draft under discussion, or in the prompt or project document under discussion, when you can see how a diagram would be better and want the author to decide. Use this tool for every change to a Mermaid diagram. A change to a diagram never goes in a text change, and never in the same call as text changes: send the text changes in their own call. Reach for it instead of describing the improvement in prose, and instead of asking permission to make one. Pass a list of diagram changes. To change a diagram, give in `before` its **current source**, copied character for character from the file as you read it, and give in `after` the **complete new source**. To remove a diagram, give `before` alone. To add a diagram, give `after` and put the exact text it follows in `after_text`. Give the source only: leave out the fence markers and the word `mermaid`. The source in `before` must belong to exactly one Mermaid diagram of the file. Where two diagrams hold the same source, put the exact text immediately before the diagram in `lead`, or the exact text immediately after it in `trail`, up to 200 characters each. The new source must be valid Mermaid. A source that does not parse is refused with the parse error, and you correct the source and call again. A diagram that is not Mermaid can not be changed with this tool. Say why the changes are worth making, in a sentence or two as you would put it to a colleague. Put one `<spoken>…</spoken>` tag in `rationale`, anywhere in it: one or two short sentences that a voice can read aloud. They say what matters, and where the written text holds more detail they end with an offer to read it. A rationale with no tag is refused. When a proposal of this file is already open, your diagram changes join it, and the author decides each one on its own. Your proposal is posted as your own comment in this conversation and your turn ends there — this call brings you no answer back, and you will be asked again later with the author's decisions, and whatever they said about them, in front of you. When your proposal is still open and the discussion asks for a different diagram, send `updates` in place of `diagrams`. Each update gives `action`: `change` with the `id` of a diagram change and its new fields, `add` with the fields of a new diagram change, or `withdraw` with the `id` of a diagram change you no longer offer. It reaches only the file you were asked about, and it changes nothing — the file is not rewritten unless the author accepts.

### Arguments
```
ProposeDiagramChangesArgs {
  path:      string,     // required; the draft-relative path of the draft's prompt,
                         //   or the project-relative path of the file
  rationale: string,     // required; why the changes are worth making
  diagrams: [            // the diagram changes; exactly one of diagrams, updates
    {
      before:     string?,   // the current source of the diagram; required but for an addition
      after:      string?,   // the complete new source; required but for a removal
      after_text: string?,   // for an addition: the exact text the new diagram follows
      lead:       string?,   // optional; exact text just before the diagram, ≤ 200 characters
      trail:      string?,   // optional; exact text just after the diagram, ≤ 200 characters
      note:       string?    // optional; one sentence about this diagram change alone
    }
  ]?,
  updates: [             // the updates of the open proposal, in the order they apply
    {
      action:     "change" | "add" | "withdraw",   // required
      id:         string?,   // for "change" and "withdraw": the id of a diagram change
      before, after, after_text, lead, trail, note   // for "change" and "add":
                             //   the fields of a diagram change, with the rules of `diagrams`
    }
  ]?
}
```

Their descriptions in the parameter schema (per TLC-FR-06):

- `path` — *"The path of the file that holds the diagrams: the draft-relative path of the draft's prompt, or the project-relative path of the prompt or project document under discussion."*
- `rationale` — *"Why the changes are worth making, in a sentence or two as you would put it to a colleague. The author reads this as your comment. It holds one `<spoken>…</spoken>` tag with one or two short sentences that a voice can read aloud."*
- `diagrams` — *"The diagram changes, in the order they should be read. To change a diagram, give `before`, its current source copied character for character from the file, and `after`, its complete new source. To remove one, give `before` alone. To add one, give `after` and put the exact text it follows in `after_text`. Give the source only, with no fence markers. The new source must be valid Mermaid. Where two diagrams hold the same source, give `lead`, the exact text immediately before the diagram, or `trail`, the exact text immediately after it, up to 200 characters each. Leave it out when you pass `updates`."*
- `updates` — *"Changes to your proposal that is still open, in place of `diagrams`. Each update gives `action`. `change` gives the `id` of a diagram change and its new `before`, `after`, `after_text`, `lead`, and `trail`, with the rules of `diagrams`; the change keeps its id and the author decides it again. `add` gives the fields of a new diagram change and no `id`. `withdraw` gives the `id` of a diagram change you no longer offer. A change that is accepted or withdrawn can not be updated, and a text change can not be updated with this tool."*

### Output
Data (per TLC-FR-08): `{ proposed: true }`. The turn ends on the call that proposed (per `../ai/CVL-conversation-loop.md` CVL-FR-15), so no further model call reads this value.

### The comment
The comment is the one of `PDC-propose-draft-changes-tool.md` on a draft origin, and the one of `PPC-propose-prompt-changes-tool.md` on an artifact origin: the `rationale` as the model wrote it, its spoken part hidden (per `../ui/CMT-comments.md` CMT-FR-BMCI), and nothing else. Beside it the comment carries exactly one attachment, of the `proposal` kind on a draft origin (per `../core/CMS-comments-storage.md` CMS-FR-60) and of the `prompt_proposal` kind on an artifact origin (CMS-FR-66). A call that joins diagram hunks to an open proposal, and a call with `updates`, post a comment of the same shape whose attachment also carries `update`, the number of hunks the call changed, added, and withdrew (per CMS-FR-BSQB).

### Refusals
The refusals of `PDC-propose-draft-changes-tool.md` apply to a draft origin and the refusals of `PPC-propose-prompt-changes-tool.md` apply to an artifact origin, for the same causes and with the same kinds, for these: no open project, no such file, not a prompt, no changes, lead too long, trail too long, lead and trail too long, changes overlap, blank rationale, no spoken part, conversation resolved, not one form, no updates, no open proposal, update malformed, no such change, change already settled, change named twice, no change proposed, and could not record. The message of a refusal names a diagram change where the text tools name a text change, and the message of **no open proposal** tells the model to send its changes in `diagrams`. A tool of this spec has no **a proposal is already pending** refusal, because a diagram change joins the open proposal (PDM-FR-WLBN). These are its own:
- **not a document conversation** — kind `PermissionDenied`, not retryable: *"This conversation is not about a draft or a file of the project, so there is nothing here to propose a change to. Say what you would change instead; asking again will not succeed."*
- **diagram not found** — kind `InvalidArgs`, retryable: *"The source you gave in `before` is not the source of a Mermaid diagram of the file. Copy it character for character from the file as you read it."*
- **diagram is not unique** — kind `InvalidArgs`, retryable: *"The source you gave in `before` belongs to more than one Mermaid diagram of the file. Add `lead` or `trail` with the exact text around the diagram so it names one diagram."*
- **addition anchor not found** — kind `InvalidArgs`, retryable, for an addition: *"The text you gave in `after_text` is not in the file. Copy it character for character from the file as you read it."*
- **addition anchor is not unique** — kind `InvalidArgs`, retryable, for an addition: *"The text you gave in `after_text` appears more than once in the file. Add `lead` or `trail` with the exact text around it so it names one place."*
- **not valid Mermaid** — kind `InvalidArgs`, retryable: a sentence that says the new source is not valid Mermaid, followed by the parse error of the parser, cut to 500 characters. The model corrects the source and calls again.
- **fence in source** — kind `InvalidArgs`, retryable: *"The new source has a line that would end the code fence. Remove the line of backticks or tildes and give the source alone."*
- **change is a text change** — kind `InvalidArgs`, retryable: *"The change you named is a text change, so this tool can not update it. Update it with the tool for text changes."*

### Side effects
Declared in full (per TLC-FR-17). A call that records a proposal produces **exactly one proposal** and **exactly one comment**, through `../core/DCP-draft-change-proposals.md`'s recording path (DCP-FR-05) on a draft origin and `../core/PCP-prompt-change-proposals.md`'s recording path (PCP-FR-05) on an artifact origin. A call that joins an open proposal, and a call with `updates`, produce **no new proposal** and **exactly one comment**, through the update path of the same module (DCP-FR-XDRV, PCP-FR-RVSN). The tool performs none of the writes itself. **The file is not modified**, a draft's version history gains nothing, no file of the project is touched, no repository state is changed, and no other store is mutated. A refused call produces no write and no comment.

## Functional requirements
1. **PDM-FR-ZXQE** The tool exists as a `rig` portable tool named `propose_diagram_changes` and conforms to `TLC-tool-conventions.md` in full — its name, description, parameter schema, output shape, refusal shape, and logging are that spec's rules applied to this tool. It is one of the tools of TLC-FR-17 that declare a side effect rather than a read-only posture, and its side effect is the one declared in the contract surface and nothing beyond it.
2. **PDM-FR-MBHW** Its `description()` returns the fixed text of the contract surface, compiled into the binary, and its `parameters()` returns the JSON Schema for the four documented arguments with the documented parameter descriptions (per TLC-FR-05). Neither varies by draft, by artifact, by conversation, by agent, or by project.
3. **PDM-FR-LJGN** The tool proposes to the file of the conversation that the turn holds, and accepts no argument naming a draft, an artifact, a conversation, a thread, a participant, or an agent. Its constructor binds it to that turn's origin and agent participant (per TLC-FR-15). On a draft origin `path` must name the draft's prompt (per `PDC-propose-draft-changes-tool.md` PDC-FR-05). On an artifact origin `path` must name the artifact the conversation is about, and the file must be a prompt or a project document (per `PPC-propose-prompt-changes-tool.md` PPC-FR-05, PPC-FR-06). Any other path is the refusal that the text tool of that origin gives for it, and nothing is recorded.
4. **PDM-FR-TPYC** A turn whose origin kind is neither a draft conversation nor an artifact conversation refuses with the **not retryable** **not a document conversation** refusal. In practice a model is not offered the chance to make it, the tool being attached to draft origins and artifact origins alone (per `../ai/CVL-conversation-loop.md` CVL-FR-08).
5. **PDM-FR-DWAF** A diagram change is one of three, and its fields decide which: `before` with `after` **changes** a diagram, `before` alone **removes** it, and `after` with `after_text` **adds** one. A change that carries neither `before` nor `after` is the **diagram not found** refusal. The tool reads no argument as a line number, an offset, or a region.
6. **PDM-FR-RNUS** A diagram is named by its **current source**. The tool finds the Mermaid fences of the file as it stands, with line endings normalised, and the fence whose source equals `before` is the diagram. The two sources are equal when they hold the same text after trailing white space is cut from both. A source that no Mermaid fence holds is **diagram not found**. A source that more than one Mermaid fence holds, where `lead` and `trail` leave more than one, is **diagram is not unique**. `lead` is the text immediately before the opening line of the fence and `trail` is the text immediately after its closing line, and each holds at most 200 characters (PDC-FR-DMTH). A fence of another language, such as a CALM fence, is never found. These two refusals are for a change and a removal, which name a diagram by `before`. An addition names no diagram: it names the text it follows, and `after_text`, with `lead` and `trail`, is found in the file as in PDC-FR-WCXD. `after_text` that the file does not hold is **addition anchor not found**. `after_text` that the file holds more than once, where `lead` and `trail` leave more than one, is **addition anchor is not unique**. The message of a refusal names the field that the model has to correct, and the model never reads a refusal about `before` for an addition. `after_text` can name text inside a fenced code block of any language, such as the source of a diagram. The new diagram is then added after the closing line of that code block (DCP-FR-WSLE), and the call is not refused.
7. **PDM-FR-HOQI** Every new source — the `after` of a change and of an addition — must be valid Mermaid before anything is recorded. The tool parses it with the Rust crate `merman`, which the backend uses to render Mermaid (per `../core/DXP-document-export.md` DXP-FR-RKJC). The parser is compiled into the application and works offline. The Editor does not use this parser: it renders with the JavaScript `mermaid` library (per `../ui/EDT-editor.md` EDT-FR-JIBV). The two parsers can disagree about one source. The check of the tool is a filter that stops a source that is clearly not a diagram while the agent can still correct it, and the Editor render decides what the author sees. Where `merman` accepts a source that the Editor can not render, the fence and the comparison pop-up show the source and the error message (per EDT-FR-XTEB). Where `merman` refuses a source that the Editor can render, the tool gives the **not valid Mermaid** refusal and the agent corrects the source. A source that is empty or only white space, or that `merman` refuses, is the **not valid Mermaid** refusal, with the parse error of `merman`. The parser reaches no network and runs no script from the source. No proposal is recorded on a refusal.
   - *Why:* The author compares two drawings. A source that does not draw would leave the author with a hunk that cannot be compared, and the agent can correct it only while the call is still its own.
8. **PDM-FR-CEZB** A new source that holds a line which would end the code fence — a line that starts with three or more backticks or tildes — is the **fence in source** refusal. The model gives the source alone and never the fence markers.
9. **PDM-FR-YKMV** A `before` that no Mermaid fence holds is **diagram not found**, whatever text it holds, so text that is not the source of a diagram never reaches a diagram hunk.
10. **PDM-FR-GFXA** A change whose `after` equals its `before` is the **no change proposed** refusal. A call with `diagrams` whose changes together alter nothing is the same refusal.
11. **PDM-FR-UITL** The tool records each diagram change as a **diagram hunk** (per `../core/DCP-draft-change-proposals.md` DCP-FR-QRVD) and every hunk of a call is placed against the file before anything is recorded (per DCP-FR-JGCD). A diagram that is not found, a diagram that is not unique, an addition anchor that is not found, an addition anchor that is not unique, a `lead` or `trail` over its bound, and two hunks that cover the same text are each the retryable `InvalidArgs` refusal named for them, and nothing is recorded. Each names the **place** of the change in the list the model sent — *Diagram change 3 of 8* (per PDC-FR-TZKQ).
12. **PDM-FR-WLBN** A call with `diagrams` joins the open proposal of the file. Where the file holds a proposal that is not resolved (per `../core/DCP-draft-change-proposals.md` DCP-FR-04, `../core/PCP-prompt-change-proposals.md` PCP-FR-04), whichever agent made it and whichever hunks it holds, the tool adds each diagram change to it as an `add` update, in one call, with one comment. Where the file holds none, the tool records a new proposal that holds the diagram hunks. Either way the file holds at most one undecided proposal, and no refusal says that a proposal is already pending.
    - *Why:* The author reviews one proposal of a file. A diagram change offered beside a text change is the same discussion, and a second proposal would break the one-undecided-proposal rule.
13. **PDM-FR-SDJP** A call carries `diagrams` or `updates`, never both. A call carrying both is the retryable **not one form** refusal, an empty `diagrams` list is the retryable **no changes** refusal, and an empty `updates` list is the retryable **no updates** refusal. Nothing is written for any of them.
14. **PDM-FR-BWOH** A call with `updates` changes the open proposal of the file through the update path of its module, on the **update rules** of `PDC-propose-draft-changes-tool.md` (PDC-FR-GMWR, PDC-FR-LGWJ, PDC-FR-UOBH, PDC-FR-DBFT, PDC-FR-DGUC, PDC-FR-VSMM, PDC-FR-SNUK, PDC-FR-VUTJ, PDC-FR-DTNJ). A `change` keeps the id of the hunk, and the author decides it again. An update names the place of the update, as *Update 2 of 4*.
15. **PDM-FR-NQEK** The updates of this tool act on **diagram hunks** alone. A `change` or a `withdraw` that names a hunk that is a text hunk is the **change is a text change** refusal, and the updates of the text tools refuse a diagram hunk in the same way (per `../core/DCP-draft-change-proposals.md` DCP-FR-GMYT). An `add` update records a diagram hunk.
16. **PDM-FR-XRVZ** A call whose `rationale` is empty or blank once trimmed is the retryable **blank rationale** refusal, and a call whose `rationale` has no spoken part (per `../ai/CVL-conversation-loop.md` CVL-FR-AGNN) is the retryable **no spoken part** refusal. Nothing is recorded for either.
17. **PDM-FR-AMCD** A conversation whose folded state is resolved (per `../core/CMS-comments-storage.md` CMS-FR-17) is the **not retryable** `PermissionDenied` refusal of the text tool of the origin, and neither a proposal nor a comment is produced.
18. **PDM-FR-FZGT** A successful call produces its proposal or its hunks and its comment as **one act** through the recording path or the update path of the module of the origin, and a failure of either produces neither. Any such failure is the retryable `Other` refusal **could not record**. The comment's body is the `rationale` as the model wrote it, less its citation markers (per `../ai/CVL-conversation-loop.md` CVL-FR-VSSU), and it is appended with the participant of the turn's agent, on the terms of PDC-FR-12, PDC-FR-13, PPC-FR-13, and PPC-FR-14.
19. **PDM-FR-JLYU** A successful call returns the data object of the contract surface and composes no sentence about what it did (per TLC-FR-08). The tool waits for no decision, holds no timer, opens no watcher, and leaves no request outstanding (per TLC-FR-16). A refusal does not end the turn: a call that recorded nothing leaves the loop running, so an agent whose source did not parse corrects it and calls again. Only a call that recorded or updated a proposal ends the turn (per `../ai/CVL-conversation-loop.md` CVL-FR-15).
20. **PDM-FR-OHSB** The tool holds no state between calls and no state of its own beyond the turn its constructor bound it to (per TLC-FR-15). With no project open it produces the shared no-open-project refusal (per TLC-FR-13).
21. **PDM-FR-PEWN** Each call emits under the `ai` and `backend` domains (per TLC-FR-14): an `INFO` record when a proposal is recorded, joined, or updated, naming the tool, the draft or the origin, the `path`, the count of diagram changes, and for an update the number of updates of each action; and a `WARN` record when it refuses, naming the tool, the reason, and the place of the change where the refusal is about one change. `path` is this tool's one loggable argument (per TLC-FR-14), bounded to the length a path can take. **No record carries a source, a parse error, the `rationale`, any part of the comment's body, or any part of the file.**
22. **PDM-FR-VQKI** The tool reaches no network and touches no credential (per TLC-FR-18): the parse of a source is local, and recording a proposal is a local write and a local append.
23. **PDM-FR-TCDX** The Conversation Agent prompts of a draft target and of an artifact target tell the agent: a change to a Mermaid diagram never goes in a text change, and never in the same call as text changes, and the agent sends diagram changes and text changes in separate calls of the matching tools. The prompts name no tool (per `../ai/CVL-conversation-loop.md` CVL-FR-05), so they say "the tool made for diagram changes" and "the tool for text changes".
24. **PDM-FR-IGRM** The text tools hold no Mermaid parser and make no judgement of the text they place. A text hunk that overlaps the fence of a diagram hunk of the same proposal is the **changes overlap** refusal (per PDC-FR-TZKQ).

## Non-functional requirements
- The `rationale` is the only text this tool produces that a person reads, and the tool composes none of it. The hunks carry the substance and the comparison pop-up shows it.
- A call costs the parse of each new source, one file write for the hunks, one for the record, and one line of I/O through the conversation's own append path.
- A parse is bounded: a source over 256 KiB is refused as not valid Mermaid, and a parse that does not end before a deadline of 5 seconds is refused as not valid Mermaid, so a call never holds the turn.
- Nothing in this tool requires network access.
- The description is written so that a model reading every tool description in this group can tell them apart on their first sentences: this one offers the author changes to Mermaid diagrams, `PDC-propose-draft-changes-tool.md`'s offers changes to the text of a draft's prompt, and `PPC-propose-prompt-changes-tool.md`'s offers changes to the text of a prompt or a document the project holds.
- A proposal that the author never decides costs nothing and holds nothing open, on the terms of PDC-FR-10.
