# Propose prompt changes tool

**Spec code:** `PPC`

## Intent
This tool proposes the **complete new text** of a prompt artifact the project already holds. This is deliberately not the shape `PDC-propose-draft-changes-tool.md` takes for a **draft**, which proposes anchored changes the author decides one by one (per `PDC-propose-draft-changes-tool.md` PDC-FR-04).

The tool an agent reaches for when it can see how a **prompt the project already holds** would be better and wants the author to decide. It **proposes** a new version of that prompt — its complete text as it should stand once the change lands — and ends the agent's turn there. The proposal is recorded as a candidate beside the project and posted into the conversation as an ordinary comment by the agent, carrying its reasoning as prose and a reference the author opens to read the change as a comparison. The author accepts it or declines it, with a word of feedback if they have one, and that decision brings the agent back with the whole conversation in front of it. The shape is the shape of a colleague offering a rewrite: here is what I would make of this, here is why, and it is yours to take or leave — rather than an assistant that edits the file and tells you afterwards. **Nothing this tool does changes the artifact.** A proposal is material sitting beside the project until the author accepts it, and the write that lands it is one the author performs from the surface that shows it to them (`../ui/PCR-prompt-change-review.md`); an agent whose proposal is declined has cost the project nothing but a comment. Out of scope: proposing to a file whose resolved artifact type is anything but `prompt`, which this tool refuses; proposing to a file the project does not hold, which it also refuses — a proposal replaces a prompt and never creates one, so no path through this tool brings a file into being; proposing to a draft, which is `PDC-propose-draft-changes-tool.md`'s and which this tool neither reaches nor changes; expressing a change as a patch, a diff, or a fragment, none of which this tool accepts — a proposal is a whole file or it is nothing; waiting for the decision, since the call returns as soon as the proposal is recorded and holds no timer, watcher, or open request; applying an accepted proposal, which is `../core/PCP-prompt-change-proposals.md`'s; and rendering the comparison, which is `../ui/PCR-prompt-change-review.md`'s.

## Contract surface
One tool, conforming to `TLC-tool-conventions.md` in full. It is attached to the turns whose origin kind is an artifact conversation and to no others, by `../ai/CVL-conversation-loop.md` (CVL-FR-08), and has no Tauri command, event, or frontend reach of its own.

### The tool
`propose_prompt_changes` — a `rig` portable tool. Like `AUC-ask-user-comment-tool.md`'s and `PDC-propose-draft-changes-tool.md`'s, and unlike the read-only tools of this group, it is **constructed per turn** (per TLC-FR-15), its constructor taking the origin of the conversation the turn belongs to and the agent participant that turn answers as, so the conversation it can post into and the agent it posts as are both fixed before the model composes a single argument.

### The description
The fixed text the model reads (per TLC-FR-05):

> Propose an improved version of a prompt the project holds, when you can see how its text would be better and want the author to decide. It reaches a file whose type is Prompt and no other kind of file, and the file has to exist already — this offers a rewrite and never a new file. Reach for it instead of describing the improvement in prose, and instead of asking permission to make one. Pass its **complete new text** — every line the prompt should hold once the change lands, and not a patch, not a diff, not the changed section on its own, and not a description of what to change: whatever you pass is what the prompt becomes if the author accepts. Say why the change is worth making, in a sentence or two as you would put it to a colleague. Your proposal is posted as your own comment in this conversation and your turn ends there — this call brings you no answer back, and you will be asked again later with the author's decision, and whatever they said about it, in front of you. Propose one change at a time: because your turn ends here, anything else you asked for in the same message is not carried out. It changes nothing — the file is not rewritten unless the author accepts.

### Arguments
```
ProposePromptChangesArgs {
  path:      string,    // required; project-relative path of the prompt to replace
  content:   string,    // required; the file's complete new text
  rationale: string     // required; why the change is worth making
}
```

Their descriptions in the parameter schema (per TLC-FR-06):

- `path` — *"The project-relative path of the prompt you are proposing a new version of. The file has to exist and its type has to be Prompt; anything else is refused and nothing is created."*
- `content` — *"The prompt's complete new text: the whole document as it should stand once the change lands. Not a patch, not a diff, not only the part you changed. If the author accepts, this becomes the file's entire contents. Pass nothing at all only if you mean to propose emptying the file, which is a change like any other and is offered to the author the same way."*
- `rationale` — *"Why the change is worth making, in a sentence or two as you would put it to a colleague. The author reads this as your comment, beside the comparison."*

### Output
Data (per TLC-FR-08): `{ proposed: true, proposal_id }`, the identity `../core/PCP-prompt-change-proposals.md` recorded, so the exchange records which proposal the turn produced. The turn ends on the call that proposed (per `../ai/CVL-conversation-loop.md` CVL-FR-15), so no further model call reads this value.

### The comment
What the author reads. The `rationale` as the model wrote it, and nothing else — no identifier, no path, no preamble, and no closing line:

```
The instructions ask for three things in one sentence and the
last of them is the one that matters. I have split them and
put the important one first.
```

Beside it the comment carries exactly one attachment, of the `prompt_proposal` kind (per `../core/CMS-comments-storage.md` CMS-FR-66), which is what the rail renders as the control that opens the review (per `../ui/CMT-comments.md` CMT-FR-48). The attachment carries the proposal's identity and no part of its content, so the comment is a line of prose and a reference however large the file being proposed.

### Refusals
- **no open project** — the shared refusal of `TLC-tool-conventions.md`: kind `NotFound`, not retryable.
- **not an artifact conversation** — kind `PermissionDenied`, not retryable: *"This conversation is not about a file of the project, so there is nothing here to propose a change to. Say what you would change instead; asking again will not succeed."*
- **no such file** — kind `NotFound`, retryable: names the path and says the project holds no file at it, and that this tool rewrites a prompt rather than creating one.
- **not a prompt** — kind `InvalidArgs`, retryable: names the path and says this tool reaches a file whose type is Prompt alone, so a different file has to be named.
- **blank rationale** — kind `InvalidArgs`, retryable: *"Say why the change is worth making. The author reads this beside the comparison."*
- **no change proposed** — kind `InvalidArgs`, retryable: *"The text you passed is what the file already holds, so there is nothing to decide."*
- **a proposal is already pending** — kind `PermissionDenied`, retryable: *"A proposed change to this file is still waiting on the author. Wait for their decision before proposing another."*
- **conversation locked** — kind `PermissionDenied`, not retryable: *"This conversation is locked and takes no further comments, so nothing was proposed and no decision is coming. Answer with what you already have; proposing again will not succeed."*
- **could not record** — kind `Other`, retryable: *"The proposed change could not be recorded."*

### Side effects
Declared in full (per TLC-FR-17). One successful call produces **exactly one proposal** and **exactly one comment**, and the tool performs neither write itself: it calls `../core/PCP-prompt-change-proposals.md`'s internal recording path (PCP-FR-05), which writes the candidate under `.synthesis/proposals/` and appends the comment through `../core/CMS-comments-storage.md`'s agent write path (CMS-FR-41) as one act, so the record and the reference to it can never disagree. **No file of the project is created, modified, deleted, renamed, or moved**, no repository state is changed, and no other store is mutated. A refused call produces neither the proposal nor the comment.

## Functional requirements
 1. **PPC-FR-01** The tool exists as a `rig` portable tool named `propose_prompt_changes` and conforms to `TLC-tool-conventions.md` in full — its name, description, parameter schema, output shape, refusal shape, and logging are that spec's rules applied to this tool. It is one of the tools of TLC-FR-17 that declare a side effect rather than a read-only posture, and its side effect is the one declared in the contract surface and nothing beyond it.
 2. **PPC-FR-02** Its `description()` returns the fixed text of the contract surface, compiled into the binary, and its `parameters()` returns the JSON Schema for the three documented arguments with the documented parameter descriptions (per TLC-FR-05). Neither varies by artifact, by conversation, by agent, or by project, so two agents holding this tool were offered byte-identical definitions of it however different the files they are looking at.
 3. **PPC-FR-03** The tool posts into the conversation of the turn that holds it and accepts no argument naming a conversation, a thread, a participant, or an agent. Its constructor binds it to that turn's origin and agent participant (per TLC-FR-15), so no argument a model composes can post into a conversation it was not asked about, and an instance outlives no turn. What the model does name is the **target**, through `path` alone (PPC-FR-05).
 4. **PPC-FR-04** `content` is the file's **complete new text** and is treated as such: it is written to the candidate verbatim and, if the author accepts, becomes the file's whole contents (per `../core/PCP-prompt-change-proposals.md` PCP-FR-13). The tool applies no patch, resolves no hunk, merges nothing against what the file holds, and interprets no part of the argument as an instruction about a region of the file. A model that passed a fragment has proposed a file consisting of that fragment, which is why the description and the parameter's own text each say so plainly (PPC-FR-02): it is the one mistake this tool cannot detect, the proposed text being valid content whatever the model meant by it.
 5. **PPC-FR-05** `path` is project-relative and names the target. It is resolved against the project's active worktree to the artifact's stable key (per `../core/ASC-artifact-scanning.md` ASC-FR-13), and the proposal is recorded against that identity rather than against the string the model composed, so a proposal survives a rename of the artifact exactly as the identity does. An absolute path, a path escaping the project root, and a path naming a directory are each the retryable `NotFound` refusal of the contract surface.
 6. **PPC-FR-06** The target must **already exist** and its **resolved artifact type must be exactly `prompt`** (per `../core/ASC-artifact-scanning.md` ASC-FR-06). A path naming nothing is the retryable `NotFound` refusal, and a path naming a file whose type resolves to any of the other seven built-in types, or to none at all, is the retryable `InvalidArgs` refusal that names the type requirement. The two are distinguished because the corrections differ: one is a path to fix, the other is a file to stop proposing against. In neither case is anything recorded, and in neither case is a file created — this tool proposes a new version of a prompt and never the creation of one, so the project's file set is unchanged by every route through it.
 7. **PPC-FR-07** A turn whose origin kind is not an artifact conversation refuses with the **not retryable** `PermissionDenied` of the contract surface, and its message says a further call will not succeed (per TLC-FR-11). In practice this is a refusal a model is not offered the chance to make, the tool being attached to artifact origins alone (per `../ai/CVL-conversation-loop.md` CVL-FR-08); it exists because a tool's refusals are its contract rather than its caller's, and a set of tools selected elsewhere is not a guarantee this tool may rest on.
 8. **PPC-FR-08** Two conditions are the retryable `InvalidArgs` refusals of the contract surface, and nothing is recorded for either: a `rationale` that is empty or blank once trimmed, and a `content` that would **change nothing on disk**. They are distinguished because each calls for a different correction: say why, and propose something that differs. The second is decided on the normalised form the write path would persist (per `../core/PCP-prompt-change-proposals.md` PCP-FR-07), so a candidate differing from the file only in its line endings is refused rather than offered as a comparison with nothing in it.
    **An empty `content` is not a refusal.** Emptying a prompt is a change like any other, and a tool that refused to propose one would be deciding for the author that a file must always hold something — which is a judgement about the material rather than a rule about the argument, and the author is the one being asked. So a `content` of no bytes against a prompt that holds something is an ordinary proposal: it is recorded, the comparison shows every line being removed, and accepting it leaves the file empty (per `../core/PCP-prompt-change-proposals.md` PCP-FR-09, PCP-FR-13). The one case it is refused in is the case every candidate is refused in — a prompt that is **already** empty, where an empty candidate would change nothing and there is nothing for the author to decide — and it is refused there as the ordinary no-change refusal rather than as a rule of its own, so the model reads one message about one thing.
 9. **PPC-FR-09** A call made while any proposal on that artifact is still `pending` (per `../core/PCP-prompt-change-proposals.md` PCP-FR-04) is the **retryable** `PermissionDenied` of the contract surface and nothing is recorded. One artifact carries at most one undecided proposal at a time, whichever agent made it, so the author is never asked to hold two competing rewrites of one file in their head. It is retryable because the author's decision is exactly what would make a further call succeed. The message says as much in the terms the model has to act on: that a change it proposed earlier is still waiting on the author, that it should say so plainly in its reply, and that it must not describe the change this call carried as proposed, because nothing was recorded.
10. **PPC-FR-10** A conversation whose folded state is locked (per `../core/CMS-comments-storage.md` CMS-FR-17) is the **not retryable** `PermissionDenied` of the contract surface, and neither the proposal nor the comment is produced: a proposal nobody can be told about is a proposal nobody will decide, so the two are recorded together or not at all (PPC-FR-12).
11. **PPC-FR-11** The tool records and returns. It waits for no decision, holds no timer, opens no watcher, and leaves no request outstanding, so TLC-FR-16 holds for it unchanged: the author's decision reaches the agent as a later turn rather than as this call's result (per `../core/AGC-agent-conversations.md` AGC-FR-29).
12. **PPC-FR-12** A successful call produces the proposal and the comment as **one act** through `../core/PCP-prompt-change-proposals.md`'s recording path (PCP-FR-05), and a failure of either produces neither: a call that could not append the comment leaves no candidate on disk, and a call that could not write the candidate appends no comment. Any such failure is the retryable `Other` refusal of the contract surface.
13. **PPC-FR-13** The comment's body is the `rationale` as the model wrote it, less its citation markers (per `../ai/CVL-conversation-loop.md` CVL-FR-VSSU), and nothing besides — no path, no identifier, no marker, no machine-readable field, and no instruction to the author about how to decide. What makes the change reachable is the comment's one `prompt_proposal` attachment (per `../core/CMS-comments-storage.md` CMS-FR-66), which the rail renders as a control (per `../ui/CMT-comments.md` CMT-FR-48); the prose beside it reads as a colleague's note and nothing about it says a tool composed it.
14. **PPC-FR-14** The comment is appended with the turn's agent participant — its agent id, its nickname as the handle, the model it runs as, and its title as the registry holds it at the moment of the append (per `../core/CMS-comments-storage.md` CMS-FR-65) — which is the same participant shape a delivered answer is appended with (per `../core/AGC-agent-conversations.md` AGC-FR-16). The fold, the rail, and the Comments panel therefore read a proposal's comment exactly as they read any other comment of that conversation.
15. **PPC-FR-15** A successful call returns the data object of the contract surface, carrying the recorded proposal's identity. It composes no sentence about what it did (per TLC-FR-08), and it returns no part of the candidate.
16. **PPC-FR-16** A refusal is not a turn's failure (per `../ai/CVL-conversation-loop.md` CVL-FR-14) **and does not end the turn**: a call that recorded nothing leaves the loop running, so an agent whose proposal was refused corrects the path, names a different file, or answers with prose instead. Only a call that actually recorded a proposal ends the turn (per CVL-FR-15).
17. **PPC-FR-17** With no project open the tool produces the shared no-open-project refusal (per TLC-FR-13), there being no artifact to propose to.
18. **PPC-FR-18** The tool holds no state between calls and no state of its own beyond the turn its constructor bound it to (per TLC-FR-15). Two turns hold two instances and neither observes the other's call, so two agents asked about one file each reach their own instance and neither's proposal is attributed to the other — which the one-pending rule of PPC-FR-09 then decides between.
19. **PPC-FR-19** Each call emits under the `ai` and `backend` domains (per TLC-FR-14): an `INFO` record when a proposal is recorded, naming the tool and the `path`; and a `WARN` record when it refuses, naming the tool, the `path`, and the reason. `path` is this tool's one **loggable argument** (per TLC-FR-14), a record about a proposed rewrite being unfollowable without saying which file was rewritten; it is bounded to the length a project-relative path can take, so no value a model composes grows a record past `../core/LGC-logging.md`'s per-record ceiling (LGC-FR-08). **No record carries the `content`, the `rationale`, any part of the comment's body, or any part of the file being replaced.**
20. **PPC-FR-20** The tool reaches no network and touches no credential (per TLC-FR-18): recording a proposal is a local write and a local append.
21. **PPC-FR-21** This tool changes `PDC-propose-draft-changes-tool.md` in no way and reaches nothing of it. It names no draft, resolves no draft-relative path, reads no draft's proposals, and holds no instance of that tool; the two are attached to disjoint origin kinds (per `../ai/CVL-conversation-loop.md` CVL-FR-08), record into different stores, and produce different attachment kinds, so an agent offered one is never offered the other and neither tool's refusals depend on the other's state.

## Non-functional requirements
- The `rationale` is the only text this tool produces that a person reads, and the tool composes none of it, because every byte it added would read as machinery in a conversation that should read as prose. The comparison carries the substance; the rationale carries the reason.
- A call costs one file write for the candidate's content, one for its record, and one line of I/O through the conversation's own append path.
- The candidate's content is written to disk rather than held in memory or carried in the comment, so a proposal against a large file costs the conversation a line and the folder a file, and folding the thread never decodes a document.
- Nothing in this tool requires network access.
- The description is written so that a model reading every tool description in this group can tell them apart on their first sentences: this one offers the author a rewrite of a prompt the project holds, `PDC-propose-draft-changes-tool.md`'s offers a rewrite of a draft's prompt, `AUC-ask-user-comment-tool.md`'s asks the author something, `RFT-read-file-tool.md`'s reads a file it is given the path of, and `SPS-specification-search-tool.md`'s finds which specifications bear on a topic. The two proposal tools are never offered together, but the sentences are written so a model reading either alone knows which material it is being offered a rewrite of.
- A proposal the author never decides costs nothing and holds nothing open: the call returned when it recorded, and what became of the turn is `../core/AGC-agent-conversations.md`'s affair rather than this tool's. What it does cost is the artifact's one pending slot (PPC-FR-09), which is a decision the author can always make.
- The tool is constructed per turn rather than once for the application. A construction is two values copied into a struct, so the cost is nothing beside the model call the turn is about to make.
