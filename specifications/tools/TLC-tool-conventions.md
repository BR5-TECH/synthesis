# Tool conventions

**Spec code:** `TLC`

## Intent

The rules every tool in this group follows, so that a tool can be handed to an agent by a caller who knows nothing about it beyond its constructor. A tool here is a capability the application lends to an agentic turn, and it comes in one of three classes. A **model-facing** tool is lent to the model itself — the model decides when to reach for it, calls it with arguments it composed, and reads the result as text in its own context — which makes its description, its parameter schema, and its refusal messages part of the contract rather than documentation about it: they are the entire interface a model has, and a description that reads well to a programmer but leaves a model guessing is a defect in the tool. A model-facing tool the application implements is expressed as a `rig` portable tool so it can be attached to any agent the framework drives, whichever provider serves it, without adapting anything. A **provider-native** tool is model-facing too, but the application implements none of it: it is one definition entry naming a capability the provider itself executes, so the provider owns the name the model sees, the arguments it composes, the work, and the result, and the application owns only the decision to offer it — which makes the provider carrying a call, and the kind of loop making it, the whole of what decides whether the tool is there. Reaching the web is the capability that takes this shape, because a search and a page retrieval are work a provider already does well and an application that did them itself would carry a client, a credential, and a failure mode for each; `WST-web-search-tool.md` and `WFT-web-fetch-tool.md` are the two tools of this class. A **loop-facing** tool is lent instead to the loop code that drives a turn, reached through a typed Rust API rather than through a model's composed JSON, because what it does is too consequential to be selected by a model's judgement — launching another agent in a container is the one such capability, and `EAC-execute-agent-cli.md` is the one tool that has it. All three classes are alike in what matters for grouping them: none renders anything, none is configurable, none registers a Tauri command, and each is a reusable capability a turn reaches for rather than a stage of any particular loop. This spec fixes all three shapes; each tool spec in this group fixes one tool's behaviour. Out of scope: which tools exist, each of which has its own spec; the agent loops that carry a tool call, dispatch it, and feed the result back to the model, which are `../ai/CVL-conversation-loop.md`'s (CVL-FR-12) and `../ai/GRL-graduation-loop.md`'s, each of which names its own set; retrieval-based tool discovery, since the set attached to an agent is named by its caller rather than searched; any user-facing surface, because nothing here renders, is configurable, or is reachable from the frontend — a tool may change something a surface then draws, and one here does, but what that surface makes of it is that surface's specification rather than this group's; and the Model Context Protocol, which this group neither speaks nor serves.

## Contract surface

This spec exposes no operation of its own. It states the shape the operations of every other spec in this group take. Nothing in this group registers a Tauri command, emits a Tauri event, or is reachable from `src/**` by any `invoke()`.

Everything in this section down to *Construction* describes a **model-facing** tool the application implements, which is what most of the group is. The two other shapes are stated separately under *The provider-native tool* and *The loop-facing tool* below.

### The tool

Every model-facing tool is one implementation of `rig::tool::PortableTool`, which is its whole public surface:

```
const NAME: &'static str            // the model-facing tool name (TLC-FR-02)
type Args:   Deserialize            // the arguments, decoded from the model's JSON
type Output: IntoToolOutput         // what the model reads back (TLC-FR-08)
type Error:  std::error::Error      // this tool's own failures (TLC-FR-09)

fn description(&self) -> String              // the agent-facing description (TLC-FR-03)
fn parameters(&self) -> serde_json::Value    // the JSON Schema for Args (TLC-FR-06)
fn map_error(&self, e: Self::Error) -> ToolExecutionError   // (TLC-FR-10)
async fn call(&self, args: Self::Args) -> Result<Self::Output, Self::Error>
```

`NAME`, `description()`, and `parameters()` together are what `rig` sends to a provider as the tool's `ToolDefinition { name, description, parameters }`, and are the only thing a model knows about the tool before calling it.

### The output

A tool's result reaches the model as content of one of two kinds, and a tool returns whichever matches what it produced (TLC-FR-08):

- **data** — a record, a set of fields, a collection: a JSON object with stable named fields. A document accompanied by the stable metadata a model needs in order to place it takes this shape too, carrying that document under a named field.
- **a document** — a file's text, returned as text and wrapped in nothing.

The two are the framework's own kinds rather than a distinction drawn here: a value that serialises to a JSON object becomes a structured block and one that is a string becomes a literal text block, and neither is ever reparsed as the other.

### The refusal

A refusal reaches the model as `rig`'s `ToolExecutionError`, carrying a normalized `ToolErrorKind`, the message the model reads, and whether calling again could succeed:

```
ToolErrorKind = InvalidArgs | NotFound | PermissionDenied | Timeout
              | Cancelled | RateLimited | Provider | Network | Other

kind        // why it failed, machine-readable (TLC-FR-10)
message     // one or two plain sentences the model acts on (TLC-FR-09)
retryable   // whether a further call could succeed (TLC-FR-11)
```

Two refusals are shared by every tool in this group that needs an open project:

- **no open project** — `NotFound`, not retryable: *"No project is open, so there is nothing to read. This will keep failing until a project is opened; do not retry."*
- **malformed arguments** — `InvalidArgs`, retryable: names the parameter at fault and what a valid value looks like.

### The provider-native tool

A provider-native tool has no implementation here at all. What the application holds is one **definition entry**, carried in the `tools` array of a request beside the definitions of the portable tools that request offers:

```
{ "type": "<provider>:<capability>" }
```

The entry is the whole of the application's side. There is no `NAME`, no `description()`, no `parameters()`, no `Args`, no `Output`, no `Error`, no `map_error`, and no `call()`, because nothing here is ever called: the provider names the tool the model sees, publishes the schema the model composes against, executes the call, and produces the result, which reaches the model through the same exchange every other tool result travels in. Two entries take this shape, both of them OpenRouter's:

```
{ "type": "openrouter:web_search" }    // WST-web-search-tool.md
{ "type": "openrouter:web_fetch" }     // WFT-web-fetch-tool.md
```

### The loop-facing tool

A loop-facing tool has no `NAME`, no `description()`, and no `parameters()`, because no model ever sees it. Its whole public surface is one typed asynchronous Rust function:

```
async fn <operation>(request: Request) -> Result<Response, Error>
```

`Request` and `Response` are that tool's own Rust types, strictly decoded where they cross a serialization boundary, and `Error` is an enumeration whose variants are the distinctions its caller has to act on. Nothing about it is composed by a model, so nothing about it is forgiving: an unknown field is a rejection rather than an ignored key, and a value out of range is a refusal rather than a clamp.

### Construction

Each tool spec of the two classes the application implements declares its own constructor, and a caller attaches the tools it wants by name. A provider-native tool declares no constructor, its own spec declaring the entry instead, and a caller attaches it by carrying that entry. This group publishes no registry, no `builtin_tools()`, and no other call returning the whole set, so a tool becomes reachable to an agent only where a caller named it.

## Functional requirements

 1. **TLC-FR-01** Every tool in this group belongs to exactly one of three classes, and its own spec says which. A **model-facing** tool is one implementation of `rig::tool::PortableTool` and exposes nothing else; a **provider-native** tool is one definition entry the provider itself executes and exposes nothing here at all; a **loop-facing** tool is one typed asynchronous Rust function and exposes nothing else. Whichever class it is, it registers no Tauri command, emits no Tauri event, and is unreachable from the frontend, so its observable effects are the value it returns to whoever called it, the records it logs (TLC-FR-14), and whatever side effects its own specification declares (TLC-FR-17) — which for every tool declared read-only is nothing further at all. TLC-FR-02 through TLC-FR-13 state what a model-facing tool owes the model that reads it and apply to that class alone; TLC-FR-14 through TLC-FR-19 apply to that class and to the loop-facing one; TLC-FR-20 states what a loop-facing tool owes its caller; and TLC-FR-21 through TLC-FR-26 state the whole of what a provider-native tool is, no other requirement here governing a tool the application neither describes nor executes.
 2. **TLC-FR-02** A tool's name is a lowercase `snake_case` verb phrase, unique across this group, and identical between the tool's `NAME` constant and the `name` of the `ToolDefinition` a provider receives. The name is a contract a model may have been trained or prompted against, so renaming a tool is a change to this group's surface rather than a refactor.
 3. **TLC-FR-03** A tool's description is addressed to the model that will decide whether to call it, and states four things: what the tool does, when to reach for it, what it returns, and what it does not do. Its first sentence alone is sufficient to decide whether the tool is relevant, because a model choosing among a dozen tools reads first sentences before it reads any of them in full.
 4. **TLC-FR-04** A description names no Rust type, no crate, no module, no internal function, and no specification identifier. A model cannot act on any of them, and each one spends the attention the description needs for what the tool is actually for.
 5. **TLC-FR-05** A tool's description and its parameter schema are fixed text compiled into the binary. Neither is assembled per call, varied by caller, derived from project state, or configurable by the author, so two agents given the same tool are given byte-identical definitions and a tool's behaviour is reproducible from the build alone.
 6. **TLC-FR-06** A tool's `parameters()` is a JSON Schema object. Every parameter carries its own `description`; the `required` list names exactly the parameters that have no default; and a parameter with a default, a bounded range, or an enumerated set states that default, those bounds, or that set in its own description, because a model reads the description and does not reliably infer constraints from schema keywords alone.
 7. **TLC-FR-07** A tool is forgiving of arguments wherever forgiveness is unambiguous, since its arguments were composed by a model rather than by a compiler: an absent optional parameter takes its documented default, a numeric parameter outside its documented bounds is clamped into them rather than refused, and an unrecognised field is ignored. An absent or undecodable *required* parameter is a refusal, because guessing one would answer a question the model did not ask.
 8. **TLC-FR-08** A tool's output takes whichever of two shapes matches what it returns. A tool returning **data** — a record, a set of fields, a collection — returns a JSON object with stable named fields, never a bare array: a collection sits under a named field, so a later addition to the output extends it rather than changing its shape. A tool whose result **is a document** returns that document as text, unwrapped, because a document carried in a JSON string field reaches the model with every line break in it escaped and costs it the shape the document was written in. The one exception is a document that cannot be acted on apart from stable metadata about what it is, which returns as data carrying the document under a named field beside that metadata; a tool taking this shape says in its own spec why the two cannot arrive separately, and `RDT-read-draft-tool.md` (RDT-FR-05) is the tool that does — a draft's prompt without its draft's name and status is material a model cannot place, and the second call that would fetch them asks again for what the first already resolved. Neither shape is ever a `Debug` rendering, and neither is a prose sentence the tool assembled about its own result.
 9. **TLC-FR-09** Every failure is an `Err` and never a panic, and its message is one or two plain sentences that say what went wrong and what would make the call succeed. A message carries no Rust type name, no backtrace, no crate name, and no absolute filesystem path, because every one of them reaches a model's context as noise it cannot act on.
10. **TLC-FR-10** Every tool implements `map_error` and normalizes its own failures to the `ToolErrorKind` that matches the reason — `InvalidArgs` for an argument the model can correct, `NotFound` for material that is not there, `Timeout` for a bounded wait that elapsed, `Other` otherwise — so a runtime can classify a failure without parsing its message.
11. **TLC-FR-11** A refusal declares whether calling again could succeed, and the test is whether any argument the model could compose would change the answer. One it could fix by calling differently is retryable, whether the fault was the shape of an argument or a value naming something that is not there — a misremembered name is corrected on the next call, and telling the model otherwise costs it a capability the project has. One no argument would change — no project open being the case every tool in this group shares — is not retryable, and says so in its message as well as its flag, so an agent loop does not spend turns re-calling a tool that will refuse identically. The flag is therefore independent of the kind (TLC-FR-10): a `NotFound` may be either, according to whether the model chose what was looked for.
12. **TLC-FR-12** A condition that is a legitimate answer rather than a failure is a success. A search that matched nothing and a set that is genuinely empty each return an empty collection, never a refusal, because "there are none" is information a model can act on and an error is not.
13. **TLC-FR-13** A tool that requires an open project refuses with the shared no-open-project refusal when none is open. It is the one condition every tool in this group answering from project state shares, so it reads identically whichever tool reported it.
14. **TLC-FR-14** Every call emits through `../core/LGC-logging.md`'s internal API under the `ai` and `backend` domains together, a tool call being work the backend performs because a model asked for it: an `INFO` record when the call ends, naming the tool and the outcome, and a `WARN` record when it refuses, naming the tool and the reason. No record carries an argument value, a returned field, or any part of a file's contents — a tool's arguments are composed by a model out of the conversation it is having, and its results carry project material, so neither is loggable. The one exception is an argument a tool's own specification names as loggable, which that specification is then answerable for: `RFT-read-file-tool.md` (RFT-FR-20) names `read_file`'s `path`, a record about a file read being unfollowable without saying which file it was; `SPS-specification-search-tool.md` (SPS-FR-19) names `search_specifications`'s `query` and `limit`, a record about a search being unfollowable without saying what was searched for and how much of it was asked for; `PDC-propose-draft-changes-tool.md` (PDC-FR-18) names `propose_draft_changes`'s `path`, a record about a proposed rewrite being unfollowable without saying which file was rewritten; `PPC-propose-prompt-changes-tool.md` (PPC-FR-19) names `propose_prompt_changes`'s `path` on exactly those terms; `DST-draft-search-tool.md` (DST-FR-21) names `search_drafts`'s `query` and `limit` on the same terms `search_specifications`'s are named; `NST-note-search-tool.md` (NST-FR-20) names `search_notes`'s `query` and `limit` on those same terms; `RDT-read-draft-tool.md` (RDT-FR-17) names `read_draft`'s `draft_id`, a record about a draft read being unfollowable without saying which draft it was; `RGF-read-graduation-file-tool.md` (RGF-FR-16) names `read_graduation_file`'s run id and `path` on the same terms `read_file`'s is named; `ESU-escalate-to-user-tool.md` (ESU-FR-15) names `escalate_to_user`'s run id and its option count, a record about a paused run being unfollowable without saying which run — while naming as unloggable the reason, the question, every option's text, and the author's answer; and `EAC-execute-agent-cli.md` (EAC-FR-29) names the resolved vendor, the process outcome, and the duration, none of which is a caller's argument and all of which a record about launching an agent is unfollowable without — while naming as unloggable the instruction, the structured input, every session and resume field, the credential, and every captured byte of the agent's own streams. A tool naming such a value bounds what it records, so that no value a model composes can grow a record past `../core/LGC-logging.md`'s per-record ceiling (LGC-FR-08) and cost it the tool and the reason it exists to carry. A call refused because its arguments do not decode into the tool's argument type is refused **before the tool runs**, so the tool records nothing of its own and the `WARN` is emitted for it at the boundary that dispatches the call, naming the tool and the reason `arguments_undecodable`. That reason is its own and is told apart from every refusal a tool authors, because each of those names a value the model chose wrongly and this one names a shape the model composed wrongly, which no tool reaches the point of describing. The record carries the **shape** of the arguments and no value of any kind: the field names and the kind of value each holds, a string reading as `string` whatever it holds and a number as `number`. A field name reaches the record only where the tool's **own parameter schema** declares it, that schema being fixed text compiled into the binary (TLC-FR-05): every name in a record is therefore a name this application wrote, and a key the model composed is recorded as `?`. The rule is the schema rather than the spelling of the key, because a credential is spelled exactly as a field name is — a token, a commit, an identifier, a login, and a path are all letters and digits within any length a field name keeps, so a rule that reads the key admits every one of them. A key nothing declares is worth exactly one mark, which says the model invented a field, and repeating it tells a reader nothing the mark does not. The shape is bounded in length and in depth on the terms every model-composed value here is bounded, so the record keeps the tool and the reason however large the argument set was, and the fields are read by name, whatever order the object holds them in, so an argument set wider than the bound is reported by its first fields by name.
14. **TLC-FR-SPRR** A call whose arguments the model sent as anything but a JSON object is refused as `arguments_undecodable` before the tool runs, also when the framework recovered fields of a cut-off object. `null` or blank arguments are an empty object. The record carries the shape of the arguments as sent; text that is not JSON reads as `string`.
    - *Why:* A tool that ran on the readable part of a cut-off object would act on half of what the model meant to send.
15. **TLC-FR-15** A tool holds no per-call state and is cheap to construct. A tool that answers the same way whoever called it needs one instance for as long as the application runs, and may be attached to several agents at once without any of them observing another's calls. A tool whose reach belongs to the thing that called it has its constructor bind it to that thing instead, so one instance serves one turn and what it can reach is fixed before the model composes an argument rather than being named in one: `AUC-ask-user-comment-tool.md`'s, `PDC-propose-draft-changes-tool.md`'s, and `PPC-propose-prompt-changes-tool.md`'s are bound to a conversation, and `ESU-escalate-to-user-tool.md`'s and `RGF-read-graduation-file-tool.md`'s to a graduation run. Either way it holds nothing between calls, and construction stays cheap enough that per-turn construction costs nothing beside the model call the turn is about to make.
16. **TLC-FR-16** A tool answers from state as it stands and never blocks on background work. It waits on no index pass, no scan, and no watcher, so a call made while the project is still settling returns what is available at that moment rather than holding the agent's turn open.
17. **TLC-FR-17** Every tool declares its side effects in its own spec, and the declaration is exhaustive: a tool changes exactly what its own specification says it changes and nothing besides. A tool declared read-only creates, modifies, and deletes no file anywhere, mutates no store, and touches no repository state. Most tools here are read-only and the declaration is the short one; a tool that is not says in its own contract surface precisely what one successful call alters, so that what an agent can do to a project is readable from the tools it was attached to rather than inferable only from their code.
18. **TLC-FR-18** No model-facing tool reads, holds, or returns a credential: no API key, token, or keychain entry is reachable through its arguments, output, error message, or log record, so nothing a model composes and nothing a model reads can touch one. The one tool that carries a credential is `EAC-execute-agent-cli.md`, which needs one to authenticate the agent it launches (EAC-FR-15, EAC-FR-16) and which no model can reach — and even there the credential enters through an internal handoff rather than a caller's argument, reaches exactly one container, and appears in no argument vector, no log record, no error payload, and no returned value.
19. **TLC-FR-19** Adding a model-facing tool to this group adds a spec and a constructor, changes no existing tool, and changes nothing here but the illustrative lists that name which tools carry which property (TLC-FR-14, TLC-FR-15, TLC-FR-18) — none of which is a registry, and none of which any implementation reads. Because there is no registry, an existing consumer keeps exactly the tools it named until it names another. Adding a provider-native tool adds a spec and one definition entry and no constructor at all, and it reaches an agent only where a consumer named it for a provider that serves it (TLC-FR-23, TLC-FR-24). The loop-facing class holds exactly one member, and a second one would be a change to this spec's shape rather than an addition under it.
20. **TLC-FR-20** A loop-facing tool is reached only from backend loop code through its typed Rust API, and there is no path by which a model can call it: it has no `NAME`, no `description()`, and no `parameters()`, appears in no `ToolDefinition` sent to any provider, and is attachable to no agent. Its request and response types are strictly decoded wherever they cross a serialization boundary, rejecting an unknown field rather than ignoring it and refusing an out-of-range value rather than clamping it, because its arguments were composed by a compiler rather than by a model and a silent coercion would hide a caller's mistake. Its failures are variants of its own error enumeration rather than a `ToolExecutionError`, and each variant exists because its caller has to act differently on it.
21. **TLC-FR-21** A provider-native tool is one **definition entry** and nothing else. The application implements no part of it: it declares no `rig::tool::PortableTool`, no `NAME`, no `description()`, no `parameters()`, no argument type, no output shape, no error type, and no `call()`, and it holds no constructor for one. The provider names the tool the model sees, publishes the schema the model composes against, executes every call, and produces every result, so what the application decides is whether the entry is offered and nothing beyond that. Like every other member of this group it registers no Tauri command, emits no Tauri event, and is unreachable from the frontend. Its own spec states the exact entry, the provider that serves it, and what that provider produces. TLC-FR-02 through TLC-FR-20 govern the two classes the application implements and govern nothing here, there being no local name, description, schema, output shape, refusal, or call for any of them to govern.
22. **TLC-FR-22** An entry is fixed text compiled into the binary, on the terms a tool's description and schema are fixed (TLC-FR-05): it is never assembled per call, varied by caller, derived from project state, or configurable by the author. Nothing about a provider-native tool is settable or stored anywhere in the application — no control on a settings surface, no field of a stored provider record, no key in the persistence format, no command argument, no validation rule, and no field of a configuration response — so the capability behaves identically for every author, every project, and every agent, at whatever default the provider applies to an entry carrying its type and nothing else.
23. **TLC-FR-23** An entry belongs to exactly one provider and is attached only to a request that provider carries. A request carried by any other provider carries no part of it, and nothing local stands in for it there: the capability is absent from that provider's conversations until that provider's own native contract is defined and mapped here, at which point it is that provider's own entry rather than a translation of this one. Tool definitions are therefore selected from the provider resolved for the call (per `../core/AAP-ai-api-integrations.md` AAP-FR-34) rather than from anything the author, the agent, or the model asked for.
24. **TLC-FR-24** A provider-native tool is attachable from a **conversational** origin alone (per `../ai/CVL-conversation-loop.md` CVL-FR-30). No graduation phase, no clarification judgement, and no other agentic loop attaches one, whichever provider carries it, so a capability whose arguments the application never sees stays where an author reads every answer it contributed to.
25. **TLC-FR-25** The application performs none of the work. It makes no request of its own to carry out a provider-native tool call, implements no local equivalent of one, holds no client and no credential for one beyond the provider key already resolved for the model call itself (per `../core/AAP-ai-api-integrations.md` AAP-FR-34), and keeps no fallback that answers when the provider's execution fails. It rewrites neither the call nor the result: what the provider produced is what the model reads (per `../ai/CVL-conversation-loop.md` CVL-FR-31), and a failure the provider reports for one of its own tools is material the model acts on rather than a failure of the turn.
26. **TLC-FR-26** A provider-native tool emits no log record of its own, there being no call the application makes and no boundary of its own to record. What is recorded about it is its loop's (per `../ai/CVL-conversation-loop.md` CVL-FR-28, CVL-FR-34), which names who was asked, of what, how it went, and which of the provider's own tools ran, and which measures a call rather than reading it — so no argument a model composed for such a tool and no part of a result it read reaches any record.
27. **TLC-FR-27** A call in flight is reported to the author as one short **activity status** naming what is being done, and the wording belongs to the surface rather than to the tool: no tool in this group declares a status of its own, carries one in its definition, or returns one, and what an author reads for a given tool is fixed by the surface rendering it (per `../ui/CTA-comment-agent-turns.md` CTA-FR-HEYB). A call whose tool that surface holds no wording for — a tool it never offers, and a tool this group holds that its own vocabulary does not name — reads **Working…**, the fallback every surface uses and the reason a status is never empty and never falls back to a tool's own name. A tool added to this group therefore leaves no surface blank (TLC-FR-19), and a status says what a tool is for and never what a call is doing it with: no argument the model composed, no value a tool returned, and no part of what it read is in one (per `../ai/CVL-conversation-loop.md` CVL-FR-27).

## Non-functional requirements

- The `rig` version this group targets is the one the crate manifest pins; `PortableTool`, `ToolDefinition`, `ToolExecutionError`, and `ToolErrorKind` are that framework's types rather than anything defined here, and this spec constrains only how they are used.
- A tool's description is the most expensive text in the group by consequence per byte: it is sent to a provider on every request that offers the tool, and it is the whole basis of the model's decision. Length is worth spending where it removes a wrong call and worth cutting everywhere else.
- Serialisation of arguments and data-shaped output is `serde`'s, so a field's name in the output shape is its name on the wire and renaming one changes what the model reads. A document-shaped output has no field name to rename: it is the file's text and nothing else.
- A tool's own work is bounded by the module it delegates to, and nothing here introduces an unbounded operation or a retry loop. The loop-facing tool is the one that waits on something of its own, and that wait is bounded by a deadline its caller supplied rather than by anything it chose.
- No model-facing tool the application implements requires network access, and none of them reaches a model: a tool is called *by* a model, never the reverse. A provider-native tool requires none of the application's network access either — the request it needs is one the provider makes for itself, inside the model call the loop was already making. The loop-facing tool is the exception on both counts — it launches an agent, and the container it launches reaches that agent's own service — which is precisely why it is not a capability a model may select.
- Access to tools is logged using the logging framework described in `../core/LGC-logging.md`.
