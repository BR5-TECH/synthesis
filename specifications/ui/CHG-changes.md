# Changes

**Spec code:** `CHG`

## Intent
Vertical-panel surface that answers "what have I changed?" and turns that answer into a commit without leaving the authoring context. It renders the project's changed files as the same folder-mirroring tree the Project panel uses, tagged by artifact type, filterable by the same lenses, with a `+added −removed` summary on every row and a checkbox on every row deciding what the next commit carries. Two modes serve two questions: **Uncommitted** shows what is modified but not yet committed and is where committing happens, and **Branch** shows everything the current branch introduces relative to a configurable target branch. What the author ticks is also what they can take back: the checked set the panel commits is the checked set it **rolls back**, returning those files to `HEAD` — discarding tracked edits staged and unstaged alike, deleting untracked files, and throwing away the in-memory edits behind them — so the surface that answers "what have I changed?" is also the one where a change is undone rather than hunted down file by file. It exists because the v1 interactive loop (author in Synthesis → commit → an external agent picks the artifacts up) makes "which artifacts did this session touch, and which of them am I handing off?" the question the author asks constantly, and answering it by scanning a flat porcelain list in the bottom panel loses the folder structure and the artifact typing that make the project legible. Out of scope: the panel commits, pushes, and rolls back, and does nothing else to the repository — branch creation, checkout, pull, and pull-request work live in the bottom-panel Git surface (`GIT-git.md`) — and the index is not a concept it exposes: the author ticks paths rather than staging them, and a rollback discards a path's staged and unstaged state together rather than offering to unstage it.

## User stories
- As a user, I want my uncommitted changes grouped by folder and tagged by artifact type so that I can see at a glance which Skills, Agents, and Specs this session touched.
- As a user, I want to filter the change list down to one artifact type so that I can review just the Specs I edited without the lockfiles and build output in the way.
- As a user preparing a hand-off, I want every file my branch introduces relative to `main` — committed and uncommitted alike — so that I can review the whole contribution as one set.
- As a user, I want files Git does not track yet called out separately so that I never commit assuming a new artifact was already included, and I want ticking one to be all it takes to get it into the commit.
- As a user, I want the files Git already tracks gathered under a group of their own, so that one tick hands the whole of this session's edits to the commit without my walking down every folder holding one.
- As a user, I want to tick exactly the artifacts this session produced and commit them under one message, so that the hand-off commit holds what I meant and nothing else.
- As a user who commits and pushes in one habitual motion, I want the button to remember which of the two I do, so that I am not re-choosing it on every commit.
- As a user, I want to click any changed file and read its diff in the main viewport, where there is room for it.
- As a user reviewing uncommitted changes, I want to select specific files and deliberately discard them so that I can return them to `HEAD` without leaving the Changes panel.
- As a user, I want selected untracked files deleted and open Editor and Diff buffers reset too, so that a rollback does not leave the filesystem, the tabs, and Git status disagreeing about what the file holds.
- As a user, I want a clear confirmation listing the affected paths, because a rollback cannot be undone from the panel.

- Layout notes: the wireframe shows the **All files** lens so the tree shape is legible; under the default **All artifacts** lens only the rows carrying a type tag (`SKILL.md`, `CHG-changes.md`) and the folders holding them remain, and the rest of the tree collapses away. The tree's top level is two groups — **Revisioned** then **Unrevisioned** — each carrying its own full folder nesting, and their labels are set in a heavier weight than the folder nodes beneath them so the two spines of the tree read apart from the folders at a glance. Every folder node and both group labels carry a count of the changed files visible beneath them, worded with the noun it counts — `1 file`, `13 files` — and placed immediately after the label rather than in the trailing column the diffstats occupy, so a folder's file count is never read as a line count; it is set a point below the UI role's size in a recessive foreground so it reads as a hint on the row rather than a second label competing with the folder's name, and at a panel width too narrow to hold both, the label truncates while the count keeps its place whole — a count cut short says less than the bare number it is made of, and this is the rule a file row already narrows by, its name yielding to the diffstat pinned beside it. Every file row carries its diffstat right-aligned; a binary entry substitutes a `binary` marker for the counts, and a renamed entry shows its previous path beside its current name. The checkbox is the leading element of every row, ahead of the disclosure triangle's indentation guide, so the column of checkboxes reads straight down whatever the nesting depth. A file row renders its name and any previous path in the case they carry on disk (per `SNV-shell-navigation.md` SNV-FR-57). The panel's three narrowing controls are arranged as every vertical panel arranges them (per `SNV-shell-navigation.md` SNV-FR-58): the in-tree text search directly beneath the panel header, then the selectors descending from broadest to narrowest — the mode toggle with its target-branch picker, then the artifact-type lens directly above the tree. The lens is the single-line toggle row of `SNV-shell-navigation.md` SNV-FR-62, each button a short text tag set in the same treatment the tree's own type tags carry and disclosing the type's full name on hover, clipping at its trailing edge rather than wrapping (SNV-FR-63); the text and lens rows read identically to the Project panel's. The footer is pinned to the bottom of the panel below the scrolling tree, with the rollback button at its leading edge and the split button at its trailing edge; the split button's footprint does not change as the selected action changes, and the two halves of that button carry one enabled-or-disabled appearance between them. The count of selected files stands on a row of its own directly above the footer and below the tree, spanning the panel's width and set in the same recessive treatment the folder counts take (CHG-FR-53). Because the rollback button holds the leading corner and the split button the trailing one, a mode that renders no rollback button moves nothing in the footer. The inline failure report of a partial rollback opens above the count row, so the tree yields the height rather than the two rows beneath it moving. The confirmation is a floating overlay centred over the window, bounded in height with its path list scrolling within it, its dismissive action leading and its destructive action trailing on one row at its foot. Panel width, collapse-to-icon, and hide are inherited from `SNV-shell-navigation.md`.

## UI contract boundary
- **Owned by the UI**: the mode toggle and which mode is active; the target-branch picker control; assembly of the flat change list into the nested folder tree; the split of that tree into the **Revisioned** and **Unrevisioned** groups, their order, and their internal nesting; the count of visible changed files each folder node and group node states; per-row diffstat, binary-marker, and rename rendering; the artifact-type tag display; the local filter UI (the artifact-type lens toggle row, which per-type buttons it renders at all, and the in-tree text search) and the folder-visibility computation those filters drive; expand/collapse and selection state; the checkbox column, every check's state, the folder cascade and its indeterminate rendering, and the computation of the commit set from checks and visibility; the footer's split action control, which action is selected, and the enablement of every action; the count row and its wording; the rollback button, its enablement and the reason its tooltip states, the rollback confirmation and everything it lists, the derivation of the rollback set from checks and visibility, the quiescing of the affected editing sessions and the wait on their in-flight saves before the operation is invoked, the per-path application of the returned outcome to checks and sessions, and the inline report of what failed; the decision to open the commit message window and the set handed to it; the routing of an authentication failure to either the token picker modal or the Global settings GitHub section; the file, comparison, and resolved artifact type a Diff tab is opened on; the revealing of a changed file another surface names — expanding its ancestors, selecting its row without touching any check, and relaxing whichever local filter would hide it (CHG-FR-54), which introduces no backend operation; inline rendering of the not-a-repository, empty, unknown-branch, and push-failure states; and panel width/collapse/hide state (inherited from `SNV-shell-navigation.md`). The UI does not classify artifact types, compute diffstats, resolve branches, or count what a remote holds, and it renders no diff itself — what a Diff tab shows is owned by `DFV-diff-viewer.md`.
- **Delegated to backend (abstract)**:
  - `"list uncommitted changes"` — the change set for Uncommitted mode. Owned by `../core/CHC-changes.md`.
  - `"list branch changes (target branch)"` — the change set for Branch mode. Owned by `../core/CHC-changes.md`.
  - `"get default branch"` — the repository's default branch, used as the initial target. Owned by `../core/CHC-changes.md`.
  - `"list comparison branches"` — populates the target-branch picker. Owned by `../core/CHC-changes.md`.
  - `"get upstream sync state"` — whether the current branch holds commits the remote does not, which decides whether **Push** is available. Owned by `../core/GTC-git.md`.
  - `"push current branch"` — the push the panel performs. Owned by `../core/GTC-git.md`.
  - `"rollback paths (paths)"` — the discard the panel performs, returning the named paths to `HEAD` and reporting the outcome of each path on its own. Owned by `../core/GTC-git.md` (GTC-FR-23).
  - `"save artifact contents"` — not invoked by this panel, but awaited by it: an in-flight write for an affected artifact must settle before a rollback is invoked (CHG-FR-60). The panel reaches it through the artifact's editing session rather than directly (per `EDT-editor.md` EDT-FR-81). Owned by `../core/PST-project-storage.md`.
  - `"append log records (records)"` — carries the one diagnostic this panel emits, the `ERROR` record for a save that failed while a rollback was being prepared (CHG-FR-61). Owned by `../core/LGC-logging.md`.
  - `"load changes panel state"` and `"save changes panel state"` — the persisted mode and target branch. Owned by `../core/PSS-project-settings-storage.md`.
  - `"load app preferences"` and `"save app preferences"` — the persisted selected action. Owned by `../core/GSS-global-settings-storage.md`.
  - The event `"changes updated"` — owned by `../core/CHC-changes.md`.
  - The event `"git operation finished"` — the terminal status of a push. Owned by `../core/GTC-git.md`.
  - The commit itself is invoked by the commit message window this panel opens, through `"commit paths (message, paths)"` (`CMW-commit-message.md`, owned by `../core/GTC-git.md`).

## Functional requirements
1. **CHG-FR-01** Changes is a vertical-panel surface with its own activity-bar toggle (per `SNV-shell-navigation.md` SNV-FR-03). It is not the default selection on project open; the Project panel is (per `OVW-overview.md` OVW-FR-05).
2. **CHG-FR-02** The panel has exactly two mutually-exclusive modes, **Uncommitted** and **Branch**, selected by an in-panel toggle in the panel header.
3. **CHG-FR-03** In Uncommitted mode the panel renders the change set returned by `"list uncommitted changes"`.
4. **CHG-FR-04** In Branch mode the panel renders the change set returned by `"list branch changes (target branch)"` for the currently configured target branch.
5. **CHG-FR-05** A target-branch picker is shown in Branch mode only; its options come from `"list comparison branches"`, and selecting one re-renders the panel against that branch. It names the branch the panel diffs *against* and never changes what is checked out: the branch the user is working on is the one the worktree selector shows (`WTS-worktree-selector.md` WTS-FR-03), and selecting a comparison target here neither checks anything out nor moves the active worktree.
6. **CHG-FR-06** On the first open of a project the target branch is the repository's default branch, obtained from `"get default branch"`.
7. **CHG-FR-07** The active mode and the configured target branch persist per machine and per worktree via `"save changes panel state"` and are restored on the next open of the same worktree via `"load changes panel state"`, so each checkout keeps the comparison it is usually reviewed against.
8. **CHG-FR-08** The panel renders changed files as a nested folder tree that mirrors the project's on-disk folder structure, with changed files as the only leaves. A folder node is rendered only when its subtree contains at least one currently-visible changed file; folders with no visible changed descendant do not appear.
9. **CHG-FR-09** The tree's top level holds exactly two groups: **Revisioned**, holding every entry Git already tracks, and **Unrevisioned**, holding every entry whose change status is untracked. **Revisioned** renders first and **Unrevisioned** second, each containing its own nested folder tree built by the rule of CHG-FR-08, and no changed file renders outside a group. A group that holds a visible file renders its own label whatever the other group holds, so the tree has no flattened form in which changed files sit at the top level. Both group labels render in a heavier weight than the folder nodes beneath them.
10. **CHG-FR-10** Each file row displays the entry's diff summary as an added-line count and a removed-line count.
11. **CHG-FR-11** A file row for a binary entry displays a binary marker in place of the line counts.
12. **CHG-FR-12** A renamed entry is placed in the tree at its current path and additionally displays its previous path.
13. **CHG-FR-13** Each file row displays its resolved artifact type as a tag; a file with no resolved type is shown without a tag, with the same tag rendering the Project panel uses (per `LIB-library.md` LIB-FR-08).
14. **CHG-FR-14** The panel exposes two local filters — an in-tree text search and an artifact-type lens — whose positions, form, and matching regimes are identical to the Project panel's (per `LIB-library.md` LIB-FR-04 and LIB-FR-05), and which are AND-combined with each other. The lens renders a per-type button only for a type at least one entry in the current change set resolves to, on the terms `LIB-library.md` LIB-FR-19 states, so the row offers the types this comparison actually touched; **All artifacts** and **All files** always render, as does whichever position is active. Because a comparison holds fewer types than the whole project does, the row is typically shorter here than in the Project panel.
15. **CHG-FR-15** The artifact-type filter defaults to **All artifacts**, so on first render the panel shows only changed files with a resolved artifact type; unclassified changed files appear once the user selects **All files** (matching `LIB-library.md` LIB-FR-12).
16. **CHG-FR-16** The filters apply inside both groups identically to the rest of the tree, and a group is hidden when no file inside it is currently visible.
17. **CHG-FR-17** Expand/collapse state per node and the current selection are preserved while the user changes filters, across vertical-panel collapse/hide cycles within a session, and across reloads triggered by CHG-FR-19 and CHG-FR-20.
18. **CHG-FR-18** Clicking a file row opens a Diff tab in the main viewport on that file for the panel's currently active comparison (per `DFV-diff-viewer.md` DFV-FR-01). The panel supplies the file, the comparison, and the file's resolved artifact type — which it already holds for every row (CHG-FR-13), and which is what lets the tab tell a Flow from any other file without re-deriving a classification the backend owns (`DFV-diff-viewer.md` DFV-FR-17). What the tab renders and how is owned by that surface. Toggling a row's checkbox is not a click on the row: it changes the check and opens nothing.
19. **CHG-FR-19** The panel subscribes to the `"changes updated"` event and reloads the active mode's change set when it fires, preserving the state of CHG-FR-17 and CHG-FR-31.
20. **CHG-FR-20** The panel exposes a manual refresh affordance that re-invokes the active mode's list operation and re-renders the returned change set.
21. **CHG-FR-21** The panel's reach over the repository is exactly three operations: committing the checked set (CHG-FR-40), pushing the current branch (CHG-FR-43), and rolling the checked set back to `HEAD` (CHG-FR-62). It exposes no staging or unstaging, creates and checks out no branch, pulls nothing, and opens no pull request; those belong to `GIT-git.md`. The two writes it makes into the working tree are the rollback's own — the restoration of a tracked path and the removal of an untracked one — and each is made only for a path the author checked and then confirmed by name (CHG-FR-59); no other route in this panel writes a file. The Diff tab it opens reaches the repository no further than this panel does (per `DFV-diff-viewer.md` DFV-FR-06): the author may correct the target revision there, which writes that one file through the write path the file already has, and nothing in that tab stages, commits, pushes, or rolls back anything.
22. **CHG-FR-22** When the open project is not a Git repository, the panel renders the first-class empty state of `SNV-shell-navigation.md` SNV-FR-60 in place of the tree, explaining that the project is not a repository and carrying no action, and does not fail to render.
23. **CHG-FR-23** When the active mode's change set is empty, the panel renders that same first-class empty state (per `SNV-shell-navigation.md` SNV-FR-60) in place of the tree, stating that the mode's comparison yields no change. It is composed and placed exactly as the not-a-repository state of CHG-FR-22 and says a different thing, so the two are told apart by what they state rather than by where they sit — an author who cannot commit needs to know which of the two situations they are in.
24. **CHG-FR-24** When the configured target branch does not resolve — for example it was deleted since it was persisted — Branch mode renders an inline error naming the branch, and the target-branch picker stays usable so the user can select an existing branch. The panel does not silently substitute a different target branch.
25. **CHG-FR-25** Every change set the panel renders describes the project's active worktree (per `../core/CHC-changes.md` CHC-FR-02); no entry from another worktree of the same repository ever appears. When the active worktree changes (per `OVW-overview.md` OVW-FR-12) the panel discards the change set it was showing and restores that worktree's own persisted mode and target branch (CHG-FR-07) before reloading. Any Diff tab the panel opened closed with the switch (per `TAB-tabs.md` TAB-FR-14), so no tab keeps rendering a comparison from the previous content root.
26. **CHG-FR-26** In Uncommitted mode every file row, every folder node, and both group nodes carry a checkbox. Branch mode renders none, because its change set mixes committed and uncommitted work and a check over it would name no commit the panel could make.
27. **CHG-FR-27** The **commit set** is exactly the file rows that are both checked and currently visible under the active filters (CHG-FR-14). A row the filters hide contributes nothing to a commit whether or not it was checked while visible, so a check the author cannot see never quietly joins a commit. The one way a hidden path reaches a commit is the author being shown it and asked (CHG-FR-48), and even then it reaches them by name in the commit message window before anything is created (`CMW-commit-message.md` CMW-FR-06).
28. **CHG-FR-28** Checking or unchecking a folder node or a group node checks or unchecks every currently-visible changed file in its subtree, so a single tick on **Revisioned** takes every tracked change the filters are showing and a single tick on **Unrevisioned** takes every new file, each without disturbing the other group. A folder or group renders checked when every visible changed file beneath it is checked, unchecked when none is, and indeterminate when some are.
29. **CHG-FR-29** A row's check is retained while the filters hide it, so re-revealing the row restores the check the author left on it; it re-enters the commit set only once it is visible again (CHG-FR-27).
30. **CHG-FR-30** Every entry of a freshly loaded change set arrives unchecked, and an entry appearing for the first time in a reload (CHG-FR-19, CHG-FR-20) arrives unchecked, so nothing is ever committed that the author did not tick in this session.
31. **CHG-FR-31** Check state is keyed by path and survives filter changes, vertical-panel collapse/hide cycles, and the reloads of CHG-FR-19 and CHG-FR-20, on the same terms as CHG-FR-17. An entry that leaves the change set loses its check and does not regain it by reappearing.
32. **CHG-FR-32** Check state is held in memory and never persisted. It is discarded when the project closes and when the active worktree changes (CHG-FR-25), so a newly opened project and a newly activated worktree both start with nothing ticked.
33. **CHG-FR-33** The panel's footer holds two controls: the rollback button at its leading edge (CHG-FR-56) and, at its trailing edge, a split control — a primary button performing the selected action, and an attached dropdown selecting among exactly three actions, **Commit**, **Commit & Push**, and **Push**. How many files the commit set holds is stated not here but on the row directly above the footer (CHG-FR-55). The dropdown behaves as every menu in the application does: it is dismissed by a click outside it, by Escape, and by the window losing focus, and activating another control that opens a menu of its own dismisses it on the way — no two menus stand open at once. The Escape that closes it closes **only** it: where the control stands inside a surface that itself dismisses on Escape, one keystroke takes down one layer. The split control is **shared**: the graduation publication choice performs its three outcomes on the same control, with its own actions, and a graduation's start preflight performs **Commit** and **Commit & Push** on it with **Push** standing inactive, so a change set published from a graduation and a worktree committed before one starts are both committed by the same gesture as a working tree committed here. Nothing about which actions the control offers, which of them can be performed, or what performing one does belongs to the control itself.
34. **CHG-FR-34** The selected action is user-global. The panel reads it on mount from `"load app preferences"` and writes it through `"save app preferences"` whenever the author picks a different one (per `../core/GSS-global-settings-storage.md` GSS-FR-25), so it is one choice across every project and every worktree, and it defaults to **Commit**. This panel is the only surface that **writes** it: a graduation's start preflight opens its control on the same stored value and never writes one back, because what an author chose for one blocked graduation is not the committing habit this record describes.
35. **CHG-FR-35** The dropdown draws the line at what the author can change. **Commit** and **Commit & Push** are always selectable, because what makes them unavailable is the author's own current selection — an empty commit set, or Branch mode — and picking the action they are about to tick files for is how they work; selecting one while it is unavailable persists the choice (CHG-FR-34) and leaves the primary button disabled. **Push** is selectable only while it is available (CHG-FR-37), because nothing the author does in this panel makes a branch that is level with its remote pushable; while it is unavailable it renders in the dropdown as an inactive entry rather than disappearing, so the control reads as the same three actions whatever the repository can do at this moment. The reason an entry is inactive is available on hover and nowhere else: the dropdown carries the action names alone, because an explanation the author has not asked for does not belong in a label. A **Push** already persisted from an earlier session stays the selected action and is not silently replaced (per `../core/GSS-global-settings-storage.md` GSS-FR-25); the primary button is simply disabled until the branch has something to publish.
36. **CHG-FR-36** **Commit** and **Commit & Push** are enabled only while the panel is in Uncommitted mode and the commit set (CHG-FR-27) is non-empty. A clean working tree, a change set with nothing ticked, and Branch mode each leave them disabled.
37. **CHG-FR-37** **Push** is enabled only while the current branch holds commits its remote does not, as reported by `"get upstream sync state"`: a branch with a configured remote and no upstream yet is pushable, because the push publishes it; a branch level with or behind its upstream is not; and a repository with no remote configured leaves **Push** disabled. Push's enablement is independent of the checkboxes and of the active mode.
38. **CHG-FR-38** The panel reads `"get upstream sync state"` on mount and again whenever `"changes updated"` fires (per `../core/CHC-changes.md` CHC-FR-16), so **Push** becomes available as soon as a commit lands and unavailable once a push completes. That state is resolved from local refs alone (per `../core/GTC-git.md` GTC-FR-21), so it describes the remote as of the last fetch.
39. **CHG-FR-39** Activating **Commit** or **Commit & Push** opens the commit message window (`CMW-commit-message.md` CMW-FR-03) carrying the commit set as it stands at that moment, together with the changed files the active filters are hiding (CHG-FR-48). Nothing is committed until that window is confirmed with a non-empty message (CMW-FR-05); dismissing it commits nothing and leaves every check as it was.
40. **CHG-FR-40** The commit is performed by that window through `"commit paths (message, paths)"` (per `CMW-commit-message.md` CMW-FR-07). Entries of the commit set the change set reports as untracked are added to version control by that operation (per `../core/GTC-git.md` GTC-FR-19); the panel names paths and draws no distinction between them.
41. **CHG-FR-41** When the window reports the commit succeeded, every check clears and the panel reloads on the `"changes updated"` that commit produces (CHG-FR-19). That same report carries the paths the commit recorded (per `CMW-commit-message.md` CMW-FR-07), which is what closes the Diff tabs this panel opened on those files (per `TAB-tabs.md` TAB-FR-22) — the review each was opened for having been finished by the commit. A rejected commit stays in the window with its message (per `CMW-commit-message.md` CMW-FR-08), closes no tab, and leaves every check exactly as it was.
42. **CHG-FR-42** **Commit & Push** pushes only after its commit has succeeded; a rejected or abandoned commit pushes nothing. Its push half is the same operation **Push** performs (CHG-FR-43) and behaves identically in every respect, failures included.
43. **CHG-FR-43** **Push** invokes `"push current branch"`. Its output streams into the push/pull output area of the Git panel's Logs section (per `GIT-git.md` GIT-FR-PZIE) and its progress is reported by the status bar (per `../core/PRG-progress-reporting.md` PRG-FR-11); the panel itself renders only that a push is running and how it ended, and hosts no output area of its own. A push is one shared operation across this panel, the Git panel, and the top-chrome **Push** control (`GIT-git.md` GIT-FR-QMYB). The terminal status arrives on `"git operation finished"` (per `../core/GTC-git.md` GTC-FR-04).
44. **CHG-FR-44** While a commit or a push started here is in flight the primary button is disabled, so neither can be submitted twice. While a push is running that another control started — the Git panel's **Push** or the top-chrome **Push** control (`GIT-git.md` GIT-FR-XXLE) — **Push** and **Commit & Push** are unavailable too, and the dropdown renders **Push** as an inactive entry stating that a push is already running.
45. **CHG-FR-45** A push that fails because the project resolves no GitHub token is answered according to its typed cause (per `../core/GTC-git.md` GTC-FR-10): `github_token_selection_required` opens the token picker modal (`GHA-github-authentication.md` GHA-FR-16), and the push runs on confirmation and is abandoned on cancellation (GHA-FR-17); `github_token_missing` renders inline in the panel with a route to the Global settings GitHub section (GHA-FR-19).
46. **CHG-FR-46** Any other push failure renders inline in the panel naming what failed. A commit that succeeded ahead of a failed push stands — the panel undoes nothing — and the author retries with **Push**.
47. **CHG-FR-47** The not-a-repository state (CHG-FR-22) renders neither checkboxes nor the action control, because there is nothing to commit to.
48. **CHG-FR-48** The panel hands the commit message window every changed file the active filters are currently hiding, so that window can ask before a commit leaves them behind (`CMW-commit-message.md` CMW-FR-13). This exists because the default **All artifacts** lens (CHG-FR-15) hides exactly the work an artifact produces — the code and tests written from a Spec — and a commit of the Spec alone is a hand-off missing the thing it describes. The set offered is the hidden one only: a row the author can see and chose to leave unticked is a decision, not an oversight, and is never offered back. A commit set the filters hide nothing behind is offered nothing, and the window opens straight on its message.
49. **CHG-FR-49** The footer's split control is one object carrying one appearance: while the selected action cannot be performed (CHG-FR-36, CHG-FR-37) the whole control — the primary button and the attached dropdown alike — takes the unavailable treatment, rather than dimming the primary half against a fully-saturated dropdown half. That treatment describes the selected *action*, not the control's reachability: the dropdown stays operable throughout and answers hover and focus like any other menu control, because changing the action is exactly what an author does when the current one cannot be performed (CHG-FR-35).
50. **CHG-FR-50** Every folder node and both group nodes state, immediately after their label, how many changed files are currently visible beneath them. The number is recursive over the node's whole subtree — every visible file row at any depth below it, not its direct file children alone — so a group node states the total of everything it holds. It renders in both modes and whether the node is expanded or collapsed, so a folder answers "how much is in here?" without being opened and keeps answering it once it is.
51. **CHG-FR-51** The count is stated with the noun it counts and agrees with it in number — `1 file`, `13 files` — rather than as a bare numeral, so a row reads as a sentence about its contents instead of leaving the reader to infer what the digit beside a folder measures.
52. **CHG-FR-52** A node's count describes exactly what the tree renders: it counts the file rows currently visible under the active filters (CHG-FR-14) and re-computes as those filters change, so the number always equals the file rows that expanding the node reveals. No node ever states a count of zero, because a node with no visible changed descendant is not rendered at all (CHG-FR-08, CHG-FR-16).
53. **CHG-FR-53** The count sets in the **UI** typographic role (per `OVW-overview.md` OVW-FR-13) one step below the size the node's own label is set at — a point smaller at the role's default size — and in a foreground recessive against that label, so it is visually distinct from the folder name it follows and reads as a hint rather than part of it. Both sizes are ratios of the role's configured size, so the pair moves together as the author changes it (per `OVW-overview.md` OVW-FR-14) and the count carries no fixed size of its own. It introduces no activation target of its own: a pointer on the count does what a pointer elsewhere on that node's row does, and it toggles no check.
54. **CHG-FR-54** Another surface may ask the Changes panel to reveal a changed file, naming it by its path. The panel expands every ancestor folder node and the group node above it, scrolls the file row into view, and makes it the current selection (CHG-FR-17). What is selected is the **file row** and never a folder or a group node, and the row is reached where the change set already places it — under whichever of the two groups of CHG-FR-09 the backend reports it in — so a reveal renders what the panel has rather than reclassifying anything. **Revealing changes no check.** It never toggles the revealed row's checkbox, never toggles any other row's, and never touches a folder or group cascade (CHG-FR-28); selecting a row and ticking one are separate acts here exactly as they are for a click (CHG-FR-18). Where a local filter would hide the row the panel relaxes that filter — switching the artifact-type lens to **All files** and clearing the in-tree text search — and only the filters that would actually hide the row are touched. Relaxing the lens re-reveals every row that lens was hiding, and a row the author had checked before it was hidden re-enters the commit set on the ordinary terms of CHG-FR-29: what a reveal changes is which rows are visible, never which are checked. The panel's **mode** and **target branch** are not filters and no reveal changes either (CHG-FR-02, CHG-FR-05), because they choose which comparison the panel is answering about rather than narrowing one; a file the active mode's change set does not hold therefore cannot be revealed, and the tree, the filters, the checks, and the selection are all left exactly as they are with nothing reported. A reveal is about where the row sits in this panel and says nothing about which surface the vertical panel is showing, which is the caller's decision (per `SNV-shell-navigation.md` SNV-FR-45). This is the path a Diff tab's own file takes when the vertical panel follows the active tab (per `SNV-shell-navigation.md` SNV-FR-64, SNV-FR-66).
55. **CHG-FR-55** How many files are selected is stated on a **row of its own**, spanning the panel between the scrolling tree and the footer. It counts the commit set (CHG-FR-27) and words the count with the noun it counts, agreeing in number — `1 file selected`, `2 files selected` — on the terms CHG-FR-51 sets for every count this panel states, and it renders whether the number is zero or not, so the row does not appear and disappear beneath the tree as the author ticks. It renders in Uncommitted mode alone, Branch mode having no checkbox to count (CHG-FR-26). It is a statement rather than a control: it takes no activation, toggles no check, and is not a filter.
56. **CHG-FR-56** The footer's leading edge holds a **rollback** button carrying the rollback icon, with the split action control keeping the trailing edge (CHG-FR-33). It is rendered in **Uncommitted mode of a Git repository** and nowhere else: Branch mode renders none, having no checked set and no working-tree question to answer, and the not-a-repository state renders none along with everything else it withholds (CHG-FR-47). Its absence reflows nothing, the split control holding the trailing edge whether or not the leading corner is occupied.
57. **CHG-FR-57** The **rollback set** is exactly the file rows that are both checked and currently visible under the active filters — the same derivation the commit set takes (CHG-FR-27), the folder and group cascades of CHG-FR-28 contributing their visible descendants on the same terms. A row the filters hide contributes nothing to a rollback whether or not it was checked while visible, and an unchecked row contributes nothing at all. Unlike a commit, a rollback is never offered the paths the filters are hiding (CHG-FR-48): a commit that leaves work behind is incomplete, while a rollback that leaves work behind has merely discarded less, and asking to widen a destruction is not a question this panel puts to anybody.
58. **CHG-FR-58** The rollback button is enabled only while all three of these hold: the panel is in Uncommitted mode, the rollback set is non-empty, and the artifact-type lens is **All files** (CHG-FR-14). The lens condition exists because a rollback is not undoable from this panel and the author must be able to see the whole of what they have ticked; under a narrowing lens the tree hides checked rows they cannot review, and CHG-FR-29 keeps those checks alive. Otherwise the button renders in the unavailable treatment, and its tooltip states the reason that currently applies — that no file is selected, or that the lens must be **All files** — naming both when both do. The button carries an accessible name naming the action, and its icon is never the only indication of what it does: the accessible name and the tooltip say it in words, and the confirmation it opens says it again (CHG-FR-59).
59. **CHG-FR-59** Activating the enabled button opens a **blocking confirmation** before anything else happens. It states how many files the rollback set holds and lists every one of them by project-relative path — a renamed entry naming both its current and its previous path, a deletion marked as one — and it warns in words that tracked changes, staged changes, untracked files, and unsaved Editor and Diff edits will all be discarded and that the panel cannot undo it. It is a floating overlay and is mutually exclusive with the window's others (per `SNV-shell-navigation.md` SNV-FR-56). **Cancel, Escape, and a dismissal from outside it perform no operation whatsoever**: nothing is quiesced, no save is awaited, no backend call is made, and every check, every buffer, every undo history, and every dirty indicator is exactly as it was.
60. **CHG-FR-60** Confirming does not reach Git immediately. The panel first **prepares**: it quiesces the editing session of every artifact in the rollback set (per `EDT-editor.md` EDT-FR-81), which cancels their scheduled writes, refuses any new edit or save for them from every route, and waits for every already in-flight `"save artifact contents"` affecting one of them to settle — an artifact showing in several Editor and Diff tabs sharing one session and one write, and so being awaited once. `"rollback paths (paths)"` is invoked only once every such write has settled, so no save can land on a file the rollback is about to write. Throughout confirmation, preparation, and execution the rollback button, the split action control, and every file row and checkbox in the tree are **inert**, so the operation cannot be submitted twice; and the preparation renders an explicit in-progress state, because a wait on somebody else's write is otherwise indistinguishable from nothing happening. From the moment preparation begins, no late save, no autosave retry, and no external-change resolution writes an affected file.
61. **CHG-FR-61** A save that fails while a rollback is being prepared is logged as exactly one `ERROR` record through `"append log records (records)"` under the `frontend` domain, carrying the affected artifact and its project-relative path and the save's typed failure as **flat fields** (per `../core/LGC-logging.md` LGC-FR-04). The same failure is retained for the report of CHG-FR-65, so the author sees it as well as the log. It neither blocks the rollback nor is retried: preparation completes once every in-flight write has settled, whatever each returned (per `EDT-editor.md` EDT-FR-81), and the path is rolled back like any other — the author having asked for the buffer to be discarded, a write that failed to persist it has cost them nothing they were keeping.
62. **CHG-FR-62** The panel then invokes `"rollback paths (paths)"` once, naming the project-relative **current** paths of the rollback set. It names paths and nothing else: which of them Git tracks, which are untracked, and which are renames is the backend's to know (per `../core/GTC-git.md` GTC-FR-23), exactly as it is for a commit (CHG-FR-40).
63. **CHG-FR-63** The returned outcome is applied **per path, never per operation**. Only for a path the result confirms in `restored_paths` or `removed_paths` does the panel clear that row's check and reset the artifact behind it — a restored path through the session reset of `EXC-editor-external-change.md` EXC-FR-JAWT, a removed path through the discard of EXC-FR-ZXWI, which closes its tabs (per `TAB-tabs.md` TAB-FR-41) — while a restored path's open Editor and Diff tabs stay open and reload (per `DFV-diff-viewer.md` DFV-FR-58, `TAB-tabs.md` TAB-FR-42). A path the result does not confirm keeps its check, its buffer, its dirty indicator, its undo history, and its external-change state untouched, its quiesce simply lifted. A renamed entry is two identities and each is applied on its own (per `../core/GTC-git.md` GTC-FR-26): the identity the result confirms is reset and the one it does not is left alone, so an entry half of which failed loses neither the buffer nor the edit history behind the half that stands.
64. **CHG-FR-64** After applying the outcome the panel reloads the active mode's change set, on the terms of CHG-FR-20 and with the state of CHG-FR-17 preserved: expand and collapse survive, the selection survives, and every check on a row the rollback did not touch survives (CHG-FR-31). The `"changes updated"` the rollback's own writes produce (per `../core/CHC-changes.md` CHC-FR-16) drives no second reload the author can see, the two coalescing rather than thrashing the tree.
65. **CHG-FR-65** A rollback in which **any** path failed shows no overall success state. The panel reports inline, above the count row, how many of the selected files could not be rolled back, naming each failed path with its typed cause (per `../core/GTC-git.md` GTC-FR-25) together with every save failure retained from preparation (CHG-FR-61), and the reloaded change set shows the repository as it actually now stands — the paths that succeeded gone from it, the paths that failed still in it, still checked, and still available to delete or restore by hand. The report clears on the next rollback and on a manual refresh. In-memory edits behind every path the backend did not confirm are preserved by CHG-FR-63, so no reachable outcome loses an edit without a successful rollback result saying that its file was written.
66. **CHG-FR-66** A graduation's **start preflight** reuses this panel's contracts without reusing the panel. It performs its actions on the split control of CHG-FR-33 with the stored action of CHG-FR-34; it commits through the commit message window this panel opens (CHG-FR-39) and therefore through `"commit paths (message, paths)"` (CHG-FR-40); and its **Commit & Push** pushes through `"push current branch"` after the commit has succeeded, on the terms CHG-FR-42 sets for the order and CHG-FR-45 sets for the two typed token causes. What it does not take is this panel's **selection**: the paths it commits are every uncommitted path the preflight reported rather than a commit set derived from checks and visibility (CHG-FR-27), and no lens, no text search, and no hidden-file question (CHG-FR-48) stands between the two. It opens no Changes panel, reveals nothing here (CHG-FR-54), and leaves every check, every filter, and this panel's mode and target branch exactly as they were; this panel learns of its commit as the ordinary `"changes updated"` reload of CHG-FR-19 and in no other way. Where its push fails the report is the preflight's own rather than this panel's inline one (CHG-FR-46), the author having by then been returned to a graduation rather than to a working tree.

## Non-functional requirements
- The tree renders incrementally; a change set covering a large refactor must not block panel responsiveness.
- Reloads driven by `"changes updated"` must not visibly thrash the tree: the event is debounced upstream (per `../core/CHC-changes.md` CHC-FR-16), and preserving expand, selection, and check state (CHG-FR-17, CHG-FR-31) keeps a reload from being disruptive.
- Folder and group counts are derived from the tree the panel has already built, so they cost no additional backend call and re-compute with a filter change rather than waiting on a reload.
- Diffstat rendering must be stable in width so rows do not shift horizontally as counts change during a reload, and the action control's footprint must be stable as the selected action changes so the footer does not reflow.
- The commit set is derived from what is currently rendered, so no reachable state commits a path the author cannot see in the tree. The rollback set is derived the same way and additionally requires the lens that hides nothing (CHG-FR-58), so no reachable state discards a path the author has not been shown twice — once in the tree and once in the confirmation.
- A rollback is the only thing this panel does that destroys work, and every step of it is answerable: nothing is prepared before the confirmation, nothing is written before every affected save has settled, and nothing in memory is discarded before the backend has confirmed the corresponding path on disk. The failure of one path costs no other path its rollback and costs no path its buffer.
- Preparing a rollback waits only on writes already in flight, never on the rest-after-typing schedule those writes would otherwise have waited out, so the wait is bounded by one filesystem write per affected artifact rather than by a timer.
- The rollback button, the count row, and the confirmation stay usable and legible at the minimum window size the shell supports, the confirmation's path list scrolling within its own bounds rather than growing the overlay past the window.
- Check state is session-lived and in memory; a relaunch into the same project starts with nothing ticked, and no file on disk records what was ticked.
- The panel hosts no push transcript. Push output is wide and line-shaped and belongs in the bottom panel, which is where it renders.
- Reading the upstream sync state reaches no remote, so opening the panel offline neither stalls nor errors; only a push touches the network.
- The panel renders its empty and not-a-repository states without network access.
