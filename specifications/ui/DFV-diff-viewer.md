# Diff viewer

**Spec code:** `DFV`

## Intent
The main-viewport tab that shows what changed in one file under one comparison, and lets the author fix what they find there without leaving it. It is the surface an author reaches for between editing and committing — "show me exactly what I did to this file" — and it answers that question three ways, because the shape of the change decides which reading is clearest: a **unified** column for a scattered edit, a **side-by-side** pair for a rewrite where the old text is the context, and the **final version** — the file as it will land, with what changed on the way to it marked in place — for reading the outcome rather than the transition. Orthogonally it renders either the file's **source** or, for the two shapes that have a reading beyond their text, the **rich** one: a Markdown file as its rendered document, so an author reviewing a Spec or a Skill reads prose as prose; a Flow as the graph it describes, so an author reviewing a workflow reads "this step now runs that prompt" rather than a diff of braces. Both choices are the author's habit rather than the file's property, so both are user-global and every open Diff tab follows them at once. The **target** revision — the file as it will land — is **editable in place**, because a review that finds a wrong word should end in the word being right rather than in a trip to another tab and back; and the target it renders is the artifact's own editing session (DFV-FR-42), so a correction made here is the same edit, in the same buffer, on the same undo history, written by the same schedule, as one made in an Editor tab on that file. The **original** revision is the fixed thing the comparison is against: it is never editable, never written, and never moves under an edit to the target. Out of scope: the tab reaches the repository not at all — it stages nothing, commits nothing, pushes nothing, and creates and checks out no branch — and the only bytes it writes are the target's own, through the write path that file already has; it shows one file rather than a multi-file changeset; a **Flow**'s rich rendering is a reading of a graph rather than of a document and stays read-only (DFV-FR-48); and it is not the renderer for the Git panel's inline commit diffs (`GIT-git.md` GIT-FR-03), the History detail tab's multi-file diff (`HVW-history-viewer.md` HVW-FR-04), or a change an agent has proposed — to a draft's prompt, to a prompt artifact the project already holds, or to the specification files a graduation run has just written — each of which is its own surface. Those three are the ones that borrow most. The prompt change review and the graduation review each read their comparison in the three visualizations, the two renderings, and every marking rule defined here, and the prompt change review takes the whole target-only editing model with it and shares the one user-global choice of which mode is active (per `PCR-prompt-change-review.md` PCR-FR-06, DFV-FR-24). The **draft** change review borrows the target-only editing model alone (per `DCR-draft-change-review.md` DCR-FR-24): it decides hunks in the document rather than reading a comparison, so it carries no visualization and no rendering of its own — what none of them borrows are the operations beneath all of it, because in both the original revision is a captured reading rather than a Git revision and the target's edits are held as a proposal candidate that reaches the file only when the author accepts. The graduation review borrows the reading alone, with no editable target and no shared choice (per `GRU-graduation-runs.md` through ), a change set being read there to be accepted or sent back rather than corrected in place.

## User stories
- As a user reviewing a scattered edit, I want a unified diff whose gutter numbers every line — added, removed, and unchanged alike — so that I can say "line 214" to a colleague without counting rows.
- As a user who rewrote a section, I want the old text on the left and the new text on the right, scrolling together, so that I can read the replacement against what it replaced.
- As a user about to commit, I want to read the file exactly as it will land, with what I changed marked inside it, so that I review the outcome without losing track of what I touched.
- As a user who changed one word of a long line, I want that word marked rather than the whole line, so that I can see the edit instead of hunting for it.
- As a user reviewing a Spec or a Skill, I want the Markdown rendered as prose with the changed paragraphs marked, so that I review the document rather than its syntax.
- As a user reviewing a Flow, I want to see which steps were added or removed, which artifacts a step references now, and which connections changed, so that I review the workflow rather than the JSON it is stored as.
- As a user who always reads diffs one way, I want that choice to survive relaunch and apply to every diff I open, so that I never re-select it.
- As a user reviewing my own change before committing it, I want to fix the typo I just spotted in the new version right where I found it, so that reviewing and correcting are one motion rather than two tabs.
- As a user correcting a diff, I want the old version to stay exactly as it was so that I can keep reading what I changed against it, and I want to be unable to type into it by accident.
- As a user who has just committed a file, I want its Diff tab to go away by itself, so that the strip holds the changes I still have to review rather than the ones I have finished with.

- Layout notes: the two toggle groups sit together in one toolbar row directly under the tab header, centred as a single cluster with a divider between them, and the row keeps its position and both groups' footprint whatever the file is — a group whose choices do not apply renders disabled rather than disappearing, so the controls never move between tabs. Each toggle is a glyph rather than a caption, and carries its mode's name as its accessible name and in its tooltip. The row's trailing end carries the target's write state (DFV-FR-51) and nothing else; the two groups keep the centre. The unified gutter is two fixed-width numeric columns, old then new, with a non-numeric placeholder holding the column a row has no number in; the placeholder's width equals a number's so rows never shift. Final carries one such column, of new-revision numbers, and a row that exists only in the old revision carries the placeholder there. In side-by-side the two panes share a single vertical scroll position and each carries its own revision's single-column gutter; a filler row occupies the side that has no counterpart and is visually inert — it carries no number and no content. The change marking is a row-level treatment, distinguishable from the gutter so a colour-blind reader can still tell an addition from a removal by the sign character, with the words that differ inside a replaced row marked more strongly still. Original content — a removed row, the whole left pane, and every filler row — carries a **read-only** treatment that is not the change marking and is not a colour alone: it is set on a surface tone of its own and, in Source, behind the same hatched field the filler rows take, so which half of a unified column accepts the caret is legible before the caret is put there. Every mode wraps its text rather than reaching sideways: no surface in the tab scrolls horizontally, and a wrapped editable line and its read-only counterpart still occupy one row.

## UI contract boundary
- **Owned by the UI**: the tab, its label and header; the two toggle groups, which member of each is active, and the enablement of the rendering group; **the derivation of the whole comparison from the two revisions the tab holds** — the hunks and their headers, the windowing unified mode applies, the pairing of old and new lines into aligned side-by-side rows, the filler rows that pairing produces, the block granularity of rich marking, and the word-level marking within a replaced unit — and its recomputation whenever the target changes (DFV-FR-43); the two-column gutter and its placeholder; the single scroll position the two panes share; final-version rendering and the marking it carries; detection of whether a file is Markdown; rendering of Markdown to a rich document and the marking of changed blocks within it; the deserialization of both revisions of a Flow, the comparison of the two graphs, and the entries and facts that comparison produces (DFV-FR-33); **which of the rendered content is the editable target and which is the read-only original, in every mode, together with the treatment and the assistive-technology state that says so** (DFV-FR-41); the target's editing surface in Source and in Rich and everything it accepts (DFV-FR-50); the affordance that restores or creates target content where the comparison has none (DFV-FR-54); the presentation of the target's write state (DFV-FR-51); the wrapping of every rendered surface; the syntax highlighting a Source rendering carries (DFV-FR-57), whose language resolution, grammar set, token layer, and theme-aware colours are `ESH-editor-source-files.md`'s (ESH-FR-BABL–ESH-FR-LXQR) applied here rather than a second scheme of this tab's own; the binary, empty, deleted, not-a-repository, and error states; retention of the fetched original for the tab's lifetime; and re-fetching in response to the change event. The UI resolves no comparison scope and reads no file from disk.
  The target's buffer, dirty state, undo history, baseline checksum, write schedule, and external-change resolution are not this tab's own either: they are the artifact's editing session, owned by `EDT-editor.md` (EDT-FR-28, EDT-FR-72), and this tab renders and edits it rather than keeping a second copy.
  The file's resolved artifact type is supplied with the file and the comparison by whatever opens the tab (`CHG-changes.md` CHG-FR-18), not derived here: the classifier that resolves it is the backend's (`../core/ASC-artifact-scanning.md` ASC-FR-06), and re-deriving it from the filename would ignore a user's explicit assignment.

- **Delegated to backend (abstract)**:
  - `"get file revisions for comparison"` — the original revision the tab compares against, together with the facts its new side carries about whether the comparison adds or deletes the file and whether it is binary. Owned by `../core/GTC-git.md`.
  - `"load artifact contents by id"` and `"save artifact contents"` — the target revision and the writes that land it, invoked through the artifact's editing session on exactly the terms an Editor tab invokes them (per `EXC-editor-external-change.md` EXC-FR-WCOM, `EDT-editor.md` EDT-FR-70). Owned by `../core/PST-project-storage.md`.
  - `"create file (location, name)"` — the file the restore affordance of DFV-FR-54 creates where the comparison deleted it. Owned by `../core/PST-project-storage.md` (PST-FR-25).
  - `"load app preferences"` and `"save app preferences"` — the persisted visualization and rendering modes. Owned by `../core/GSS-global-settings-storage.md`.
  - The events `"changes updated"` (`../core/CHC-changes.md`) and `"artifact changed externally"` (`../core/PST-project-storage.md` PST-FR-16), the second of which reaches the tab through the artifact's editing session rather than being subscribed to here.

## Functional requirements
1. **DFV-FR-01** A Diff tab is a main-viewport tab (per `TAB-tabs.md` TAB-FR-02) showing exactly one file under exactly one comparison. It is opened from the Changes panel (per `CHG-changes.md` CHG-FR-18), which supplies the file and the comparison.
2. **DFV-FR-02** The tab's label is the word `Diff`, a colon, and the file's base name — `Diff: CHG-changes.md`.
3. **DFV-FR-03** The comparison is named in the tab's own header alongside the file's project-relative path, and in the tab's tooltip. The header's file name and path both read in the case they carry on disk (per `SNV-shell-navigation.md` SNV-FR-57). Two Diff tabs on the same file under different comparisons therefore carry identical labels (DFV-FR-02) and are told apart from the tooltip or from the header of whichever is active.
4. **DFV-FR-04** A Diff tab is identified by the pair of its file and its comparison; a request for a Diff tab that is already open jumps focus to it rather than opening a second one, and a request for the same file under a different comparison opens a separate tab.
5. **DFV-FR-05** A Diff tab is exempt from the single-tab-per-artifact rule (per `TAB-tabs.md` TAB-FR-06), so it coexists with an Editor tab and with other Diff tabs on the same artifact. The exemption costs the rule nothing: the several tabs are several views onto **one** editing session rather than several sessions of the same file (DFV-FR-42). Save acts on the tab while its target holds a write that has not yet landed and is disabled otherwise, exactly as it is over an Editor tab on the same artifact (per `SNV-shell-navigation.md` SNV-FR-28).
6. **DFV-FR-06** The tab's reach is the target's own bytes and nothing else. No staging, unstaging, committing, pushing, pulling, branch creation, or checkout is reachable from it; it writes no file but the one under comparison; and it writes that one only through the artifact's own write path (DFV-FR-42), never through a save mechanism of its own. The original revision accepts no text input anywhere, in any visualization mode and either rendering (DFV-FR-41).
7. **DFV-FR-07** A toolbar directly under the tab header holds two toggle groups: a **visualization** group of three and a **rendering** group of two. Exactly one member of each group is active at any moment. The two groups sit together as one centred cluster rather than at opposite ends of the row, and each toggle is a glyph carrying its mode's name as its accessible name and in its tooltip.
8. **DFV-FR-08** The visualization group's three members are **Unified**, **Side-by-side**, and **Final**, and they are mutually exclusive: activating one deactivates the previously active one.
9. **DFV-FR-09** **Unified** renders the comparison's changed regions as hunks in one column, each introduced by its hunk header, with unchanged context lines around each region. It renders no part of the file outside a hunk. What it does not render is still part of the target the tab holds and writes (DFV-FR-44): windowing is a choice about reading rather than a truncation of the file.
10. **DFV-FR-10** The unified gutter is two numeric columns — the old revision's line number, then the new revision's. A context line carries a number in both. A removed line carries a number in the old column only, an added line in the new column only, and the column it has no number in carries a non-numeric placeholder of the same width rather than being blank of layout. Every rendered content row therefore carries at least one line number, whatever its kind.
11. **DFV-FR-11** **Side-by-side** renders two panes — the old revision on the left, the new revision on the right — each showing its revision's file in full rather than only its changed regions. The two panes are laid out as aligned rows: a line and its counterpart occupy the same row, and where one side has no counterpart the opposite side carries an inert filler row, so the alignment holds down the whole file.
12. **DFV-FR-12** Each side of a side-by-side view marks change in the terms of its own revision: the left marks the lines the change acted on — removed outright or replaced — and the right marks the result — lines added or the replacements that stand in the old lines' place. An unchanged line is marked on neither side. A line that replaced another additionally marks the words within it that differ (DFV-FR-32). Each pane's gutter carries its own revision's line numbers only.
13. **DFV-FR-13** The two side-by-side panes share one vertical scroll position: scrolling either pane moves both, so a row and the row it is aligned with (DFV-FR-11) stay opposite each other at every scroll offset. This holds however the scroll is driven — wheel, scrollbar drag, keyboard, or a jump to a change — and neither pane can be scrolled vertically on its own.
14. **DFV-FR-14** **Final** renders the file's complete new-revision content with the changes that produced it marked in place. An added or replaced line is marked as added and, where it replaced another, carries the word-level marking of DFV-FR-32; **only the outcome is shown**, so a replaced line's predecessor does not appear. A line the comparison removed with nothing standing in its place is shown in position, marked as removed.
   - *Why:* A deletion is the one edit a finished file cannot otherwise show, its evidence being exactly the text that is no longer there.. There are no hunk headers, and the gutter is a single column of new-revision line numbers, with the placeholder of DFV-FR-10 on a removed line, which has no number in that revision.
15. **DFV-FR-15** When the comparison deletes the file outright, **Final** renders an inline state saying the file does not exist in the new revision, and renders no content in its place — together with the restore affordance of DFV-FR-54, which is the one way an outcome that is nothing at all becomes something to type into. The other two visualization modes render the deletion as they render any change — every line removed — the old revision being content those modes show; having no target, all three render nothing editable until the file is restored. A file that exists but is empty is not this state: it has a new revision, that revision is an editable target, and it renders as one.
16. **DFV-FR-16** The rendering group's two members are **Source** and **Rich**, and they are mutually exclusive. **Source** renders the file's literal text, unrendered, in every visualization mode.
17. **DFV-FR-17** **Rich** has a reading for two shapes of file: Markdown and Flow. For Markdown it renders the formatted document — headings, emphasis, lists, tables, code blocks, links — rather than as its source text. For a Flow it renders the graph comparison of DFV-FR-33. It applies to no other file. Which of the two a file is, is decided for Markdown by the file's own text format and for a Flow by its **resolved artifact type** (`../core/ASC-artifact-scanning.md` ASC-FR-06) — not by its name: `.flow` is the path convention and a user's type assignment overrides it. A file that is both — a Flow whose name ends `.md` — reads as the artifact it resolved to. The Markdown document is typeset exactly as the Editor typesets the same file in WYSIWYG (`EDT-editor.md` EDT-FR-02): one page, one set of document styles, so an artifact the Editor renders that way (per `ESH-editor-source-files.md` ESH-FR-FKZB) is one document here and there. A file whose text is Markdown but whose name the Editor edits as source is still read here as the document its text describes; it simply has no rich surface elsewhere to be identical to.
18. **DFV-FR-18** Both rendering toggles are always rendered in the toolbar. When the file is neither Markdown nor a Flow, or is binary, both are disabled with **Source** active, and the tab states that rich rendering does not apply to this file. The disablement is display-only: the persisted rendering mode (DFV-FR-23) is not written by it, so a file rich rendering does have a reading of, opened afterwards, still renders rich if that is the stored choice.
19. **DFV-FR-19** In **Rich**, change is marked at block granularity: the smallest rendered block containing a change — a paragraph, heading, list item, table row, block quote, or fenced code block — carries an added, removed, or changed treatment as a whole, and the block is rendered unbroken: it is never split into separately-marked fragments. A block that replaced another additionally marks the words within it that differ (DFV-FR-32). A table row is the exception and carries its whole-block marking alone, its cells already being the finer unit.
20. **DFV-FR-20** **Rich** with **Unified** renders the new revision's document with each changed block marked in place, and renders a removed or replaced block immediately above the block that replaces it, so the old rendering and its outcome read in sequence.
21. **DFV-FR-21** **Rich** with **Side-by-side** renders the old revision's document in the left pane and the new revision's in the right, marked per DFV-FR-12 at the block granularity of DFV-FR-19, aligned block-to-block with filler where a block has no counterpart, and sharing the single scroll position of DFV-FR-13.
22. **DFV-FR-22** **Rich** with **Final** renders the new revision's document on the terms of DFV-FR-14: a changed or added block marked and word-marked, a block removed outright shown in position marked as removed, and a replaced block's predecessor not shown at all. That last point is what separates it from DFV-FR-20, which shows the pair.
23. **DFV-FR-23** The active visualization mode and the active rendering mode are user-global and survive relaunch: they are read from `"load app preferences"` and written through `"save app preferences"` whenever the user activates a different toggle (per `../core/GSS-global-settings-storage.md` GSS-FR-24). A user who has never chosen starts in **Unified** and **Source**.
24. **DFV-FR-24** Because the two modes are one user-global choice rather than a property of a tab, activating a toggle in any Diff tab re-renders every open Diff tab into that mode immediately, and a Diff tab opened afterwards opens in it too. The choice is not this tab's own: the prompt change review modal reads and writes the same preference (per `PCR-prompt-change-review.md` PCR-FR-08), so a toggle activated in either re-renders every open Diff tab on exactly these terms, and one activated here is the mode both modals next open in. An author who reads the diffs of their own work one way therefore reads all of them that way. The one surface outside that set is the **graduation review**, which opens every time on the outcome read as a document whatever this preference holds and keeps its toggles to itself: a change set an agent wrote is read there to be accepted or sent back rather than to check work the author did, so the author's habit is not the right default for it and a mode chosen inside it is no statement about how they read their own diffs. Nothing that surface does writes this preference and nothing it does re-renders a Diff tab.
25. **DFV-FR-25** A tab opening invokes `"get file revisions for comparison"` once for its file and comparison and retains the **original** revision it returns for the tab's lifetime, and establishes the artifact's editing session for the **target** (DFV-FR-42) — a session the artifact already carries costs no read at all, and one it does not costs the single `"load artifact contents by id"` that opening the file in an Editor tab would have cost. Every mode is then rendered from those two held revisions, so switching among the six combinations is a local re-render with no further round-trip. The tab holds the whole target in every mode, including **Unified**, the target it edits being the complete revision rather than the rows a hunk happens to show (DFV-FR-44).
26. **DFV-FR-26** The tab subscribes to the `"changes updated"` event and re-fetches the **original** revision when it fires, discarding the one it held, so the tab never compares against a base that has moved on. It takes no target from that fetch: the target is the editing session's, and a working-tree change that reached it while the author's edits stood is answered by the external-change resolution of DFV-FR-53 rather than by a re-fetch replacing the buffer. The active visualization and rendering modes, the target's buffer, its undo history, and its scroll position are all unaffected.
27. **DFV-FR-27** When the file is binary, the tab renders an inline state saying so in place of any content, in all three visualization modes, with the rendering group disabled per DFV-FR-18.
28. **DFV-FR-28** When the comparison yields no change for the file, the tab renders an empty state that is visually distinct from the binary state of DFV-FR-27 and the deleted state of DFV-FR-15.
29. **DFV-FR-29** When the open project is not a Git repository, the tab renders an inline explanatory state in place of any content and does not fail to render. Any other failure of the two backend operations renders inline in the same position.
30. **DFV-FR-30** Every Diff tab closes when the project's active worktree changes (per `TAB-tabs.md` TAB-FR-14), and nothing it held — diff, revisions, or scroll position — outlives it, its file and comparison naming a path in the content root it was opened from.
31. **DFV-FR-31** When the comparison *adds* the file, **Final** renders it with no marking at all. Every line of it is new, so marking every line distinguishes nothing within the file and says only what the comparison already says; the mode reads as the document it is. This applies to **Final** alone — the other two modes show the file as the addition it is. A file that was rewritten rather than added still has an old revision, and is marked normally.
32. **DFV-FR-32** Wherever a unit of content **replaced** another — a line opposite the line it replaced, a block opposite the block it replaced — the parts of it that differ from its counterpart are marked more strongly than the unit as a whole, on both the old side and the new. This is what turns "this line changed" into "this word changed" on a long line with a small edit. It applies only to a replacement: a unit with no counterpart is wholly new or wholly gone, and marking each of its words repeats at higher contrast what its own marking already says. Two units too unalike to read as one edit are left to their whole-unit marking rather than speckled, and so are two too large to compare cheaply. In **Rich** the comparison is made over the text the block *renders to* rather than its Markdown source, so a change to a link's target or the addition of emphasis marks the block without marking any word.
33. **DFV-FR-33** **Rich** over a Flow compares the two revisions as the graphs they describe (`FLO-flow.md` FLO-FR-03, `../core/FGV-flow-graph-validation.md` FGV-FR-01) rather than as text, and renders the result as entries: the Flow's own name and description, one entry per node, one per loop, and one per connection. A node or a loop pairs with the element carrying the same id, which `FLO-flow.md` FLO-FR-06 makes stable across saves, so a renamed step is one element that changed rather than one added and one removed; a connection pairs by its endpoints. Each entry is marked added, removed, changed, or unmarked as a whole, and a changed entry states which of its facts differ and what each was and became: for a node, its name, each artifact it references (gained and lost individually), and its inline prompt; for a loop, its name, each artifact it references on those same terms, and its pass bound; for a connection, its label. Then, for any element, **which container it sits in** — an element that moved into or out of a loop, named by the loop it left and the one it joined (`FLO-flow.md` FLO-FR-40). Last, its position on the canvas and, for a loop, its size. A loop's entry states what it holds by naming its members rather than by nesting their entries inside it, so every element of the Flow is one entry at one level however deeply the loops nest. A revision that cannot be deserialized as a Flow renders an inline state naming the failure in place of the comparison, rather than falling back to text.
34. **DFV-FR-34** The visualization group governs a Flow comparison as it governs a document: **Unified** renders only the entries that changed, each showing only the facts that differ; **Final** renders the whole of the new Flow with what changed marked in place and an entry removed outright shown in the position it held; and a Flow the comparison *added* renders in **Final** with no marking at all, on the terms of DFV-FR-31.
35. **DFV-FR-35** **Rich** with **Side-by-side** over a Flow renders the old Flow's entries in the left pane and the new Flow's in the right, each entry opposite its counterpart with inert filler where one revision has no counterpart for it, sharing the single scroll position of DFV-FR-13. Each side states the facts its own revision holds, so a reference the change added appears only on the right and one it dropped only on the left.
36. **DFV-FR-36** A Flow comparison whose file changed but whose graph did not — a reformatting, a reordering of keys — renders in **Unified** as an explicit statement that the file changed and the Flow it describes did not, rather than as an empty surface. This is distinct from the no-change state of DFV-FR-28, which is reached when the comparison reports no change to the file at all.
37. **DFV-FR-37** The tab's two rendering modes set text in the typographic roles of `OVW-overview.md` OVW-FR-13. **Source** (DFV-FR-16) sets the file's literal text, and the line-number gutter beside it, in the **Source code** role, so the gutter's fixed width and the alignment of the two side-by-side panes hold at any size the role carries. **Rich** (DFV-FR-17) sets a Markdown document's prose in the **Rich Markdown** role and its fenced and inline code and frontmatter in the Source code role, which is what makes its typographic identity with an Editor tab's WYSIWYG surface hold (`EDT-editor.md` EDT-FR-62). The roles govern family, size, and line height alone: change marking, word marking, block alignment, the token colours of a highlighted Source rendering (DFV-FR-57), and the filler of DFV-FR-21 are unaffected by any of them.
38. **DFV-FR-38** **Rich** over a Markdown document renders it on the **page** an Editor tab sets its WYSIWYG surface on (`EDT-editor.md` EDT-FR-63) — the same inset sheet with the same edge over the same recessed field — which is the other half of the identity DFV-FR-17 asserts: the artifact read here and the artifact open for editing are framed alike as well as typeset alike. In **Side-by-side** each revision occupies a page of its own, the two set on one field with the field showing between them. **Source** (DFV-FR-16) takes no page: its literal text and its line-number gutter fill the tab's panes as they do. The framing carries none of the tab's marking and none of its editing: change marking, word marking, and the filler of DFV-FR-21 render inside the page exactly as they do without it, and the page is where the editable target is typed into (DFV-FR-47).

39. **DFV-FR-39** The Diff tab carries the **action control** of `ACT-action-control.md` (ACT-FR-01), bound to the file it is comparing **at that file's current identity in the project** rather than to either revision on screen (ACT-FR-02), so a conversation begun while reading a change is the same conversation the Editor tab on that file shows. It offers **Discuss** alone, whatever the file's type: this tab is one reading of one comparison of a file, and the hand-off belongs on the file's own tab (ACT-FR-04). Over **Rich**, which sets its content on a page (DFV-FR-38), the control stands in the field beside that page and covers none of it; over **Source** and in **Side-by-side**, which take no such field, it floats in the tab's bottom-trailing corner over the panes (ACT-FR-09, ACT-FR-10). Its discussions are whole-target discussions of the file with no fragment (per `ACT-action-control.md` ACT-FR-LXKD), read in the floating panel as the shared discussion surface, this tab lending the comment rail no margin (ACT-FR-20).
40. **DFV-FR-40** Discussing a file changes nothing this tab shows and nothing it holds. The composer and the panel, which render the shared discussion surface, lie over the comparison without re-rendering it, hold the shared scroll position (DFV-FR-13), and touch neither revision: what a discussion writes is a comment log, so the target's buffer, its dirty state, and its undo history are exactly as they were and the index and the working tree are untouched (per `ACT-action-control.md` ACT-FR-24). A file the comparison shows as deleted, or one the project no longer holds, carries a control whose Discuss is disabled (per `ACT-action-control.md` ACT-FR-07), there being no file left to talk about.
41. **DFV-FR-41** The **target** revision is editable and the **original** revision is not, in all three visualization modes and both renderings. The rule is the tab's whole editing model and admits no exception: wherever content on screen belongs to the original — a removed row, the left pane, a filler row, the predecessor of a replacement — it accepts no caret, no keystroke, no paste, and no drop, and reports itself read-only to assistive technology; and wherever content belongs to the target it is ordinary editable text. The distinction is carried by more than colour: the original's read-only surface tone and hatch (layout notes) and the change marking's own sign character are separate signals, so a reader who cannot discriminate the two colours can still tell which half of a unified column they may type into.
42. **DFV-FR-42** The target the tab renders and edits **is the artifact's editing session** — the buffer, dirty state, active editing mode, single undo/redo history, indentation convention, and baseline checksum `EDT-editor.md` keys by the artifact's stable key (EDT-FR-28, EDT-FR-72) — and not a copy of it. One consequence carries the rest: an edit made here is the same edit an Editor tab on that file would have made, so the two surfaces show one buffer and one dirty state, one undo reverses the last edit whichever of them produced it, the write that lands it is the one schedule of EDT-FR-70, and the tab presents no Save control and no save mechanism of its own. Two Diff tabs on the same file under different comparisons therefore edit one target and render it against their own two originals.
43. **DFV-FR-43** The tab derives the whole comparison itself, from the **original** revision it fetched and the **target** as it currently stands: the hunks and their headers, the pairing of lines, the filler rows, the rich block granularity, and the word-level marking within a replaced unit are all computed here, on the terms DFV-FR-09 through DFV-FR-22 and DFV-FR-32 define them. It is recomputed as the target changes, so the marking always describes the text on screen. The original is the revision the comparison captured and stays exactly that: an edit to the target re-derives what is shown *against* it, never re-reads it, never re-bases the comparison onto the edited text, and never makes it writable.
44. **DFV-FR-44** In **Unified**, an added row and a context row both carry target content and are editable; a removed row carries original content and is not. Editing a row edits the position it occupies in the whole target, not merely the rows the hunk renders, and the file outside every hunk is held and written unchanged — so a correction inside a hunk is one edit to one file rather than a patch applied to a window. A row the edit turns from a context row into a changed one re-marks in place (DFV-FR-43), and the hunk grows, splits, or closes as the recomputation has it.
45. **DFV-FR-45** In **Side-by-side**, the **right** pane is the target and is editable; the **left** pane is the original and is not, and neither is a filler row on either side. Focus and the caret do not cross between the panes: keyboard navigation off the end of an editable row moves within the target, tabbing does not land inside the left pane's text, and a selection begun in the right pane does not extend into the left. Editing the right pane re-derives the alignment (DFV-FR-43) and the two panes stay row-for-row opposite each other through it, wrapping included, so no edit and no rewrap is ever seen with the panes at different offsets.
46. **DFV-FR-46** In **Final**, the rendered outcome is the target and is editable throughout — added rows, replaced rows, and unmarked rows alike. A row shown in position marked as removed is the original's evidence for a deletion (DFV-FR-14) and is read-only; typing where it sits inserts into the target at that position rather than reviving it. A comparison that deletes the file outright has no outcome to type into and offers the restore affordance of DFV-FR-54 instead.
47. **DFV-FR-47** In **Rich** over a Markdown file, the target is edited with the **same Markdown editing semantics the Editor's WYSIWYG surface carries**: the same constructs modelled and editable (per `EDT-editor.md` EDT-FR-68), the same frontmatter region with its parse-driven treatment and description budget (EDT-FR-18, EDT-FR-20, EDT-FR-21, EDT-FR-59), the same keyboard formatting and input rules, and the same serialisation guarantees — semantically lossless, stable, and byte-for-byte on a file that was only read (EDT-FR-66, EDT-FR-67, EDT-FR-69). What the tab adds is that the diff survives the editing: a block the edit changes re-marks at the block granularity of DFV-FR-19, the marking renders inside the rendered document rather than around it, and the boundary between target and original blocks holds — an original block rendered here (DFV-FR-20) is inert rich content that accepts no input.
48. **DFV-FR-48** **Rich** over a **Flow** is read-only. The graph comparison of DFV-FR-33 is a reading of two graphs rather than a document, so no entry, fact, name, or value in it accepts text input, and the Markdown editing contract of DFV-FR-47 is not exposed over it at all. A Flow's target is edited in a Flow tab (`FLO-flow.md`), which is where a graph has an editing surface. **Source** over a Flow is the file's literal JSON and is editable on the ordinary target-only terms.
49. **DFV-FR-49** Where rich rendering does not apply to a file (DFV-FR-18), **Source** is editable on exactly the target-only rule of DFV-FR-41. The rendering group's disablement decides how the comparison reads and never whether it can be corrected, so a plain text file's diff is as editable as a Spec's.
50. **DFV-FR-50** The target's editing surface accepts what an editing surface accepts: text selection by pointer and keyboard, typing, paste, drag-free cut and copy, and the platform-standard undo and redo, which act on the artifact's single history (per `EDT-editor.md` EDT-FR-15, EDT-FR-22). It takes focus with a treatment of its own distinct from the read-only original's, and carries an accessible name naming the file and identifying the revision as the target — so a screen-reader user landing in it knows which of the two revisions their keystrokes will reach. The Editor's formatting toolbar and its Find and Find & Replace band (per `EFR-editor-find-replace.md` EFR-FR-ABHF) are not reproduced here: this tab's toolbar row carries the two toggle groups, which are about how the comparison reads.
51. **DFV-FR-51** The tab states the target's write state explicitly at the trailing end of its toolbar row — that an edit is pending, that a write is in flight, that the buffer has reached disk, or that a write failed — reading the artifact's own dirty state and write outcome (per `EDT-editor.md` EDT-FR-04, EDT-FR-71) rather than tracking one of its own, so this tab and an Editor tab on the same file never disagree about whether the file is written. A write that fails keeps every edit in the buffer and renders the typed error inline in the tab; nothing is discarded, no retry runs on a timer, and the next edit or File → Save retries it (per `EDT-editor.md` EDT-FR-71, EDT-FR-34).
52. **DFV-FR-52** Switching the visualization mode, the rendering mode, or both while the target holds unsaved edits preserves the edited target, its dirty state, its undo and redo history, and the tab's scroll position, and preserves the selection wherever the incoming mode has a place to put it. The switch is a re-derivation of the comparison from the two revisions the tab already holds (DFV-FR-25, DFV-FR-43) and re-reads neither of them, so no mode change can put the pre-edit target back on screen.
53. **DFV-FR-53** A target that changes outside the application, and a `"changes updated"` re-fetch reporting a newer working tree, are both answered by the artifact's **external-change resolution**: the modal of `EXC-editor-external-change.md` EXC-FR-QCNO through EXC-FR-VNLZ with its two explicit resolutions, raised on this tab as it is on an Editor tab. It is the answer to every change the author did not ask for, and the rollback of DFV-FR-58 — which they did ask for, on another surface, and which has already taken effect on disk — is the one reset that arrives without it. Until the author resolves it the buffer is neither reloaded nor overwritten, the scheduled write is held rather than performed or dropped (per `EDT-editor.md` EDT-FR-70), and the tab's editing surface is inert. Choosing to load from the filesystem re-derives the comparison against the newly loaded target; choosing to keep the local version writes it and re-derives the same way.
54. **DFV-FR-54** A target with nothing in it is still a place to write. A file that exists but is empty renders an empty editable target carrying a statement that the new revision holds nothing, and typing into it is an ordinary edit. A comparison that **deletes** the file has no target at all, so the deleted state of DFV-FR-15 carries a **restore** affordance stating what it will do; activating it invokes `"create file (location, name)"` at the comparison's own path, and the tab then holds an editing session on the recreated file whose target opens empty and editable, the original being unchanged and the comparison re-derived against it. A failure to create renders inline in the same position and leaves the tab in its deleted state.
55. **DFV-FR-55** A Diff tab closes when a commit successfully includes the file it is comparing (per `TAB-tabs.md` TAB-FR-22), the review having been finished by the commit it was for. It closes on confirmed success alone — a commit merely started, abandoned, or refused closes nothing — and every Diff tab on that file closes, however many comparisons they hold, while the Editor tab on the same file stays open with the artifact's editing session intact. The target's pending write is brought forward before the tab is removed and a write that cannot proceed safely refuses the close, on the ordinary terms of `TAB-tabs.md` TAB-FR-10 and TAB-FR-11.
56. **DFV-FR-56** Every marking the tab draws stays legible through an edit. An addition the author extends is still marked as an addition; a replacement they rewrite re-derives its word-level marking against the same counterpart (DFV-FR-32); a change they undo back to the original's text loses its marking, because the recomputation says there is no longer a difference there; and a wrapped line, a rich block, and a table row carry their marking across every visual line they occupy. No marking is ever left describing text that has since been edited out from under it.
57. **DFV-FR-57** **Source** (DFV-FR-16) renders its text with the syntax highlighting the Editor gives a source file (per `ESH-editor-source-files.md` ESH-FR-BABL–ESH-FR-LXQR), resolved once for the file the tab compares and applied to **both** revisions, so the original and the target read in one language rather than in two. The resolution is that spec's and not a second scheme of this tab's own (per `ESH-editor-source-files.md` ESH-FR-CFEQ): a file whose final extension is `.md` receives no token colouring here either, its reading being **Rich** (DFV-FR-17), a file no language resolves for renders plain, and a binary file is highlighted nowhere, having no text rendered to highlight (DFV-FR-27). The colouring is presentation over the text and never over the comparison. It is carried on a layer that takes no pointer, keyboard, selection, clipboard, drag, or composition event (per `ESH-editor-source-files.md` ESH-FR-VNPW), so the target is typed into exactly as it is without it (DFV-FR-41, DFV-FR-50) and the original is as read-only as ever; and every marking the tab draws wins wherever the two meet — a row's added, removed, or changed treatment, the word-level marking within a replaced unit (DFV-FR-32), the read-only surface tone and hatch of the original, and the gutter's sign character are all legible over any token colour, and none of them is carried by token colour or defeated by one.
58. **DFV-FR-58** A Diff tab whose file a rollback has **restored** stays open and re-reads the comparison it is showing. The target is the artifact's session and is reset by that session (per `EXC-editor-external-change.md` EXC-FR-JAWT) — reloaded from disk, its dirty indicator cleared, its undo and redo history discarded — the **original** revision is re-fetched through `"get file revisions for comparison"` exactly as a `"changes updated"` re-fetch fetches it (DFV-FR-26), and the whole comparison is re-derived from the two (DFV-FR-43). The tab's visualization mode, rendering mode, and scroll position are unaffected. No external-change modal stands between the author and any of it (DFV-FR-53), so there is no route by which the discarded version can be kept: a tab that was showing an edit the author chose to throw away shows the restored file instead, marked against the original the rollback left standing. Where the rollback **removed** the file, the tab does not persist to render a deleted state — it closes with every other tab bound to that file (per `TAB-tabs.md` TAB-FR-41), so the restore affordance of DFV-FR-54 is never the answer to a removal the author asked for. A file the rollback confirmed as neither keeps the tab exactly as it was, its edited target, its dirty indicator, its undo history, and any external-change modal over it all intact.
59. **DFV-FR-59** Nothing about a rollback is reachable **from** this tab. DFV-FR-06 stands unchanged: the tab stages, commits, pushes, and rolls back nothing, and carries no affordance that discards a change. What DFV-FR-58 describes is the tab being reset by an operation the Changes panel performed (per `CHG-changes.md` CHG-FR-62), on the same footing as the commit that closes it (DFV-FR-55) — something that happens to the file the tab is showing rather than something the tab can do to it.

## Non-functional requirements
- Whole-file modes render incrementally: a side-by-side or final view of a large file must not block the tab from painting its header and toolbar, and must not stall the toggle groups.
- The single shared scroll position (DFV-FR-13) must track without visible lag between the panes at any scroll velocity; the two panes must never be seen at different offsets mid-scroll.
- Every gutter column is fixed in width, so rows do not shift horizontally as line numbers gain digits or as a re-fetch (DFV-FR-26) changes the hunk set — and, in side-by-side, so the two panes stay aligned across a change of digit count.
- Change marking is conveyed by more than colour — a sign character in the gutter for source rendering, a block-level marker for rich — so the diff is readable without colour discrimination. The word-level marking of DFV-FR-32 is an additional treatment on content that is already marked, never the only signal that something changed.
- Every mode soft-wraps its content: a long line is read by wrapping it, and no surface in the tab scrolls horizontally. In side-by-side a wrapped line and its counterpart still occupy one row, so the alignment of DFV-FR-11 survives wrapping on either side.
- The word-level comparison of DFV-FR-32 is bounded per unit, so a file whose every line was rewritten costs no more to render than one that was not.
- Switching either mode is a local re-render: it invokes `"get file revisions for comparison"` at most once per comparison per tab and reads the target through the artifact's editing session at most once per artifact (DFV-FR-25).
- Re-deriving the comparison under the author's typing (DFV-FR-43) keeps the target's editing surface responsive at the document sizes the Editor is responsive at, and is settled rather than run per keystroke, so a burst of typing re-marks once rather than once per character. The caret never moves as a consequence of a re-derivation, and neither does the scroll position.
- The two revisions are compared with line terminators normalised on both sides, on the terms `../core/GTC-git.md` GTC-FR-17 normalises them, so a checkout convention that differs from the committed blob's renders as no change rather than as every line changed. The bytes a write puts on disk are unaffected: their convention is the project's and is applied by the write (per `EDT-editor.md` EDT-FR-40).
- Tokenising a Source rendering (DFV-FR-57) resolves the language once per tab and runs off the typing path, so it delays neither the first paint of a comparison nor the re-derivation an edit triggers; a rendering whose tokens are not ready shows its plain text, marking and all, until they are.
- The tab renders its binary, empty, deleted, and not-a-repository states without network access.
- The tab stays usable and legible at the minimum window size the shell supports (≥1280×800) in every one of the six mode combinations, editable target included: nothing in it scrolls horizontally at that width, and side-by-side keeps two editable-and-read-only panes rather than dropping one.
