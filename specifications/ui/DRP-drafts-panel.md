# Drafts

**Spec code:** `DRP`

## Intent
Vertical-panel surface listing the drafts in the project's active worktree — the artifacts being developed with AI before they exist in the project (per `NAW-new-artifact.md`). A draft is long-lived by design and several sit in flight at once, so they need somewhere to be seen together: what exists, how far along each is, and which one an agent is working on right now. Drafts also accumulate faster than they graduate, so the panel is a **tree** rather than a flat list: the author cuts folders of their own — UI, backend, research — and files the drafts into them. A folder here is an ordinary directory under the worktree's drafts root, so the shape on screen is the shape on disk, and a draft moved between folders stays the draft it was: same id, same files, same status, same destination root, same open tab. Not every draft that was started is still being worked on, so the panel shows the **active** ones by default and keeps the **archived** ones and the **graduated** ones each one position away — a draft that went nowhere is retired rather than deleted, and a draft that became a specification is kept rather than removed, so nothing any of them holds leaves the disk. A draft may also be in the middle of becoming a specification, which is a thing the author needs to see from here rather than by opening it: a row says whether a graduation run has it, what that run is doing, and leads to the run itself. It is the **only** place a draft is created, and where one is reopened, renamed, organised, found again, retired, restored, followed while it graduates, and abandoned for good — the **New Artifact** entries of the File menu and the Project context menu create typed project files instead (`NTA-new-typed-artifact.md`) and reach no draft at all; everything that happens *inside* a draft belongs to its New Artifact tab. A draft is often easier to recognise by a phrase somewhere in its text than by the name it was given weeks ago, so the panel's filter reaches into the drafts' contents as readily as into their names. Out of scope: the draft's files, conversation, and review threads, none of which this panel renders — the file tree *inside* one draft is that draft's own rail in its tab (`NAW-new-artifact.md`) and shares nothing with the folders here; graduating a draft into the project, which is the tab's action (`NAW-new-artifact.md` NAW-FR-20); and the artifacts already in the project, which are the Project panel's (`LIB-library.md`).

## User stories
- As an author with several specifications in flight, I want one list telling me what I am still working on, without the ones I gave up on months ago in it.
- As an author whose drafts span several parts of the project, I want to file them under folders I named myself, so that finding the one I want is navigating rather than scanning a column.
- As an author, I want to move a draft into a folder without it becoming a different draft, so that organising my work costs me nothing I would have to undo.
- As an author working without a mouse, I want to reorganise drafts from the keyboard, so that the structure of my own work is not behind a pointer gesture.
- As an author, I want to retire a draft I have stopped working on and still be able to find it again if I change my mind.
- As an author whose draft is being turned into a specification, I want its row to say so and to take me to the run, rather than letting me start editing a prompt an agent is already working from.
- As an author, I want the drafts that have become specifications kept in their own view, so my active list is not a history of everything I ever finished.
- As an author, I want to tell at a glance whether a draft became a specification here or an issue on GitHub, because the two send the work to different places.
- As an author returning after a week away, I want to find the draft I left unfinished by a phrase I remember writing in it, without remembering what I called it.
- As an author, I want to see at a glance that an agent is still working on a draft I am not currently looking at.
- As an author, I want to abandon a draft that went nowhere without it leaving anything behind in my repository.

- Layout notes: the text filter sits directly beneath the panel header and the status filter beneath it, directly above the tree, as every vertical panel arranges the pair (per `SNV-shell-navigation.md` SNV-FR-58); both are pinned above the scrollable tree and stay visible while it scrolls, and the create affordance is pinned below it, centred across the panel's width. The status filter is the single-line toggle row of `SNV-shell-navigation.md` SNV-FR-62 — four buttons acting as one radio group, each carrying a short tag and disclosing its position's full name on hover — rather than a dropdown, and it clips at its trailing edge rather than wrapping at a narrow panel width, its leading, trailing, and active buttons each rendering at every width (SNV-FR-63). A folder row carries a disclosure triangle, a leading icon, its name, and a `[⋯]` button at its trailing edge; it is a single line, having no second line to carry, and truncates its name rather than widening the panel. A draft row carries `[⋯]` at its top-right, always rendered rather than revealed on hover, the build and graduation indicators immediately before it, and a second line carrying the relative last-activity time, the word for an in-flight build, or — where a graduation run holds the row — that run's state as a short phrase which is itself the route to the run. A row matched by its contents rather than its name carries a third line saying so. An archived draft's row and a graduated draft's row each carry their own marker distinguishing them from an active one and from each other; there are no status group headers in any filter position. Depth is expressed by indentation alone, and the implicit root is the tree's container rather than a row of its own — nothing renders above the top-level folders. Menus, the two confirmations, and the folder picker use the visual primitives, spacing, leading icons, and dismissal behaviour of the Project context menu (`LCM-library-context-menu.md` LCM-FR-07), and the two confirmations are centred modal overlays exactly as its recursive-delete confirmation is. A drop target under the pointer is highlighted for as long as the drag is over it; a target the move would be refused on is never highlighted. The empty state replaces the tree entirely, both filter controls included, and is composed as every vertical panel's is (per `SNV-shell-navigation.md` SNV-FR-60): one block centred across the panel's width and down the height the tree would have occupied, holding a stated line, a sentence on a measure narrower than the panel naming what a draft is, and the create affordance as its single button. It carries that affordance itself, and the pinned one is not rendered beside it, so there is one thing to do rather than a control to find. A filter matching nothing is a different state and stays in the tree's own region with both controls present (per `SNV-shell-navigation.md` SNV-FR-61). A draft just created renders with that same inline name field already open on its row, seeded and selected (DRP-FR-36), so the wireframe's field is what the author meets immediately after creating as well as after choosing **Rename…**. Errors returned by a backend operation attach inline to the row that triggered them, at the inline field where one is open, and below the create affordance for a failed create.

## UI contract boundary
- **Owned by the UI**: the panel's rendering as a vertical-panel surface; the hierarchical tree, the indentation that expresses depth, which folders are expanded, and the ordering of folders and drafts within each parent; the four-position status filter, its rendering as a toggle row, and which position is active; the text filter, the debounce that decides when it is dispatched, the annotation naming why a row matched, and the ancestor revelation a match forces; the archived and graduated markers; relative-timestamp formatting and the hover disclosure of absolute timestamps; the build indicator and the state it reflects; the graduation indicator, the run-state phrase it renders, the route that phrase carries, and which row actions a lock disables (DRP-FR-35); the per-row `[⋯]` overflow menus for drafts and folders, the root's own menu, the entries each offers, and the fixed position of **Information** immediately after **Open** on every draft row (DRP-FR-KDVX); the inline rename and inline creation fields and the client-side name validation that decides what never reaches the backend; the drag-and-drop gesture, which target is a valid drop, the drop feedback, and the refusal of a drop onto a folder's own subtree; the **Move to Folder…** picker and its keyboard operation; both delete confirmations; the create affordance; the empty state and the empty-folder affordance; the preservation of selection and focus across a mutation; the revealing of a draft another surface names by id — expanding its ancestors, selecting it, and relaxing whichever filter would hide it (DRP-FR-34), which introduces no backend operation; and the routing of a row activation to a New Artifact tab.
- **Delegated to backend (abstract)**:
  - `"list drafts"` — returns the active worktree's whole drafts hierarchy: every folder, and every draft with its id, name, status, last-activity instant, the folder it sits in, and the graduation run the project's queue holds for it (per `../core/DRS-draft-storage.md` DRS-FR-18). Owned by `../core/DRS-draft-storage.md` (DRS-FR-08), alongside `"create draft (name)"`, `"rename draft (id, name)"`, `"set draft status (id, status)"`, and `"delete draft (id)"`, which this panel invokes directly and which `NAW-new-artifact.md` names in its own contract boundary. `"create draft (name)"` is reached from this panel alone, from the two routes of DRP-FR-06 and DRP-FR-26, and it is what copies the project's draft template into the new draft (per `../core/DRS-draft-storage.md` DRS-FR-39); the panel neither reads the template nor passes it, and it is never routed through the typed-artifact window of `NTA-new-typed-artifact.md`, which creates project files and no draft. The panel renders folders, drafts, and their graduation state alike from this one call, however deep the tree; the graduation row rides on it rather than costing a call of its own, for the same reason the pending-proposal marker does.
  - The event `"graduation run changed"` (`../core/GRD-graduation.md` GRD-FR-EFAU) is what moves a row's graduation state, and `"graduation queue changed"` (the same requirement) is what re-lists when a run is enqueued or leaves the queue. This panel invokes no graduation operation of its own: starting one is a draft's action (`NAW-new-artifact.md` NAW-FR-18) and every decision on a run is taken in `GRU-graduation-runs.md` or `GRU-graduation-runs.md`.
  - `"create drafts folder (parent, name)"`, `"rename drafts folder (path, name)"`, `"delete drafts folder (path)"`, `"move draft to folder (id, folder)"`, and `"move drafts folder (path, destination)"` — the organisation of the drafts root, owned by `../core/DRS-draft-storage.md` (DRS-FR-29 through DRS-FR-34). None of them addresses anything inside a draft, and no operation anywhere reaches inside one to add, rename, or remove a file, a draft being exactly one prompt (per `../core/DRS-draft-storage.md` DRS-FR-11, DRS-FR-13).
  - `"search drafts (text)"` — returns the drafts whose name or file contents match the entered text, each saying which of the two matched. Owned by `../core/DRS-draft-storage.md` (DRS-FR-17). It is the one operation this panel makes that reads a draft's files.
  - `"load drafts panel state"` and `"save drafts panel state"` — the persisted filter position, filter text, and set of expanded folders, held per machine and per worktree in the project-local store (per `../core/PSS-project-settings-storage.md` PSS-FR-20).
  - The events `"drafts changed"` and `"draft build state changed"` (`../core/DRS-draft-storage.md` DRS-FR-22, DRS-FR-23) are what keep the tree itself and the build indicator current without the author refreshing anything.
  - The pending-proposal marker of DRP-FR-19 rides on `"list drafts"`' own row rather than on a call of its own: `../core/DRS-draft-storage.md` (DRS-FR-08) carries whether a draft holds an undecided proposal, because this panel's cost is one list call however many drafts the worktree holds. The event `"draft change proposals changed"` (`../core/DCP-draft-change-proposals.md` DCP-FR-16) is what re-lists it. This panel invokes no operation that reads or decides a proposal.
  - Opening a draft routes to `NAW-new-artifact.md`, and **Information** routes to `DFI-draft-information.md`; neither introduces an operation here, and this panel reads no statistic of its own.
  - The panel invokes `"open publication issue (draft id, url)"` (`../core/GHP-github-publication.md` GHP-FR-MJTB) for the issue link of a GitHub-shadow row alone (DRP-FR-NPZO), and **Graduate…** on that row opens the start dialog of `GSD-graduation-start-dialog.md` and invokes nothing itself.
  - The panel invokes **no other publication operation**. The status a row states is the one `"list drafts"` already returns (per `../core/DRS-draft-storage.md` DRS-FR-RJYF), so a row costs no read of a draft's publication store, and **Publish to GitHub** is offered by the draft's own tab alone (per `NAW-new-artifact.md` NAW-FR-GKBP).

## Functional requirements
1. **DRP-FR-01** Drafts is a vertical-panel surface, selected by its own toggle in the activity bar's leading cluster (per `SNV-shell-navigation.md` SNV-FR-44).
2. **DRP-FR-02** The panel renders the drafts of the project's **active worktree** and the folders they are organised into, served by `"list drafts"`, both living inside that worktree (per `NAW-new-artifact.md` NAW-FR-24). No draft and no folder of any other worktree appears in it, and changing the active worktree replaces the whole tree with the incoming worktree's own.
3. **DRP-FR-03** Each draft row shows the draft's name and a compact relative last-activity timestamp. Hovering the timestamp discloses the absolute instant. It shows no file count, a draft being one prompt (per `NAW-new-artifact.md` NAW-FR-06).
4. **DRP-FR-04** A draft with a build in flight renders a build indicator on its row and the word for that state in place of its timestamp. The indicator clears when the build ends, by whichever route.
5. **DRP-FR-05** The panel reacts to the `"drafts changed"`, `"draft build state changed"`, `"graduation queue changed"`, and `"graduation run changed"` events without manual refresh: a draft created, renamed, archived, restored, moved, graduated, or deleted, and a folder created, renamed, moved, or deleted, from anywhere — this panel, a New Artifact tab, or a completing graduation run — is reflected in the tree; a build starting or ending moves its row's indicator; and a run enqueued, advancing, or leaving the queue moves its row's graduation state (DRP-FR-35).
6. **DRP-FR-06** The panel carries a pinned create affordance that invokes `"create draft"` and opens the new draft — named `Untitled`, or the first `Untitled N` free in the worktree, and holding the prompt of that name (per `NAW-new-artifact.md` NAW-FR-04, NAW-FR-06) — in a New Artifact tab, made the active tab (per `NAW-new-artifact.md` NAW-FR-03). The new draft is created holding the project's **draft template** where the project configures one and an empty prompt where it does not; the copy is the creation operation's (per `../core/DRS-draft-storage.md` DRS-FR-39), so this panel asks for no template, passes none, and both of its creation routes produce the same starting content. The affordance asks the author for no name either, a draft being named by working in it rather than before it exists, and it creates the draft at the tree's root; the folder-scoped **New Draft** of DRP-FR-26 is how one is created inside a folder. This panel is the only surface that creates a draft: the **New Artifact** entries of the File menu (`SNV-shell-navigation.md` SNV-FR-24) and of the Project context menu (`LCM-library-context-menu.md` LCM-FR-08) open the typed-artifact window (`NTA-new-typed-artifact.md` NTA-FR-14) and create none.
7. **DRP-FR-07** The status filter is the toggle row of `SNV-shell-navigation.md` SNV-FR-62 and offers exactly four positions, in this order — **active** (the default), **archived**, **graduated**, and **all drafts** (per `NAW-new-artifact.md` NAW-FR-16). Active is the default, and each of the other two positions is one step away rather than gone. **Graduated** admits a draft whose status is `graduated` **or** `published`, both being drafts whose work has left the panel for somewhere else. **Graduated** is never folded into **archived**: a draft that became a specification and one the author gave up on are different facts, and a position that showed both would answer neither question. A draft whose graduated status has been released reads `active` and stands in the active position like any other (per `../core/DRS-draft-storage.md` DRS-FR-KQTW), the panel filtering on the status the row reports rather than on the run it names. The status filter narrows which drafts the tree holds and never which folders it holds: a folder left with no admitted draft still renders (DRP-FR-29), being the author's structure rather than a consequence of what is in it.
8. **DRP-FR-08** The tree is the panel's only structure, and there are no status group headers in any filter position. Every row **states its own stored status** wherever more than one status can stand in the position: an archived row reads `Archived`, a `graduated` row reads `Graduated`, and a `published` row reads `Published`, each with its own marker distinct from the others and from an active row, so a folder holding one of each renders once rather than four times. The **archived** position needs no such marking and carries none. The **graduated** position admits two statuses (DRP-FR-07) and therefore keeps the `Graduated` and `Published` labels on its rows.
9. **DRP-FR-09** Activating a draft row opens that draft in a New Artifact tab and focuses it, or jumps focus to the tab already showing it (per `NAW-new-artifact.md` NAW-FR-02). Activating a folder row expands or collapses it (DRP-FR-20).
10. **DRP-FR-10** Every draft row carries a `[⋯]` overflow button opening a menu anchored to it with exactly six entries, in this order: **Open** (DRP-FR-09), **Information** (DRP-FR-KDVX), **Rename…** (DRP-FR-11), **Move to Folder…** (DRP-FR-28), the archive entry (DRP-FR-18), and **Delete** (DRP-FR-12), with a seventh — **Go to run** — added below a divider on a row a graduation run holds (DRP-FR-35), and with the entries of DRP-FR-NPZO on a GitHub-shadow row. **Information** sits immediately after **Open**, being the only other entry that changes nothing. It offers no folder action: **New Folder**, **New Draft**, and the folder **Rename** and **Delete** of DRP-FR-22 appear on folder rows and on the root alone, and never here.
11. **DRP-FR-11** **Rename…** turns the row's name into an editable field in place, seeded with the current name. It is the one inline name field a draft row has, and it is the same field a newly created draft's row opens with (DRP-FR-36). Committing invokes `"rename draft"`, returns the row to its rendered form, and renames that draft's open tab if it has one (per `NAW-new-artifact.md` NAW-FR-04) — the strip's label follows the draft's name whichever surface the rename was made from. The rename carries the draft's prompt with it (per `NAW-new-artifact.md` NAW-FR-25). Escape and a commit of an empty name both leave the stored name untouched, and a backend refusal is shown inline against the field, leaving the row as it was. A name is not required to be unique (per `NAW-new-artifact.md` NAW-FR-04), and renaming a draft never moves it between folders.
12. **DRP-FR-12** **Delete** opens a confirmation naming the draft and stating that its prompt, its version history, its conversation, and its review threads go with it; confirming invokes `"delete draft"` and removes the row, closing that draft's New Artifact tab if one is open. Dismissing the confirmation invokes nothing. Deleting a draft writes nothing into the project, a draft having never been in it, and it leaves the folder that held it standing and empty.
13. **DRP-FR-13** The panel carries a text filter, available in every status position, narrowing the tree to the drafts the entered text is **found in** — matched against each draft's name and against the text of every file it holds, so a draft is found by a phrase written inside it and not only by what it was called. Matching is served by `"search drafts"` and is case-insensitive. The result narrows whatever the status filter already admits rather than replacing it. A draft the text admits renders inside its own folders with every ancestor of it revealed for as long as the filter holds, and a folder renders when its own name matches the text or its subtree holds an admitted draft, on the terms the Project panel's tree already follows (per `LIB-library.md` LIB-FR-09); a folder admitted on neither count is hidden. Revelation the filter forced is not the author's own and is not persisted (DRP-FR-14): clearing the filter returns every folder to the expansion state the author left it in.
14. **DRP-FR-14** The filter position, the filter text, and the set of expanded folders are sticky: they survive a panel switch and an application relaunch into the same worktree, persisted through `"save drafts panel state"` and restored through `"load drafts panel state"` (per `../core/PSS-project-settings-storage.md` PSS-FR-20). Expansion is recorded rather than collapse, so a folder absent from the persisted set — a newly created one, or every folder on a first-ever open — renders collapsed. A persisted path naming a folder not currently present is ignored when rendering and retained rather than pruned, so a folder that disappears and returns comes back expanded; an unresolvable path is never surfaced as an error. The panel coalesces rapid changes — a run of keystrokes, several folders expanded in succession — into a single write.
15. **DRP-FR-15** A worktree holding neither a draft nor a folder renders the first-class empty state of `SNV-shell-navigation.md` SNV-FR-60 in place of the tree and both filter controls: one centred block stating that there are no drafts yet, naming what a draft is, and carrying the create affordance of DRP-FR-06 as its single button — the pinned create affordance is not rendered alongside it, so the empty panel offers exactly one thing to activate. A worktree holding folders but no draft is not that state and renders its folders normally, each showing the affordance of DRP-FR-29. Neither is a filter that matches nothing; it renders in the tree's own region with both filter controls still present (per `SNV-shell-navigation.md` SNV-FR-61), because those states call for different actions.
16. **DRP-FR-16** At most one of the panel's floating surfaces is open at a time — a draft row's `[⋯]` dropdown, a folder row's menu, the root's menu, the draft-delete confirmation, the folder-delete confirmation, and the **Move to Folder…** picker — and opening one dismisses the other, each dismissing on Escape or an outside click without invoking any operation. The inline fields of DRP-FR-11, DRP-FR-23, and DRP-FR-24 are not floating surfaces, but only one is ever open, and opening any of the surfaces above closes an open field without committing it.
17. **DRP-FR-17** A row surviving the text filter on the strength of its contents rather than its name is annotated as matching the text, so it is clear why a row whose name says nothing about the query is in the tree. A row matched by its name carries no annotation, because the reason is already on the row, and no row carries one while the filter is empty.
18. **DRP-FR-18** The overflow menu's archive entry reads **Archive** on an active or `published` draft and **Restore** on an archived one, and invokes `"set draft status"` with the other position. Archiving a `published` draft leaves its publication history untouched, and restoring it returns it to `active` with that history intact (per `../core/DRS-draft-storage.md` DRS-FR-10). It asks for no confirmation, because it destroys nothing and reverses in one action from the same menu. Archiving moves nothing between folders: the row stays where it sits, gaining or losing the marker of DRP-FR-08, and leaves the tree only when the filter position no longer admits its new status. A draft with an open New Artifact tab keeps it open, the tab following the change into or out of its archived marker (per `NAW-new-artifact.md` NAW-FR-16) — a tab closed out from under the author by something done in a panel is a surprise, where a tab closed by the Archive action taken *in* it is not (per `NAW-new-artifact.md` NAW-FR-28). Restore is the counterpart of an archive made from either surface, so a draft retired from its tab is brought back from here without reopening it.
19. **DRP-FR-19** A draft carrying changes an agent has proposed of which at least one is still undecided (per `../core/DCP-draft-change-proposals.md` DCP-FR-04, DCP-FR-PWSF) renders a distinct marker on its row, read from the row `"list drafts"` already returns (per `../core/DRS-draft-storage.md` DRS-FR-08) so the marker costs this panel no call of its own, so a proposal waiting on the author is visible from the panel whether or not that draft's tab is open — the same reason the build indicator of DRP-FR-04 is there, and distinguishable from it, because a build in flight is work happening and a proposal pending is work waiting. Activating the row opens the draft on the ordinary terms of DRP-FR-09 and opens nothing else: the decision is made in the New Artifact tab (per `NAW-new-artifact.md` NAW-FR-35) and this panel offers no way to accept or decline anything. The marker clears when the proposal is decided, by whichever route.
20. **DRP-FR-20** The panel renders one hierarchical tree holding folders and drafts together, rooted at an **implicit root** that is the tree's container rather than a row: it is never rendered as a folder, is never selected, renamed, moved, or deleted, and is reached through the panel's own background rather than through a row of its own. A folder expands and collapses independently of every other, by its disclosure triangle or by activating its row, and a folder's expansion says nothing about its parent's or its children's. Depth is unbounded, and the tree is rendered from the single `"list drafts"` call of DRP-FR-02 however deep it runs.
21. **DRP-FR-21** Within every parent, folders render before drafts. Folders are ordered case-insensitively by name, and drafts are ordered most-recent-activity first, the ordering `"list drafts"` returns them in (per `../core/DRS-draft-storage.md` DRS-FR-08). The two orderings are stable across re-lists, so a tree redrawn by a `"drafts changed"` event does not reshuffle beneath the author.
22. **DRP-FR-22** A folder row carries a `[⋯]` button opening a menu with exactly five entries: **New Draft** (DRP-FR-26), **New Folder** (DRP-FR-23), **Rename** (DRP-FR-24), **Move to Folder…** (DRP-FR-28), and **Delete** (DRP-FR-25), the two creation entries leading the menu as one cluster separated by a divider from the three that act on the folder itself, exactly as the Project context menu's creation cluster leads its own (per `LCM-library-context-menu.md` LCM-FR-01). The implicit root offers **New Draft** and **New Folder** alone, having nothing to rename, move, or delete. Every entry carries a leading icon, and the menus use the visual primitives, spacing, and dismissal behaviour of the Project context menu (per `LCM-library-context-menu.md` LCM-FR-07) so the two surfaces read as one system.
23. **DRP-FR-23** **New Folder** opens an inline name field as a provisional row inside the folder the menu was opened on — or at the root, from the root's menu — expanding that folder if it was collapsed so the field is where the folder will be. Enter commits and invokes `"create drafts folder"`; Escape abandons it and invokes nothing. The name is validated in the panel before any call, as non-empty and free of path separators on the same rules the New Folder window applies (per `NFW-new-folder.md` NFW-FR-08), and a name failing them is refused at the field with the reason shown and the field left open holding what was typed. A backend refusal — a sibling of that name, a name the filesystem will not take — is surfaced the same way at the same field, which stays open with its value intact so the author corrects one name rather than starting over. A committed folder is revealed in the tree, expanded and empty, and becomes the selection.
24. **DRP-FR-24** **Rename** turns the folder row's name into an editable field in place, seeded with the current name. Enter commits and invokes `"rename drafts folder"`; Escape cancels and invokes nothing. An empty name, a name containing a path separator, and a name identical to the current one are each refused by the panel with no call made, the field staying open with the reason shown, on the same terms the Project context menu's rename applies its own client-side rejections (per `LCM-library-context-menu.md` LCM-FR-12). A backend refusal leaves the folder under its previous name and shows the reason at the field. A rename moves nothing: the folder keeps its parent, its subtree, and its expansion, and every draft beneath it keeps its id and its files.
25. **DRP-FR-25** **Delete** on a folder opens a confirmation naming it and stating that the drafts and folders it holds **move to its parent** rather than being deleted, counting them so the author knows the size of what is about to move. Confirming invokes `"delete drafts folder"`, which reparents every direct child into the folder's parent and then removes the emptied folder (per `../core/DRS-draft-storage.md` DRS-FR-31); the descendant hierarchy beneath each moved folder is preserved whole, and no draft is deleted, closed, or changed in id, prompt, status, or destination root. Deleting a top-level folder moves its contents to the implicit root. Dismissing the confirmation invokes nothing. A failure is reported inline against the folder's row naming what could not be moved, and the panel re-lists (DRP-FR-32) so the tree it shows is what is on disk rather than what was attempted.
26. **DRP-FR-26** **New Draft** on a folder invokes `"create draft"` with that folder as the draft's location and opens the new draft in a New Artifact tab on the identical terms of DRP-FR-06 — the same creation operation, the same `Untitled` naming, the same single prompt, the same draft template copied into it, and the same immediate rename mode of DRP-FR-36 — differing only in where the draft is filed. The folder says where the draft sits in this panel and nothing about where its specification eventually lands, a draft carrying no project destination at all (per `../core/DRS-draft-storage.md` DRS-FR-07) and the graduation agent choosing the paths from the captured prompt (per `NAW-new-artifact.md` NAW-FR-19). Nothing is written into the project artifact tree by creating a draft or by filing one. **New Draft** from the root creates the draft at the root.
27. **DRP-FR-27** A draft row and a folder row can each be picked up and dropped onto a folder row or onto the implicit root. Dropping a draft invokes `"move draft to folder"` and moves that draft alone; dropping a folder invokes `"move drafts folder"` and moves that folder with its whole subtree. A drop is refused — and its target never highlighted — where it would land an item in the parent it already sits in, land a folder on itself, land a folder anywhere inside its own subtree, or collide with a name already in the destination; a draft never collides, being identified in the tree by its id rather than by its name (per `../core/DRS-draft-storage.md` DRS-FR-30). A valid target is highlighted for as long as the pointer is over it and is distinguished from a refused one, so the author sees the outcome before releasing. Nothing moves from dragging over a row: the panel commits on release over a valid target and at no earlier moment, and a drag abandoned, released over empty space, or released over a refused target invokes nothing and leaves the item where it was. A failed move leaves the source in its original location and reports the error against its row (DRP-FR-31).
28. **DRP-FR-28** Every move available by dragging is available without a pointer. **Move to Folder…** on a draft row, a folder row, and in the same menus opens a picker listing the implicit root and every folder the item may legally move into, marking the item's current parent and every destination refused under DRP-FR-27 as unavailable rather than omitting them, so the reason a folder cannot be a destination is legible. The picker is operated entirely from the keyboard, confirms into the same `"move draft to folder"` and `"move drafts folder"` operations a drop invokes, and reports a failure exactly as a drop does. Every row is reachable and activatable by keyboard: folders expand, collapse, and open their menus, drafts open and open their menus, and the tree carries screen-reader labels naming each row's kind, its depth, whether a folder is expanded, whether an item can be moved, and — after a move, a rename, a create, or a delete — what has just happened and where the item now sits.
29. **DRP-FR-29** A folder holding nothing the current filters admit still renders, carrying a short line in place of its children saying so, rather than disappearing. A folder is the author's structure and outlives what is in it: one just created, one emptied by graduating the last draft in it, and one whose drafts the active status or text filter excludes are all still there to drop something into.
30. **DRP-FR-30** Selection and focus survive every mutation. A renamed or moved item stays selected and stays focused, following its new name or its new place in the tree; a created folder or draft becomes the selection. After a folder is deleted, focus lands on the first of its reparented children in the tree's order, or on the folder's parent — the root included — when it had none. Expansion is likewise preserved: a moved folder arrives expanded if it was expanded, and the folders around it keep their own state.
31. **DRP-FR-31** A typed error returned by any folder or move operation is surfaced inline against the row that initiated it — at the open inline field where there is one, at the row itself otherwise — rather than as a window-level notice, so the author reads it beside the thing it is about. While an operation is in flight the affordance that started it is disabled and the item cannot be dragged, so one gesture produces one call; a second create, rename, delete, or move on the same item is not accepted until the first has returned.
32. **DRP-FR-32** The tree is rendered from what the backend reports rather than from what the panel attempted. After every create, rename, delete, and move — successful or failed — and on every `"drafts changed"` event, the panel re-lists through `"list drafts"` and redraws from the result, preserving expansion (DRP-FR-14) and selection (DRP-FR-30). No mutation is reflected in the tree before it has landed, so the panel never shows an organisation the disk does not have, and an external change to the drafts root is reconciled by the same path.
33. **DRP-FR-33** A draft the backend reports as **inconsistent** — its storage holding something other than the one prompt a draft is (per `../core/DRS-draft-storage.md` DRS-FR-15) — still renders as a row, marked distinctly and stating that it cannot be opened. Activating it opens its tab on the inconsistency state rather than on an editing surface (per `NAW-new-artifact.md` NAW-FR-41), its **Rename…**, **Move to Folder…**, and archive entries render disabled, and **Delete** stays enabled, that being the one thing left to do with material that is not a draft. The row is never hidden and never silently repaired: a draft is not dropped from the panel for being unopenable, because the author is the one who decides what becomes of it.
34. **DRP-FR-34** Another surface may ask the Drafts panel to reveal a draft, naming it by its **id** rather than by its name or by the folder it sits in, so a draft renamed or moved since the caller last saw it is still the row that is reached. The panel expands every ancestor folder of that row, scrolls it into view, and makes it the selection and the focused row on the terms of DRP-FR-30; the expansion is recorded like the author's own (DRP-FR-14). A reveal always ends with the row visible: where a filter would hide it the panel relaxes that filter — moving the status filter to **all drafts**, which admits every status, `graduated` among them, rather than swapping one single-status position for another, and clearing the text filter — and only the filters that would actually hide the row are touched, so a reveal of a draft the current position already admits changes nothing about the panel's filtering. Relaxed filters persist like any other filter change (DRP-FR-14). Revealing opens nothing and mutates nothing: no tab is opened, no operation is invoked, and the draft's name, status, folder, and prompt are untouched. A reveal is about where the row sits in this panel and says nothing about which surface the vertical panel is showing, which is the caller's decision (per `SNV-shell-navigation.md` SNV-FR-45). An id the listed tree does not hold — a draft deleted, graduated, or belonging to another worktree — cannot be revealed, and the tree, the filters, and the selection are left exactly as they are with nothing reported. This is the path a New Artifact tab's own draft takes when the vertical panel follows the active tab (per `SNV-shell-navigation.md` SNV-FR-64, SNV-FR-66).
35. **DRP-FR-35** A draft the project's graduation queue holds a run for renders that run on its row, read from the row `"list drafts"` already returns (per `../core/DRS-draft-storage.md` DRS-FR-18) so it costs this panel no call of its own. The row carries a **graduation indicator** distinct from the build indicator of DRP-FR-04 and from the pending-proposal marker of DRP-FR-19 — a run writing a specification, a build in flight, and a proposal waiting are three different things about a draft — and its second line carries the run's state as a short phrase in place of the timestamp. The phrase is itself a route: activating it opens the Runs panel's graduation section on that run (per `GRU-graduation-runs.md` GRU-FR-MYFA), except for a run in `awaiting_review`, which opens the review instead; the same route is the menu's **Go to run** entry (DRP-FR-10), so it is reachable without a pointer. While the run is **non-terminal** the row is locked: **Rename…**, **Move to Folder…**, the archive entry, and **Delete** all render disabled with the reason stated, the row cannot be dragged, and it is refused as a drop source, because every one of those would change a draft an agent is working from — a refusal the backend enforces too (per `../core/DRS-draft-storage.md` DRS-FR-19), so a race ends in a typed error surfaced against the row rather than in a change that should not have landed. A **graduated** draft is locked on the same terms, permanently, and keeps its route to the run that graduated it. A **published** draft is not locked at all: its **Rename…**, **Move to Folder…**, archive, and **Delete** entries are all enabled and its row drags like an active one, publication being a fact about where the prompt was sent rather than a hold on the draft. Activating the row itself always opens the draft on the ordinary terms of DRP-FR-09; this panel offers no way to accept, reject, continue, answer, or publish anything.
36. **DRP-FR-36** A draft created from either route of DRP-FR-06 and DRP-FR-26 enters **rename mode at once**. Its row is revealed in the tree — its folder expanded where it was collapsed — selected, and rendered with the inline name field of DRP-FR-11 already open, seeded with the name it was created under and with the text selected, and **keyboard focus is placed in that field**. The author therefore names the draft by typing rather than by finding the row and choosing **Rename…**, which is why the creation asks for no name up front. The tab opened by the same act is the active tab in the main viewport (DRP-FR-06) and does not take the keystrokes: the author names the draft first and writes in it second. The field behaves exactly as an ordinary rename does thereafter — committing invokes `"rename draft"` and carries the prompt's filename with it (DRP-FR-11, per `NAW-new-artifact.md` NAW-FR-25), Escape and a commit of an empty name both leave the created name standing, and a backend refusal is shown inline against the field with the field left open — so there is one rename behaviour rather than a second one for new drafts. Opening any of the panel's floating surfaces closes the field without committing it (DRP-FR-16), and the draft exists whether the field is committed, abandoned, or closed, a create and a rename being two operations rather than one.
37. **DRP-FR-KDVX** **Information** opens that draft's statistics modal (per `DFI-draft-information.md` DFI-FR-ZGBU) and does nothing else: it invokes no operation of this panel's own, changes no draft, and leaves the row, the selection, and the tree exactly as they were. It is **enabled on every draft row without exception** — active, archived, `graduated`, held by a non-terminal graduation run, and reported inconsistent alike — because it reads an account of the draft rather than touching the draft, so the lock of DRP-FR-35 reaches it at no point and it is the one entry beside **Open** a locked row still offers. Its position is fixed immediately after **Open** in every one of those states, so the entry does not move under the pointer as a draft's state changes.
38. **DRP-FR-ZRJJ** A GitHub-shadow draft (per `../core/DRS-draft-storage.md` DRS-FR-XDWS) renders at the drafts root with a **GitHub** marker naming its repository and issue number, distinct from every other marker. Its row reads `GitHub task` while its status is `github_shadow` and `Graduated` once it reports `graduated`.
39. **DRP-FR-YVXS** The **active** filter position admits a draft whose status is `github_shadow`, and the **graduated** position admits a GitHub-shadow draft that reports `graduated`, on the terms of DRP-FR-07.
40. **DRP-FR-NPZO** A GitHub-shadow row's menu offers **Open**, **Information**, **Graduate…**, and **Open issue on GitHub**. **Rename…**, **Move to Folder…**, the archive entry, and **Delete** render disabled with the reason that the draft mirrors a GitHub issue, and the row cannot be dragged.
41. **DRP-FR-YYZU** **Graduate…** on a GitHub-shadow row opens the start dialog of `GSD-graduation-start-dialog.md` for that draft. It is disabled while a graduation run holds the draft or while the draft reports `graduated`. **Open issue on GitHub** invokes `"open publication issue (draft id, url)"` with the draft's issue URL.

## Non-functional requirements
- The panel is a narrow vertical surface: a long draft or folder name truncates on its row rather than widening the panel, and discloses in full on hover. Depth is expressed by indentation that stays legible at the panel's smallest width rather than pushing rows off it.
- The whole tree, at every depth, costs one `"list drafts"` call. A folder costs no call of its own, and expanding one issues nothing.
- The text filter is dispatched a short rest after the last keystroke rather than on each one, so typing a word costs one search rather than one per character; the tree stays interactive while a search is outstanding and never blanks between results.
- Folder names are validated in the panel before any operation is invoked, so a malformed name costs no round trip.
- Relative timestamps refresh as time passes without the author reopening the panel.
- The panel reads a draft's files only through `"search drafts"`, and only while the text filter holds something. A panel opened and never filtered costs one list call, whatever the size of the drafts in the worktree.
- A drag never writes. No operation is invoked while an item is being dragged, however long the gesture lasts or however many rows it crosses.
- A failed panel-state write is not surfaced as a blocking error — the tree stays usable and the state is written again on the next change.
