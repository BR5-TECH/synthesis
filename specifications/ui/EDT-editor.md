# Editor

**Spec code:** `EDT`

## Intent
Markdown WYSIWYG (Tiptap) for artifact authoring. A single editor handles every Markdown-based artifact type in v1 — Skill, Agent, Prompt, Spec, Instructions, Scenario, Scratchpad — and the plain text files of the project that carry no artifact type at all, so anything the Project panel or search can surface has somewhere to open (per `ESH-editor-source-files.md` ESH-FR-ATDS). What a file is named decides which surface it gets: a **Markdown file** — one whose name ends `.md` — is the rich document this editor was built for, read and written in either of two modes over one buffer (EDT-FR-17), while every other file is **source** and is edited as source alone, on one plain-text surface owned by `ESH-editor-source-files.md`. Structure lives in the Markdown content, not in editor chrome. A file's leading frontmatter is read as the YAML it is, so the rich surface renders it by the structure a parse gives it rather than by the shape of its lines, and reports how much of the 1024-character description budget an agent reads the block's `description` spends (EDT-FR-21, EDT-FR-59). An artifact's editing session belongs to the artifact rather than to the tab showing it, so tab churn never costs the author their buffer or their undo history — and so a surface other than an Editor tab can edit the artifact without becoming a second session of it: the editable target of a Diff tab on that file is this same buffer, this same history, and this same write (EDT-FR-72). An edit is written without being asked for: the buffer reaches disk a short rest after the last keystroke, so nothing an author typed is lost to a save they never thought to trigger, and the tab carries no Save control because there is no longer anything for one to do (EDT-FR-70). The editing surface reads as a page rather than as a wall of text filling the tab: an inset sheet with an edge of its own, set on a recessed field that carries the chrome around it, so an author who has just opened a file can see where the document begins and ends (EDT-FR-63). Discussion about the artifact sits beside it rather than inside it: the threads anchored to ranges of the text render in the empty margin the page already leaves, owned by `CMT-comments.md` (EDT-FR-61), and the conversation about the file as a whole is begun from the one floating control the tab carries in the corner of that field, owned by `ACT-action-control.md` (EDT-FR-64). A file the author opens is a file they can trust the Editor to hand back: the rich surface models the Markdown this project actually writes, returns it semantically unchanged, and leaves a file it was only asked to display exactly as it found it, so reading costs nothing and editing costs nothing beyond the edit (EDT-FR-66–EDT-FR-69). Out of scope: the Find and Find & Replace panels that take over the band above the editing surface, which are `EFR-editor-find-replace.md`'s; the two shapes of file, the source surface, and the syntax highlighting over it, which are `ESH-editor-source-files.md`'s; the baseline checksum, the external-change modal, and the resets a confirmed rollback produces, which are `EXC-editor-external-change.md`'s; and any repair or normalisation of the YAML the frontmatter region reads, so a block that does not parse and a description that overruns its budget are both reported rather than corrected (EDT-FR-58, EDT-FR-60).

## User stories
- As an author, I want a WYSIWYG Markdown editor so that I can write artifacts without juggling raw syntax.

## UI contract boundary
- **Owned by the UI**: WYSIWYG rendering, formatting toolbar, keyboard shortcuts, the indicator reporting whether the buffer has reached disk (EDT-FR-04), the scheduling of the writes that put it there (EDT-FR-70, EDT-FR-71), embedded mode chrome adjustments.
- **Owned by the UI**: the right-aligned action cluster of graphical controls in the tab chrome (the comments control, and the editing-mode toggle where the open file carries two modes — EDT-FR-16), the WYSIWYG⇄raw-Markdown dual editing mode and its toggle (EDT-FR-17), the visual treatment of YAML frontmatter (EDT-FR-18) together with the parse that drives it and the invalid-block indication it raises (EDT-FR-21, EDT-FR-58), and the description character count the frontmatter region reports against a fixed UI-side limit of 1024 (EDT-FR-59, EDT-FR-60). These introduce no new backend operation — both editing modes save the same Markdown bytes through the existing `"save artifact contents"`, and the artifact's type arrives via the Project panel's load contract (`../core/ASC-artifact-scanning.md`, `../core/PST-project-storage.md`) already.
- **Owned by the UI**: the Markdown the WYSIWYG surface parses on the way in and serialises on the way out (EDT-FR-66–EDT-FR-69) — which constructs the rich document models, what a construct the surface does not model survives as, the canonical spelling serialisation settles on, and the point in an artifact's life at which the buffer stops being the bytes that were loaded and starts being that serialisation. All of it is client-side and introduces no backend operation: the bytes still reach disk through the same `"save artifact contents"`, and the line-ending normalisation applied to them remains the backend's (EDT-FR-40).
- **Delegated to backend (abstract)**: `"load artifact contents by id"` (returns `{ body, checksum }`) and `"save artifact contents"` (returns `{ checksum }` of the bytes written), both owned by `../core/PST-project-storage.md`. They serve a plain text file exactly as they serve a Markdown artifact (per `ESH-editor-source-files.md` ESH-FR-TLJZ). The `"artifact changed externally"` event these two are paired with is consumed and resolved by `EXC-editor-external-change.md`, which owns the baseline checksum that decides whether an arriving event is a real divergence. Stubs may load/save in memory during the walking skeleton.
- **Owned by the UI**: reliance on the shell's native Edit menu (per `SNV-shell-navigation.md` SNV-FR-14) for OS-level edit accelerators — of which the Editor claims Undo and Redo and routes them to the artifact's single edit history (EDT-FR-22–EDT-FR-25). That history and the session-lived retained edit state it belongs to (EDT-FR-28–EDT-FR-30) are entirely client-side and introduce no new backend operation: the state is held in memory and never persisted, so it needs no storage contract. The rest-after-typing schedule that decides *when* an artifact is written (EDT-FR-70) is likewise the Editor's own; it changes no operation's shape, only how often one is invoked. Every write it performs, every flush it brings forward when a tab, the project, or the application closes (EDT-FR-31–EDT-FR-33), and every write the File menu's Save and Save All items demand (EDT-FR-34–EDT-FR-36) go through the same `"save artifact contents"`. A Diff tab's editable target is a surface of this same session (EDT-FR-72) and introduces no operation of its own for exactly that reason: it loads through `"load artifact contents by id"` and writes through `"save artifact contents"` because it *is* the artifact being edited, not a second thing that resembles it.
- **Owned by the UI**: the framing of the editing surface as a page set on a field (EDT-FR-63) — the page's inset, its edge, its measure, and the recessed treatment of the field around it. It is presentation over content the load contract already supplies, so it introduces no backend operation and changes no byte a save writes.
- **Owned by the UI**: the tab region the comments occupy (EDT-FR-61) and the comments control that shows and hides them from the action cluster (EDT-FR-16). Everything within that region — the threads, their anchors, their composers, and the operations that persist them — belongs to `CMT-comments.md`, so the Editor introduces no backend operation for it and their own contract is declared there.
- **Owned by the UI**: the tab corner the action control occupies (EDT-FR-64) and the division of actions between it and the action cluster (EDT-FR-65). The control itself, the actions it offers, the composer it opens, the discussion panel, and the operations behind all of them belong to `ACT-action-control.md`, so the Editor introduces no backend operation for any of it and their contract is declared there.
- **Owned by the UI**: the tab's hosting of a review of a change an agent proposed to a prompt artifact (EDT-FR-84) — that the modal is anchored within this tab and that the pending indication sits in the action cluster. The modal itself, the comparison it renders, the candidate it edits, and every operation behind them belong to `PCR-prompt-change-review.md` and `../core/PCP-prompt-change-proposals.md`.
- **Owned by the UI**: the quiescing of an artifact's writes (EDT-FR-81) — what a quiesce cancels, refuses, and awaits. It introduces no backend operation of its own: it only decides whether an existing `"save artifact contents"` is started or awaited. What a confirmed rollback then does to the session belongs to `EXC-editor-external-change.md` (EXC-FR-JAWT, EXC-FR-ZXWI).
- **Owned by the UI**: the detection of an artifact's indentation convention from its Markdown body and the Tab-key behaviour that convention drives (EDT-FR-37–EDT-FR-39), which are entirely client-side and introduce no backend operation. Line endings are not: the buffer is agnostic about them and the bytes reaching disk are normalised by the backend to the project's convention (EDT-FR-40, EDT-FR-41), so neither editing mode carries a line-ending notion of its own.
- **Delegated to no operation of its own**: the band above the editing surface is shared with `EFR-editor-find-replace.md`, and which of the two shapes a file takes is `ESH-editor-source-files.md`'s. Neither introduces a backend operation, and both are reached from this tab rather than from a surface of their own.

## Functional requirements
1. **EDT-FR-01** Editor is a tab in the main viewport opened when an artifact — or a plain text file (per `ESH-editor-source-files.md` ESH-FR-ATDS) — is selected from the Project panel, Search, Dashboard widgets, or Flow click-through (per `OVW-overview.md` OVW-FR-07).
2. **EDT-FR-02** Editor renders Markdown content as WYSIWYG; the underlying Markdown file remains free of Synthesis-specific syntax.
3. **EDT-FR-03** All v1 Markdown artifact types (Skill, Agent, Prompt, Spec, Instructions, Scenario, Scratchpad) use the same Editor component; no per-type chrome is added.
4. **EDT-FR-04** An artifact holds unsaved changes from the moment the user's first edit is applied until the write carrying it lands. An indicator stands on **every** tab showing that artifact for as long as it does — the Editor tab's chrome, and the write state a Diff tab on the same file carries (per `DFV-diff-viewer.md` DFV-FR-51) — so whether the buffer has reached disk is legible wherever the author is looking at it and no two surfaces disagree about it; it clears on a successful write and stands again on the next edit.
5. **EDT-FR-07** Opening the same artifact from a second source focuses the existing Editor tab rather than creating a duplicate (per `TAB-tabs.md`).
6. **EDT-FR-15** OS-level edit operations — undo, redo, cut, copy, paste, select-all — work inside the Editor via the platform-standard accelerators, backed by the shell's native Edit menu roles (per `SNV-shell-navigation.md` SNV-FR-14). Cut, copy, paste, and select-all act on the focused editing surface; undo and redo are claimed by the Editor and act on the artifact's edit history (EDT-FR-22), not on save points — a save neither clears that history nor bounds how far undo reaches.
7. **EDT-FR-16** The Editor's primary actions — the comments control (EDT-FR-61, per `CMT-comments.md` CMT-FR-29) and, over a Markdown file, the editing-mode toggle (EDT-FR-17) — are presented as graphical icon controls (not text-label buttons), sized as comfortable pointer targets, grouped in a single right-aligned action cluster within the Editor tab's chrome. Over a source file the cluster holds the comments control alone: that file has one editing surface, so there is nothing for a toggle to move between (per `ESH-editor-source-files.md` ESH-FR-LKNM). The cluster carries no Save control: an artifact writes itself (EDT-FR-70), so a control to write it would either do nothing or duplicate what has already happened.
8. **EDT-FR-17** Over a **Markdown file** (per `ESH-editor-source-files.md` ESH-FR-FKZB) the Editor supports two editing modes across the same buffer: **WYSIWYG** and **raw Markdown text** (source). The mode toggle (EDT-FR-16) switches between them, and **WYSIWYG is the default** the first time such a file opens in a session — a tab reopened onto retained edit state resumes in the mode that was active when it last closed (EDT-FR-29); undo and redo also switch the mode when the step they traverse belongs to the other one (EDT-FR-25). The raw-text surface exposes the **entire Markdown file as one editable document**, including any leading frontmatter (EDT-FR-18). Toggling modes is lossless: it preserves the in-memory buffer and the dirty state (EDT-FR-04), reformats nothing, and — absent an edit — leaves the bytes a save would write unchanged (EDT-FR-66). Both modes read and write the same Markdown through the existing `"save artifact contents"` (per `EXC-editor-external-change.md` EXC-FR-HKKG).
9. **EDT-FR-18** When a **Markdown file** (per `ESH-editor-source-files.md` ESH-FR-FKZB) begins with a YAML frontmatter block (delimited by leading `---` fences), the two modes treat it differently. In **WYSIWYG** mode the frontmatter is carved out into a visually distinct region separated from the rich body: it is never interpreted as body content (never rendered as a thematic break, heading, or paragraph) and is editable as that distinct region. In **raw-text** mode the frontmatter is **not** split into a separate region — it is the literal leading lines of the editable source document and is edited in place there, since the source surface is the same Markdown file (EDT-FR-17). Frontmatter is preserved on round-trip and save unless the user edits it (in either mode). The WYSIWYG frontmatter region is **never internally scrollable**: while expanded it grows vertically to fit its full content (no vertical scrollbar and no fixed height that would clip lines), and long lines **soft-wrap** rather than scrolling horizontally (no horizontal scrollbar), so that — when expanded — all frontmatter is visible at once without scrolling within the region. (The region may be collapsed to a single line by the scroll-driven behavior in EDT-FR-20.)
10. **EDT-FR-20** In WYSIWYG mode, the frontmatter region's expanded/collapsed display is driven by the artifact's scroll position, with scroll position authoritative. It is shown **fully expanded** when the artifact is scrolled to (or sitting at) the top — including immediately after opening (EDT-FR-18). When the artifact is **scrolled down** away from the top, the region **automatically collapses to a single minified line**. Clicking the collapsed single line expands it as a **transient peek**: the next scroll-down away from the top re-collapses it (scroll wins). While the region is expanded, a small **minimize button in its top-right corner** collapses it to the single line on demand without scrolling. The collapsed single line stays identifiable as frontmatter and is the click target to expand; it is a summary bar, not an editing surface (editing the frontmatter, per EDT-FR-18, happens in the expanded region). This collapse/expand is presentation-only — frontmatter content, editability, and byte-preservation (EDT-FR-18) are unchanged — and applies to WYSIWYG mode only; raw-text mode keeps frontmatter inline in the source (EDT-FR-17).
11. **EDT-FR-21** In WYSIWYG mode, within the distinct frontmatter region (EDT-FR-18), the block is rendered from a **YAML parse of it** rather than from the shape of its lines, and each piece carries the treatment of the role the parse gives it: every mapping key — nested keys included — is rendered **bold**; every scalar value is rendered in normal (non-bold) weight, including the folded lines of a block scalar; and the `---` fences, `:` separators, list markers, quoting characters, block-scalar indicators (`|`, `>`) and comments carry a receding treatment distinct from both. The parse reads and never rewrites: nothing is re-serialised, re-indented, re-quoted, reordered, or folded differently, so the treatment is **presentation-only** — it changes no bytes and does not affect frontmatter editability or byte-preservation (EDT-FR-18). It does not apply in raw-text mode (where the frontmatter is literal source, EDT-FR-17) nor to the collapsed single-line summary bar (EDT-FR-20).
12. **EDT-FR-22** Each artifact has exactly one undo/redo history, covering every user edit made to it during the application session regardless of which editing surface produced it: the WYSIWYG rich body, the WYSIWYG frontmatter region (EDT-FR-18), the raw-text source surface (EDT-FR-17), and the editable target of every Diff tab open on that file (per `DFV-diff-viewer.md` DFV-FR-42). Undo and redo traverse that single history in strict edit order, so the most recent edit is always the next one reversed, whichever surface it was made on. The history belongs to the artifact, not to the tab displaying it (EDT-FR-28, EDT-FR-72).
13. **EDT-FR-23** Only user edits occupy a position in the history. Content the Editor writes into an editing surface itself is never an undoable step — specifically the initial population of the surface when the artifact loads, the restoration of retained edit state when a tab reopens (EDT-FR-29), the synchronisation performed when a mode becomes active (EDT-FR-17), and the replacement performed by "Load from filesystem" (per `EXC-editor-external-change.md` EXC-FR-WDAV). Operating a find panel is likewise not an edit: opening or closing it, changing its query, its replacement text, or its active match mode, and moving the current match occupy no position in the history (per `EFR-editor-find-replace.md`). The replacements those panels perform are user edits and do occupy one (per `EFR-editor-find-replace.md` EFR-FR-FYNZ). No sequence of undo can therefore reach a state the user did not author, and in particular can never empty an artifact that loaded with content.
14. **EDT-FR-24** The oldest state undo can reach is the artifact exactly as the Editor last adopted it from `"load artifact contents by id"` (per `EXC-editor-external-change.md` EXC-FR-WCOM) — the content as it first opened in this session, or as it was last replaced by "Load from filesystem" (per `EXC-editor-external-change.md` EXC-FR-WDAV). Undo past that point is a no-op that leaves the buffer, the mode, and the dirty indicator (EDT-FR-04) unchanged. A successful "Load from filesystem" discards the history together with the buffer it discards, making the newly loaded content the new oldest reachable state; undo never resurrects content from before that replacement, and a rollback reset (per `EXC-editor-external-change.md` EXC-FR-JAWT) moves the floor the same way and for the same reason. Reopening a tab onto retained edit state adopts nothing and so moves nothing: the floor stays exactly where the artifact's editing session left it (EDT-FR-29).
15. **EDT-FR-25** When the step undo or redo traverses was made in a mode other than the active one, the Editor switches to that mode (EDT-FR-17) before applying the step, so every reversal is visible where it happened. When the step belongs to the WYSIWYG frontmatter region and that region is collapsed, the region expands as a peek (EDT-FR-20) for the same reason. Toggling modes is itself not an edit and never occupies a position in the history (EDT-FR-23); a mode switch performed as part of an undo or redo is not separately undoable.
16. **EDT-FR-28** An artifact the user has edited carries a **retained edit state** for the rest of the application session, comprising its Markdown buffer, its dirty state (EDT-FR-04), its active editing mode (EDT-FR-17), its undo/redo history (EDT-FR-22), and its baseline checksum (per `EXC-editor-external-change.md` EXC-FR-WCOM). The state is keyed by the artifact's stable key — the same identity the single-tab rule uses (per `TAB-tabs.md` TAB-FR-04) — and is held only in memory: no part of it is written to disk. It is what **every** tab bound to that artifact renders and edits, however many there are and of whichever kind (EDT-FR-72). It comes into being with the artifact's first edit, the first opening of one of its find panels (per `EFR-editor-find-replace.md` EFR-FR-GBJT), or the opening of a Diff tab on the file, which needs a target to render (per `DFV-diff-viewer.md` DFV-FR-25); an artifact that is opened and read in an Editor tab without an edit or a find panel carries none. It is discarded when the open project closes (per `SNV-shell-navigation.md` SNV-FR-25), when the application exits (SNV-FR-26), when the active project is switched (per `OVW-overview.md` OVW-FR-11), and when the project's active worktree changes (per `OVW-overview.md` OVW-FR-12) — never by closing its tab, by activating another tab, or by saving. Each of those four discards happens only after every unsaved change has been written (EDT-FR-33), so nothing the user authored is lost with the state. A rollback that removes the artifact's file discards the state as a fifth case and is the one that deliberately does **not** write first (per `EXC-editor-external-change.md` EXC-FR-ZXWI), the author having just asked for that file to be gone.
17. **EDT-FR-29** Opening an Editor tab for an artifact that carries retained edit state (EDT-FR-28) resumes that state: the retained buffer renders in the retained editing mode with the retained dirty indicator, and the full undo/redo history is immediately traversable, so an edit made before the tab was closed is still the next one undo reverses. The Editor still invokes `"load artifact contents by id"` on that open and compares the returned `checksum` against the retained baseline; when the two differ, the file changed on disk while no tab was showing the artifact, and the external-change modal is raised with its two resolutions (per `EXC-editor-external-change.md` EXC-FR-TYKX) rather than either version being silently adopted or silently discarded. An artifact with no retained state opens as a first load (EDT-FR-01, per `EXC-editor-external-change.md` EXC-FR-WCOM).
18. **EDT-FR-30** Activating another tab does not end an artifact's editing session. An Editor tab or a Diff tab that is not the active tab keeps the artifact's buffer, dirty state, editing mode, and undo/redo history, an Editor tab keeping any open find panel with its query and match mode (per `EFR-editor-find-replace.md` EFR-FR-GBJT) and a Diff tab keeping its own held original and modes (per `DFV-diff-viewer.md` DFV-FR-52); making either active again performs no reload, reverses nothing, and leaves the next undo exactly where it was.
19. **EDT-FR-31** Closing an Editor tab or a Diff tab while the artifact holds unsaved changes brings the pending write forward rather than waiting out the rest of EDT-FR-70: `"save artifact contents"` is invoked with the buffer, the returned `checksum` becomes the artifact's baseline (per `EXC-editor-external-change.md` EXC-FR-HKKG), and only then does the tab close. Closing a tab whose buffer has already reached disk writes nothing, and neither does closing one of several tabs on an artifact whose write another of them has already brought forward. Either way the retained edit state outlives the close (EDT-FR-28), so the history is intact when the artifact is reopened in a tab of either kind.
20. **EDT-FR-32** A close-time flush never overrides a guard. When the tab has an unresolved external-change modal (per `EXC-editor-external-change.md` EXC-FR-VTUH, EXC-FR-VNLZ), or when `"save artifact contents"` fails (EDT-FR-71), the close is cancelled: the tab stays open and focused with the blocking modal or error visible, and it closes only when the user resolves the blocker and closes again.
21. **EDT-FR-33** Closing the open project, quitting the application, switching the active project, and changing the project's active worktree all flush the same way: every artifact holding unsaved changes is written through `"save artifact contents"` before any tab is torn down (per `SNV-shell-navigation.md` SNV-FR-25 and SNV-FR-26 and `OVW-overview.md` OVW-FR-11 and OVW-FR-12). A flush blocked by EDT-FR-32 cancels the transition and focuses the Editor tab holding the blocker, so the project stays open on its current worktree and the application keeps running until the user resolves it.
22. **EDT-FR-34** The File menu's Save item (per `SNV-shell-navigation.md` SNV-FR-28) brings forward the pending write of the artifact the active tab is bound to, whether that tab is an Editor tab or a Diff tab: the same `"save artifact contents"` invocation the rest of EDT-FR-70 would have performed on its own, adopting the returned `checksum` as the new baseline (per `EXC-editor-external-change.md` EXC-FR-HKKG) and clearing the indicator of EDT-FR-04. It is the one way an author writes an artifact on demand, no surface that edits one carrying a Save control of its own (EDT-FR-16, per `DFV-diff-viewer.md` DFV-FR-42), and it is also how a failed write is retried (EDT-FR-71).
23. **EDT-FR-35** Save All (per `SNV-shell-navigation.md` SNV-FR-31) brings forward the pending write of every artifact holding unsaved changes, each through `"save artifact contents"` with its own buffer and each adopting the `checksum` that its write returns as its baseline. Its scope is the set of artifacts whose retained edit state (EDT-FR-28) holds unsaved changes, not the set of open tabs — an artifact is written because its buffer has not reached disk, not because a tab is showing it — and an artifact whose buffer already has is not written at all.
24. **EDT-FR-36** A write blocked by EDT-FR-32 does not abort a Save All sweep. Every artifact whose write is not blocked is still written; afterwards the first blocked artifact's Editor tab is focused with its blocking modal or error visible, opening a tab for that artifact if none is open. The blocked artifact keeps its unsaved changes, so Save All stays available and writes it once the user resolves the blocker and invokes Save All again.
25. **EDT-FR-37** Each artifact has an **indentation convention** — tabs, or spaces with a width — detected client-side from its Markdown body when the artifact first loads, and reported by the status bar's indentation control (per `STB-status-bar.md` STB-FR-21). An artifact whose body contains no indented line is described as spaces with a width of 2. Detection reads the content and changes nothing about it.
26. **EDT-FR-38** The convention decides what the raw-text editing surface (EDT-FR-17) inserts when the user presses Tab. Selecting a different convention in the status bar's control (per `STB-status-bar.md` STB-FR-23) changes only what subsequent Tab keypresses insert: it rewrites no existing line, alters no byte on its own, does not mark the artifact dirty (EDT-FR-04), and occupies no position in the undo history (EDT-FR-23).
27. **EDT-FR-39** An artifact's active indentation convention is part of its retained edit state (EDT-FR-28) alongside the buffer, dirty state, editing mode, undo history, and baseline checksum. It therefore survives the tab closing and reopening within the session and is discarded with that state; an artifact carrying no retained state is described by detection alone on its next load.
28. **EDT-FR-40** The in-memory buffer carries no line-ending convention of its own. The bytes written to disk are normalised to the open project's convention by `"save artifact contents"` (per `../core/PST-project-storage.md` PST-FR-22), and the baseline the Editor adopts after a save is the `checksum` that write returns (per `EXC-editor-external-change.md` EXC-FR-HKKG) — computed over the normalised bytes — so a normalisation performed on write never presents afterwards as an external change (per `EXC-editor-external-change.md` EXC-FR-ALXA).
29. **EDT-FR-41** Changing the project's line-ending convention, from either entry point (per `STB-status-bar.md` STB-FR-18 and `SET-project-settings.md` SET-FR-11), marks the artifact of every open Editor tab dirty (EDT-FR-04) without altering any buffer and without adding a step to any undo history (EDT-FR-23), so the pending conversion is visible and is written when the user saves. An artifact with no open tab gains no dirty marker and is converted whenever it is next written.
30. **EDT-FR-58** When the leading block does not parse as YAML, the frontmatter region renders its content as plain unhighlighted text — none of the role treatments of EDT-FR-21 apply — and carries an indication that the block is not valid YAML. The region stays exactly as editable, as expandable and collapsible (EDT-FR-20), and as byte-preserving (EDT-FR-18) as it is over a block that parses; the failure to parse marks the artifact dirty (EDT-FR-04) no more than rendering it does, and the Editor never rewrites an unparseable block on the user's behalf. The indication clears, and the role treatments return, the moment an edit makes the block parse.
31. **EDT-FR-59** When the parsed block (EDT-FR-21) carries a top-level `description` key whose value is a scalar string, the frontmatter region reports its length as `<count>/1024` against a fixed UI-side limit of **1024** characters — the description budget the agents that read these files accept. The reading is present in **both** of the region's displays (EDT-FR-20): expanded, it sits on a line along the region's bottom edge, aligned to its trailing edge; collapsed, it rides at the trailing edge of the single-line summary bar, so the budget stays visible while the artifact is scrolled into its body. It is part of the bar rather than a control of its own, so clicking it expands the region like clicking anywhere else on the bar. The reading follows the key rather than the artifact's type, so every artifact type and every untyped Markdown file (per `ESH-editor-source-files.md` ESH-FR-ATDS, ESH-FR-FKZB) whose frontmatter carries such a `description` shows it. It is absent when the block carries no top-level `description`, when that key's value is not a scalar string, when the block does not parse (EDT-FR-58), in raw-text mode (EDT-FR-17), and on a source file, which has no such region at all (per `ESH-editor-source-files.md` ESH-FR-SSDV).
32. **EDT-FR-60** The count is the length of the description's **parsed scalar value** — the string YAML yields once quotes are stripped, a block scalar (`|`, `>`) is folded, and continuation lines are joined — rather than the number of source characters the key occupies. It is recomputed from the buffer whenever the buffer changes, including edits made in the raw-text surface and steps traversed by undo and redo (EDT-FR-22), so both displays are current the moment they render. At or below the limit the reading renders in its normal treatment; above it the reading renders in a warning treatment while continuing to read the true count (`1180/1024`), identically whether the region is expanded or collapsed. Overrunning the limit blocks nothing: it prevents no edit, gates no save, holds back no write the artifact had scheduled (EDT-FR-70), and changes no byte. The reading is region chrome rather than an editing surface — it is not editable, contributes no match to the find panels (per `EFR-editor-find-replace.md` EFR-FR-DDUX), and occupies no position in the undo history (EDT-FR-23).
33. **EDT-FR-61** The Editor tab lends the empty margin beside its centred page to the artifact's **comments** (per `CMT-comments.md` CMT-FR-01). That margin is field rather than page (EDT-FR-63), so a card sits beside the document instead of on it. They take no column of their own and the page never narrows for them, so a glance at a thread costs the author no word of the text they are reading, and where the margin fits beside the page showing or hiding them moves nothing at all. What yields on a tab too narrow to leave that margin its measure is the page's position rather than its measure: the leading field is given up first and the page slides toward the leading edge (EDT-FR-63), and the cards take a column below the page's foot rather than a place over it once even that is spent (per `CMT-comments.md` CMT-FR-64). Below the width at which the page's own inset would be lost, the measure yields too, so the sheet never runs flush to the tab's boundaries and a page set in a narrow column keeps its edge (EDT-FR-63). Comments render wherever the Editor sets the file's text on that page: a Markdown file's WYSIWYG surface, and the one surface a source file has (per `ESH-editor-source-files.md` ESH-FR-SSDV, per `CMT-comments.md` CMT-FR-02) — a Markdown file toggled to raw text hides them (EDT-FR-17). The control that shows and hides them — carrying the artifact's unresolved-thread count — sits in the action cluster (EDT-FR-16) throughout. They belong to the tab's own chrome rather than being a floating overlay, on the same footing as the band above the editing surface (per `EFR-editor-find-replace.md` EFR-FR-AVML). Nothing they render is part of the editing surface: their content contributes no match to the find panels (per `EFR-editor-find-replace.md` EFR-FR-DDUX), a replacement never rewrites it, and no action taken in them occupies a position in the artifact's undo history (EDT-FR-23) or marks the artifact dirty (EDT-FR-04). Whether they are shown is part of the artifact's retained edit state (EDT-FR-28).
34. **EDT-FR-62** The Editor's surfaces set text in the typographic roles of `OVW-overview.md` OVW-FR-13: the WYSIWYG surface's prose in the **Rich Markdown** role, and the raw-text source surface — a Markdown file's, and the single surface a source file carries (per `ESH-editor-source-files.md` ESH-FR-SSDV) — in the **Source code** role. Within WYSIWYG, fenced and inline code and the frontmatter region (EDT-FR-18, EDT-FR-21) set in the Source code role rather than the Rich Markdown one, so code reads as code on whichever surface the author is on. The roles govern family, size, and line height alone: the YAML treatment of EDT-FR-21, the token colours of a highlighted source file (per `ESH-editor-source-files.md` ESH-FR-YNIV), the mode toggle (EDT-FR-17), the dirty state, the undo history, and the bytes a save writes are all unaffected by any of them, and a role changed mid-session re-typesets the open tab without disturbing its buffer or its scroll position.
35. **EDT-FR-63** The editing surface renders as a **page**: a bounded sheet carrying a background of its own, inset from the tab's boundaries on every side, and separated from the **field** behind it by an edge — a hairline border together with a soft elevation — so where the document begins and ends is legible the moment a file opens rather than inferred from where the text happens to stop. The field is everything of the tab that is not the page: the band above the surface (per `EFR-editor-find-replace.md` EFR-FR-ABHF), the margin the comments occupy (EDT-FR-61), and the empty width beside the centred page. It carries a recessed background distinct from the page's, and the two stay distinguishable under either theme (per `OVW-overview.md` OVW-FR-09, OVW-FR-10). The page holds a bounded measure whatever width the tab has and pads its text clear of its own edge; it scrolls within the field beneath the band, so its leading and trailing edges are both reachable and it never runs flush into the band above it. It is horizontally **centred** in field the tab has no other use for: where the margin beside it carries comments (EDT-FR-61) and the tab is too narrow to leave them their measure, the page slides toward the leading edge by as much as the leading field can spare — never past the inset it keeps from the tab's own edge — so the trailing field grows to hold them, and it re-centres the moment that margin no longer needs the room. Its measure is the same either way, so no line of the document reflows and the caret does not move. A surface that borrows this framing with no margin to fill — a Diff tab's rich rendering (per `DFV-diff-viewer.md` DFV-FR-38) — is centred at every width. Both editing modes render on the same sheet (EDT-FR-17) — the raw-text surface is the page the WYSIWYG surface is, not a bare region — as does the single surface of a source file, coloured or plain (per `ESH-editor-source-files.md` ESH-FR-SSDV, ESH-FR-BABL), and as does a file that loaded with no content at all. The framing is presentation-only: it changes no byte, marks nothing dirty (EDT-FR-04), occupies no position in the undo history (EDT-FR-23), and contributes no match to the find panels (per `EFR-editor-find-replace.md` EFR-FR-DDUX).
36. **EDT-FR-64** The Editor tab carries the **action control** of `ACT-action-control.md` (ACT-FR-01), floating in the bottom-trailing corner of the field around the editing surface and bound to the open artifact or plain text file (ACT-FR-02). It is present in **both** editing modes (EDT-FR-17), unlike the comments, because starting a conversation about the file in front of the author is not a thing the shape of the text on screen has any bearing on. What it offers is decided there and not here: **Discuss** on everything the Editor opens, and **Implement** in addition on an artifact whose type is `spec` (ACT-FR-04). It stands in the field beside the page and covers no part of it at any window size (ACT-FR-09), and the discussions it opens are read in the rail's Discussion section while the tab is in WYSIWYG mode and in the floating panel while it is in raw-text mode (ACT-FR-19, ACT-FR-20) — and a discussion the Editor cannot show is read in a conversation tab (per `CVP-conversation-presentation.md`). It is the tab's own chrome rather than a floating overlay, on the same footing as the band above the editing surface (per `EFR-editor-find-replace.md` EFR-FR-AVML), and nothing it opens touches the buffer: no match for a find panel (per `EFR-editor-find-replace.md` EFR-FR-DDUX), no step in the undo history (EDT-FR-23), no dirty marker (EDT-FR-04), and no byte a save writes.
37. **EDT-FR-65** The action control stands apart from the action cluster in the tab's chrome (EDT-FR-16), which keeps the editing-mode toggle and the comments control exactly as it holds them. The two divide by what they act on: the cluster carries how the Editor shows the file — which surface it is edited on, whether the threads beside it are in view — and the control carries what is done with the file as a whole, which is the same wherever that file is open. An action therefore appears in one of the two and never in both.
38. **EDT-FR-66** An artifact's buffer holds the bytes it loaded with until the user edits it. Opening a file, rendering it in either mode, toggling between them (EDT-FR-17), scrolling, collapsing or expanding the frontmatter region (EDT-FR-20), and operating a find panel without performing a replacement (per `EFR-editor-find-replace.md`) all leave the buffer exactly as `"load artifact contents by id"` returned it, so a save performed without an edit writes the file back byte-for-byte and a file the author only reads is never rewritten. The first user edit is what changes the buffer: an edit made on the raw-text surface makes it exactly what the author typed, and an edit made on the WYSIWYG surface makes it that surface's serialisation of its document (EDT-FR-67). A source file (per `ESH-editor-source-files.md` ESH-FR-SSDV) is only ever the former, having no rich surface to serialise from: its buffer is the bytes it loaded with until the author types, and thereafter exactly what they typed. Because a whole file is serialised at once, the canonical spelling reaches every part of it and not only the passage that was edited.
39. **EDT-FR-67** The WYSIWYG surface's serialisation is **semantically lossless**. No content is discarded and no text changes meaning: every character of the document's prose survives as the character the author wrote, so a `<` or a `>` is written literally and never as an entity, and a sequence that resembles an HTML tag — `<artifact>`, `<discussion_history>`, `<a pre-clear sequence>` — is prose that survives intact rather than markup to interpret and discard. What serialisation may settle is the **spelling** of Markdown syntax where the choice carries no meaning a reader of the file depends on: which marker a bullet list takes, which delimiter emphasis uses, whether a heading is written ATX or setext, and how a hard line break is spelled. It may not drop a construct, alter what one means, reorder anything, or change any text inside a code span or a fenced block, whose contents are literal in both directions.
40. **EDT-FR-68** The WYSIWYG surface models every Markdown construct this project's files are written in, so that round-tripping one is a question of spelling (EDT-FR-67) rather than of survival: headings, paragraphs, emphasis and strong, inline code, fenced code carrying its language, links, images, blockquotes, ordered and bullet lists including nested ones, task lists, tables, thematic breaks, strikethrough, footnotes, and hard breaks. Each renders as itself on the rich surface and is editable there, an image rendering through the resolution its host supplies (EDT-FR-85). A construct the surface does not model is **preserved rather than dropped**: it survives the round trip byte-for-byte and renders as inert content, editable on the raw-text surface (EDT-FR-17). An HTML comment and any other raw HTML in the file are preserved on exactly those terms — never rendered as markup, never interpreted, and never deleted.
41. **EDT-FR-69** Serialisation is **stable**: a buffer the WYSIWYG surface has already serialised serialises again to itself. Saving an artifact twice with no edit between the two saves writes identical bytes, and opening a file the Editor itself last wrote, editing it, and saving changes only what that edit changed. Canonical spelling therefore settles once and converges, rather than drifting a file a little further on every visit.
42. **EDT-FR-70** An artifact **writes itself**. An edit made on any of its surfaces (EDT-FR-22) schedules a write through `"save artifact contents"` a short rest after the last keystroke, so a burst of typing is one write rather than one per character, and no edit is lost to a save the author never thought to trigger. A further edit made before the rest elapses restarts it, so the write carries the settled text rather than an intermediate one. The write happens immediately, without waiting the rest out, when the tab closes (EDT-FR-31), when the project closes, the application quits, the active project changes or the project's active worktree changes (EDT-FR-33), and when the File menu's Save or Save All is activated (EDT-FR-34, EDT-FR-35). Activating another tab schedules nothing extra and cancels nothing: a pending write lands on its own while the tab sits in the background (EDT-FR-30). A scheduled write is **held** for as long as the tab's external-change modal is unresolved (per `EXC-editor-external-change.md` EXC-FR-VTUH, EXC-FR-VNLZ) — neither performed nor dropped while the author has yet to answer it — and what becomes of it follows the answer: "Keep my version" performs it at once (per `EXC-editor-external-change.md` EXC-FR-NMXQ), and "Load from filesystem" discards it along with the buffer it would have carried (per `EXC-editor-external-change.md` EXC-FR-WDAV). A scheduled write is **cancelled outright** while the session is quiesced (EDT-FR-81), because the buffer it would carry is one the author has asked to discard.
43. **EDT-FR-71** A write that fails leaves the buffer, the editing mode, the undo history, and the indicator of EDT-FR-04 exactly as they were, and attaches the typed error to every tab bound to that artifact, so the edit is still held in memory and still reversible and the failure is visible wherever the author is. The Editor does not retry on a timer: the next edit schedules the next write, and Save (EDT-FR-34) retries on demand. The error clears on the next successful write. A tab whose artifact's last write failed refuses to close until one succeeds (EDT-FR-32), so a failure is answered before the buffer holding it can be put out of sight.
44. **EDT-FR-72** An artifact's editing session is not the Editor tab's alone. The **editable target of a Diff tab** on that file is a surface of this same session (per `DFV-diff-viewer.md` DFV-FR-42) — the same buffer, the same dirty state, the same single undo/redo history, the same indentation convention, the same baseline checksum, and the same scheduled write — rather than a second session of the same bytes. Every requirement of this spec that governs an artifact's buffer, its writes and the schedule they run on, its undo history, its serialisation fidelity, and its external-change resolution therefore governs it there too, and the requirements that name a tab bind whichever kind of tab the author is in. Two consequences are worth stating outright, because they are what the arrangement is for: an edit made in either surface is immediately what the other shows, with one dirty state and one write between them; and closing either tab ends that tab and not the session (EDT-FR-28), so a correction made in a diff survives being reopened in the Editor and the other way round. What the Diff tab adds is its own and is defined there: which of its rendered content is target and which is original, and the comparison it derives around the buffer.
45. **EDT-FR-81** An artifact's editing session can be **quiesced**: put into a state in which it neither schedules nor starts a write, by a surface that is about to replace the file's whole contents on the author's instruction — the Changes panel's rollback (per `CHG-changes.md` CHG-FR-60), and the acceptance of a change an agent proposed to a prompt artifact (per `PCR-prompt-change-review.md` PCR-FR-11). Quiescing cancels the artifact's scheduled write (EDT-FR-70) rather than performing it, holds back the write a further edit would schedule, and refuses to start a new `"save artifact contents"` for that artifact by **any** route: the schedule, the File menu's Save and Save All (EDT-FR-34, EDT-FR-35), and a close-time flush (EDT-FR-31) alike. A write already **in flight** is neither cancelled nor abandoned but **awaited to settle**, because a write the filesystem has already begun cannot be recalled and a rollback that raced it would be rolling back a file mid-write. One artifact is awaited **once** however many Editor and Diff tabs are open on it, the several surfaces sharing one session and one write (EDT-FR-72). A write that settles successfully completes normally and its returned `checksum` becomes the baseline (per `EXC-editor-external-change.md` EXC-FR-HKKG); one that fails does not hold the quiesce open, is retried by neither a timer nor the quiesce itself (EDT-FR-71), and is reported to the surface that asked for the quiesce as its typed error together with the artifact it belongs to.
46. **EDT-FR-84** The Editor tab is where a change an agent has proposed to a **prompt artifact** is reviewed. The tab lends its own bounds to the review modal of `PCR-prompt-change-review.md` (PCR-FR-01) and its action cluster (EDT-FR-16) to that surface's pending indication (PCR-FR-16), and it introduces no backend operation for either: the modal, the comparison it renders, the candidate it edits, the two decisions, and every operation behind them belong to that spec and to `../core/PCP-prompt-change-proposals.md`. What this spec owns is the hosting alone — that the modal is anchored within this tab rather than in the window, that it dismisses none of the tab's other transient surfaces and is dismissed by none of them, and that the indication sits in the cluster beside the comments control rather than in a chrome of its own. The candidate the author edits in that modal is **not** this artifact's editing session (per `PCR-prompt-change-review.md` PCR-FR-20): it holds its own buffer and its own undo history, so no keystroke in the review reaches the buffer of EDT-FR-28, its dirty state, or its write schedule, and one undo issued in the tab and one issued in the review reverse two different edits. What does reach the session is the acceptance, on the terms of EDT-FR-81 and of `EXC-editor-external-change.md` EXC-FR-JAWT, together with three things this spec states here because they are exceptions to rules stated elsewhere in it. The acceptance **passes through the external-change machinery**: an `"artifact changed externally"` event for that artifact raises no modal for as long as a review of it is showing (per `PCR-prompt-change-review.md` PCR-FR-24), and a modal already standing is dismissed with neither of its resolutions taken when **Accept** is activated (per `EXC-editor-external-change.md` EXC-FR-AEQZ, EXC-FR-JAWT). The acceptance **does not consult the baseline checksum** of `EXC-editor-external-change.md` EXC-FR-WCOM, so no divergence between the session's baseline and the file on disk can refuse it; the checksum the acceptance returns becomes the new baseline on success. And an acceptance that **fails** changes none of it: the session is left exactly as it stood with its baseline unmoved and its buffer intact, the quiesce is lifted, and an external change that was passed over on the way in is raised as an ordinary modal once it is, the replacement it was passed over for not having happened.
47. **EDT-FR-85** An image's **destination is resolved by the tab that hosts the surface**, not by the surface itself. The surface reads the destination the Markdown carries — from an inline image or from the definition a reference-style image resolves to — and asks its host for content to draw; an Editor tab on a project file resolves it against that file, and a New Artifact tab resolves it against the draft (per `NAW-new-artifact.md` NAW-FR-52). A destination the host does not resolve renders as a **labelled placeholder** carrying an accessible name that states the image could not be loaded and names the destination, never as an empty frame and never as nothing at all, and the Markdown behind it is **preserved exactly**, so the author sees which reference is broken and can repair it on either surface. A destination still being resolved renders as a pending placeholder on the same terms. Resolution never blocks editing: typing, selection, and the write schedule of EDT-FR-70 all proceed while an image is pending or unresolved.
48. **EDT-FR-86** Image data **pasted or dropped onto either surface is offered to the host first**. Where the host takes it, the host decides what is written and where, and the surface applies that as one ordinary edit at the cursor — one undo step, one selection change, one entry in the write schedule of EDT-FR-70 — so the insertion behaves exactly as typed text does. Where the host does not take it, the paste or drop falls back to what it does today: the text flavour of the clipboard is inserted, and image data with no text flavour inserts nothing. An Editor tab on a project file takes none, so pasting a picture into a project file is unchanged; a New Artifact tab takes it (per `NAW-new-artifact.md` NAW-FR-50).
49. **EDT-FR-FDGH** In the WYSIWYG surface, the surface itself acts on a key press that types a backtick, on any layout and with any modifier, so the platform adds no character of its own. EDT-FR-VCOH to EDT-FR-FKJP set what the press does. Dead keys, input methods, ⌘ or ⌃ shortcuts, and node or cell selections keep the platform's handling.
    - *Why:* the macOS webview can insert a second backtick for one press, and then the code-fence rule never matches.
50. **EDT-FR-VCOH** A backtick in plain text, with an empty selection and no backtick directly before the cursor, opens an inline-code span at the cursor, unless EDT-FR-FKJP closes a literal one. It inserts no character, and the text typed next is inline code. Directly after inline code, the span joins that code. Moving the cursor away from an empty span drops it.
51. **EDT-FR-LLBU** An inline-code span is open while text typed at the cursor joins it. While it is open, a virtual closing backtick shows at the span's end. The virtual backtick is not content: the buffer does not hold it, a save does not write it, and the author cannot select or edit it.
52. **EDT-FR-CCBX** A backtick at the end of an open span, or the forward arrow key (→ in left-to-right text, ← in right-to-left text), closes the span. The cursor does not move, no character is inserted, and the text typed next is plain.
53. **EDT-FR-APAL** A backtick with a non-empty selection inside one textblock makes the selected text inline code, and the span stays open with the cursor at its end. A selection that spans textblocks is deleted first, and the backtick then acts as on an empty selection.
54. **EDT-FR-XTGK** A backtick in an empty open span drops the span and inserts two literal backticks. A backtick directly after a literal backtick is literal. So ```` ``` ```` or ```` ```lang ```` at the start of a paragraph, then Space or Enter, opens a fenced code block with that language.
55. **EDT-FR-EKEZ** A character other than a backtick, typed between exactly one literal backtick on each side, becomes inline code. The two literal backticks are removed, and the span stays open.
56. **EDT-FR-FKJP** A backtick in a fenced code block, or inside an inline-code span before its end, is literal text. A backtick typed after plain text that follows a literal opening backtick turns that text into inline code and removes the opening backtick.

## Non-functional requirements
- Editing remains responsive on documents up to several thousand lines of Markdown.
- The external-change modal must not lose unsaved work: raising it, and either resolution, operates only on the in-memory buffer and the on-disk file — no implicit third state.
- Retained edit state, undo histories included, is in-memory only: no part of it is persisted, and it does not outlive the running application.
- Undo depth is bounded only by the length of the editing session; no fixed step limit silently truncates the history during normal authoring.
- Retained-state memory grows with the number of artifacts edited in the open project and the length of their histories; artifacts that are only opened and read add nothing to it.
- Indentation detection runs once over the body when an artifact loads, not per keystroke, so it adds nothing to editing latency on a large document.
- Recomputing the match set on a document of several thousand lines keeps pace with typing, both in the query input and in the editing surface, so neither shows perceptible input lag while a panel is open.
- The frontmatter parse covers the leading block alone rather than the whole document and re-runs only when that block changes, so it keeps pace with typing inside the region and adds nothing to editing latency in the body.
- The description character count is derived from that same parse rather than from a second pass over the source, so reporting it costs nothing beyond it.
- Find-panel state adds a small, bounded amount to an artifact's retained edit state — a query, a replacement string, a mode, and an open/closed form — and, like the rest of that state, no part of it is persisted.
- Showing and hiding the comments reflows nothing in the editing surface and moves neither the caret nor the scroll position, so a glance at a thread does not cost the author their place.
- Round-trip fidelity (EDT-FR-67, EDT-FR-69) is a property the project's own Markdown corpus is the measure of: every file under `specifications/`, `resources/`, and the project's instruction files survives a parse and a serialisation semantically unchanged, and a second pass over the result changes nothing further.
- Holding a file's loaded bytes alongside its rendered document until the first edit (EDT-FR-66) costs one additional copy of the file's text per open artifact, which is bounded by the same document sizes editing is already responsive on.
- The rest that precedes a write (EDT-FR-70) is short enough that an author who stops typing and looks away considers the file saved, and long enough that ordinary prose typing produces one write per pause rather than a stream of them. Serialising the buffer and invoking the write happen off the typing path, so neither shows as input lag on a document of several thousand lines.
- Resolving a source file's language costs a lookup on its filename; the text is weighed only where the map has no answer for it, so the common case adds nothing measurable to opening a file.
- The registered grammar set is the library's common languages plus Dart and Scala rather than its whole catalogue, so the bundle carries what the map of `ESH-editor-source-files.md` ESH-FR-PBFJ names and the autodetection pass has a bounded set to weigh rather than the full one.
- Tokenising runs off the typing path: a source file of several thousand lines keeps pace with typing, and where it cannot, plain text is what stands until it can (per `ESH-editor-source-files.md` ESH-FR-MJRH).
- The token layer costs one additional rendered copy of the file's text, on the same order as the loaded-bytes copy of EDT-FR-66 and bounded by the same document sizes editing is already responsive on.
- Writes arrive at editing cadence rather than at the cadence of a user deciding to save, so every consumer downstream of `"save artifact contents"` — the checksum computation, the external-change event, and the recently-edited list it feeds (per `../core/PST-project-storage.md` PST-FR-17) — absorbs many writes per authoring session for a single artifact.
