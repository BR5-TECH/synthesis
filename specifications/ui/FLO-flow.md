# Flow

**Spec code:** `FLO`

## Intent
Flow is the visual graph editor for the project's `flow` artifacts: a main-viewport tab in which the author wires prompts and the artifacts that hold them into a workflow. A Flow answers "what runs, in what order, and what feeds what" — a graph of AI agent execution, or equivalently a graph of prompts that can later be fused into a single instruction for one agent. It exists because assembling that structure by hand in prose loses the shape of the thing: the branches, the fan-in, the retry that goes back a step. Not every part of a workflow is a fixed order, either, which is what a **loop** is for: a bounded region of the canvas whose steps are candidates rather than a sequence, each one deciding which of its neighbours runs next until the loop is done and the workflow moves on. A loop is built out of the project's artifacts on exactly the terms a node is, which is where an author says what ends it: the prompt a loop references is the instruction the loop is run under. Building all of it out of artifacts already in the project keeps the workflow and the prompts it is made of in one place, so editing a prompt does not leave a copy of it stale inside a workflow description. A graph the author has drawn is a graph that is already on disk: the canvas writes itself a short rest after the last change, on the same terms an artifact does in `EDT-editor.md`, so a workflow assembled over an afternoon of dragging never depends on the author remembering to keep it (FLO-FR-27). Out of scope: fusing a Flow into a single prompt and executing a Flow as an agent workflow — this surface authors and persists the graph and does not run it, evaluate it, or compile it; spec-to-scenario coverage, which this canvas does not render; editing state that outlives a Flow tab, since a Flow has no counterpart to the session-lived retained edit state and undo history an artifact carries in `EDT-editor.md`; and comments pinned to a node, an edge, or an inline prompt, this canvas anchoring no conversation to anything inside the graph (FLO-FR-36) — a Flow is discussed as the whole workflow it is, through the action control every tab carries (`ACT-action-control.md`).

## User stories
- As a prompt author, I want to connect a set of prompts and their outputs into a graph so that I can see how a multi-step agent workflow hangs together before I commit to running it.
- As an author, I want a node to point at an artifact that already exists in the project so that the workflow references the prompt I maintain rather than a copy of it.
- As an author, I want to draw an edge that goes back to an earlier node so that a retry or a loop is expressible as the graph it actually is.
- As an author, I want to name my edges so that a branch reads as "on failure" or "needs review" rather than as an unlabelled arrow.
- As an author, I want to gather the steps of an agentic loop inside a container so that the part of the workflow where an agent chooses its own next step is visibly bounded, and the rest of the graph connects to the loop as one thing rather than to its insides.
- As an author, I want a node's prompt to read as the formatted text it is when I am not editing it so that a canvas of steps reads as prose rather than as Markdown source.
- As an author, I want to see at a glance which way a connection runs so that a graph with a retry in it reads as the loop it is, without my having to select an edge or remember which node I dragged from.

- Layout notes: the tab is a single band holding the Flow's **name** and **description** (FLO-FR-25) above a canvas that takes the rest; the band carries no actions at all, and the tab label carries the dirty indicator (`●`) described in FLO-FR-26. Every action lives on the canvas it acts on: **add** is a transparent `+` in the canvas's top-right corner that expands into a short menu of what can be added — **Node** and **Loop** (FLO-FR-07), each a named entry carrying its own glyph, drawn in the same treatment as the action control's menu (`ACT-action-control.md` ACT-FR-05) so the tab's two menus read as one kind of surface rather than two — and the view controls, zoom out, the zoom level, zoom in, and **fit**, sit as icons in the opposite corner, bottom-right, beside the element readout, with the action control and the discussions control beside them on that same line, leading of the view controls (FLO-FR-34). The floating discussion panel opens at the tab's trailing side, over the canvas and bounded to a share of it, laid on the graph rather than taking a column from it (FLO-FR-35). Each is a glyph rather than a caption and carries its name as its accessible name and in its tooltip.
- A node renders three stacked regions, any of which may be absent: its **name** on top, one row per **artifact reference** beneath (display name preceded by the artifact-type chip of `LIB-library.md`, with a click-through affordance `↗`, and — while the node is selected — a remove affordance of its own), and its **inline prompt** below a divider. The prompt renders as rich text from Markdown while the node is not selected and as its Markdown source in an editable field while it is (FLO-FR-13), which is the same selected-or-not distinction that shows and hides the artifact picker and the per-reference remove affordances; the node is as tall as the region needs. A node carrying no artifact reference and no inline prompt renders name-only; an unresolved reference (FLO-FR-11) replaces the chip-and-name row with a warning row naming the stored id, elided to fit. A selected node also renders the artifact picker, which adds to the node's references rather than replacing them. A node reads as a light surface carrying the canvas's own texture rather than as an opaque slab set on it: the graph is the figure and a node is part of it, so a canvas of many nodes reads as one drawing rather than as a scatter of cards.
- A **loop** renders as a container drawn around what it holds (FLO-FR-38): a header carrying its name and its pass bound where it has one, its artifact references beneath on exactly the terms a node's render (FLO-FR-11), over a region holding its member nodes and nested loops. It is resized from its own edges and corners, and its border is its connection anchor exactly as a node's is — the graph reaches it as one element and never reaches past it (FLO-FR-39, FLO-FR-40). Its name and pass bound are short single-line text edited in place and rendered as the plain text they are, the rich-text treatment being the node prompt's alone. Its header and its reference rows are drawn above whatever the loop holds: a member the author placed under them covers neither, and every affordance the container carries stays reachable however its members are arranged.
- Edges are directed and say so: each carries an **arrowhead at the end where it arrives** (FLO-FR-48), scaled to the edge rather than to the elements it joins — small enough that a dense graph does not read as a field of triangles, large enough to be read at the zoom an author works at. A label sits at the midpoint, and an unlabelled edge is the bare stroke and its head. A connection being drawn renders as a provisional edge from its source to the pointer (FLO-FR-32), carrying that same head at its free end, drawn dashed until it snaps to an element (FLO-FR-33), at which point it lands on that element's anchor and the element is highlighted. Nothing about the graph's shape is imposed by the layout — an element has no fixed input or output side, and edges route between whichever sides are nearest, which is what lets a back-edge such as `"retry"` read as a return rather than as a mistake: its head arriving at the earlier step is what says so.

## UI contract boundary
- **Owned by the UI**: canvas rendering (nodes, loops, edges, labels, pan, zoom, selection); element and edge creation, removal, renaming, placement, and resizing; the artifact-association picker, what it offers (FLO-FR-10), and the rendering of resolved and unresolved references; inline prompt editing and the rendering of a prompt as rich text (FLO-FR-13); the in-flight rendering of a connection and the element it snaps to (FLO-FR-32, FLO-FR-33); which container a dragged element lands in and what that costs its edges (FLO-FR-42, FLO-FR-43); the immediate, local enforcement of every graph rule while the author draws (FLO-FR-16, FLO-FR-17, FLO-FR-18, FLO-FR-40, FLO-FR-41) and the feedback a refused connection produces; the Flow tab's unsaved-changes state and its dirty indicator (FLO-FR-26); and the serialization and deserialization of the Flow document.

  The document's **shape** is not owned here: it is defined and validated by `../core/FGV-flow-graph-validation.md` (FGV-FR-01), which is also the authority on whether a given document is a Flow at all. This surface serializes to that schema and deserializes from it, and treats the report a validation returns as the truth about a document it did not itself build (FLO-FR-46, FLO-FR-47). A Flow's `name` is always written, empty or not (FLO-FR-25).

- **Delegated to backend (abstract)**:
  - `"load artifact contents by id"` — serves the Flow file's body for deserialization (owned by `../core/PST-project-storage.md` PST-FR-15).
  - `"validate flow document"` — judges a body against the Flow schema and the graph's structural rules, returning the violations it carries (owned by `../core/FGV-flow-graph-validation.md` FGV-FR-02). The canvas invokes it on the body a load returns, before rendering anything (FLO-FR-46).
  - `"save artifact contents"` — writes the serialized document back (owned by `../core/PST-project-storage.md` PST-FR-09). A `flow`-typed artifact is validated inside that write and a document carrying violations is refused rather than written (per `../core/PST-project-storage.md` PST-FR-28), so no path through this surface — Save, Save All, or a flush on close — can put an invalid Flow on disk.
  - `"load project tree (filesystem nodes tagged by artifact type)"` — populates the artifact-association picker and resolves a node's stored artifact references to display names and artifact types, including the name a skill declares for itself (`../core/ASC-artifact-scanning.md` ASC-FR-19). Owned by `../core/PST-project-storage.md` PST-FR-07. The canvas reads no artifact's contents to render a reference: a Flow tab opening in a project of many skills must not read them all.
  - `"open artifact by id"` — routes a node's click-through to the referenced artifact's natural surface (owned by `../core/PST-project-storage.md` PST-FR-08).

  The action control the tab carries (FLO-FR-34), the composer it opens, and the floating discussion panel (FLO-FR-35) are owned by `ACT-action-control.md`, which declares the operations behind them; this surface introduces none for them and reads nothing of a discussion itself.

  Flow defines no backend operation of its own: a Flow is an artifact file like any other, so the writes the canvas schedules for itself (FLO-FR-27), the Save and Save All items of `SNV-shell-navigation.md` (SNV-FR-29, SNV-FR-31), and the flushes on tab, project, and application close all drive the same `"save artifact contents"` an Editor tab drives, and the validation those writes pass through belongs to `../core/FGV-flow-graph-validation.md`. The rest-after-editing schedule that decides *when* a Flow is written is this surface's own and changes no operation's shape, only how often one is invoked.

## Functional requirements
1. **FLO-FR-01** Flow is a tab in the main viewport, opened when a file whose resolved artifact type is `flow` is selected from the Project panel, Search, or a Dashboard widget (per `LIB-library.md` LIB-FR-03).
2. **FLO-FR-02** Each Flow opens in its own tab and multiple Flows coexist as separate tabs; a request to open a Flow that already has a tab jumps focus to it rather than opening a second one (per `TAB-tabs.md` TAB-FR-04 and TAB-FR-05).
3. **FLO-FR-03** A Flow is a single JSON document conforming to the schema `../core/FGV-flow-graph-validation.md` defines (FGV-FR-01). Opening the tab deserializes the file's body into the Flow, and saving serializes it back. The document is the whole of a Flow's persisted state: its name and description, its nodes, its loops, its edges, which container each element sits in, and each element's position and — for a loop — its size.
4. **FLO-FR-04** A file body that is empty or contains only whitespace deserializes to an empty graph, so a Flow created through the New Artifact window (per `NTA-new-typed-artifact.md` NTA-FR-11), through New File, or by an external `touch` opens ready to edit rather than in an error state (per `../core/FGV-flow-graph-validation.md` FGV-FR-05).
5. **FLO-FR-05** A body the validation of FLO-FR-46 reports as invalid puts the tab in an error state listing the violations it returned, each naming the element or edge it sits on where it has one. The canvas renders no graph and offers no editing, and the tab performs no write while in that state, so a file the editor cannot read is never replaced by an empty graph.
6. **FLO-FR-06** Nodes and loops are both **elements**, and every element carries an id that is unique among all of them within the document and stable across saves, a name, and a position. Every element carries any number of references to project artifacts, including none (FLO-FR-10). A node additionally carries an optional inline prompt body; a loop additionally carries what FLO-FR-37 gives it. Every element also carries which container holds it (FLO-FR-42).
7. **FLO-FR-07** Adding to the graph is a single affordance on the canvas that expands into a menu of what can be added — **Node** and **Loop** — each placing a new, unconnected element of that kind. A node arrives with a default name, no artifact references, and no inline prompt; a loop arrives with a default name, no artifact references, no pass bound, a default size, and nothing inside it. The affordance sits on the canvas itself rather than in the tab's band, so the band stays the Flow's own fields (FLO-FR-25) and the action sits on the surface it adds to. Its entries are named and carry a glyph apiece, in the treatment the action control's own menu uses (per `ACT-action-control.md` ACT-FR-05): the two menus a Flow tab can open are one kind of surface, and an author who has met either has met both. Its menu is one of the tab's transient surfaces: opening it dismisses whichever of them was open and it is dismissed by any of them opening, by Escape, by a pointer-down elsewhere in the tab, and by choosing one of its entries (per `ACT-action-control.md` ACT-FR-12). Like them it is anchored within the tab rather than being a floating overlay of the main window, so opening it closes none of the window's mutually-exclusive overlays and none of them closes it (per `ACT-action-control.md` ACT-FR-11 and `SNV-shell-navigation.md` SNV-FR-56).
8. **FLO-FR-08** Removing a node removes it together with every edge for which it is the source or the target; no edge survives without both of its endpoints.
9. **FLO-FR-09** A node is renamed in place on the canvas. A name is free text and is not required to be unique — a node's identity is its id (FLO-FR-06), never its name.
10. **FLO-FR-10** An element — a node or a loop alike — references any number of the project's artifacts. References are added through a picker populated from `"load project tree (filesystem nodes tagged by artifact type)"`, which stores the chosen artifact's stable id and offers only artifacts a workflow step is made of — those whose resolved artifact type is `skill`, `prompt`, or `instructions`, and of the files classified `skill` only a skill's own `SKILL.md`, never the supporting files that live beside it in the skill's folder. The picker adds to an element's references rather than replacing them, and does not offer an artifact the element already references. Each reference is removed individually from the element, leaving its other references in place. The picker and the per-reference remove affordances appear while the element is selected, on the same terms for a loop as for a node (FLO-FR-13).
11. **FLO-FR-11** A stored reference that resolves against the project tree renders on the element as the artifact's display name with its artifact-type chip. The display name is the one the project tree carries for the artifact (`../core/ASC-artifact-scanning.md` ASC-FR-19), falling back to its filename: that is the filename for every artifact whose file identifies it, and the declared name for a skill, whose file is always `SKILL.md`. A reference that does not resolve — the artifact was deleted, moved, or renamed — renders as an unresolved reference naming the stored id. The element, its other references, and its edges are untouched, and nothing in the graph is removed on the user's behalf; the user resolves it by removing that reference (FLO-FR-10) or the element itself (FLO-FR-08, FLO-FR-45).
12. **FLO-FR-12** Activating one of an element's resolved artifact references opens that artifact in its natural surface — an Editor tab, or a Flow tab for a nested Flow (per `LIB-library.md` LIB-FR-03) — through `"open artifact by id"`, subject to the single-tab focus-jump rule of `TAB-tabs.md` TAB-FR-07. An unresolved reference (FLO-FR-11) opens nothing.
13. **FLO-FR-13** A node's inline prompt is **Markdown**, and which of its two faces the node shows is decided by whether the node is selected — the same distinction that shows and hides the artifact picker and the per-reference remove affordances (FLO-FR-10). A node that is not selected renders the prompt as rich text: emphasis, inline code, links, and short lists read as themselves rather than as their source characters, on the same terms a comment's body renders (per `CMT-comments.md` CMT-FR-09). A selected node presents that same prompt as its Markdown source in an editable field, so what the author types is exactly what is stored and nothing rewrites it on the way in or out. The field is a plain one: it carries no formatting toolbar and no embedded Editor, and therefore no Find or Find & Replace — ⌘F and ⌘R do nothing while a Flow tab has focus (per `SNV-shell-navigation.md` SNV-FR-43).
14. **FLO-FR-14** A node may carry artifact references, an inline prompt, both, or neither; neither field is required for the node to be valid or connectable.
15. **FLO-FR-15** An edge is directed, running from a source element to a target element, either of which may be a node or a loop (FLO-FR-39). Any number of edges may leave an element and any number may arrive at it, so fan-out and fan-in are both unconstrained, subject to the rule of FLO-FR-40 about which elements may be joined at all.
16. **FLO-FR-16** A connection whose source and target are the same element is refused: no edge is created and the canvas gives immediate feedback that the connection was rejected.
17. **FLO-FR-17** An ordered pair of elements carries at most one edge. Connecting A to B when an A→B edge already exists creates no second edge and leaves the existing one unchanged. B→A is a different ordered pair and is a separate, permitted edge.
18. **FLO-FR-18** The graph is not constrained to be acyclic. A path that returns to an earlier node is valid — it is how a loop or a retry is expressed — and no connection is ever refused on the grounds that it would form a cycle.
19. **FLO-FR-19** An edge carries an optional label, renamed in place on the canvas and rendered along the edge. Labels are free text and are not required to be unique or present.
20. **FLO-FR-20** Removing an edge removes only that edge; both endpoint nodes remain in the graph with their other edges intact.
21. **FLO-FR-21** Dragging an element changes its position, and that position is part of the document (FLO-FR-03), so a Flow reopens with its layout as the author left it. A position is measured from the origin of whatever holds the element — the canvas for a top-level element, the container for one inside a loop — so moving a loop moves everything in it and changes one element's position rather than every member's.
22. **FLO-FR-22** Pan, zoom, and selection are view state rather than document state: they are not serialized, not persisted, and a reopened Flow presents a default view of the saved layout. Their controls — zoom out, the zoom level, zoom in, and fit-to-content — sit on the canvas, apart from the Flow's own fields, because none of them changes anything the document holds. A press on one of them is a press on a control and not on the canvas behind it: it neither pans the view nor clears the current selection.
23. **FLO-FR-23** A Flow is variable-size; the UI imposes no cap on element or edge count, on how many elements one loop holds, or on how deeply loops nest.
24. **FLO-FR-24** The Project panel does not contain a dedicated "Flows" section; Flows appear under their natural parent in the Project panel's tree (per `LIB-library.md` LIB-FR-07).
25. **FLO-FR-25** A Flow carries a name and an optional description, both part of the document (FLO-FR-03) and both edited in place at the top of the tab. They describe the Flow as a thing to be run rather than as a file, which is why they are the Flow's own fields and not its filename. The name is required: the editor marks its absence, and a name of only whitespace counts as absent. That marking is the whole of the enforcement — an unnamed Flow still saves, still closes, and still writes on every path FLO-FR-27 to FLO-FR-29 describe, because refusing to write a Flow until it is named would cost the author the graph they just drew. The description is optional and is absent from the document when empty.
26. **FLO-FR-26** A Flow holds unsaved changes from the moment the user's first edit is applied — adding, removing, renaming, moving, or resizing an element, moving one into or out of a loop, adding or removing one of an element's artifact references, editing a node's inline prompt, editing a loop's pass bound, or adding, removing, or renaming an edge — until it is next written. An action that leaves the graph exactly as it was is not an edit and raises nothing; neither is selecting an element, which only decides which face its prompt shows (FLO-FR-13). The Flow tab exposes a dirty-state indicator while unsaved changes exist and clears it on a successful write.
27. **FLO-FR-27** A Flow **writes itself**. An edit (FLO-FR-26) schedules a write a short rest after the last one, at which point the canvas serializes the current graph and writes it through `"save artifact contents"`; a further edit made before the rest elapses restarts it, so a drag is one write on release rather than one per frame. The write happens immediately, without waiting the rest out, when the tab closes (FLO-FR-28), when the project closes, the application quits, the active project changes or the project's active worktree changes (FLO-FR-29), and when the File menu's Save or Save All is activated while that tab is active (per `SNV-shell-navigation.md` SNV-FR-28, SNV-FR-29, SNV-FR-31). Activating another tab schedules nothing extra and cancels nothing: a pending write lands while the tab sits in the background (FLO-FR-30). The tab's band carries no Save control, writing being something the author reads about rather than something they do. Every write validates the document and refuses one carrying violations (FLO-FR-47).
28. **FLO-FR-28** Closing a Flow tab that holds unsaved changes brings its pending write forward rather than waiting out the rest of FLO-FR-27, writing through `"save artifact contents"` before the tab closes (per `TAB-tabs.md` TAB-FR-12); closing a Flow tab whose graph has already reached disk writes nothing. Nothing survives the close: reopening the Flow deserializes the on-disk document afresh.
29. **FLO-FR-29** Closing the open project, quitting the application, switching the active project, and changing the project's active worktree write every Flow holding unsaved changes before any tab is torn down (per `SNV-shell-navigation.md` SNV-FR-25 and SNV-FR-26 and `OVW-overview.md` OVW-FR-11 and OVW-FR-12), the same set of writes Save All performs (SNV-FR-31). A write that fails cancels the transition, leaving the project open on its current worktree with the error visible.
30. **FLO-FR-30** Activating another tab does not discard a Flow's unsaved changes. A Flow tab that is not the active tab keeps its graph and its dirty indicator, and making it active again performs no reload (per `TAB-tabs.md` TAB-FR-09).
31. **FLO-FR-31** A Flow tab holding no unsaved changes reloads its graph when its file is reported changed externally (per `../core/PST-project-storage.md` PST-FR-16). A Flow tab holding unsaved changes keeps them and stays on its in-memory graph, and its next write replaces the file's contents.
32. **FLO-FR-32** A connection being drawn is visible while it is being drawn: from the moment the drag begins, the canvas renders a provisional edge running from the source element to the pointer, carrying the direction marker of FLO-FR-48 at its free end so the author sees which way the edge would run before releasing, and otherwise distinguished from the graph's own edges so it does not read as an edge that already exists. It is a preview only — no edge is in the document until the connection completes (FLO-FR-15), and abandoning the drag leaves the graph untouched.
33. **FLO-FR-33** While a connection is being drawn, the nearest element within a snap distance of the pointer that the connection could land on is highlighted, and the provisional edge snaps to it, its marker settling onto that element's anchor exactly where a completed edge's would sit, so the author sees the edge they would get before releasing. Releasing completes the connection onto the highlighted element without having to land on it; releasing with nothing highlighted and nothing under the pointer abandons the drag, which is not a refusal and produces no feedback. A drag whose release the canvas never sees — the pointer left the window, or the system took it away — is abandoned on the same terms: a connection is created only by a release the canvas actually observed, so no edge appears that the author did not let go of. An element the connection cannot land on is never highlighted — the source element itself (FLO-FR-16), one already connected in that direction (FLO-FR-17), and one in a different container (FLO-FR-40) — but releasing directly on one still connects to it, and is refused with the feedback those requirements describe.
34. **FLO-FR-34** The Flow tab carries the **action control** of `ACT-action-control.md` (ACT-FR-01), bound to the Flow file the tab is open on (ACT-FR-02) and offering **Discuss** (ACT-FR-04) — a workflow being exactly the kind of thing an author wants to ask about as a whole, its shape rather than any line of its JSON being what is under discussion. It floats over the canvas in the tab's bottom-trailing corner, leading of the view controls (FLO-FR-22), which keep the trailing end of that line (ACT-FR-10); it covers none of them and takes no activation meant for one. A press on it is a press on a control and not on the canvas behind it: it neither pans the view nor clears the current selection, on exactly the terms FLO-FR-22 sets for the view controls. It holds that corner while the canvas is panned and zoomed (ACT-FR-08).
35. **FLO-FR-35** The Flow's discussions are read in the **floating discussion panel** (per `ACT-action-control.md` ACT-FR-20), a Flow tab lending the comment rail no margin to pin them in, shown and hidden by the discussions control beside the action control. Each discussion renders there as the shared discussion surface, the same one every owner surface renders (per `ACT-action-control.md` ACT-FR-RWHV), and the panel stays bounded and anchored at the tab's trailing side. Neither the panel nor the composer is part of the canvas: opening either lays a surface over the graph without re-laying it, moves no node, changes no edge, and adds nothing to the document (FLO-FR-03), so a Flow discussed is a Flow unchanged and its dirty state is what its edits left it (FLO-FR-26).
36. **FLO-FR-36** A discussion targets the Flow **file**, as a whole-target discussion of the artifact with no fragment (per `ACT-action-control.md` ACT-FR-LXKD), not a part of it. Nothing in this tab anchors a conversation to a node, a loop, an edge, or an inline prompt, and no affordance anywhere on the canvas opens one; the picker, the reference rows, the loop's own fields, and the connection drag are what an element offers and none of them is a comment. A remark about one step of a workflow, or about one loop of it, is made in a discussion about the Flow that names it.
37. **FLO-FR-37** A **loop** is an element that holds other elements. It carries a name, any number of artifact references on the terms FLO-FR-10 sets for every element, an optional **pass bound**, a position, and a size. It expresses the part of a workflow that is not a fixed order: its members are the candidate steps, each deciding from its own prompt which of its neighbours runs next, and the artifacts the loop itself references are the instruction the loop is run under — which is where an author writes what ends it, in the prompt that says so rather than in a field of its own. The pass bound is a whole number greater than zero capping how many times the loop may run before it gives up. Neither an artifact reference nor a pass bound is required, and a loop carrying neither is an ordinary loop whose author has not yet written down how it ends.
38. **FLO-FR-38** A loop renders as a container drawn around what it holds: a header carrying its name and its pass bound where it has one, its artifact references beneath as the rows of FLO-FR-11 with their type chips and click-throughs, over a region holding its members. Its name and its pass bound are edited in place as the short, single-line plain text they are — the rich-text rendering of FLO-FR-13 belongs to a node's prompt and to nothing else, a loop carrying no inline prompt of its own. A loop holding nothing renders as an empty container at its own size rather than collapsing away, an empty loop being a region the author is about to fill.
39. **FLO-FR-39** A loop is connectable as an element of whatever contains it: an edge runs from or to a loop exactly as it runs from or to a node, landing on the loop's own border. An edge arriving at a loop is the workflow entering it, and an edge leaving a loop is the workflow moving on once the loop is done. No edge reaches past that border to anything inside.
40. **FLO-FR-40** An edge is permitted only between two elements sharing the same container — both at the top level, or both immediate members of the same loop. A connection between elements in different containers is refused: no edge is created and the canvas gives immediate feedback, on the same terms as FLO-FR-16 and FLO-FR-17. This single rule is the whole of what a loop constrains; it is what keeps a loop's steps choosing among themselves, and it is why the graph reaches a loop through the loop rather than through its members.
41. **FLO-FR-41** A loop holds nodes and other loops alike, to any depth. A nested loop is an ordinary member of the loop containing it — connected to its siblings under FLO-FR-40 and to nothing outside — and the rule reads the same at every level. A loop is never placed inside itself, directly or through any chain of containers.
42. **FLO-FR-42** Which container holds an element is decided by where the author drops it: an element released within the bounds of a loop becomes a member of the innermost loop whose bounds contain it, and one released on open canvas becomes a top-level element. An element placed by the add affordance (FLO-FR-07) joins whatever container it lands in on the same terms. A drop is the only thing that changes membership.
43. **FLO-FR-43** Dragging an element out of the container it is in severs the edges that would then cross a boundary — every edge joining it to an element it is leaving behind. Where there is at least one such edge, the canvas asks before the move lands, naming how many connections it costs; confirming moves the element and removes those edges, and cancelling moves nothing and touches no edge. An element carrying no such edge moves with no question asked. A loop dragged out takes its whole contents and the edges among them with it, and only its own edges to its former siblings are severed.
44. **FLO-FR-44** A loop is resized from its own edges and corners, and resizing never changes what it holds: it cannot be made smaller than the bounds of its members, so no element is put outside its container by a gesture aimed at the container. Moving a loop moves everything in it (FLO-FR-21). Membership changes only by the drop of FLO-FR-42.
45. **FLO-FR-45** Removing a loop that holds nothing removes it and its edges outright, on the terms FLO-FR-08 sets for any element. Removing a loop that holds anything asks the author which they mean: **remove its contents with it**, taking every element and edge inside it, nested loops and all; or **release its contents**, keeping them and moving each into whatever contained the loop, where the edges among them stay valid because they stay siblings. Either way the loop's own edges go with it.
46. **FLO-FR-46** A Flow tab validates the body a load returns through `"validate flow document"` before it renders anything. A body reported valid is deserialized and rendered; one reported invalid puts the tab in the error state of FLO-FR-05. The canvas enforces FLO-FR-16, FLO-FR-17, and FLO-FR-40 itself, locally and immediately, as the author draws — so this validation is not what keeps a graph under the author's hands correct. It is what decides whether a document the author did not draw can be opened at all.
47. **FLO-FR-47** A write the validation inside `"save artifact contents"` refuses (per `../core/PST-project-storage.md` PST-FR-28) writes nothing: the tab surfaces every violation the report names, keeps its graph and its dirty state exactly as they were, and leaves the file on disk untouched. The canvas does not retry on a timer — the next edit schedules the next write (FLO-FR-27), so a graph the author is midway through repairing is not re-refused every few seconds — and the violations the tab lists are replaced by those of the next refusal or cleared by the next success. A refused write is a write that cannot proceed safely, so closing the tab, closing the project, switching the active worktree, and quitting are each cancelled by one on the terms FLO-FR-28 and FLO-FR-29 already set, and the author resolves it in the tab that is still open.
48. **FLO-FR-48** An edge renders its direction as an **arrowhead at its target end**, sitting where the edge lands on the target element's anchor — a node's border or a loop's (FLO-FR-15, FLO-FR-39) — and pointing along the edge's own direction at that point, so the head of a curved edge follows the curve rather than the straight line between the two elements. Every edge carries one whether or not it is labelled: a label says what a branch is and the head says which way it runs, and neither stands in for the other (FLO-FR-19). The marker is drawn as part of the edge and takes its appearance, the emphasis of a selected edge included, and it is a rendering of the direction the edge already has (FLO-FR-15) rather than anything the document carries a field of its own for (FLO-FR-03). It is what tells the two edges of a reciprocal pair apart: A→B and B→A join the same two elements over the same ground (FLO-FR-17) and are read apart by which end each one's head is on.

## Non-functional requirements
- Pan, zoom, selection, resizing, and connection dragging remain responsive on graphs of at least several hundred elements, whatever the nesting depth of the loops among them.
- Every graph rule is enforced client-side and answers immediately as the author draws: a refused self-connection (FLO-FR-16), duplicate connection (FLO-FR-17), or cross-container connection (FLO-FR-40) costs no backend round-trip. That the backend is the authority on whether a document is a Flow (FLO-FR-46, FLO-FR-47) does not make it a participant in drawing one — no connection, drop, or resize waits on a call.
- An edge's direction is carried by shape rather than by colour, motion, or state: the arrowhead of FLO-FR-48 reads the same to a viewer who distinguishes no colours and in a monochrome screenshot of the canvas, and it needs no hover, no selection, and no animation to be seen. It belongs to the edge, so it scales with the canvas and keeps its proportion to the stroke it terminates at every zoom level rather than detaching from the point the edge lands on; several hundred edges each carrying one stay within the responsiveness the canvas already holds to.
- A node's prompt renders as rich text at the pace the canvas is panned and zoomed: rendering Markdown is not something a Flow of several hundred nodes pays for on every frame, and a node whose prompt is long is a tall node rather than a slow one.
- Serialization round-trips: saving a Flow that was opened and not edited produces a document that deserializes to the same graph, and the serialized form is stable in key order and formatting, so a Flow is a plain, committed, diffable JSON file whose Git history shows only what the author actually changed.
- A Flow's unsaved changes are in-memory only: no part of them is written outside the file `"save artifact contents"` targets, and they do not outlive the Flow tab holding them.
