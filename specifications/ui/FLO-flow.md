# Flow

**Spec code:** `FLO`

## Intent
Flow is the project's **delivery plan**: a main-viewport tab in which an architect breaks a high-level design down into deliverables, milestones, epics, features, tasks, and defects, and draws which work blocks which. It answers "what are we delivering, in what order, how far along is each part, and what can run in parallel" on one canvas, from the HLD down to the drafts the tasks are worked in. It exists because a project or a program is planned by the architect and the agents together, and both need the same picture: the plan is a committed document the agent reads in every Flow discussion, each task is a draft the agent helps to write, and each item can be the same issue on GitHub that the rest of the team sees. A project holds any number of Flows. The canvas shows the state of each item, which items are blocked, and which tasks that could run in parallel touch the same files, so the architect can split or order them before the overlap costs a merge. Out of scope: starting, queueing, or gating a graduation run from the plan, a blocked task being shown and never enforced; agent proposals that edit the plan, the agent helping through the Flow's discussion; Jira, which the tracker boundary of `../core/FTS-flow-tracker-sync.md` leaves room for; and comments pinned to an item or an edge (FLO-FR-36).

## Functional requirements
1. **FLO-FR-01** Flow is a tab in the main viewport, opened when a file whose resolved artifact type is `flow` is selected from the Project panel, Search, or a Dashboard widget (per `LIB-library.md` LIB-FR-03).
2. **FLO-FR-02** Each Flow opens in its own tab and multiple Flows coexist as separate tabs; a request to open a Flow that already has a tab jumps focus to it rather than opening a second one (per `TAB-tabs.md` TAB-FR-04 and TAB-FR-05).
3. **FLO-FR-03** A Flow is a single JSON document that conforms to the schema of `../core/FGV-flow-graph-validation.md` (FGV-FR-01). Opening the tab deserializes the file's body, and a write serializes it back. The document is the whole of a Flow's persisted state: its name, description, references, items, edges, sync section, and each item's container, position, and size.
4. **FLO-FR-04** A file body that is empty or contains only whitespace deserializes to an empty plan, so a Flow created through the New Artifact window (per `NTA-new-typed-artifact.md` NTA-FR-11), through New File, or by an external `touch` opens ready to edit rather than in an error state (per `../core/FGV-flow-graph-validation.md` FGV-FR-05).
5. **FLO-FR-05** A body that the validation of FLO-FR-46 reports as invalid puts the tab in an error state that lists the violations, each naming its item or edge where it has one. The canvas renders no plan, offers no editing, and performs no write in that state. A version `1` document shows this state with its `unknown_version` violation.
6. **FLO-FR-06** Every element of the canvas is an **item**. An item carries an id that is unique in the document and stable across saves, a **kind**, a name, a position, any number of artifact references (FLO-FR-10), an optional Markdown description (FLO-FR-13), and its container (FLO-FR-42). The kind decides which other fields it carries (per `../core/FGV-flow-graph-validation.md` FGV-FR-MZIA).
7. **FLO-FR-07** One add affordance on the canvas expands into a menu of the six kinds — **Deliverable**, **Milestone**, **Epic**, **Feature**, **Task**, and **Defect** — each with its own glyph, in the treatment of the action control's menu (per `ACT-action-control.md` ACT-FR-05). It is a transient surface of the tab (per ACT-FR-12) and closes no floating overlay of the window.
8. **FLO-FR-08** Removing an item removes it together with every edge for which it is the source or the target; no edge survives without both of its endpoints.
9. **FLO-FR-09** An item is renamed in place on the canvas. A name is free text and is not required to be unique — an item's identity is its id (FLO-FR-06), never its name.
10. **FLO-FR-10** An item references any number of project artifacts through a picker populated from `"load project tree (filesystem nodes tagged by artifact type)"`. The picker offers every file whose artifact type is not `flow`, and of a skill's folder only its `SKILL.md`. It never offers an artifact the item already references, and each reference is removed on its own.
11. **FLO-FR-11** A stored reference that resolves against the project tree renders as the artifact's display name (per `../core/ASC-artifact-scanning.md` ASC-FR-19), falling back to its filename, with its artifact-type chip. A reference that does not resolve renders as an unresolved reference naming the stored id. Nothing in the plan is removed on the author's behalf.
12. **FLO-FR-12** Activating one of an item's resolved artifact references opens that artifact in its natural surface — an Editor tab, or a Flow tab for another Flow (per `LIB-library.md` LIB-FR-03) — through `"open artifact by id"`, subject to the single-tab focus-jump rule of `TAB-tabs.md` TAB-FR-07. An unresolved reference (FLO-FR-11) opens nothing.
13. **FLO-FR-13** An item's description is **Markdown**. An unselected item renders it as rich text on the terms of a comment body (per `CMT-comments.md` CMT-FR-09). A selected item shows its Markdown source in a plain editable field with no toolbar and no embedded Editor, so ⌘F and ⌘R do nothing while a Flow tab has focus (per `SNV-shell-navigation.md` SNV-FR-43).
14. **FLO-FR-14** An item needs no field beyond its kind and its name to be valid or connectable. References, a description, a draft, a footprint, and a due date are each optional.
15. **FLO-FR-15** An edge carries a **type**: `blocks` or `relates`. A `blocks` edge runs from the blocking item to the blocked item. A `relates` edge records that two items are connected and carries no order. An edge joins any two items, wherever their containers sit, subject to FLO-FR-16, FLO-FR-17, FLO-FR-ZEPI, and FLO-FR-GZCH.
16. **FLO-FR-16** A connection whose source and target are the same item is refused: no edge is created and the canvas gives immediate feedback that the connection was rejected.
17. **FLO-FR-17** Two items carry at most one edge between them, whatever its direction and type. A connection between two items that an edge already joins creates no second edge, leaves the existing one unchanged, and gives the feedback of FLO-FR-16.
18. **FLO-FR-CEVI** A completed connection creates a `blocks` edge from the item the drag started on. A selected edge offers its type as a two-way choice, **Blocks** and **Relates**, and a **Reverse** action on a `blocks` edge. A change of type or direction that FLO-FR-GZCH refuses leaves the edge as it was.
19. **FLO-FR-GZCH** A connection, a change of type, a reversal, or a drop into another container (FLO-FR-42) that would give the plan a `dependency_cycle` (per `../core/FGV-flow-graph-validation.md` FGV-FR-PMTY) is refused, with feedback that names the items of the cycle. A refused drop returns the item to where it was. A `relates` edge never forms a cycle.
20. **FLO-FR-ZEPI** A connection between an item and one of its ancestors or descendants is refused with the feedback of FLO-FR-16.
21. **FLO-FR-20** Removing an edge removes only that edge; both endpoint items remain in the plan with their other edges intact.
22. **FLO-FR-21** Dragging an item changes its position, and that position is part of the document (FLO-FR-03), so a Flow reopens with its layout as the author left it. A position is measured from the origin of whatever holds the item, so moving a container moves everything in it and changes one item's position.
23. **FLO-FR-22** Pan, zoom, selection, and which containers are collapsed are view state: they are not serialized, and a reopened Flow presents a default view with every container expanded. The view controls — zoom out, the zoom level, zoom in, and fit — sit on the canvas. A press on one of them neither pans the view nor clears the selection.
24. **FLO-FR-23** A Flow is variable-size; the UI imposes no cap on item or edge count or on how many items one container holds.
25. **FLO-FR-24** The Project panel does not contain a dedicated "Flows" section; Flows appear under their natural parent in the Project panel's tree (per `LIB-library.md` LIB-FR-07).
26. **FLO-FR-25** A Flow carries a name and an optional description, both in the document and both edited in place in the tab's band. The editor marks a name that is absent or only whitespace. That mark is the whole of the enforcement: an unnamed Flow still writes (FLO-FR-27). An empty description is absent from the document.
27. **FLO-FR-YDWT** The band carries the Flow's **references** beside its name: the HLD and any other documents the whole plan answers to. They are added through the picker of FLO-FR-10, render as the rows of FLO-FR-11, and open as FLO-FR-12 describes. A Flow with no reference shows an **Add HLD** affordance in their place.
28. **FLO-FR-26** A Flow holds unsaved changes from the first edit until its next write, and the tab shows a dirty indicator meanwhile. An edit adds, removes, or changes an item, an edge, or the Flow's own fields: a name, kind, container, position, size, type, direction, reference, description, draft link, footprint, due date, or local-only flag. Selecting and collapsing are not edits.
29. **FLO-FR-27** A Flow **writes itself**. An edit (FLO-FR-26) schedules a write through `"save artifact contents"` a short rest after the last edit, and a further edit restarts the rest. The write happens at once on tab close (FLO-FR-28), on the transitions of FLO-FR-29, on Save and Save All (per `SNV-shell-navigation.md` SNV-FR-31), and before a sync (FLO-FR-AKMV).
30. **FLO-FR-28** Closing a Flow tab that holds unsaved changes brings its pending write forward rather than waiting out the rest of FLO-FR-27, writing through `"save artifact contents"` before the tab closes (per `TAB-tabs.md` TAB-FR-12); closing a Flow tab whose plan has already reached disk writes nothing. Nothing survives the close: reopening the Flow deserializes the on-disk document afresh.
31. **FLO-FR-29** Closing the open project, quitting the application, switching the active project, and changing the project's active worktree write every Flow holding unsaved changes before any tab is torn down (per `SNV-shell-navigation.md` SNV-FR-25 and SNV-FR-26 and `OVW-overview.md` OVW-FR-11 and OVW-FR-12), the same set of writes Save All performs (SNV-FR-31). A write that fails cancels the transition, leaving the project open on its current worktree with the error visible. While the active worktree is gone, nothing is written and nothing cancels the transition (per `WTS-worktree-selector.md` WTS-FR-OSKY).
32. **FLO-FR-30** Activating another tab does not discard a Flow's unsaved changes. A Flow tab that is not the active tab keeps its plan and its dirty indicator, and making it active again performs no reload (per `TAB-tabs.md` TAB-FR-09).
33. **FLO-FR-31** A Flow tab holding no unsaved changes reloads its plan when its file is reported changed externally (per `../core/PST-project-storage.md` PST-FR-16), a sync's own write included. A Flow tab holding unsaved changes keeps them and stays on its in-memory plan, and its next write replaces the file's contents.
34. **FLO-FR-32** A connection being drawn is visible while it is being drawn: from the moment the drag begins, the canvas renders a provisional edge from the source item to the pointer, carrying the arrowhead of FLO-FR-48 at its free end, and drawn dashed so it does not read as an edge that exists. Abandoning the drag leaves the plan untouched.
35. **FLO-FR-33** While a connection is drawn, the nearest item within a snap distance that it could land on is highlighted, and a release completes the connection onto it. An item that FLO-FR-16, FLO-FR-17, FLO-FR-ZEPI, or FLO-FR-GZCH would refuse is never highlighted, and a release directly on one is refused with feedback. A release the canvas never sees abandons the drag.
36. **FLO-FR-34** The Flow tab carries the **action control** of `ACT-action-control.md` (ACT-FR-01), bound to the Flow file (ACT-FR-02) and offering **Discuss** (ACT-FR-04). It floats in the tab's bottom-trailing corner, leading of the view controls (ACT-FR-10), and holds that corner while the canvas pans and zooms (ACT-FR-08). A press on it neither pans the view nor clears the selection.
37. **FLO-FR-35** The Flow's discussions are read in the **floating discussion panel** (per `ACT-action-control.md` ACT-FR-20), shown and hidden by the discussions control beside the action control, and each renders as the shared discussion surface (per ACT-FR-RWHV). A Flow tab renders no discussion column. Opening the panel or the composer changes nothing in the document.
38. **FLO-FR-36** A discussion targets the Flow **file** as a whole, with no fragment (per `ACT-action-control.md` ACT-FR-LXKD). Nothing on the canvas anchors a conversation to an item or an edge. A remark about one item is made in a discussion about the Flow that names it, and the agent reads the plan with its delivery state and its overlaps (per `../core/AGC-agent-conversations.md` AGC-FR-KQNF).
39. **FLO-FR-38** A container item — a deliverable, a milestone, an epic, or a feature — renders around what it holds: a header with its kind glyph, name, status chip (FLO-FR-KQCE), and, on a milestone, due date (FLO-FR-XAPK); its references; and a region for its members. An empty container keeps its size. A task or a defect renders as a card.
40. **FLO-FR-39** An edge to or from a container lands on the container's border; an edge to or from a member lands on the member's border, whether or not the other end is in the same container. A `blocks` edge into a container blocks everything in it, which is how `../core/FDL-flow-delivery.md` reads it (FDL-FR-PXHL).
41. **FLO-FR-42** An item dropped inside the bounds of a container becomes a member of the innermost container whose bounds contain it, and one dropped on open canvas becomes a top-level item. An item the add affordance places joins the container it lands in on the same terms. A drop is the only thing that changes membership, and it changes no edge.
42. **FLO-FR-OAOZ** A drop or a placement that would put an item into a container its kind does not permit (per `../core/FGV-flow-graph-validation.md` FGV-FR-YHFX), or that would make an edge join an item to its ancestor or descendant, is refused. A refused drop returns the item to where it was, and the canvas states which containers the kind can join.
43. **FLO-FR-44** A container is resized from its own edges and corners. It cannot be made smaller than the bounds of its members, so a resize never puts a member outside it. Moving a container moves everything in it (FLO-FR-21).
44. **FLO-FR-45** Removing a container that holds nothing removes it and its edges, on the terms of FLO-FR-08. Removing a container that holds anything asks first, naming how many items go with it; confirming removes it with every item under it and all their edges, and cancelling removes nothing.
45. **FLO-FR-ZASL** A container's header carries a collapse toggle. A collapsed container renders as its header alone, with a count of the leaves under it by state. Edges to its hidden members land on its border while it is collapsed.
46. **FLO-FR-HGIY** A selected item's kind can change to any kind that its container and its members still permit. A change that FGV-FR-YHFX or FGV-FR-MZIA would refuse is not offered. A change from a leaf kind to a container kind removes the draft link and the footprint after the canvas asks.
47. **FLO-FR-KQCE** Each item renders a **status chip** from the state `"load flow delivery state"` returns for it (per `../core/FDL-flow-delivery.md` FDL-FR-VGZI): **Not started**, **Drafting**, **In progress**, **Done**, or **Dropped**. The chip is drawn in shape and in words, not in colour alone. An item with no answer yet renders no chip.
48. **FLO-FR-IKMM** An item that the delivery state reports as blocked carries a **Blocked** marker. Its tooltip names each blocking item that is not done. Activating the marker selects those items. The marker changes nothing in the drafts or the runs.
49. **FLO-FR-KWFH** A leaf item that `"analyze flow overlap"` reports in an overlap (per `../core/FOA-flow-overlap-analysis.md` FOA-FR-RSBH) carries an **Overlap** marker. Its tooltip names each other item in the overlap and the shared paths. Activating it selects those items.
50. **FLO-FR-STUN** The canvas invokes `"load flow delivery state"` and `"analyze flow overlap"` with the serialized plan when the tab opens, a short rest after each edit, and on each `"drafts changed"` and `"graduation run changed"` event. A newer answer replaces an older one, and an answer for a superseded body is discarded.
51. **FLO-FR-NRBV** A selected task or defect with no draft link offers **Create draft**. It invokes `"create draft (name)"` with the item's name, stores the returned draft's id in the item's `draftId`, and opens the draft in a New Artifact tab. A refused creation stores nothing and shows the error on the item.
52. **FLO-FR-QZUR** A task or a defect with a draft renders the draft's name as a row. Activating the row opens the draft through `"open draft (id)"`. A draft the delivery state reports as missing renders a warning row naming the stored id, with **Unlink** in place of the open action.
53. **FLO-FR-RMVR** A selected task or defect offers **Link draft**, a picker of the worktree's drafts that no other item of this Flow links, and **Unlink** while it has a draft. Linking stores the chosen draft's id. Unlinking removes `draftId` and changes nothing in the draft.
54. **FLO-FR-ZEJU** A selected task or defect shows its **footprint**: the project paths its work is expected to change. Paths are added through a picker of the project tree's files and folders and removed one at a time. A footprint entry that names nothing on disk renders marked as missing.
55. **FLO-FR-XAPK** A selected milestone offers a **Due** date field that stores a calendar date or nothing. An unselected milestone shows its due date in its header, and marks it as past when the date is before today and the milestone is not done.
56. **FLO-FR-TZSU** A selected item offers a **Local only** toggle. A local-only item is never created on the tracker by a sync (per `../core/FTS-flow-tracker-sync.md` FTS-FR-HDRR), and its header carries a local-only mark.
57. **FLO-FR-AKMV** The band carries a **Sync** control. On a Flow with no sync section it reads **Connect to GitHub**, and activating it adds the sync section and starts a sync. Otherwise it reads **Sync**. A sync first writes any pending changes, then invokes `"sync flow with tracker"`. A write refused before the sync starts no sync.
58. **FLO-FR-KHBY** While a sync is running, the Sync control shows progress, every edit affordance of the tab is inert, and the canvas schedules no write. When the sync returns, the tab reloads its plan from disk (FLO-FR-31) and the affordances return.
59. **FLO-FR-WLHA** A sync that returns conflicts or skipped items marks the Sync control with their count and opens the sync review (per `FSR-flow-sync-review.md` FSR-FR-KGOY). A sync that returns none shows a short confirmation with the counts of what it pushed and pulled. A sync error shows its typed text in the band.
60. **FLO-FR-ULEM** An item with a sync link carries a **tracker tag** naming the repository and the issue or milestone number. Activating it invokes `"open tracker link"` with the link's URL. An item without a link in a synced Flow carries no tag until a sync creates its issue.
61. **FLO-FR-TYEZ** A selected item in a synced Flow with no sync link offers **Link to existing**, which takes an issue or milestone number and invokes `"read tracker item"`. On success the item takes the tracker's name and description, and its sync link stores the reference with those values as its base. A refusal shows its typed text and stores nothing.
62. **FLO-FR-46** A Flow tab validates the body a load returns through `"validate flow document"` before it renders anything. A body reported valid is deserialized and rendered; one reported invalid puts the tab in the error state of FLO-FR-05. The canvas enforces FLO-FR-16, FLO-FR-17, FLO-FR-ZEPI, FLO-FR-GZCH, and FLO-FR-OAOZ itself, locally and immediately, as the author draws.
63. **FLO-FR-47** A write that the validation inside `"save artifact contents"` refuses (per `../core/PST-project-storage.md` PST-FR-28) writes nothing: the tab lists every violation, keeps its plan and its dirty state, and leaves the file untouched. The canvas does not retry on a timer. A refused write cancels a tab close, a project close, a worktree switch, a quit, and a sync.
64. **FLO-FR-48** A `blocks` edge renders an **arrowhead at the blocked end**, at the point where the edge lands on that item's border and pointing along the edge's own direction there. A `relates` edge renders as a dashed stroke with no arrowhead. Both carry their type in shape, not in colour alone, and a selected edge takes the selection emphasis.

## User stories
- As an architect, I want to break my HLD down into deliverables, milestones, features, and tasks on one canvas so that the whole delivery reads as one picture rather than as a list of tickets.
- As an architect, I want to draw which work blocks which so that I and the agent see the order the delivery must keep.
- As an architect, I want each task to be a draft so that the agent and I write the task in the place it will be graduated from.
- As an architect, I want to see which tasks touch the same files while they could run in parallel so that I split or order them before they collide.
- As an architect, I want my plan and the GitHub issues of my team to stay the same plan so that nobody works from a stale copy.
- As an architect, I want the agent in a Flow discussion to see the plan, its state, and its overlaps so that it helps me split features with the same context I have.
- As a program lead, I want more than one Flow in a project so that each program or release has its own plan.

- Layout notes: the tab is a band above a canvas that takes the rest. The band holds the Flow's name and description (FLO-FR-25), its references (FLO-FR-YDWT), and the Sync control at its trailing end (FLO-FR-AKMV); the tab label carries the dirty indicator (FLO-FR-26). The add affordance is a transparent `+` in the canvas's top-right corner (FLO-FR-07). The element readout, the action control, the discussions control, and the view controls share the bottom line, in that order (FLO-FR-34).
- Each kind has its own glyph — deliverable `◆`, milestone `⚑`, epic `◈`, feature `▣`, task `☐`, defect `✱` — and the glyph, not colour, says what an item is. Containers nest by kind, and a container whose members are hidden shows `[▸]` and its leaf counts (FLO-FR-ZASL).
- A container's header carries, in order: glyph, name, due date for a milestone, status chip, and tracker tag. A card carries its glyph and name, its status chip, its markers (Blocked `⊘`, Overlap `⧉`), and its draft row (`✎`). References and the description render below the header or the name line, the description as rich text while the item is not selected (FLO-FR-13).
- A `blocks` edge is solid with an arrowhead at the blocked end; a `relates` edge is dashed with none (FLO-FR-48). Edges route between the nearest sides of the items they join and cross container borders freely (FLO-FR-39).
- The selected item shows the editing affordances its kind carries in a panel attached below its card or header and drawn over the canvas: the description source, the kind choice, the draft actions (Create draft, Link draft, Unlink), the footprint list, the due date, the Local only toggle, Link to existing, and the reference picker. The panel changes no item's size and no container's bounds (FLO-FR-44).

## UI contract boundary
- **Owned by the UI**: canvas rendering (items, containers, edges, markers, chips, pan, zoom, selection, collapse); item and edge creation, removal, renaming, retyping, reversal, placement, and resizing; the reference, draft, and footprint pickers and what they offer; the rendering of a description as rich text (FLO-FR-13); the in-flight rendering of a connection (FLO-FR-32, FLO-FR-33); the immediate, local enforcement of every plan rule while the author draws (FLO-FR-16, FLO-FR-17, FLO-FR-ZEPI, FLO-FR-GZCH, FLO-FR-OAOZ) and the feedback a refusal produces; the edits a draft link, a sync connection, and a link to an existing tracker item make to the document; the unsaved-changes state and its indicator; the inert state during a sync; and the serialization and deserialization of the Flow document.

  The document's **shape** is defined and validated by `../core/FGV-flow-graph-validation.md` (FGV-FR-01), which is also the authority on whether a document is a Flow at all. This surface serializes to that schema and treats the report a validation returns as the truth about a document it did not itself build (FLO-FR-46, FLO-FR-47). An item's state, its blocked flag, and its overlaps are never computed here: they are read from the operations below.

- **Delegated to backend (abstract)**:
  - `"load artifact contents by id"` — serves the Flow file's body (owned by `../core/PST-project-storage.md` PST-FR-15).
  - `"validate flow document"` — judges a body against the Flow schema and its structural rules (owned by `../core/FGV-flow-graph-validation.md` FGV-FR-02).
  - `"save artifact contents"` — writes the serialized document back, and refuses an invalid Flow (owned by `../core/PST-project-storage.md` PST-FR-09 and PST-FR-28).
  - `"load project tree (filesystem nodes tagged by artifact type)"` — populates the reference and footprint pickers and resolves references to display names and types (owned by `../core/PST-project-storage.md` PST-FR-07). The canvas reads no artifact's contents to render a reference.
  - `"open artifact by id"` — routes a reference's click-through to its natural surface (owned by `../core/PST-project-storage.md` PST-FR-08).
  - `"create draft (name)"`, `"open draft (id)"`, and `"list drafts"` — create a task's draft, open it, and populate the Link draft picker (owned by `../core/DRS-draft-storage.md`).
  - `"load flow delivery state"` — each item's state, draft, and blocked flag (owned by `../core/FDL-flow-delivery.md`).
  - `"analyze flow overlap"` — the overlaps among the plan's leaf items (owned by `../core/FOA-flow-overlap-analysis.md`).
  - `"sync flow with tracker"`, `"read tracker item"`, and `"open tracker link"` — sync the Flow, read an existing tracker item to link, and open a tracker URL (owned by `../core/FTS-flow-tracker-sync.md`).

  The action control, its composer, and the floating discussion panel are owned by `ACT-action-control.md`. The sync review is owned by `FSR-flow-sync-review.md`. The `"drafts changed"` and `"graduation run changed"` events are owned by `../core/DRS-draft-storage.md` and `../core/GRD-graduation.md`.

## Non-functional requirements
- Pan, zoom, selection, resizing, collapse, and connection dragging remain responsive on plans of at least several hundred items, whatever the depth of the hierarchy.
- Every plan rule is enforced client-side and answers immediately as the author draws: no connection, drop, kind change, or resize waits on a backend call. The cycle check of FLO-FR-GZCH runs locally on every connection attempt.
- The delivery state and the overlaps arrive after the plan renders. The canvas is usable before they answer, and a slow answer never blocks an edit.
- An edge's type and direction are carried by shape: the arrowhead, the dash, and the kind glyphs read the same in a monochrome screenshot and to a viewer who distinguishes no colours.
- Serialization round-trips: writing a Flow that was opened and not edited produces a document that deserializes to the same plan, and the serialized form is stable in key order and formatting, so a Flow is a plain, diffable JSON file whose Git history shows only what changed.
- A Flow's unsaved changes are in-memory only and do not outlive the Flow tab holding them.
