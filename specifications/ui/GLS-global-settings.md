# Global settings

**Spec code:** `GLS`

## Intent
Global settings is the **Global group** of the Settings window (`SWN-settings-windows.md`), for configuration that belongs to the user and the machine rather than to any one project: the app **theme** and the **fonts** it sets text in (Appearance), whether the vertical panel's selection follows the active tab (Navigation), the **recent-projects** list and its management, the user-global **registries** of installed plugins and installed agent adapters, the author's stored **GitHub tokens**, the **AI integrations** the application may use — the API providers it calls itself, with the share of a model's context window a document under discussion may fill (AI API) and the agentic backends it hands work to (Agentic AI), each its own section — the **embeddings** that improve the ranking of search, with the model that makes them (Indexing), the **Personal agents** the author can hold a conversation with, described here once for the machine and available in every project, the **Docker** backend the application reaches a container runtime through, the **Isolation** that the agents of graduation runs run under, and the **relay endpoint** the application reaches a remote client through (Remote connectivity). It is the counterpart to `SET-project-settings.md`, which holds the project-scoped sections of the same window. Its backend is `../core/GSS-global-settings-storage.md`. Out of scope: any control over the main window's full-screen presentation or the universal search bar's query mode, each of which is owned by the surface that presents it (GLS-FR-14).

## User stories
- As a user, I want to choose the app's theme (light, dark, or follow the system) so the app matches the rest of my environment.
- As a returning user, I want to curate my recent-projects list — remove stale entries, clear it, and pin the ones I care about — so the picker stays useful.
- As a user, I want to install plugins and agent adapters once for my machine, separately from deciding which ones a given project uses.
- As a user, I want each section to say what it governs, so that I know whether a model I choose in it is the one my agents will answer on.
- As a user, I want the GitHub tokens I have given the app to live in one place I can review, verify, and clean out.
- As a user, I want to point the app at the coding-agent I intend it to drive — whether that is a CLI I have installed or an endpoint I reach over the network — and pick the model it should use, once, for my machine.
- As a user, I want to give the app the AI provider endpoint and key it should use for the model calls it makes itself, in the same place and with the same care as the tokens it already holds.
- As a user, I want to give the app the address of the relay my phone will reach it through, and prove that the relay is there and speaks what the app needs, before I try to pair a device.
- As a user, I want to tell the app how it reaches Docker on this machine — through the Docker Engine or through the Docker CLI — and prove that it can, once, before any project asks it to build or run an image.
- As a user, I want the agents of my graduation runs to run inside a micro VM with a bounded number of CPU cores, a bounded amount of RAM, and no access to my local network, so that a rogue agent cannot harm my machine.

## UI contract boundary
- **Owned by the UI**: the Global group's sections and their order, the Appearance theme selector, the Appearance typography controls for the three typographic roles together with their specimens, the bounding of the sizes and line heights they commit, and the presentation of a stored family the machine no longer has, the Recent projects list with remove / clear / pin affordances, the Installed plugins registry list with install / uninstall, the Installed adapters registry list with install, inline validation, per-section dirty/save behaviour, applying the chosen theme to the application root on selection, the Navigation section's **Selection follows tab** switch (GLS-FR-28), the Notifications section's switch, its statement of the operating system's disposition, and its rehearsal control (GLS-FR-25 through GLS-FR-27), the Docker section's backend-mode selector, endpoint control, CLI path field, Verify action, and verification status line (GLS-FR-29 through GLS-FR-31), the Isolation section's mode selector, CPU cores slider, RAM slider, local network switch, allowed local hosts list with its inline validation, its statements, and its unsupported-host state (GLS-FR-YAEA through GLS-FR-GHYV), the Indexing section's embeddings switch, model picker with its marks and its confirmation, progress lines, and download failure state with its Retry action (GLS-FR-JDUM through GLS-FR-UWFA), the Remote connectivity section's relay endpoint field, Verify action, and validation status line (GLS-FR-KVNP through GLS-FR-RBLM), and the AI API section's Document size limit field with its note and its inline validation (GLS-FR-DLMP, GLS-FR-WQHT). The GitHub section's own list, dialog, and actions are owned by `GHA-github-authentication.md`, the AI API and Agentic AI sections' tabs, fields, and actions by `AII-ai-integrations.md`, and the Personal Agents section's list, persona editor, and actions by `AGT-agents.md`; this spec places all four sections in the Global group and states how each participates in the window's save model. The window itself — its side nav and groups, its modality, its size, its centring, the one-settings-window rule, the save-before-close sweep, and the status bar button and the application-menu entry that open it — is owned by `SWN-settings-windows.md`. What the rehearsal's raise then does — whether it is posted, and where activating it lands the author — is owned by `NTF-notifications.md`.
- **Delegated to backend (abstract)**: "load app preferences", "save app preferences", "list system fonts", "list recent projects", "remove recent project", "clear recent projects", "pin recent project", "unpin recent project", "list installed plugins", "install plugin (source)", "uninstall plugin", "list agent adapters", "install adapter (source)", "get notification permission", "request notification permission", "load docker backend", "save docker backend", "detect docker cli binary", "verify docker backend", "load isolation settings", "save isolation settings", "load relay endpoint", "save relay endpoint", "verify relay endpoint", "load embeddings settings", "save embeddings settings", "list embedding models", "retry embeddings model download", "get embeddings status", "load document limit percent", "save document limit percent". The two Document size limit operations are owned by `../core/GSS-global-settings-storage.md` (GSS-FR-PCTL) and serve GLS-FR-DLMP and GLS-FR-WQHT. The five Indexing operations and the event `"embeddings status changed"` are owned by `../core/EMB-embeddings-index.md` and serve GLS-FR-JDUM through GLS-FR-UWFA. The three Remote connectivity operations are owned by `../core/GSS-global-settings-storage.md` and serve GLS-FR-KVNP through GLS-FR-RBLM. The four Docker operations are owned by `../core/GSS-global-settings-storage.md` and serve GLS-FR-29 through GLS-FR-31. The two Isolation operations are owned by `../core/GSS-global-settings-storage.md` and serve GLS-FR-YAEA through GLS-FR-GHYV. The two notification operations are owned by `../core/NTD-notification-delivery.md` and serve GLS-FR-26; the rehearsal of GLS-FR-27 posts through `NTF-notifications.md` rather than reaching the notification commands itself, and introduces no operation here. The GitHub section's operations are delegated by `GHA-github-authentication.md`, the two AI sections' by `AII-ai-integrations.md`, and the Personal Agents section's by `AGT-agents.md`, rather than here. Stubs may keep state in memory during the walking skeleton.

## Functional requirements
3. **GLS-FR-03** The Global group of the Settings window holds these sections, in this order: Appearance, Navigation, Notifications, Recent projects, Installed plugins, Installed adapters, GitHub, AI API, Agentic AI, Indexing, Personal Agents, Docker, Isolation, Remote connectivity. The side nav and the one-section-at-a-time rule belong to the window (per `SWN-settings-windows.md` SWN-FR-QXTV).
4. **GLS-FR-04** The Appearance section presents a theme selector offering exactly three mutually-exclusive choices — light, dark, system — initialised from "load app preferences" on mount; the default theme is `system`.
5. **GLS-FR-05** Selecting a theme applies it to the application root immediately (no relaunch) and persists it via "save app preferences"; the app-wide application of the value and the behaviour of "system" are governed by `OVW-overview.md` OVW-FR-09 and OVW-FR-10. The same user-global preference is also editable from the shell top-chrome theme selector (`SNV-shell-navigation.md` SNV-FR-15 / SNV-FR-16); both entry points read and write one shared value.
6. **GLS-FR-06** The Recent projects section lists entries from "list recent projects" showing name, path, last-opened, and pinned state, with pinned entries sorted first.
7. **GLS-FR-07** The Recent projects section supports removing a single entry (via "remove recent project"), clearing the whole list (via "clear recent projects"), and pinning/unpinning an entry (via "pin recent project" / "unpin recent project"); removing or clearing never deletes the project on disk. The Project picker also pins, unpins, and removes single entries (per `PPK-project-picker.md` PPK-FR-SDXU).
8. **GLS-FR-08** The Installed plugins section lists the user-global registry via "list installed plugins" and supports installing via "install plugin (source)" and uninstalling via "uninstall plugin"; plugin **enablement** is managed in Project settings (`SET-project-settings.md` SET-FR-04), not here.
9. **GLS-FR-09** The Installed adapters section lists the user-global adapter registry via "list agent adapters" and supports installing via "install adapter (source)"; adapter **configuration** is managed in Project settings (`SET-project-settings.md` SET-FR-05), not here.
10. **GLS-FR-10** Each section that edits through a save maintains an independent dirty state; saving applies that section's changes via the appropriate operation and clears its dirty state. A section holding a dirty state is a pending change the window writes before it closes, whether or not that section is the one on screen (per `SWN-settings-windows.md` SWN-FR-08, SWN-FR-09), and a save the section reports as failed keeps the window open with that section presented (SWN-FR-11). The Appearance, Navigation, Notifications, GitHub, AI API, Agentic AI, Indexing, Docker, Isolation, and Remote connectivity sections are not among them (GLS-FR-05, GLS-FR-20, GLS-FR-28, GLS-FR-25, GLS-FR-15, GLS-FR-16, GLS-FR-UWFA, GLS-FR-31, GLS-FR-GHYV, GLS-FR-RBLM).
12. **GLS-FR-12** Every section renders a first-class empty state before any plugin or adapter is installed, before any GitHub token is stored, before any integration is configured in the AI API section or in the Agentic AI section, before any agent has been described, before the Docker backend has been verified, before a relay endpoint has been given, and before any project has ever been opened (an empty recent list is not an error).
13. **GLS-FR-13** Closing the Settings window saves every pending change in every section of both groups first and shows no discard-unsaved-changes prompt (per `SWN-settings-windows.md` SWN-FR-08 through SWN-FR-10). A save that fails cancels the close and leaves the window open (SWN-FR-11).
14. **GLS-FR-14** The Appearance section edits the theme and the three typographic roles (GLS-FR-17) and nothing else. The user-global app-preferences record it saves through also carries the main window's OS full-screen state, which the shell owns (`SNV-shell-navigation.md` SNV-FR-38), the universal search bar's active query mode, which the search input owns (`SCH-search.md` SCH-FR-13), the diff viewer's visualization and rendering modes, which a Diff tab owns (`DFV-diff-viewer.md` DFV-FR-23), the notifications switch, which the Notifications section owns (GLS-FR-25), and the selection-follows-tab switch, which the Navigation section owns (GLS-FR-28); this section presents no control for any of them. Because "save app preferences" is a whole-record write (`../core/GSS-global-settings-storage.md` GSS-FR-20), saving Appearance carries every one of those fields through unchanged, and a save from the Navigation or Notifications section carries Appearance's own values through the same way.
15. **GLS-FR-15** The GitHub section lists the author's stored GitHub tokens and is where they are added, verified, relabelled, and removed; its content, dialog, and behaviour are specified by `GHA-github-authentication.md` (GHA-FR-01). Every action in it applies immediately rather than through a section save, so it holds no dirty state and never contributes to the save-before-close sweep of GLS-FR-13. Which token a given project uses is not decided here — that is a project-scoped choice made in the token picker modal (`GHA-github-authentication.md` GHA-FR-15) and shown in Project settings (`SET-project-settings.md` SET-FR-12).
16. **GLS-FR-16** The AI the application may use is configured across two sections, one per level of `AII-ai-integrations.md` (AII-FR-01): **AI API**, the API endpoints it calls itself, each carrying a base URL, a key, a model, and the reasoning that model can be asked for — the endpoints and keys serving every call the application makes for itself, and the model and reasoning serving the graduation loop alone, an agent running instead on what its own description in the Agents section carries (GLS-FR-24, `AII-ai-integrations.md` AII-FR-54); and **Agentic AI**, the agent backends it hands work to, whether a CLI installed on this machine or an endpoint reached over the network, each carrying its own configuration, model, and reasoning effort. One integration is active in each, chosen there. They are two sections rather than two halves of one because the levels present the same shape — tabs, a status line, a model selector, an activation control — and stacked together they read as a single continuous list of fields whose second half happens to be about agents; only the selected section is on screen, which is what keeps each level's configuration unmistakably its own. Each section's content and behaviour are specified by `AII-ai-integrations.md`, except the AI API section's **Document size limit** field (GLS-FR-DLMP). Every action in either applies immediately, so like the GitHub section neither holds a dirty state nor contributes to the save-before-close sweep of GLS-FR-13. Both are distinct from the Installed adapters section (GLS-FR-09): an adapter transforms Synthesis artifacts into an external agent's workspace layout (`../core/ADP-adapters.md`), while an AI integration is something this application calls or drives itself. Which integration a given project uses is not decided here — a project may override either level's active choice from Project settings (`SET-project-settings.md` SET-FR-13, SET-FR-14).
16. **GLS-FR-DLMP** The AI API section carries one **Document size limit** field above the provider tabs, for every provider. It holds a whole percent from 1 to 100, read from "load document limit percent" on mount. A note says it is the share of the model's context window the discussed document may fill before the agent gets only part of it.
16. **GLS-FR-WQHT** The Document size limit field commits on Enter and on blur through "save document limit percent", and applies at once with no section save. A value that is empty, not a whole number, or outside 1 to 100 shows an inline message and commits nothing. A refused save restores the stored value and shows the refusal inline.
17. **GLS-FR-17** The Appearance section presents typography controls for exactly three typographic roles — **UI**, **Rich Markdown**, and **Source code** — the roles `OVW-overview.md` OVW-FR-13 defines. Each role carries three independent controls: font family, font size, and line height. All nine are initialised from "load app preferences" on mount.
18. **GLS-FR-18** Each role's family control offers the application's built-in default face for that role together with every family "list system fonts" reports (`../core/FNT-font-enumeration.md` FNT-FR-02, FNT-FR-08). The Source code role's control presents the families reported as fixed-width first and marks them as such, and offers the remainder below rather than withholding them, so a family the platform describes imprecisely is still choosable for code.
19. **GLS-FR-19** A font size and a line height are each bounded to a range the section enforces before committing, so a value that would leave the application unreadable or unusable cannot be persisted. The section owns this bounding; `../core/GSS-global-settings-storage.md` stores whatever value it is given (GSS-FR-29).
20. **GLS-FR-20** A change to any of the nine controls applies to the whole application immediately with no relaunch and persists at once via "save app preferences"; app-wide application of the three roles is governed by `OVW-overview.md` OVW-FR-14. The section therefore holds no dirty state and never contributes to the save-before-close sweep of GLS-FR-13, exactly as the theme selector does not (GLS-FR-05).
21. **GLS-FR-21** Each role's control group carries a specimen set in that role's current family, size, and line height, so the effect of a choice on the Rich Markdown or Source code role is legible without leaving the window.
22. **GLS-FR-22** A stored family that "list system fonts" does not report — a font uninstalled since it was chosen — is presented in its role's control as unavailable while remaining that role's stored selection, and the role renders in the application's built-in default face for as long as the family is absent. Reinstalling the font restores the role to it with no further action, and choosing another family replaces the stored selection; the absence alone rewrites nothing.
23. **GLS-FR-23** Each role offers a reset returning its family, size, and line height to the application's built-in defaults, and the section offers a reset returning all three roles at once. A reset applies and persists on the terms of GLS-FR-20.

24. **GLS-FR-24** The **Personal Agents** section is where the author describes the Personal agents they can talk to — each a nickname, an optional title naming the role it takes, a model drawn from the AI API provider that is active for the open project, the reasoning that model is asked for, and optional instructions — and is the only place a Personal agent is created, edited, or deleted. A Personal agent is stored on this machine and is available in every project without any action from the author; no project can exclude it, and the section is available when no project is open. The model and the reasoning an agent runs on are chosen in the persona editor only. An agent takes only the active provider's endpoint and key from the AI API section, never that section's own model or reasoning selection (`AGT-agents.md` AGT-FR-01, `AII-ai-integrations.md` AII-FR-54). Its content and behaviour are specified by `AGT-agents.md` (AGT-FR-09 through AGT-FR-21, and AGT-FR-42 for the title field). It sits beside the two AI integration sections rather than inside either because an agent is not an integration: it is a collaborator described in terms of one, so an author who has configured a provider once can describe several agents against it. Every action in it applies immediately through its own operation, so like the GitHub section it holds no dirty state and never contributes to the save-before-close sweep of GLS-FR-13. The agents of a single project are not described here — a project defines its own in the Project Agents section of Project settings (`SET-project-settings.md` SET-FR-15).
25. **GLS-FR-25** The Notifications section presents a single switch governing whether the application posts OS notifications at all, initialised from "load app preferences" on mount and defaulting to on (per `../core/GSS-global-settings-storage.md` GSS-FR-32). Toggling it persists at once via "save app preferences" and takes effect from the next raise onward with no relaunch (per `NTF-notifications.md` NTF-FR-11, NTF-FR-12), so the section holds no dirty state and never contributes to the save-before-close sweep of GLS-FR-13. It governs the operating system's notifications alone: with it off no OS notification is posted, while a toast still shows when the main window holds OS focus (per `NTF-notifications.md` NTF-FR-PCVX), and a tab the author is not looking at still takes the in-app attention indication of `NTF-notifications.md` NTF-FR-29, which no preference here or anywhere turns off. It is one switch rather than a set of them: what a notification is worth raising for is decided by the surface that raises it, and this section decides only whether the operating system is used to interrupt the author.
26. **GLS-FR-26** The section states the operating system's own disposition toward the application, read from "get notification permission" (`../core/NTD-notification-delivery.md` NTD-FR-02), because a switch that is on while the OS is refusing would otherwise describe nothing the author can observe. While that disposition is unrequested it offers a control that requests it via "request notification permission", which is one of the only two places in the application a permission prompt originates (per `NTF-notifications.md` NTF-FR-13). Once granted the control is absent; where the OS has refused, the section states that notifications are turned off in the operating system's own settings rather than offering a control that cannot succeed; and where the state is `unsupported` it states that this build of the application cannot post notifications — the case of a platform with no notification centre, and of a development run outside an application bundle — and renders the switch disabled.
27. **GLS-FR-27** The section offers a **rehearsal** — a control that raises one notification after a delay long enough for the author to leave the window, addressing the Notifications section of the Settings window for the open project (per `NTF-notifications.md` NTF-FR-25) — so the whole path can be exercised end to end: posted while the author is elsewhere, or shown as a toast while the main window holds OS focus, then activated or clicked, and arriving back on a real surface. It is enabled only while the switch is on, the operating system's disposition is granted, and a project is open, and is disabled and rendered greyed-out otherwise, because there is nothing for it to demonstrate in the first two cases and no project for an address to name in the third. The delay is stated on the control, so the author knows how long they have to switch away.
28. **GLS-FR-28** The Navigation section presents a single switch, **Selection follows tab**, governing whether a change of the main viewport's active tab moves the vertical panel's selection to the item that tab is a view onto (per `SNV-shell-navigation.md` SNV-FR-64). It is initialised from "load app preferences" on mount and defaults to on, both on a fresh install and for a stored record that carries no such field (per `../core/GSS-global-settings-storage.md` GSS-FR-33), so the behaviour is opt-out rather than opt-in. Toggling it persists at once via "save app preferences" and takes effect from the next qualifying tab activation with no relaunch, so the section holds no dirty state and never contributes to the save-before-close sweep of GLS-FR-13. Toggling it is not itself a navigation: it selects no item, reveals nothing, and switches no panel (per `SNV-shell-navigation.md` SNV-FR-69). It is one switch rather than one per panel, because the author is deciding whether the panel keeps step with them at all rather than which kinds of work it keeps step for.

29. **GLS-FR-29** The **Docker** section is where the machine's Docker backend is configured, and it holds three controls. A **backend mode** selector offers exactly two mutually-exclusive choices — **Bollard / Docker Engine** and **Docker CLI** — initialised from "load docker backend" on mount and defaulting to Bollard / Docker Engine. A **Docker endpoint** control offers the four platform-neutral forms the backend supports (per `../core/GSS-global-settings-storage.md` GSS-FR-36): the platform's automatic default, a Unix socket path, a Windows named pipe, and a TCP endpoint, with the automatic default preselected. A **Docker CLI path** field carries the executable the Docker CLI mode runs. The endpoint control is presented for Bollard / Docker Engine mode and the path field for Docker CLI mode, so the section shows the fields the selected mode actually uses; each keeps what it last held while the other mode is selected. When the path field renders empty, the section invokes "detect docker cli binary" and fills it with what that returns, marking the value as detected, exactly as a CLI-kind agentic tab does (per `AII-ai-integrations.md` AII-FR-17), and the author may replace it by typing or through a file picker.
30. **GLS-FR-30** The section verifies the selected backend **the way an agentic CLI binary is verified**: a **Verify** action invokes "verify docker backend" with the selected mode and the values that mode uses, and a status line beneath the controls says what the backend is — unverified, verified naming the Docker server version it answered with, or the one typed failure the attempt returned. The failures it renders are the selected mode's own (per `../core/GSS-global-settings-storage.md` GSS-FR-38): in Docker CLI mode a missing or invalid executable and a Docker daemon that cannot answer are different lines, and in Bollard / Docker Engine mode an invalid endpoint and a daemon that cannot answer are likewise different lines, because each asks the author to correct a different thing. The section never presents a backend as verified on a daemon that did not answer.
31. **GLS-FR-31** Every change in the section applies immediately through "save docker backend", so the section holds no dirty state and never contributes to the save-before-close sweep of GLS-FR-13. Changing the mode, the endpoint, or the CLI path returns the status line to unverified without invoking any verification (per `../core/GSS-global-settings-storage.md` GSS-FR-39), because the success that was earned belonged to the values that earned it. A verified backend stays verified across a relaunch and across a daemon that is stopped and started, and the section re-reads it from "load docker backend" rather than re-probing on mount.

32. **GLS-FR-KVNP** The **Remote connectivity** section is where the one relay endpoint this machine reaches is configured, and it holds one control: a **relay endpoint** field carrying the URL of the relay, initialised from "load relay endpoint" on mount and empty until the author gives one. The section presents one endpoint rather than a list, because the application reaches one configured relay.
33. **GLS-FR-QWTD** A **Verify** action invokes "verify relay endpoint" with the URL in the field, and a status line beneath the control says what the endpoint is — unset, unverified, verified naming the relay version it answered with, or the one typed failure the attempt returned. Each failure of `../core/GSS-global-settings-storage.md` GSS-FR-HPWE renders as its own line.
   - *Why:* An empty URL, an unsupported scheme, a relay that did not answer, and a relay that lacks a capability each ask the author to correct a different thing.
34. **GLS-FR-RBLM** A change to the field applies immediately through "save relay endpoint" and returns the status line to unverified without invoking any verification (per `../core/GSS-global-settings-storage.md` GSS-FR-NLDC), so the section holds no dirty state and never contributes to the save-before-close sweep of GLS-FR-13. The section reads its state from "load relay endpoint" on mount and probes nothing.
35. **GLS-FR-XDUJ** The section displays, edits, persists, and validates no `SYNTHESIS_SERVER_TOKEN`, no relay credential, and no private key. It presents no field for one, and the status line names no secret.
   - *Why:* The token reaches the application, the relay, and the mobile client as runtime configuration, so a control for it here would create a second, weaker home for a credential.

36. **GLS-FR-YAEA** The **Isolation** section presents a mode selector with exactly two mutually-exclusive choices, **None** and **Microsandbox**, initialised from "load isolation settings" on mount and defaulting to None. The mode governs the agent launches of graduation runs — stream runs, direct runs, and merge runs — and no other agentic CLI launch (per `../tools/EAC-execute-agent-cli.md` EAC-FR-SNMS). The section states this scope.
37. **GLS-FR-USNH** While Microsandbox is selected, the section shows a **CPU cores** slider from 1 to the logical CPU count and a **RAM** slider from 1 GB to the total RAM in 1 GB steps, as "load isolation settings" reports them. The defaults are min(4, CPU maximum) and min(8 GB, RAM maximum). A stored value above a maximum renders at it.
38. **GLS-FR-LKXZ** While Microsandbox is selected, the section states that outbound internet access is always allowed, and it shows a **Block local network access** switch, which defaults to on. The switch states that it blocks the loopback, private, and link-local ranges and this machine itself.
39. **GLS-FR-QFWZ** Below the switch, the section shows the **allowed local hosts** list, each entry with a remove control, and an entry field with an Add control. An entry is an IP address, a CIDR range, or a host name. An invalid or repeated entry is refused inline. While the switch is off, the list is disabled and keeps its entries.
40. **GLS-FR-CWJX** Beside the list, the section warns that a Custom Gateway (per `AII-ai-integrations.md`) whose base URL names `localhost` or a local network address is blocked until the author adds its host to the list, and that the application does not add the gateway host automatically.
41. **GLS-FR-WAGX** The section states that under Microsandbox the project's Docker-in-Docker setting is ignored: no host Docker socket is mounted into the sandbox, and a graduation start does not check the socket (per `SET-project-settings.md` SET-FR-PMHB).
42. **GLS-FR-EZRL** Where "load isolation settings" reports that this machine cannot run Microsandbox, the section disables the Microsandbox choice, keeps None selected, and states the reason: the platform is not Linux or macOS, the Mac has no Apple Silicon, or KVM is missing or not accessible. A stored Microsandbox on such a machine renders selected with the reason, and None stays selectable.
    - *Why:* Microsandbox needs hardware virtualisation, and a stored choice copied from another machine must stay visible rather than look like None while every launch fails.
42. **GLS-FR-PVQT** While Microsandbox is selected, the section shows a **Disk** slider in 1 GB steps, as "load isolation settings" reports it: from 8 GB, or the disk size where that is smaller, to the disk size. The default is min(64 GB, disk size), and a larger stored value renders at the maximum.
42. **GLS-FR-WMKD** Beside the Disk slider, the section states that the value sizes the sandbox disk, which grows only as it is used, and caps what an agent writes into each writable folder.
43. **GLS-FR-GHYV** Every change in the section applies at once through "save isolation settings", so the section holds no dirty state and takes no part in the save-before-close sweep of GLS-FR-13. Changes made in quick succession are all kept: the section saves one change at a time, and each save carries every earlier change of the section, so a later save never writes back a value that an earlier change replaced. A refused save keeps the previous value in the control and renders the refusal inline. A change takes effect at the next agent launch of a graduation run.
44. **GLS-FR-JDUM** The **Indexing** section holds the Global **Embeddings** switch, the model picker, and the progress of the model download and of the embedding jobs. It reads "load embeddings settings", "list embedding models", and "get embeddings status" on mount, and it follows `"embeddings status changed"`. It states that BM25 search is always on, and that embeddings improve how specifications and documents rank.
45. **GLS-FR-QRJM** The switch is off until the user turns it on. A change persists at once through "save embeddings settings". Turning the switch on starts the model download and then the indexing of the open project, with no confirmation (per `../core/EMB-embeddings-index.md` EMB-FR-NNOK, EMB-FR-OVPR).
46. **GLS-FR-KRZU** The model picker lists every model of "list embedding models" in the order it returns. The four recommended models carry a **Recommended** mark, and BGE-small-en-v1.5 also carries a **Default** mark. Each entry shows the model name and its vector dimension.
47. **GLS-FR-ZBQR** Choosing another model while the switch is on opens a confirmation. It states that every project embeds its specifications and documents again, and that search uses BM25 only until that ends. Confirming saves the model through "save embeddings settings". Cancelling keeps the previous model. While the switch is off, a choice saves at once with no confirmation.
48. **GLS-FR-RQFK** While the model downloads, the section shows a progress bar in bytes. While a job of the open project runs, the section shows the job name and its count of chunks. With no project open, the section shows the model state only.
49. **GLS-FR-HEPP** A failed download shows its reason and a **Retry** action that calls "retry embeddings model download". The section states that search uses BM25 only until the model is ready.
50. **GLS-FR-UWFA** Every change in the Indexing section applies at once, so the section holds no dirty state and takes no part in the save-before-close sweep of GLS-FR-13. A refused save keeps the previous value in the control and renders the refusal inline.

## Non-functional requirements
- The Global group can be opened, navigated, and its forms rendered without network access and with empty registries.
- The Appearance section renders its typography controls without an intermediate loading state, and a machine carrying a large font set does not delay the section's first paint.
- The theme selection applies before the Appearance section's next paint; there is no visible flash of the previous theme after a selection.
- The Remote connectivity section renders without reaching the network: mounting it reads the stored record alone. Verification is the one action in it that contacts anything, and it is bounded rather than open-ended.
- The Isolation section renders without booting a VM and without reaching a daemon or the network: mounting it reads the stored record and the facts of this machine.
- The Docker section renders without reaching a daemon: mounting it reads the stored record and, where the path field is empty, looks for an executable. Verification is the one action in it that contacts anything, and it is bounded rather than open-ended.
