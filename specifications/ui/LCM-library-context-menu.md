# Project context menu

**Spec code:** `LCM`

## Intent
The right-click context menu on the Project panel's tree nodes — the action surface for item-bound operations on the files and folders the Project panel (`LIB-library.md`) renders. It gathers the file operations (Delete, Copy, Rename, Paste), the folder-scoped creation affordances (New File, New Artifact, New Folder), artifact-type curation (the Artifact Type submenu and Clear Type), the per-artifact navigation affordance (Notes), and the hand-off of an item to tools outside the application (the Open In submenu) into one menu whose entries vary by node kind and artifact type, so a user can act on a tree item without first opening it. Which entries a given node offers is governed by a single declarative action-applicability mapping, so retargeting an action to a different node kind or artifact type is a one-place edit. A removal that would take a folder's contents with it asks first, so the one action here that cannot be undone is the one action that requires a deliberate second answer. The Open In submenu lets the user work on an item the application made with the system terminal, an in-app terminal tab, or the platform file manager. The menu owns its own structure, that confirmation, and the session-local copy clipboard; the filesystem mutations, type assignments, and outside-app hand-offs it triggers are owned by the backend (`../core/PST-project-storage.md`, `../core/ASC-artifact-scanning.md`, `../core/TRS-terminal-sessions.md`).

## User stories
- As a user, I want to right-click a file or folder in the Project panel to delete, rename, copy/paste, retype, or take notes on it, so that I can act on tree items without leaving the tree.
- As a user, I want the menu to show only the actions that make sense for what I clicked, so that folder-only, artifact-only, and skill-only actions never appear where they don't apply.
- As a user, I want to open a file or folder of the Project panel in a terminal or in the file manager of my platform, so that I can work on the items the application made with tools outside it.
- As a maintainer, I want each action's availability defined in one place, so that changing which node kinds or artifact types an action applies to is a single, low-risk edit.

- Layout notes: `[i]` marks a leading icon, required on every entry and every submenu (LCM-FR-07); the glyphs shown are illustrative — the contract is that an icon is present, not which glyph. A node's entries vary by node kind and artifact type per the applicability mapping (LCM-FR-01): **Delete / Copy / Rename** are universal across files and folders; **New File**, **New Artifact**, and **New Folder** appear only on folders, sit at the top of the menu as one creation cluster in that order, and are followed by a separator (LCM-FR-08, LCM-FR-09, LCM-FR-10); **Paste** appears only on folders and is greyed when the in-panel clipboard is empty; **Notes** appears on artifact files, Flows included. **Open In** is universal across files and folders and sits directly above **Artifact Type**; its last entry reads **Finder** on macOS, **Explorer** on Windows, and **File Manager** elsewhere, and **Terminal Tab** is absent on Windows (LCM-FR-WBHG, LCM-FR-VTLR, LCM-FR-XWFO). Artifact-type curation lives entirely inside the nested **Artifact Type** submenu — the ten built-in types followed by a separator and **Clear Type** at the very bottom — rather than at the menu's top level. The **Artifact Type** and **Open In** submenus open on mouse-over, without a click, and at most one of them is open at a time. The recursive-delete confirmation is a centered modal overlay rather than a menu region: it appears only for a folder the backend reports as non-empty (LCM-FR-11), names the folder it is about, and offers **Delete** as its confirming action and **Cancel**/✕ as its dismissing one, with **Cancel** taking focus so a stray Enter removes nothing.

## UI contract boundary
- **Owned by the UI**: the context-menu structure, the declarative action-applicability mapping that decides which entries a node of a given kind and artifact type offers, the actions it hosts (the **Notes** panel switch, the **Delete / Copy / Rename** file operations together with the recursive-delete confirmation window Delete may raise (LCM-FR-11) and the client-side rename validation that decides what never reaches the backend (LCM-FR-12), folder **Paste** and its enablement from the in-panel copy clipboard, the folder-only **New File**, **New Artifact**, and **New Folder** triggers, the nested **Artifact Type** submenu containing the type choices and **Clear Type**, and the nested **Open In** submenu with its platform label, its folder choice (LCM-FR-PKIH), and its choice of the active worktree's terminal target), the per-entry icons, and the session-local copy clipboard itself. The menu opens on the Project panel's tree nodes (`LIB-library.md` LIB-FR-02) and never decides artifact types on its own.
- **Delegated to backend (abstract)**:
  - `"delete path (path, recursive)"`, `"rename path"`, and `"copy path into folder"` — file-tree mutations owned by `../core/PST-project-storage.md`. After each completes, the resulting structural change reaches the Project panel through the `"project tree changed"` event (`../core/ASC-artifact-scanning.md`) rather than a direct return payload (per `LIB-library.md` LIB-FR-10). The menu never decides for itself whether a folder is empty: the `recursive = false` attempt and the typed "not empty" error it may return are what tell it (LCM-FR-11).
  - `"append log records (records)"` — owned by `../core/LGC-logging.md`, used for the diagnostic record a client-side rejection produces (LCM-FR-12). It mutates nothing and is not part of any file operation.
  - `"assign artifact type (path, type, scope = file | folder)"` and `"clear artifact type assignment (path)"` — artifact-type curation owned by `../core/ASC-artifact-scanning.md`.
  - **New File** is triggered here but the creation modal and its `"create file (location, name)"` operation are owned by `NFI-new-file.md` (NFI-FR-07); the menu passes only the right-clicked folder as the starting location.
  - **New Artifact** is triggered here but the creation modal and its `"create typed file (location, name, artifact type)"` operation are owned by `NTA-new-typed-artifact.md` (NTA-FR-08); the menu passes only the right-clicked folder as the starting location. It creates no draft and invokes no operation of `../core/DRS-draft-storage.md`.
  - **New Folder** is triggered here but the creation modal and its `"create folder (location, name, artifact type)"` operation are owned by `NFW-new-folder.md` (NFW-FR-07); the menu passes only the right-clicked folder as the starting parent.
  - `"open in system terminal (path)"` and `"reveal in file manager (path)"` — outside-app hand-offs owned by `../core/PST-project-storage.md`. They change nothing on disk.
  - `"list terminal targets"` and `"create terminal (target, kind, vendor, start folder)"` — the **Terminal Tab** entry, owned by `../core/TRS-terminal-sessions.md`. The new tab opens through the terminal tab of `TRM-terminals.md`.
  - **Notes** switches the Notes vertical-panel scope (`NTS-notes.md` NTS-FR-02) and invokes no backend operation.

## Functional requirements
1. **LCM-FR-01** A file or folder node in the Project panel may be right-clicked (or equivalent) to open a context menu whose entries are determined by node kind and resolved artifact type. The set of entries is driven by a single declarative action-applicability mapping — each action declares the node kinds and artifact types it applies to in one place, so changing an action's availability is a single edit rather than a scattered code change. Under that mapping: every file and folder node offers the file operations **Delete**, **Copy**, and **Rename** (LCM-FR-02), the nested **Open In** submenu (LCM-FR-WBHG), and the nested **Artifact Type** submenu (LCM-FR-04); folder nodes additionally offer **Paste** (LCM-FR-03) and the top-of-menu creation entries **New File** (LCM-FR-10), **New Artifact** (LCM-FR-08), and **New Folder** (LCM-FR-09) in that order; and artifact files, Flows included, additionally offer the **Notes** action (LCM-FR-05). Folders offer no Notes, and neither does a file the scan surfaces without a resolved artifact type. The menu operates on the Project panel's tree nodes (`LIB-library.md` LIB-FR-02).
2. **LCM-FR-02** The context menu of any file or folder node offers **Delete**, **Copy**, and **Rename**. **Delete** removes the node's path on the two-phase terms of LCM-FR-11. **Rename** collects a new basename, validated client-side as non-empty, free of path separators, and different from the node's current basename (LCM-FR-12), and invokes `"rename path"` with it. **Copy** places the node's path on the Project panel's in-panel clipboard (LCM-FR-03) and performs no filesystem mutation on its own. A completed delete or rename is reflected in the tree through the watcher-driven reload (`LIB-library.md` LIB-FR-10), which preserves expand/collapse state and selection (`LIB-library.md` LIB-FR-06), and a delete additionally closes whatever tabs the removed path backed (per `TAB-tabs.md` TAB-FR-19).
3. **LCM-FR-03** The Project panel maintains a session-local in-panel clipboard holding at most one copied node path, set by **Copy** (LCM-FR-02). Folder context menus offer **Paste**, enabled only while the clipboard holds a path and shown greyed/disabled when the clipboard is empty. Paste invokes `"copy path into folder"` with the clipboard path as the source and the right-clicked folder as the destination, duplicating the source into that folder. The clipboard is copy-only: a Paste does not clear it, so the same source may be pasted into several folders, and Copy/Paste never moves or removes a node. A destination name collision reported by the backend is surfaced inline and leaves the tree unchanged.
4. **LCM-FR-04** Artifact-type curation is presented as a single nested **Artifact Type** submenu rather than as top-level menu entries. The submenu entry carries an icon (LCM-FR-07) and opens on mouse-over, without requiring a click. The submenu lists the ten built-in artifact types (`../core/ASC-artifact-scanning.md` ASC-FR-02), Document included, each with the icon and tag of `LIB-library.md` LIB-FR-08; choosing a type invokes `"assign artifact type (path, type, scope = file | folder)"` with `scope = file` for a file node and `scope = folder` for a folder node. Below the ten types, separated from them by a divider, **Clear Type** sits at the very bottom of the same submenu and invokes `"clear artifact type assignment (path)"`. After assignment or clearing, the affected node's tag (`LIB-library.md` LIB-FR-08) updates without requiring a full manual reload.
5. **LCM-FR-05** Every artifact file node, a Flow node included, offers a **Notes** action that switches the Notes vertical-panel surface (`NTS-notes.md`) to that artifact's scope: it drives the panel's scope selector to its entity position (`NTS-notes.md` NTS-FR-09) bound to that artifact (`NTS-notes.md` NTS-FR-02), so the user can jump to an artifact's notes without first opening it in a tab. The action is purely a navigation affordance: it triggers no filesystem mutation and opens no Editor or Flow tab.
7. **LCM-FR-07** Every context-menu entry and every submenu — at the top level, within the **Artifact Type** submenu, including each of the ten type entries and **Clear Type**, and within the **Open In** submenu — carries a leading icon. This is a universal requirement: no entry renders without an icon.
8. **LCM-FR-08** Folder nodes offer a **New Artifact** entry as the second item of the creation cluster that opens the menu, directly below **New File** (LCM-FR-10) and above the file operations. It is folder-only: file nodes — including artifact files, skill artifacts, and Flows — do not offer it. The entry carries a leading icon (LCM-FR-07); selecting it opens the New Artifact modal (`NTA-new-typed-artifact.md`) with the right-clicked folder as the starting location, which the user may still change, and with the artifact type unchosen regardless of any type the right-clicked folder carries (per `NTA-new-typed-artifact.md` NTA-FR-08). Confirming there creates one empty file in the chosen location and assigns it the chosen type; it creates **no draft**, applies no draft template, and opens no New Artifact tab (per `NTA-new-typed-artifact.md` NTA-FR-14) — a draft is created in the Changes panel alone (`DRP-drafts-panel.md` DRP-FR-06, DRP-FR-26). The menu only triggers the modal; the creation inputs and the creation operation are owned by `NTA-new-typed-artifact.md`.
9. **LCM-FR-09** Folder nodes offer a **New Folder** entry immediately below **New Artifact**, completing the three-entry creation cluster that the divider separates from the file operations. It is folder-only on the same terms as LCM-FR-08: no file node offers it. The entry carries a leading icon (LCM-FR-07); selecting it opens the New Folder modal (`NFW-new-folder.md`) with the right-clicked folder as the starting parent, which the user may still change, and with the artifact type unset regardless of any type the right-clicked folder carries (per `NFW-new-folder.md` NFW-FR-07). The menu only triggers the modal; the creation inputs and the creation operation are owned by `NFW-new-folder.md`.
10. **LCM-FR-10** Folder nodes offer a **New File** entry as the first item of the menu, at the head of the creation cluster that opens it, above **New Artifact** (LCM-FR-08) and **New Folder** (LCM-FR-09). It is folder-only on the same terms as those two: no file node offers it. The entry carries a leading icon (LCM-FR-07); selecting it opens the New File modal (`NFI-new-file.md`) with the right-clicked folder as the starting location, which the user may still change (per `NFI-new-file.md` NFI-FR-07). The menu only triggers the modal; the creation inputs and the creation operation are owned by `NFI-new-file.md`.

11. **LCM-FR-11** **Delete** is a two-phase operation, and the first phase is what discovers whether consent is needed. It invokes `"delete path (path, recursive)"` with `recursive = false`. A file, and a folder that holds nothing, is removed by that first call and no confirmation is ever shown. A folder holding anything returns the typed "not empty" error (per `../core/PST-project-storage.md` PST-FR-18), which removes nothing and instead opens the recursive-delete confirmation: a modal naming that folder and stating that its contents go with it. Confirming re-invokes the same operation with `recursive = true`; dismissing it — via **Cancel**, the close control, Escape, or an outside click — invokes nothing further and leaves the folder and its contents exactly as they were. Because emptiness is decided by the backend against the filesystem rather than by this menu against the tree it renders, a folder whose only contents are gitignored or otherwise excluded from the scan (`../core/ASC-artifact-scanning.md` ASC-FR-09) still prompts, so the user is never asked to consent to a removal they were shown nothing about — nor denied the chance to.
12. **LCM-FR-12** A **Rename** whose entered basename equals the node's current basename is rejected by this menu: `"rename path"` is not invoked, no filesystem operation is attempted, the rename input stays open with the offending value intact and the reason shown inline, and one `ERROR` record is emitted through `"append log records (records)"` (`../core/LGC-logging.md`) under the `frontend` domain naming the path and the unchanged name. The rejection is the menu's own and does not depend on the backend's matching refusal (`../core/PST-project-storage.md` PST-FR-19), which stays in force underneath it for any other caller. The same treatment covers the two other client-side rejections of LCM-FR-02, an empty name and one containing a path separator, so no malformed or pointless rename reaches the backend.
13. **LCM-FR-TDWE** **Rename**, **Delete**, and **Paste** read the branch write guard of the active worktree's branch before they invoke `"rename path"`, `"delete path (path, recursive)"`, or `"copy path into folder"`, on the terms of `MBW-main-branch-write.md` MBW-FR-RMCO. On a main branch with no confirmation, the confirmation shows first, and nothing changes until the author confirms.

14. **LCM-FR-WBHG** Every file and folder node offers a nested **Open In** submenu directly below **Rename**, after a separator, and directly above **Artifact Type**. It opens on mouse-over, and a click also opens it. It lists **System Terminal**, **Terminal Tab**, and the file-manager entry, in that order. Opening one of **Open In** and **Artifact Type** closes the other.
15. **LCM-FR-PKIH** For a folder node, the **System Terminal** and **Terminal Tab** entries use that folder. For a file node, they use the folder that holds the file, which for a top-level file is the root folder of the active worktree.
16. **LCM-FR-PAUK** **System Terminal** invokes `"open in system terminal (path)"` with the path of the node, and the menu closes. The entry writes nothing, so it does not read the branch write guard.
17. **LCM-FR-XWFO** **Terminal Tab** invokes `"list terminal targets"`, takes the target whose `is_active_worktree` is true, and invokes `"create terminal (target, kind, vendor, start folder)"` with that target, kind `host_shell`, no vendor, and the folder of LCM-FR-PKIH. On success, the new session's tab opens and takes focus, as `TRM-terminals.md` TRM-FR-FYYB says. No target for the active worktree is an error (LCM-FR-WNPH).
    - *Why:* the target of a work-stream copy is the work stream, not the worktree, so the menu does not build the target from the worktree path.
18. **LCM-FR-NJVW** On Windows, **Terminal Tab** is not rendered (per `TRM-terminals.md` TRM-FR-DQYZ). Where no worktree is active, for example in a project outside Git, the entry is shown greyed and does nothing.
19. **LCM-FR-VTLR** The file-manager entry reads **Finder** on macOS, **Explorer** on Windows, and **File Manager** on every other platform. It invokes `"reveal in file manager (path)"` with the path of the node, and the menu closes. The file manager shows the node selected in the window of its parent folder, for a file and for a folder.
20. **LCM-FR-WNPH** A failed **Open In** entry shows its error inline in the Project panel, as a Paste collision does (LCM-FR-03), and changes nothing in the tree. It emits one `WARN` record through `"append log records (records)"` under the `frontend` domain. The record names the entry and the error. It names no path.
21. **LCM-FR-PDXH** The menu and each open submenu stay inside the window. A menu that would overhang the bottom or the right edge moves up or left until it fits. A submenu that would overhang the bottom moves up until it fits, and stays beside its parent entry.
22. **LCM-FR-UCJY** While a submenu is open, the pointer may cross another submenu's parent entry on its way into the open submenu. The open submenu changes only when the pointer stays on the other parent entry for 300 ms, and closes only when the pointer stays out of its parent entry for 300 ms. A click changes the submenu at once.
    - *Why:* the Open In entries sit to the right of the Artifact Type entry, so a straight pointer path to them crosses that entry.

## Non-functional requirements
- Disabled entries (for example **Paste** with an empty clipboard, per LCM-FR-03) are shown greyed rather than hidden, so the menu's shape stays stable across invocations on the same node kind.
- The recursive-delete confirmation is a floating overlay and is therefore mutually exclusive with the window's other overlays (per `SNV-shell-navigation.md` SNV-FR-56): opening it closes any other that is open.
- Deleting an empty folder or a file costs one backend call; only the non-empty-folder case costs two, and the second is made solely because the user confirmed. The menu never issues a separate call to ask whether a folder is empty.
- The action-applicability mapping (LCM-FR-01) is the single source of truth for which entries appear; adding an action or retargeting one to a different node kind or artifact type is done there, not by editing per-node rendering logic.
- The menu dismisses on Escape or an outside click without invoking any action.
