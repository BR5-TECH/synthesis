# Project

**Spec code:** `LIB`

## Intent
Vertical-panel surface that renders the project's filesystem as a tree, mirroring the folders and files actually on disk. It is named for what it shows: the project itself, as it exists on disk right now. Every file Synthesis recognises is tagged with its artifact type (Skill, Agent, Prompt, Spec, Flow, Instructions, Scenario, Scratchpad); folders that contain no supported artifacts are hidden by default. Default vertical-panel selection on project open. Primary place to browse what exists and to curate artifact types; item-bound actions (Delete, Copy/Paste, Rename, type assignment, Notes) are offered through the Project context menu (`LCM-library-context-menu.md`). The scan, classification, attribution storage, and change-watching are owned by the backend (`../core/ASC-artifact-scanning.md`); this surface renders the tree and reacts to its change events.

## User stories
- As a user, I want a tree of my real project files tagged by artifact type so that I can see at a glance what Skills, Agents, Specs, and Flows exist without leaving the tree.
- As a user, I want folders with no Synthesis artifacts hidden by default so that the tree is not buried under unrelated code and tooling files.
- As a user, I want to assign a type to a file or a whole folder when inference gets it wrong or can't tell, so that my project's structure is reflected accurately.
- As a user, I want the tree to update on its own when files are created or changed outside the app so that it never goes stale.
- As a user, I want the folders I expanded and the filters I set to still be in place the next time I open the project so that I don't rebuild my place in the tree on every launch.

The lens row at two panel widths — the tree holds Skills, Agents, Specs, and Instructions and no Prompt, Flow, Scenario, or Scratchpad, so those four have no button at all:
```
wide enough for every present type
│ (All)(Skill)(Agent)(Spec)(Instr)(Files) │

narrowed — the middle clips, the ends and the active one hold
│ (All)(Skill)(Ag…            (Files) │
        ▲ active
```
- Layout notes: each file node shows a type tag to the right of its name; unclassified files render with no tag (and surface only under the **All files** lens). The two filter controls are arranged as every vertical panel arranges them — the text search directly beneath the panel header, the lens beneath it and directly above the tree (per `SNV-shell-navigation.md` SNV-FR-58) — and both stay visible while the tree scrolls; the rescan affordance sits in the panel header above them. The lens is the single-line toggle row of `SNV-shell-navigation.md` SNV-FR-62, each button a short text tag set in the same treatment the tree's own type tags carry and disclosing the type's full name on hover; it clips at its trailing edge rather than wrapping (SNV-FR-63), and the panel's width is what the author changes to see the rest. There is no separate "show all folders" control. A file node renders its name in the case it carries on disk (per `SNV-shell-navigation.md` SNV-FR-57). Panel width, collapse-to-icon, and hide are inherited from `SNV-shell-navigation.md`.

## UI contract boundary
- **Owned by the UI**: tree rendering from the filesystem node shape, per-node artifact-type tag display, which nodes are expanded and which are collapsed, local filter UI (the artifact-type lens toggle row — including its **All artifacts** default, its trailing **All files** position, which per-type buttons it renders at all (LIB-FR-19), and its clipping at narrow widths — and the in-tree text search), the current selection, and panel width/collapse/hide state (inherited from `SNV-shell-navigation.md`). The UI decides what its panel state is and when to persist it; the storage of that state is delegated. Revealing a node another surface names — expanding its ancestors, selecting it, and relaxing whichever local filter would hide it (LIB-FR-18) — is likewise the panel's own work and introduces no backend operation. Right-clicking a node opens the Project context menu (`LCM-library-context-menu.md`), which owns the item-bound actions and the in-panel copy clipboard. The UI computes folder visibility from which files are visible under the active filter — using the per-folder `has_artifacts` flag the backend supplies for the default **All artifacts** lens — and does not itself decide artifact types. The pinned **View map** button (LIB-FR-VMAQ) and the routing of a Spec file click to the Map tab (LIB-FR-SJDC) are the panel's own and introduce no backend operation.
- **Delegated to backend (abstract)**:
  - `"load project tree (filesystem nodes tagged by artifact type)"` — returns the filesystem-mirroring tree with type tags and per-folder `has_artifacts`. Owned by `../core/PST-project-storage.md`, backed by the scanner in `../core/ASC-artifact-scanning.md`.
  - `"open artifact by id"` — resolves to Editor or Flow per artifact type (owned by `../core/PST-project-storage.md`).
  - `"rescan project tree"` and the event `"project tree changed"` — owned by `../core/ASC-artifact-scanning.md`.
  - `"load library panel state"` and `"save library panel state"` — the persisted set of expanded folder paths and the panel's two local filters. Owned by `../core/PSS-project-settings-storage.md`.

## Functional requirements
1. **LIB-FR-01** Project is a vertical-panel surface; it is selected by default when a project is opened.
2. **LIB-FR-02** The panel renders the project's filesystem as a tree that mirrors the on-disk folder and file structure (per `../core/ASC-artifact-scanning.md` ASC-FR-01), rooted at the project's active worktree (per `../core/WTC-worktree-context.md` WTC-FR-03). The filesystem is the source of truth for the tree; there is no abstract entity hierarchy in the panel's nesting, and no node from a worktree other than the active one appears in it.
3. **LIB-FR-03** Clicking a file node opens it in its natural surface based on its resolved artifact type: a Flow opens a Flow tab (per `FLO-flow.md` FLO-FR-01); every other recognised artifact type opens an Editor tab (per `EDT-editor.md`). Clicking a folder node expands or collapses it. LIB-FR-SJDC names the one exception.
4. **LIB-FR-04** The panel exposes two local filters in-panel: an in-tree text search and an artifact-type lens. The lens is the single-select toggle row of `SNV-shell-navigation.md` SNV-FR-62, whose positions are, in order: **All artifacts** (leading, and the default), each of the eight built-in artifact types (`../core/ASC-artifact-scanning.md` ASC-FR-02), and **All files** (trailing). These are panel-local lenses that hide non-matching nodes and do not replace the universal search bar (`SCH-search.md`).
5. **LIB-FR-05** The artifact-type filter and the text filter are AND-combined. The artifact-type filter has three regimes that determine which file nodes are eligible: **All artifacts** shows only files with a resolved `artifact_type` (per `../core/ASC-artifact-scanning.md` ASC-FR-06); a specific type shows only files resolving to that type; **All files** applies no type constraint and shows every file. An empty text filter applies no text constraint.
6. **LIB-FR-06** A node's expanded/collapsed state and the current selection are preserved while the user changes filters, across vertical-panel collapse/hide cycles, and across live tree reloads triggered by the watcher (LIB-FR-10). Expand/collapse state additionally survives closing and reopening the project, restored from the persisted panel state (LIB-FR-14); the selection is session-local and starts empty on every open of a project.
7. **LIB-FR-07** The panel does not have a separate "Flows" section; Flows appear at their natural filesystem location in the tree (per `FLO-flow.md` FLO-FR-24).
8. **LIB-FR-08** Each file node displays its resolved artifact type as a tag/badge; a file with no resolved type is shown without a tag. The tag reflects the type and source (inferred / assigned / inherited) supplied by `../core/ASC-artifact-scanning.md`. A folder node carrying a folder-scope assignment of its own (per `../core/ASC-artifact-scanning.md` ASC-FR-18) displays that type as a tag on the same terms, so the association a folder imposes on its contents is legible from the tree rather than only from the context menu; a folder with no assignment is shown without a tag whatever its contents resolve to.
9. **LIB-FR-09** A folder node is shown when either its subtree holds at least one file node currently visible under the active artifact-type and text filters, or the folder is itself eligible under those filters with no visible descendant. A folder is itself eligible under the artifact-type filter when it carries a folder-scope artifact-type assignment the active lens admits — any assignment under **All artifacts**, an assignment of that type under a specific type lens (`has_artifacts = true`, per `../core/ASC-artifact-scanning.md` ASC-FR-08) — and unconditionally under **All files**, which constrains nothing; it is eligible under the text filter when its own name matches. A folder eligible on neither count is hidden. Under the default **All artifacts** lens this hides folders whose subtree contains no supported artifacts and which carry no assignment of their own; selecting **All files** reveals those folders together with their unclassified files. There is no separate "show all folders" control — **All files** is the escape hatch. An empty folder is therefore surfaced rather than swallowed: one carrying an artifact type appears under **All artifacts** and under its own type lens from the moment it exists, and one carrying none appears under **All files**.
10. **LIB-FR-10** The panel subscribes to the backend `"project tree changed"` event and reloads the tree when it fires (debounced upstream per `../core/ASC-artifact-scanning.md` ASC-FR-10), preserving expand/collapse state and selection (LIB-FR-06).
11. **LIB-FR-11** The panel exposes a manual rescan affordance that invokes `"rescan project tree"` and re-renders the returned tree, for the case where the user wants to force a refresh.
12. **LIB-FR-12** The artifact-type filter's default is **All artifacts** — the lens the panel takes whenever no filter has been persisted for the active worktree (LIB-FR-14) — so a project opened for the first time on this machine shows only classified artifact files and the folders that contain them; unclassified files (for example tooling and config files such as `package.json` or lockfiles in the project root) are hidden until the user selects **All files** or a broader lens. **All files** is the only lens that surfaces unclassified files.
13. **LIB-FR-13** When the project's active worktree changes (per `OVW-overview.md` OVW-FR-12), the Project panel reloads against the new content root and becomes the selected vertical-panel surface again. No panel state crosses the switch — expanded paths name folders in the previous content root — so the tree restores the incoming worktree's own persisted state (LIB-FR-14), falling back to the defaults of LIB-FR-12 and LIB-FR-15 when that worktree has none. The selection is dropped and is not restored.
14. **LIB-FR-14** The panel's own state — the set of expanded folder paths, the active artifact-type lens, and the in-tree text filter — is persisted through `"save library panel state"` and restored on the next open of the same worktree through `"load library panel state"`. It is held per machine and per worktree in the gitignored project-local store (per `../core/PSS-project-settings-storage.md` PSS-FR-18), so it never enters the project's Git repository and one user's tree shape is never imposed on anyone who clones it. The current selection is not part of the persisted state.
15. **LIB-FR-15** Expansion is recorded rather than collapse: a folder renders expanded if and only if its path is in the persisted set, so a folder absent from that set — a newly-created one, or every folder on a first-ever open — renders collapsed. The root's immediate children are always visible, so the tree is never restored into a state with nothing to click.
16. **LIB-FR-16** A persisted path naming a folder not currently present in the tree is ignored when rendering and is retained in the persisted set rather than dropped, so a folder that disappears and returns — as when a Git checkout in the same worktree changes the on-disk structure — comes back expanded. An unresolvable path is never surfaced as an error.
17. **LIB-FR-17** The panel persists its state after any change to the expanded set, the lens, or the text filter, coalescing rapid changes — a run of keystrokes in the text filter, several folders expanded in succession — into a single write rather than one write per change. Because `"save library panel state"` writes the record whole, persisting one of the three values carries the other two through unchanged.
18. **LIB-FR-18** Another surface may ask the Project panel to reveal a node. The panel expands every ancestor of that node, scrolls it into view, and makes it the current selection (LIB-FR-06). A reveal always ends with the node visible: where a local filter would hide it, the panel relaxes that filter — switching the artifact-type lens to **All files** and clearing the in-tree text filter — and only the filters that would actually hide the node are touched, so a reveal of a node the active lens already admits changes nothing about the panel's filtering. Relaxed filters are persisted like any other filter change (LIB-FR-17). A reveal is about where the node sits in this panel and says nothing about which surface the vertical panel is showing: whether the Project panel is on screen at all is the caller's decision, made on the ordinary terms of `SNV-shell-navigation.md` SNV-FR-45. A node the loaded tree does not hold cannot be revealed, and a request for one leaves the tree, the filters, and the selection exactly as they are, reporting nothing. This is the path the post-creation reveals take: the New File window's (`NFI-new-file.md` NFI-FR-12) and the New Folder window's (`NFW-new-folder.md` NFW-FR-11), and the path an Editor or Flow tab's own file takes when the vertical panel follows the active tab (per `SNV-shell-navigation.md` SNV-FR-64, SNV-FR-66). A graduated draft writes several files at once and reveals none of them, reaching the tree through `"project tree changed"` like any other external creation (per `NAW-new-artifact.md` NAW-FR-20), because there is no single node a reveal could land on.
19. **LIB-FR-19** The lens row renders a per-type button only while the loaded tree holds at least one node carrying that type — a file whose resolved `artifact_type` is it, or a folder carrying it as a folder-scope assignment (per `../core/ASC-artifact-scanning.md` ASC-FR-18) — so the row offers the types the project has rather than the eight it could have, and a project of Skills and Specs shows two type buttons rather than eight. **All artifacts** and **All files** name no type and always render, and so does whichever position is active (per `SNV-shell-navigation.md` SNV-FR-63): a lens the author selected never vanishes from under them when the last file carrying that type leaves the tree, and the tree beneath it renders the narrowed-to-nothing state of `SNV-shell-navigation.md` SNV-FR-61 rather than the panel silently changing lens on their behalf. The row is re-computed from every tree load (LIB-FR-10), so a type gains its button the moment the project's first file of that type appears and loses it once the author has moved off it.
20. **LIB-FR-VMAQ** A **View map** button with the layers icon is pinned below the tree, centred across the panel's width, and it stays visible while the tree scrolls. Activating it opens the Map tab or jumps focus to it (per `SMP-specification-map.md` SMP-FR-HZRA).
21. **LIB-FR-SJDC** While the Map tab is the active tab, a click on a file node whose resolved artifact type is Spec selects that spec on the map (per `SMI-specification-map-inspector.md` SMI-FR-PRSL) and opens no tab. The node becomes the current selection of the panel. Every other click follows LIB-FR-03.

## Non-functional requirements
- Tree must render incrementally — large subtrees should not block panel responsiveness.
- Live reloads must not visibly thrash the tree: because the backend debounces and coalesces change bursts (ASC-FR-10), the UI reloads at most once per burst, and preserves the user's expand/selection state so a reload is not disruptive.
- The panel-state load is issued alongside the tree load when the panel mounts, so the first painted tree is already in its restored shape rather than flashing the default state and then re-expanding.
- Persisting panel state never blocks tree interaction, and a failed write is not surfaced as a blocking error — the tree stays usable and the state is written again on the next change.
