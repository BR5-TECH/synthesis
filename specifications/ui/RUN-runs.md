# Runs

**Spec code:** `RUN`

## Intent
Bottom-panel surface where agent activity is watched. Behaves like the output panel in a typical IDE: the user keeps editing in the main viewport while work runs below. It holds one section for the project's queue of graduation runs and one for the live output of whichever piece of agent work is running, because all of it is agent work and an author looking for agent work should look in one place: **agent output**, the streaming log of an adapter-invoked run, of a graduation turn, or of a work stream update's semantic turn, and **graduation**, the project's queue of graduation runs, which turn drafts into specifications and merge work streams into their base branches. Neither is started here — an adapter run begins outside this window through the backend's own surface (per `../core/ADP-adapters.md`), a graduation run begins on a draft (per `NAW-new-artifact.md` NAW-FR-18), and a merge run begins from a conflicting merge in the work stream selector (per `WSS-work-stream-selector.md`) — so this panel initiates nothing and offers no control that would (RUN-FR-09). Out of scope: everything a graduation run renders, controls, and routes to, which is `GRU-graduation-runs.md`'s; the graduation queue and run state themselves, which are `../core/GRD-graduation.md`'s; the **persisted Source and Structured log streams of a graduation run**, which are `../core/GRS-graduation-run-log-storage.md`'s and are read in the log window a run's own progress bar opens (`GLW-graduation-log-window.md`), and which this panel neither reads, follows, searches, nor stands in for; and the project-level overview of that queue, which is the Dashboard's (`DSH-dashboard.md`).

## User stories
- As a user with an agent run under way, I want to glance at the bottom of the IDE to see whether it is making progress.
- As a user, I want to stop a runaway run without leaving my current editing tab.
- As a user with a graduation queued and an adapter run streaming, I want both under one panel toggle rather than two places to check.

## UI contract boundary
- **Owned by the UI**: bottom-panel rendering; the section control of RUN-FR-10 and which section is active; the append-only log surface, its cancel/stop control, its live indicator, and the persistence of the most recent run output until dismissed or replaced; and the empty state of each section.
- **Delegated to backend (abstract)**: `"read agent activity (run id, after, limit)"` and the event `"agent activity appended"`, both owned by `../core/AGV-agent-activity.md`; `"list graduation queue"` with the events `"graduation queue changed"` and `"graduation run changed"`, owned by `../core/GRD-graduation.md`; and the event `"work stream update progress"`, owned by `../core/WKS-work-streams.md`; the graduation events and this event together are how this panel learns which piece of work to show and whether it is still working. This surface reads and follows; it invokes nothing that starts, stops, or changes a run, and it never invokes "start run", which no surface of the application invokes (RUN-FR-09). It invokes **neither** `"read graduation logs (run id, phase id, pass, stream, cursor, limit, query)"` **nor** anything else `../core/GRS-graduation-run-log-storage.md` owns: the persisted graduation activity is read in the log window and nowhere here (RUN-FR-DTJO). The graduation section introduces no operation here: every command and event it reads is named in `GRU-graduation-runs.md`'s own contract boundary.

## Functional requirements
1. **RUN-FR-01** Runs is a bottom-panel surface, selected by its own toggle in the activity bar's bottom-panel cluster (per `SNV-shell-navigation.md` SNV-FR-44). It is the bottom panel's default surface in a project with no persisted layout.
2. **RUN-FR-02** The **agent output** section shows one piece of agent work at a time, chosen from what the backend holds rather than by the author: the graduation run that is working — a draft run or a merge run alike, and whichever of its phases is working, a work turn and a review turn both being agent work of the same run — a work stream update that is running, or, where several are working at once, the more recently updated of them. Where none is working it shows the most recently updated, so a turn that has just ended is still readable — its output is the whole account of why it ended, and it would otherwise vanish at the moment it became interesting. The section shows one piece of work's activity and never two at once. The **graduation** section shows a queue rather than one run, because a project may hold several graduation runs at once with exactly one of them working (per `../core/GRD-graduation.md` GRD-FR-BNTC); how that queue is rendered and selected within is `GRU-graduation-runs.md`'s.
3. **RUN-FR-03** In the agent output section, output is rendered append-only as records arrive. Each row carries the local wall-clock time the record was written, its kind, and its one-line summary, and the kind is what a reader scans the column of: what went wrong, what the agent decided, and what it merely narrated are told apart without opening anything.
4. **RUN-FR-04** A live indicator is visible while the adapter run is in the "running" state; it clears when the run transitions to finished, failed, or cancelled.
5. **RUN-FR-05** This section offers no control that acts on a run. Stopping, continuing, discarding, and answering a run are the graduation section's, which is where a run's state is (per `GRU-graduation-runs.md`), so nothing here can act on a run by accident from a surface whose whole job is reading one.
6. **RUN-FR-06** When an adapter run ends, its output persists in the panel until dismissed by the user or replaced by a new run.
7. **RUN-FR-07** Activating Runs from a Dashboard widget or Search result opens and focuses the bottom panel on the Runs surface (per the routing rule in `DSH-dashboard.md` DSH-FR-06 and `SCH-search.md` SCH-FR-08).
8. **RUN-FR-08** The user can dismiss what the section is showing through a clear control. It clears the view and nothing else: the run's own record is the backend's, is untouched, and re-selecting the run brings it back — clearing hides output rather than deleting it. A section cleared this way says so, and never that the run recorded no output: the run recorded plenty, the reader dismissed it, and saying otherwise is the surface reporting its own state as the run's.
9. **RUN-FR-09** **This panel starts nothing.** It renders and controls work the backend already holds, and it offers no affordance anywhere to begin any of it: an adapter run begins outside this window through the backend's own surface (per `../core/ADP-adapters.md`), and a graduation run begins on a draft through its **Graduate** action (per `NAW-new-artifact.md` NAW-FR-18) and its start dialog (per `GRU-graduation-runs.md` GRU-FR-GLSO). A section with nothing to show renders its own empty state saying so rather than a control to begin one, and the Cancel and Stop controls of RUN-FR-05 act on a run already in flight and are absent from it.
10. **RUN-FR-10** The panel carries a **section control** at its head choosing between **graduation** and **agent output**, exactly one active at a time, each carrying a short label and the graduation one carrying the count of runs the project's streams hold between them, one run being counted once whichever stream it is in, so the work in flight is legible without switching to it. The choice persists per project with the rest of the panel's state (per `../core/PSS-project-settings-storage.md` PSS-FR-06). A section the author is not in still receives its events and is current the moment they switch to it, so nothing is missed by looking elsewhere. A section switched away from and back to renders what the author left in it rather than its opening state: what that means for the graduation section — which run is selected and which of its iterations is being read — is `GRU-graduation-runs.md`'s (GRH-FR-NCJK, `GRU-graduation-runs.md` GRU-FR-IZKI), and neither section is reset by the other being looked at.

11. **RUN-FR-11** Each row's time is rendered in the local time zone, from the instant the backend recorded the line rather than the instant this surface received it, so a stream read after the fact carries the times the run actually had.
12. **RUN-FR-12** The list follows the newest record while it is pinned. Scrolling up releases the pin and reveals a control that resumes it, and scrolling back to the foot resumes it as well, so reading something older is never fought by arriving output. The pin is on when the section is first shown for a run.
13. **RUN-FR-13** The section reads its own records: it takes the newest page when it opens on a run, and on being told the run grew it asks for the records after the newest it holds. It renders nothing from an event payload, holds no record twice however the two overlap, and discards everything it holds when the run it is showing changes — a sequence belongs to one run, so carrying a cursor across would ask the wrong question of the wrong run. Two things follow that a reader would otherwise never see the cause of. An answer that arrives for a run no longer being shown is discarded rather than merged, because both its records and the cursor they would set belong to another run; without that, one run's output appears under another's name and the run now showing goes silent for the rest of its life. And the section acts on *any* event for its run rather than comparing what the event carries against its cursor: records made at the same moment are announced independently, so an event can name a sequence below one already announced, and a comparison that skipped on it would skip the read that was going to catch up.
14. **RUN-FR-14** Activating a row expands it in place to show the vendor's own event verbatim beneath it, and activating it again collapses it. The summary is this build's reading of an event; the verbatim event is what a reader needs when that reading is the thing that is wrong. An event the backend cut is shown as cut rather than as a short event.
15. **RUN-FR-15** The section tells a run that has said nothing yet from a run that said nothing: a working run with no records says it is waiting, and a finished one with none says it recorded no output. It also says at its head when older records are no longer held, so a reader knows the top of the list is not where the run began (per `../core/AGV-agent-activity.md` AGV-FR-05).
16. **RUN-FR-16** A read that fails leaves the section rendered and empty rather than blank or thrown out of. A panel that crashes on a read is worse than one that shows nothing, and the run it was watching is unaffected either way.

17. **RUN-FR-DTJO** The **agent output** section is not a graduation log. It renders `../core/AGV-agent-activity.md`'s **session-lifetime, memory-bounded** stream of whichever run it is showing (RUN-FR-02), and that record is bounded, evicted, forgotten when a run is discarded, and gone after a relaunch (per `../core/AGV-agent-activity.md` AGV-FR-05, AGV-FR-06, AGV-FR-12). The **Agent Activity** stream of a graduation run is a different record with different rules — safe, complete, durable, mandatory, and retained for the lifetime of the run (per `../core/GRS-graduation-run-log-storage.md` GRS-FR-JQOO, GRS-FR-FORV) — and this section neither reads it nor stands in for it.
18. **RUN-FR-GTEU** This section therefore carries **no stream toggle, no phase selector, no pass selector, and no search**, and nothing in it opens the log window. A graduation run's activity log is opened from **that run's own progress bar** in the graduation section, which is the one route to it.
19. **RUN-FR-VKLS** A work stream update is shown here as what it is and never as a graduation run: the section names the stream, the update's strategy, and which semantic turn of the bound it is on, learning them from `"work stream update progress"`. It offers none of the run controls of RUN-FR-05; **Cancel update** is the selector's (per `WSS-work-stream-selector.md` WSS-FR-BDMU).
20. **RUN-FR-ZQWA** An update's records reach this section through the sink every agent turn's records reach it through, keyed by the update attempt rather than by a run (per `../core/AGV-agent-activity.md` AGV-FR-03). They are read with the same operation, and a settled update's records stay readable on the terms of RUN-FR-06 until they are dismissed or replaced.
21. **RUN-FR-MVTX** What this section says about missing output is about **its own** record and never about a run's persisted activity: a statement that older records are no longer held (RUN-FR-15) is a statement about the memory bound of the stream it is reading, and it never implies that the run's persisted Agent Activity is short, evicted, or empty.
22. **RUN-FR-BWNK** A merge run is a graduation run. The graduation section lists it in the queue with every other run of the project and counts it once in the section control's count (RUN-FR-10), and it renders as `GRU-graduation-runs.md` sets for a merge run. This panel has no separate section, row or control for a merge.
23. **RUN-FR-LQDT** A merge run's work turns and review turns are agent work of that run. The agent output section shows their activity under RUN-FR-02 with the same selection rule as for every run, keyed by the run's id and read with the same operation (per `../core/AGV-agent-activity.md` AGV-FR-03). The section keeps the run's activity readable after the turn ends, and the clear control of RUN-FR-08 dismisses it as it dismisses every run's.
24. **RUN-FR-YQAE** A row of the log window's Agent Activity (per `GLW-graduation-log-window.md` GLW-FR-KHGP) has the same visible parts as a row of this section: the local time, the kind with its label, and the one-line summary. This section keeps its own behaviour for every run unchanged, including its expansion to the verbatim event (RUN-FR-14) and its kinds that the persisted stream excludes.

## Non-functional requirements
- Append performance must keep up with a sustained line rate typical of agent stdout streams without UI stalls.
- The panel does not require focus to receive new output lines.
- Switching sections costs no call: each renders from state it already holds, and neither re-fetches on becoming active.
