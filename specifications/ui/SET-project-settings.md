# Project settings

**Spec code:** `SET`

## Intent
Project settings is a native child window (`SWN-settings-windows.md`) for configuration that belongs to the **currently open project**: project configuration, target repo bindings, agent-adapter configuration, MCP server connections, plugin enablement, and the Docker image each agentic CLI vendor's work runs in. Installation of plugins and adapters and all user-global preferences (including the theme) live in Global settings (`GLS-global-settings.md`); this window manages only what travels with, or is local to, the project — the project's draft template among them, the one piece of project configuration the author writes rather than picks — together with the four project-scoped pointers into user-global registries — which GitHub token the project authenticates with, which agentic integration it hands work to, which AI API integration it calls, and which of the author's conversational agents it may talk to. Plugin enablement is in v1 because the plugin system is architectural bedrock.

## User stories
- As a user, I want one window where I can configure this project's adapters, MCP servers, plugin enablement, and bindings so that I don't have to hunt across surfaces.
- As a user, I want to enable, disable, and configure installed plugins for the project I'm working in.
- As an author, I want to write once the headings and prompts every new draft should start from, so that a draft opens on the shape my project expects rather than on a blank page I fill in from memory each time.
- As an author, I want to choose how many graduation runs may work at the same time in this project, so that I use the machine as much as I want and no more.
- As an author, I want to name the Docker image my project's agent runs in, point at the Dockerfile that builds it, and build it from here in one click, so that a graduation runs in the environment my project actually needs.

## UI contract boundary
- **Owned by the UI**: Project settings window layout, sectioned navigation within the window, per-section forms (plugin list and enablement toggles, adapter configuration form, MCP connection form, project-config form, repo-bindings form), the Project section's line-ending selector and its immediate application (SET-FR-10), the Project section's read-only display of the project's GitHub token and the action that opens the picker (SET-FR-12), the Draft template section — its reuse of the Editor's rich Markdown editing surface, the debounce that decides when the template is written, the saving / saved / save-failed report it renders, and the loading state it holds while a read is outstanding (SET-FR-16 through SET-FR-20) — the Docker section's vendor tabs, their image, tag, and Dockerfile fields, the Dockerfile picker, the build control and its enablement, and the inline progress, terminal result, and retry each tab renders (SET-FR-21 through SET-FR-27), the GitHub Project settings section's Project picker, interval selector, and configuration report (SET-FR-TTTB through SET-FR-GXJU) and its parent issue Type filter, sub-issue Type selector, and sub-issue milestone policy control (SET-FR-BLQN through SET-FR-ZHCT), the Graduation section's execution time limit row and its inline refusal (SET-FR-DHFS, SET-FR-YMRV), the Graduation section's concurrency drop-down with its loading, saving, and save-failure states (SET-FR-QKKQ through SET-FR-IHQE), inline validation, dirty-state and save-per-section behavior, opening from the status bar's Project settings button and from the application menu (per `SWN-settings-windows.md` SWN-FR-13). The Project section's two AI integration controls are owned by `AII-ai-integrations.md`; this spec places them in the section and states how each participates in the window's save model (SET-FR-13, SET-FR-14). The window itself — its modality, its fixed size, its centring, the one-settings-window rule, the save-before-close sweep, and the application-menu entry that opens it only while a project is open — is owned by `SWN-settings-windows.md`.
- **Delegated to backend (abstract)**: "load project config", "save project config", "list installed plugins", "enable plugin", "disable plugin", "configure plugin (id, config)", "list agent adapters", "configure adapter (id, config)", "list MCP server connections", "add MCP server connection", "remove MCP server connection", "test MCP server connection", "get project github token binding", "set project github token binding", "get project agentic integration", "set project agentic integration", "get project ai api integration", "set project ai api integration", "list project agents", "enrol project agent", "remove project agent", "load project docker images", "save project vendor image", "build project vendor image", "cancel project vendor image build", "load docker backend", "list github projects", "get github polling state", "set github polling settings (project node id, interval minutes)", "get github publication settings", "set github publication settings (parent issue types, sub issue type, sub issue milestone policy)", "list github issue types". The three GitHub polling operations are owned by `../core/GPP-github-polling.md`, and the window follows that module's `"github polling changed"` event. The three GitHub publication operations are owned by `../core/GHP-github-publication.md` (GHP-FR-KVRH, GHP-FR-NQWX, GHP-FR-PTYL). The registry reads ("list installed plugins", "list agent adapters") are owned by Global settings storage and consumed here to render enablement/configuration controls, the two GitHub binding operations are owned by `../core/GTS-github-token-storage.md`, the two agentic operations by `../core/AIC-agentic-integrations.md`, the two AI API operations by `../core/AAP-ai-api-integrations.md`, and the three agent operations by `../core/AGR-agent-registry.md`. The four Docker image operations are owned by `../core/PSS-project-settings-storage.md` and "load docker backend" by `../core/GSS-global-settings-storage.md`, and the window subscribes to that module's `"project image build progress"` and `"project image build finished"` events for what a build is doing (SET-FR-25, SET-FR-26). The remaining project-scoped operations are owned by `../core/PSS-project-settings-storage.md`. Stubs may keep configuration in memory during the walking skeleton.

## Functional requirements
1. **SET-FR-01** Project settings is a native child window of the application, opened by activating the Project settings button in the status bar's leading region (see `STB-status-bar.md` STB-FR-04) or the application menu's Project settings entry, which is offered only while a project is open (per `SWN-settings-windows.md` SWN-FR-14, SWN-FR-16). It is neither a tab of the main viewport nor a surface drawn inside another window (per `SWN-settings-windows.md` SWN-FR-01).
2. **SET-FR-02** The window is subject to the settings-window rules of `SWN-settings-windows.md`: it is application-modal to the main window (SWN-FR-02), holds a fixed outer size of 800 × 600 px (SWN-FR-03), opens centred on the active display (SWN-FR-04), and is the only settings window on screen (SWN-FR-05). Opening Project settings while its window is already open focuses that window rather than opening a second (SWN-FR-06), and opening it while Global settings is open closes that window first (SWN-FR-07).
3. **SET-FR-03** The Project settings window is divided into sections: Project, Draft template, Target repo bindings, GitHub Project settings, Agent adapters, MCP servers, Plugins, Agents, Docker, Graduation. Sections are navigable within the window (e.g. a side nav inside the window body).
4. **SET-FR-04** Plugins section lists installed plugins (via "list installed plugins") with enable/disable toggles and a per-plugin configuration entry; plugin **installation** is not here — it lives in Global settings (`GLS-global-settings.md` GLS-FR-08).
5. **SET-FR-05** Agent adapters section lists installed adapters (via "list agent adapters") and supports per-adapter configuration via "configure adapter (id, config)"; adapter **installation** is not here — it lives in Global settings (`GLS-global-settings.md` GLS-FR-09).
6. **SET-FR-06** MCP servers section lists configured server connections and supports add/remove/test via the corresponding abstract operations; test results render inline in the section.
7. **SET-FR-07** Target repo bindings section lists configured bindings and supports add/edit/remove; in v1 the UI only manages the list and nothing in the application reads it.
8. **SET-FR-08** Each section maintains an independent dirty state; saving applies the section's changes via the appropriate operation and clears that section's dirty state. A section holding a dirty state is a pending change the window writes before it closes, whether or not that section is the one on screen (per `SWN-settings-windows.md` SWN-FR-08, SWN-FR-09), and a save the section reports as failed keeps the window open with that section presented (SWN-FR-11).
9. **SET-FR-09** Closing the Project settings window saves every pending change in every section first and shows no discard-unsaved-changes prompt (per `SWN-settings-windows.md` SWN-FR-08 through SWN-FR-10). A save that fails cancels the close and leaves the window open (SWN-FR-11).
10. **SET-FR-10** The Project section presents the project's line-ending convention as exactly two mutually-exclusive choices — **LF** and **CRLF** — initialised from "load project config" on mount. Selecting one persists it immediately via "save project config" rather than waiting for a section save, so this control sits outside the section's dirty state (SET-FR-08); every artifact written from then on uses the chosen convention (per `../core/PST-project-storage.md` PST-FR-22).
11. **SET-FR-11** This selector and the status bar's line-ending control (`STB-status-bar.md` STB-FR-16) read and write one shared project preference (`../core/PSS-project-settings-storage.md` PSS-FR-17); each reflects a change made from the other without a reload, and a change made here marks the artifact of every open Editor tab dirty exactly as one made from the status bar does (per `STB-status-bar.md` STB-FR-18).

12. **SET-FR-12** The Project section shows which GitHub token this project's authenticated operations use, read from "get project github token binding" on mount, and offers an action that opens the token picker within this window (`GHA-github-authentication.md` GHA-FR-20) to change it. It renders the token's label, account, and masked hint and nothing more of it (per `GHA-github-authentication.md` GHA-FR-03), it states when the project resolves a token implicitly because only one is stored, and it names the Global settings GitHub section as where tokens are added when none is. Confirming a selection in the picker persists it at once via "set project github token binding", so this control sits outside the section's dirty state (SET-FR-08).
13. **SET-FR-13** The Project section shows which agentic integration this project hands work to and how it resolved — inherited from that level's global choice, overridden for this project, or nothing resolved — read from "get project agentic integration" on mount, and offers an action that changes it. The control's content and behaviour are specified by `AII-ai-integrations.md` (AII-FR-31 through AII-FR-35); the integrations themselves are configured and verified in Global settings (`GLS-global-settings.md` GLS-FR-16), never here. Choosing an integration or returning the project to the global choice persists at once via "set project agentic integration", so this control sits outside the section's dirty state (SET-FR-08).
14. **SET-FR-14** The Project section shows which AI API integration this project calls and how it resolved, read from "get project ai api integration" on mount, and offers an action that changes it, persisting at once via "set project ai api integration" and likewise sitting outside the section's dirty state. It is a second, independent control beside the agentic one (SET-FR-13), governed by the same rules in `AII-ai-integrations.md` (AII-FR-31 through AII-FR-35), because the two levels are chosen independently: overriding one leaves the other's resolution untouched.

15. **SET-FR-15** The Agents section lists the conversational agents this project may talk to, read from "list project agents" when the section mounts, and is where one is enrolled into the project and removed from it through "enrol project agent" and "remove project agent". The section's content and behaviour are specified by `AGT-agents.md` (AGT-FR-22, AGT-FR-23); the personas themselves are described in Global settings (`GLS-global-settings.md` GLS-FR-24), never here, so this section decides membership and nothing about how an agent behaves. Both actions persist at once, so the section sits outside the window's dirty state (SET-FR-08). It is a section of its own rather than a control in the Project section because a project's roster is a list that grows, where the three pointers of SET-FR-12 through SET-FR-14 each name exactly one thing.

16. **SET-FR-16** The **Draft template** section holds exactly one thing: the project's optional Markdown **draft template**, the starting content every draft created in this project is born holding (per `../core/DRS-draft-storage.md` DRS-FR-39). It presents that text in the **same rich Markdown editing surface an Editor tab sets a Markdown file on** — the two modes of `EDT-editor.md` EDT-FR-17, the frontmatter region of EDT-FR-18, the formatting band of `EFR-editor-find-replace.md` EFR-FR-ABHF, the page framing of EDT-FR-63, and the round-trip fidelity of EDT-FR-66 through EDT-FR-69 — reused whole rather than reimplemented, with its formatting band and mode toggle placed within the section because the window's chrome belongs to the window rather than to one of its sections. There is no second editor implementation and no plain text area anywhere in this section. Its editing behaviour, its serialisation, its line-ending handling, its focus behaviour, and its accessibility behaviour are therefore the surface's own and are unchanged by being used here. The section carries nothing else — no name, no path, no artifact type, no destination, and no per-draft setting — because a template is one document and everything else about a draft is decided in the draft.
17. **SET-FR-17** The template **writes itself**. An edit schedules a write through "save project config" a short rest after the last keystroke, so a burst of typing is one write rather than one per character, and a further edit before the rest elapses restarts it so the write carries the settled text. The write additionally happens immediately when the user navigates away from the section within the window, and a write already in flight when the window closes is one of the pending changes the close waits for rather than starts again (per `SWN-settings-windows.md` SWN-FR-09). The section therefore carries **no Save control**, takes no part in the per-section dirty state of SET-FR-08, and raises no discard-unsaved-changes confirmation when the window closes (SET-FR-09) — there is nothing to discard, because what the author typed is already on its way to disk. The write is a whole-store write that carries every other project-public section through unchanged (per `../core/PSS-project-settings-storage.md` PSS-FR-17).
18. **SET-FR-18** The section reports where the author's text stands, in three states and no others: **saving** while a write is in flight, **saved** once it has landed, and a **save failure** naming what went wrong. A failed write **keeps the author's content in the editor exactly as they left it** — nothing is reverted, reloaded, or replaced by what is on disk — and offers a retry, so a transient failure costs the author a click rather than the text they wrote. A failed **load** is surfaced in the section on the same terms as any other project-config read error (per `../core/PSS-project-settings-storage.md` PSS-FR-10): the section states that the project's configuration could not be read and edits nothing, and it never presents an empty editor as though the project configured no template, so a damaged store is never mistaken for a cleared one and is never overwritten by what the section happened to be showing.
19. **SET-FR-19** **Deleting all of the template's content clears the template.** When the editor is left holding no text, the automatic write of SET-FR-17 persists the **unset** state rather than a configured empty template (per `../core/PSS-project-settings-storage.md` PSS-FR-21), so the project returns to the behaviour it had before a template was ever written and drafts created afterwards open on an empty prompt (per `../core/DRS-draft-storage.md` DRS-FR-06). Unset and configured are distinct states in this section as they are in the store: a section showing an empty editor for a project with no template and one showing an empty editor because the author just deleted the text both describe the same unset project, and neither is a configured empty template.
20. **SET-FR-20** The section never shows a template that is not the active worktree's own. It reads the template through "load project config" when it mounts. Neither the active project nor the project's active worktree can change while the window is open, the main window being blocked behind it (per `SWN-settings-windows.md` SWN-FR-02), so the window opened after such a change mounts against the new worktree and reads there. While a read is outstanding the section renders a loading state rather than any previously-read template, and the editing surface accepts no edit until the read has landed, so the author can neither see nor overwrite one project's template while another project's is loading.

21. **SET-FR-21** The **Docker** section settles which container image each agentic CLI vendor's work runs in for this project. It presents one tab per vendor — Claude Code, Codex, and OpenCode, in that order, Claude Code selected when the section opens — and each tab renders the same controls in the same order: an **image name** field, an optional **tag** field, an optional project-relative **Dockerfile** field, a **Build** control, and the region the build's progress and its result are rendered in. The section reads every tab from "load project docker images" when it mounts, so a tab renders the committed project's own entry rather than anything this window holds.
22. **SET-FR-22** A tab's Dockerfile field is filled either by typing a project-relative path or by **selecting a Dockerfile from the current project** through a picker rooted at the project, so the author chooses a file that exists rather than remembering where it is. A path that leaves the project, an absolute one, and one that does not name a file are refused by the backend's validation (per `../core/PSS-project-settings-storage.md` PSS-FR-24) and render inline in the tab, naming which of the three the path was.
23. **SET-FR-23** A tab states **what its configuration is worth**, in the four states "load project docker images" reports (per `../core/PSS-project-settings-storage.md` PSS-FR-25): nothing configured, configured in the committed project, configured with a Dockerfile and an image reference that are valid for this project, and unavailable for graduation. It distinguishes an **absent optional Dockerfile** from a **configured Dockerfile that is invalid**: the first is a tab that simply configures no build, stated as such and not as a problem, and the second names the problem and offers the field to correct it. The OpenCode tab states that OpenCode cannot be executed yet rather than that its configuration is wrong, because its entry is stored and valid and it is execution support that is missing.
24. **SET-FR-24** A tab's image name is **required for every vendor the project selects for graduation**, and the section marks the tab of the vendor the project resolves to — read from "get project agentic integration", the same resolution the Project section names (SET-FR-13) — as the one graduation needs. It states, on a tab whose image name is empty, that graduation cannot start until it is filled. A Dockerfile is optional everywhere; where one **is** configured the image name is required on that tab as well, because it is the build target and the reference graduation runs. Editing a field persists at once through "save project vendor image", so the section holds no dirty state and takes no part in the per-section save model of SET-FR-08. The section additionally states, once and **at the top of the section**, that the Docker backend itself is configured and verified in Global settings (`GLS-global-settings.md` GLS-FR-29), never here; it reads whether it is verified through "load docker backend" and states that too, because a Build control this section cannot enable is most often disabled by it. That statement is a **control that opens the Docker section of Global settings** rather than only a name, so the author reaches the place they are sent to (per `SWN-settings-windows.md` SWN-FR-13).
25. **SET-FR-25** **Build** builds that tab's Dockerfile into that tab's image with **one click**, invoking "build project vendor image" for the vendor. The build is **local**: it produces an image in this machine's own image store and pushes it to no registry (per `../core/PSS-project-settings-storage.md` PSS-FR-26). It is enabled only while the tab configures both a Dockerfile and an image name and the Docker backend is verified, and it states which of the three is missing while it is disabled. **While a build is running, every vendor tab's Build control in this window is disabled**, whichever tab started it, because a project builds one image at a time (per `../core/PSS-project-settings-storage.md` PSS-FR-29).
26. **SET-FR-26** The tab that started a build renders **its progress and its outcome inline**, from the backend's own events: an indeterminate indication until a total is reported and a determinate one afterwards, the phase and the message each update carries — which **accumulate in a scrolling output region of bounded height**, oldest lines dropped first, rather than each update replacing the last, because a build is read as the sequence of steps it ran and the window it is read in cannot be resized (per `SWN-settings-windows.md` SWN-FR-03) — and then the single terminal result — succeeded naming the image reference that was built, failed naming what went wrong, or cancelled. The author reads the build where they configured it rather than in another surface, and a build that is running when the section is left and returned to is still rendered against its own tab.
27. **SET-FR-27** A **failed build keeps the tab's configuration exactly as it was** — no field is cleared, reverted, or rewritten — renders the final error inline, and offers **Retry**, which is one more "build project vendor image" for that vendor. Nothing retries on its own: a build happens because the author activated Build or Retry, and a failure neither disables Retry nor prevents a later build once the project is free (per `../core/PSS-project-settings-storage.md` PSS-FR-29).
28. **SET-FR-TTTB** The **GitHub Project settings** section lists the GitHub Projects of `"list github projects"` in one selector, each by title and owner, with a **None** choice. The selected Project is read from `"get github polling state"` when the section mounts.
29. **SET-FR-NLIX** The section offers the polling interval as **Off**, **1**, **5**, **15**, **30**, and **60 minutes**. **Off** is the unset interval, which disables the launch and timed polls and keeps the manual **Refresh** of `GIT-git.md` GIT-FR-EZFL.
30. **SET-FR-VLQJ** A change of the Project or the interval persists at once through `"set github polling settings (project node id, interval minutes)"`, outside the section dirty state of SET-FR-08. A refused write keeps the previous values in the controls and renders the error inline.
31. **SET-FR-GKTA** The section states the configuration in words: no Project selected, valid with the Project title, or an error that names what to fix — a missing or unreadable Project, or a `Status` field without exactly `Ready` and `In Progress`. It also states that polling is disabled while the error stands.
32. **SET-FR-GXJU** A Project list that cannot be read renders the error inline with a **Retry** action and keeps the stored selection. The section re-reads its state on `"github polling changed"`, so a configuration error found by a poll appears without reopening the window.
33. **SET-FR-BLQN** The GitHub Project settings section holds the polling controls of SET-FR-TTTB through SET-FR-GXJU and a **Publication** group beneath them. It has no second GitHub Project selector: the Project of the polling controls is the only Project the section names.
34. **SET-FR-DWRC** The Publication group offers a **Parent issue Types** filter that accepts one or more Types, with `Feature` selected when none is stored. The author cannot clear the last selected Type. The filter decides which open issues the publication chooser offers as parents (per `NAW-new-artifact.md` NAW-FR-YLKD).
35. **SET-FR-HPKV** The Publication group offers a **Sub-issue Type** selector, with `Task` selected when none is stored. The selected Type is the Type of every sub-issue that Publish to GitHub creates, and the publication chooser offers no override (per `NAW-new-artifact.md` NAW-FR-JXDN).
36. **SET-FR-ZHCT** The Publication group offers the **Sub-issue milestone** policy as exactly three mutually exclusive choices: **Inherit parent milestone**, **No milestone**, and **Author-selectable milestone**. **Inherit parent milestone** is selected when none is stored.
37. **SET-FR-MQUE** A change in the Publication group persists at once through `"set github publication settings (parent issue types, sub issue type, sub issue milestone policy)"`, outside the section dirty state of SET-FR-08. A refused write keeps the previous values in the controls and renders the error inline.
38. **SET-FR-XFNA** The section reads the stored values through `"get github publication settings"` and the available Types through `"list github issue types"` when it mounts. While the Type read is outstanding, the Type controls render a loading state and keep the stored values.
39. **SET-FR-LJYT** A stored Type that the Type list does not hold renders as selected and marked **unavailable**. The section does not replace it, clear it, or write it again. A Type list that is empty or cannot be read renders a notice with the displayable error and a **Retry** action, keeps every stored value, and writes nothing.
40. **SET-FR-DHFS** The **Graduation** section holds an **Execution time limit** row. It reads the stored execution timeout through "load project config" and shows it in minutes. An unset value shows the two-hour default as a placeholder. A helper line says that the limit bounds each graduation turn and each conversation turn whose provider stores no turn timeout.
41. **SET-FR-YMRV** An entry commits on Enter or on blur and persists at once through "save project config", outside the section dirty state of SET-FR-08. An empty entry stores the unset value (per `../core/PSS-project-settings-storage.md` PSS-FR-ZLCF). An entry that is not a whole number from 1 to 360 is refused inline, and the stored value stays.
42. **SET-FR-QKKQ** The **Graduation** section also holds a **Concurrent graduation runs** drop-down for the project-wide limit of `../core/GRD-graduation.md` GRD-FR-KKKN. It offers **1**, **2**, **4**, **8**, and **Unlimited**, in that order. It states in words that the limit counts stream runs and direct runs together and that each stream or worktree works one run at a time.
43. **SET-FR-ZNXA** The control shows the limit read through "load project config" (per `../core/PSS-project-settings-storage.md` PSS-FR-JRWC), and **1** where the store holds none. A stored positive integer that the list does not hold, such as **3**, is offered as one more option in numeric order and is selected. It stays selected until the author chooses another value, and nothing writes it again.
44. **SET-FR-HQKK** A change of the selection marks the Graduation section as a pending change in the dirty state of SET-FR-08. The change is not written at once. "save project config" writes it with the other pending changes of the window, and the close of the window writes it as SET-FR-09 requires, even while another section is on screen.
45. **SET-FR-TFNG** While the read is outstanding, the control renders a loading state and accepts no choice. While a write is in flight, the section states that it saves. A failed write keeps the selection, leaves the section pending, renders the error, and offers **Retry**. A failed read states that the limit could not be read and offers no choice.
46. **SET-FR-IHQE** The selection survives a change to another section within the window. The Graduation section stays pending until a write lands. A write names the limit alone, so it carries every other project-public section through unchanged (per `../core/PSS-project-settings-storage.md` PSS-FR-ZVSD).

## Non-functional requirements
- Project settings can be opened, navigated, and forms rendered before any plugin or adapter is installed (empty states are first-class).
- The Project section renders its GitHub token display without network access; it describes the binding rather than verifying the token.
- The Project section renders both AI integration controls without network access and without running any binary; each names what the project resolves to rather than re-verifying it, and neither renders an endpoint, a key, a masked hint, or a binary path.
- The Agents section renders without network access and reaches no model: it names who the project may talk to and never talks to any of them.
- The Draft template section renders without network access. It reads and writes one value in the project's own configuration and reaches no draft: opening it, editing in it, and saving from it change nothing in any draft that already exists.
- The template is ordinary Markdown in `.synthesis/project.toml` and carries no Synthesis-specific syntax, so a project's template is readable and editable outside the application and is reviewed in a pull request like any other committed configuration.
- The Docker section renders without reaching a Docker daemon and without running any executable: it reads the project's committed entries and states what they are worth. Building is the one action in it that reaches a runtime.
- A build's progress is rendered from the events the backend streams, so a long build shows what it is doing while the window stays responsive and every other section stays usable.
- A section's heading is followed by one sentence saying what that section settles, written for the section rather than assembled from its own name. A sentence built out of the label reads back as a tautology on a section called Project, and flattens an acronym on one called MCP servers.
