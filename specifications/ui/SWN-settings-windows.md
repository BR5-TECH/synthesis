# Settings windows

**Spec code:** `SWN`

## Intent
Configuration is not authoring, and it does not look like it. Global settings (`GLS-global-settings.md`) and Project settings (`SET-project-settings.md`) are each a **native child window** of the application rather than a tab in the main viewport, so the surfaces that change how the application behaves are visually separate from the workspace the author works in. Each window is application-modal to the window that opened it, opens at one fixed size in the centre of the active display, and is the only settings window on screen: a request for the other one closes this one first. A settings window writes every change the author made before it goes, so leaving it never asks them to choose between their edits and their exit. This spec owns the two windows as windows — how they open, where they open, what they block, how they close, and where the application menu offers them. What each window presents inside its frame belongs to its own spec.

## User stories
- As an author, I want settings to open in a window of their own so that configuration never reads as one more document in my workspace.
- As an author, I want a settings window to keep what I typed when I close it, so that a change I made in a section I moved away from is not lost and I am not asked about it.
- As an author, I want Global settings before I have opened a project, so that I can set up the machine first.

- Layout notes: the child window carries the platform's own title bar and frame; nothing of the main window's chrome — no tab strip, no activity bar, no status bar — is drawn inside it. It is centred on the display its parent occupies (SWN-FR-04) and holds a fixed outer size of 800 × 600 px at every opening (SWN-FR-03). The parent window stays visible behind it and accepts no interaction until it closes (SWN-FR-02). Exactly one settings window is on screen at a time (SWN-FR-05), so the two frames above never sit side by side.

## UI contract boundary
- **Owned by the UI**: the two child windows and their creation; the parent each is modal to and the blocking of that parent; the fixed outer size and the refusal to resize; the centring on each opening and the absence of any persisted window position; the one-settings-window rule, the focus of a window already open, and the ordered save-close-open of a switch; the save-before-close sweep, what counts as a pending change, the awaiting of a write already in flight, and the cancelling of a close or a switch when a save fails; the inertness of the close and switch actions while a sweep runs; the application-menu entries, their labels, their platform placement, their order, and the absence of the Project settings entry while no project is open; and each window's title.
- **Delegated to backend (abstract)**: none. The windows introduce no operation of their own: every read and write a settings section makes is one `GLS-global-settings.md` and `SET-project-settings.md` already delegate, and the menu entries introduce no backend command, exactly as the File and Edit menus do not (per `SNV-shell-navigation.md` SNV-FR-23).

## Functional requirements
1. **SWN-FR-01** Global settings and Project settings are each a **native child window** of the application. Neither is a tab of the main viewport (per `TAB-tabs.md` TAB-FR-03), neither is a surface drawn inside another window, and neither is one of the main window's mutually-exclusive floating overlays (per `SNV-shell-navigation.md` SNV-FR-56): a settings window neither closes an overlay by opening nor is closed by one opening.
2. **SWN-FR-02** A settings window is **application-modal** to its parent window: while it is open the parent renders normally but accepts no pointer, keyboard, or menu interaction, and it regains interaction the moment the settings window closes. The parent is the **main window** while a project is open, and the **Project picker** where Global settings is opened while no project is open (per `PPK-project-picker.md` PPK-FR-15). Because the parent is blocked, no project close, project switch, or active-worktree change can start while a settings window is open (per `OVW-overview.md` OVW-FR-02, OVW-FR-11, OVW-FR-12).
3. **SWN-FR-03** A settings window is presented at a fixed outer size of **800 × 600 px** and is not user-resizable: it offers no drag-to-resize, no maximize, and no OS full-screen, and it opens at that same size every time whichever window it is.
4. **SWN-FR-04** A settings window is **centred on the active display** — the display its parent window occupies — each time it opens, so it appears over the window it blocks. No position of a settings window is persisted, and a window moved by the author before it closed opens centred again rather than where it was left.
5. **SWN-FR-05** At most **one** settings window exists at a time. Opening either settings window closes any settings window that is currently open before the requested one opens (SWN-FR-07), so Global settings and Project settings are never both on screen.
6. **SWN-FR-06** A request for the settings window that is **already open** focuses that window and opens no second instance of it. The window is not reloaded and its sections keep their state; a request naming a section (SWN-FR-13) presents that section in the window it focuses.
7. **SWN-FR-07** A request for the **other** settings window runs in one fixed order: the open window saves every pending change (SWN-FR-08, SWN-FR-09), then closes, then the requested window opens. The requested window opens only after the open one has closed, so the switch is never two windows in flight at once.
8. **SWN-FR-08** Before a settings window closes — however the close was requested, and whether the close is the author's own or the first half of a switch (SWN-FR-07) — it saves **every pending change in every one of its sections**, not only the section on screen. A section holding edits the author never scrolled back to is saved on exactly the terms the visible one is.
9. **SWN-FR-09** A **pending change** is either a section holding a dirty state (per `GLS-global-settings.md` GLS-FR-10 and `SET-project-settings.md` SET-FR-08) or a settings write already **in flight** — a write a section has scheduled or issued and that has not yet landed, such as the Draft template's own write (per `SET-project-settings.md` SET-FR-17). A write already in flight is **awaited** rather than started again: the sweep issues no second write for it, and the window closes once it lands.
10. **SWN-FR-10** No discard-unsaved-changes prompt exists for a settings window. Closing one never asks the author to choose between keeping their edits and leaving, because the close writes them (SWN-FR-08); no section, and no state of any section, raises such a prompt.
11. **SWN-FR-11** A pending save that **fails** cancels the transition. The settings window stays open, the requested close or switch does not happen, no other settings window opens, and the failed section keeps the author's edits exactly as they were — nothing is reverted, reloaded, or replaced — and presents its own error and its own retry (per `GLS-global-settings.md` GLS-FR-10 and `SET-project-settings.md` SET-FR-08, SET-FR-18). The window presents that section, so the error and the retry are visible rather than behind a section the author is not on. A section that saved successfully in the same sweep stays saved and is not written a second time when the close is requested again.
12. **SWN-FR-12** While a save sweep is running, the close and the settings-switch actions are **inert**: a second close request, a request for the same settings window, and a request for the other settings window each start no further save, duplicate no write already in flight, and open no second settings window. The sweep either completes and the transition proceeds (SWN-FR-07, SWN-FR-08) or fails and the window stays (SWN-FR-11).
13. **SWN-FR-13** A settings window is opened from three kinds of place, all of them governed by SWN-FR-05 through SWN-FR-07: the **status bar's** Global settings and Project settings buttons while a project is open (per `STB-status-bar.md` STB-FR-04); the **application menu's** two settings entries (SWN-FR-14); and any surface that routes the author to a named section of either window — the agents roster (per `AGT-agents.md` AGT-FR-06, AGT-FR-07), a failure offering a route to the Global settings GitHub section (per `GIT-git.md` GIT-FR-10), a graduation run stopped at its time limit (per `GRU-graduation-runs.md` GRU-FR-QLRQ), and an activated notification carrying a settings address (per `NTF-notifications.md` NTF-FR-17) among them — which opens or focuses that window on the section it names.
14. **SWN-FR-14** The application menu carries exactly two settings entries, labelled **Global settings** and **Project settings**, with Global settings first. On **macOS** both sit in the **app-name menu**; on **every other platform** both sit in the **File menu**, between Save All and Close Project (per `SNV-shell-navigation.md` SNV-FR-23). Activating an entry opens its window, or focuses it when it is already open (SWN-FR-06), or switches to it when the other one is open (SWN-FR-07).
15. **SWN-FR-15** The **Global settings** entry is available at all times — while a project is open and while the Project picker is the only window (per `PPK-project-picker.md` PPK-FR-15) — because everything Global settings holds belongs to the user and the machine rather than to a project (per `GLS-global-settings.md` GLS-FR-11).
16. **SWN-FR-16** The **Project settings** entry is available **only while a project is open**. While no project is open the entry is **absent** from the menu rather than present and greyed-out, so the menu offers nothing that names a project that does not exist, and no route anywhere in the application opens the Project settings window in that state.
17. **SWN-FR-17** Each settings window carries a title naming which settings it holds — **Global settings** and **Project settings** — so the two are told apart in the platform's own window list as well as on screen.
18. **SWN-FR-18** A settings window occupies no place in the main window's tab strip: no settings tab exists, no tab is created, focused, or closed by opening or closing one, and the never-empty invariant of the strip is untouched by either (per `TAB-tabs.md` TAB-FR-15). A settings window takes no needs-attention indication, an indication marking an open tab alone (per `NTF-notifications.md` NTF-FR-27, NTF-FR-28).
19. **SWN-FR-19** Quitting the application writes the pending changes of an open settings window first, on the terms of SWN-FR-08 and SWN-FR-09, and a write that cannot proceed safely cancels the quit and leaves the window open with its failed section presented (SWN-FR-11), exactly as an artifact that cannot be written does (per `SNV-shell-navigation.md` SNV-FR-26).

## Non-functional requirements
- Both windows render, navigate their sections, and save without network access; a section that reaches the network for its own content says so in its own spec.
- The modality of SWN-FR-02 is the window's own: it is enforced by the platform's window relationship rather than by a scrim, a focus trap, or a listener drawn in the parent, so a parent that is repainted, resized, or moved is blocked throughout.
- A settings window opens at its fixed size, centred, before it is interactive, so it is never seen at another size or another position first.
- The save sweep of SWN-FR-08 runs on the sections the window already holds and starts no read of its own, so a close is not delayed by a section reloading what it is about to write.
- The window's frame renders in the current theme and the three typographic roles exactly as the main window does (per `OVW-overview.md` OVW-FR-13, OVW-FR-14); a settings window is a separate window rather than a separately-styled application.
